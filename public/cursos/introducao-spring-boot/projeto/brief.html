Leque de Vagas — a API 💼

Vagas de tecnologia para quem está migrando de carreira. Vocês não vão construir a tela — vão construir o outro lado: o programa que guarda as vagas, as empresas e as candidaturas, e as entrega para quem pedir. O projeto nasce na aula 02 como três classes e termina como uma API autenticada, documentada e rodando em contêiner.

🔌

A tela já existe

O Leque de Vagas é também o projeto da disciplina de Introdução ao Next.js, onde a turma constrói a interface. Hoje aquele front usa dados de mentira, escritos à mão num arquivo. A API de vocês é o que vai substituir esse arquivo.

Vocês podem consultar o front como referência de quais dados ele espera: github.com/Um-Leque-de-Tecnologia/leque-de-vagas. Não é obrigatório — mas é a diferença entre projetar uma API no vácuo e projetar uma API que alguém vai usar.

As quatro frentes

A equipe tem quatro pessoas, e o projeto tem quatro frentes. Cada integrante assume uma e a carrega o semestre inteiro — em toda aula, o desafio tem uma parte para cada frente.

Frente 1

Vaga

O recurso principal. Cadastro, listagem, detalhe, e a evolução dele: DTO, validação, entidade JPA, paginação. É a frente que puxa as outras — quem a assume entrega o contrato primeiro.

Frente 2

Empresa

Quem publica as vagas. Perfil público, as vagas de uma empresa, e mais pra frente o relacionamento Empresa → Vagas no banco.

Frente 3

Pessoa e candidatura

Quem se candidata, e o ato de se candidatar. É a frente que ganha autenticação e autorização por perfil quando chegarmos na aula 10.

Frente 4

Busca e números

Filtros, ordenação, e as estatísticas do catálogo. É a frente que mais exercita consulta — e a que vira @Query e projeção na aula 07.

🤝

Como quatro pessoas trabalham sem se atropelar

As frentes 3 e 4 precisam dos dados que a frente 1 guarda. Se cada pessoa esperar a outra terminar, a equipe entrega uma frente por semana em vez de quatro.

A saída é combinar o contrato antes de codar. Na primeira meia hora, a equipe decide junto: quais campos a Vaga tem, e qual é a assinatura dos métodos que as outras frentes vão chamar. Escrito isso, cada pessoa programa contra a assinatura — mesmo antes de ela existir.

Não é burocracia de sala de aula: é literalmente como um time de verdade trabalha, e é por isso que a primeira coisa que se define num projeto novo é o contrato.

O modelo — o mínimo que a API precisa

Este é o piso, não o teto. Cada frente vai acrescentar campo próprio ao longo do semestre — o que não pode é faltar algum destes.

As quatro entregas
Aula 02 · 18/08

O esqueleto em camadas

A API responde com dados fixos em memória, mas já separada em controller, service e repository. Sem banco, sem validação — só o desenho certo desde o primeiro dia.

Aula 12 · 03/11

Checkpoint 1 — segura e documentada

Banco de verdade, relacionamentos, validação, tratamento de erro padronizado, autenticação com JWT e autorização por perfil. Swagger UI gerado do código, com todos os endpoints navegáveis.

Aula 15 · 24/11

Checkpoint 2 — no ar

Testes automatizados, configuração por ambiente, observabilidade, e a aplicação rodando em contêiner numa nuvem gratuita. README, variáveis de ambiente e coleção de requisições prontos para quem for usar.

Aulas 16 e 17

Apresentação

Vinte minutos por equipe. Cada pessoa apresenta a sua frente: o que construiu, que decisão tomou e por quê. Depois, uma demonstração da API inteira funcionando junto.

Requisitos técnicos obrigatórios
  • Java 21 e Spring Boot 4.1 — a versão estável mais alta do Initializr.
  • Maven, com o projeto num repositório no GitHub, um por equipe.
  • As três camadas separadas desde a aula 02, sempre. Nenhum controller com regra dentro.
  • Injeção por construtor, campo final. Nenhum new entre as classes de vocês.
  • Um commit por pessoa, por entrega, no mínimo. O histórico do Git é a evidência de quem fez o quê — e ele conta na nota individual.
  • README na raiz, com: como rodar, as quatro frentes e quem assumiu cada uma, e as decisões da equipe.
Extras, pra quem quiser ir além ✨
  • Uma coleção de requisições (.http ou Insomnia) versionada no repositório.
  • GET /vagas/{id}/parecidas — vagas da mesma área, fora ela mesma.
  • Filtro por faixa de data de publicação.
  • Um endpoint de saúde que diga quantos registros existem de cada coisa.
O que NÃO pode 🚫
  • Trocar de tema. O projeto é o mesmo para a turma inteira, e é de propósito: assim o semestre é gasto aprendendo Spring, não decidindo o que construir.
  • Uma pessoa fazer duas frentes e outra nenhuma. O Git mostra, e a nota individual cai para quem não aparecer.
  • Regra de negócio no controller. Vale desde a aula 02 até a apresentação.
  • Construir tela. Não é esta disciplina. Se quiserem ver a API funcionando numa interface, usem o Swagger da aula 12.

A nota tem parte individual. Cada pessoa é avaliada pela sua frente: o código dela, os commits dela e a explicação dela. Equipe boa com um integrante ausente não carrega o integrante ausente.
Como começar hoje
  1. Formem a equipe — quatro pessoas.
  2. Escolham a frente de cada uma. Anotem no README: é o contrato de quem faz o quê.
  3. Combinem os campos da Vaga antes de qualquer pessoa abrir a IDE.
  4. Criem o repositório no GitHub, com todo mundo como colaborador.
  5. Façam o desafio da aula 02 — é a primeira evolução do projeto, e já vem dividido em quatro partes.
