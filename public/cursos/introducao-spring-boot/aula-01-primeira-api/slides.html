parte 2 · vocabulário
🧱

Cinco palavras antes de qualquer código

dependência · acoplamento · framework · contêiner · anotação

palavra 1 · dependência

Dependência é "eu preciso de outro"

Quando uma classe sua precisa de outra classe pra funcionar, essa outra classe é uma dependência dela.

// A classe Pedido precisa da classe Impressora pra funcionar. // Logo: Impressora é uma DEPENDÊNCIA de Pedido. public class Pedido { private Impressora impressora; // <-- a dependência public void finalizar() { impressora.imprimirCupom(); // sem ela, não dá pra finalizar } }

Guarde: dependência = uma classe de que a sua classe depende. Só isso. Nada mais misterioso do que isso.

palavra 1 · atenção ao duplo sentido

A mesma palavra, dois usos

Dependência entre classes

A classe Pedido depende da classe Impressora. É o sentido do slide anterior — é sobre o seu código.

Dependência do projeto

O seu projeto inteiro depende de uma biblioteca de outra pessoa — por exemplo, o próprio Spring. Você declara isso num arquivo e alguém baixa pra você.

São coisas diferentes com o mesmo nome. Quando eu disser "adiciona a dependência no pom.xml", é o segundo sentido: baixar uma biblioteca. Quando eu disser "injetar a dependência", é o primeiro: entregar um objeto pra outro objeto.

Isso confunde 100% das turmas. Por isso está num slide separado.

palavra 2 · acoplamento

Acoplamento é o quanto uma coisa está grudada na outra

Acoplamento forte 👎

Trocar uma peça obriga a mexer na outra. É como um abajur com a lâmpada soldada: queimou a lâmpada, joga o abajur fora.

Acoplamento fraco 👍

As peças se encaixam por um padrão. Lâmpada de rosca: queimou, troca só a lâmpada. O abajur nem sabe qual marca você comprou.

No código, a "rosca" é a interface — o contrato que diz o que a peça faz, sem dizer como.

O curso inteiro empurra o seu código do lado esquerdo pro lado direito. Guarde a imagem da lâmpada: ela volta várias vezes hoje.

palavra 2 · a analogia virando código

O abajur com a lâmpada soldada

LampadaLed.java
public class LampadaLed { public void acender() { System.out.println("Luz branca!"); } }
Abajur.java
public class Abajur { // a solda: o abajur FABRICA a lâmpada dele private LampadaLed lampada = new LampadaLed(); public void ligar() { lampada.acender(); } }

O que está errado aqui

O Abajur sabe demais. Ele não deveria nem conhecer o nome LampadaLed — o trabalho dele é ligar uma lâmpada, qualquer uma.

O teste da troca

Chegou a LampadaColorida. Pra usar, você precisa abrir e editar o Abajur.java — um arquivo que não tem nada a ver com o tipo de lâmpada.

A regra por trás

Quem escreve new fica casado com o tipo que criou. Todo new é uma solda.

Repare que o código funciona. Acoplamento forte não dá erro de compilação nem exceção — ele cobra a conta depois, na primeira vez que algo precisa mudar.

palavra 2 · o mesmo código, com rosca

Trocando a solda pela interface

Lampada.java — a rosca
public interface Lampada { void acender(); // o que faz, não como }
as duas lâmpadas
public class LampadaLed implements Lampada { public void acender() { ... "Luz branca!" } } public class LampadaColorida implements Lampada { public void acender() { ... "Luz roxa!" } }
Abajur.java
public class Abajur { // conhece a ROSCA, não a marca da lâmpada private final Lampada lampada; // a lâmpada chega de fora, já pronta public Abajur(Lampada lampada) { this.lampada = lampada; } public void ligar() { lampada.acender(); } }
quem monta escolhe
new Abajur(new LampadaLed()).ligar(); new Abajur(new LampadaColorida()).ligar(); // Abajur.java não foi aberto nenhuma vez.

Guarde esse construtor recebendo a Lampada: em alguns slides ele vai ganhar nome próprio — injeção de dependência. Você acabou de escrever, sem saber, o padrão que sustenta o Spring inteiro.

palavra 2 · o placar

O que uma linha de diferença mudou

PerguntaLâmpada soldadaLâmpada de rosca
O Abajur sabe o nome da lâmpada concreta?sim, LampadaLednão, só Lampada
Pra trocar de lâmpada preciso editar Abajur.java?simnão
Consigo testar o abajur com uma lâmpada de mentira?não, o new está trancadosim, passo no construtor
O campo pode ser final?na prática não ajuda em nadasim, e o compilador garante
Quem decide qual lâmpada usar?o próprio abajurquem monta, de fora

A última linha é a mais importante do bloco: a decisão saiu de dentro da classe. Essa mudança de lugar tem nome, e é o assunto da parte 4 da aula.

Aqui ainda somos nós escrevendo new Abajur(new LampadaLed()) na mão. O que o Spring faz é assumir essa linha — e é só isso, no fundo.

palavra 3 · framework

Biblioteca × framework: quem chama quem

Biblioteca

Você chama ela. É uma caixa de ferramentas: você decide quando pegar o martelo.

Math.sqrt(9) — você chamou quando quis.

Framework

Ele chama você. É uma casa já construída: você preenche os cômodos, mas a planta e a hora de cada coisa são dele.

Você escreve um método e o Spring decide quando executar.

Isso tem até nome de piada em inglês: "Hollywood Principle" — don't call us, we'll call you. Não nos ligue, nós ligamos pra você. Segure essa frase: ela é literalmente a definição de inversão de controle.

palavra 4 · contêiner

Contêiner é a caixa que guarda os objetos prontos

Um programa Java comum cria objetos com new espalhados pelo código. No Spring existe uma caixa central que:

  • cria os objetos quando a aplicação sobe;
  • guarda cada um deles;
  • entrega o objeto certo pra quem pedir;
  • destrói tudo quando a aplicação para.

Essa caixa tem nome próprio em Java: ApplicationContext.

Analogia: um almoxarifado. Você não fabrica sua própria caneta — você pede no balcão e recebe uma que já existe.

palavra 5 · anotação

Anotação é uma etiqueta colada no código

Toda palavra que começa com @ é uma anotação. Ela não executa nada sozinha: é um bilhete grudado na classe, no método ou no parâmetro, esperando que alguém leia.

@RestController // bilhete: "sou uma classe que responde requisições web" public class OlaController { }

Quem escreve

você, em cima da classe ou do método.

Quem lê

o Spring, quando a aplicação sobe.

O que muda

o Spring passa a tratar aquela classe de um jeito especial.

Você já viu isso em OO: @Override é uma anotação lida pelo compilador. É exatamente a mesma ideia, só que agora quem lê é o Spring.

parte 3 · o problema
🩹

Por que alguém inventou o Spring?

Antes de aprender a solução, a gente precisa sentir a dor. Vamos escrever um código em Java puro que funciona — e depois quebrar ele.

// cenário

Um sistema de pedidos

Três classes bem simples, do jeito que você faria hoje com o que já sabe:

Notificador

envia o aviso pro cliente. Hoje, por e-mail.

PedidoService

a regra: registra o pedido e avisa o cliente.

Main

a classe que dispara tudo.

Guarde a seta: PedidoService depende de Notificador. Todo o resto da aula gira em torno de como essa seta é construída.

// versão 1 — java puro

O código que funciona

EmailNotificador.java
public class EmailNotificador { public void enviar(String msg) { System.out.println("E-mail: " + msg); } }
PedidoService.java
public class PedidoService { private EmailNotificador notificador = new EmailNotificador(); public void criar(String item) { System.out.println("Pedido criado: " + item); notificador.enviar("Seu pedido de " + item + " foi criado!"); } }

Funciona. Roda. Entrega o que promete. E ainda assim tem um problema sério escondido na linha destacada.

// zoom

Três decisões numa linha só

private EmailNotificador notificador = new EmailNotificador();

Qual implementação usar

o PedidoService decidiu sozinho que é e-mail. Não é SMS, não é push. É e-mail, e ponto.

Quando criar o objeto

na hora em que o PedidoService nascer. Nem antes, nem depois.

Como configurar

construtor vazio. Se amanhã o notificador precisar de servidor e senha, é aqui dentro que vai ter que aparecer.

Pergunta que vale a aula: o trabalho do PedidoService é registrar pedidos. Por que ele está decidindo essas três coisas sobre notificação?

dor 1 · mudança de requisito

"Agora é por SMS"

O cliente pediu SMS em vez de e-mail. Você cria a classe SmsNotificador... e agora precisa abrir e editar o PedidoService, que não tem nada a ver com o assunto.

// abrir PedidoService.java e trocar na mão: private EmailNotificador notificador = new EmailNotificador(); private SmsNotificador notificador = new SmsNotificador(); // e se 12 classes usam o notificador? 12 arquivos abertos.

Uma mudança de uma decisão obrigou a mexer em muitos arquivos. Isso é acoplamento forte — a lâmpada soldada no abajur.

dor 2 · teste

Como testar sem enviar e-mail de verdade?

@Test void deveCriarPedido() { PedidoService s = new PedidoService(); s.criar("Pizza"); // ...e aqui ele DISPARA UM E-MAIL DE VERDADE // toda vez que o teste roda. }

O problema

Não existe brecha pra colocar um notificador de mentira. O new está trancado dentro da classe.

A consequência

ou o teste manda e-mail de verdade, ou você não testa. Nas duas opções, alguém perde.

Guarde: código difícil de testar quase sempre é código com acoplamento forte. Testabilidade é um sintoma, não um objetivo isolado.

dor 3 · desperdício

Cada um com o seu, sem precisar

Se dez classes fazem new EmailNotificador(), existem dez objetos idênticos na memória fazendo exatamente a mesma coisa.

Com new espalhado

10 conexões abertas, 10 configurações carregadas, 10 vezes o mesmo custo.

Com um objeto compartilhado

1 objeto criado uma vez, usado por todo mundo. É assim que o Spring trabalha por padrão.

Escala isso pra uma conexão com banco de dados e o desperdício deixa de ser detalhe: vira o motivo de a aplicação cair.

// diagnóstico

A raiz das três dores é a mesma

A classe que usa um objeto é a mesma que fabrica esse objeto.

Usar

chamar notificador.enviar(...). Isso é trabalho do PedidoService. Faz sentido.

Fabricar

decidir qual classe, quando criar e como configurar. Isso não é trabalho do PedidoService.

A solução, então, é separar as duas coisas: alguém de fora fabrica, e a classe só usa.

Esse "alguém de fora" é o Spring. E o nome dessa separação é o próximo bloco da aula.

parte 4 · o conceito central
🔄

Inversão de controle e injeção de dependência

Dois nomes assustadores pra duas ideias simples. Vamos por partes — literalmente palavra por palavra.

IoC · palavra por palavra

"Inversão de controle"

Controle

o poder de decidir. No nosso caso: decidir qual objeto criar, quando criar e como ligá-lo aos outros.

Quem tinha esse controle

a sua própria classe, na linha do new. Ela mandava em tudo.

Inverter

tirar esse poder da sua classe e entregar pra alguém de fora — o framework.

Juntando: inversão de controle é o seu código deixar de decidir como os objetos são criados e ligados, e passar essa decisão pro framework.

Repare que IoC é um princípio, uma ideia. Ainda não falamos de nenhuma linha de código Spring.

IoC · analogia

Restaurante × cozinha de casa

Cozinha de casa (com new)

Você compra os ingredientes, acende o fogo, cozinha, serve e lava a louça. Controle total — e trabalho total. Se acabar o gás, o almoço é problema seu.

Restaurante (com IoC)

Você pede o prato. Não escolhe a marca da panela, não acende o fogo, não sabe quem é o fornecedor. Você declara o que quer; o restaurante resolve como.

O Spring é o restaurante. Sua classe é o cliente que só diz: "eu preciso de um notificador".

Note o que você perde: controle sobre detalhes. E o que você ganha: só se preocupa com o que o seu código realmente faz.

DI · palavra por palavra

"Injeção de dependência"

Dependência

já sabemos: o objeto de que a sua classe precisa. Aqui, o notificador.

Injeção

entregar de fora pra dentro. Sua classe não busca: ela recebe.

Juntando

injeção de dependência é a técnica de entregar prontos, de fora, os objetos de que uma classe precisa.

Analogia direta: você não fabrica seu sangue quando precisa de transfusão. Alguém injeta em você um sangue que já existe, produzido em outro lugar.

DI · sem Spring nenhum

Isso funciona em Java puro

Injeção de dependência não é uma invenção do Spring. É um jeito de escrever classes. Olha só — só mudou o construtor:

PedidoService.java
public class PedidoService { private final Notificador notificador; // interface, não classe concreta! // a dependência CHEGA de fora, pelo construtor public PedidoService(Notificador notificador) { this.notificador = notificador; } public void criar(String item) { System.out.println("Pedido criado: " + item); notificador.enviar("Seu pedido de " + item + " foi criado!"); } }

Sumiu o new. A classe agora declara o que precisa e para por aí. Quem monta é outro.

DI · e quem monta?

Alguém tem que ligar os fios

Main.java — Java puro
public class Main { public static void main(String[] args) { // 1. crio a dependência Notificador n = new EmailNotificador(); // 2. injeto na classe que precisa dela PedidoService service = new PedidoService(n); service.criar("Pizza"); } }

Funciona lindamente — com 3 classes. Agora imagine 200 classes, cada uma pedindo 3 ou 4 outras, e ordem de criação importando.

Essa main viraria um monstro de mil linhas. É exatamente esse trabalho que o Spring faz por você.

DI · agora com Spring

Duas etiquetas e acabou

EmailNotificador.java
@Component public class EmailNotificador implements Notificador { ... }
PedidoService.java
@Service public class PedidoService { private final Notificador n; public PedidoService(Notificador n) { this.n = n; } }

O que o Spring lê

@Component: "essa classe eu devo criar e guardar".

O que ele faz

Vê que PedidoService pede um Notificador no construtor, procura no contêiner quem é um Notificador, acha o EmailNotificador e entrega.

O que sumiu

A main que ligava tudo na mão. Nenhum new escrito por você.

Esse é o coração do Spring inteiro. As 17 aulas seguintes são variações e ferramentas em cima disso.

// a pergunta que sempre volta

IoC e DI são a mesma coisa?

IoC — o princípio

"Quem decide como os objetos nascem e se conectam não é o meu código." É uma ideia, um jeito de pensar.

DI — a técnica

"Recebo pelo construtor o que eu preciso." É a forma concreta de aplicar aquela ideia.

DI é uma maneira de fazer IoC. IoC é o objetivo; DI é o caminho mais usado pra chegar lá.

Analogia: "se alimentar melhor" é o princípio; "cortar refrigerante" é a técnica. Não são sinônimos, mas uma serve à outra.

DI · as três formas

Existem três jeitos. Use um.

FormaComo éVeredito
Construtora dependência chega como parâmetro do construtorUse sempre esta. Permite final, deixa claro o que a classe precisa e funciona em teste sem Spring.
Setterum método setNotificador(...)Casos raros, quando a dependência é mesmo opcional.
Campo (@Autowired no atributo)o Spring preenche o campo por reflexãoEvite. O campo não pode ser final, a classe esconde do que depende e você não consegue instanciá-la num teste puro.

Você vai ver muito tutorial na internet com @Autowired em cima do atributo. É código antigo. A própria documentação do Spring recomenda construtor desde 2016. Aprofundamos na aula 02.

parte 5 · o ecossistema

Afinal, o que é "o Spring"?

Spring não é um programa. É uma família de projetos que compartilham o mesmo contêiner de objetos.

Spring Framework

a base: o contêiner, a injeção de dependência e o Spring MVC (web). É o tronco.

Spring Data JPA

fala com banco de dados sem você escrever SQL. Aulas 5 a 8.

Spring Security

login, senha, permissões e token. Aulas 10 e 11.

Tem mais: Spring Cloud, Spring Batch, Spring Boot Actuator... Você não precisa conhecer todos. Precisa saber que o tronco é sempre o mesmo.

Fixe: Spring Framework = tronco. Os outros "Spring alguma coisa" são galhos que se plugam nele.

// como era antes de 2014

Spring tradicional: poderoso e insuportável

Você tinha que declarar cada objeto num arquivo XML, na mão:

applicationContext.xml — o passado
<beans> <bean id="notificador" class="br.com.loja.EmailNotificador"/> <bean id="pedidoService" class="br.com.loja.PedidoService"> <constructor-arg ref="notificador"/> </bean> </beans> // mais: configurar servidor, dialeto do banco, codificação, // versão de cada biblioteca... tudo na mão, tudo em XML.

Era comum passar o primeiro dia inteiro configurando antes de escrever uma linha de regra de negócio. Todo mundo fazia igual, e todo mundo fazia de novo em cada projeto.

// a resposta

Spring Boot: "eu já sei o que você quer"

Spring Boot não é um Spring diferente. É o mesmo Spring com decisões padrão já tomadas por você.

Autoconfiguração

ele olha o que existe no seu projeto e configura sozinho.

Starters

pacotes de dependências que já vêm combinando entre si.

Servidor embutido

o servidor web vem dentro do seu programa. main e pronto.

A frase que resume: convenção sobre configuração. Se você não disser nada, ele usa o padrão razoável. Se disser, ele obedece.

Boot · autoconfiguração

O que é autoconfiguração, na prática

Quando a aplicação sobe, o Spring Boot faz uma série de perguntas do tipo "se... então...":

Se

existe a biblioteca do Tomcat no projeto e você não configurou nenhum servidor...

Então

eu subo um Tomcat na porta 8080.

Se

existe um driver de banco H2 e você não declarou nenhuma conexão...

Então

eu crio um banco em memória e conecto nele.

Nada de mágica: são centenas de regrinhas dessas escritas por gente do time do Spring. Você pode sobrescrever qualquer uma — é o que vamos fazer no application.properties.

Boot · starters

Starter é um combo

Um starter é uma dependência que, sozinha, traz um conjunto de bibliotecas que combinam entre si, nas versões certas.

Sem starter

você declara Spring MVC, Tomcat, Jackson, validação... e reza pra que as versões sejam compatíveis.

Com spring-boot-starter-web

uma linha traz todas elas, testadas juntas pelo time do Spring.

Três ferramentas antes do primeiro projeto: JDK, Maven e uma IDE. Vamos entender o que cada uma é — não só instalar.

ferramenta 1 · JDK 21

JDK, JRE, JVM — três siglas, três coisas

SiglaNomeO que é
JVMJava Virtual Machineo "motor" que executa o programa Java. É ela que faz o mesmo código rodar no Windows, Mac e Linux.
JREJava Runtime Environmenta JVM + as bibliotecas básicas. Suficiente pra rodar um programa pronto.
JDKJava Development Kito JRE + o compilador e as ferramentas de desenvolvimento. É o que você precisa, porque você escreve código.

$ java -version openjdk version "21.0.5" 2024-10-15 LTS # se aparecer 17, 11 ou "comando não encontrado", precisa instalar

Regra de bolso: JDK ⊃ JRE ⊃ JVM. Instalando o JDK, você tem os três.

ferramenta 2 · Maven

Maven é o montador do projeto

Maven faz três coisas que você não vai querer fazer na mão:

Baixa as bibliotecas

você escreve o nome da biblioteca num arquivo e ele busca na internet, junto com tudo de que ela depende.

Compila

transforma os seus .java em .class, na ordem certa.

Empacota

junta tudo num arquivo .jar — o programa pronto pra rodar em qualquer máquina com Java.

Você não precisa instalar o Maven separado: o projeto gerado já vem com um Maven Wrapper (mvnw) que se vira sozinho.

Maven · o pom.xml

O arquivo que descreve o projeto

pom.xml
<!-- quem é este projeto: as "coordenadas" dele --> <groupId>br.edu.faculdade</groupId> <!-- a organização --> <artifactId>biblioteca</artifactId> <!-- o nome do projeto --> <version>0.0.1-SNAPSHOT</version> <!-- a versão --> <!-- de que este projeto precisa --> <dependencies> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> </dependency> </dependencies>

Repare: não tem versão na dependência. Quem decide a versão é o "pai" do projeto, o spring-boot-starter-parent. Por isso as bibliotecas nunca brigam entre si.

POM = Project Object Model. Toda biblioteca do mundo Java tem essas três coordenadas: groupId, artifactId e version.

parte 7 · anatomia

O que veio dentro do zip

biblioteca/ ├── pom.xml ← as dependências e a identidade ├── mvnw · mvnw.cmd ← o Maven embutido (não mexa) ├── src/main/java/ │ └── br/edu/faculdade/biblioteca/ │ └── BibliotecaApplication.java ← o main() ├── src/main/resources/ │ ├── application.properties ← a configuração da aplicação │ ├── static/ ← arquivos públicos (imagens, css) │ └── templates/ ← páginas HTML (não usaremos) └── src/test/java/ ← os testes (aula 09)

Só três lugares importam hoje: pom.xml, a pasta do seu pacote em src/main/java e o application.properties. O resto é infraestrutura.

anatomia · a classe principal

Onde tudo começa

BibliotecaApplication.java
package br.edu.faculdade.biblioteca; import org.springframework.boot.SpringApplication; import org.springframework.boot.autoconfigure.SpringBootApplication; @SpringBootApplication public class BibliotecaApplication { public static void main(String[] args) { SpringApplication.run(BibliotecaApplication.class, args); } }

É a mesma main de sempre — a que você escreve desde a primeira aula de Java. A diferença é a linha de dentro: ela entrega o controle pro Spring.

Traduzindo SpringApplication.run(...): "Spring, assume daqui. Monte o contêiner, ligue os objetos e suba o servidor."

anatomia · a etiqueta mestre

@SpringBootApplication são três em uma

@SpringBootConfiguration

"esta classe é uma fonte de configuração do projeto".

@EnableAutoConfiguration

"ligue a autoconfiguração" — as centenas de regras se... então... que vimos.

@ComponentScan

"vasculhe o pacote desta classe e todos os subpacotes, e crie um objeto pra cada classe etiquetada".

⚠️ O terceiro item é a causa do erro nº 1 da aula: uma classe criada fora do pacote da Application simplesmente não é enxergada. O Spring não reclama — o endpoint só devolve 404.

anatomia · configuração

application.properties

Requisição e resposta

Toda a web é uma conversa de duas falas: alguém pergunta, alguém responde. O protocolo dessa conversa se chama HTTP.

O servidor nunca começa a conversa. Ele fica calado esperando alguém perguntar. Por isso sua aplicação "não faz nada" depois de subir — ela está esperando.

código · o primeiro endpoint

Sete linhas

br/edu/faculdade/biblioteca/OlaController.java
package br.edu.faculdade.biblioteca; // mesmo pacote da Application! import org.springframework.web.bind.annotation.*; @RestController public class OlaController { @GetMapping("/ola") public String ola() { return "Olá, mundo Spring!"; } }

Não existe nenhum new OlaController() em lugar nenhum. Você só colou a etiqueta — o Spring fez o resto.

código · peça por peça

O que cada linha significa

@RestController

Duas coisas ao mesmo tempo: (1) "crie um objeto desta classe e guarde no contêiner"; (2) "o que os métodos devolverem vira corpo da resposta HTTP, não nome de página".

@GetMapping("/ola")

"quando chegar uma requisição GET no caminho /ola, execute este método".

public String ola()

um método Java comum. O nome dele não tem importância nenhuma pro Spring — quem define a rota é a anotação.

return "Olá..."

o valor devolvido vira o conteúdo que o navegador mostra, com status 200 automaticamente.

// o que acontece de verdade

Da URL até o seu método

Você digita a URL

o navegador abre uma conexão na porta 8080 e manda GET /ola.

O Tomcat recebe

o servidor embutido pega a requisição e entrega pro Spring.

O DispatcherServlet decide

uma peça central do Spring MVC consulta a tabela de rotas: "quem respondeu por GET /ola?"

Seu método roda

o Spring chama ola() no objeto que ele mesmo criou lá no start.

A resposta volta

o retorno vira corpo da resposta, com status 200, e o navegador mostra.

Repare de novo: você nunca chamou o seu método. O framework chamou. Isso é a inversão de controle acontecendo na sua frente.

// antes do próximo código

O que é JSON

Texto puro num formato que qualquer linguagem entende. É como sistemas trocam dados hoje — e é o que a sua API vai devolver o semestre inteiro.

{ "titulo": "Duna", "autor": "Frank Herbert", "ano": 1965, "disponivel": true }

Chaves

sempre entre aspas duplas.

Textos

entre aspas. Números e true/false, sem aspas.

Listas

entre colchetes: [ {...}, {...} ].

JSON = JavaScript Object Notation. Nasceu no JavaScript, mas hoje é universal — Java, Python, C#, celular, tudo lê.

código · devolvendo objeto

De String pra JSON, de graça

Livro.java
// record: classe só de dados, imutável public record Livro( String titulo, String autor, int ano) { }
OlaController.java
@GetMapping("/livro") public Livro livro() { return new Livro("Duna", "Frank Herbert", 1965); }

O que sai no navegador

{"titulo":"Duna", "autor":"Frank Herbert", "ano":1965}

Quem converteu?

Uma biblioteca chamada Jackson, que veio junto no starter-web. Ela lê os campos do objeto e monta o JSON.

Você não escreveu uma linha de conversão. Isso é autoconfiguração + starter trabalhando: o Jackson estava no classpath, então o Spring o usou.
