O mesmo comportamento de antes, com cada coisa no seu lugar. Compare com o seu — depois de ter feito. Se a sua solução é diferente da minha mas o DECISOES.md explica por quê, ela vale igual.

Não existe uma resposta certa só

Você pode ter chamado a classe de ReceitaService, usado for no lugar de stream, ou posto as classes em subpastas. Tudo isso passa.

O que não passa: a lista aparecer mais de uma vez, if de regra dentro do controller, ou new entre as suas classes.

Defeito 1 · A lista, uma vez só
ReceitaRepository.java
package br.edu.faculdade.receitas;

import org.springframework.stereotype.Repository;
import java.util.List;

@Repository
public class ReceitaRepository {

    public List<Receita> todas() {
        return List.of(
            new Receita("Bolo de fubá", 40),
            /* ... as outras onze, exatamente como estavam ... */
            new Receita("Torrada com ovo", 7));
    }
}
o que essa classe não tem

Nenhum if, nenhum for, nenhum construtor. Ela é a única das três que não precisa de ninguém — só sabe onde o dado está.

Na aula 05 esse método vira uma consulta no banco. Nada fora desta classe vai precisar mudar — e é exatamente esse o motivo de ela existir separada hoje, quando a lista ainda é escrita à mão.

Defeito 2 · As duas regras, no service
CatalogoService.java
package br.edu.faculdade.receitas;

import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class CatalogoService {

    private final ReceitaRepository repositorio;

    public CatalogoService(ReceitaRepository repositorio) {
        this.repositorio = repositorio;
    }

    public List<Receita> todas() {
        return repositorio.todas();
    }

    public List<Receita> rapidas() {
        return repositorio.todas().stream()
                .filter(r -> r.minutos() <= 30)
                .toList();
    }

    public List<Receita> longas() {
        return repositorio.todas().stream()
                .filter(r -> r.minutos() > 60)
                .toList();
    }
}
duas coisas pra reparar

1. Os métodos se chamam rapidas() e longas() — o nome diz a regra, não o endereço HTTP. Se amanhã o endpoint virar /catalogo/express, este arquivo não muda. Nome de método de service que fala de HTTP é sinal de que a camada errada está mandando.

2. Tem um todas() que só repassa para o repository. Parece inútil e não é: o controller nunca fala com o repository direto. Se amanhã "todas" passar a excluir as arquivadas, a mudança cabe aqui e ninguém mais fica sabendo.

se você usou for em vez de stream

Está certo também. Isto é equivalente e vale a mesma nota:

public List<Receita> rapidas() {
    List<Receita> saida = new ArrayList<>();
    for (Receita r : repositorio.todas()) {
        if (r.minutos() <= 30) saida.add(r);
    }
    return saida;
}

O que a aula 02 cobra é onde o if mora, não como ele está escrito. Um if aqui está no lugar certo; o mesmo if no controller, não.

Defeito 3 · O controller, enxuto
CatalogoController.java
package br.edu.faculdade.receitas;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import java.util.List;

@RestController
public class CatalogoController {

    private final CatalogoService servico;

    public CatalogoController(CatalogoService servico) {
        this.servico = servico;
    }

    @GetMapping("/catalogo")
    public List<Receita> todas() {
        return servico.todas();
    }

    @GetMapping("/catalogo/rapidas")
    public List<Receita> rapidas() {
        return servico.rapidas();
    }

    @GetMapping("/catalogo/longas")
    public List<Receita> longas() {
        return servico.longas();
    }
}
o teste do controller enxuto

De 60 linhas para 25, e o que sobrou é só endereço e chamada. Leia qualquer método em voz alta: "devolve as rápidas". Nenhuma decisão, nenhum laço, nenhum dado.

Se o seu controller ainda tem if, for, new ArrayList ou algum número solto, sobrou regra nele.

O DECISOES.md

Curto assim. O que se avalia é o porquê, não o tamanho. 

# Decisões da refatoração

## 1. A lista, uma vez só
As três cópias viraram um método todas() num @Repository. Antes,
adicionar uma receita significava editar três lugares — e esquecer
um não dava erro nenhum, só fazia os endpoints discordarem entre si.

## 2. As regras no service
Os dois filtros viraram rapidas() e longas() num @Service. Nomeei
pela regra e não pelo endpoint: se a rota mudar de nome, este
arquivo não muda. E agora dá pra testar as regras sem subir servidor.

## 3. O controller enxuto
Cada método ficou com uma linha. O service chega pelo construtor,
num campo final — nenhuma classe minha dá new na outra, quem
constrói é o Spring.

## A prova
Adicionar uma receita nova: antes 3 arquivos, agora 1.

Onde isso continua

Na aula 05 o método todas() do repository vira uma consulta em banco de verdade — e nem o service nem o controller mudam uma linha. Na aula 08 o service ganha transações. Esse desenho de hoje é o que torna as duas coisas simples.
