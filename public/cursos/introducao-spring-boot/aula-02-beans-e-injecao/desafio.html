Desafio · Aula 02

Um controller virando três 🔧

Você recebe um controller com três endpoints — e a mesma lista escrita por extenso três vezes, uma em cada método. Sua tarefa é separá-lo em repository, service e controller sem mudar uma vírgula do que a API devolve.

🎯

O que este desafio verifica

Exatamente o que a aula treinou, com mais código: reconhecer o que está no lugar errado e mover para onde pertence.

É de propósito que a saída não muda. Assim você tem um critério objetivo: se a resposta de qualquer endpoint mudou, você quebrou algo no caminho. Refatorar é melhorar o desenho sem alterar o comportamento — se o comportamento mudou, não foi refatoração.

🧪

Faça os labs antes

Este desafio é o mesmo caminho dos quatro labs, com um código maior. Se você não fez os labs, comece por exercicios.html — lá cada passo tem gabarito. Aqui não tem.

O código que você recebe

Está inteiro, pronto pra colar, em codigos-desafio.html. Adapte para o seu tema — o desenho do problema é o mesmo em qualquer um. 

@RestController
public class CatalogoController {

    @GetMapping("/catalogo")
    public List<Receita> todas() {
        return List.of( /* as 12 receitas */ );
    }

    @GetMapping("/catalogo/rapidas")
    public List<Receita> rapidas() {
        List<Receita> todas = List.of( /* as 12 de novo */ );
        List<Receita> saida = new ArrayList<>();
        for (Receita r : todas) {
            if (r.minutos() <= 30) saida.add(r);
        }
        return saida;
    }

    @GetMapping("/catalogo/longas")
    public List<Receita> longas() {
        List<Receita> todas = List.of( /* e mais uma vez */ );
        List<Receita> saida = new ArrayList<>();
        for (Receita r : todas) {
            if (r.minutos() > 60) saida.add(r);
        }
        return saida;
    }
}
😖

Antes de começar, sinta o problema

Adicione uma receita nova ao catálogo, no código como ele está. Conte quantos lugares você teve que editar.

Agora imagine que você esqueceu um deles. O /catalogo mostra 13 itens e o /catalogo/rapidas continua olhando 12. Ninguém recebe erro nenhum — o sistema só passa a mentir.

Os três defeitos

1 · A lista está copiada três vezes

Três cópias da mesma verdade. Toda mudança precisa acontecer em três lugares, e esquecer um não gera erro — gera resposta errada em silêncio.

Você vai: criar um @Repository com a lista uma vez só, num método todas().

2 · As regras estão dentro do controller

"Rápida é até 30 minutos" e "longa é mais de 60" são decisões do negócio, não do transporte HTTP. Do jeito que está, para testar essas duas regras é preciso subir um servidor web e abrir o navegador.

Você vai: mover os dois filtros para um @Service, em dois métodos com nomes que digam a regra.

3 · O controller monta tudo sozinho

Ele busca os dados, percorre a lista, decide o que entra e monta a saída. São quatro trabalhos num método só.

Você vai: deixar cada método do controller com uma linha — chamar o service e devolver. O service chega pelo construtor, num campo final. Nenhum new entre as suas classes.

Passo a passo
01

Rode o código quebrado e guarde as três respostas

Cole o código no seu projeto, suba e chame os três endpoints. Copie cada JSON num arquivo à parte. Eles são o seu gabarito: no fim, as três respostas têm que ser idênticas.

02

Crie o repository

Uma classe com @Repository e um método todas() devolvendo a lista — uma vez só. Apague as três cópias do controller.

O projeto vai quebrar. É esperado, igual ao lab 1.

03

Crie o service

Uma classe com @Service, recebendo o repository pelo construtor, com dois métodos: um para as rápidas, outro para as longas.

Nomeie os métodos pela regra, não pelo endpoint: rapidas() e longas() — não getCatalogoRapidas().

04

Enxugue o controller

Campo final do service, construtor recebendo ele, e os três métodos com uma linha cada.

05

Compare com o gabarito do passo 1

Os três endpoints, mesmos itens, mesma ordem. Diferente? Você mudou comportamento sem querer — ache onde antes de seguir.

06

Agora a prova de fogo

Adicione a mesma receita nova do começo. Quantos arquivos você editou desta vez? Anote o número — ele vai para o DECISOES.md.

07

Escreva o DECISOES.md

Um arquivo curto na raiz do repositório, com uma seção por defeito. Em cada uma, duas frases: o que você fez e por quê. Feche com o número do passo 6, antes e depois.

Este arquivo é parte da nota. Código certo com justificativa vazia mostra que funcionou por acaso.

O que não entra neste desafio

Banco de dados, DTO, validação, tratamento de erro, teste automatizado e configuração por ambiente são as próximas aulas. Se você já sabe e quiser fazer, faça — mas não conta ponto, e um desafio inchado é mais difícil de corrigir e de te dar retorno útil.
