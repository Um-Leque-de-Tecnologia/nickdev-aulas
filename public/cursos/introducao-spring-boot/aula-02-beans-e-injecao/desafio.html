O esqueleto do Leque de Vagas 🦴

A primeira evolução do projeto do semestre. A API vai responder com dados fixos em memória — sem banco, sem validação — mas já separada em controller, service e repository. O desenho certo desde o primeiro dia, porque é muito mais barato do que consertar depois.

💼

Ainda não leu o briefing?

Leia antes de qualquer coisa: o briefing do Leque de Vagas explica o projeto inteiro, as quatro frentes e onde isso chega em dezembro. Este desafio é só o primeiro passo dele.

👥

Quatro pessoas, quatro partes

Cada integrante assume uma frente e faz a parte correspondente. Todas as quatro têm o mesmo tamanho e a mesma forma: um record, um @Repository, um @Service e um @RestController.

É de propósito que sejam iguais. Nesta aula todo mundo precisa escrever o padrão com as próprias mãos — a partir da aula 03 as frentes começam a divergir de verdade.

Antes de codar — a combinação de 30 minutos
🤝

A parte 4 depende da parte 1. Resolvam isso agora.

A frente de números conta vagas — e para contar, precisa da lista que a frente de Vaga vai escrever. Se ela esperar a parte 1 ficar pronta, a equipe entrega em série o que podia ter entregado em paralelo.

Sentem juntos e escrevam estas duas coisas antes de abrir a IDE. Com elas no papel, as quatro pessoas programam ao mesmo tempo.

// 1. O record da Vaga — combinado pela equipe, igual para todo mundo.
public record Vaga(
    String id,
    String titulo,
    String descricao,
    String area,          // Front-end, Back-end, Dados, Mobile…
    String senioridade,   // Estágio, Júnior, Pleno, Sênior
    String local,
    boolean aceitaIniciante,
    String empresaSlug
) { }

// 2. A assinatura que a parte 4 vai chamar. A parte 1 promete entregar isto.
@Repository
public class VagaRepository {
    public List<Vaga> todas() { /* … */ }
}

Escrevam o record primeiro, num commit só, e avisem a equipe. Assim as outras três pessoas já têm o tipo para compilar contra — mesmo antes de a lista existir.

As quatro partes
PARTE 1

Vaga

frente 1

O recurso principal da API. É a parte que as outras esperam — entregue o record cedo.

  • Vaga — o record combinado com a equipe.
  • VagaRepository com @Repository e o método todas(), devolvendo no mínimo 12 vagas escritas à mão.
  • VagaService com @Service, recebendo o repository por construtor: listar() e buscarPorId(String id).
  • VagaController com @RestController, recebendo o service.
rotadevolve
GET /vagasa lista inteira
GET /vagas/{id}uma vaga, ou lista vazia se não achar

As 12 vagas precisam variar. Pelo menos 4 áreas diferentes, 3 senioridades e uma mistura de aceitaIniciante. Com dados uniformes, a parte 4 devolve números sem graça e a busca da aula 03 não mostra diferença.

PARTE 2

Empresa

frente 2

Quem publica as vagas. Independente da parte 1 — dá para fazer em paralelo do começo ao fim.

  • Empresa — record com id, nome, slug, site e descricao.
  • EmpresaRepository, EmpresaService e EmpresaController, no mesmo formato da parte 1.
  • No mínimo 5 empresas, e os slug delas precisam bater com os empresaSlug que a parte 1 usou nas vagas.
rotadevolve
GET /empresasa lista inteira
GET /empresas/{slug}uma empresa pelo slug

Combinem os slugs com a parte 1. É a segunda coisa que a equipe precisa acertar antes de codar — aurora-tech num lado e auroratech no outro quebra a junção na aula 06.

PARTE 3

Pessoa

frente 3

Quem se candidata. Também independente — nesta aula ela ainda não se liga a vaga nenhuma.

  • Pessoa — record com id, nome, email, area de interesse e senioridade.
  • PessoaRepository, PessoaService e PessoaController, no mesmo formato.
  • No mínimo 6 pessoas.
rotadevolve
GET /pessoasa lista inteira
GET /pessoas/{id}uma pessoa

Sem senha por enquanto. Guardar senha exige cuidado que a gente ainda não tem — o campo entra na aula 10, junto com o jeito certo de guardá-la. E aí GET /pessoas deixa de ser público.

PARTE 4

Números do catálogo

frente 4

A única parte sem recurso próprio: ela consulta o que a parte 1 guarda. É a que exige a combinação de contrato.

  • EstatisticasService com @Service, recebendo o VagaRepository por construtor — não o service da parte 1.
  • EstatisticasController com uma rota só.
  • Os números: total de vagas, quantas aceitam iniciante, quantas por área e quantas por senioridade.
rotadevolve
GET /estatisticasum objeto com os quatro números
// o formato da resposta, combinado com a equipe
{
  "totalDeVagas": 12,
  "aceitamIniciante": 7,
  "porArea": { "Front-end": 4, "Back-end": 3, "Dados": 3, "Mobile": 2 },
  "porSenioridade": { "Estágio": 2, "Júnior": 6, "Pleno": 4 }
}

Por que o repository e não o service? Porque estatística é uma regra de negócio, e regra não chama regra por preguiça — ela busca o dado e decide. Se um dia o VagaService filtrar vagas expiradas, a contagem não deve mudar junto sem alguém decidir isso.

Depois: juntar
05

As quatro partes no mesmo projeto

Todo mundo trabalha no mesmo repositório, cada pessoa numa branch, e no fim tudo se encontra na main.

  • Suba a aplicação e chame as sete rotas, uma a uma.
  • Confira que os empresaSlug das vagas existem em /empresas.
  • Confira que os números de /estatisticas batem com o que /vagas devolve — conte na mão se precisar.

Achou divergência? Isso é a entrega funcionando. Foi exatamente para pegar esse tipo de coisa que a integração é um passo com nome próprio, e não "e aí a gente junta".

Requisitos mínimos
  • As quatro partes entregues, e o Git mostrando quem fez cada uma.
  • As sete rotas respondendo.
  • Toda classe com o estereótipo certo: @Repository, @Service, @RestController.
  • Toda dependência por construtor, em campo final. Nenhum new entre as classes de vocês.
  • Nenhum if nem for de regra dentro de controller.
  • Nenhum record anotado — record é dado, não é bean.
  • README com as quatro frentes e quem assumiu cada uma.
O que NÃO pode 🚫
  • Banco de dados. É a aula 05. Aqui a lista é escrita à mão, e é de propósito.
  • DTO, validação ou tratamento de erro. São as aulas 03 e 04.
  • Uma pessoa fazer duas partes. Se alguém travou, a equipe ajuda — mas o commit é de quem fez.
  • Uma classe só com tudo dentro. Foi o que a aula inteira desmontou.
Como isso é avaliado
critérioo que se esperapeso

📦 Como entregar

  • Link do repositório da equipe no GitHub.
  • README com as quatro frentes, quem assumiu cada uma, e como rodar.
  • Pelo menos um commit por pessoa — o histórico é a evidência.
  • Prazo: até a aula 03 (25/08), antes do início.

Travou? Traga na aula 03 com o erro na tela. Print do stack trace vale mais que descrição do problema.
