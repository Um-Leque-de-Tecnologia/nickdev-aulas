Exercícios em aula · Aula 02

Uma classe de cada vez 🧱

Você vai pegar o controller da aula 01 — aquele que faz tudo — e separá-lo em três classes. Uma por lab, de baixo para cima, sem pressa.

🧭

A ordem importa

Repository primeiro, service depois, controller por último. É a ordem em que as classes dependem umas das outras: o service precisa do repository já existir, e o controller precisa do service.

Nos labs 1 e 2 o projeto vai ficar temporariamente quebrado. Isso é esperado e está avisado no lugar certo — não tente consertar antes da hora.

📋

O formato que se repete três vezes

Toda classe que precisa de outra segue exatamente este desenho. Você vai escrevê-lo duas vezes hoje. Copiar daqui é o esperado.

private final OQueEuPreciso campo;      // 1. campo final

public MinhaClasse(OQueEuPreciso campo) {  // 2. recebe no construtor
    this.campo = campo;                // 3. guarda
}

Nunca new. Quem constrói é o Spring; a sua classe só recebe pronto.

✅

Antes de começar

  • O projeto da aula 01 abre na sua IDE.
  • Ele sobe: aparece Started ...Application in ... seconds.
  • Pelo menos um endpoint responde no navegador.

Se alguma falhar, resolva agora — os quatro labs dependem das três.

Os labs
LAB 1

Crie o seu repository

~15 min

Tirar os dados de dentro do controller e pôr numa classe que só cuida disso.

  1. Crie a classe no mesmo pacote da sua Application, com o nome do seu tema seguido de Repository.
  2. Ponha @Repository em cima da classe.
  3. Recorte o List.of(...) do controller e cole num método todas().
  4. Coloque pelo menos 8 itens, com valores variados — no lab 2 você vai filtrar essa lista, e com poucos itens o filtro não mostra diferença.
// ReceitaRepository.java — troque Receita pelo seu tema
package br.edu.faculdade.receitas;

import org.springframework.stereotype.Repository;
import java.util.List;

@Repository
public class ReceitaRepository {

    public List<Receita> todas() {
        return List.of(
            new Receita("Bolo de fubá", 40),
            new Receita("Omelete", 8),
            new Receita("Feijoada", 180),
            new Receita("Vitamina", 5),
            new Receita("Lasanha", 90),
            new Receita("Panqueca", 22),
            new Receita("Sopa", 45),
            new Receita("Torrada", 7));
    }
}

O controller vai ficar quebrado — a lista que ele devolvia sumiu. É esperado. Conserta no lab 3.

responda
  1. Sua classe tem um método só?
  2. Tem algum if dentro dela? (a resposta certa é não — por quê?)
  3. Por que ela não precisa de construtor?
conferir depois de responder

1. Um método. O repository de hoje só sabe devolver tudo. Na aula 05, quando virar banco, ele vai ganhar mais métodos — mas todos com o mesmo papel: buscar e guardar.

2. Não. Um if é uma decisão, e decisão é trabalho da cozinha, não da despensa. Se o filtro morasse aqui, você teria que criar um método novo no repository para cada regra nova que aparecesse.

3. Porque ela não precisa de ninguém. É a única das três que não depende de outra classe — por isso ela é a primeira a ser construída, e por isso a gente começou por ela.

LAB 2

Crie o seu service

~15 min

Escrever pela primeira vez o formato que se repete: campo final, construtor, regra dentro.

  1. Crie a classe com @Service, nome terminando em Service.
  2. Copie o formato do construtor (está lá em cima, na caixa roxa).
  3. Escreva um método com uma regra do seu tema. Receitas rápidas, discos antes de 2000, jogos curtos — algo que decida o que entra e o que fica de fora.
  4. O projeto continua sem subir. Ainda é esperado.
// CatalogoService.java
package br.edu.faculdade.receitas;

import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class CatalogoService {

    private final ReceitaRepository repositorio;

    public CatalogoService(ReceitaRepository repositorio) {
        this.repositorio = repositorio;
    }

    public List<Receita> rapidas() {
        return repositorio.todas().stream()
                .filter(r -> r.minutos() <= 30)
                .toList();
    }
}

Não sabe usar stream? Pode fazer com for e uma lista nova — funciona igual. O que importa neste lab é onde a regra mora, não como ela está escrita.

responda
  1. O seu campo é private final?
  2. Você deu new ReceitaRepository() em algum lugar? (se sim, apague — de onde vem o objeto então?)
  3. Qual é a regra que você escreveu, em uma frase?
conferir depois de responder

1. Tem que ser. final significa que, depois que o objeto existe, ninguém troca essa dependência por outra coisa — e o compilador garante isso pra você.

2. Nenhum new. O objeto chega pelo construtor, e quem o entrega é o Spring: ele viu o @Repository, criou a instância e guardou. Quando for construir o seu service, ele olha o construtor, vê que precisa de um ReceitaRepository, e passa o que já tem pronto.

3. Se você não consegue dizer a regra em uma frase, provavelmente colocou coisa demais no método. Uma regra por método.

LAB 3

Ligue os três e rode

~15 min

Fechar a cadeia e ver a aplicação voltar a responder — agora com as responsabilidades separadas.

  1. No controller, escreva o formato do construtor pela segunda vez — agora recebendo o service.
  2. Deixe o método do endpoint com uma linha só.
  3. Suba e chame no navegador.
  4. Confira: Controller → Service → Repository, e nenhum new entre elas.
// ReceitaController.java
@RestController
public class ReceitaController {

    private final CatalogoService servico;

    public ReceitaController(CatalogoService servico) {
        this.servico = servico;
    }

    @GetMapping("/receitas/rapidas")
    public List<Receita> rapidas() {
        return servico.rapidas();
    }
}
responda
  1. Quantas linhas tem o corpo do seu método de endpoint?
  2. Abra os três arquivos. Você consegue dizer numa frase o que cada um faz?
  3. Se amanhã a regra mudar de 30 para 20 minutos, quantos arquivos você abre?
conferir depois de responder

1. Uma. Se tiver mais, olhe o que sobrou ali — provavelmente é regra, e regra é da cozinha.

2. "Recebe o pedido e devolve a resposta" / "decide quais são as rápidas" / "sabe onde a lista está". Se algum arquivo precisa de duas frases com um "e" no meio, ele está fazendo dois trabalhos.

3. Um — o service. É esse o ganho concreto de hoje: você sabe onde procurar antes de abrir qualquer arquivo. No controller da aula 01 a resposta seria "abro o único que existe e procuro no meio de tudo".

LAB 4

Quebre de propósito

~10 min

Provocar agora, com calma, o erro que mais vai aparecer no semestre — e aprender a ler as três partes dele.

  1. Apague só a anotação @Service da sua classe. Rode.
  2. Leia o erro inteiro antes de consertar.
  3. Recoloque a anotação e confirme que volta a subir.
  4. Agora a outra causa: com a anotação no lugar, mova o service para um pacote fora do da Application (ex.: br.edu.outro). Rode. Mesmo erro, motivo diferente.
  5. Traga a classe de volta para o pacote certo.
APPLICATION FAILED TO START Description: Parameter 0 of constructor in br.edu.faculdade.receitas.ReceitaController required a bean of type 'br.edu.faculdade.receitas.CatalogoService' that could not be found. Action: Consider defining a bean of type 'br.edu.faculdade.receitas.CatalogoService' in your configuration.
responda
  1. Quais três informações esse erro te dá?
  2. O erro aconteceu ao subir a aplicação ou ao chamar o endpoint? Por que isso é uma boa notícia?
  3. No passo 4 a anotação estava lá e mesmo assim falhou. Por quê?
conferir depois de responder

1. Quem pediu (ReceitaController, no construtor), o que faltou (uma classe CatalogoService que o Spring conheça) e o que fazer. Quase todo erro de dependência do Spring tem esse formato — reconhecendo o formato, você lê em cinco segundos.

2. Ao subir. E é ótimo: o Spring monta todas as ligações na hora de ligar, então esse tipo de erro aparece antes de qualquer usuário chegar, não às três da tarde com gente na tela.

3. Porque o Spring só procura classes anotadas no pacote da Application e abaixo dele. Classe fora dali é invisível, por mais anotada que esteja. Esta é a segunda causa mais comum — e a mais difícil de achar, porque a anotação está lá e parece tudo certo.

Se travar
o que apareceo que costuma ser
required a bean ... that could not be foundFaltou a anotação na classe, ou ela está fora do pacote da Application.
cannot find symbol: class ReceitaRepositoryFaltou o import, ou a classe está em outro pacote. A IDE resolve com Alt+Enter em cima do nome vermelho.
variable repositorio might not have been initializedO campo é final mas o construtor não atribui ele. Falta a linha this.repositorio = repositorio;.
Port 8080 was already in useFicou uma execução anterior de pé. Pare pelo quadrado vermelho da IDE.
O endpoint responde [] vazioA regra do service filtrou tudo. Confira os valores da sua lista no repository — o filtro está certo, os dados é que não batem.
404 Not Found no navegadorO endereço do @GetMapping não é o que você digitou. Compare os dois, caractere por caractere.

📦 Entrega de hoje — atividade 1

No fim da aula, suba o link do repositório com o projeto contendo:

  • As três classes separadas, cada uma com a sua anotação.
  • O endpoint respondendo a lista filtrada pela sua regra.
  • Nenhum new entre as suas classes, e todo campo de dependência final.
  • Um arquivo RESPOSTAS.md na raiz, com as suas respostas às perguntas dos quatro labs.

Isto não é o projeto. Os quatro labs são treino individual, no seu projetinho da aula 01. O projeto da disciplina — o Leque de Vagas, em equipe — começa no desafio desta aula.
