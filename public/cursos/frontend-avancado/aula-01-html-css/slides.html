parte 1 · 40 min

HTML não é enfeite

o problema · e você já escreveu isso

A sopa de div

😖 o que costuma aparecer
<div class="topo"> <div class="titulo">Leque de Eventos</div> <div class="menu"> <div onclick="ir()">Eventos</div> </div> </div> <div class="card"> <div class="card-titulo">Meetup #42</div> </div>
✅ o mesmo, com significado
<header> <h1>Leque de Eventos</h1> <nav> <a href="/eventos">Eventos</a> </nav> </header> <article> <h2>Meetup #42</h2> </article>

Os dois renderizam igual. Um deles é utilizável por quem não enxerga a tela — e é o mesmo que o Google entende, que o leitor de tela navega e que a próxima pessoa do time lê sem abrir o CSS.

a ideia · por que isso importa de verdade

Três razões, e nenhuma é estética

Acessibilidade

Leitor de tela navega por landmarks e títulos. Sem eles a pessoa tem que ouvir a página inteira, do começo, toda vez.

Comportamento grátis

<button> já responde a Enter e Espaço, entra na ordem do Tab e avisa que é botão. Uma div não faz nada disso.

Manutenção

<article> diz o que a coisa é. class="card" diz como ela parece — e parecer muda toda hora.

E tem a razão que vale pro resto do curso: framework facilita errar isso. Quando cada pedacinho da tela é um componente isolado, é fácil perder a noção da estrutura do documento inteiro.

html · o esqueleto da página

Os landmarks

São as regiões que um leitor de tela lista pra pessoa pular direto pro que interessa. São só estes:

ElementoO que marcaQuantos por página
<header>topo do site ou de um artigo1 no nível da página
<nav>bloco de navegaçãovários — dê aria-label a cada um
<main>o conteúdo principalexatamente 1
<aside>conteúdo relacionado, secundárioquantos precisar
<footer>rodapé do site ou de um artigo1 no nível da página
<section>seção temática — só vale com títuloquantas precisar

Erro clássico: usar <section> como se fosse <div>. Section sem um título dentro não vira landmark e não ajuda ninguém — nesse caso, use <div> mesmo, sem culpa.

html · a segunda forma de navegar

Títulos são um índice

Não faça

<h1>Leque de Eventos</h1> <h4>Próximos</h4> ← pulou h2 e h3 <h3>Meetup #42</h3>

Escolher o nível pelo tamanho da fonte. Tamanho é CSS.

Faça

<h1>Leque de Eventos</h1> <h2>Próximos eventos</h2> <h3>Meetup #42</h3> <h3>Workshop de CSS</h3>

Escolher pelo aninhamento lógico. Sem pular níveis.

Um <h1> por página, e nunca pule níveis. Pessoas que usam leitor de tela navegam saltando de título em título — a hierarquia é literalmente o índice do documento.

html · onde mais se erra

Formulário acessível em 4 regras

📄 busca de eventos
<form role="search"> 1. todo campo tem label ligada por id <label for="q">Buscar eventos</label> <input id="q" name="q" type="search" 2. type e autocomplete certos = teclado certo no celular autocomplete="off" 3. erro anunciado, não só pintado de vermelho aria-describedby="q-erro" /> <p id="q-erro">Digite ao menos 3 letras.</p> 4. button de verdade, com type explícito <button type="submit">Buscar</button> </form>

Placeholder não é label. Ele some quando a pessoa digita, tem contraste baixo por padrão e alguns leitores de tela ignoram. Se você só tem espaço pro placeholder, use <label> visualmente escondida — nunca ausente.

html · dois detalhes que valem no projeto

Imagem e data

alt que serve

decorativa: alt vazio, e o leitor pula <img src="onda.svg" alt="" /> informativa: descreva a FUNÇÃO <img src="mapa.png" alt="Local: Rua X, 200, Recife" />

Nunca "imagem de", nunca o nome do arquivo.

data que a máquina lê

<time datetime="2026-09-12T19:00"> 12 de setembro, 19h </time>

A pessoa lê "12 de setembro". O buscador e o "adicionar à agenda" leem o datetime.

No Leque de Eventos as duas coisas aparecem em toda tela: o card do evento tem data, e a página de detalhe tem imagem. Comece certo — reescrever isso depois, em componente, custa muito mais.

mão na massa · 3 minutos, agora

Solte o mouse

Abra qualquer página que você já fez. Navegue só com Tab, Shift+Tab e Enter.

Dá pra chegar em tudo?

Todo link e botão precisa ser alcançável.

Dá pra ver onde você está?

Se sumiu o contorno, alguém escreveu outline: none.

A ordem faz sentido?

Ela segue o HTML — não o que o CSS mostra na tela.

Este é o teste mais barato de acessibilidade que existe, e ele entra na rubrica do projeto, em todas as entregas.

parte 2 · 45 min

CSS: layout de verdade

css · a pergunta que resolve 90% dos casos

Flexbox ou Grid?

Flexbox — uma direção

O conteúdo manda no tamanho. Use quando os itens estão em linha ou em coluna e você quer distribuir espaço entre eles.

Barra de navegação, grupo de botões, um chip ao lado do outro.

Grid — duas direções

O container manda no tamanho. Use quando existe alinhamento em linhas E colunas, ou quando você desenha a página inteira.

Galeria de cards, layout da página, formulário em duas colunas.

Regra de bolso: o conteúdo decide → Flex. Você decide → Grid.

E eles se combinam o tempo todo: a página em Grid, e cada card por dentro em Flex. Não é escolher um time.

live code · a galeria de eventos

Uma linha que substitui 3 media queries

🎨 a listagem do projeto
.lista-eventos { display: grid; gap: 1.5rem; /* o coração disto: */ grid-template-columns: repeat(auto-fit, minmax(280px, 1fr)); }
  • auto-fit — encaixe quantas colunas couberem
  • minmax(280px, 1fr) — cada uma com no mínimo 280px, e o resto do espaço dividido igual
  • Resultado: 1 coluna no celular, 2 no tablet, 4 no monitor — sem uma media query sequer

Isso é responsividade que reage ao espaço disponível, não a uma lista de larguras de aparelho que você tentou adivinhar. Bem mais robusto.

css · tamanho que se vira sozinho

clamp: mínimo, ideal, máximo

h1 { /* nunca menor ideal (cresce) nunca maior */ font-size: clamp(1.75rem, 4vw + 1rem, 3.5rem); } .conteudo { width: min(100% - 2rem, 70ch); /* margem OU largura máxima */ margin-inline: auto; }

clamp()

Tipografia que acompanha a tela sem quebrar nos extremos.

min()

"O menor entre os dois" — largura com margem garantida.

ch

Largura em caracteres. 60 a 75ch é a faixa legível de um parágrafo.

Repare no margin-inline em vez de margin-left/right: são as propriedades lógicas, que funcionam também em idioma escrito da direita pra esquerda.

css · o pulo do gato pra componente

O card que enxerga o próprio espaço

Media query pergunta o tamanho da janela. Mas o card não se importa com a janela — ele se importa com o espaço que ele recebeu.

.lista-eventos { container-type: inline-size; /* "meço meus filhos por mim" */ } /* quando o CARD tiver 400px — não a tela */ @container (min-width: 400px) { .card-evento { grid-template-columns: 120px 1fr; /* imagem ao lado */ } }

É a ferramenta pra quem escreve componente. O mesmo card fica empilhado na barra lateral estreita e lado a lado no meio largo da página — sem saber onde foi colocado. Isso importa muito no Angular e no Next.

parte 3 · 25 min

CSS como sistema

css · pare de repetir cor no código

Custom properties são tokens

:root { /* a paleta, num lugar só */ --cor-fundo: #0d0b14; --cor-texto: #f3f0fa; --cor-marca: #7B4FD0; /* escala de espaço: nada de 13px, 17px, 22px soltos */ --esp-1: .5rem; --esp-2: 1rem; --esp-3: 1.5rem; --raio: 12px; } .card-evento { background: var(--cor-fundo); padding: var(--esp-3); border-radius: var(--raio); }

Não é só economia de digitação: é o que permite trocar o tema inteiro mudando um bloco — e é exatamente o mecanismo que a próxima tela usa.

css · tema em 6 linhas

Claro e escuro, de verdade

/* 1. o padrão é o claro */ :root { --cor-fundo: #ffffff; --cor-texto: #18181b; } /* 2. quem prefere escuro, recebe escuro */ @media (prefers-color-scheme: dark) { :root { --cor-fundo: #0d0b14; --cor-texto: #f3f0fa; } } /* 3. e quem escolheu na mão, manda em cima dos dois */ :root[data-tema="dark"] { --cor-fundo: #0d0b14; }

Nenhum componente sabe que existe tema. Todos usam var(--cor-fundo) e pronto. É esse desacoplamento que faz o tema ser barato — e é requisito do desafio de hoje.

css · o fim do !important

@layer: a cascata sob controle

O problema clássico: você escreve uma regra, ela não aplica, e a solução vira !important — que gera o próximo !important.

/* declare a ordem UMA vez, no topo do arquivo */ @layer reset, base, componentes, utilitarios; @layer base { a { color: var(--cor-marca); } } @layer componentes { .card-evento a { color: var(--cor-texto); } }

Quem vem depois na lista de camadas vence — mesmo com seletor mais fraco. A especificidade deixa de ser uma corrida.

Camadas ganham de tudo dentro delas, mas CSS fora de qualquer camada ainda ganha das camadas. Por isso vale colocar tudo em camadas, ou nada.

css · o seletor que faltava há 20 anos

:has() — estilizar o pai

/* card que TEM selo de gratuito ganha borda verde */ .card-evento:has(.selo-gratuito) { border-color: var(--cor-ok); } /* o campo cujo input está inválido E já foi tocado */ .campo:has(input:invalid:not(:placeholder-shown)) { border-color: var(--cor-erro); } /* a lista que NÃO tem nenhum item = estado vazio */ .lista-eventos:not(:has(.card-evento)) { display: grid; place-items: center; }

Antes disso, cada um desses casos exigia JavaScript pra adicionar uma classe. Hoje é CSS — e continua funcionando mesmo se o JavaScript falhar.

css · sem pré-processador

Aninhamento é nativo agora

🎨 CSS puro, hoje
.card-evento { padding: var(--esp-3); & h3 { margin-block-end: .5rem; } &:hover { border-color: var(--cor-marca); } @media (width >= 48rem) { padding: var(--esp-4); } }

O que você ganha

Sass e Less deixam de ser obrigatórios só pra ter aninhamento. Um passo de build a menos.

O que você arrisca

Aninhar 5 níveis gera seletor gigante e específico demais. Vá até 2, no máximo 3.

Repare também no @media (width >= 48rem) — a sintaxe de comparação, bem mais legível que min-width. E em rem, não px: assim o layout respeita quem aumentou a fonte do navegador.

css · o problema que os frameworks resolvem

Tudo é global. E isso dói.

Você escreve .card { padding: 1rem } numa página. Três meses depois, outra pessoa escreve .card em outro arquivo. Uma das duas telas quebra, e ninguém sabe qual até alguém reclamar.

A gambiarra histórica

Convenção de nome tipo BEM: card-evento__titulo--destaque. Funciona, e é feio.
