HTML e CSS: a base

Uma revisão com a régua alta. Não é "o que é uma tag" — é por que a escolha da tag muda o comportamento do navegador, e como escrever CSS que continua fazendo sentido no arquivo número duzentos.

🎯 O que esta aula assume. Que você já escreveu HTML e CSS antes e já montou uma página inteira. O que muda aqui é a régua: a partir de hoje, não basta ficar parecido com o desenho — precisa funcionar no teclado, fazer sentido pra quem não enxerga a tela, e não quebrar quando outra pessoa mexer.

O dicionário desta aula

As palavras que vão aparecer o tempo todo daqui pra frente.

PalavraO que é
Semântica Escolher a tag pelo significado do conteúdo, não pela aparência. <button> porque é um botão — não porque quero um retângulo clicável.
Landmark Uma região da página que a tecnologia assistiva reconhece e lista, pra pessoa pular direto pra ela. <main>, <nav>, <header>.
Leitor de tela Programa que lê a página em voz alta. Ele não vê o layout: navega pela estrutura do HTML.
Foco O elemento que está selecionado no momento pelo teclado. Anda com Tab, e precisa ser visível.
ARIA Atributos que completam a informação para tecnologia assistiva (aria-label, aria-describedby). Complementam o HTML — nunca substituem a tag certa.
Cascata As regras que o navegador usa pra decidir qual CSS vence quando duas regras atingem o mesmo elemento.
Especificidade O peso de um seletor nessa disputa. #id vence .classe, que vence div.
Token Um valor de design com nome, guardado num só lugar e reusado: --cor-marca, --esp-2.
Escopo de estilo O alcance de uma regra CSS. Em CSS puro é sempre a página inteira — e é isso que dá problema.
Baseline Termo da web pra dizer que um recurso já é seguro de usar em todos os navegadores atuais. Tudo nesta aula é.

Por que semântica importa

Todo mundo já ouviu "use HTML semântico". Quase ninguém ouviu por quê, e sem o porquê a regra não sobrevive ao primeiro prazo apertado.

São três motivos, e nenhum deles é estético.

1. É como quem não enxerga navega

Um leitor de tela não mostra a página: lê. Se a pessoa tivesse que ouvir tudo do começo toda vez, seria inviável. Então ela usa atalhos: listar as regiões da página, listar os títulos, listar os links.

Esses atalhos são construídos a partir das suas tags. Sem <main>, não existe "pular para o conteúdo principal". Sem <h2>, não existe índice.

2. Você ganha comportamento de graça

Compare o que cada um faz sem nenhuma linha de JavaScript:

<button>

  • Entra na ordem do Tab
  • Dispara com Enter e Espaço
  • Anunciado como "botão"
  • Ganha estado desabilitado
  • Envia formulário

<div onclick>

  • Invisível pro teclado
  • Ignora Enter e Espaço
  • Anunciado como… nada
  • Não tem estado
  • Não envia nada

Para empatar com o <button>, a <div> precisa de tabindex="0", role="button", listener de clique, listener de teclado tratando duas teclas, e gestão de estado. Cinco coisas para reimplementar, mal, o que já vinha pronto.

3. Descreve o que a coisa é, não como parece

<article> continua verdadeiro depois do redesign. class="card-azul" vira mentira no dia em que o card fica verde.

E o motivo que vale pro resto do curso. Framework facilita errar isso. Quando cada pedaço da tela é um componente isolado, ninguém mais enxerga o documento inteiro — e aí aparecem três <h1> na mesma página, cada um dentro de um componente que parecia certo sozinho. Na aula 03 e na 10 eu volto nisso.

O link "pular para o conteúdo"

Sem ele, quem usa teclado passa por todos os links do menu antes de chegar no conteúdo — em toda página, toda vez. Ele fica escondido até receber foco:

.pular {
  position: absolute;
  left: -9999px;
}
.pular:focus {
  left: 1rem;
  top: 1rem;
}
O erro mais comum com section. Usar <section> onde caberia <div>. Section sem título não vira landmark, não ajuda ninguém e ainda polui a árvore de acessibilidade. Se não tem título, use <div> — ela existe justamente pra isso, e não tem nada de errado com ela.

Hierarquia de títulos

Os títulos formam o índice do documento. Quem usa leitor de tela navega saltando entre eles, e é assim que a pessoa entende a estrutura da página sem ver o layout.

Duas regras, e só:

  • Um <h1> por página, dizendo do que a página trata
  • Nunca pule níveis descendo: de h2 vai pra h3, jamais direto pra h4

Errado

<!-- escolhido pelo tamanho -->
<h1>Leque de Eventos</h1>
  <h4>Próximos</h4>
<h3>Meetup #42</h3>

Certo

<!-- escolhido pelo aninhamento -->
<h1>Leque de Eventos</h1>
  <h2>Próximos eventos</h2>
    <h3>Meetup #42</h3>
Se o tamanho está errado, o problema é do CSS. Nunca escolha <h4> porque "h2 fica grande demais". Escolha o nível certo e ajuste com font-size. Nível é estrutura, tamanho é aparência — e é justamente isso que a gente está separando hoje.

Listas, artigos e o resto

Lista é lista

A listagem de eventos é uma lista. Envolver em <ul> faz o leitor de tela anunciar "lista com 8 itens" — informação que a pessoa usa pra decidir se vale percorrer.

<ul class="lista-eventos">
  <li>
    <article class="card-evento"> … </article>
  </li>
</ul>
E o CSS não atrapalha. list-style: none tira as bolinhas sem tirar a semântica. Colocar display: grid no <ul> também está perfeitamente ok.

article ou div?

O teste é simples: esse pedaço faz sentido sozinho, fora da página? Um card de evento, se você o mandasse isolado pra alguém, ainda se explicaria — então é <article>. Um wrapper que existe só pra posicionar duas coisas é <div>.

Botão ou link?

UseQuandoExemplo no projeto
<a href>Leva pra outro lugar. Muda a URL.Abrir o detalhe do evento
<button>Faz alguma coisa aqui mesmo.Abrir filtro, alternar tema
O sinal de que está errado: se você precisa de href="#", provavelmente era um botão. Se você precisa de onclick que troca de página, provavelmente era um link.

Formulários acessíveis

É onde mais se erra, e onde o erro mais atrapalha — porque formulário é onde a pessoa precisa fazer alguma coisa, não só ler.

Toda entrada precisa de label

<!-- ligadas por for/id: clicar no texto foca o campo -->
<label for="cidade">Cidade</label>
<input id="cidade" name="cidade" type="text" />
Placeholder não é label. Ele some quando a pessoa começa a digitar (justo quando ela precisaria conferir), tem contraste baixo e não é lido por todo leitor de tela. Se o desenho não tem espaço pro rótulo, esconda a label visualmente — nunca a remova.
/* esconde da tela, mantém pro leitor de tela */
.so-leitor {
  position: absolute;
  width: 1px; height: 1px;
  padding: 0; margin: -1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
}

O type certo muda o teclado do celular

typeO que a pessoa ganha
emailTeclado com @ à mão
telTeclado numérico grande
searchBotão de limpar, tecla "buscar"
urlTeclado com .com
datetime-localSeletor nativo de data e hora
E autocomplete economiza a vida. autocomplete="email", "name", "street-address" deixam o navegador preencher. Numa tela de cadastro, é a diferença entre trinta segundos e três minutos.

Erro precisa ser anunciado

Pintar a borda de vermelho não informa quem não enxerga cor — e quem não enxerga nada.

<label for="email">E-mail</label>
<input id="email" type="email"
       aria-describedby="email-erro"
       aria-invalid="true" />
<p id="email-erro">Formato inválido. Exemplo: nome@site.com</p>
  • aria-describedby — liga a mensagem ao campo
  • aria-invalid — diz que este campo está com erro
  • A mensagem diz como corrigir, não só que está errado

Agrupe o que é um grupo

<fieldset>
  <legend>Formato do evento</legend>
  <label><input type="radio" name="formato" /> Presencial</label>
  <label><input type="radio" name="formato" /> Online</label>
</fieldset>

Sem o <fieldset>, o leitor anuncia "Presencial, botão de opção" sem dizer de que pergunta aquilo é resposta.

Imagem, data e mídia

alt: descreva a função, não a figura

SituaçãoO que escrever
Decorativa (onda, textura)alt="" — vazio de propósito, o leitor pula
InformativaO que ela comunica: alt="Mapa: Rua X, 200"
Dentro de um linkPara onde o link leva: alt="Ver perfil do React Recife"
Já explicada no texto ao ladoalt="" — repetir só atrapalha
Nunca escreva "imagem de". O leitor de tela já anuncia que é imagem. E nunca deixe sem alt: sem o atributo, alguns leitores leem o nome do arquivo — e ninguém merece ouvir "IMG underscore 2026 underscore final v3 ponto png".

Datas que a máquina entende

<time datetime="2026-09-12T19:00">12 de setembro, 19h</time>

A pessoa lê o texto; o buscador e integrações de agenda leem o atributo. No projeto, todo card de evento tem data — comece com <time> desde a entrega 0.

Imagem que não empurra o layout

<img src="capa.jpg" alt=""
     width="800" height="450"
     loading="lazy" decoding="async" />
  • width e height — o navegador reserva o espaço e a página não "pula" quando a imagem carrega
  • loading="lazy" — só baixa quando estiver perto da tela. Não use na imagem principal do topo
Aquele "pulo" tem nome — layout shift — e é uma das métricas de performance que o Google mede. Volta com todas as letras na aula 14.

O teste do teclado

O teste de acessibilidade mais barato que existe, e o que mais pega problema. Solte o mouse e navegue com Tab, Shift+Tab, Enter e Espaço.

  1. Chego em tudo? Todo link, botão e campo precisa ser alcançável
  2. Vejo onde estou? Se o contorno sumiu, alguém escreveu outline: none
  3. A ordem faz sentido? Ela segue o HTML, não a posição visual
  4. Consigo sair? Nada pode prender o foco
O crime mais comum do CSS. *:focus { outline: none } — escrito porque "fica feio". Isso torna o site inutilizável por teclado. Se não gosta do contorno padrão, troque, não apague:
/* :focus-visible só aparece pra quem navega por teclado */
:focus-visible {
  outline: 2px solid var(--cor-marca);
  outline-offset: 2px;
  border-radius: 4px;
}

:focus-visible é a solução elegante: o contorno aparece pra quem usa Tab e não aparece no clique de mouse — que era a reclamação original.

Isso vale nota. A navegação por teclado está na rubrica do projeto, em todas as seis entregas. É comum o projeto nascer acessível e ir perdendo isso quando os componentes chegam.

Flexbox ou Grid

A dúvida mais recorrente do CSS, e ela tem resposta.

Flexbox — uma direção

Os itens ficam em linha ou em coluna, e o espaço se distribui entre eles. O conteúdo decide o tamanho.

Barra de navegação, grupo de botões, chips de filtro, o rodapé de um card.

Grid — duas direções

Existe alinhamento em linhas e colunas ao mesmo tempo. Você decide o tamanho, no container.

Galeria de cards, layout da página inteira, formulário em duas colunas.

Regra de bolso: o conteúdo decide → Flex. Você decide → Grid.

Não é escolher um time. O normal é a página em Grid e cada card, por dentro, em Flex. Eles foram feitos pra conviver.

Grid na prática

A galeria que se vira sozinha

.lista-eventos {
  display: grid;
  gap: var(--esp-3);
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
}

Uma linha, e nenhuma media query:

  • auto-fit — crie quantas colunas couberem
  • minmax(280px, 1fr) — cada coluna tem no mínimo 280px; o espaço que sobrar é dividido igualmente

Celular estreito: 1 coluna. Tablet: 2. Monitor: 4. Sem você listar nenhuma largura de aparelho.

auto-fit ou auto-fill? Com poucos itens, auto-fit faz eles esticarem pra ocupar a linha; auto-fill mantém colunas vazias e os itens no tamanho mínimo. Para galeria, quase sempre auto-fit.

Layout da página com áreas nomeadas

.pagina {
  display: grid;
  min-height: 100dvh;
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "cabecalho"
    "conteudo"
    "rodape";
}

header { grid-area: cabecalho; }
main   { grid-area: conteudo; }
footer { grid-area: rodape; }

O 1fr no meio faz o rodapé grudar embaixo mesmo com pouco conteúdo — sem position: absolute, sem cálculo de altura.

Repare no 100dvh. O vh tradicional conta a barra de endereço do celular e gera aquele corte estranho. dvh acompanha a altura que realmente está visível.

Tamanho fluido: clamp e min

h1 {
  /*      mínimo      ideal (cresce)   máximo */
  font-size: clamp(1.75rem, 4vw + 1rem, 3.5rem);
}

.conteudo {
  width: min(100% - 2rem, 70ch);
  margin-inline: auto;
}
RecursoPra que serve
clamp(min, ideal, max)Valor que acompanha a tela mas nunca sai da faixa
min(a, b)O menor dos dois — largura com margem garantida
chLargura em caracteres. 60–75ch é a faixa legível
margin-inlineMargem horizontal, respeitando o sentido da escrita
Use rem, não px, em tipografia e media query. Quem aumentou a fonte padrão do navegador — por baixa visão, por exemplo — só é atendido se você usar unidade relativa. Com px, o ajuste da pessoa é simplesmente ignorado.
Propriedades lógicas. margin-inline, padding-block, inset substituem left/right/top/bottom e funcionam em qualquer direção de escrita. Custa o mesmo e já deixa o projeto pronto pra internacionalização.

Container queries

O recurso mais importante desta aula pra quem vai escrever componente — e é por isso que ele aparece antes de Angular e Next.

O problema: media query pergunta o tamanho da janela. Mas um card não se importa com a janela. Ele se importa com o espaço que recebeu. O mesmo card pode estar numa barra lateral de 300px ou no meio da página com 900px — e a janela é a mesma nos dois casos.

/* 1. o pai declara que é um container mensurável */
.lista-eventos {
  container-type: inline-size;
  container-name: lista;
}

/* 2. o filho reage ao tamanho DO PAI, não da tela */
@container lista (min-width: 400px) {
  .card-evento {
    grid-template-columns: 120px 1fr;
  }
}
@media@container
MedeA janela do navegadorO elemento pai
Serve praLayout geral da páginaComponente reutilizável
O componente precisa saber onde está?SimNão
Por que isso muda tudo com framework. Um componente de card é escrito uma vez e usado em cinco lugares de larguras diferentes. Com media query você acaba criando variações (card--estreito, card--largo) e passando prop pra escolher. Com container query o card se resolve sozinho, onde quer que seja colocado.
Pegadinha: container-type: inline-size faz o elemento medir a si mesmo — e um elemento não pode depender do tamanho do próprio conteúdo pra isso. Se o container "sumir" ou colapsar, é quase sempre isso. Declare o container no pai do que você quer estilizar, nunca no próprio elemento.

Custom properties como tokens

Um token é um valor de design com nome. Em vez de espalhar #7B4FD0 por quarenta lugares, você o declara uma vez.

:root {
  /* cor */
  --cor-fundo: #ffffff;
  --cor-superficie: #f4f4f5;
  --cor-texto: #18181b;
  --cor-marca: #7B4FD0;

  /* escala de espaço — nada de 13px, 17px, 22px soltos */
  --esp-1: .5rem;
  --esp-2: 1rem;
  --esp-3: 1.5rem;
  --esp-4: 2.5rem;

  /* forma */
  --raio: 12px;
  --borda: 1px solid rgb(0 0 0 / .1);
}

E o uso:

.card-evento {
  background: var(--cor-superficie);
  padding: var(--esp-3);
  border-radius: var(--raio);
}

Elas cascateiam — e isso é o truque

Diferente de variável de Sass, custom property é viva no navegador e herda. Você pode redefinir num pedaço da árvore:

.card-evento.destaque {
  --cor-superficie: #faf5ff;   /* só aqui dentro */
}
Valor padrão: var(--x, 1rem) usa 1rem se --x não existir. Ótimo pra escrever componente que funciona mesmo sem o tema carregado.
Nomeie pelo papel, não pela aparência. --cor-marca sobrevive ao redesign; --roxo vira mentira no dia em que a marca fica verde. Vale a mesma lógica de escolher <article> em vez de class="card-azul".

Tema claro e escuro

Com tokens no lugar, o tema custa poucas linhas — e nenhum componente precisa saber que ele existe.

/* 1. o padrão */
:root {
  color-scheme: light dark;
  --cor-fundo: #ffffff;
  --cor-texto: #18181b;
}

/* 2. quem prefere escuro no sistema */
@media (prefers-color-scheme: dark) {
  :root {
    --cor-fundo: #0d0b14;
    --cor-texto: #f3f0fa;
  }
}

/* 3. e a escolha manual vence os dois */
:root[data-tema="dark"] {
  --cor-fundo: #0d0b14;
  --cor-texto: #f3f0fa;
}
:root[data-tema="light"] {
  --cor-fundo: #ffffff;
  --cor-texto: #18181b;
}

Os componentes seguem usando var(--cor-fundo) e não mudam uma linha. Esse desacoplamento é o ponto — não o tema em si.

color-scheme: light dark não é enfeite. Ele faz o navegador adaptar o que você não controla: barra de rolagem, campos de formulário nativos, seletor de data. Sem ele, você tem um site escuro com um <input> branco brilhante.
Contraste continua valendo nos dois temas. Texto normal precisa de 4.5:1 contra o fundo. Uma combinação que passa no claro pode falhar no escuro — teste os dois. O DevTools mostra a razão de contraste quando você inspeciona uma cor.

@layer

A cena clássica: você escreve uma regra, ela não aplica, e a saída vira !important — que obriga o próximo !important, e em seis meses ninguém sabe mais quem manda em quê.

A causa é a especificidade: .pagina .lista .card a ganha de .card a, mesmo que a segunda seja mais recente e mais correta.

@layer resolve isso deixando você declarar a ordem de prioridade antes de escrever qualquer regra:

/* declare a ordem UMA vez, no topo. só isso já define tudo */
@layer reset, base, componentes, utilitarios;

@layer base {
  a { color: var(--cor-marca); }
}

@layer componentes {
  /* seletor mais fraco, mas vence: a camada é posterior */
  .card-evento a { color: var(--cor-texto); }
}

@layer utilitarios {
  .texto-suave { color: var(--cor-texto-2); }
}

Quem está numa camada posterior vence, independente da especificidade. A disputa deixa de ser uma corrida de seletor.

A regra que confunde: CSS fora de qualquer camada vence todas as camadas. Isso é proposital — deixa você sobrescrever uma biblioteca em camadas com um CSS avulso. Mas significa que misturar os dois estilos dá confusão: coloque tudo em camadas, ou nada.
Onde isso brilha: importar CSS de terceiro dentro de uma camada — @import url(lib.css) layer(vendor) — e pronto: o seu CSS ganha da biblioteca inteira sem um !important sequer.

:has() e aninhamento

:has() — o seletor de pai

Por vinte anos o CSS só descia na árvore. :has() permite estilizar um elemento pelo que existe dentro dele.

/* card que TEM selo de gratuito */
.card-evento:has(.selo-gratuito) {
  border-color: var(--cor-ok);
}

/* o campo cujo input está inválido — e que a pessoa já preencheu */
.campo:has(input:invalid:not(:placeholder-shown)) {
  border-color: var(--cor-erro);
}

/* lista sem nenhum card = estado vazio */
.lista-eventos:not(:has(.card-evento)) {
  display: grid;
  place-items: center;
  min-height: 40vh;
}

Cada um desses casos exigia JavaScript pra adicionar uma classe. Agora é CSS, e continua funcionando se o JavaScript falhar.

O truque do :not(:placeholder-shown). Sozinho, :invalid pinta o campo de vermelho antes de a pessoa digitar qualquer coisa, o que é hostil. Combinado assim, o erro só aparece depois que ela mexeu no campo.

Aninhamento nativo

Sem Sass, sem passo de build:

.card-evento {
  padding: var(--esp-3);
  border-radius: var(--raio);

  & h3 { margin-block-end: var(--esp-1); }

  &:hover { border-color: var(--cor-marca); }

  @media (width >= 48rem) {
    padding: var(--esp-4);
  }
}
Vá até 2 níveis, no máximo 3. Aninhar fundo gera seletores enormes e específicos demais — exatamente o problema que @layer veio resolver. Aninhamento é conveniência de escrita, não licença pra criar .a .b .c .d .e.
Repare em @media (width >= 48rem): a sintaxe de comparação, mais legível que min-width. E em margin-block-end, a versão lógica de margin-bottom.

O problema do escopo

Esta seção existe pra plantar uma pergunta que volta na aula 03 e na aula 10.

Em CSS puro, toda regra é global. Você escreve .card { padding: 1rem } pensando na listagem de eventos. Três meses depois, outra pessoa escreve .card pensando no perfil do organizador. Uma das duas telas quebra — e ninguém descobre até alguém reclamar.

Não é falta de cuidado: é uma característica da linguagem. As saídas historicamente foram:

AbordagemComo funcionaO custo
Convenção de nome (BEM).card-evento__titulo--destaqueFunciona, mas é manual e verboso
Estilo no componente (Angular)O framework reescreve os seletores pra valerem só aliPrecisa do framework
CSS Modules (Next)O build gera nomes únicos: .card_a3f9Precisa do passo de build
@scope (CSS nativo)Delimita onde as regras valem, sem ferramentaAinda chegando aos navegadores
Guarde esta seção. Na aula 03, quando o Angular isolar o CSS do componente automaticamente, e na aula 10, quando o Next fizer o mesmo por outro caminho, a pergunta vai ser: que problema isso resolve? É este. Quem entende o problema entende a solução em cinco minutos; quem não entende decora sintaxe.

No desafio de hoje vocês vão sentir isso na mão: três telas, um arquivo de CSS, e a necessidade de inventar uma convenção de nome pra não colidir.

Erros comuns 🔧

O foco sumiu quando navego por Tab

Alguém escreveu outline: none. Troque por um :focus-visible com contorno próprio — nunca simplesmente remova.

Meu @container não faz nada

Duas causas: faltou container-type: inline-size no pai, ou você declarou o container no próprio elemento que está tentando estilizar. Ele mede o ancestral.

A regra certa não aplica e eu apelei pro !important

É especificidade. Em vez do !important, organize em @layer — ou reduza o seletor que está ganhando, que normalmente é longo demais.

O grid não quebra em coluna única no celular

Provavelmente o mínimo do minmax() é maior que a tela. minmax(280px, 1fr) numa tela de 320px com padding não cabe. Use minmax(min(280px, 100%), 1fr).

A página "pula" enquanto carrega

Imagem sem width e height. Declare os dois, mesmo usando CSS pra redimensionar.

Meu site escuro tem inputs brancos

Faltou color-scheme: light dark no :root. Os controles nativos não seguem as suas variáveis.

Zoom no celular quando toco num campo

O iOS dá zoom em campo com fonte menor que 16px. Use no mínimo 1rem nos inputs.

100vh corta o conteúdo no celular

A barra de endereço entra na conta. Use 100dvh.

O leitor de tela lê o nome do arquivo da imagem

A imagem está sem alt. Se for decorativa, o certo é alt="" — vazio, mas presente.

Cola rápida

/* ---------- estrutura da página ---------- */
<header> <nav aria-label="…"> <main> <aside> <footer>
<section>  só com título
<article>  faz sentido sozinho
<div>      sem significado — e tudo bem

/* ---------- títulos ---------- */
1 <h1> por página · nunca pule níveis · nível é estrutura, tamanho é CSS

/* ---------- formulário ---------- */
<label for="x"> + <input id="x">      sempre
type / autocomplete corretos           teclado certo no celular
aria-describedby + aria-invalid        erro anunciado
<fieldset> + <legend>                  grupo de opções

/* ---------- layout ---------- */
conteúdo decide o tamanho  → flex
você decide o tamanho      → grid

grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
grid-template-rows: auto 1fr auto;      rodapé no fim

/* ---------- tamanho fluido ---------- */
font-size: clamp(1.75rem, 4vw + 1rem, 3.5rem);
width: min(100% - 2rem, 70ch);
min-height: 100dvh;                     não 100vh

/* ---------- componente que se resolve ---------- */
.pai  { container-type: inline-size; }
@container (min-width: 400px) { .filho { … } }

/* ---------- sistema ---------- */
:root { --cor-marca: …; --esp-2: 1rem; --raio: 12px; }
color-scheme: light dark;
@media (prefers-color-scheme: dark) { :root { … } }
@layer reset, base, componentes, utilitarios;

/* ---------- seletores novos ---------- */
.card:has(.selo)                        estiliza o pai
.campo:has(input:invalid:not(:placeholder-shown))
:focus-visible                          foco só no teclado

1. essa tag descreve o que a coisa É?     → semântica
2. isso funciona só com o teclado?        → acessibilidade
3. esse valor se repete?                  → token
