Uma entrega nota cheia 🧱

O desafio resolvido por uma equipe. O código é curto e não tem nada de exótico — o que separa esta entrega de uma mediana é o README, que justifica cada escolha, e o fato de as decisões de acessibilidade terem sido testadas, não só escritas.

O README — 20% da nota, e o desempate dos outros 80%
README.md
# Leque de Eventos — protótipo estático (Equipe 2) Entrega 0 do projeto de Frontend Avançado. 🔗 No ar: https://equipe2.github.io/leque-de-eventos-estatico ⌨️ Vídeo da navegação por teclado: docs/teclado.mp4 (34s) ## Equipe | Pessoa | O que fez | |--------|-----------------------------------------------| | Ana | tokens.css, tema claro/escuro, contraste | | Bento | eventos.html, grid da listagem, container query| | Clara | evento.html, formulário de busca, fieldset | | Davi | index.html, cabeçalho, link pular, base.css | ## Os tokens e o critério de nome A regra que a gente combinou: nomear pelo papel, nunca pela aparência. Então `--cor-marca`, não `--roxo`; `--cor-superficie`, não `--cinza-claro`. O motivo prático apareceu na hora de fazer o tema escuro: a cor de marca precisou mudar (#6d28d9 → #a98ce0) porque o roxo original não tinha contraste suficiente sobre o fundo quase preto. Se a variável se chamasse `--roxo-6d28d9`, o nome teria virado mentira. Chamando de `--cor-marca`, o nome continuou verdadeiro e só o valor mudou. | Token | Claro | Escuro | |-------------------|----------|----------| | --cor-fundo | #ffffff | #0d0b14 | | --cor-superficie | #f4f4f5 | #161122 | | --cor-texto | #18181b | #f3f0fa | | --cor-marca | #6d28d9 | #a98ce0 | Espaçamento: só 4 valores (.5 / 1 / 1.5 / 2.5rem). A gente proibiu valor solto — quando bateu vontade de usar 18px, era sinal de que --esp-2 ou --esp-3 resolvia. ## Onde usamos @container e por quê Na `.lista-eventos`, com o card reagindo a 420px. O motivo: na home a mesma lista aparece em dois lugares — no meio da página (largo) e numa coluna lateral de "Próximos" (estreita). Com media query a gente teria que criar uma variação `.card-evento--compacto` e escolher na mão em cada lugar. Com container query o card se resolve sozinho: lado a lado no meio largo, empilhado na lateral. Mesmo HTML, zero classe extra. Isso foi o que mais impressionou a gente nesta entrega. ## Onde usamos :has() e o que ele evitou Dois lugares: 1. `.card-evento:has(.selo-gratuito)` → borda verde. Sem isso a gente precisaria adicionar uma classe `card-evento--gratuito` no HTML de cada card gratuito. Com :has(), o CSS deduz a partir do conteúdo. 2. `.lista-eventos:not(:has(.card-evento))` → estado vazio. Ainda não tem filtro (é aula 02), mas já deixamos pronto. ## O momento em que quase usamos !important Aconteceu de verdade. O link dentro do `<h3>` do card ficava roxo porque `base.css` tinha `a { color: var(--cor-marca) }`, e a nossa regra `.card-evento h3 a { color: inherit }` não ganhava — as duas tinham especificidade parecida e a ordem dos arquivos mandava. A primeira reação foi `!important`. Aí lembramos das camadas: como `base.css` está em @layer base e `componentes.css` em @layer componentes, e componentes vem depois na declaração, bastou garantir que a regra estava dentro da camada certa. Resolveu sem !important e sem aumentar o seletor. Foi aí que a gente entendeu pra que serve @layer — antes parecia burocracia. ## Contagem final: 0 !important no projeto. ## Acessibilidade — o que testamos - Tab por todas as 3 telas: chega em tudo, foco sempre visível - "Pular para o conteúdo" no primeiro Tab de cada página - Zoom 200%: nada some nem se sobrepõe - 360px: sem rolagem horizontal - Contraste conferido no DevTools nos dois temas (mín. 4.5:1) - Lighthouse acessibilidade: 100 ## O que foi mais difícil O @container. A gente colocou `container-type: inline-size` no próprio `.card-evento` e passou uns 40 minutos sem entender por que nada acontecia. O container mede o pai, não ele mesmo — um elemento não pode se medir pra decidir o próprio tamanho. Movendo a declaração pra `.lista-eventos`, funcionou de primeira. ## Pergunta que ficou pra aula 03 A gente inventou uma convenção de nome (`card-evento__capa`) pra não colidir com outras classes. Funcionou, mas é manual e verboso. O guia diz que Angular resolve isso sozinho — e a gente quer ver como.
🎯

Por que este README pontua

Quatro coisas que um README mediano não faz. Justifica com um caso real — o token não mudou de nome por teoria, mudou porque o contraste no escuro obrigou. Explica a escolha pelo problema: o container query não está lá porque foi pedido, mas porque a lista aparece em dois lugares. Conta um erro com o sintoma e a causa — quem escreveu aquele parágrafo sobre o container-type não erra de novo. E termina com uma pergunta em aberto, que é exatamente o gancho da aula 03.

css/tokens.css
@layer base {
  :root {
    color-scheme: light dark;

    --cor-fundo:      #ffffff;
    --cor-superficie: #f4f4f5;
    --cor-texto:      #18181b;
    --cor-texto-2:    #52525b;
    --cor-marca:      #6d28d9;
    --cor-ok:         #15803d;
    --cor-linha:      rgb(0 0 0 / .12);

    --esp-1: .5rem;
    --esp-2: 1rem;
    --esp-3: 1.5rem;
    --esp-4: 2.5rem;

    --raio:  12px;
    --borda: 1px solid var(--cor-linha);
    --largura-texto: 70ch;
  }

  @media (prefers-color-scheme: dark) {
    :root {
      --cor-fundo:      #0d0b14;
      --cor-superficie: #161122;
      --cor-texto:      #f3f0fa;
      --cor-texto-2:    #b4aec6;
      /* clareado de propósito: o roxo original não passava
         no contraste sobre fundo escuro */
      --cor-marca:      #a98ce0;
      --cor-ok:         #5fd08a;
      --cor-linha:      rgb(255 255 255 / .12);
    }
  }
}

css/componentes.css · listagem e container query
@layer componentes {
  .lista-eventos {
    display: grid;
    gap: var(--esp-3);
    list-style: none;
    padding: 0;
    grid-template-columns: repeat(auto-fit, minmax(min(280px, 100%), 1fr));

    /* aqui, no PAI — não no card */
    container-type: inline-size;
    container-name: lista;
  }

  .card-evento {
    background: var(--cor-superficie);
    border: var(--borda);
    border-radius: var(--raio);
    overflow: hidden;
    height: 100%;

    & h3 a { color: inherit; }
    &:hover { border-color: var(--cor-marca); }
  }

  .card-evento:has(.selo-gratuito) { border-color: var(--cor-ok); }

  @container lista (min-width: 420px) {
    .card-evento { display: grid; grid-template-columns: 140px 1fr; }
    .card-evento__capa { height: 100%; object-fit: cover; }
  }
}
Por que essa entrega funciona

Semântica de verdade

Landmarks, um h1, títulos sem pulo, lista como lista, card como article, data em <time>. O leitor de tela navega a página sem esforço.

Testou, não só escreveu

O vídeo do teclado, o zoom em 200%, o contraste conferido nos dois temas e o Lighthouse. Acessibilidade aqui é resultado medido, não intenção declarada.

CSS é sistema

Quatro espaçamentos, nenhuma cor literal fora do tokens.css, camadas organizando a cascata, e a contagem explícita: zero !important.

💡

O detalhe que eu mais valorizo

A seção "o momento em que quase usamos !important". Ela mostra uma equipe que encontrou o atrito real da cascata, resistiu ao atalho e entendeu por que a ferramenta existe. Um README que diz apenas "usamos @layer para organizar" não prova nada — este prova.

Checklist batido
  • Três telas ligadas, com 8 eventos plausíveis
  • Link pular para o conteúdo como primeiro focável
  • Um <main>, um <h1>, títulos sem pular nível
  • <ul> + <article> + <time datetime>
  • Imagens com alt adequado e width/height
  • Tokens sem cor literal fora de tokens.css, e a marca reajustada no escuro
  • color-scheme: light dark declarado
  • Grid auto-fit com min() protegendo os 320px
  • @container no pai, com justificativa real no README
  • :has() em dois lugares, com propósito
  • @layer resolvendo um conflito de verdade · zero !important
  • Teclado, zoom 200% e 360px testados, com vídeo
  • Publicado no GitHub Pages, commits de todo mundo
