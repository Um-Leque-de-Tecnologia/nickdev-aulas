README.md
# Leque de Eventos — dados e interação (Equipe 2) Entrega 1. Mesmo repositório da entrega 0. 🔗 No ar: https://equipe2.github.io/leque-de-eventos-estatico 📦 TypeScript: 6.0.3 · strict: true · 0 usos de `any` ## Equipe | Pessoa | O que fez | |--------|------------------------------------------------| | Ana | tipos.ts, eventos.json, decisões de modelagem | | Bento | api.ts, os 4 estados, tratamento de erro | | Clara | filtros.ts, busca combinada, imutabilidade | | Davi | render.ts, escapar(), tema.ts persistido | ## Por que `cidade?` e `vagas: number | null` Não são a mesma coisa, e a gente discutiu isso por uns 15 minutos até fechar: - `cidade?: string` → o campo pode não existir. Evento online não tem cidade, ponto. É ausência. - `vagas: number | null` → o campo existe sempre, e `null` quer dizer "ilimitado". É informação, não ausência. Se a gente tivesse usado `vagas?: number`, "não sabemos quantas vagas" e "vagas ilimitadas" virariam a mesma coisa na tela — e a gente mostraria "ilimitado" para um evento que só não teve o dado preenchido. A distinção evita a tela mentir. ## Onde quase mutamos a lista — e como descobrimos Aconteceu na ordenação. O primeiro `filtros.ts` terminava assim: return eventos.filter(...).sort((a, b) => ...) Funcionava. Até a gente notar um bug estranho: depois de filtrar e limpar, a ordem dos eventos tinha mudado para sempre — mesmo os que voltaram. O motivo: `sort` muta. Como `filter` já devolve um array novo, a gente achou que estava seguro — e estávamos, naquele caso. Mas num teste a gente chamou `sort` direto na lista original e ela nunca mais foi a mesma. A solução foi dupla: 1. trocar `sort` por `toSorted` 2. marcar o parâmetro como `readonly Evento[]` A segunda foi a que mais ensinou: com `readonly`, o compilador passou a RECUSAR `push` e `sort` ali dentro. A gente parou de depender de lembrar da regra — a ferramenta lembra. ## Um erro real que o strict pegou const primeiro = eventos[0]; document.title = primeiro.titulo; // ~~~~~~~~ Object is possibly 'undefined' Com `noUncheckedIndexedAccess`, `eventos[0]` é `Evento | undefined` — porque a lista pode estar vazia. A gente ia escrever `primeiro!.titulo` pra calar o erro. Aí testamos com o JSON vazio: sem a checagem, a página quebrava com "cannot read property of undefined". O erro que a gente ia silenciar era um bug de verdade. ## Os quatro estados | Estado | Como testamos | Print | |------------|------------------------------------|--------------------| | Carregando | DevTools → Network → Slow 3G | ![](docs/load.png) | | Erro | renomeamos eventos.json → .bak | ![](docs/erro.png) | | Vazio | busca por "zzzzz" | ![](docs/vazio.png)| | Com dados | normal | ![](docs/ok.png) | O vazio foi o que a gente quase esqueceu. Só percebeu testando os filtros combinados: Online + gratuito + uma busca específica dá zero resultado com facilidade, e a tela ficava totalmente em branco — parecia site quebrado. ## Decisão: js/ vai pro git O GitHub Pages não compila TypeScript, então a pasta `js/` gerada está commitada. Não é o ideal (mistura fonte e build), mas sem servidor de build é o caminho. A partir da aula 03, o Angular resolve isso. ## Acessibilidade — não regrediu Refizemos o teste do teclado depois de tudo pronto. Um problema apareceu: ao filtrar, o `innerHTML` recriava a lista e o foco voltava pro começo da página. Ainda não resolvemos direito (só garantimos que o campo de busca mantém o foco). Ficou anotado como dívida — queremos ver como o Angular lida com isso quando ele passar a controlar a renderização. ## O que foi mais difícil Entender que `filter` e `map` devolvem coisa nova mas `sort` não. Parecia arbitrário até a gente sacar a lógica: os métodos antigos mutam, e os `to*` (toSorted, toReversed, toSpliced) foram criados depois justamente pra não mutar. Agora a regra é fácil: viu `to` na frente, é seguro.
🎯

Por que este README pontua

A seção do sort descreve um bug que eles viveram — o sintoma, a investigação, a causa e as duas soluções. A do strict mostra o momento em que resistiram ao atalho: iam escrever !, testaram, e descobriram que o erro era real. A do vazio admite que quase esqueceram. E a dívida de foco fica registrada em aberto, ligada à aula seguinte — em vez de varrida pra baixo do tapete.

O código
src/filtros.ts
import type { Evento, Formato } from "./tipos.js";

export type Filtros = {
  busca: string;
  formato: Formato | "todos";
  soGratuitos: boolean;
};

export const FILTROS_VAZIOS: Filtros = {
  busca: "", formato: "todos", soGratuitos: false,
};

// readonly: o compilador recusa push/sort/splice aqui dentro.
// Foi o que resolveu o bug de ordenação que contamos no README.
export function aplicarFiltros(
  eventos: readonly Evento[],
  f: Filtros,
): Evento[] {
  const busca = f.busca.trim().toLowerCase();

  return eventos
    .filter((e) => !f.soGratuitos || e.gratuito)
    .filter((e) => f.formato === "todos" || e.formato === f.formato)
    .filter((e) =>
      busca === "" ||
      e.titulo.toLowerCase().includes(busca) ||
      e.organizador.toLowerCase().includes(busca)
    )
    .toSorted((a, b) => a.inicioEm.localeCompare(b.inicioEm));
}
src/api.ts
import type { Evento } from "./tipos.js";

export async function carregarEventos(): Promise<Evento[]> {
  const resposta = await fetch("dados/eventos.json");

  // fetch não rejeita em 404. Sem isto, o .json() abaixo
  // tentaria ler uma página de erro como JSON.
  if (!resposta.ok) {
    throw new Error(`Servidor respondeu ${resposta.status}`);
  }

  return resposta.json();
}
src/eventos-page.ts · o trecho dos estados
let todos: readonly Evento[] = [];
let filtros: Filtros = { ...FILTROS_VAZIOS };

function redesenhar(): void {
  const visiveis = aplicarFiltros(todos, filtros);

  if (visiveis.length === 0) {
    lista.innerHTML = "";
    aviso.textContent = "Nenhum evento encontrado. Tente limpar os filtros.";
    return;
  }

  aviso.textContent = `${visiveis.length} evento(s) encontrado(s)`;
  lista.innerHTML = listaHtml(visiveis);
}

async function iniciar(): Promise<void> {
  aviso.textContent = "Carregando eventos…";
  try {
    todos = await carregarEventos();
    redesenhar();
  } catch (erro) {
    console.error(erro);
    lista.innerHTML = "";
    aviso.textContent = "Não consegui carregar os eventos. Recarregue a página.";
  }
}

// filtro novo = objeto NOVO, nunca filtros.busca = ...
campoBusca.addEventListener("input", (ev) => {
  filtros = { ...filtros, busca: (ev.target as HTMLInputElement).value };
  redesenhar();
});
src/tema.ts
type Tema = "light" | "dark";

function temaSalvo(): Tema | null {
  const v = localStorage.getItem("tema");
  return v === "light" || v === "dark" ? v : null;
}

function aplicar(tema: Tema): void {
  document.documentElement.dataset.tema = tema;
  localStorage.setItem("tema", tema);
}

// sem escolha salva, o CSS segue o sistema — não sobrescrevemos
const salvo = temaSalvo();
if (salvo) aplicar(salvo);
Por que essa entrega funciona

TypeScript de verdade

strict ligado, união literal em formato, zero any, narrowing em vez de !. E o readonly transformando uma regra de disciplina em garantia do compilador.

Os quatro estados, testados

Cada um com print e com a descrição de como foi provocado. O vazio — o mais esquecido — tem seção própria contando que quase passou batido.

A base não regrediu

A semântica da entrega 0 sobreviveu ao innerHTML, o escapar() protege os dados, e o teste do teclado foi refeito no fim.

💡

O detalhe que eu mais valorizo

A dívida de foco registrada em aberto. Eles encontraram um problema real — o foco se perde quando a lista é recriada —, resolveram parcialmente e disseram isso, ligando à aula seguinte. Isso é honestidade técnica, e vale mais do que uma entrega que finge não ter arestas.

Checklist batido
  • TypeScript 6.0.3 com strict e noUncheckedIndexedAccess
  • União literal em formato e nivel, com ? e | null justificados
  • Eventos em JSON, fora do HTML
  • fetch com if (!resposta.ok) — e o erro testado de verdade
  • Cards renderizados com a semântica preservada e escapar() no texto
  • Quatro estados na tela, com print de cada um
  • Busca + 2 filtros combinando, com readonly garantindo imutabilidade
  • Detalhe pelo slug, com "não encontrado" tratado
  • Tema persistido, respeitando o sistema quando não há escolha
  • tsc --noEmit limpo · zero any · zero !
  • Teste do teclado refeito, com a dívida documentada
