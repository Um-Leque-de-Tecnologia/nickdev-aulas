JavaScript moderno

módulos · o fim do arquivo único

Cada coisa no seu arquivo

📄 dados/eventos.js
export const eventos = [ … ]; export function porSlug(slug) { return eventos.find( (e) => e.slug === slug ); }
📄 main.js
import { eventos, porSlug } from "./dados/eventos.js"; console.log(eventos.length);

No HTML: <script type="module" src="main.js"></script>. O type="module" é obrigatório — sem ele o import não existe. E módulo já vem com defer embutido e escopo próprio: nada vaza pro global.

escopo · a base de tudo que vem depois

const, let e o que fecha em volta

const eventos = []; // a LIGAÇÃO não muda… eventos.push("a"); // …mas o conteúdo sim. const ≠ imutável // closure: a função "lembra" de onde nasceu function criarContador() { let total = 0; // vive só aqui dentro return () => ++total; // e essa função guarda acesso a ela } const conta = criarContador(); conta(); conta(); // 1, depois 2

Closure não é curiosidade de entrevista. É o mecanismo por trás de estado privado, de signal() no Angular e de useState no React. Você vai encontrar isso escrito de outro jeito nas duas metades do curso.

sintaxe · a que mais aparece em código de framework

Desestruturação e spread

// tirar campos de um objeto, com apelido e valor padrão const { titulo, cidade = "Online", organizador: quem } = evento; // o resto, num objeto novo const { id, ...semId } = evento; // copiar e mudar UM campo — sem tocar no original const destacado = { ...evento, destaque: true }; // juntar listas const todos = [...gratuitos, ...pagos]; // direto no parâmetro da função function Card({ titulo, inicioEm }) { … }

A última linha é literalmente como um componente recebe dados nos dois frameworks. Se a desestruturação em parâmetro te parece estranha hoje, ela vai te atrapalhar em toda aula a partir da 04.

array · os quatro que resolvem quase tudo

map, filter, find, reduce

// map — transforma cada item. Devolve array do MESMO tamanho const titulos = eventos.map((e) => e.titulo); // filter — seleciona. Devolve array MENOR ou igual const online = eventos.filter((e) => e.formato === "Online"); // find — devolve UM item, ou undefined const achado = eventos.find((e) => e.slug === slug); // reduce — reduz a lista a um valor só const vagasTotais = eventos.reduce((soma, e) => soma + e.vagas, 0); // e eles se encadeiam const nomesGratis = eventos .filter((e) => e.gratuito) .map((e) => e.titulo);

Todos devolvem coisa nova; nenhum altera o original. Guarde isso — é o assunto do próximo slide, e é o motivo de eles dominarem código de interface.

o conceito que sustenta framework reativo

Por que não alterar o original

Mutação

lista.push(novo); lista.sort(); evento.titulo = "outro";

A referência é a mesma. Quem observa a lista não tem como saber que algo mudou.

Cópia nova

const l2 = [...lista, novo]; const l3 = lista.toSorted(); const e2 = { ...evento, titulo };

Referência nova. Uma comparação simples já detecta a mudança.

Framework reativo pergunta "mudou?" comparando referências. Se você muta, ele não vê — e a tela não atualiza.

Existem versões que não alteram o original: toSorted(), toReversed(), toSpliced() e with(). Prefira sempre elas às antigas.

funções · e a pegadinha clássica

Arrow, e o que ela faz com o this

// função normal: o "this" depende de COMO foi chamada const obj = { nome: "Leque", normal() { console.log(this.nome); }, // "Leque" seta: () => console.log(this.nome), // undefined! }; // mas dentro de callback, a seta é justamente o que você quer class Lista { itens = []; carregar() { buscar().then((dados) => { this.itens = dados; // "this" continua sendo a Lista ✓ }); } }

Regra prática: arrow em callback, método normal em objeto e classe. A seta não tem this próprio — ela pega o de fora, e é exatamente por isso que funciona bem dentro de then, map e listeners.

os dois operadores que limpam código

?. e ??

// antes const cidade = evento && evento.local && evento.local.cidade; // agora: para tudo e devolve undefined se algo pelo caminho não existir const cidade = evento?.local?.cidade; // ?? usa o padrão só quando é null ou undefined const vagas = evento.vagas ?? "ilimitadas"; // ATENÇÃO: || também troca 0 e "" — quase sempre um bug const errado = evento.vagas || "ilimitadas"; // 0 vira "ilimitadas" 💥

Essa diferença entre || e ?? é responsável por uma quantidade absurda de bugs sutis. Zero é um valor válido — e || não sabe disso.

parte 2 · 70 min

Código que espera

o problema · por que existe tanta cerimônia

Buscar dados leva tempo

JavaScript executa uma coisa por vez. Se ele parasse e esperasse a resposta do servidor, a página inteira congelaria — nada de rolar, clicar ou digitar.

Se fosse síncrono

A tela trava por 800ms. Ninguém consegue nem clicar em "cancelar".

Como realmente é

Ele dispara o pedido, continua a vida, e volta a mexer na tela quando a resposta chega.

Toda a sintaxe que vem a seguir — Promise, async, await — existe pra descrever "faça isso quando chegar" de um jeito legível.

promise · o vale

Um objeto que representa "ainda não"

// uma Promise está sempre num de três estados: // pendente → resolvida (deu certo) // → rejeitada (deu erro) fetch("/dados/eventos.json") // devolve uma Promise .then((resposta) => resposta.json()) // …que devolve outra .then((eventos) => render(eventos)) .catch((erro) => mostrarErro(erro));

Funciona — mas encadear .then fica ilegível rápido, especialmente com condicional no meio.

Você vai encontrar .then em código real e em resposta de IA. Precisa saber ler. Mas pra escrever, o próximo slide é melhor em quase todos os casos.

async/await · a forma que você vai escrever

O mesmo código, na vertical

async function carregarEventos() { const resposta = await fetch("/dados/eventos.json"); const eventos = await resposta.json(); render(eventos); }
  • await = "espere chegar e me dê o valor, não o vale"
  • Só funciona dentro de função marcada com async — vêm em par
  • Uma função async sempre devolve uma Promise, mesmo que você retorne um número

É a mesma dupla que vocês vão ver no Next.js, na aula 11, lendo dados no servidor. A sintaxe não muda — só o lugar onde ela roda.

fetch · a pegadinha que derruba todo mundo

404 não é erro pro fetch

async function carregarEventos() { try { const resposta = await fetch("/dados/eventos.json"); // ⚠️ fetch só rejeita se a REDE falhar. // 404 e 500 chegam aqui como resposta "normal". if (!resposta.ok) { throw new Error(`Servidor respondeu ${resposta.status}`); } return await resposta.json(); } catch (erro) { console.error(erro); throw erro; // deixa quem chamou decidir o que mostrar } }

Sem o if (!resposta.ok), um 404 vira resposta.json() falhando com uma mensagem incompreensível sobre token inesperado. É o bug mais comum desta aula.

quando são vários pedidos

Em paralelo, não em fila

🐌 em série · 900ms
const a = await buscar(1); const b = await buscar(2); const c = await buscar(3);

Cada um espera o anterior terminar.

⚡ em paralelo · 300ms
const [a, b, c] = await Promise.all([ buscar(1), buscar(2), buscar(3), ]);

Os três saem juntos.

Promise.all falha inteiro se um falhar. Se você quer o resultado de cada um, dê certo ou errado, use Promise.allSettled. E se os pedidos dependem um do outro, aí a fila é obrigatória mesmo.

o laço de eventos · na medida certa

O que trava a tela

Existe uma fila de execução. Enquanto uma função está rodando, nada mais acontece — nem clique, nem rolagem, nem animação.

Não trava

Esperar rede, timer, resposta de arquivo. O navegador fica livre enquanto isso, porque quem espera é ele, não o seu código.

Trava

Um laço com 10 milhões de voltas, ordenar 500 mil itens, JSON.parse de 40 MB. Aqui o seu código está ocupando a fila.

A conclusão prática: await não deixa nada mais rápido — ele só libera a vez enquanto a resposta não chega. Se a sua página travar, procure processamento pesado, não chamada de rede.

typescript · o básico que resolve 80%

Tipos e inferência

// na maior parte do tempo, não escreva o tipo: ele deduz let titulo = "Meetup"; // string let vagas = 40; // number let gratuito = true; // boolean // escreva onde ele NÃO tem como deduzir: parâmetros e retorno function formatar(data: string): string { return new Date(data).toLocaleDateString("pt-BR"); } // arrays e objetos const titulos: string[] = []; const porSlug: Record<string, Evento> = {};

Não anote o que ele já sabe. const titulo: string = "Meetup" é ruído. Anote parâmetro, retorno e estrutura de dados — o resto ele deduz melhor que você.

descrevendo o formato dos dados

O tipo Evento do projeto

export type Formato = "Presencial" | "Online" | "Híbrido"; export type Evento = { id: string; slug: string; titulo: string; organizadorSlug: string; formato: Formato; // só um dos três valores acima cidade?: string; // o ? = pode não vir (evento online) inicioEm: string; gratuito: boolean; vagas: number | null; // null = ilimitado, de propósito };

Repare em Formato: em vez de string, os três valores possíveis. Agora escrever "presencial" em minúscula vira erro no editor.

type ou interface? Para o formato dos seus dados, type resolve e é mais flexível. interface brilha quando algo vai ser estendido ou implementado por classe — o que aparece bastante no Angular.

o recurso mais útil e menos ensinado

Narrowing: o tipo se afina sozinho

function local(evento: Evento): string { // aqui, cidade é: string | undefined if (evento.cidade === undefined) { return "Online"; } // ✨ aqui embaixo o TS SABE que é string. Sem cast, sem "!" return evento.cidade.toUpperCase(); } // funciona com a união também if (evento.formato === "Online") { // o TS sabe que cidade não faz sentido neste ramo }

É por isso que find() devolver Evento | undefined é bom, não chato: o TypeScript te obriga a tratar o caso "não achei" — que é justamente o 404 que vocês vão implementar.

genéricos · sem mistério

Uma função que serve pra qualquer tipo

// sem genérico: devolve any, e você perde o tipo function primeiro(lista: any[]): any { return lista[0]; } // com genérico: "seja lá o que entrar, é isso que sai" function primeiro<T>(lista: T[]): T | undefined { return lista[0]; } const e = primeiro(eventos); // e: Evento | undefined ✓ const n = primeiro([1, 2, 3]); // n: number | undefined ✓

O <T> é só um espaço em branco pro tipo, preenchido na hora da chamada.

Você vai ler genéricos muito mais do que escrever: signal<Evento[]>([]) no Angular, useState<Evento | null>(null) no React. Reconhecer já basta.

utility types · os quatro que valem a pena

Tipos derivados de outros

TipoO que fazQuando você usa
Partial<T>Todos os campos viram opcionaisFormulário de edição
Omit<T, "id">Tira camposCriar evento: o id vem do servidor
Pick<T, "id"|"titulo">Fica só com essesResposta enxuta de listagem

// o que o formulário de novo evento envia: tudo menos o id type NovoEvento = Omit<Evento, "id">; // o que a edição aceita: qualquer subconjunto type EdicaoEvento = Partial<NovoEvento>;

A vantagem: se você adicionar um campo em Evento, os três tipos derivados se atualizam sozinhos. Uma fonte de verdade.

a configuração que separa TS de "JS com enfeite"

strict, ligado desde o dia 1

📄 tsconfig.json
{ "compilerOptions": { "strict": true, // ← o que importa "noUncheckedIndexedAccess": true, "target": "ES2022", "module": "ESNext", "moduleResolution": "bundler" } }
  • strict liga um pacote de checagens — a mais importante é strictNullChecks: null e undefined deixam de caber em qualquer tipo
  • noUncheckedIndexedAccess faz lista[0] ser T | undefined — porque o índice pode não existir mesmo

Sem strict, o TypeScript vira decoração: ele aceita null em tudo e você perde justamente a checagem que evita o erro nº 1 de JavaScript. No TS 7, strict já é o padrão — sinal de para onde a coisa foi.
