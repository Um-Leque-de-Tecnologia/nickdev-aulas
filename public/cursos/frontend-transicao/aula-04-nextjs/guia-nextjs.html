Preparando a máquina

Três coisas antes de qualquer linha de código:

1. Node.js 20.9 ou mais novo

node -v
# precisa aparecer v20.9.0 ou maior (v22 e v24 também servem)

Se aparecer menos que isso (ou "comando não encontrado"), baixe a versão LTS em nodejs.org e reinicie o terminal.

Você já usou nas aulas anteriores. Vamos precisar dele de novo pro deploy.

Componente = função que devolve tela

Você já fez isso na aula 03, sem saber o nome bonito:

Aula 03 — JavaScript puro

function criarCard(p) {
  const d = document.createElement("div");
  d.innerHTML = `<h3>${p.titulo}</h3>`;
  return d;
}

Hoje — React

function VagaCard({ vaga }) {
  return (
    <article>
      <h3>{vaga.titulo}</h3>
    </article>
  );
}

Três regras de componente:

  1. O nome começa com letra maiúscula — é assim que o React sabe que é seu componente e não uma tag HTML
  2. Ele devolve a interface (com return)
  3. Um arquivo, um componente principal, exportado com export default
Atalho: no VS Code, digite rafce num arquivo .tsx vazio e aperte Tab. Ele escreve o esqueleto do componente pra você.

JSX — HTML dentro do JavaScript

JSX é HTML escrito direto no meio do JavaScript. Quase igual ao que você já sabe, com cinco diferenças:

No HTMLNo JSXPor quê
class="card"className="card"class já é palavra reservada do JS
for="email"htmlFor="email"for também é
onclick="f()"onClick={f}passa a função em si, não um texto
<br> <img><br /> <img />toda tag precisa fechar
style="color:red"style={{ color: "red" }}vira objeto JavaScript

As chaves { } são o portal pro JavaScript

const nome = "Nicoly";
const vagas = 9;

<p>Oi, {nome}! Temos {vagas} vagas.</p>
<p>Metade disso é {vagas / 2}.</p>
<p>{nome.toUpperCase()}</p>

Mostrar algo só às vezes

// só aparece se for verdadeiro
{vaga.remoto && <span>🏠 Remoto</span>}

// um ou outro (if/else em uma linha)
{salva ? "★" : "☆"}

Um return, um elemento só

Se precisar devolver dois elementos lado a lado, envolva num fragmento — a tag vazia <> </>, que não vira nada no HTML:

<>
  <h1>Título</h1>
  <p>Texto</p>
</>

Props — os parâmetros do componente

Props são os dados que um componente recebe de quem o usa. É exatamente a mesma ideia dos parâmetros de função da aula 02.

// definindo
function Selo({ texto, cor }) {
  return <span style={{ color: cor }}>{texto}</span>;
}

// usando (parece uma tag HTML sua)
<Selo texto="Remoto" cor="#A98CE0" />
<Selo texto="Júnior" cor="#F24487" />

Texto vai entre aspas; qualquer outra coisa (número, objeto, array, função, variável) vai entre chaves:

<VagaCard vaga={vaga} destaque={true} posicao={1} />

Com TypeScript

function Selo({ texto, cor }: { texto: string; cor: string }) {
  return <span style={{ color: cor }}>{texto}</span>;
}
Vale o esforço: com os tipos escritos, o VS Code passa a completar os nomes pra você e avisa na hora quando você digita vaga.titlo.

children — o conteúdo entre as tags

function Caixa({ children }) {
  return <div className="caixa">{children}</div>;
}

<Caixa><p>isto aqui vira o children</p></Caixa>

É exatamente assim que o layout.tsx funciona. 😉

Listas e keys

O .map() da aula 02 continua sendo a ferramenta — só que agora ele devolve componentes:

<div className={estilos.grade}>
  {vagas.map((vaga) => (
    <VagaCard key={vaga.slug} vaga={vaga} />
  ))}
</div>
A key é obrigatória. Ela é o "RG" de cada item: é como o React sabe qual card é qual quando a lista muda de ordem ou tamanho. Use algo único e estável — o slug, o id. Evite o índice do array quando a lista puder ser reordenada ou filtrada.

Lista vazia

{vagas.length === 0 ? (
  <p>Nenhuma vaga com esses filtros 😔</p>
) : (
  vagas.map((v) => <VagaCard key={v.slug} vaga={v} />)
)}

Nunca esqueça deste caso — é o que separa um projeto de estudo de um projeto que parece profissional.

Estrutura de pastas

leque-de-vagas/

│   ├── layout.tsx     a moldura de todas as páginas
│   ├── page.tsx       a home ("/")
│   └── globals.css    tokens da marca e utilitários
├── components/       suas peças reutilizáveis
├── lib/              dados e funções (nada de interface aqui)

components/ e lib/ não são obrigatórias — o Next não liga. Mas separar é o que mantém o projeto navegável daqui a dois meses:

  • app/ — rotas e páginas
  • components/ — peças de interface reutilizáveis
  • lib/ — dados, tipos e funções que não desenham nada

O atalho @/

// em vez disto:
import VagaCard from "../../../components/VagaCard";

// escreva isto (@ = a raiz do projeto):
import VagaCard from "@/components/VagaCard";

Rotas por pasta

A regra do App Router cabe numa frase: pasta = rota, arquivo page.tsx = a página. Não existe arquivo de configuração de rotas.

Você criaURL que nasce
app/page.tsx/
app/sobre/page.tsx/sobre
app/vagas/page.tsx/vagas
app/vagas/[slug]/page.tsx/vagas/qualquer-coisa
Pegadinha nº 1 da aula: criar app/sobre.tsx em vez de app/sobre/page.tsx. Sem o arquivo chamado exatamente page.tsx dentro da pasta, a rota não existe e você toma 404.

Os arquivos com nome reservado

ArquivoO que faz
page.tsxa página. Só ela cria a rota.
layout.tsxmoldura ao redor da página e de tudo abaixo dela
loading.tsxaparece automaticamente enquanto a página busca dados
error.tsxaparece se algo quebrar (precisa de "use client")
not-found.tsxseu 404

Pastas que NÃO viram rota

Uma pasta entre parênteses serve só pra organizar: app/(institucional)/sobre/page.tsx continua sendo /sobre. Útil quando um grupo de páginas precisa de um layout próprio.

layout.tsx — escreva o cabeçalho uma vez

Aquela dor de copiar a <nav> em todo arquivo HTML? Resolvida:

📄 app/layout.tsx
import Cabecalho from "@/components/Cabecalho";
import Rodape from "@/components/Rodape";
import "./globals.css";

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="pt-BR">
      <body>
        <Cabecalho />
        <main>{children}</main>   ← a página entra aqui
        <Rodape />
      </body>
    </html>
  );
}

Pontos importantes:

  • O layout raiz é obrigatório e é o único lugar com <html> e <body>
  • Ao navegar entre páginas, o layout não é remontado — por isso o cabeçalho não pisca
  • Layouts se aninham: app/vagas/layout.tsx envolve tudo dentro de /vagas, dentro do layout raiz

Navegação com <Link>

❌ <a href="/vagas">

Recarrega o site inteiro. Tela branca, JavaScript do zero, tudo de novo.

✅ <Link href="/vagas">

Troca só o que mudou e já baixa a página antes de você clicar (prefetch). 
import Link from "next/link";

<Link href="/vagas">Ver as vagas</Link>
<Link href={`/vagas/${vaga.slug}`}>{vaga.titulo}</Link>
<Link href="/vagas?nivel=Estágio">Só estágios</Link>
Regra: link interno do seu site → sempre <Link>. Link pra fora (GitHub, LinkedIn) → <a> normal com target="_blank" rel="noopener noreferrer".

Rota dinâmica [slug]

Uma pasta com o nome entre colchetes cria uma página por item. Nove vagas no array = nove páginas no site, e você escreveu um arquivo só.

📄 app/vagas/[slug]/page.tsx
import { notFound } from "next/navigation";
import { buscarVagaPorSlug, listarSlugs } from "@/lib/vagas";

type Props = { params: Promise<{ slug: string }> };

// Diz ao Next quais slugs existem → ele pré-gera essas páginas no build.
export async function generateStaticParams() {
  const slugs = await listarSlugs();
  return slugs.map((slug) => ({ slug }));
}

export default async function PaginaVaga({ params }: Props) {
  const { slug } = await params;        ← Next 16: params é Promise!
  const vaga = await buscarVagaPorSlug(slug);

  if (!vaga) notFound();               ← renderiza o not-found.tsx

  return <h1>{vaga.titulo}</h1>;
}
Pegadinha nº 2 da aula: no Next 16, params é uma Promise. Escrever params.slug direto (como em todo tutorial de 2024) dá erro. Sempre const { slug } = await params;.

Busca e filtros na URL

Quem vem do JavaScript puro pensa em useState pra guardar o filtro. No App Router existe um caminho melhor: guardar na própria URL.

📄 app/vagas/page.tsx
// /vagas?busca=react&area=Front-end
export default async function PaginaVagas({
  searchParams,
}: {
  searchParams: Promise<{ busca?: string; area?: string }>;
}) {
  const { busca = "", area = "" } = await searchParams;
  const vagas = await listarVagas({ busca, area });
  ...
}

E a busca é um formulário HTML comum, sem JavaScript nenhum:

<form action="/vagas">
  <input type="search" name="busca" defaultValue={busca} />
  <button type="submit">Buscar</button>
</form>

O navegador monta /vagas?busca=react sozinho. E os filtros viram simples <Link> que trocam a query string.

Por que isso é melhor que useState

  • 🔗 dá pra compartilhar o link com o filtro aplicado
  • ⬅️ o botão voltar do navegador desfaz o filtro, de graça
  • 🔌 funciona sem JavaScript
  • ⚡ a filtragem acontece no servidor — o navegador só recebe o resultado

Componentes de Servidor

Este é o conceito mais importante da aula. No App Router, todo componente é de servidor por padrão.

Isso significa que o código dele roda no servidor, monta o HTML, e o navegador recebe a página já pronta. O componente em si não vira JavaScript enviado pro navegador.

Você ganhaNa prática
Página levemenos JavaScript pra baixar = abre rápido no 4G
SEOo Google lê o conteúdo já no HTML
Segurançachave de API e senha de banco ficam no servidor
await diretosem useEffect, sem estado de "carregando" na mão

O que ele NÃO pode fazer

  • useState, useEffect e outros hooks
  • onClick, onChange e outros eventos
  • window, document, localStorage

Pra isso existe o Componente de Cliente. 👇

Componentes de Cliente — "use client"

Quando o componente precisa reagir a quem usa, ele também precisa rodar no navegador. Você marca isso com uma linha:

📄 components/SalvarButton.tsx
"use client";   ← tem que ser a PRIMEIRA linha do arquivo

import { useState } from "react";

export default function SalvarButton() {
  const [salva, setSalva] = useState(false);

  return (
    <button onClick={() => setSalva(!salva)}>
      {salva ? "★" : "☆"}
    </button>
  );
}

useState em 30 segundos

const [valor, setValor] = useState(inicial);
  • valor — o dado atual
  • setValor(novo) — troca o dado e redesenha a tela
  • Nunca faça valor = novo na mão: o React não fica sabendo

useEffect: pra depois que a tela apareceu

useEffect(() => {
  // só roda no navegador, depois de renderizar
  setSalva(lerDoLocalStorage(slug));
}, [slug]);   ← roda de novo quando slug mudar
Por que não ler localStorage direto no corpo do componente? Porque o servidor não tem localStorage. O HTML do servidor sairia diferente do que o navegador desenha, e o React reclama: "hydration mismatch". Leia sempre dentro do useEffect.

Quando precisa de "use client"

Preciso de…Qual componente
Buscar dados, ler banco, usar chave secretaServidor (padrão)
Só mostrar conteúdoServidor (padrão)
useState, useEffectCliente
onClick, onChange, onSubmitCliente
window, localStorage, animaçãoCliente

A fronteira: empurre o "use client" pra baixo

Este é o erro mais comum de quem está começando: colocar "use client" no topo da página. Aí tudo dentro dela vira cliente, e você perde as vantagens do servidor.

❌ "use client" na página

A página, a lista, os 9 cards — tudo vira JavaScript baixado pelo navegador. 
"use client";
export default function Pagina() {
  ...9 cards...
}

✅ "use client" só no botão

A página e os cards continuam no servidor. Só a estrela vai pro navegador. 
// SalvarButton.tsx
"use client";
export default function SalvarButton() {...}

No Leque de Vagas há um único arquivo com "use client": o SalvarButton. O resto do projeto inteiro é servidor.

Regras da fronteira

  • Um componente de cliente não pode importar um de servidor diretamente
  • Mas ele pode receber um de servidor como children ou prop
  • Props que atravessam a fronteira precisam ser "serializáveis": texto, número, array, objeto simples. Função não atravessa.
  • "use client" contamina pra baixo: tudo que ele importa também vira cliente

Buscando dados

Em Componente de Servidor, é só colocar async na função e usar await. Só isso.

export default async function PaginaVagas() {
  const vagas = await listarVagas();
  return <div>{vagas.map(...)}</div>;
}

Duas buscas ao mesmo tempo

// ❌ uma espera a outra: 400ms + 400ms = 800ms
const vagas = await listarVagas();
const areas = await listarAreas();

// ✅ as duas ao mesmo tempo: 400ms no total
const [vagas, areas] = await Promise.all([
  listarVagas(),
  listarAreas(),
]);

A camada de dados

Repare que nenhuma página do projeto conhece o arquivo lib/dados.ts (o array). Todas passam por lib/vagas.ts:

📄 lib/vagas.ts
export async function listarVagas(filtro = {}) {
  // hoje: filtra um array
  // aula 05: consulta um banco de verdade
  // as páginas NÃO mudam — elas já usam await
}
Por que isso importa: na aula 05 a gente troca o array por um banco. Só um arquivo muda. Isso é o que separa código que aguenta crescer de código que precisa ser reescrito.

loading.tsx — carregamento sem escrever um if

Crie o arquivo, e pronto. O Next mostra ele automaticamente enquanto o page.tsx da mesma pasta busca os dados.

📄 app/vagas/loading.tsx
export default function Carregando() {
  return <p>carregando vagas…</p>;
}

Você nunca escreve if (carregando). Não existe estado de loading pra gerenciar.

UX de gente grande: em vez de "carregando…", desenhe retângulos cinzas com a forma dos cards (skeleton). A espera parece bem menor. É o que o loading.tsx do nosso projeto faz.

Suspense: carregar só um pedaço

Se só uma parte da página é lenta, envolva ela em <Suspense> — o resto aparece na hora:

import { Suspense } from "react";

<h1>Vagas</h1>                       ← aparece já
<Suspense fallback={<p>buscando…</p>}>
  <ListaDeVagas />                    ← chega depois
</Suspense>

Aprofundamos isso na aula 05.

error.tsx e not-found.tsx

404 personalizado

📄 app/not-found.tsx
export default function NaoEncontrado() {
  return <h1>Essa vaga saiu do ar 🙃</h1>;
}

Ele aparece quando a URL não existe ou quando alguma página chama notFound().

Rede de proteção

📄 app/error.tsx
"use client";   ← error.tsx é SEMPRE cliente

export default function Erro({ error, reset }) {
  return (
    <div>
      <h1>Deu ruim por aqui 😅</h1>
      <button onClick={reset}>Tentar de novo</button>
    </div>
  );
}

Se qualquer coisa explodir ao renderizar, só este bloco aparece — o site inteiro não cai. Em produção a mensagem técnica fica escondida de quem usa (você recebe só um digest pra achar no log).

Metadata e SEO

Você não escreve <head>. Você exporta um objeto e o Next monta as tags.

Página fixa

import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "Vagas",
  description: "Todas as vagas do mural.",
};

Página dinâmica

export async function generateMetadata({ params }: Props) {
  const { slug } = await params;
  const vaga = await buscarVagaPorSlug(slug);
  if (!vaga) return { title: "Vaga não encontrada" };

  return {
    title: `${vaga.titulo} — ${vaga.empresa}`,
    description: vaga.resumo,
    openGraph: { title: vaga.titulo, description: vaga.resumo },
  };
}

Template de título no layout raiz

export const metadata = {
  title: {
    default: "Leque de Vagas",
    template: "%s · Leque de Vagas",   ← %s vira o title da página
  },
};

Página com title: "Vagas" vira <title>Vagas · Leque de Vagas</title>.

Por que se importar: é o openGraph que faz seu link aparecer bonito quando alguém cola no WhatsApp ou no LinkedIn. Em portfólio, isso conta ponto.

CSS Modules e fontes

É o mesmo CSS da aula 01 e 03. A única novidade é o nome do arquivo terminar em .module.css.

/* components/VagaCard.module.css */
.card { border-radius: 16px; padding: 22px; }
.titulo { font-size: 18px; font-weight: 600; }
// components/VagaCard.tsx
import estilos from "./VagaCard.module.css";

<article className={estilos.card}>
  <h3 className={estilos.titulo}>...</h3>
</article>

No HTML final, .card vira VagaCard_card__x7f2q. Ou seja: sua .card nunca vai brigar com a .card de outro componente. Adeus, !important.

Juntando classes

className={`${estilos.card} ${ativo ? estilos.ativo : ""}`}
className={`container ${estilos.interno}`}   ← global + módulo

Onde fica o global

app/globals.css, importado uma única vez no layout raiz. Coloque ali só o que é do site inteiro: variáveis de cor, reset e utilitários.

next/font

import { Space_Grotesk } from "next/font/google";

const grotesk = Space_Grotesk({
  subsets: ["latin"],
  variable: "--fonte-titulo",
  display: "swap",
});

<html className={grotesk.variable}>

O Next baixa a fonte no build e serve do seu próprio domínio: sem requisição pro Google e sem o "pisca-texto" ao carregar.

Imagens

import Image from "next/image";

<Image src="/logo.png" alt="Logo" width={120} height={40} />

O <Image> converte pra formato moderno, gera vários tamanhos e só carrega quando a imagem chega perto da tela. width e height são obrigatórios (é o que evita a página "pular" enquanto carrega).

  • Imagens locais ficam em public/ e o caminho começa com /
  • Imagem de outro site precisa ser liberada em images.remotePatterns no next.config.ts
  • alt sempre. Sempre.

TypeScript: o mínimo que você precisa hoje

TypeScript não muda o que o código faz. Ele só avisa quando você escreve algo diferente do combinado — antes de você abrir o navegador.

// um "molde" pros dados
export type Vaga = {
  slug: string;
  titulo: string;
  remoto: boolean;
  tags: string[];
  nivel: "Estágio" | "Júnior" | "Pleno";   ← só esses três valores
  salario?: string;                          ← o ? = opcional
};

// usando no componente
function VagaCard({ vaga }: { vaga: Vaga }) { ... }

O ganho imediato: você digita vaga. e o VS Code lista todos os campos. Digitou vaga.titlo? Sublinhado vermelho na hora.

Travou num erro de tipo? Não perca a aula por causa disso. Escreva o código, chame a monitoria, seguimos. TypeScript se aprende usando, não decorando.

Deploy na Vercel

  1. Rode npm run build local. Passou? Ótimo.
  2. git push pro GitHub
  3. Em vercel.com → Add New… → Project → importe o repositório
  4. Não mexa em nada. A Vercel reconhece o Next sozinha.
  5. Deploy 🎉

A partir daí, todo git push na main republica o site automaticamente. E cada Pull Request ganha um link de pré-visualização próprio.

Erros comuns 🔧

"You're importing a component that needs useState…"

Faltou "use client" na primeira linha do arquivo. Coloque no componente menor possível, não na página.

"params should be awaited before using its properties"

Clássico do Next 16. Troque params.slug por const { slug } = await params; e deixe a função async.

404 numa página que eu acabei de criar

O arquivo precisa se chamar exatamente page.tsx, dentro da pasta. app/sobre.tsx não vira rota.

"Hydration failed" / "Text content did not match"

O HTML do servidor saiu diferente do navegador. Causas quase sempre: localStorage/window lidos fora do useEffect, ou Math.random() / hora atual no meio da renderização.

"Module not found: Can't resolve '@/components/…'"

Confira a maiúscula no nome do arquivo. No Windows funciona vagacard, no servidor da Vercel (Linux) não. Escreva igualzinho.

Meu CSS não aparece

Em CSS Module você precisa importar e usar className={estilos.card} — className="card" puro não funciona ali.

"Cannot read properties of undefined"

Você acessou um campo de algo que ainda não existe. Use vaga?.titulo ou verifique antes com if (!vaga) ….

Mudei o arquivo e nada mudou na tela

Salvou? O npm run dev ainda está rodando? Se sim, pare (Ctrl+C), apague a pasta .next e rode de novo.
