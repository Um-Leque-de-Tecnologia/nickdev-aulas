Do Java puro ao Spring

O que é inversão de controle, por que injeção de dependência muda o jeito de escrever classes, e o passo a passo pra colocar sua primeira API REST no ar com Spring Boot.

🎯 O que esta aula assume. Que você já modela em orientação a objetos: classes, encapsulamento, interfaces e a ideia de separar em camadas. O Spring não substitui nada disso — ele organiza o que você já sabe e tira do caminho o código repetitivo.

Revisão: o que o Spring usa de você

Da metade final do curso de OO, cinco coisas aparecem hoje mesmo dentro do Spring. Se alguma estiver enferrujada, é aqui que você desenferruja.

1. Exceções

Exceção é pra o que foge do esperado — não pra controlar fluxo normal. "Lista vazia" não é exceção; "id que não existe" é.

public class MidiaNaoEncontradaException extends RuntimeException {
  public MidiaNaoEncontradaException(String titulo) {
    super("Mídia não encontrada: " + titulo);
  }
}

RuntimeException (unchecked) não obriga try/catch; Exception (checked) obriga. Em API, o padrão é lançar unchecked e deixar um tratador global converter em resposta HTTP — assunto da aula 03.

2. Coleções e generics

ColeçãoUse quandoNo Spring aparece em
List<T>ordem importa, aceita repetidoretorno de rota que lista
Set<T>não pode repetirperfis de acesso de um usuário
Map<K,V>busca por chaveparâmetros, cabeçalhos, agrupamentos
Cuidado com List.of(): ela devolve lista imutável. Chamar add() lança UnsupportedOperationException. Pra uma lista que muda, use new ArrayList<>().

3. Lambdas e Stream API

É o que você vai usar no desafio de hoje, na rota com filtro:

// filtrar
acervo.stream()
      .filter(m -> m.genero().equalsIgnoreCase(genero))
      .toList();

// o maior
acervo.stream()
      .max(Comparator.comparingDouble(Midia::nota))
      .orElseThrow();

// agrupar
acervo.stream()
      .collect(Collectors.groupingBy(Midia::genero));

4. Optional

O tipo que diz "pode não ter nada aqui". Evita NullPointerException porque força você a tratar o caso vazio:

Optional<Midia> achada = acervo.stream()
    .filter(m -> m.titulo().equals(titulo))
    .findFirst();

Midia m = achada.orElseThrow(() -> new MidiaNaoEncontradaException(titulo));
Guarde este: na aula 04, o findById() do Spring Data devolve exatamente um Optional. Quem entendeu aqui não estranha lá.

5. Records

public record Midia(String titulo, int ano, String genero) {}

Uma classe imutável com construtor, getters, equals, hashCode e toString prontos. É o que vamos devolver nas rotas — e o Jackson converte pra JSON lendo esses getters.

"Instalar" o Spring

Você não instala o Spring. Essa é a pergunta mais comum da primeira aula, e a resposta surpreende: o Spring não é um programa que se instala na máquina, como o Java ou o IntelliJ. Ele é uma biblioteca — um conjunto de arquivos .jar que o Maven baixa pra dentro do seu projeto, na primeira vez que você o abre.

Quer dizer que:

  • Não existe "instalador do Spring" pra baixar
  • Cada projeto tem a sua versão do Spring, declarada no pom.xml — dois projetos na mesma máquina podem usar versões diferentes
  • Quem baixa é o Maven, e ele guarda tudo numa pasta .m2 na sua pasta de usuário, pra reaproveitar entre projetos
  • Por isso a primeira execução demora (ele está baixando) e as seguintes são rápidas

O trecho do pom.xml que traz o Spring:

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.1.0</version>   <!-- a versão do Spring é ESTA linha -->
</parent>

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
</dependencies>
Precisa instalar o Maven? Não. O projeto vem com o mvnw (Maven Wrapper), um script que baixa a versão certa do Maven sozinho. É por isso que a gente roda ./mvnw e não mvn.

Por que o Spring existe

Escreva uma aplicação Java média sem framework e três problemas aparecem sempre:

  1. Quem cria os objetos? Alguém precisa dar new em tudo, na ordem certa, e passar uns pros outros.
  2. Configuração espalhada. Servidor, porta, banco, JSON — cada um configurado num canto.
  3. Código repetido. Abrir conexão, ler requisição, converter pra objeto, fechar tudo. De novo. E de novo.

O Spring resolve os três. Mas o primeiro é o mais importante — e é o único que muda o jeito de escrever suas classes.

Inversão de controle

Olhe esta classe. Ela tem um problema que não é óbvio à primeira vista:

class MidiaServico {
  private MidiaRepositorio repo = new MidiaRepositorioArquivo();

  public List<Midia> listar() {
    return repo.buscarTodas();
  }
}

Ela faz duas coisas: usa um repositório e decide qual repositório é. A segunda não deveria ser responsabilidade dela.

O que dói na prática

  • Trocar por um repositório de banco exige editar o serviço — que não tem nada a ver com essa decisão
  • Num teste, você não consegue pôr um repositório falso: ele nasce dentro do método
  • Se dez classes criarem o repositório assim, você tem dez cópias da mesma decisão

Inversão de controle é tirar essa decisão da sua classe e passar pra outra pessoa — no nosso caso, o contêiner do Spring. A classe deixa de buscar o que precisa e passa a declarar o que precisa.

De onde vem o nome: normalmente o seu código controla o fluxo e chama as bibliotecas. Com um framework, o controle inverte: o framework chama o seu código na hora certa. Daí "inversão".

Injeção de dependência

Injeção de dependência é como a inversão de controle acontece: em vez de a classe criar o que precisa, ela recebe pronto — normalmente pelo construtor.

❌ a classe decide

class MidiaServico {
  private MidiaRepositorio repo =
    new MidiaRepositorioArquivo();
}
Acoplada à implementação. Trocar = editar.

✅ a classe pede

@Service
class MidiaServico {
  private final MidiaRepositorio repo;

  MidiaServico(MidiaRepositorio repo) {
    this.repo = repo;
  }
}
Depende do tipo, não da implementação.

O que você ganha

GanhoPor quê
Trocar sem editaroutra implementação do mesmo tipo entra sem tocar no serviço
Testar de verdadeno teste é um new comum, passando um dublê pelo construtor
Uma decisão sóqual implementação usar fica num lugar, não espalhada
Objeto sempre completocom final, é impossível existir um serviço sem repositório
Analogia: num restaurante você não vai à cozinha buscar o prato — você pede pelo cardápio e alguém traz. Sua classe declara o que quer (o tipo, no construtor) e o Spring resolve como conseguir.

Spring, Boot e starters

Três nomes que aparecem juntos e confundem:

NomeO que é
Spring FrameworkO contêiner de injeção de dependência, mais módulos para web, dados, segurança e outros. Existe desde 2003.

Antes do Boot, subir uma aplicação Spring pedia dezenas de linhas de XML e um servidor instalado à parte. Ele existe exatamente para você não fazer isso.

Gerenciar os JDKs instalados

Todo JDK que o IntelliJ baixa por você vai parar em C:\Users\seu-usuario\.jdks (ou ~/.jdks no macOS e Linux). Vale abrir essa pasta de tempos em tempos: é comum acumular quatro ou cinco versões de projetos antigos, e cada uma ocupa uns 300 MB.

Pra ver e limpar pela própria IDE: File → Project Structure → Platform Settings → SDKs. Remova ali os que nenhum projeto seu usa, e apague a pasta correspondente em .jdks pra liberar o disco de fato.

Disco cheio quebra o Maven de um jeito confuso. Sem espaço, o import não consegue baixar as dependências nem criar a pasta target/ — e a mensagem que aparece fala de "configuração do Maven", não de disco. Se um projeto se recusar a importar, confira o espaço livre antes de sair mexendo em configuração. Um projeto Spring Boot precisa de uns 500 MB entre dependências e build.

A classe principal

📄 CatalogoApplication.java
@SpringBootApplication
public class CatalogoApplication {

  public static void main(String[] args) {
    SpringApplication.run(CatalogoApplication.class, args);
  }
}

É o mesmo public static void main de sempre. O que muda é o que ele faz: sobe o contêiner do Spring e um servidor web.

O que @SpringBootApplication liga

Anotação embutidaO que faz
@Configurationmarca a classe como fonte de configuração
@EnableAutoConfigurationconfigura sozinho conforme o que encontra no classpath: achou Spring Web, sobe servidor
@ComponentScanvarre o pacote atrás das suas classes anotadas
Erro nº 1 de quem começa. O @ComponentScan varre a partir do pacote da classe main, para baixo. Se você criar um controller em com.outracoisa, o Spring nunca vai encontrá-lo — e a rota dá 404 sem nenhum erro no terminal. Mantenha tudo dentro de com.nickdev.catalogo.

Primeiro controller

Crie o pacote controller dentro do pacote principal, e dentro dele:

📄 controller/SaudacaoController.java
package com.nickdev.catalogo.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class SaudacaoController {

  @GetMapping("/ola")
  public String ola() {
    return "Olá, mundo Spring!";
  }
}

Salve e abra localhost:8080/ola. Pronto — API no ar.

O que cada peça faz

PeçaPapel
@RestControllerfaz da classe um bean que responde HTTP, e faz o retorno virar o corpo da resposta
@GetMapping("/ola")liga o método ao verbo GET no caminho /ola
o retornovira o corpo da resposta, com status 200
@Controller × @RestController: com @Controller puro, o Spring entende que o retorno é o nome de uma página a renderizar — e você vê um erro estranho ou uma tela em branco. O @RestController é @Controller + @ResponseBody, e é o que você quer numa API.

Devolvendo JSON

Devolva um objeto em vez de uma String e o JSON sai de graça:

public record Midia(String titulo, int ano, String genero) {}

@GetMapping("/midias/destaque")
public Midia destaque() {
  return new Midia("Duna", 2021, "Ficção");
}

O que chega no navegador:

{
  "titulo": "Duna",
  "ano": 2021,
  "genero": "Ficção"
}

Ninguém escreveu conversão. O starter web trouxe a biblioteca Jackson, que serializa o objeto lendo os getters — e um record já os tem.

record é Java puro. Não é coisa do Spring: é uma classe imutável com construtor, getters, equals, hashCode e toString gerados. Perfeito para transportar dados.

Beans e estereótipos

Um bean é um objeto que o Spring criou e guarda pra você. Ao subir, ele varre o pacote, acha as classes anotadas e cria uma instância de cada — que fica disponível pra ser injetada.

AnotaçãoPapel na arquitetura
@RestControllerrecebe requisição HTTP e devolve resposta
@Serviceregra de negócio
@Repositoryacesso a dados
@Componentqualquer outro bean
As quatro fazem tecnicamente a mesma coisa: viram bean. A diferença é a intenção — quem lê o código sabe na hora qual é o papel da classe. Use a mais específica que couber.

Por padrão, um bean é único

O Spring cria uma instância só de cada bean e entrega a mesma para todo mundo que pedir (escopo singleton). Duas consequências:

  • É eficiente — não se cria um serviço novo a cada requisição
  • Beans não devem guardar estado de uma requisição, porque são compartilhados. Estado vai em parâmetro e retorno, não em atributo.

Camadas na prática

A mesma separação da aula de arquitetura em camadas, agora com o Spring ligando as peças:

📄 service/MidiaService.java
@Service
public class MidiaService {

  public List<Midia> listar() {
    return List.of(
      new Midia("Duna", 2021, "Ficção"),
      new Midia("Cidade de Deus", 2002, "Drama")
    );
  }
}
📄 controller/MidiaController.java
@RestController
@RequestMapping("/midias")
public class MidiaController {

  private final MidiaService service;

  // injeção por construtor — sem @Autowired, porque só há um construtor
  public MidiaController(MidiaService service) {
    this.service = service;
  }

  @GetMapping
  public List<Midia> listar() {
    return service.listar();
  }
}

Repare que não existe new MidiaService() em lugar nenhum. O Spring viu o construtor pedindo um MidiaService, encontrou o bean e entregou.

Construtor, não campo

❌ @Autowired no campo

@Autowired
private MidiaService service;
Não pode ser final, o objeto pode existir incompleto, e o teste precisa de reflexão pra injetar um dublê.

✅ no construtor

private final MidiaService service;

public MidiaController(MidiaService s) {
  this.service = s;
}
final, objeto sempre completo, e o teste é um new comum.
Teste de sanidade das camadas: se você apagasse o controller e expusesse a mesma funcionalidade por linha de comando, o service continuaria funcionando? Se sim, a separação está certa. Se o service souber o que é HTTP, está errada.

Testar a API

O navegador só faz GET. Pra ver status e cabeçalhos — e mais pra frente fazer POST — use o curl:

$ curl localhost:8080/midias [{"titulo":"Duna","ano":2021,"genero":"Ficção"}, {"titulo":"Cidade de Deus","ano":2002,"genero":"Drama"}] $ curl -i localhost:8080/ola HTTP/1.1 200 Content-Type: text/plain;charset=UTF-8 Olá, mundo Spring!

O -i mostra a linha de status e os cabeçalhos. Alternativas com interface gráfica: Bruno, Insomnia ou Postman.

Erros comuns 🔧

Whitelabel Error Page · 404

A rota não existe. Confira, nesta ordem: o caminho está escrito igual? A classe tem @RestController? Ela está dentro do pacote da classe main?

Port 8080 was already in use

Já tem algo rodando nessa porta — provavelmente uma execução anterior que não morreu. Pare a outra, ou mude em application.properties: server.port=8081.

No qualifying bean of type '...MidiaService'

O Spring não encontrou o bean. Faltou a anotação (@Service) ou a classe está fora do pacote varrido pelo @ComponentScan.

A rota devolve o texto como se fosse nome de página

Você usou @Controller em vez de @RestController.

package org.springframework... does not exist

As dependências não foram baixadas. Rode ./mvnw clean install ou peça pra IDE recarregar o projeto Maven.

Salvei e nada mudou

O DevTools reinicia sozinho, mas só depois que o arquivo é compilado. Em algumas IDEs isso exige um build manual. Na dúvida, pare e rode de novo.

Leia a primeira linha do erro, não a pilha inteira. O Spring costuma dizer exatamente o que faltou — e frequentemente sugere a correção logo abaixo, num bloco chamado Action.

Cola rápida

// ---------- subir a aplicação ----------
./mvnw spring-boot:run          Linux/macOS
mvnw.cmd spring-boot:run        Windows

// ---------- controller ----------
@RestController
@RequestMapping("/midias")      prefixo de todas as rotas da classe
public class MidiaController {

  private final MidiaService service;

  public MidiaController(MidiaService service) {
    this.service = service;   injeção por construtor
  }

  @GetMapping                  GET /midias
  public List<Midia> listar() { ... }
}

// ---------- estereótipos ----------
@RestController   responde HTTP
@Service          regra de negócio
@Repository       acesso a dados
@Component        qualquer outro bean

// ---------- record como transporte de dados ----------
public record Midia(String titulo, int ano, String genero) {}

// ---------- testar ----------
curl localhost:8080/midias
curl -i localhost:8080/ola     com status e cabeçalhos

// ---------- mudar a porta ----------
// application.properties
server.port=8081
