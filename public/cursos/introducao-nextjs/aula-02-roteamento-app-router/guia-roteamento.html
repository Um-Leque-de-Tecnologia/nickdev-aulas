Roteamento com App Router

Uma pasta que atende infinitas páginas, os arquivos cujo nome já é a instrução, e como andar entre as telas sem a página piscar. É a aula que transforma "um site de duas páginas" em "um site de verdade".

🎯 O que esta aula assume. Só a aula 01: você sabe que um componente é uma função que devolve tela, e que criar app/sobre/page.tsx faz nascer o endereço /sobre. Você ainda não precisa saber React nem entender Server e Client Components — isso é a aula 03. Onde eles aparecerem aqui, eu aviso e digo exatamente o que fazer.

O dicionário desta aula

As palavras novas de hoje, em português normal. Volte aqui sempre que esbarrar numa que você esqueceu.

De rotas

PalavraO que é, em palavras simples
Rota Um endereço do seu site. O /vagas em meusite.com/vagas é uma rota.
Segmento Cada pedaço do endereço separado por barra. Em /vagas/12 há dois segmentos: vagas e 12. Cada segmento é uma pasta.
Rota dinâmica Uma rota em que um dos pedaços muda. /vagas/12 e /vagas/13 são a mesma rota dinâmica, atendida pelo mesmo arquivo.
params A caixinha com os pedaços que vieram na URL. Se a pasta é [id] e a pessoa acessou /vagas/12, dentro de params está id: "12".
Slug Um identificador legível usado na URL, em minúsculas e com hífens: dev-front-end-junior. É o nome que se dá àquele pedaço bonitinho do endereço.
404 O código que a internet usa pra "não achei". Quando você digita um endereço que não existe, é 404 que volta.

De espera

PalavraO que é, em palavras simples
await "Espere chegar." Algumas coisas não ficam prontas na hora — precisam de um instante. Essa palavra segura a fila até o valor chegar, e só então continua.
async A plaquinha que autoriza o await dentro daquela função. Elas andam sempre em par: se tem await dentro, precisa de async na frente.
Promise O "vale" de um valor que ainda não chegou. Você não usa o vale — você usa o que ele vira depois do await. Se aparecer [object Promise] na sua tela, foi um await esquecido.

De navegação

PalavraO que é, em palavras simples
Prefetch Adiantar o serviço. O Next vai buscando a página de destino antes de você clicar, enquanto o link está visível na tela. Quando o clique vem, ela já está pronta.
Histórico A pilha de páginas por onde a pessoa passou. É o que o botão "voltar" do navegador consulta.
"use client" Uma linha no topo do arquivo que diz "isto também roda no navegador da pessoa". Hoje é só uma etiqueta que alguns arquivos precisam ter. O porquê é a aula 03 inteira.
Hook Uma função pronta do React cujo nome começa com use. Você não precisa saber como funciona por dentro hoje — só que ela só pode ser chamada em arquivo com "use client".
Não decore nada disto. Você vai usar cada uma dessas palavras dezenas de vezes no semestre, e daqui a um mês vai falar sem perceber. Esta tabela é pra consultar quando travar, não pra memorizar.

O que veio da aula 01

Toda a aula de hoje se apoia numa frase só, e ela é da semana passada:

Pasta = rota. Arquivo page.tsx = a página. Não existe arquivo de configuração de rotas em nenhum lugar do projeto.
Você criaURL que nasce
app/page.tsx/
app/sobre/page.tsx/sobre
app/vagas/page.tsx/vagas

Hoje a gente estica essa regra até onde ela vai: pastas cujo nome é um espaço em branco, pastas que somem da URL, e arquivos que não são páginas mas mudam o comportamento da rota.

O problema: 200 vagas

Imagine o Leque de Vagas com duzentas vagas cadastradas. Cada uma precisa da sua página, com seu endereço próprio — porque a pessoa vai querer mandar o link daquela vaga específica pra alguém.

Com o que você sabe até agora, a única saída seria:

app/
└── vagas/
    ├── vaga-1/page.tsx
    ├── vaga-2/page.tsx
    ├── vaga-3/page.tsx
    ├── ...
    └── vaga-200/page.tsx

Duzentas pastas. Duzentos arquivos praticamente idênticos — muda só o texto dentro. E quando a empresa publicar uma vaga nova amanhã, alguém tem que criar a pasta na mão e publicar de novo.

É a mesma dor da aula 01, em escala maior. Lá era o cabeçalho copiado em doze páginas. Aqui é a página inteira copiada em duzentas. A solução também segue o mesmo espírito: escrever uma vez o que é um só.

A pasta entre colchetes

A resposta do Next é uma pasta cujo nome é um espaço em branco. Você escreve o nome entre colchetes, e ele passa a aceitar qualquer coisa naquele lugar do endereço.

app/
└── vagas/
    └── [id]/page.tsx     ← atende /vagas/qualquer-coisa
Você acessaQuem respondeO que chega
/vagas/12app/vagas/[id]/page.tsxid = "12"
/vagas/13o mesmo arquivoid = "13"
/vagas/dev-junioro mesmo arquivoid = "dev-junior"

Uma pasta. Um arquivo. Infinitas páginas. O que muda de uma pra outra é só o pedacinho que veio no endereço.

O nome dentro dos colchetes é escolha sua. [id], [slug], [vaga] — tanto faz. Ele vira o nome da chave que você vai ler lá dentro. Escolha um que descreva o que aquele pedaço da URL significa.
O que chega é sempre texto. Mesmo acessando /vagas/12, o id vale "12" — com aspas, como texto. Se você for comparar com um número, converta: Number(id). Essa é a fonte de uns bons vinte minutos de confusão na primeira vez.

params e o await

A página recebe uma caixinha chamada params com o que veio na URL. Assim:

📄 app/vagas/[id]/page.tsx
export default async function PaginaDaVaga({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;

  return <h1>Vaga {id}</h1>;
}

São três coisas acontecendo, e vale separar cada uma:

  1. { params } — a página recebe a caixinha
  2. await params — espera a caixinha ficar pronta
  3. const { id } = — tira de dentro dela a chave id

Por que esse await?

Porque no Next 16 o params não chega pronto: ele chega como um vale — uma promessa de que o valor vem num instante. O await é o que troca o vale pelo valor.

Não precisa entender o motivo hoje. O porquê tem a ver com como o Next prepara a página antes de mandar pro navegador, e isso é assunto da aula 04. Por enquanto vale a receita: params sempre com await, e a função sempre com async.
O sintoma de esquecer o await. Ou o Next reclama no terminal, ou aparece [object Promise] na tela em vez do valor. Quando ver isso, procure um await faltando — é quase sempre isso.

As chaves em volta de params não são enfeite

Este é o erro que mais aparece, e o mais difícil de achar sozinho. Repare nos dois:

// ERRADO — sem as chaves
export default async function PaginaDaVaga(params: Promise<{ id: string }>) {
  const { id } = await params;   id fica undefined

// CERTO — com as chaves
export default async function PaginaDaVaga({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;   "12"

O Next não entrega a caixinha na sua mão. Ele entrega uma sacola com a caixinha dentro — mais ou menos assim:

{ params: Promise<{ id }>, searchParams: Promise<{ … }> }

As chaves em { params } são o que diz "tire o params de dentro da sacola". Sem elas, você só deu o apelido params pra sacola inteira — e a sacola não tem nenhum id dentro. O resultado é undefined.

Por que ele é traiçoeiro. O React simplesmente não escreve nada quando o valor é undefined. Então não há erro vermelho, não há aviso no terminal, e o npm run build passa normalmente. Você só vê "Vaga" sozinho na tela, sem o número.

A regra: sumiu o valor e o terminal está limpo? Olhe as chaves antes de olhar o await. O [object Promise] é o sintoma do await faltando; o buraco calado é o sintoma das chaves faltando.

Um jeito mais curto de escrever o tipo

Escrever Promise<{ id: string }> à mão funciona, mas o Next 16 já sabe quais são os pedaços de cada rota. Dá pra pedir pra ele:

export default async function Page(props: PageProps<"/vagas/[id]">) {
  const { id } = await props.params;
  return <h1>Vaga {id}</h1>;
}

Não precisa importar nada: PageProps já existe sozinho. As duas formas estão certas — use a que você entender melhor. No desafio, qualquer uma serve.

Uma vantagem concreta desta forma. Aqui não existe chave pra esquecer: você escreve props.params e pronto. E se errar mesmo assim, o editor sublinha na hora, com o nome do problema: Property 'id' does not exist on type PageProps<"/vagas/[id]">. Na forma escrita à mão, o mesmo erro passa calado. Se você é do tipo que prefere o computador avisando, fique com esta.

E o que vem depois do ? na URL

Endereços como /vagas?area=dados têm uma segunda caixinha, chamada searchParams. Funciona igual, inclusive no await:

export default async function Vagas({ searchParams }) {
  const { area } = await searchParams;   "dados"
}
A diferença entre as duas. params é o que está no caminho (/vagas/12); searchParams é o que vem depois do ? (/vagas?area=dados). Filtro e busca usam a segunda — e isso volta com força na aula de listagem.

Catch-all: [...slug]

O [id] pega um pedaço do endereço. Às vezes você não sabe quantos vêm — em documentação, por exemplo, onde as categorias podem ter três ou cinco níveis.

PastaPegaNão pegaO que chega
[id]/vagas/12/vagas/12/xtexto
[...slug]/docs/a, /docs/a/b/c/docslista
[[...slug]]/docs e tudo abaixo—lista (às vezes vazia)
// app/docs/[...slug]/page.tsx acessado em /docs/guia/rotas
const { slug } = await params;   ["guia", "rotas"]
Provavelmente você não vai usar isto no projeto. Está aqui porque é uma das quatro formas de rota que existem, e porque quando você ler o código de outra pessoa vai esbarrar nela. Reconhecer já basta.

Os arquivos especiais

Dentro de app/, alguns nomes de arquivo são reservados. Eles não viram páginas — eles mudam o comportamento da rota onde estão.

A regra que vale pra todos. Você não importa, não registra, não configura. Criou o arquivo com o nome certo, o comportamento passa a existir. É a mesma lógica do page.tsx.
ArquivoPra que serveEntra em cena quando
page.tsxo conteúdo da rotasempre — sem ele a rota não existe
layout.tsxa moldura em voltasempre, e não remonta ao navegar
loading.tsxa tela de esperaenquanto a página se prepara
error.tsxa tela de erroquando algo quebra ali dentro
not-found.tsxa tela de "não existe"quando o conteúdo não é encontrado
template.tsxmoldura que remontaigual ao layout, mas do zero a cada navegação

Cada um vale só pra pasta onde está e as pastas de dentro dela. Um error.tsx em app/vagas/ cobre /vagas e /vagas/12 — mas não cobre /sobre.

Existem outros, e eles chegam depois. route.ts (aula 06, quando o assunto for backend), default.tsx (rotas paralelas) e global-error.tsx (o erro que pega até o layout raiz). Nenhum deles é da aula de hoje.

Layouts aninhados

Na aula 01, o layout.tsx era um só, na raiz, com o cabeçalho do site. Agora vem a parte boa: cada pasta pode ter o seu, e eles se encaixam um dentro do outro.

app/
├── layout.tsx          cabeçalho e rodapé do site
├── page.tsx             /
└── vagas/
    ├── layout.tsx      título e filtros da área de vagas
    ├── page.tsx         /vagas
    └── [id]/
        └── page.tsx     /vagas/12

Ao abrir /vagas/12, a tela é montada assim, de fora pra dentro:

┌─ layout da raiz ──────────────────────┐
│  cabeçalho do site                    │
│  ┌─ layout de vagas ────────────────┐ │
│  │  filtros                         │ │
│  │  ┌─ page de [id] ──────────────┐ │ │
│  │  │  os dados da vaga 12        │ │ │
│  │  └─────────────────────────────┘ │ │
│  └──────────────────────────────────┘ │
│  rodapé                               │
└───────────────────────────────────────┘
📄 app/vagas/layout.tsx
export default function LayoutVagas({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <div className="area-vagas">
      <h1>Vagas</h1>
      {children}   {/* ← a página da vez entra aqui */}
    </div>
  );
}
Só o layout da raiz tem <html> e <body>. Os layouts de dentro devolvem só um pedaço — uma <div>, uma <section>. Se você escrever <html> num layout aninhado, quebra.

A parte que responde o gancho da aula passada

Ao navegar de /vagas/12 pra /vagas/13, os dois layouts não são remontados. Eles continuam ali, do jeito que estavam — só o miolo troca.

É por isso que a navegação não pisca: o Next não joga a página fora e monta outra. Ele substitui só a parte que mudou. Se você tivesse um campo de busca digitado no layout, o texto continuaria lá.

layout × template

O template.tsx faz a mesma coisa que o layout — envolve a página — com uma diferença única:

layout.tsx

Sobrevive à navegação. Vai de /vagas/12 pra /vagas/13 e ele continua o mesmo, sem remontar.

É o que você quer em 99% dos casos.

template.tsx

Remonta do zero a cada navegação. Toda troca de página, ele nasce de novo.

Útil quando você quer uma animação de entrada repetindo a cada página, por exemplo.

Na dúvida, use layout. Sério. O template está aqui pra você saber que existe e não se assustar ao ver num projeto alheio. Se os dois existirem na mesma pasta, o template fica dentro do layout.

loading.tsx

Toda página leva um tempinho pra ficar pronta — às vezes milissegundos, às vezes segundos, se tiver que buscar dados. O loading.tsx é o que aparece nesse intervalo.

📄 app/vagas/loading.tsx
export default function Loading() {
  return <p>Carregando vagas…</p>;
}

Pronto. Não precisa importar nem ligar em lugar nenhum — o Next encontra sozinho e usa quando a página daquela pasta estiver se preparando.

  • O layout continua na tela — cabeçalho, filtros, tudo. Só o miolo mostra o "carregando"
  • Ele vale pra pasta onde está e as de dentro
  • Dá pra ter vários: um em app/vagas/, outro em app/vagas/[id]/, cada um com sua mensagem
Melhor que "Carregando…": um esqueleto. Em vez de texto, desenhe caixinhas cinzas no formato do conteúdo que vai chegar. A pessoa já entende o que está vindo, e a troca fica bem menos brusca. É CSS comum — algumas div com fundo cinza e altura fixa.
Você pode não ver o loading no seu projeto hoje. Se a página fica pronta em 5 milissegundos, ele pisca e some. Pra testar de verdade, o código de referência da aula tem um truque: uma função que segura a página por dois segundos de propósito.

error.tsx

Quando alguma coisa quebra dentro de uma rota, sem esse arquivo a pessoa vê uma tela de erro feia — ou, em produção, uma tela genérica. Com ele, vê uma tela sua, e o resto do site continua de pé.

📄 app/vagas/error.tsx
"use client";   // ← obrigatório neste arquivo

export default function Error({
  error,
  retry,
}: {
  error: Error & { digest?: string };
  retry: () => void;
}) {
  return (
    <div>
      <h2>Algo deu errado ao carregar as vagas</h2>
      <button onClick={() => retry()}>Tentar de novo</button>
    </div>
  );
}

O que chega pra ele

O quêPra que serve
errorO erro que aconteceu. Em desenvolvimento você vê a mensagem real; em produção ela é escondida, pra não vazar detalhe do servidor pra qualquer visitante.
retry()Uma função pronta: chamou, o Next tenta montar a página de novo. Se der certo desta vez, a tela de erro some sozinha.
Sobre o "use client". Essa linha diz "este arquivo também roda no navegador da pessoa". Ela é obrigatória no error.tsx — sem ela, o Next reclama. Por que isso é necessário é exatamente o assunto da aula 03. Hoje: escreva a linha e siga.
O erro do layout escapa daqui. Um error.tsx não pega erros do layout.tsx da mesma pasta — porque o layout está por fora dele. Quem pega é o error da pasta de cima. Veja o desenho na próxima seção.
Você vai ver reset por aí. Era o nome antigo. A partir do Next 16.3 o recomendado é retry, que além de limpar o erro busca os dados de novo. Se a IA te devolver reset, não está errado — está velho.

not-found.tsx

Rota dinâmica aceita qualquer coisa no lugar do [id] — inclusive /vagas/banana. Alguém vai digitar isso, ou clicar num link antigo de uma vaga que já saiu do ar. O que aparece nessa hora é você quem decide.

Passo 1 — avise que não achou

📄 app/vagas/[id]/page.tsx
import { notFound } from "next/navigation";

export default async function PaginaDaVaga({ params }) {
  const { id } = await params;
  const vaga = vagas.find((v) => v.id === id);

  if (!vaga) {
    notFound();   // ← para tudo aqui e mostra o not-found
  }

  return <h1>{vaga.titulo}</h1>;
}

Passo 2 — escreva a tela

📄 app/vagas/[id]/not-found.tsx
import Link from "next/link";

export default function VagaNaoEncontrada() {
  return (
    <div>
      <h2>Vaga não encontrada</h2>
      <p>Ela pode ter sido preenchida ou removida.</p>
      <Link href="/vagas">Ver todas as vagas</Link>
    </div>
  );
}
Sempre ofereça um caminho de volta. Um 404 sem link é um beco sem saída. Um 404 com "ver todas as vagas" transforma um erro em mais uma chance de a pessoa encontrar o que queria.

O not-found da raiz é especial

O arquivo app/not-found.tsx faz duas coisas: atende o notFound() chamado na raiz e vira a tela de qualquer endereço que não bate com rota nenhuma do site. Digitou /pagina-que-nao-existe? É ele que aparece.

Todo projeto deveria ter um. Sem app/not-found.tsx, o visitante que erra o endereço vê a tela padrão do Next — cinza, em inglês, sem o seu cabeçalho e sem saída. São dez linhas pra resolver.

A ordem das camadas

Os arquivos especiais se envolvem numa ordem fixa. Vale guardar este desenho — ele explica vários comportamentos que parecem estranhos.

<layout>                    a moldura
  <error>                  pega o que quebrar aqui dentro
    <loading>              enquanto o miolo não vem
      <not-found>
        <page />           o conteúdo
      </not-found>
    </loading>
  </error>
</layout>

Duas consequências práticas que caem em prova de vida real:

  • O layout está por fora do error. Então um erro dentro do layout.tsx não é pego pelo error.tsx da mesma pasta — quem pega é o da pasta de cima. E um erro no layout raiz só é pego por um global-error.tsx.
  • O error está por fora do loading. Então se a página quebrar enquanto carregava, o "carregando" é substituído pela tela de erro — não fica um em cima do outro.

Route groups

Às vezes você quer agrupar páginas — pra dar um layout comum a elas, ou só pra organizar — sem que o nome do grupo apareça no endereço.

Parênteses no nome da pasta resolvem: ela some da URL.

app/
└── (institucional)/            ← não aparece no endereço
    ├── layout.tsx             moldura só destas páginas
    ├── termos/page.tsx        → /termos
    └── privacidade/page.tsx   → /privacidade

O endereço é /termos, não /institucional/termos. A pasta existe pro seu editor de código, não pro navegador.

Pra que isso serve de verdade

SituaçãoComo o grupo ajuda
Layout diferente pra um conjuntoAs páginas de termos e privacidade ganham um layout mais sóbrio, sem os filtros de vaga, sem mexer na URL.
Arrumar a casaQuando app/ tem vinte pastas soltas, agrupar em (marketing) e (app) deixa legível — e nenhum link quebra.
Separar público de privado(publico) e (logado), cada um com seu layout. Isso volta na aula de autenticação.
Cuidado com colisão. Se você criar (a)/sobre/page.tsx e (b)/sobre/page.tsx, os dois querem ser /sobre — e o build falha. Os parênteses somem da URL, então o que sobra tem que ser único.

Paralelas e interceptadas

Existem mais duas formas de rota no App Router. Nenhuma das duas cai no desafio — estão aqui pra você reconhecer o nome quando esbarrar.

Rotas paralelas — @pasta

Duas telas no mesmo endereço, cada uma navegando por conta própria. Pense num painel dividido: a metade de cima e a de baixo mudam sem uma esperar a outra.

app/painel/
├── layout.tsx        recebe as duas metades como props
├── @vagas/page.tsx
└── @candidaturas/page.tsx

Rotas interceptadas — (.)pasta

Aquele comportamento do Instagram: você clica numa foto do feed e ela abre num modal por cima, mas a URL muda como se fosse página cheia. Se você recarregar ou mandar o link pra alguém, aí sim vem a página cheia.

Por que estou mostrando. Porque essas duas resolvem problemas que a gente normalmente resolve com gambiarra — e porque, quando você ler que "Next tem rotas interceptadas", vai saber que é aquele modal, não algo mágico e inalcançável.

Link e prefetch

Na aula 01 ficou a regra: use <Link>, não <a>. Agora o porquê completo.

Com <a href>

O navegador joga fora a página inteira e baixa tudo de novo: HTML, CSS, JavaScript. Tela branca no meio, cabeçalho remontado, rolagem perdida.

Com <Link>

O Next troca só o pedaço que mudou. Os layouts continuam de pé. E, antes do clique, ele já foi buscar a página de destino em segundo plano.

import Link from "next/link";

// link fixo
<Link href="/vagas">Ver vagas</Link>

// link montado a partir de um dado
<Link href={`/vagas/${vaga.id}`}>{vaga.titulo}</Link>
Aquelas crases são propositais. Em JavaScript, `texto ${variavel}` é um texto com um buraco preenchido na hora. É como você monta endereços que dependem de um dado.

Prefetch: o adiantamento

Quando um <Link> aparece na tela, o Next já começa a buscar a página de destino em segundo plano. Quando a pessoa clica, boa parte do trabalho já está feita — por isso parece instantâneo.

Prefetch só acontece no site publicado. Em npm run dev ele fica desligado de propósito. Se a navegação parecer lenta na sua máquina e instantânea na Vercel, está tudo certo — é exatamente esse o motivo.

Três props que vale conhecer

PropO que faz
replaceNavega sem deixar rastro no histórico. O botão voltar pula essa página. Útil depois de um login.
scroll={false}Não mexe na posição da rolagem ao trocar de página.
prefetch={false}Desliga o adiantamento naquele link. Use em listas gigantes, onde adiantar tudo seria desperdício.
E o <a>, morreu? Não. Ele continua certo pra links que saem do seu site: LinkedIn, GitHub, o site da empresa que publicou a vaga. A regra é: dentro do seu site, Link; pra fora, <a>.

Link ativo com usePathname

Todo menu decente marca em que página a pessoa está. Pra isso você precisa saber qual é o endereço atual — e quem sabe disso é o navegador.

📄 components/MenuLink.tsx
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";

export default function MenuLink({
  href,
  children,
}: {
  href: string;
  children: React.ReactNode;
}) {
  const caminho = usePathname();   "/vagas", por exemplo
  const ativo = caminho === href;

  return (
    <Link href={href} className={ativo ? "menu-link ativo" : "menu-link"}>
      {children}
    </Link>
  );
}

E o CSS, comum, no globals.css:

.menu-link { color: #a1a1aa; }
.menu-link.ativo { color: #fafafa; font-weight: 600; }
Por que este arquivo precisa de "use client". Saber em que endereço a pessoa está só é possível no navegador dela — e por padrão os arquivos do Next rodam antes disso, no servidor. A linha é o que autoriza este a rodar também no navegador. A aula 03 explica isso inteiro; por hoje, a regra prática é: usou algo que começa com use, escreva "use client" no topo.
O detalhe que pega todo mundo. Com caminho === href, o link "Vagas" acende em /vagas mas apaga em /vagas/12. Se você quiser que ele fique aceso na seção inteira, use caminho.startsWith(href) — mas cuidado: o link da home ("/") aí acende em tudo. Trate a home à parte.

useRouter

Às vezes não existe link pra clicar: a navegação precisa acontecer depois de alguma coisa — enviar um formulário, fechar um modal, clicar num botão "voltar". Pra isso existe o useRouter.

📄 components/BotaoVoltar.tsx
"use client";

import { useRouter } from "next/navigation";

export default function BotaoVoltar() {
  const router = useRouter();

  return (
    <button onClick={() => router.back()}>
      ← Voltar
    </button>
  );
}
MétodoO que faz
router.push("/vagas")Vai pra lá e guarda no histórico — o botão voltar do navegador funciona.
router.replace("/vagas")Vai pra lá apagando a página anterior do histórico. Depois de um login, pra ninguém "voltar" pro formulário.
router.back()Volta uma página, igual à seta do navegador.
router.refresh()Recarrega os dados da página atual sem perder o que a pessoa digitou. Volta com força na aula de Server Actions.
Vem de next/navigation. Sempre. Existe um useRouter antigo em next/router, do Next de antigamente. Se você importar dele, quebra — e a mensagem de erro não é nada óbvia. É um dos erros mais comuns de quem segue tutorial velho.
A regra de ouro. Se dá pra usar <Link>, use <Link>. Ele funciona sem JavaScript, o navegador entende, dá pra abrir em nova aba com o botão do meio, e tem prefetch. O useRouter é pro que sobra.

Erros comuns 🔧

Apareceu [object Promise] na tela

Faltou await antes de params. E confira se a função tem async na frente — os dois andam em par.

A página abre, mas o valor não aparece

Aparece "Vaga" e o número some, sem nenhum erro no terminal. Quase sempre são as chaves: é ({ params }: { params: … }), e não (params: …). Sem as chaves, params vira a sacola inteira de props e o id sai undefined — e undefined o React não escreve na tela. Detalhe cruel: o npm run build passa mesmo assim.

404 na rota dinâmica que acabei de criar

Confira se a pasta está com colchetes de verdade: [id], não (id) nem id. E se o arquivo dentro dela se chama exatamente page.tsx.

O route group virou parte da URL

Você usou colchetes em vez de parênteses. (institucional) some da URL; [institucional] vira um pedaço dinâmico do endereço.

You're importing a component that needs useRouter…

Faltou "use client" na primeira linha do arquivo — antes de qualquer import. Vale pra usePathname, useRouter e para o error.tsx.

NextRouter was not mounted

Você importou o useRouter de next/router. No App Router é next/navigation.

O loading.tsx nunca aparece

Sua página fica pronta rápido demais — o que é ótimo. Pra testar, segure a página de propósito por dois segundos; o código de referência da aula mostra como.

O error.tsx não pegou o erro

Se o erro aconteceu no layout.tsx da mesma pasta, ele escapa — o layout fica por fora. Ponha um error.tsx na pasta de cima.

A comparação com o id nunca dá certo

O que vem da URL é sempre texto. Se os seus dados guardam o id como número, "12" === 12 dá falso. Converta com Number(id), ou guarde os ids como texto desde o começo.

Build falha com "duplicate page" ou rota repetida

Dois arquivos querem o mesmo endereço — quase sempre por causa de route groups. Lembre que os parênteses somem da URL.

Funciona no dev, quebra na Vercel

Continua sendo o suspeito nº 1 da aula 01: maiúscula em nome de arquivo. Windows perdoa, o servidor da Vercel (Linux) não.
