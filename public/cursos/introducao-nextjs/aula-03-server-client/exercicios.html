Exercícios em aula · Aula 03

Uma coisa de cada vez 🧩

Hoje você sai da aula com quatro coisas funcionando na sua máquina, uma de cada vez — e a última é o começo do desafio da semana.

🧭

A ordem importa

Primeiro você descobre onde o seu código roda. Depois você atravessa a fronteira entre o servidor e o navegador. Só então dá memória a um componente. É a ordem em que uma coisa depende da outra: sem saber que a página roda no servidor, a linha "use client" parece enfeite; e sem essa linha, useState nem existe.

Nos labs 1 e 2 ainda não aparece useState. É de propósito. Você vai passar dois labs sentindo a falta que ele faz — e quando ele chegar, no lab 3, chega como remédio de uma dor que você já sentiu, não como mais uma linha para decorar.

📋

O formato que se repete

Toda memória de componente é uma linha só, sempre com este desenho. Você vai escrevê-lo duas vezes hoje e mais algumas no desafio. Copiar daqui é o esperado.

const [copiado, setCopiado] = useState(false);
//      ↑          ↑                     ↑
//      o valor    como mudar            o valor inicial
o valorVocê lê, e nunca atribui. Ele é a foto daquele render.
como mudarA única forma de mexer. É ele que avisa o React.
o valor inicialVale só na primeira vez. Depois o React devolve o que guardou.

O nome dentro dos colchetes é seu: copiado, busca, aberta. A convenção é que o segundo seja o primeiro com set na frente — busca e setBusca. Não é regra da linguagem, é hábito de quem vai ler o seu código depois.

✅

Antes de começar

  • O projeto da aula 02 abre no seu editor.
  • Ele sobe: npm run dev e o terminal mostra Ready in ... ms, sem erro vermelho.
  • /vagas e /vagas/1 respondem no navegador.

Se alguma falhar, resolva agora — os quatro labs dependem das três. Chame na aula: quinze minutos aqui valem mais do que uma hora tentando fazer o lab 4 em cima de um projeto que não sobe.

Os labs
LAB 1

Ache o seu console.log

~8 min

Descobrir, com os seus próprios olhos, que a sua página roda no servidor.

  1. Abra app/vagas/page.tsx. Não mude nada do que já está lá.
  2. Antes do return, escreva um console.log com uma marca que você reconheça.
  3. Suba com npm run dev e abra http://localhost:3000/vagas.
  4. Abra o console do navegador (F12 → Console). Procure a sua linha.
  5. Agora olhe o terminal onde o npm run dev está rodando. Procure de novo.
  6. Recarregue a página duas vezes e conte quantas linhas apareceram.
// app/vagas/page.tsx
import { vagas } from "@/data/vagas";

export default function Vagas() {
  console.log("[servidor] montando a listagem");

  return (
    <>
      <h1>Vagas</h1>
      {/* o que já estava aqui, sem mexer */}
    </>
  );
}

Não achou o terminal? É a janela onde você digitou npm run dev e que ficou "presa", sem devolver o cursor. Ela é o servidor. Deixe-a visível ao lado do navegador durante a aula inteira — metade dos erros de hoje aparece ali primeiro.

responda
  1. A sua linha apareceu no console do navegador, no terminal, ou nos dois?
  2. Você recarregou duas vezes. Quantas linhas saíram no terminal?
  3. Se essa função roda no servidor, o navegador recebeu o quê?
ver a resposta — depois de tentar

1. Só no terminal. E isso costuma dar um susto, porque a sua cabeça diz "é JavaScript, e JavaScript roda no navegador". Hoje não. Essa função foi executada na sua máquina, pelo servidor do Next, antes de qualquer coisa chegar ao navegador. O console do navegador nunca viu essa linha porque essa linha nunca esteve lá.

2. Duas — uma por pedido. Cada recarga é um pedido novo, e o servidor roda a sua função de novo para montar a resposta. Se em vez de recarregar você navegou pelos links, pode ter visto uma linha só: o Next reaproveita o que já buscou. Ver isso hoje te poupa confusão na aula 04.

3. O resultado, não a receita. O servidor rodou a sua função, virou HTML e mandou o HTML. O navegador recebeu texto pronto para desenhar — não recebeu o seu console.log, não recebeu o import, não recebeu a lista de vagas em código. Isso tem nome: Server Component, e é o padrão. Repare que você não escreveu nada para conseguir isso. Todo componente já nasce assim.

LAB 2

Quebre de propósito

~10 min

Provocar agora, com calma e com a turma junto, o erro que você ia encontrar sozinha às onze da noite — e aprender a achar a palavra que entrega a causa.

  1. Crie components/BotaoCopiarLink.tsx. Não escreva "use client" — é esse o ponto do lab.
  2. Escreva o botão abaixo. Ele tem um onClick, e é o onClick que vai quebrar.
  3. Importe e use em app/vagas/[id]/page.tsx: <BotaoCopiarLink titulo={vaga.titulo} />.
  4. Abra /vagas/1. Leia o erro inteiro, da primeira à última linha, antes de mexer em qualquer coisa.
  5. Ache a palavra que entrega a causa. Ela está na primeira linha.
  6. Só agora ponha "use client" como primeira linha do arquivo, antes de qualquer import. Recarregue.
// components/BotaoCopiarLink.tsx — a versão que quebra, de propósito

export default function BotaoCopiarLink({ titulo }: { titulo: string }) {
  return (
    <button
      type="button"
      onClick={() => {
        // navigator e location só existem no navegador.
        navigator.clipboard.writeText(location.href);
        alert(`Link de “${titulo}” copiado`);
      }}
    >
      🔗 Copiar link
    </button>
  );
}

Por que alert? Porque neste lab você ainda não tem memória nenhuma dentro do componente. O alert é o aviso pobre que a aula 02 usava. No lab 3 ele sai e o botão passa a mudar o próprio texto — é a mesma tela, com memória.

responda
  1. Qual palavra do erro entrega a causa? (uma palavra, não a frase inteira)
  2. O erro apareceu no terminal, no navegador, ou nos dois?
  3. A página app/vagas/[id]/page.tsx também precisa da linha? Por quê?
ver a resposta — depois de tentar

1. handlers. "Event handlers cannot be passed" — funções que escutam evento não podem ser passadas. O servidor manda resultado, e uma função não é resultado: não dá para escrever "esta função aqui" dentro de um HTML e mandar pelo cabo. O erro está dizendo, com todas as letras, exatamente o que você fez. Reconhecendo o formato, você lê esse erro em cinco segundos pelo resto do semestre.

2. Nos dois — no navegador, naquela tela vermelha de desenvolvimento, e no terminal, em texto. Leia o do terminal: ele vem inteiro, com a lista de arquivos embaixo, e é ali que você descobre qual componente causou. A tela vermelha corta o começo com mais frequência do que você gostaria.

3. Não. A linha marca a folha, não a raiz. A página continua no servidor: ela lê os dados e entrega prontos para o botão. Se você puser "use client" na página, tudo que ela importa desce para o navegador junto — inclusive o que não precisava — e a fronteira que você acabou de desenhar sobe para o topo da casa. O contrário também vale, e é a confusão nº 1 da turma: quem é importado por um componente de cliente já entra junto, e por isso não repete a linha. A linha marca a porta, não cada móvel.

LAB 3

O botão que lembra

~12 min

Ver as duas versões: a que muda a variável e não muda a tela, e a que tem memória. Você tem que ver as duas — a segunda só faz sentido depois da primeira.

  1. Primeiro a versão que não funciona. No BotaoCopiarLink (que já tem "use client"), declare let copiado = false; dentro da função.
  2. No onClick, escreva copiado = true; e um console.log logo depois. Troque o texto do botão por {copiado ? ... : ...}.
  3. Clique. A tela continua igual. Não conserte ainda.
  4. Olhe o console do navegador — agora o componente é de cliente, e o log sai lá. O que está escrito?
  5. Agora a versão com memória. Duas mudanças: o import em cima e a linha do useState no lugar do let. Troque copiado = true por setCopiado(true).
  6. Clique de novo. Cole o link em algum lugar para conferir que ele copiou mesmo.
// versão 1 — a que NÃO funciona (é para rodar assim mesmo)
"use client";

export default function BotaoCopiarLink({ titulo }: { titulo: string }) {
  let copiado = false;  // ← nasce false a cada renderização

  return (
    <button
      type="button"
      onClick={() => {
        navigator.clipboard.writeText(location.href);
        copiado = true;
        console.log("[navegador] copiado agora é", copiado);
      }}
    >
      {copiado ? "✓ Link copiado" : "🔗 Copiar link"}
    </button>
  );
}
// versão 2 — a que funciona. Mudou o quê? Duas linhas.
"use client";

import { useState } from "react";

export default function BotaoCopiarLink({ titulo }: { titulo: string }) {
  const [copiado, setCopiado] = useState(false);

  return (
    <button
      type="button"
      onClick={() => {
        // location e navigator só existem no navegador.
        navigator.clipboard.writeText(location.href);
        setCopiado(true);
      }}
    >
      {copiado ? `✓ Link de “${titulo}” copiado` : "🔗 Copiar link"}
    </button>
  );
}

Um teste que vale ouro: escreva setCopiado(true); e, na linha seguinte, console.log(copiado). Ele mostra o valor antigo. Não é bug e não é atraso: copiado é a foto daquele render, e o valor novo só chega no render seguinte.

responda
  1. Na versão com let, o console.log mostrou true? E a tela, mudou?
  2. O que o setCopiado faz que o copiado = true não faz?
  3. Se toda variável nasce do zero a cada renderização, onde o valor fica guardado entre um clique e o outro?
ver a resposta — depois de tentar

1. Mostrou true, e a tela não mudou. Guarde essa cena: a variável mudou de verdade. O seu código estava certo em JavaScript e mesmo assim a tela ficou parada — porque ninguém avisou o React. Ele não fica vigiando as suas variáveis. E tem um segundo estrago: da próxima vez que a função rodar, a linha let copiado = false roda de novo e apaga tudo. É o erro que todo mundo comete uma vez. O caro não é errar; é passar quinze minutos procurando o defeito no lugar errado.

2. Ele avisa. Repare no que você não fez em momento nenhum: não mexeu no texto do botão, não procurou o elemento na tela, não trocou nada na mão. Você mexeu no dado, e a tela veio atrás. O caminho completo é este: você chama setCopiado → o React guarda o valor novo → o React roda a sua função de novo → o useState devolve o valor guardado → a tela sai diferente. (E não, nada disso precisa de useEffect. useEffect não é hoje.)

3. Fora da sua função. Quem guarda é o React, do lado de fora, amarrado àquele componente naquela aba. É por isso que a linha do useState não é uma atribuição comum: ela é um pedido de memória. O false lá dentro vale só na primeira vez; da segunda em diante o React ignora e devolve o que ele tem guardado. Recarregue a página e o botão volta para "🔗 Copiar link" — a memória é daquela aba, naquele momento, e mais nada.

LAB 4

O campo de busca

~15 min

Escrever o primeiro componente que guarda o que a pessoa digita — e sair da aula com a frente 4 do desafio já começada.

Leia antes de começar: este lab é o início da frente 4 do desafio da semana. O que você escrever aqui não vai para o lixo: no desafio esse mesmo arquivo ganha o filtro por área, o componente Filtros.tsx e as contagens. Se a frente 4 é sua, você está adiantando o seu trabalho. Se não é, você está entendendo a peça que a sua colega vai carregar o semestre inteiro.

  1. Crie components/MuralDeVagas.tsx com "use client" na primeira linha.
  2. Um estado: const [busca, setBusca] = useState(""). Um só. Resista à vontade de criar um segundo.
  3. Campo controlado: value={busca} e onChange. Escreva os dois.
  4. Apague o onChange por dez segundos e tente digitar no campo. Depois devolva. Isso vai cair na pergunta.
  5. A lista filtrada é estado derivado: visiveis é uma const calculada, não um useState.
  6. Em app/vagas/page.tsx, importe o mural e passe as vagas por prop: <MuralDeVagas vagas={vagas} />. A página continua no servidor.
  7. Digite e apague. Confira o número mudando junto com a lista.
// components/MuralDeVagas.tsx — a versão de hoje: só a busca
"use client";

import { useState } from "react";
import CardDeVaga from "./CardDeVaga";
import type { Vaga } from "@/data/vagas";

export default function MuralDeVagas({ vagas }: { vagas: Vaga[] }) {
  const [busca, setBusca] = useState("");

  // Estado derivado: recalculado a cada renderização, nunca guardado.
  const visiveis = vagas.filter((vaga) => {
    const termo = busca.toLowerCase();
    return (
      vaga.titulo.toLowerCase().includes(termo) ||
      vaga.empresa.toLowerCase().includes(termo)
    );
  });

  return (
    <section>
      <input
        type="search"
        placeholder="Buscar por título ou empresa"
        value={busca}
        onChange={(e) => setBusca(e.target.value)}
      />

      <p className="numeros">
        <strong>{visiveis.length}</strong> de {vagas.length} vagas
      </p>

      {visiveis.length === 0 ? (
        <p>Nenhuma vaga com esse filtro. Tente outra palavra.</p>
      ) : (
        <ul className="lista">
          {visiveis.map((vaga) => (
            <CardDeVaga key={vaga.id} vaga={vaga} />
          ))}
        </ul>
      )}
    </section>
  );
}

Ainda não tem o CardDeVaga? Ele é da frente 1 e entra no desafio. Por hoje ponha <li key={vaga.id}>{vaga.titulo} · {vaga.empresa}</li> no lugar dele. Este lab é sobre o estado, não sobre o card.

// app/vagas/page.tsx — continua no servidor. Nenhuma linha "use client" aqui.
import { vagas } from "@/data/vagas";
import MuralDeVagas from "@/components/MuralDeVagas";

export default function Vagas() {
  // Continua saindo no TERMINAL: a página não virou de cliente.
  console.log("[servidor] montando a listagem");

  return (
    <>
      <h1>Vagas</h1>
      <MuralDeVagas vagas={vagas} />
    </>
  );
}
responda
  1. Sem o onChange, o campo deixou digitar? Por que isso não é bug?
  2. visiveis não é useState. Se fosse, o que quebraria — e quando?
  3. O console.log do lab 1 continua no terminal ou foi para o navegador? Por quê?
ver a resposta — depois de tentar

1. Não deixou, e ficou com cara de campo travado. Não é bug: é a peça funcionando. O value={busca} prende o campo ao estado, e sem onChange nada troca o estado — então o campo mostra sempre a mesma string. Isso se chama campo controlado: o campo é a janela para o dado, nunca o dono do dado. Quem manda é o estado, e o onChange é o único caminho de volta.

2. Você passaria a ter dois estados que precisam combinar: busca e visiveis. Funciona no primeiro dia. Quebra no dia em que aparecer um segundo jeito de mexer na lista — o filtro por área, no desafio — e alguém atualizar um e esquecer o outro. Aí a tela mente: mostra vagas que não batem com o que está escrito no campo, e o bug é dos difíceis, porque cada pedaço está certo sozinho. A regra da aula: se dá para calcular do que você já tem, não guarde. A conta roda de novo a cada renderização, e ela é barata.

3. Continua no terminal. A página não virou de cliente — quem tem a linha é o MuralDeVagas. E é a aula inteira em uma linha só: <MuralDeVagas vagas={vagas} />. A página busca os dados e entrega prontos; o componente de cliente cuida do que muda. Cada um faz o que só ele consegue fazer.

🎯 Do lab 4 para o desafio das quatro frentes

O desafio desta semana é o projeto do semestre — o Leque de Vagas — dividido em quatro frentes, uma por integrante. Cada frente entrega um componente de cliente com estado, e as quatro formas de estado são diferentes de propósito: no fim da semana a equipe inteira viu as quatro.

  • Frente 1 · Vaga — o contrato da equipe (data/vagas.ts), o card e a página de detalhe. Estado booleano: ver mais / ver menos.
  • Frente 2 · Empresa — quem publica: data/empresas.ts e a página da empresa. Estado que é texto escolhendo: abas Sobre / Vagas.
  • Frente 3 · Pessoa e candidatura — o formulário de candidatura. Campo controlado + lista.
  • Frente 4 · Busca e números — filtros, busca e as contagens do catálogo. Estado derivado + estado levantado. É o lab 4 crescendo.

Quem faz uma frente aqui tem uma frente irmã no curso de Spring Boot: lá a mesma equipe constrói a API do mesmo Leque de Vagas, com exatamente estas quatro divisões.

A combinação de 30 minutos, antes de qualquer um escrever tela: as frentes 2, 3 e 4 dependem do tipo Vaga. A frente 1 sobe data/vagas.ts primeiro, num commit só, e avisa a equipe — assim as outras três programam contra o tipo antes de as telas existirem. Segunda combinação: os empresaSlug das vagas têm que existir em data/empresas.ts. aurora-tech de um lado e auroratech do outro quebra a página da empresa, e ninguém descobre isso sozinho na véspera.

Prazo: até a aula 04, em 02/09, antes do início. E o que ficou de fora hoje tem endereço: a espera de verdade — dados que demoram, com Suspense e streaming — é a aula 04; guardar a candidatura para valer é a aula 05; filtro que sobrevive a compartilhar o link (o que mora na URL) é a aula 06.
