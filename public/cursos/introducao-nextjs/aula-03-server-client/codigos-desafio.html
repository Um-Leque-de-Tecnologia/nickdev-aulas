Aula 03 · código do desafio

As quatro frentes, linha por linha

O desafio resolvido e comentado, uma frente de cada vez. Use como referência quando travar — mas tente antes. O código aqui é curto de propósito: o que custa nesta semana não é digitar, é entender onde cada pedaço roda e o que o componente precisa lembrar.

🧩

Doze arquivos, quatro donos

Cada frente aparece com a sua cor: Vaga · Empresa · Pessoa e candidatura · Busca e números. Ache a sua e comece por ela.

Leia as outras três depois de entregar a sua. As quatro formas de estado desta semana são diferentes de propósito — booleano, texto que escolhe, campo controlado com lista, estado derivado. No fim da semana a equipe inteira viu as quatro, e quem só leu a própria frente viu um quarto da aula.

🧭

por que 12 vagas, e não 3

Porque a frente 4 filtra por área e conta quantas aceitam quem está começando. Com três vagas quase iguais, o filtro sempre devolve a lista inteira e o número nunca muda — o recurso funciona e ninguém consegue ver.

por que este arquivo não tem "use client"

Porque ele não tem nada para lembrar e não escuta nada. Recebe uma vaga por prop, devolve HTML. Se o componente não guarda estado e não tem evento, ele não precisa da linha — e enquanto ninguém de cliente o importar, ele não vira JavaScript no navegador.

Repare que ele acaba rodando dentro do MuralDeVagas, que é de cliente. Isso não é contradição: ele entra junto pela porta que o mural abriu. O que importa é que ninguém precisou escrever a linha aqui.

components/DescricaoDaVaga.tsx
"use client";
// ↑ Primeira linha do arquivo, antes de qualquer import.
//   Sem ela não existe useState, e o onClick lá embaixo não tem quem escute.

import { useState } from "react";

// Fora do componente de propósito: é uma constante do arquivo. Não muda,
// e não tem por que nascer de novo a cada renderização.
const LIMITE = 180;

export default function DescricaoDaVaga({ texto }: { texto: string }) {
  // A memória do componente. Um booleano: aberta ou fechada.
  // [o valor, como mudar] = useState(o valor inicial)
  const [aberta, setAberta] = useState(false);

  // Estado derivado: as duas linhas abaixo saem do texto e do estado.
  // Nenhuma vira useState. Se dá pra calcular, não guarde.
  const cabeInteira = texto.length <= LIMITE;
  const visivel = aberta || cabeInteira ? texto : texto.slice(0, LIMITE) + "…";

  return (
    <div>
      <p>{visivel}</p>
      {!cabeInteira && (
        // setAberta(!aberta) — nunca "aberta = !aberta".
        // Mexer na variável na mão não avisa o React de nada.
        <button type="button" onClick={() => setAberta(!aberta)}>
          {aberta ? "ver menos ▲" : "ver mais ▼"}
        </button>
      )}
    </div>
  );
}
por que este arquivo precisa de "use client" e a página da vaga não

Porque a diferença não é o assunto, é o momento. A página da vaga faz todo o trabalho dela antes de a tela existir: acha a vaga pelo id e escreve o HTML. Terminou, mandou, foi embora.

Este componente faz o trabalho dele depois. O clique no "ver mais" acontece quando a página já está na tela, no dedo de quem acessou — e alguém precisa estar no navegador para escutar. Esse alguém é o JavaScript que a linha "use client" mandou baixar.

Marque a folha, não a raiz. Se a linha subisse para a página, a descrição, o título e a lista inteira desceriam para o navegador junto — sendo que nada disso muda depois de aparecer.

components/BotaoCopiarLink.tsx
"use client";

import { useState } from "react";

export default function BotaoCopiarLink({ titulo }: { titulo: string }) {
  const [copiado, setCopiado] = useState(false);

  return (
    <button
      type="button"
      onClick={() => {
        // location e navigator só existem no navegador.
        // É a segunda razão de este arquivo ser de cliente.
        navigator.clipboard.writeText(location.href);
        setCopiado(true);
      }}
    >
      {copiado ? `✓ Link de “${titulo}” copiado` : "🔗 Copiar link"}
    </button>
  );
}
por que o alert sumiu

Na aula 02 este botão avisava com alert(), porque a turma ainda não tinha estado. O alert não é bonito, mas era honesto: era a única forma de o botão dizer "deu certo" sem memória.

Agora o retorno mora no copiado. É a mesma tela, com memória. O botão lembra que foi clicado, e o texto dele passa a ser calculado a partir dessa lembrança.

Uma observação de quem já viu isso quebrar na apresentação: navigator.clipboard exige contexto seguro. Em localhost e em HTTPS funciona; num arquivo aberto direto do disco, não.

por que o slug é o campo mais perigoso do projeto

Porque ele é o único dado que duas pessoas diferentes escrevem à mão. Você escreve "nuvem-rosa" aqui; a frente 1 escreve "nuvem-rosa" lá. Se uma das duas escrever "nuvemrosa", o TypeScript não reclama — os dois são string válida — e a página da empresa cai no notFound().

Combine na primeira reunião: minúsculas, sem acento, hífen no lugar do espaço. E confira a lista das duas frentes lado a lado antes de abrir o pull request.

components/AbasDaEmpresa.tsx
"use client";

import { useState } from "react";
import Link from "next/link";
import type { Vaga } from "@/data/vagas";

export default function AbasDaEmpresa({
  sobre,
  vagas,
}: {
  sobre: string;
  vagas: Vaga[];
}) {
  // O estado aqui é TEXTO, não booleano: "sobre" ou "vagas".
  // Com booleano, a terceira aba (que um dia vem) não caberia.
  const [aba, setAba] = useState("sobre");

  return (
    <div>
      <div className="abas">
        <button
          type="button"
          // A classe é calculada do estado. Isto é estado derivado também:
          // nada de um useState só para guardar "qual botão está aceso".
          className={aba === "sobre" ? "aba ativa" : "aba"}
          onClick={() => setAba("sobre")}
        >
          Sobre
        </button>
        <button
          type="button"
          className={aba === "vagas" ? "aba ativa" : "aba"}
          onClick={() => setAba("vagas")}
        >
          Vagas ({vagas.length})
        </button>
      </div>

      {aba === "sobre" ? (
        <p>{sobre}</p>
      ) : (
        <ul className="lista">
          {vagas.map((vaga) => (
            <li key={vaga.id}>
              <Link href={`/vagas/${vaga.id}`}>{vaga.titulo}</Link>
            </li>
          ))}
        </ul>
      )}
    </div>
  );
}
por que texto e não dois booleanos

A tentação é const [mostraSobre, setMostraSobre] = useState(true) e const [mostraVagas, setMostraVagas] = useState(false). Funciona hoje. E um dia alguém esquece de desligar um dos dois, e a tela mostra as duas abas juntas — ou nenhuma.

Dois estados que precisam combinar são uma dupla que um dia vai brigar. Um estado só, que guarda qual aba está aberta, não tem como ficar inconsistente: ele só vale uma coisa por vez.

De quebra, quando a equipe quiser uma aba "Cultura" na aula 08, é uma string a mais e nenhum booleano novo.

app/empresas/[slug]/page.tsx
// SEM "use client". É uma página de servidor, e continua sendo.
import { notFound } from "next/navigation";
import { vagas } from "@/data/vagas";
import { empresas } from "@/data/empresas";
import AbasDaEmpresa from "@/components/AbasDaEmpresa";

export default async function PaginaDaEmpresa({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  // await params: igualzinho à aula 02. A fronteira não mudou isso.
  const { slug } = await params;
  const empresa = empresas.find((e) => e.slug === slug);
  if (!empresa) notFound();

  // O cruzamento acontece AQUI, no servidor, antes de a tela existir.
  const vagasDaEmpresa = vagas.filter((v) => v.empresaSlug === slug);

  return (
    <article>
      <h1>{empresa.nome}</h1>
      {/* Um texto e uma lista de objetos atravessam a fronteira sem susto. */}
      <AbasDaEmpresa sobre={empresa.sobre} vagas={vagasDaEmpresa} />
    </article>
  );
}
por que a lista já vem filtrada do servidor

Porque o componente de abas não tem nada que ver com o cruzamento entre vaga e empresa. Ele recebe as vagas desta empresa e cuida de uma coisa só: qual aba está aberta.

Se o filtro estivesse dentro do componente de cliente, o navegador precisaria receber as doze vagas para mostrar as duas que importam. Filtre no servidor o que dá para filtrar no servidor — o que desce pela fronteira é o que a pessoa vai usar.

FRENTE 3

Pessoa e candidatura

campo controlado + lista

Quem se candidata. É a frente com mais estado da semana: cinco useState, dois valores derivados, e uma lista que cresce e diminui na mão de quem preenche.

components/FormularioDeCandidatura.tsx
"use client";

import { useState } from "react";

export default function FormularioDeCandidatura({
  tituloDaVaga,
}: {
  tituloDaVaga: string;
}) {
  // Cinco memórias. Cada uma guarda uma coisa que o servidor não tem
  // como saber: o que a pessoa digitou nesta aba, agora.
  const [nome, setNome] = useState("");
  const [email, setEmail] = useState("");
  const [rascunho, setRascunho] = useState("");
  const [habilidades, setHabilidades] = useState<string[]>([]);
  const [enviada, setEnviada] = useState(false);

  // Estado derivado — nada disto vira useState.
  // "O botão está habilitado?" é uma conta, não uma lembrança.
  const emailParece = email.includes("@") && email.includes(".");
  const podeEnviar = nome.trim() !== "" && emailParece && habilidades.length > 0;

  function adicionar() {
    const nova = rascunho.trim();
    // vazio ou repetido: não faz nada, e não some com o que a pessoa digitou
    if (nova === "" || habilidades.includes(nova)) return;
    setHabilidades([...habilidades, nova]); // lista NOVA, não push
    setRascunho("");
  }

  // Duas telas no mesmo arquivo. O "enviada" decide qual delas aparece.
  if (enviada) {
    return (
      <div className="ok">
        <h3>Candidatura registrada ✓</h3>
        <p>
          {nome}, guardamos a sua candidatura para <strong>{tituloDaVaga}</strong> com{" "}
          {habilidades.length} habilidade(s).
        </p>
        {/* Voltar significa desligar este estado: os outros quatro continuam lá. */}
        <button type="button" onClick={() => setEnviada(false)}>
          corrigir alguma coisa
        </button>
      </div>
    );
  }

  return (
    <form
      onSubmit={(e) => {
        // sem isto o navegador recarrega a página e apaga tudo
        e.preventDefault();
        setEnviada(true);
      }}
    >
      <label>
        Nome
        {/* value + onChange andam JUNTOS. Só o value prende o campo. */}
        <input value={nome} onChange={(e) => setNome(e.target.value)} />
      </label>

      <label>
        E-mail
        <input type="email" value={email} onChange={(e) => setEmail(e.target.value)} />
      </label>
      {/* o aviso só aparece depois que a pessoa começou a digitar */}
      {email !== "" && !emailParece && <p className="erro">Isso não parece um e-mail.</p>}

      <label>
        Habilidades
        <input
          value={rascunho}
          onChange={(e) => setRascunho(e.target.value)}
          onKeyDown={(e) => {
            if (e.key === "Enter") {
              // dentro de um form, Enter envia. Aqui ele adiciona.
              e.preventDefault();
              adicionar();
            }
          }}
        />
      </label>
      <button type="button" onClick={adicionar}>
        adicionar
      </button>

      <ul className="chips">
        {habilidades.map((h) => (
          <li key={h}>
            {h}
            <button
              type="button"
              aria-label={`remover ${h}`}
              // filter também devolve lista NOVA. É o mesmo princípio.
              onClick={() => setHabilidades(habilidades.filter((x) => x !== h))}
            >
              ×
            </button>
          </li>
        ))}
      </ul>

      {/* disabled sai de podeEnviar, que é conta. Não há useState de botão. */}
      <button type="submit" disabled={!podeEnviar}>
        Enviar candidatura
      </button>
    </form>
  );
}
por que [...habilidades, nova] e nunca push

habilidades.push(nova) mexe na lista que já existe. Depois dele, a lista tem um item a mais — e continua sendo a mesma lista. O React compara o que você entregou com o que ele tinha guardado, vê que é o mesmo objeto, conclui que nada mudou e não redesenha. Você digita, aperta adicionar, e a tela fica parada.

[...habilidades, nova] monta uma lista nova: copia os itens que já estavam lá e acrescenta o último. Objeto diferente, diferença visível, tela redesenhada.

É a mesma razão de o remover usar filter: ele também devolve lista nova. Estado se troca, não se remenda.

por que podeEnviar não é um useState

Porque ele é resposta de uma pergunta que já tem os dados: tem nome, o e-mail parece e-mail, tem ao menos uma habilidade. Se você guardasse esse resultado num estado, precisaria lembrar de recalcular em três lugares diferentes — no onChange do nome, no do e-mail e no adicionar.

Esquecer um deles é a origem clássica do bug "o botão continua apagado mesmo com tudo preenchido". Sendo const, a conta refaz sozinha a cada renderização. Se dá pra calcular do que você já tem, não guarde.

app/vagas/[id]/page.tsx
// SEM "use client" — e é a página que usa MAIS componentes de cliente.
import Link from "next/link";
import { notFound } from "next/navigation";
import { vagas } from "@/data/vagas";
import BotaoCopiarLink from "@/components/BotaoCopiarLink";
import DescricaoDaVaga from "@/components/DescricaoDaVaga";
import FormularioDeCandidatura from "@/components/FormularioDeCandidatura";

export default async function PaginaDaVaga({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const vaga = vagas.find((v) => v.id === id);
  if (!vaga) notFound();

  return (
    <article>
      {/* Título e ficha: vêm prontos do servidor. Não mudam depois. */}
      <h1>{vaga.titulo}</h1>
      <p>
        {vaga.empresa} · {vaga.area} · {vaga.senioridade} · {vaga.local}
      </p>

      {/* Daqui pra baixo, três componentes de cliente lado a lado.
          Cada um tem a própria memória, e nenhum sabe do outro. */}
      <BotaoCopiarLink titulo={vaga.titulo} />
      <DescricaoDaVaga texto={vaga.descricao} />

      <Link href={`/empresas/${vaga.empresaSlug}`}>ver a empresa</Link>

      <h2>Candidatar-se</h2>
      <FormularioDeCandidatura tituloDaVaga={vaga.titulo} />
    </article>
  );
}
por que a candidatura some quando você recarrega

Porque estado é isso: o que só existe naquela aba, naquele momento. O useState vive na memória do navegador. Fechou a aba, recarregou a página, apertou F5 sem querer — a memória zera e o formulário volta vazio. Não é bug do seu código.

Guardar de verdade tem duas metades, e as duas têm data marcada. Mandar o formulário para o servidor é Server Action, aula 05 (09/09). Escrever num banco, para continuar lá amanhã, é aula 06 (16/09).

Hoje o objetivo é menor e é suficiente: a tela responde. Quem preenche vê o que digitou, vê a habilidade virar chip, vê o botão acender. Isso é o trabalho do cliente, e ele não muda quando o banco chegar.

FRENTE 4

Busca e números

estado derivado + estado levantado

A frente que costura tudo. Você entrega o mural que guarda a busca e a área escolhida, os filtros que não guardam nada, e as contagens que mudam sozinhas porque são conta, não lembrança.

components/MuralDeVagas.tsx
"use client";

import { useState } from "react";
import Filtros from "./Filtros";
import CardDeVaga from "./CardDeVaga";
import type { Vaga } from "@/data/vagas";

export default function MuralDeVagas({ vagas }: { vagas: Vaga[] }) {
  // O estado mora AQUI, no pai comum dos filtros e da lista.
  // Dois componentes precisam da busca: quem mora sozinho não serve.
  const [busca, setBusca] = useState("");
  const [area, setArea] = useState("Todas");

  // Estado derivado: recalculado a cada renderização, nunca guardado.
  // new Set tira os repetidos; o espalhamento devolve array de novo.
  const areas = ["Todas", ...new Set(vagas.map((v) => v.area))];

  const visiveis = vagas.filter((vaga) => {
    const termo = busca.toLowerCase();
    // tudo minúsculo dos dois lados: quem busca "React" acha "react"
    const bateBusca =
      vaga.titulo.toLowerCase().includes(termo) ||
      vaga.empresa.toLowerCase().includes(termo);
    const bateArea = area === "Todas" || vaga.area === area;
    return bateBusca && bateArea;
  });

  // Mais uma conta. Muda sozinha quando visiveis muda.
  const aceitamIniciante = visiveis.filter((v) => v.aceitaIniciante).length;

  return (
    <section>
      {/* O dado desce por prop (busca, area) e o aviso sobe por função. */}
      <Filtros
        busca={busca}
        aoMudarBusca={setBusca}
        area={area}
        aoMudarArea={setArea}
        areas={areas}
      />

      <p className="numeros">
        <strong>{visiveis.length}</strong> de {vagas.length} vagas ·{" "}
        <strong>{aceitamIniciante}</strong> aceitam quem está começando
      </p>

      {/* A lista vazia é um estado da tela, não um esquecimento. */}
      {visiveis.length === 0 ? (
        <p>Nenhuma vaga com esse filtro. Tente outra palavra.</p>
      ) : (
        <ul className="lista">
          {visiveis.map((vaga) => (
            <CardDeVaga key={vaga.id} vaga={vaga} />
          ))}
        </ul>
      )}
    </section>
  );
}
por que areas e visiveis são const, e não useState

Porque nenhuma das duas é lembrança: as duas são conta. As áreas saem das vagas. As visíveis saem das vagas, da busca e da área. Todo mundo já está aqui dentro.

Imagine que visiveis fosse estado. Toda vez que a busca mudasse, você precisaria lembrar de recalcular e chamar setVisiveis. Toda vez que a área mudasse, de novo. Um dia alguém acrescenta um terceiro filtro e esquece de um dos caminhos — e a tela passa a mentir: os chips dizem "Front-end" e a lista mostra vaga de Dados.

Sendo const, o erro não tem onde nascer. A função roda de novo, a conta refaz, a lista bate com o filtro. Guarde só o que a pessoa escolheu; o resto, calcule.

por que aoMudarBusca={setBusca} pode, se a aula 02 disse que função não atravessa

A regra da aula 02 continua verdadeira, e ela tem um lado: de servidor para cliente. Uma função que existe no servidor não cabe no HTML que viaja pela rede — não dá para embrulhar código executável num texto e mandar. Por isso a página não pode passar onClick={fazAlgo} para um componente de cliente.

Aqui não há travessia nenhuma. MuralDeVagas tem "use client", e Filtros entra junto por ser importado por ele. Os dois moram do mesmo lado da linha, no navegador. Dentro do cliente, função circula à vontade — é assim que o aviso sobe do filho para o pai.

Se essa distinção ficou embaçada em agosto, é normal: a aula 02 mostrou metade da regra porque a outra metade ainda não fazia sentido.

components/Filtros.tsx
// Sem "use client": quem importa este arquivo já é de cliente.
// A linha marca a porta, não cada móvel da casa.

export default function Filtros({
  busca,
  aoMudarBusca,
  area,
  aoMudarArea,
  areas,
}: {
  busca: string;
  // o tipo de uma função: recebe texto, não devolve nada
  aoMudarBusca: (valor: string) => void;
  area: string;
  aoMudarArea: (valor: string) => void;
  areas: string[];
}) {
  // Nenhum useState aqui. Este componente não lembra de nada:
  // ele mostra o que recebe e avisa quando alguém mexe.
  return (
    <div className="filtros">
      <input
        type="search"
        placeholder="Buscar por título ou empresa"
        value={busca}
        // sem este onChange o campo não deixa digitar
        onChange={(e) => aoMudarBusca(e.target.value)}
      />

      <div className="chips">
        {areas.map((nome) => (
          <button
            key={nome}
            type="button"
            className={nome === area ? "chip ativo" : "chip"}
            onClick={() => aoMudarArea(nome)}
          >
            {nome}
          </button>
        ))}
      </div>
    </div>
  );
}
por que este arquivo não tem "use client", mesmo cheio de onChange e onClick

Porque MuralDeVagas tem. E MuralDeVagas importa este arquivo. A linha marca a porta, não cada móvel da casa: quando o Next empacota o mural para o navegador, tudo que ele importa vai junto — inclusive este componente.

Repetir a linha aqui não daria erro. Não daria nada: seria uma linha sem efeito, e quem lesse o projeto depois ficaria com a impressão errada de que todo arquivo com onClick precisa dela.

O teste é sempre este: quem importa este arquivo? Se a resposta é "um componente de cliente", ele já está do lado de dentro. Se a resposta é "uma página", aí sim a linha é necessária.

app/vagas/page.tsx
import { vagas } from "@/data/vagas";
import MuralDeVagas from "@/components/MuralDeVagas";

export default function Vagas() {
  // Continua saindo no TERMINAL: a página não virou de cliente.
  // É a prova mais rápida de que a fronteira ficou onde você deixou.
  console.log("[servidor] montando a listagem");

  return (
    <>
      <h1>Vagas</h1>
      {/* A página busca o dado e entrega pronto. Quem cuida do
          que muda é o mural — e só ele desce para o navegador. */}
      <MuralDeVagas vagas={vagas} />
    </>
  );
}
por que /vagas continua sem "use client" tendo um componente interativo dentro

Porque a página não é interativa — o mural é. A página faz uma coisa só: pega as vagas e entrega. Ela não escuta clique, não guarda nada, não muda depois que apareceu na tela. Servidor usando cliente é o caminho fácil; o contrário é que tem regra.

Se você escrever "use client" no topo desta página, funciona. E aí o título e todo o resto descem para o navegador sem precisar, e o console.log ganha um segundo lugar: continua saindo no terminal, porque a página segue sendo pré-renderizada no servidor, e passa a sair também no console do navegador. A linha não tira nada do servidor — ela acrescenta o navegador. Esse é o teste de um segundo — recarregue com o terminal e o console abertos e veja em quantos lugares a linha aparece.

A fronteira certa desta página tem o tamanho exato do que muda: o campo de busca, os chips, a lista e os dois números.

🚫 os erros que este código evita

Sete erros. Todos vão aparecer nesta semana em algum repositório — é a estatística de todo semestre. A terceira coluna mostra onde o código acima já fecha a porta para cada um.

o que você escreve o que acontece, e por quê onde este código escapa
aberta = true A tela não muda. O React não fica sabendo — só o setAberta avisa que houve mudança. DescricaoDaVaga troca o valor com setAberta(!aberta), nunca na mão.
<input value={busca} /> sem onChange O campo não deixa digitar. Não é bug: o valor está preso ao estado, e nada está trocando o estado. Em Filtros e no formulário, value e onChange aparecem sempre no mesmo elemento.
habilidades.push(nova) A tela não atualiza. É a mesma lista — o React compara a lista com ela mesma e não vê diferença. setHabilidades([...habilidades, nova]) monta lista nova; o remover usa filter pelo mesmo motivo.
setBusca("a"); console.log(busca) Mostra o valor antigo. busca é a foto daquele render; o valor novo chega no render seguinte. Nenhum arquivo lê o estado logo depois de mudá-lo. Quem precisa do valor recém-digitado usa e.target.value.
"use client" em page.tsx Tudo desce pro navegador. A fronteira subiu pra raiz — marque a folha. As três páginas continuam sem a linha, e o console.log de /vagas prova isso no terminal.
dois estados que precisam combinar Um dia a tela mente: os chips dizem uma coisa e a lista mostra outra. Derive em vez de guardar. visiveis, areas, cabeInteira, emailParece e podeEnviar são todos const.
onClick num arquivo sem "use client" Erro citando "Event handlers cannot be passed to Client Component props". O servidor não tem quem escute o clique. Filtros tem onClick e não tem a linha — e funciona, porque quem o importa tem.

Os quatro testes de trinta segundos

  • Frente 1: abra uma vaga com descrição longa. O "ver mais" aparece; numa vaga curta, não aparece botão nenhum.
  • Frente 2: troque de aba e volte. Sem recarregar a página, sem piscar.
  • Frente 3: adicione a mesma habilidade duas vezes. Ela entra uma vez só, e o campo não some com o que você digitou.
  • Frente 4: digite uma palavra que não existe. Os números vão a zero e a mensagem de lista vazia aparece.

E o teste que vale pelos quatro: recarregue /vagas com o terminal do npm run dev visível. O [servidor] montando a listagem tem que sair lá, e nunca no console do navegador.
