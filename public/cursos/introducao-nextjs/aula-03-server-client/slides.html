O dia em que isso não basta

Você quer um botão Copiar link na página da vaga. A pessoa clica, o endereço vai para a área de transferência dela.

📄 components/BotaoCopiarLink.tsx · sem a linha
export default function BotaoCopiarLink() {
  return (
    <button
      type="button"
      onClick={() => navigator.clipboard.writeText(location.href)}
    >
      🔗 Copiar link
    </button>
  );
}
Error: Event handlers cannot be passed to Client Component props. <button type="button" onClick={function onClick}> ^^^^^^^^^^^^^^^^^^ If you need interactivity, consider converting part of this to a Client Component.

Em português: "você me deu uma função para escutar o clique, e eu não tenho quem escute". O clique acontece no dedo da pessoa, depois que a página já está na tela — e a essa altura o servidor terminou o trabalho e foi embora. navigator e location também só existem lá, no navegador dela.

É essa a linha

📄 components/BotaoCopiarLink.tsx
"use client";
1Primeira linha do arquivo, antes de qualquer import. Com aspas e ponto e vírgula: não é comentário, é uma instrução para o Next.
2Ela não tira o arquivo do servidor — ela acrescenta o navegador. O HTML continua vindo pronto; o que muda é que agora o código também viaja junto, para o clique ter quem o escute.
3Marque a folha, não a raiz. Tudo que está dentro de um componente de cliente viaja com ele. Se a linha for para o page.tsx, a página inteira desce para o navegador junto.

Um arquivo com essa linha é um Client Component. Sem ela, é um Server Component — que é o padrão. Você nunca escreve "use server" para isso: o servidor já é o normal.

// conceito 2 · o mal-entendido nº 1

A linha marca a porta, não cada móvel

Quem é importado por um componente de cliente já entra junto. Não repita a linha em cada arquivo.

app/vagas/page.tsx servidor · sem a linha └─ MuralDeVagas.tsx "use client" ← a fronteira corta aqui ├─ Filtros.tsx entra junto · não repete a linha └─ CardDeVaga.tsx entra junto · não repete a linha

O que a turma faz

Põe "use client" em todo arquivo que tem um botão dentro, por precaução. Aí a linha vira ruído: ninguém mais sabe onde a fronteira realmente está.

O que fazer

Uma linha por porta de entrada. Do MuralDeVagas para baixo, é tudo navegador — e repetir a linha não muda nada, só engana quem lê.

Repare no Filtros.tsx: ele tem onChange, tem onClick, e mesmo assim não tem a linha. Ele já nasceu do lado de dentro.

// conceito 3

O botão que não muda nada

O clique funciona. E a tela continua igual. Este é o problema da segunda metade da aula. Um botão de curtir a vaga: você guarda a resposta numa variável e troca ela no clique. Parece certo.

📄 rascunho na aula · não é arquivo do projeto
"use client";

export default function BotaoCurtir() {
  let curtido = false;   // uma variável comum

  return (
    <button
      type="button"
      onClick={() => { curtido = true; }}
    >
      {curtido ? "★ curtida" : "☆ curtir"}
    </button>
  );
}
pense dez segundos antes de ler a resposta

O clique acontece. A variável curtido vira true — dá para conferir com um console.log dentro do onClick. Então por que a estrela não muda na tela?

Porque a função roda de novo

Um componente é uma função. Desenhar a tela é chamar essa função. E a cada chamada, toda variável de dentro nasce do zero.

1️⃣
Render 1a função roda
curtido = false
a tela mostra ☆
→
👆
Você clicaa variável daquela
rodada vira true
e ninguém foi avisado
→
2️⃣
Render 2a função roda de novo
let curtido = false
a tela mostra ☆

O que você mudou

Uma variável que morre no fim da rodada. Ninguém guardou, ninguém foi avisado, e no render seguinte ela nasce false de novo.

O que faltava

Alguém fora da função para segurar o valor entre uma rodada e outra — e para avisar o React de que a tela precisa ser refeita.

A função do componente não tem memória. Guarde essa frase: metade dos bugs de estado da sua vida começa por esquecê-la.

// conceito 3 · a solução

useState: a memória do componente

Uma linha, três coisas. Leia da esquerda para a direita.

const [curtido, setCurtido] = useState(false);
       │        │                      │
       │        │                      └─ o valor inicial — vale só na primeira vez
       │        └─ como mudar — a única forma de avisar o React
       └─ o valor agora — você lê, nunca escreve nele
1Você lê a variável, nunca escreve nela. curtido = true não é erro de sintaxe — é pior: não acontece nada, e você fica quinze minutos procurando o motivo.
2Só a função set avisa o React. É por isso que ela existe. Ela guarda o valor novo e pede uma tela nova; a variável sozinha não pede nada a ninguém.
3O valor inicial só vale na primeira vez. Nos renders seguintes o React devolve o que ele guardou e ignora o que está dentro do useState(...).

O nome entre colchetes é seu: [busca, setBusca], [aberta, setAberta], [aba, setAba]. A convenção set + nome não é obrigação da linguagem — é o que faz a próxima pessoa entender o seu arquivo em três segundos.

O que acontece quando você chama setCurtido

👆
Você chamasetCurtido(true)
→
🧠

fora da sua função
→
🔁
Ele roda a sua função de novoe agora curtido
já vem true
→
✨
A tela mudasó o pedaço
que ficou diferente

Você não mexe na tela. Você mexe no dado — e a tela vem atrás.

Isso é a virada de chave do curso inteiro. Nada de procurar o botão pelo id e trocar o texto dele na mão: você troca o valor, e o React refaz o que ficou diferente.

Efeito colateral que confunde: logo depois de setBusca("a"), um console.log(busca) mostra o valor antigo. Não está quebrado — busca é a foto daquela rodada. O valor novo chega no render seguinte.

// conceito 4

Campo controlado: value anda com onChange

Quando o value do campo vem do estado, quem manda no que aparece ali é o estado — e mais ninguém.

o campo trava 
const [busca, setBusca] = useState("");

<input value={busca} />

// você digita e nada aparece.

O valor está preso a busca, que continua "". Nada troca o estado, então nada muda. Isso não é bug do React — é o combinado sendo cumprido à risca.

o campo responde 
const [busca, setBusca] = useState("");

<input
  value={busca}
  onChange={(e) => setBusca(e.target.value)}
/>

Cada tecla chama setBusca, o React guarda, roda a função de novo e o campo desenha o valor novo. O ciclo do slide 9, uma letra por vez.

Vantagem de ter o texto no estado: agora o resto da tela também sabe o que a pessoa digitou. É isso que faz a lista filtrar no lab 4.

⭐ conceito 5 · estado derivado · estado que é lista

Duas regras que salvam a semana

regra 1 · se dá para calcular, não guarde
dois estados 
const [busca, setBusca] = useState("");
const [visiveis, setVisiveis] = useState(vagas);

// e agora, em TODO lugar que muda a busca,
// você tem que lembrar de arrumar a outra:
setBusca(valor);
setVisiveis(vagas.filter(...));

Esqueceu uma das duas linhas — num botão de limpar, num filtro novo — e a tela passa a mentir: o campo diz uma coisa, a lista mostra outra.

um estado e uma conta 
const [busca, setBusca] = useState("");

// não é estado: é uma conta refeita a cada render
const visiveis = vagas.filter((vaga) =>
  vaga.titulo.toLowerCase().includes(busca.toLowerCase())
);

const aceitamIniciante =
  visiveis.filter((v) => v.aceitaIniciante).length;

A função roda de novo a cada mudança — lembra? Então a conta se refaz sozinha. Não tem como desalinhar: só existe uma fonte da verdade.

Dois estados que precisam combinar são uma dupla que um dia vai brigar. Antes de escrever um useState, pergunte: isso eu tenho como calcular do que já está aqui? Se tem, é conta, não é estado.

regra 2 · lista nova, nunca a mesma

O formulário de candidatura guarda as habilidades que a pessoa adiciona. Aqui mora o erro mais teimoso do dia.

a tela não atualiza 
function adicionar() {
  habilidades.push(nova);
  setHabilidades(habilidades);
}

O push mexe dentro da lista que já existe. Você entrega ao React a mesma lista de antes.

a tela atualiza 
function adicionar() {
  const nova = rascunho.trim();
  if (nova === "" || habilidades.includes(nova)) return;
  setHabilidades([...habilidades, nova]); // lista NOVA
  setRascunho("");
}

Os três pontinhos espalham o que já tinha dentro de uma lista recém-criada, e o item novo entra no fim. É outra lista.

por quê

Quando você chama a função set, o React compara o que chegou com o que ele já tinha guardado. Com push, ele compara a lista com ela mesma — são o mesmo objeto na memória. Não vê diferença, não refaz a tela. Vale igual para remover: setHabilidades(habilidades.filter(...)) devolve uma lista nova, e por isso funciona.

// conceito 6

Onde o estado mora

O campo de busca está no Filtros. A lista está no MuralDeVagas. Os dois precisam do mesmo texto. Então o estado sobe: ele mora no pai comum.

quem guarda
📄 components/MuralDeVagas.tsx
"use client";

export default function MuralDeVagas({ vagas }) {
  const [busca, setBusca] = useState("");

  return (
    <Filtros
      busca={busca}
      aoMudarBusca={setBusca}
    />
  );
}
quem só recebe
📄 components/Filtros.tsx
// Sem "use client": quem importa já é de cliente.

export default function Filtros({ busca, aoMudarBusca }) {
  return (
    <input
      value={busca}
      onChange={(e) => aoMudarBusca(e.target.value)}
    />
  );
}

Dado desce por prop, aviso sobe por função. O Filtros não guarda nada e não decide nada: ele mostra o que recebeu e avisa quando a pessoa mexeu. Componente burro é componente reaproveitável.

Função não atravessa a fronteira — mas dentro do cliente ela circula à vontade

Alguém aí travou nesse par: "mas você disse que função não pode ir por prop". Disse. A regra vale de servidor para cliente. Entre dois componentes de cliente, é o normal do dia a dia.

servidor → cliente
📄 app/vagas/page.tsx · servidor
export default function Vagas() {
  function aoMudarBusca(valor) { /* ... */ }

  return <MuralDeVagas aoMudarBusca={aoMudarBusca} />;
}
// Error: Functions cannot be passed directly
// to Client Components.

O que sai do servidor vira texto para viajar pela internet. Um número vira "42" e volta a ser número do outro lado. Uma função não tem como virar texto.

cliente → cliente
📄 components/MuralDeVagas.tsx · "use client"
const [busca, setBusca] = useState("");

return <Filtros busca={busca} aoMudarBusca={setBusca} />;

// nenhum erro: os dois rodam no navegador.

Nada precisou virar texto: ninguém atravessou nada. O setBusca é uma função que já está na memória do navegador, entregue a outro arquivo que também está lá.

Como saber de que lado você está? Suba a árvore até achar a linha. Se existe um "use client" acima de você, você é cliente e passa função à vontade. Se não existe, você é servidor — e aí só dado atravessa.

E repare: a app/vagas/page.tsx continua sem a linha. O console.log do lab 1 continua saindo no terminal — a fronteira desceu para a folha, a página não mudou de lado.

O que fica de hoje

  • Servidor é o padrão. Todo arquivo seu roda lá, a menos que você diga o contrário — e "use client" não tira do servidor, acrescenta o navegador.
  • A linha marca a porta, não cada móvel. Marque a folha, e quem for importado por ela entra junto.
  • A função do componente não tem memória. Variável comum nasce do zero a cada render; useState é o que sobrevive entre as rodadas.
  • Você não mexe na tela, mexe no dado. Só a função set avisa o React — e lista nova, nunca push.
  • Se dá para calcular, não guarde. Dois estados que precisam combinar são uma dupla que um dia vai brigar.
