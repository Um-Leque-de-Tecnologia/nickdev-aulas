O primeiro “use client” do LequePlay

O ticket da sprint 1 resolvido e comentado, arquivo por arquivo. Use como referência quando travar — mas tente antes, e abra o PR com o que você entendeu, não com o que você copiou. O que custa nesta semana não é digitar: é saber onde cada pedaço roda e por que a página não levou a linha.

🧩

Você está mudando a história do repositório

Antes deste ticket, não existe um único "use client" no lequeplay-web. Todo arquivo é Server Component. Rode o grep abaixo antes de começar e guarde o resultado: vazio.

Não é exercício de mentira. É o primeiro componente de cliente de um projeto de verdade, e ele vai para o PR com o seu nome.

📐

As regras da casa que este ticket toca

Elas estão em .github/copilot-instructions.md, versionadas no repositório. Vale reler as quatro que valem aqui:

  • Server Component é o padrão. Só use "use client" quando houver estado, efeito, evento de usuário ou API de navegador — e diga por quê na descrição do PR.
  • Tailwind em classe utilitária no JSX. Sem CSS-in-JS, sem arquivo .css novo.
  • Arquivo em kebab-case, componente em PascalCase. Daí botao-copiar-link.tsx exportando BotaoCopiarLink — igual a card-midia.tsx exportando CardMidia.
  • Nada de any, nada de ! para calar o compilador.

PEÇA 1

Copiar link

clique + API de navegador

O botão que copia o endereço da página do título. É o exemplo da aula: ele tem as duas razões para ser de cliente ao mesmo tempo, no mesmo arquivo.

components/botao-copiar-link.tsx
"use client";
// ↑ Primeira linha do arquivo, antes de qualquer import. Antes de você,
//   esta linha não existia em lugar nenhum do lequeplay-web.

import { useState } from "react";

// Três situações possíveis, uma variável só. Nunca duas ao mesmo tempo:
// é o mesmo raciocínio do campo `tipo` em lib/tipos.ts, em miniatura.
type Situacao = "parado" | "copiado" | "falhou";

// Export nomeado, PascalCase, arquivo em kebab-case — igual ao CardMidia.
export function BotaoCopiarLink({ titulo }: { titulo: string }) {
  // A memória do componente. O servidor não tem como saber disto:
  // "já clicaram neste botão, nesta aba, agora".
  const [situacao, setSituacao] = useState<Situacao>("parado");

  async function copiar() {
    try {
      // navigator e window.location só existem no NAVEGADOR.
      // No servidor eles não estão definidos — e esta é a segunda
      // razão de o arquivo ser de cliente.
      await navigator.clipboard.writeText(window.location.href);
      setSituacao("copiado");
    } catch {
      // A área de transferência exige contexto seguro (localhost ou
      // HTTPS) e permissão. Quando ela nega, a pessoa precisa saber.
      // Sem este catch, o botão mente que copiou.
      setSituacao("falhou");
    }

    // Volta ao normal sozinho. Um alert() não faria isto: ele trava a
    // página e fica esperando alguém clicar em OK.
    setTimeout(() => setSituacao("parado"), 2000);
  }

  return (
    <div className="mt-5 flex flex-wrap items-center gap-3">
      <button
        type="button"
        onClick={copiar}
        // As mesmas classes do botão "Buscar" em app/midias/page.tsx.
        // Tailwind em utilitária, nenhum arquivo .css novo.
        className="rounded-md bg-violet-600 px-4 py-2 text-sm font-medium text-white transition hover:bg-violet-500"
      >
        🔗 Copiar link
      </button>

      {/*
        O retorno mora aqui, e não no nome do botão. Botão que troca de
        nome no meio do clique confunde quem usa leitor de tela e some
        com o alvo de quem está com o dedo em cima.
        role="status" faz o leitor anunciar a mudança SEM roubar o foco.
      */}
      <span role="status" className="text-sm text-zinc-400">
        {situacao === "copiado" && `Link de “${titulo}” copiado ✓`}
        {situacao === "falhou" && "Não consegui copiar. Copie da barra de endereço."}
      </span>
    </div>
  );
}
por que este arquivo precisa da linha, e a página do título não

Porque a diferença não é o assunto — é o momento. A página faz todo o trabalho dela antes de a tela existir: chama buscarMidia(slug), monta o HTML, manda e vai embora. Quando o seu navegador recebe aquilo, a página já acabou.

Este botão faz o trabalho dele depois. O clique acontece com a página já na tela, no dedo de quem acessou — e alguém precisa estar no navegador escutando. Esse alguém é o JavaScript que "use client" mandou baixar.

Marque a folha, não a raiz. Se a linha subisse para app/midias/[slug]/page.tsx, a capa, a ficha técnica e a lista de temporadas desceriam para o navegador junto — sendo que nada disso muda depois de aparecer. Você teria pago o transporte de tudo para animar um botão.

as duas razões, juntas, no mesmo arquivo

A regra do repositório diz: use a linha quando houver estado, efeito, evento de usuário ou API de navegador. Este arquivo tem duas dessas quatro, e vale separar as duas porque elas costumam vir sozinhas.

A primeira é o evento. onClick é uma função que precisa ficar de plantão esperando o clique. O servidor não fica de plantão: ele responde e desliga. Escrever onClick num arquivo de servidor é oferecer um telefone para quem já foi embora.

A segunda é a API de navegador. navigator.clipboard e window.location são coisas que o navegador tem. No Node que roda o servidor do Next elas não existem — e o erro que sai de lá é navigator is not defined, seco assim.

Guarde a distinção: um arquivo com onClick e sem navigator ainda precisa da linha. Um arquivo com navigator e sem clique nenhum também precisa. Aqui as duas apareceram no mesmo lugar, o que torna este botão o melhor exemplo do repositório — e o pior lugar para você chutar a resposta certa pelo motivo errado.

por que o retorno é estado, e não alert()

O alert("Copiado!") é a primeira coisa que vem à cabeça, e o Copilot sugere ele com frequência. Ele até funciona. Mas ele para a página inteira e obriga a pessoa a clicar em OK para continuar navegando — um pedágio para um recurso que ninguém pediu com tanta cerimônia.

Com estado, a resposta é da tela: aparece ao lado do botão, some sozinha em dois segundos, e não interrompe ninguém. É a mesma tela, com memória.

E tem o caso que o alert não cobre: quando a cópia falha. Com situacao, o mesmo lugar da tela diz outra coisa e a pessoa sabe o que fazer. Com alert, você precisaria de dois alert diferentes — ou, o que costuma acontecer, de nenhum, e o botão passa a mentir em silêncio.

Sobre acessibilidade: role="status" não é enfeite. Sem ele, quem navega por leitor de tela clica no botão e não recebe retorno nenhum — o texto muda na tela e ninguém avisa. O checklist do PR pergunta por isso.

PEÇA 2

Sinopse expansível

um booleano · ver mais / ver menos

Uma das opções do ticket. Aqui não tem navigator nem window: tem só o clique e a memória — e mesmo assim a linha é obrigatória. É o que prova que as duas razões são independentes.

components/sinopse-expansivel.tsx
"use client";
// Mesma linha, motivo mais enxuto: existe um onClick e existe um
// useState. Nenhuma API de navegador aparece neste arquivo.

import { useState } from "react";

// Fora do componente de propósito: é constante do arquivo. Não muda,
// e não tem por que nascer de novo a cada renderização.
const LIMITE = 140;

export function SinopseExpansivel({ texto }: { texto: string }) {
  // A memória: aberta ou fechada. Um booleano dá conta.
  // [o valor, como mudar] = useState(o valor inicial)
  const [aberta, setAberta] = useState(false);

  // Estado derivado: as duas linhas saem do texto e do booleano.
  // Nenhuma delas vira useState. Se dá para calcular, não guarde.
  const cabeInteira = texto.length <= LIMITE;
  const visivel = aberta || cabeInteira ? texto : `${texto.slice(0, LIMITE)}…`;

  return (
    <div className="mt-5">
      {/* max-w-prose e text-zinc-300: as MESMAS classes que o <p> tinha
          antes na página. A troca não pode mudar a aparência de nada. */}
      <p className="max-w-prose text-zinc-300">{visivel}</p>

      {!cabeInteira && (
        <button
          type="button"
          // setAberta(!aberta) — nunca "aberta = !aberta". Mexer na
          // variável na mão não avisa o React de nada, e a tela
          // fica parada enquanto você jura que clicou.
          onClick={() => setAberta(!aberta)}
          // aria-expanded diz ao leitor de tela em que estado o
          // controle está. É uma prop, não um comentário.
          aria-expanded={aberta}
          className="mt-2 text-sm font-medium text-violet-300 transition hover:text-violet-200"
        >
          {aberta ? "ver menos ▲" : "ver mais ▼"}
        </button>
      )}
    </div>
  );
}
por que 140, e não 300

Porque o número precisa bater com o dado real. As oito sinopses de data/midias.json têm entre 127 e 192 caracteres. Com LIMITE = 300, o botão nunca aparece — o recurso funciona e ninguém consegue ver. Com 140, quatro dos oito títulos mostram o "ver mais" e quatro não: você testa os dois caminhos sem inventar dado.

Abra /midias/sinais-de-carbono (192 caracteres, tem botão) e depois /midias/primeira-cadeira (127, não tem). Se os dois se comportarem igual, a sua condição está errada.

por que visivel é const e não um terceiro estado

Porque ele não é lembrança: é conta. O texto visível sai do texto inteiro mais o booleano. Se você o guardasse num useState, precisaria lembrar de recalcular toda vez que aberta mudasse — e o dia em que esquecer, a tela vai mostrar o texto cortado com o botão escrito "ver menos".

Dois estados que precisam combinar são uma dupla que um dia vai brigar. Sendo const, a conta se refaz sozinha a cada renderização e não tem como discordar de si mesma.

PEÇA 3

A página que não mudou de lado

servidor · await params · sem a linha

O trecho alterado de app/midias/[slug]/page.tsx. Ela passa a usar os dois componentes de cliente — e continua sendo um Server Component, async, com await params, exatamente como estava.

app/midias/[slug]/page.tsx — trecho alterado
// Repare no que NÃO está aqui: nenhuma linha "use client".
// E é a página que usa os dois componentes de cliente novos.
import type { Metadata } from "next";
import Image from "next/image";
import Link from "next/link";
import { notFound } from "next/navigation";
import { BotaoCopiarLink } from "@/components/botao-copiar-link";    // ← NOVO
import { SinopseExpansivel } from "@/components/sinopse-expansivel";  // ← NOVO
import { buscarMidia } from "@/lib/api";
import type { Midia } from "@/lib/tipos";

// … generateMetadata, formatarDuracao e FichaTecnica: intactos.
//    Você não encostou em nenhum dos três.

export default async function PaginaDaMidia({
  params,
}: PageProps<"/midias/[slug]">) {
  // params é Promise no Next 16 — continua sendo, e continua com await.
  // Nada disto mudou por causa dos componentes de cliente lá embaixo.
  const { slug } = await params;
  const midia = await buscarMidia(slug);

  if (!midia) notFound();

  return (
    <article>
      {/* … a trilha e a capa continuam como estavam … */}

      <div>
        <h1 className="text-2xl font-semibold tracking-tight sm:text-3xl">
          {midia.titulo}
        </h1>

        <p className="mt-2 text-sm text-zinc-500">
          {midia.notaMedia !== null
            ? `★ ${midia.notaMedia.toFixed(1)} · ${midia.totalAvaliacoes} avaliações`
            : "Ainda sem avaliações"}
        </p>

        {/* ANTES:
              <p className="mt-5 max-w-prose text-zinc-300">{midia.sinopse}</p>

            DEPOIS: o mesmo texto, agora com memória. O que atravessa a
            fronteira é uma STRING — não o objeto `midia` inteiro. Mande
            o menor pedaço que resolve. */}
        <SinopseExpansivel texto={midia.sinopse} />

        {/* O botão recebe só o título, para escrever a mensagem de
            retorno. O endereço ele descobre sozinho, no navegador. */}
        <BotaoCopiarLink titulo={midia.titulo} />

        <div className="mt-8">
          <FichaTecnica midia={midia} />
        </div>
      </div>

      {/* … a seção de temporadas continua igual, e continua no servidor … */}
    </article>
  );
}
por que a página continua async e com await params

Porque "use client" e async respondem a perguntas diferentes. async/await é sobre esperar: o slug chega numa Promise, e no Next 16 params e searchParams são Promise sempre. A fronteira servidor/cliente é sobre onde. Uma coisa não desfaz a outra.

Colocar um componente de cliente dentro de uma página de servidor não converte a página. Ela continua rodando no servidor, continua esperando o buscarMidia, e continua mandando HTML pronto. O que ela faz a mais é deixar um bilhete: "neste ponto do HTML, quando você chegar aí, ligue este JavaScript".

O teste de dez segundos: ponha um console.log("[servidor] montando", slug) logo depois do await params e recarregue a página. Ele tem que sair no terminal do npm run dev, e nunca no console do navegador. Se aparecer no navegador, alguma linha subiu para onde não devia.

por que os componentes recebem string, e não a Midia inteira

Seria mais rápido escrever <BotaoCopiarLink midia={midia} /> e resolver os dois de uma vez. Mas tudo que atravessa a fronteira é serializado e enviado ao navegador junto com o HTML. Mandar o objeto inteiro é mandar sinopse, capa, ficha, temporadas e créditos para um botão que só precisa do título.

E tem o efeito colateral bom: um componente que recebe texto: string serve para a sinopse de hoje e para o texto de uma resenha amanhã. Prop estreita é componente reaproveitável.

🤖 o que o Copilot sugere aqui, e como você percebe

Esta tabela não existe para você desconfiar de tudo. Existe porque o copiloto afirma com a mesma segurança quando acerta e quando erra — e no Next 16 ele erra num conjunto pequeno e muito previsível de lugares. Saber quais são é metade do trabalho.

o que ele sugere o que acontece como você percebe
onClick sem "use client" O clássico, e o mais útil de todos. No Next que ele viu no treino isso passava; o padrão mudou e ele não soube. A página quebra com "Event handlers cannot be passed to Client Component props". Leia o erro inteiro: ele está dizendo "você me deu uma função para escutar o clique, e eu não tenho quem escute".
"use client" no page.tsx É o que ele propõe depois que o erro acima aparece — e é a correção que dói mais tarde. A capa, a ficha e as temporadas passam a descer para o navegador. O erro some e você não sabe por quê. Este é o mais perigoso da lista, porque parece vitória. Confira: a linha tem que estar no componente, nunca em app/.
{ params }: { params: { slug: string } } Ele tipa params à mão, sem Promise, e lê params.slug direto. O TypeScript reclama, ou o slug vem undefined e todo título cai no notFound(). Use o tipo gerado PageProps<"/midias/[slug]">.
useEffect + fetch na tela Ele busca os dados no cliente, como faria num React sem servidor. Quebra a regra da casa: componente não chama fetch direto. Apareceu fetch( num arquivo que não é lib/api.ts. Se falta uma função lá, você a cria lá — não contorna.
document.execCommand("copy") API obsoleta, do tempo anterior ao navigator.clipboard. Funciona em alguns navegadores, por enquanto. Você não percebe pelo erro — não tem erro. Percebe pela data: quando a sugestão usa uma API que a MDN marca como deprecated, ela veio do passado do modelo.
const cor = nota || "sem nota" || descarta o 0, que é nota válida. O repositório usa ?? por isso, e o card-midia.tsx tem o comentário explicando. Um título com nota 0 aparece como "sem nota". Não quebra nada — só mente.
um arquivo .css ou styled-components Ele estiliza do jeito que viu mais vezes no treino, que não é o jeito deste projeto. Apareceu import "./algo.css" ou um styled.button. Aqui é Tailwind em classe utilitária, e app/globals.css já tem os tokens.
por que ele erra justamente aqui — e por que o próprio Next avisa

Abra o AGENTS.md na raiz do repositório. Ele não foi escrito pelo time: é gerado pelo próprio next dev, e diz, em inglês, que esta versão tem mudanças que quebram o que os modelos viram no treino, e que a doc da versão instalada está em node_modules/next/dist/docs/.

Pare um segundo nisso. O framework está avisando os modelos de que eles estão desatualizados. Não é opinião do seu instrutor: é um arquivo que o seu terminal escreveu sozinho na primeira vez que você rodou npm run dev.

Daí a regra de trabalho desta sprint: quando a sugestão divergir da doc local, a doc local ganha. E o .github/copilot-instructions.md — esse sim escrito pelo time, versionado, mudado por PR — é o que puxa o copiloto de volta para as convenções da casa. Ler os dois leva cinco minutos e economiza uma tarde.

Uma última: o erro do onClick não é um contratempo do laboratório. É o melhor professor da aula, e você vai reencontrá-lo em todo projeto Next que pegar. Rode antes de consertar. Leia o erro inteiro antes de colar a linha.

Os testes de trinta segundos, antes de abrir o PR

  • O grep. grep -rn "use client" --include="*.tsx" . devolve dois arquivos, os dois em components/. Se aparecer algo em app/, volte.
  • O terminal. Recarregue a página de um título com o npm run dev visível. O log do servidor sai lá, não no navegador.
  • O botão. Clique, cole em outro lugar. É o endereço da página que você estava vendo, com o slug certo.
  • A sinopse. Um título de sinopse longa mostra "ver mais"; um de sinopse curta não mostra botão nenhum.
  • O teclado. Chegue nos dois botões só de Tab, acione com Enter, e confira que o foco continua visível. Está no checklist do pull_request_template.md.
  • O build. npm run build passa. Antes do push, sempre.

O campo que a revisão lê primeiro

O template do PR tem uma seção chamada "A decisão que eu tomei", e ela é obrigatória. Neste ticket a decisão já está escolhida para você — só falta escrever por quê.

Um rascunho honesto: "Marquei botao-copiar-link.tsx e sinopse-expansivel.tsx como client porque os dois têm evento de usuário e o primeiro usa navigator.clipboard. Deixei app/midias/[slug]/page.tsx no servidor: subir a linha para lá mandaria a ficha técnica e as temporadas para o navegador sem necessidade."

E não deixe em branco a última seção, "O que a IA sugeriu e eu recusei". Se o Copilot propôs o "use client" na página e você recusou, isso vale mais na revisão do que o código em si. Saber recusar é metade da habilidade.
