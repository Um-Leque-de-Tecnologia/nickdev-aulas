Comece por aqui

Como usar este guia

Este guia foi escrito para quem nunca ouviu falar de inversão de controle, injeção de dependência ou Spring. Nenhum termo aparece aqui sem ser explicado antes.

  • Leia a Parte 1 antes da aula, se der. São só conceitos, sem computador. Chegar com essas ideias na cabeça muda completamente o aproveitamento do dia.
  • Faça a Parte 3 antes da aula. Instalar Java e IDE demora e não é o que a gente quer fazer na aula. Se der problema, me chame antes.
  • Siga a Parte 4 e 5 junto comigo, na aula. Elas são o passo a passo idêntico ao que vamos fazer na tela.
  • Volte no "Erros comuns" quando travar. Quase toda pane da primeira aula está catalogada lá.
🎯 O que esta aula assume que você já sabe. Orientação a objetos com Java: o que é uma classe, um objeto, um método, uma interface e herança. Se algum desses estiver enferrujado, revise antes — o Spring não substitui orientação a objetos, ele organiza o que você já sabe.

O conceito

O que é uma dependência

Quando uma classe sua precisa de outra classe pra funcionar, essa outra classe é chamada de dependência dela. Só isso — o nome assusta mais do que a ideia.

// A classe Pedido precisa da Impressora pra finalizar.
// Logo: Impressora é uma DEPENDÊNCIA de Pedido.

public class Pedido {

  private Impressora impressora;   // <-- a dependência

  public void finalizar() {
    impressora.imprimirCupom();   // sem ela, não dá pra finalizar
  }
}

Cuidado: a mesma palavra tem dois usos

Dependência entre classes

A classe Pedido depende da classe Impressora. É sobre o seu código. É esse sentido que aparece em "injeção de dependência".

Dependência do projeto

O projeto inteiro depende de uma biblioteca de terceiros — o Spring, por exemplo. É esse sentido que aparece em "adicione a dependência no pom.xml".

Como diferenciar na prática: se a frase fala de pom.xml, Maven ou "baixar", é dependência-biblioteca. Se fala de construtor, classe ou objeto, é dependência entre classes.

O que é acoplamento

Acoplamento é o quanto uma peça está grudada na outra. Quanto mais grudadas, mais difícil trocar uma sem quebrar a outra.

Acoplamento forte 👎

Um abajur com a lâmpada soldada. Queimou a lâmpada? Joga o abajur fora. Trocar uma peça obriga a mexer na outra.

Acoplamento fraco 👍

Um abajur com rosca. Queimou? Troca só a lâmpada. O abajur nem sabe qual marca você comprou — ele só conhece o formato da rosca.

Isso não é figura de linguagem: dá pra escrever a analogia inteira em Java. Vamos ver os dois abajures em código.

Versão 1 — a lâmpada soldada

LampadaLed.java
public class LampadaLed {
  public void acender() {
    System.out.println("Luz branca!");
  }
}
Abajur.java
public class Abajur {

  // a solda: o abajur FABRICA a própria lâmpada
  private LampadaLed lampada = new LampadaLed();

  public void ligar() {
    lampada.acender();
  }
}

O código funciona. O problema aparece na primeira mudança: chegou a LampadaColorida e, pra usá-la, você precisa abrir e editar o Abajur.java — um arquivo que não tem nada a ver com o tipo de lâmpada. O abajur sabe demais: ele nem deveria conhecer o nome LampadaLed.

Todo new é uma solda. Quem escreve new X() fica casado com o tipo X. Guarde essa frase — ela explica praticamente tudo que vem a seguir nesta aula.

Versão 2 — a lâmpada de rosca

A "rosca" no código é a interface: o contrato que diz o que a peça faz, sem dizer como.

Lampada.java — a rosca
public interface Lampada {
  void acender();          // só o contrato, sem implementação
}
as lâmpadas que servem nessa rosca
public class LampadaLed implements Lampada {
  public void acender() { System.out.println("Luz branca!"); }
}

public class LampadaColorida implements Lampada {
  public void acender() { System.out.println("Luz roxa!"); }
}
Abajur.java — agora só conhece a rosca
public class Abajur {

  private final Lampada lampada;      // o tipo é a interface

  // a lâmpada chega de fora, já pronta
  public Abajur(Lampada lampada) {
    this.lampada = lampada;
  }

  public void ligar() {
    lampada.acender();
  }
}
quem monta é que escolhe
new Abajur(new LampadaLed()).ligar();       // Luz branca!
new Abajur(new LampadaColorida()).ligar();  // Luz roxa!

// e o arquivo Abajur.java não foi aberto nenhuma vez.

O placar

PerguntaSoldadaDe rosca

A última linha é a chave. A decisão saiu de dentro da classe e foi pra quem monta. Essa mudança de lugar tem nome próprio — inversão de controle — e é o assunto de duas seções à frente. E aquele construtor recebendo a Lampada? Você acabou de escrever, sem saber, uma injeção de dependência.
Guarde a imagem da lâmpada. Todo o curso empurra o seu código do abajur soldado pro abajur com rosca. Sempre que eu disser "diminuir o acoplamento", é disso que estou falando.

A frase clássica: "Don't call us, we'll call you" — não nos ligue, nós ligamos pra você. Chamam isso de Princípio de Hollywood, porque é o que dizem aos atores depois do teste. Segure essa frase: ela é literalmente a definição de inversão de controle.

O problema, em código

Antes de aprender a solução, precisamos sentir a dor. Vamos escrever um código Java puro que funciona — e depois quebrar ele de três jeitos.

A versão inocente

EmailNotificador.java
public class EmailNotificador {
  public void enviar(String msg) {
    System.out.println("E-mail: " + msg);
  }
}
PedidoService.java
public class PedidoService {

  private EmailNotificador notificador = new EmailNotificador();

  public void criar(String item) {
    System.out.println("Pedido criado: " + item);
    notificador.enviar("Seu pedido de " + item + " foi criado!");
  }
}

Funciona. Roda. Entrega o que promete. E mesmo assim tem um problema sério escondido na linha destacada.

Três decisões numa linha só

Aquele new EmailNotificador() não é uma decisão — são três:

  1. Qual implementação usar. O PedidoService decidiu sozinho que é e-mail. Não é SMS, não é push.
  2. Quando criar o objeto. No instante em que o PedidoService nascer.
  3. Como configurar. Construtor vazio. Se amanhã o notificador precisar de servidor e senha, vai ter que aparecer aqui dentro.

A pergunta que vale a aula: o trabalho do PedidoService é registrar pedidos. Por que ele está decidindo três coisas sobre notificação?

Dor 1 — mudou o requisito

"Agora é por SMS." Você cria o SmsNotificador e precisa abrir e editar o PedidoService, que não tem nada a ver com o assunto. Se doze classes usam o notificador, são doze arquivos abertos.

Dor 2 — não dá pra testar

@Test
void deveCriarPedido() {
  PedidoService s = new PedidoService();
  s.criar("Pizza");
  // ...e aqui ele dispara um e-mail DE VERDADE, toda vez.
}

Não existe brecha pra colocar um notificador de mentira: o new está trancado dentro da classe. Ou o teste manda e-mail de verdade, ou você não testa.

Regra de ouro: código difícil de testar quase sempre é código com acoplamento forte. Dificuldade de teste é um sintoma, não a doença.

Dor 3 — desperdício

Se dez classes fazem new EmailNotificador(), existem dez objetos idênticos na memória. Com um notificador de mentirinha isso é inofensivo. Com uma conexão de banco de dados, é o motivo de a aplicação cair em produção.

O diagnóstico

As três dores têm a mesma raiz: a classe que usa o objeto é a mesma que fabrica o objeto.

Usar

chamar notificador.enviar(...). Isso é trabalho do PedidoService.

Fabricar

decidir qual classe, quando criar, como configurar. Isso não é trabalho do PedidoService.

A solução é separar as duas coisas: alguém de fora fabrica, e a classe só usa. Esse "alguém de fora" vai ser o Spring.

Inversão de controle (IoC)

Vamos quebrar o nome em pedaços, porque cada palavra significa alguma coisa.

  • Controle o poder de decidir. Aqui: decidir qual objeto criar, quando criar e como ligá-lo aos outros.
  • Quem tinha esse controle a sua própria classe, na linha do new. Ela mandava em tudo.
  • Inverter tirar esse poder da sua classe e entregar pra alguém de fora — o framework.
Definição fechada: inversão de controle é o seu código deixar de decidir como os objetos são criados e conectados, passando essa decisão pro framework.

A analogia do restaurante

Cozinha de casa (com new)

Você compra o ingrediente, acende o fogo, cozinha, serve e lava a louça. Controle total — e trabalho total. Acabou o gás? Problema seu.

Restaurante (com IoC)

Você pede o prato. Não escolhe a panela, não acende o fogo, não conhece o fornecedor. Declara o que quer; o restaurante resolve como.

A seta que vira

Sem frameworkCom Spring
Quem cria os objetosseu código, com newo Spring, no start da aplicação

Atenção: IoC é um princípio, uma ideia de arquitetura. Não é uma anotação, não é uma classe, não é código. Você não "usa IoC" — você escreve código que respeita IoC.

Injeção de dependência (DI)

De novo, palavra por palavra:

  • Dependência: o objeto de que a sua classe precisa (já sabemos).
  • Injeção: entregar de fora pra dentro. A classe não busca — ela recebe.
Definição fechada: injeção de dependência é a técnica de entregar prontos, de fora, os objetos de que uma classe precisa.

Analogia direta: você não fabrica sangue quando precisa de transfusão. Alguém injeta em você um sangue que já existe, produzido em outro lugar.

Passo 1 — a classe passa a receber, não a criar

Repare que isso é Java puro. Não tem nada de Spring ainda:

PedidoService.java
public class PedidoService {

  private final Notificador notificador;   // a INTERFACE, não a classe concreta

  // a dependência CHEGA de fora, pelo construtor
  public PedidoService(Notificador notificador) {
    this.notificador = notificador;
  }

  public void criar(String item) {
    System.out.println("Pedido criado: " + item);
    notificador.enviar("Seu pedido de " + item + " foi criado!");
  }
}

Sumiu o new. A classe agora declara o que precisa e para por aí. E olha o que ela ganhou de graça: as três dores acabaram. Trocar e-mail por SMS não abre este arquivo. Testar é passar um notificador falso no construtor.

Passo 2 — alguém precisa ligar os fios

Main.java — ainda Java puro
public class Main {
  public static void main(String[] args) {

    // 1. crio a dependência
    Notificador n = new EmailNotificador();

    // 2. injeto na classe que precisa dela
    PedidoService service = new PedidoService(n);

    service.criar("Pizza");
  }
}

Funciona lindamente — com três classes. Agora imagine duzentas classes, cada uma pedindo três ou quatro outras, e a ordem de criação importando. Essa main viraria um monstro de mil linhas.

Passo 3 — o Spring assume essa main

É exatamente esse trabalho que o Spring faz por você. Duas etiquetas e o monstro desaparece:

EmailNotificador.java
@Component                                  // "Spring: crie e guarde um objeto desta classe"
public class EmailNotificador implements Notificador { ... }
PedidoService.java
@Service                                    // mesma coisa, com nome de camada
public class PedidoService {

  private final Notificador notificador;

  public PedidoService(Notificador notificador) {   // o Spring lê este construtor
    this.notificador = notificador;
  }
}

O que o Spring faz quando a aplicação sobe, na ordem:

  1. Varre as classes do projeto procurando etiquetas.
  2. Acha EmailNotificador com @Component, cria um objeto dele e guarda no contêiner.
  3. Acha PedidoService com @Service e vê que o construtor pede um Notificador.
  4. Procura no contêiner alguém que seja um Notificador. Acha o EmailNotificador.
  5. Chama new PedidoService(aquele objeto) e guarda o resultado no contêiner também.
Vocabulário: cada objeto que mora nesse contêiner chama-se bean. E o contêiner tem nome de classe em Java: ApplicationContext. Vamos abrir os dois na aula 02.

IoC × DI: são a mesma coisa?

Não. Elas se relacionam, mas não são sinônimos — e essa é a pergunta que mais volta em entrevista de emprego.

IoC — o princípio

"Quem decide como os objetos nascem e se conectam não é o meu código." É uma ideia, um jeito de pensar arquitetura.

DI — a técnica

"Recebo pelo construtor tudo de que preciso." É a forma concreta de aplicar aquela ideia.

DI é uma maneira de fazer IoC. IoC é o objetivo; DI é o caminho mais usado pra chegar lá.

Analogia: "se alimentar melhor" é o princípio; "cortar refrigerante" é a técnica. A segunda serve à primeira, mas não são a mesma frase.

As três formas de injetar

Existem três jeitos de a dependência entrar na classe. Você vai usar um.

1. Por construtor — use esta

@Service
public class PedidoService {
  private final Notificador notificador;      // pode ser final!

  public PedidoService(Notificador notificador) {
    this.notificador = notificador;
  }
}

Se a classe tem um só construtor, o Spring usa aquele automaticamente — nem precisa de @Autowired.

2. Por setter — casos raros

@Autowired
public void setNotificador(Notificador n) { this.notificador = n; }

Faz sentido só quando a dependência é mesmo opcional.

3. Por campo — evite

@Autowired
private Notificador notificador;   // parece mais curto, custa caro
CritérioConstrutorCampo
Campo pode ser finalsimnão
Dá pra instanciar em teste sem Springsimnão
A classe deixa claro do que dependesim, na assinaturanão, fica escondido
Avisa cedo se a classe tem dependências demaissim, o construtor inchanão, só cresce a lista
Por que você vai ver o contrário na internet: injeção por campo era o padrão até uns dez anos atrás, então metade dos tutoriais ainda usa. A própria documentação do Spring recomenda construtor desde 2016. Nesta disciplina, construtor sempre.
O Spring

O ecossistema Spring

"Spring" não é um programa só. É uma família de projetos que compartilham o mesmo contêiner de objetos.

Fixe: Spring Framework é o tronco. Todo "Spring alguma coisa" é um galho que se pluga nele — e todos usam a mesma injeção de dependência que você acabou de aprender.

Spring tradicional × Spring Boot

Antes de 2014, usar Spring significava declarar cada objeto na mão, em XML:

applicationContext.xml — o passado
<beans>
  <bean id="notificador" class="br.com.loja.EmailNotificador"/>

  <bean id="pedidoService" class="br.com.loja.PedidoService">
    <constructor-arg ref="notificador"/>
  </bean>
</beans>

E isso era só o começo: ainda faltava configurar servidor, dialeto do banco, codificação e a versão de cada biblioteca. Era normal passar o primeiro dia inteiro configurando antes de escrever uma linha de regra de negócio — e refazer tudo no projeto seguinte.

Spring Boot não é um Spring diferente. É o mesmo Spring, com as decisões padrão já tomadas por você. O lema é convenção sobre configuração: se você não disser nada, ele usa um padrão razoável; se disser, ele obedece.

Contêiner, IoC e DIigualigual
A última linha é a mais importante: o conceito não mudou. Tudo que você aprendeu de IoC e DI vale exatamente igual nos dois.

Autoconfiguração

Quando a aplicação sobe, o Spring Boot roda centenas de regrinhas no formato "se... então...":

  • Se existe a biblioteca do Tomcat no projeto e você não configurou nenhum servidor, então subo um Tomcat na porta 8080.
  • Se existe um driver do banco H2 e você não declarou conexão nenhuma, então crio um banco em memória e conecto nele.
  • Se a biblioteca Jackson está presente, então uso ela pra converter objetos em JSON.

Não tem mágica: são regras escritas por gente do time do Spring, e você pode sobrescrever qualquer uma — é justamente pra isso que serve o application.properties.

Palavra nova: classpath é a lista de tudo que está disponível pro seu programa em tempo de execução — as suas classes mais todas as bibliotecas baixadas. Quando eu disser "o Jackson está no classpath", leia: "a biblioteca Jackson foi baixada e está disponível".

Starters

Um starter é uma dependência-combo: sozinha, ela traz um conjunto de bibliotecas que já funcionam juntas, nas versões certas.

Sem starter

Você declara Spring MVC, Tomcat, Jackson, validação... e torce pra que as versões sejam compatíveis entre si.

Uma linha traz todas elas, testadas juntas pelo time do Spring.

Qual versão

JDK 21. É uma versão LTS (Long Term Support, suporte prolongado) e é a que esta disciplina usa. O Spring Boot 4 roda a partir da 17, mas fixamos a 21 para a turma inteira estar na mesma base — e a 11 não serve de jeito nenhum.

  • Execute Next → Next → Install. Não mude o caminho de instalação.
  • Confira Abra o Prompt de Comando (tecle Windows, digite cmd) e rode o comando da seção seguinte.

Baixe na mesma página o ARM64 DMG Installer (chips M1/M2/M3) ou x64 DMG Installer (Macs Intel), e abra o .dmg.

"E onde eu instalo o Spring?" Em lugar nenhum. Spring não é um programa que se instala — é um conjunto de bibliotecas que o Maven baixa dentro do projeto quando você declara no pom.xml. Cada projeto tem a sua cópia.

Maven e o pom.xml

Maven é a ferramenta que monta o projeto. Ela faz três coisas que você não vai querer fazer na mão:

  1. Baixa as bibliotecas. Você escreve o nome; ela busca na internet, junto com tudo de que aquela biblioteca depende.
  2. Compila. Transforma seus .java em .class, na ordem certa.
  3. Empacota. Junta tudo num arquivo .jar — o programa pronto pra rodar em qualquer máquina com Java.
Boa notícia: você não precisa instalar o Maven. O projeto gerado já vem com o Maven Wrapper (os arquivos mvnw e mvnw.cmd), que baixa e usa a versão certa sozinho.

O pom.xml, pedaço por pedaço

POM = Project Object Model. É a carteira de identidade do projeto:

pom.xml
<!-- 1. quem é o "pai" deste projeto: quem decide as versões -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.1.1</version>
</parent>

<!-- 2. as coordenadas deste projeto -->
<groupId>br.edu.faculdade</groupId>      <!-- a organização -->
<artifactId>biblioteca</artifactId>       <!-- o nome do projeto -->
<version>0.0.1-SNAPSHOT</version>       <!-- a versão -->

<!-- 3. a versão do Java usada pra compilar -->
<properties>
  <java.version>21</java.version>
</properties>

<!-- 4. de que este projeto precisa -->
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
</dependencies>

Repare que a dependência não tem versão. Quem decide é o parent. É por isso que as bibliotecas do Spring nunca brigam entre si: uma autoridade central escolheu um conjunto que funciona junto.

Coordenadas. Toda biblioteca do mundo Java é identificada por três informações: groupId (quem fez), artifactId (o quê) e version (qual versão). É como autor + título + edição de um livro.

A classe principal

src/main/java/br/edu/faculdade/biblioteca/BibliotecaApplication.java
package br.edu.faculdade.biblioteca;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class BibliotecaApplication {

  public static void main(String[] args) {
    SpringApplication.run(BibliotecaApplication.class, args);
  }
}

É a mesma main de sempre — a que você escreve desde a primeira aula de Java. A novidade é a linha de dentro, que se traduz como: "Spring, assume daqui: monte o contêiner, ligue os objetos e suba o servidor."

@SpringBootApplication são três anotações em uma

Anotação embutidaO que ela liga
@SpringBootConfigurationmarca esta classe como fonte de configuração do projeto
@EnableAutoConfigurationliga a autoconfiguração — as centenas de regras se... então...
@ComponentScanmanda vasculhar o pacote desta classe e todos os subpacotes criando um bean pra cada classe etiquetada
⚠️ A causa do erro nº 1 da aula está na terceira linha. Se você criar uma classe fora do pacote da Application — por exemplo em br.edu.outracoisa — o Spring simplesmente não a enxerga. Ele não reclama, não avisa: o endpoint só devolve 404. Toda classe sua vai dentro do pacote base ou de um subpacote dele.

A API

Como a web funciona (o mínimo)

Sem isso, o resto vira decoreba. São quatro ideias.

1. O que é uma API, afinal

Você vai ouvir essa palavra o semestre inteiro, então vale parar nela.

Abra o Instagram no celular. As fotos não estão dentro do aplicativo — ele acabou de baixar do seu celular e não tem foto nenhuma guardada. O que ele faz é pedir as fotos para um computador da Meta.

E repare no que esse computador devolve: não é uma tela pronta. Ele devolve só os dados crus — quem postou, qual imagem, quantas curtidas, que horas foi. Quem pega esses dados e monta a telinha bonita é o aplicativo, no seu celular.

Esse programa do outro lado, que devolve dados em vez de tela, é uma API.

Um site comumUma API
Quem usauma pessoaoutro programa
O que devolveuma página pronta pra olhardados crus, pra serem usados
Exemploo site do banco que você abreo que o app do banco consulta por trás
É isso que você vai construir neste semestre. Não um site com telas — o outro lado: o programa que guarda os dados e os entrega para quem pedir. Depois, em outra disciplina, você aprende a fazer a tela que consome uma API dessas.

2. Requisição e resposta

Toda a web é uma conversa de duas falas: alguém pergunta (requisição) e alguém responde (resposta). O protocolo — o idioma dessa conversa — chama-se HTTP.

  • Cliente: quem pergunta. Navegador, aplicativo de celular, outro sistema.
  • Servidor: quem responde. A sua aplicação Spring.

3. A URL, pedaço por pedaço

Dissecando http://localhost:8080/livros:

PedaçoNomeSignificado
http://protocoloo idioma da conversa. Em produção vira https, a versão criptografada.
localhosthost"esta máquina aqui". É apelido pro endereço 127.0.0.1, que sempre aponta pro seu próprio computador.
:8080portaqual programa da máquina deve atender. Um computador tem 65 mil portas; a sua aplicação ocupou a 8080.
/livroscaminho (path)o que você quer daquele programa. É isso que você mapeia no código.

4. Verbos e status

Verbos — a intenção

GET quero ver  ·  POST quero criar
PUT quero alterar  ·  DELETE quero apagar

Status — o resultado

200 deu certo  ·  404 não existe
400 você mandou errado  ·  500 o servidor quebrou

Hoje só usamos GET: é o que o navegador manda automaticamente quando você digita uma URL. Os outros verbos são a aula 03.

Primeiro endpoint

Endpoint é um endereço da sua API que responde a alguma coisa. Vamos criar o primeiro em sete linhas.

  • Clique com o botão direito no pacote Aquele que tem a Application — br.edu.faculdade.biblioteca.
  • New → Java Class Nome: OlaController.
  • Escreva o código abaixo
br/edu/faculdade/biblioteca/OlaController.java
package br.edu.faculdade.biblioteca;      // mesmo pacote da Application!

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OlaController {

  @GetMapping("/ola")
  public String ola() {
    return "Olá, mundo Spring!";
  }
}

Rode a aplicação e abra http://localhost:8080/ola no navegador.

O que cada peça faz

PeçaSignificado
@RestControllerduas coisas: (1) "crie um objeto desta classe e guarde no contêiner"; (2) "o que os métodos devolverem vira o corpo da resposta HTTP".
@GetMapping("/ola")"quando chegar um GET no caminho /ola, execute este método".
public String ola()um método Java comum. O nome dele não importa pro Spring — quem define a rota é a anotação.
return "Olá..."vira o conteúdo que o navegador mostra, com status 200 automaticamente.
Repare no que não existe: em nenhum lugar do projeto tem new OlaController(). Você só colou a etiqueta — o Spring criou o objeto, guardou e chamou o método na hora certa. Isso é inversão de controle acontecendo na sua frente.

O caminho da requisição

O que acontece de verdade entre você apertar Enter e o texto aparecer:

  • Você digita a URL O navegador abre uma conexão na porta 8080 e envia GET /ola.
  • O Tomcat recebe O servidor embutido pega a requisição e entrega pro Spring.
  • O DispatcherServlet decide Uma peça central do Spring MVC consulta a tabela de rotas montada no start: "quem se registrou pra GET /ola?"
  • Seu método roda O Spring chama ola() no objeto OlaController que ele mesmo criou.
  • A resposta volta O retorno vira o corpo da resposta, com status 200, e o navegador mostra.
Vocabulário: DispatcherServlet é o "porteiro" do Spring MVC — toda requisição passa por ele antes de chegar no seu método. Você nunca precisa criá-lo nem configurá-lo; ele veio no starter-web e a autoconfiguração o ligou.

Devolvendo JSON

Antes: o que é JSON

JSON (JavaScript Object Notation) é texto puro num formato que qualquer linguagem entende. É assim que sistemas trocam dados hoje — e é o que a sua API vai devolver o semestre inteiro.

{
  "titulo": "Duna",
  "autor": "Frank Herbert",
  "ano": 1965,
  "disponivel": true
}
  • Chaves sempre entre aspas duplas.
  • Textos entre aspas; números e true/false sem aspas.
  • Listas entre colchetes: [ {...}, {...} ].

Agora: devolvendo um objeto

Vamos usar um record — uma classe só de dados, imutável, com construtor e getters gerados automaticamente:

Livro.java
package br.edu.faculdade.biblioteca;

public record Livro(String titulo, String autor, int ano) { }
OlaController.java — adicionando dois métodos
@GetMapping("/livro")
public Livro umLivro() {
  return new Livro("Duna", "Frank Herbert", 1965);
}

@GetMapping("/livros")
public List<Livro> todos() {
  return List.of(
      new Livro("Duna", "Frank Herbert", 1965),
      new Livro("Neuromancer", "William Gibson", 1984));
}

Abrindo http://localhost:8080/livros:

[{"titulo":"Duna","autor":"Frank Herbert","ano":1965},
 {"titulo":"Neuromancer","autor":"William Gibson","ano":1984}]
Quem converteu? Uma biblioteca chamada Jackson, que veio dentro do starter-web. Ela lê os campos do objeto e monta o JSON. Você não escreveu uma linha de conversão — isso é starter + autoconfiguração trabalhando juntos.
Por que record e não classe normal? Porque aqui o objeto é só um pacote de dados: não tem comportamento, não muda depois de criado. O record gera construtor, equals, hashCode e toString sozinho — três linhas viram trinta. Voltamos nisso na aula 04, com DTOs.

Fechando

Erros comuns 🔧

Port 8080 was already in use

Já tem uma aplicação rodando nessa porta — normalmente a sua mesma, de uma execução anterior que você não parou.

  • Pare a execução anterior (botão ■ vermelho na IDE, aba Services ou Run).
  • Ou mude a porta em application.properties: server.port=8081.

404 numa rota que existe

Na esmagadora maioria das vezes: a classe está fora do pacote da Application, e o @ComponentScan não a enxergou. Confira a primeira linha do arquivo — o package tem que começar com o mesmo pacote da Application.

Se o pacote está certo, confira letra por letra: /Livros é diferente de /livros.

Whitelabel Error Page

É a página de erro padrão do Spring Boot. Significa que a aplicação subiu, mas não existe nada mapeado no caminho que você digitou. Leia o status na página: 404 é rota inexistente; 500 é erro no seu código.

invalid target release: 21

A IDE está apontando pra um JDK mais antigo que o do projeto. File → Project Structure → Project → SDK e escolha um 21.

A resposta vem sem JSON / aparece o nome do método

Você usou @Controller em vez de @RestController. Sem o Rest, o Spring interpreta o retorno como nome de página HTML, não como conteúdo. Troque a anotação.

cannot find symbol / o import não aparece

O Maven ainda não baixou as bibliotecas. Botão direito no pom.xml → Maven → Reload project e espere a barra de progresso terminar.

A aplicação sobe e fecha na hora

Falta o spring-boot-starter-web no pom.xml. Sem ele não existe servidor web pra manter o processo vivo, e a aplicação encerra depois de subir o contêiner.

Regra de ouro pra ler erro em Java: a pilha tem 200 linhas, mas a primeira linha e a que menciona uma classe sua resolvem 80% dos casos. O Spring escreve mensagens boas — o problema é que quase ninguém lê.
