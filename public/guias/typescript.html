TypeScript, o JavaScript que avisa antes

Tipar não é burocracia: é mover o erro do usuário para o seu editor. Da inferência automática ao narrowing, dos genéricos ao strict — e qual versão instalar sem quebrar o projeto.

Antes de tudo

⚠️ Qual TypeScript instalar

Comece por aqui, porque errar isto custa uma tarde inteira na aula 03.

VersãoO que éServe para
7.0.2 A mais recente. O compilador foi portado para Go e ficou de 8 a 12× mais rápido. Next.js ✓ · Angular ✗
6.0.3 A faixa que o Angular 22 exige: typescript >=6.0 <6.1 O nosso curso ✓

Por que o Angular não pode usar o 7 ainda: o TypeScript 7 ainda não expõe a API pública de compilador que ferramentas usam pra analisar código. O Angular precisa dela pra checar os tipos dentro dos templates HTML — então ele fica na faixa 6.0.x até o port terminar. O mesmo vale, por enquanto, para Vue, Svelte e Astro.

$ npm install typescript@latest # num projeto Angular ✗ ERESOLVE unable to resolve dependency tree @angular/compiler-cli requires typescript >=6.0 <6.1
A boa notícia: a linguagem é a mesma. O 7 é um port, não uma reescrita da semântica — as regras de tipo vieram do 6 de propósito. Tudo que você aprender aqui vale nas duas versões. O que muda é a velocidade do compilador, não o que é válido.
Não tente "resolver" com --force ou --legacy-peer-deps. O aviso não é burocracia: com o TS errado, a checagem de template do Angular simplesmente não roda, e você perde exatamente a rede de segurança pela qual instalou TypeScript.

Por que TypeScript

// JavaScript: descobre em produção
render(evento.titlo);       // undefined na tela, silêncio total

// TypeScript: descobre enquanto você digita
render(evento.titlo);
//            ~~~~~ Property 'titlo' does not exist on type 'Evento'.
//                  Did you mean 'titulo'?
  • Erro cedo — typo e campo inexistente aparecem no editor
  • Autocompletar de verdade — o editor conhece o formato dos dados
  • Refatoração segura — renomeou um campo? Ele lista os 14 lugares que quebraram
  • Documentação que não desatualiza — o tipo é a assinatura
O tipo some no build. Nada disso existe no navegador — é ferramenta de tempo de escrita. Por isso "TypeScript deixa o site mais lento" não faz sentido: no fim, o que roda é JavaScript.
Os tipos

Tipos e inferência

// deixe ele deduzir
let titulo = "Meetup";       // string
let vagas = 40;              // number

// anote onde ele NÃO tem como deduzir
function formatar(data: string): string {
  return new Date(data).toLocaleDateString("pt-BR");
}

// estruturas vazias precisam de ajuda
const titulos: string[] = [];
const porSlug: Record<string, Evento> = {};
Não anote o óbvio. const titulo: string = "Meetup" é ruído — ele já sabe. Anote parâmetro, retorno e estrutura de dados; o resto ele deduz melhor que você.
any desliga o TypeScript. É a saída fácil quando o erro incomoda, e ela devolve exatamente o problema que você instalou TypeScript pra evitar. Se precisar de escape, use unknown: ele obriga você a checar antes de usar.

Descrevendo os dados

📄 dados/tipos.ts
export type Formato = "Presencial" | "Online" | "Híbrido";
export type Nivel = "Iniciante" | "Intermediário" | "Avançado";

export type Evento = {
  id: string;
  slug: string;
  titulo: string;
  resumo: string;
  descricao: string;
  organizador: string;
  organizadorSlug: string;
  categoria: string;
  formato: Formato;
  cidade?: string;          // opcional: evento online não tem
  inicioEm: string;         // ISO 8601
  duracaoMin: number;
  gratuito: boolean;
  vagas: number | null;    // null = ilimitado, de propósito
  nivel: Nivel;
};

União literal em vez de string solta

formato: Formato em vez de formato: string muda tudo: escrever "presencial" em minúscula vira erro no editor, e o autocompletar oferece os três valores.

? ou | null?

EscolhaSignifica
cidade?: stringO campo pode não vir
vagas: number | nullO campo vem sempre, e null tem significado próprio
No projeto, vagas: null quer dizer "ilimitado" — é informação, não ausência. Por isso ele é | null e não ?. Essa distinção parece detalhe e evita muita confusão depois.

type ou interface?

Para descrever o formato dos seus dados, type resolve e é mais flexível (aceita união, que interface não aceita). interface brilha quando algo vai ser estendido ou implementado por classe — o que aparece bastante no Angular. Na dúvida, type.

Narrowing

O recurso mais útil e menos ensinado do TypeScript: dentro de um if, ele sabe mais do que sabia fora.

function local(evento: Evento): string {
  // aqui, cidade é: string | undefined

  if (evento.cidade === undefined) {
    return "Online";
  }

  // ✨ aqui embaixo é string. Sem cast, sem "!"
  return evento.cidade.toUpperCase();
}

Com find, que é o caso do projeto

const evento = eventos.find((e) => e.slug === slug);
// evento: Evento | undefined

if (!evento) {
  mostrarNaoEncontrado();
  return;
}

// daqui pra baixo é Evento — o TS garante
render(evento.titulo);
find devolver | undefined é bom, não chato. É o TypeScript te obrigando a tratar o "não achei" — que na tela vira a página de 404. Sem isso, o caso passa despercebido até alguém digitar um slug errado.
Evite o !. evento!.titulo diz "confia, existe" e desliga a checagem. Se você estiver errado, volta o erro de runtime que o TypeScript existia pra prevenir. Prefira um if de verdade.
Indo além

Genéricos

// sem genérico: perde o tipo
function primeiro(lista: any[]): any { return lista[0]; }

// com genérico: "o que entrar é o que sai"
function primeiro<T>(lista: T[]): T | undefined {
  return lista[0];
}

const e = primeiro(eventos);    // Evento | undefined ✓
const n = primeiro([1, 2]);    // number | undefined ✓

O <T> é um espaço em branco pro tipo, preenchido na hora da chamada.

Com restrição

// T precisa ter pelo menos um campo slug
function buscarPorSlug<T extends { slug: string }>(
  lista: T[],
  slug: string,
): T | undefined {
  return lista.find((item) => item.slug === slug);
}

// serve pra Evento e pra Organizador, mantendo o tipo certo
Você vai ler genéricos muito mais do que escrever: signal<Evento[]>([]) no Angular, useState<Evento | null>(null) no React. Reconhecer a forma já resolve 90% dos casos.

Utility types

// o que o formulário de novo evento envia
type NovoEvento = Omit<Evento, "id">;

// o que a edição aceita
type EdicaoEvento = Partial<NovoEvento>;

// agrupamento
const porCategoria: Record<string, Evento[]> = {};
A vantagem é a fonte única. Adicione um campo em Evento e os três derivados se atualizam sozinhos. Se você tivesse copiado o tipo três vezes, teria três lugares pra esquecer.
Rigor

strict

📄 tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "noEmit": true
  },
  "include": ["src"]
}
OpçãoO que muda
strictLiga um pacote de checagens. A principal é strictNullChecks: null e undefined deixam de caber em qualquer tipo
noUncheckedIndexedAccesslista[0] passa a ser T | undefined — porque o índice realmente pode não existir
Sem strict, TypeScript é decoração. Ele aceita null em tudo e você perde justamente a checagem que previne o erro nº 1 de JavaScript — o famoso "cannot read property of undefined".
No TypeScript 7, strict já é padrão, e as depreciações do 6 viraram erro. É um bom sinal de para onde a linguagem foi — e mais um motivo pra começar com ele ligado.
