git switch -c

Branches, merge e o conflito que todo mundo teme

No fim de hoje você cria uma linha do tempo paralela, trabalha nela em paz, junta com a main — e provoca um conflito de propósito, só pra descobrir que ele é mansinho.

precisa: o repositório da aula 01, com os três commits. ainda é tudo local — o GitHub de verdade é a aula 03.

use ← → pra navegar · manual desta aula

// o problema

Uma pasta só, duas coisas ao mesmo tempo

Você está no meio de um rodapé novo, metade pronto, quando chega o recado: o menu está quebrado no celular, conserta agora.

1Commitar o rodapé pela metade só pra desimpedir a pasta. O histórico ganha um commit que não funciona.
2Consertar o menu no meio do rodapé. Aí os dois assuntos entram no mesmo commit e ninguém separa depois.
3Copiar a pasta pra um site-com-rodape/ e continuar lá. A gente já viu no que isso dá — foi a aula 01 inteira.
projetos/ site/ ← o menu quebrado mora aqui site-com-rodape-novo/ ← e o rodapé, aqui site-JUNTAR-DEPOIS/ ← este ninguém abre nunca

O problema não é a mudança. É a mudança de dois assuntos disputando a mesma pasta.

Branch é a resposta do Git pra isso — e não custa uma cópia da pasta. Não custa quase nada, na verdade.

// o conceito

Branch não é cópia da pasta

Este é o mal-entendido do dia. Se você sair daqui achando que git switch -c duplica arquivos no disco, tudo que vem depois fica estranho.

o que muita gente acha

Uma segunda pasta

"Criei a branch, então agora tenho duas cópias do projeto — uma com o rodapé e outra sem." Nesse modelo, trocar de branch seria abrir outra janela do gerenciador de arquivos.

o que é de verdade

Uma linha do tempo paralela

A pasta é uma só, sempre. O que muda é qual versão da história está estendida nela agora. O Git troca o conteúdo dos arquivos no lugar, em silêncio, em milissegundos.

A analogia: a pasta é a mesa. A branch é o caderno aberto em cima dela. Trocar de branch é fechar um caderno e abrir outro — a mesa continua sendo a mesma mesa.

// por dentro

Uma branch é um apontador com nome

A ── B ── C ← os commits da aula 01 ↑ main ← só um nome apontando pro C HEAD ← e você está aqui

Criar uma branch é escrever mais um nome apontando pro mesmo commit. É um arquivo de 41 bytes. Não copia nada.

1Um commit é a foto. Ele nunca muda de lugar nem de nome.
2Uma branch é um nome que aponta pra um commit. A cada commit novo, o nome anda pra frente sozinho.
3HEAD é "onde eu estou agora". Quase sempre ele aponta pra uma branch, e a branch pra um commit.
4Por isso branch é barata: criar, apagar e recriar não custa quase nada. Crie sem medo.
// git switch

Criar e trocar de branch

terminal
# ver em que branch você está (a do * é a atual)
git branch

# criar uma branch nova E ir pra ela
git switch -c rodape

# voltar pra uma que já existe
git switch main

# a forma antiga, que ainda aparece em tutorial
git checkout -b rodape   # = switch -c
git checkout main        # = switch main
1O -c é de create. Sem ele, o switch só troca pra uma branch que já existe.
2A branch nova nasce onde você está. Vá pra branch certa antes de criar.
3O checkout não está errado nem foi removido — ele fazia coisas demais, e o Git 2.23 partiu em dois: switch pra branch, restore pra arquivo.
4Nome de branch sem espaço. Use hífen ou barra: rodape, fix/menu-mobile. Convenção de time é a aula 07.

Depois do switch -c, rode git status: a primeira linha deixou de ser On branch main.

// mão na massa
LAB 1

A sua primeira branch

~8 min

No repositório da aula 01, o mesmo dos três commits. Nada aqui apaga nada.

Confirme onde você está

Uma branch só, chamada main, com o asterisco do lado.

cd meu-primeiro-repo
git status
git branch

Crie a branch e vá pra ela

Repare que o terminal não demora nada. É só um nome novo.

git switch -c rodape
git branch

Trabalhe nela

Um arquivo novo e um commit — igualzinho à aula 01, só que aqui dentro.

echo "Feito com carinho pela NickDev" > rodape.txt
git add rodape.txt
git commit -m "feat: adiciona o rodapé"
quando terminar

Rode git log --oneline: são quatro commits. Agora guarde a pergunta — se você voltar pra main agora, quantos commits o log vai mostrar?

// o susto saudável

O arquivo "sumiu" — e está tudo certo

$ git switch main Switched to branch 'main' $ ls README.md # cadê o rodape.txt? $ git log --oneline c3f9a12 chore: ignora .env e node_modules 7d3b112 fix: menu quebrado no celular e05a4c8 chore: primeiro commit
  • O rodape.txt não foi apagado. Ele existe no commit que está na branch rodape.
  • A main nunca soube dele — e por isso a pasta, agora, é a main exatamente como você a deixou.
  • Volte com git switch rodape e o arquivo reaparece. Isto é a pasta obedecendo à linha do tempo, não mágica.
  • É este vaivém que prova que branch não é cópia. Se fosse cópia, os dois arquivos estariam ali ao mesmo tempo.

Sempre commite antes de trocar de branch. Mudança solta na pasta atravessa junto e vira confusão. Guardar trabalho pela metade sem commitar é o stash, da aula 11.

// git merge

Voltar com o trabalho: merge

Terminou o rodapé. Agora ele precisa entrar na main — que é a linha do tempo oficial do projeto.

🚪
git switch mainvá pra branch que vai receber
→
🤝
git merge rodapetraga a outra pra dentro dela
→
🧹
git branch -d rodapeapague o nome — os commits ficam

A ordem confunde e é sempre a mesma: você vai pra branch de destino e puxa a outra. Quem está de pé é quem recebe. O git merge rodape rodado na main muda a main, não a rodape.

// caso 1

Fast-forward: só andar o apontador

Acontece quando a main não andou desde que você criou a branch. Não há duas histórias pra juntar — há uma só, mais comprida.

antes do merge
A ── B ── C ← main parada aqui \ D ── E ← rodape
depois do merge
A ── B ── C ── D ── E ← main e rodape juntas
1O Git não cria commit nenhum. Ele só empurra o nome main de C pra E.
2A saída diz Fast-forward. É o Git avisando qual caminho ele tomou.
3O histórico fica reto, como se você tivesse trabalhado direto na main.
4Dá pra recusar o atalho com git merge --no-ff rodape: aí o commit de merge nasce mesmo sem necessidade. Alguns times preferem, pra enxergar onde a branch existiu.
// caso 2

Commit de merge: quando as duas andaram

Você fez commits na branch e alguém — ou você mesmo — fez commits na main. Agora são duas histórias de verdade, e juntá-las exige um commit novo.

antes do merge
A ── B ── C ── F ← main andou \ D ── E ← rodape também
depois do merge
A ── B ── C ── F ── M ← M é o commit de merge \ / D ── E ─── ← com dois pais: F e E
1O commit M é o único tipo de commit com dois pais. É ele que registra o encontro.
2O Git abre um editor com a mensagem pronta — Merge branch 'rodape'. Aceite e saia. Se cair no Vim: Esc, :wq, Enter.
3O histórico deixa de ser reto e vira grafo. É por isso que o próximo slide existe.
4Se as duas histórias mexeram na mesma linha do mesmo arquivo, é aqui que nasce o conflito — a segunda metade da aula.
parada obrigatória

Sem seguir sem responder

O conflito, que é a segunda metade da aula, empilha em cima destas três. Se alguma travar, é agora que a gente resolve.

1Você criou a branch rodape. Quantas pastas existem no seu computador agora?
2Pra levar o rodapé pra main, em qual branch você precisa estar antes de rodar o merge?
3Quando o merge é fast-forward e quando ele cria um commit novo?

respostas: 1 — uma; 2 — na main; 3 — fast-forward quando a main não andou, commit de merge quando as duas andaram.

// git log --graph

Ler o histórico em grafo

terminal
git log --graph --oneline --all
$ git log --graph --oneline --all * 9b1c0aa (HEAD -> main) Merge branch 'rodape' |\ | * 4e77d31 (rodape) feat: adiciona o rodapé * | a1c9f0e fix: menu quebrado no celular |/ * c3f9a12 chore: ignora .env * e05a4c8 chore: primeiro commit
1Cada * é um commit. As barras são os fios ligando pai e filho — leia de baixo pra cima, do mais antigo pro mais novo.
2O |\ é onde a história se abriu em duas; o |/ é onde ela se juntou de novo.
3O --all mostra todas as branches. Sem ele, você só vê a linha em que está — e acha que a outra sumiu.
4HEAD -> marca onde você está. Se a saída travar com : no fim, é o paginador: q pra sair.

Vale criar um atalho: git config --global alias.g "log --graph --oneline --all". Aí é só git g.

LAB 2

Juntar de volta

~10 min

Continuação direta do LAB 1. Leia a saída do merge antes de seguir — a palavra que aparece nela é o assunto dos dois slides anteriores.

Vá pra branch que vai receber

A main. Repare de novo que o rodape.txt não está na pasta.

git switch main
ls

Traga a outra pra dentro dela

Agora o arquivo aparece — e o log da main tem quatro commits.

git merge rodape
ls
git log --oneline

Olhe o grafo e limpe o nome

Apagar a branch não apaga commit nenhum — o trabalho já está na main.

git log --graph --oneline --all
git branch -d rodape
git branch
quando terminar

A saída do merge disse Fast-forward? Devia. A main não recebeu nenhum commit enquanto você trabalhava na outra branch — então não havia duas histórias, só uma mais comprida.

// segunda metade

O conflito não é um erro

Na maioria esmagadora das vezes o Git junta tudo sozinho, sem perguntar nada. Duas pessoas em arquivos diferentes: resolve. Em partes distantes do mesmo arquivo: resolve também.

o git resolve sozinho

Mudanças que não se cruzam

Você mexeu no rodapé, a outra pessoa no cabeçalho. Arquivos diferentes, ou linhas distantes no mesmo arquivo. O merge passa liso e você nem fica sabendo.

o git pergunta

A mesma linha, dos dois lados

As duas histórias mudaram a mesma linha do mesmo arquivo, cada uma de um jeito. Escolher uma delas seria jogar fora o trabalho de alguém — e essa escolha não é do Git.

Conflito é o Git dizendo "não tenho como adivinhar qual das duas versões você quis". Ele para, marca o lugar exato e devolve a decisão pra você. É o comportamento mais educado possível.

// de propósito

Vamos causar um agora

A receita do conflito é curta: a mesma linha, dois valores, duas branches.

terminal
# na main: uma linha simples
git switch main
echo "Contato: contato@nickdev.com" > contato.txt
git add contato.txt
git commit -m "feat: página de contato"

# numa branch, muda a linha
git switch -c contato-telefone
echo "Contato: (11) 90000-0000" > contato.txt
git commit -am "feat: contato por telefone"

# de volta na main, muda A MESMA linha
git switch main
echo "Contato: @nickdev no Instagram" > contato.txt
git commit -am "feat: contato pelo Instagram"

# e agora, o encontro
git merge contato-telefone
$ git merge contato-telefone Auto-merging contato.txt CONFLICT (content): Merge conflict in contato.txt Automatic merge failed; fix conflicts and then commit the result.

Está feito. E repare: o Git não desfez nada e não perdeu nada. Ele parou no meio do merge e está esperando você.

O -am do commit é add + -m num gesto só, e vale pra arquivo já rastreado.

// os marcadores

Ler o que o Git escreveu no arquivo

contato.txt
<<<<<<< HEAD
Contato: @nickdev no Instagram
=======
Contato: (11) 90000-0000
>>>>>>> contato-telefone

Abra o arquivo no editor. Isso aqui é texto comum, escrito lá dentro pelo Git — dá pra apagar com a tecla de apagar, como qualquer outra letra.

1<<<<<<< HEAD — daqui pra baixo é a versão de onde você está, a branch que recebe.
2======= é a linha divisória. Não é conteúdo: é só a fronteira entre as duas versões.
3>>>>>>> contato-telefone — acima dele está a versão que vinha chegando. O nome no fim é o da branch.
4Resolver é deixar o arquivo do jeito certo e apagar as três linhas de marcação. Uma das versões, a outra, ou uma terceira que você escreve na hora.
// resolver

Editar, marcar como resolvido, fechar

contato.txt · depois de você editar
Contato: @nickdev no Instagram
Telefone: (11) 90000-0000

# ficaram as duas — foi a sua decisão,
# e nenhum marcador sobrou no arquivo
terminal
git add contato.txt
git status
git commit

Abra e decida

Fique com uma versão, com a outra, ou escreva a mistura das duas. Quem decide é você — o Git só apontou o lugar.

Apague os marcadores

As três linhas com <<<, === e >>> não podem sobrar. Esquecer uma é o erro nº 1 do dia.

git add = "resolvi este"

Aqui o add ganha um segundo sentido: além de pôr na bancada, ele marca o arquivo como resolvido.

git commit fecha o merge

Sem -m: o Git já traz a mensagem pronta. Aceite e saia do editor.

Enquanto houver conflito aberto, o git status é o seu mapa. Ele lista os arquivos em both modified e some com eles conforme você resolve.

// mão na massa
LAB 3

Provocar e resolver um conflito

~15 min

O laboratório mais importante do curso até aqui. Vai quebrar de propósito — é esse o objetivo.

Prepare os dois lados

A mesma linha do mesmo arquivo, com dois valores diferentes.

git switch main
echo "Contato: contato@nickdev.com" > contato.txt
git add contato.txt && git commit -m "feat: contato"
git switch -c contato-telefone
echo "Contato: (11) 90000-0000" > contato.txt
git commit -am "feat: telefone"
git switch main
echo "Contato: @nickdev no Instagram" > contato.txt
git commit -am "feat: instagram"

Provoque o conflito e leia a saída inteira

Não pule a leitura. O Git diz o nome do arquivo e o que ele espera de você.

git merge contato-telefone
git status
cat contato.txt

Resolva no editor e feche

Deixe o arquivo do jeito que você quer, sem nenhum marcador, e só então:

git add contato.txt
git commit
git log --graph --oneline --all
quando terminar

No grafo, ache o commit de merge — o de cima, com o |\ embaixo. Ele tem dois pais, e é o registro permanente de que aquele encontro aconteceu e de como você resolveu.

// saída de emergência

Deu ruim no meio do merge?

terminal
# cancela o merge e devolve tudo pro estado
# de antes — nada se perde
git merge --abort

# quero simplesmente a versão da branch atual
git checkout --ours contato.txt

# quero simplesmente a versão que chegou
git checkout --theirs contato.txt

# e depois, sempre
git add contato.txt
  • O --abort é seguro. Ele desmonta o merge em andamento e devolve a pasta como estava. Respire e tente de novo.
  • --ours é a branch em que você está; --theirs é a que estava chegando. Só use quando tiver certeza de que uma das versões pode ser descartada inteira.
  • Um merge conflituoso não corrompe repositório. Nenhum commit já feito é apagado por um conflito — nunca.
  • Desfazer um merge já concluído é outra história, e tem comando próprio: aula 11.
