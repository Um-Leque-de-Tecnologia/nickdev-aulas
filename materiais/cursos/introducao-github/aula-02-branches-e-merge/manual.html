Branches, merge e o conflito que todo mundo teme

O passo a passo para você refazer a aula sozinho, no seu ritmo: criar uma branch, commitar nela, voltar para a main, fazer o merge, ler o histórico em grafo — e, no fim, provocar um conflito de verdade e resolvê-lo. Tudo local; o GitHub, o site, entra só na aula 03.

Antes de começar

01De onde a gente parte

Este manual continua exatamente de onde a aula 01 parou: uma pasta chamada meu-primeiro-repo, com git init feito, três commits e um .gitignore. Se você não tem isso, refaça o manual da aula 01 antes — leva uns quarenta minutos e vale mais que ler este aqui pela metade.

Confira o ponto de partida:

terminal
cd meu-primeiro-repo
git status
git log --oneline

O que se espera ver:

$ git status On branch main nothing to commit, working tree clean $ git log --oneline c3f9a12 chore: ignora .env e node_modules 7d3b112 fix: menu quebrado no celular e05a4c8 chore: primeiro commit
Continua tudo local: nesta aula o seu repositório ainda não vai para o site do GitHub. Nenhum comando daqui precisa de internet, de conta ou de senha. Conectar o repositório ao GitHub — clone, push, pull, fetch — é a aula 03, e as branches que você criar hoje vão junto quando esse dia chegar.
Os hashes vão ser outros. Aqueles c3f9a12 são os do exemplo. Os seus commits têm códigos diferentes, e está certo — o hash é único por commit, por máquina, por instante.

02O que é uma branch

Antes de digitar qualquer coisa, desfaça a confusão que atrapalha todo mundo: branch não é cópia da pasta.

O que ela não é

Não é uma segunda pasta no disco. Não duplica arquivo nenhum. Depois de git switch -c rodape, o seu computador continua com uma pasta de projeto — a mesma de antes.

O que ela é

Uma linha do tempo paralela: um nome que aponta para um commit e anda para a frente a cada commit novo. Trocar de branch faz o Git reescrever o conteúdo dos arquivos naquela mesma pasta, para deixá-la igual à outra linha do tempo.

A imagem que costuma resolver: a pasta é a mesa; a branch é o caderno aberto em cima dela. Trocar de branch é fechar um caderno e abrir outro. A mesa continua sendo a mesma mesa, e só cabe um caderno aberto por vez.

como o Git enxerga
A ── B ── C          ← os três commits da aula 01
          ↑
        main           ← "main" é só um nome apontando pro C
        HEAD           ← "HEAD" é onde você está agora
commit
A foto do projeto num instante. Nunca muda de lugar nem de nome depois de criada.
branch
Um nome que aponta para um commit. A cada commit novo, o nome anda para a frente sozinho. Ocupa 41 bytes no disco.
HEAD
Onde você está agora. Quase sempre aponta para uma branch, e a branch para um commit.
main
A branch principal, criada pelo git init. Não tem nada de especial para o Git — é convenção nossa tratá-la como a linha oficial do projeto.
merge
Trazer o trabalho de uma branch para dentro de outra.
Consequência prática: como branch é barata, crie uma para cada assunto. Um conserto, uma branch. Uma ideia maluca que talvez não dê certo, uma branch. Se não der, apaga o nome e não sobrou lixo em lugar nenhum.
Trabalhar em paralelo

03Criar e trocar de branch

Três comandos dão conta de tudo nesta seção: git branch para ver, git switch -c para criar e git switch para ir.

terminal
# ver as branches — a atual vem com um * do lado
git branch

# criar uma branch nova E já ir pra ela
git switch -c rodape

# voltar pra uma branch que já existe
git switch main

O que se espera ver:

$ git branch * main $ git switch -c rodape Switched to a new branch 'rodape' $ git branch main * rodape

E o checkout -b que aparece em todo tutorial?

É a forma antiga de fazer a mesma coisa. Não foi removida, não está errada, e você vai encontrá-la em quase todo texto escrito antes de 2019. Vale saber traduzir:

forma antigaforma de hojeo que faz
git checkout -b rodapegit switch -c rodapeCria a branch e vai para ela.
git checkout maingit switch mainVai para uma branch existente.
git checkout -- arquivo.txtgit restore arquivo.txtDescarta a mudança no arquivo.

O motivo da separação: o checkout fazia coisas demais — trocava de branch e mexia em arquivo, com a mesma palavra. No Git 2.23 ele foi partido em dois verbos com nomes honestos: switch para branch, restore para arquivo.

Cuidado com o ponto de partida: a branch nova nasce de onde você está. Se você criar a rodape estando numa branch errada, ela carrega os commits daquela branch junto. Rode git branch antes do switch -c — sempre.
Nome de branch: sem espaço e sem acento. Use hífen ou barra — rodape, fix/menu-mobile, feat/login. Combinar o padrão com o time é assunto da aula 07.

04Commitar dentro da branch

Aqui não tem novidade nenhuma: é o mesmo ciclo status → add → commit da aula 01. A única diferença é onde o commit cai — na branch em que você está.

Certifique-se de estar na rodape e faça o trabalho:

terminal
git switch rodape
echo "Feito com carinho pela NickDev" > rodape.txt
git status
git add rodape.txt
git commit -m "feat: adiciona o rodapé"

O que se espera ver:

$ git status On branch rodape Untracked files: rodape.txt $ git commit -m "feat: adiciona o rodapé" [rodape 4e77d31] feat: adiciona o rodapé 1 file changed, 1 insertion(+) create mode 100644 rodape.txt

Repare em duas coisas na saída: o status agora diz On branch rodape, e o commit trouxe o nome da branch entre colchetes. É assim que o Git responde "recebi, e guardei aqui".

Confira o histórico dos dois lados:

terminal
git log --oneline

São quatro commits: os três da aula 01 mais o seu. Guarde essa conta — na próxima seção ela muda.

Atalho útil: para arquivo que o Git já rastreia, o git commit -am "mensagem" faz o add e o commit de uma vez. Para arquivo novo, não funciona: o Git ainda não conhece o arquivo, então o add tem que ser explícito.

05O arquivo que "some"

Esta é a demonstração que faz a ficha cair. Volte para a main e olhe a pasta:

terminal
git switch main
ls
git log --oneline

O que se espera ver:

$ git switch main Switched to branch 'main' $ ls README.md $ git log --oneline c3f9a12 chore: ignora .env e node_modules 7d3b112 fix: menu quebrado no celular e05a4c8 chore: primeiro commit

O rodape.txt não está mais na pasta, e o log voltou a ter três commits. Nada foi perdido: o arquivo e o quarto commit continuam existindo, na linha do tempo rodape. A main simplesmente nunca soube deles.

Volte e veja o arquivo reaparecer:

terminal
git switch rodape
ls
É esta a prova de que branch não é cópia: se fossem duas pastas, os dois arquivos estariam ali ao mesmo tempo. Como é uma pasta só, o conteúdo dela muda conforme a linha do tempo que você tem aberta.
Commite antes de trocar de branch. Mudança solta na pasta atravessa junto para a outra branch, e às vezes o Git nem deixa trocar — é o erro Your local changes would be overwritten. Guardar trabalho pela metade sem commitar tem comando próprio, o git stash, e ele é da aula 11.
Juntar de volta

06O merge

O rodapé está pronto. Agora ele precisa entrar na main, que é a linha oficial do projeto. É o git merge quem faz isso.

  1. Vá para a branch que vai receber Quem está de pé é quem recebe. Para trazer o rodapé para a main, você precisa estar na main.
  2. Puxe a outra para dentro dela git merge rodape altera a main. A branch rodape não muda em nada.
  3. Confira O arquivo aparece na pasta e o log da main cresce.
terminal
git switch main
git merge rodape
ls
git log --oneline

O que se espera ver:

$ git merge rodape Updating c3f9a12..4e77d31 Fast-forward rodape.txt | 1 + 1 file changed, 1 insertion(+) create mode 100644 rodape.txt $ ls README.md rodape.txt
A ordem confunde todo mundo no começo. Se você rodar git merge main estando na rodape, o Git obedece — e leva a main para dentro da rodape, que é o contrário do que você queria. Antes de todo merge, pergunte: "em qual branch eu quero que a mudança apareça?" É nela que você tem que estar.

07Fast-forward × commit de merge

A palavra Fast-forward apareceu na saída acima. Ela é o Git contando qual dos dois caminhos ele tomou — e a diferença entre os dois é só uma: a branch de destino andou ou não andou enquanto você trabalhava?

Caso 1 — fast-forward

A main ficou parada desde que você criou a branch. Não há duas histórias para juntar: há uma só, mais comprida. O Git nem cria commit — ele só empurra o nome main para a frente.

antes → depois
A ── B ── C              ← main parada aqui
           \
            D ── E       ← rodape

A ── B ── C ── D ── E    ← main andou até E. nenhum commit novo.

Caso 2 — commit de merge

As duas andaram: você commitou na branch e a main recebeu commits também. Agora existem mesmo duas histórias, e juntá-las exige um commit novo, o commit de merge — o único tipo de commit com dois pais.

antes → depois
A ── B ── C ── F         ← main andou (commit F)
           \
            D ── E       ← rodape também andou

A ── B ── C ── F ── M    ← M é o commit de merge
           \       /
            D ── E       ← pais de M: F e E

Nesse caso o Git abre um editor com a mensagem já escrita (Merge branch 'rodape'). Você aceita e sai — normalmente basta salvar e fechar. Se cair no Vim sem querer: Esc, depois :wq, depois Enter.

fast-forwardcommit de merge
quandoA branch de destino não recebeu commits.As duas receberam commits.
cria commit?Não. Só move o apontador.Sim, um commit com dois pais.
históricoFica reto.Vira um grafo, com bifurcação e reencontro.
pede editor?Não.Sim, para a mensagem do merge.
pode dar conflito?Não.Sim — se as duas mexeram na mesma linha.
Se você quiser o registro mesmo assim: git merge --no-ff rodape obriga o Git a criar o commit de merge, mesmo quando o fast-forward seria possível. Alguns times preferem, porque assim dá para enxergar no histórico onde cada branch existiu. É preferência, não regra.

08O histórico em grafo

Com branches em cena, o git log --oneline deixa de contar a história inteira: ele mostra só a linha em que você está. O desenho completo sai daqui:

terminal
git log --graph --oneline --all

O que se espera ver, depois de um merge com commit de merge:

$ git log --graph --oneline --all * 9b1c0aa (HEAD -> main) Merge branch 'rodape' |\ | * 4e77d31 (rodape) feat: adiciona o rodapé * | a1c9f0e fix: menu quebrado no celular |/ * c3f9a12 chore: ignora .env e node_modules * e05a4c8 chore: primeiro commit
pedaçoo que significa
*Um commit. Leia de baixo para cima: embaixo o mais antigo, em cima o mais novo.
|\Aqui a história se abriu em duas linhas.
|/Aqui as duas se juntaram de novo.
(HEAD -> main)Onde você está agora, e em que branch.
(rodape)Onde o nome rodape está apontando.
--allMostra todas as branches. Sem ele você só vê a sua, e parece que a outra sumiu.

Como é comando comprido e você vai usar muito, vale um apelido:

terminal
git config --global alias.g "log --graph --oneline --all"

A partir daí, git g faz o mesmo.

Se a saída travar com um : no canto, não travou nada: é o paginador. Setas para rolar, tecla q para sair.

09Apagar a branch usada

Depois que o trabalho entrou na main, o nome da branch não serve mais para nada. Apagar é limpeza, não perda: os commits ficam — eles já são parte da main.

terminal
git branch -d rodape
git branch
$ git branch -d rodape Deleted branch rodape (was 4e77d31). $ git branch * main
Se aparecer error: the branch 'rodape' is not fully merged: o Git está protegendo você. Quer dizer que aquela branch tem commit que não entrou em lugar nenhum — apagar o nome deixaria o trabalho sem endereço. Faça o merge primeiro. Se a branch é lixo mesmo e você quer descartar de propósito, o comando é git branch -D rodape, com D maiúsculo. Pense duas vezes antes.
O conflito

10Provocar um conflito

Agora a parte que assusta — e que deixa de assustar hoje. Primeiro, o essencial: conflito não é erro. Na maioria esmagadora das vezes o Git junta tudo sozinho e nem avisa. Ele só para quando as duas linhas do tempo mudaram a mesma linha do mesmo arquivo de jeitos diferentes — porque aí escolher uma delas significaria jogar fora o trabalho de alguém, e essa decisão não é dele.

A receita é curta: a mesma linha, dois valores, duas branches. Rode os quatro blocos abaixo na ordem, no mesmo repositório.

1 · na main, crie o arquivo

terminal
git switch main
echo "Contato: contato@nickdev.com" > contato.txt
git add contato.txt
git commit -m "feat: página de contato"

2 · numa branch nova, mude a linha

terminal
git switch -c contato-telefone
echo "Contato: (11) 90000-0000" > contato.txt
git commit -am "feat: contato por telefone"

3 · de volta na main, mude a MESMA linha

terminal
git switch main
echo "Contato: @nickdev no Instagram" > contato.txt
git commit -am "feat: contato pelo Instagram"

4 · o encontro

terminal
git merge contato-telefone

O que se espera ver — e sim, é isto que a gente queria:

$ git merge contato-telefone Auto-merging contato.txt CONFLICT (content): Merge conflict in contato.txt Automatic merge failed; fix conflicts and then commit the result.

Pronto: conflito provocado com sucesso. Antes de mexer em qualquer coisa, peça o mapa:

terminal
git status
$ git status On branch main You have unmerged paths. (fix conflicts and run "git commit") Unmerged paths: both modified: contato.txt
Repare no que não aconteceu: nenhum commit foi apagado, nenhum arquivo foi perdido e o repositório não corrompeu. O Git só parou no meio do merge e está esperando você decidir. Dá para desistir a qualquer momento — é a seção 12.

11Ler os marcadores e resolver

Abra o contato.txt no seu editor (ou dê um cat contato.txt). O Git escreveu isto lá dentro:

contato.txt · com o conflito
<<<<<<< HEAD
Contato: @nickdev no Instagram
=======
Contato: (11) 90000-0000
>>>>>>> contato-telefone

Isso é texto comum dentro do seu arquivo — não é tela do Git, não é menu, não é nada de especial. Dá para apagar com a tecla de apagar, como qualquer outra letra.

marcadoro que ele delimita
<<<<<<< HEADComeça aqui a versão de onde você está — a branch que recebe o merge. No exemplo, a main.
=======A fronteira. Não é conteúdo: é só o traço que separa uma versão da outra.
>>>>>>> contato-telefoneTermina aqui a versão que estava chegando. O nome depois das setas é o da branch que você mandou entrar.

Resolver é editar o arquivo à mão

Você tem três saídas, e todas são legítimas: ficar com a versão de cima, ficar com a de baixo, ou escrever uma terceira coisa que junte as duas. O que não pode é sobrar marcador.

contato.txt · resolvido
Contato: @nickdev no Instagram
Telefone: (11) 90000-0000

# ficaram as duas informações — decisão sua.
# nenhuma linha com <<<, === ou >>> sobrou.

Agora avise ao Git que este arquivo está resolvido e feche o merge:

terminal
git add contato.txt
git status
git commit

O que se espera ver:

$ git status On branch main All conflicts fixed but you are still merging. (use "git commit" to conclude merge) $ git commit [main 9b1c0aa] Merge branch 'contato-telefone'

O git commit aqui vai sem -m de propósito: o Git já preparou a mensagem (Merge branch 'contato-telefone') e abre o editor só para você confirmar. Salve e feche. No Vim: Esc, :wq, Enter.

Confirme no grafo que o encontro ficou registrado:

terminal
git log --graph --oneline --all
cat contato.txt
O git add tem dois sentidos aqui. Fora de um merge, ele põe a mudança na bancada. Durante um conflito, ele também significa "este eu resolvi" — e é isso que faz o arquivo sair da lista de Unmerged paths do status.
O erro nº 1 do dia é commitar com marcador esquecido no arquivo. O Git não confere o conteúdo: para ele, <<<<<<< é texto igual a qualquer outro, e ele commita numa boa. O código é que quebra depois. Antes do git add, rode git diff e passe o olho — ou procure por <<< no editor.
Vários arquivos em conflito? Mesma receita, um de cada vez: abra, resolva, git add aquele arquivo. O git status vai encurtando a lista. Quando ela zerar, git commit.

12Saída de emergência

Se no meio do conflito você se perder, não precisa consertar nada no susto. Dá para cancelar o merge e voltar exatamente ao estado de antes:

terminal
git merge --abort
git status

O status volta a dizer working tree clean, os marcadores somem dos arquivos e o repositório fica como estava antes do git merge. Nada se perde. Respire, e tente de novo quando quiser.

Quando uma das versões pode ser descartada inteira

Às vezes você sabe que uma das duas versões é a certa e a outra não interessa. Nesse caso dá para escolher em bloco, sem editar:

terminal
# fica com a versão da branch em que você ESTÁ
git checkout --ours contato.txt

# fica com a versão que estava CHEGANDO
git checkout --theirs contato.txt

# e depois, sempre, marque como resolvido
git add contato.txt
Use com parcimônia. --ours e --theirs descartam o outro lado inteiro, sem perguntar. Numa mudança grande, isso apaga trabalho de outra pessoa sem ninguém perceber. Na dúvida, abra o arquivo e resolva na mão.
E desfazer um merge que já terminou? Aí é outro assunto, com comandos próprios — revert, reset, reflog — e é a aula 11 inteira. Nada do que você fizer hoje é irreversível, mas o caminho de volta a gente aprende lá.

14Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
fatal: invalid reference: rodape Você tentou ir para uma branch que não existe, ou esqueceu o -c na hora de criar. git branch para ver os nomes; git switch -c rodape para criar. Veja a seção 03.
Your local changes would be overwritten by checkout Você tentou trocar de branch com mudança solta na pasta. Commite antes de trocar. Guardar sem commitar é git stash, da aula 11.
Commitei na main sem querer Faltou o git switch -c antes de começar a mexer. Nesta aula, siga em frente. O reflexo que evita: rodar git branch antes do primeiro add. Mover o commit para outra branch é aula 11.
CONFLICT (content): Merge conflict in … As duas branches mudaram a mesma linha do mesmo arquivo. Não é erro. Abra o arquivo, resolva, apague os marcadores, git add e git commit. Seção 11.
Depois do merge, o código quebrou com <<<<<<< no meio Sobrou marcador de conflito dentro do arquivo e ele foi commitado assim. Apague as três linhas de marcação, git add e commite de novo.
error: Committing is not possible because you have unmerged files Ainda há arquivo em conflito sem git add. git status lista quem falta. Resolva cada um e dê git add nele.
Me perdi no meio do conflito e quero voltar atrás Acontece, e tem saída limpa. git merge --abort. Volta tudo ao estado anterior, sem perder nada.
Abriu uma tela estranha depois do git merge e não sai É o editor pedindo a mensagem do commit de merge — provavelmente o Vim. Esc, depois :wq, depois Enter. Isso aceita a mensagem e conclui o merge.
error: the branch 'x' is not fully merged A branch tem commit que não entrou em lugar nenhum. O -d está protegendo você. Faça o merge primeiro. Se for descarte mesmo, git branch -D x.
Fiz o merge e o arquivo da outra branch não apareceu Você fez o merge estando na branch errada — levou a main para dentro da outra. git switch main e refaça o merge de lá. Confira sempre com git branch antes.
O git log não mostra a outra branch Sem --all, o log mostra só a linha em que você está. git log --graph --oneline --all.
Não acho estas branches no site do GitHub O repositório é local. Nesta aula nada foi enviado para lá. Não há o que consertar — está certo. Enviar para o GitHub é a aula 03.
Antes de pedir ajuda: rode git status e cole a saída inteira. Durante um conflito ele é literalmente um roteiro — diz quais arquivos faltam resolver e qual é o próximo comando. Em nove de cada dez casos, a resposta já está escrita ali.
