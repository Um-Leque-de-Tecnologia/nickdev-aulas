Qualidade automática: testes, lint e segurança no PR

O passo a passo para você fazer sozinho: acrescentar lint, formatação e testes ao ci.yml que já existe desde a aula 08, transformar o resultado em condição de merge na branch protection da aula 07, ligar Dependabot, secret scanning e code scanning — e o procedimento de emergência para quando um segredo já foi parar no histórico.

Antes de começar

01O que você vai montar aqui

Este manual é o passo a passo da aula 09. No fim dele o seu repositório roda lint, formatação e testes a cada Pull Request, não deixa fazer merge com check vermelho, recebe PR automático de atualização de dependência e tem três alarmes de segurança ligados.

O que você precisa ter antes

  1. Um repositório no GitHub com o ci.yml da aula 08. Aquele workflow em .github/workflows/ci.yml que já roda o build a cada push e a cada Pull Request. Hoje a gente cresce esse arquivo — não cria outro.
  2. A main protegida, como na aula 07. Se você ainda não tem a regra de branch protection, crie agora: sem ela, o passo mais importante desta aula não tem onde encaixar.
  3. Um projeto com script de lint e de teste. Em Node: npm run lint e npm test. Se o seu projeto ainda não tem nenhum dos dois, comece pelo lint — dá resultado no primeiro dia.
  4. Permissão de administrador no repositório. Marcar check como obrigatório e ligar alarme de segurança são coisas de quem administra.
Importante: este manual não ensina a escrever um workflow do zero — isso é a aula 08 inteira, e ela já aconteceu. Também não fala de tag, release nem deploy: é a aula 10. E o .gitignore, que teria evitado metade dos problemas da seção 10, é da aula 01.

Vocabulário desta aula

status check
O resultado que um robô reporta sobre um commit: verde, vermelho ou pendente. Todo job do seu workflow vira um status check, com o nome do job.
check obrigatório
Um status check que a branch protection exige que esteja verde para liberar o merge. É a peça que liga a aula 08 à aula 07.
lint
Programa que procura erro provável sem rodar o código: variável não usada, import inexistente, await esquecido.
formatação
Programa que só cuida de aparência — aspas, vírgula final, largura de linha. Não opina sobre certo e errado.
Dependabot
Robô do GitHub que avisa sobre dependência vulnerável e abre Pull Request subindo a versão.
secret scanning
Varredura que reconhece o formato de chaves e tokens. Com push protection ligado, recusa o push antes de o segredo entrar.
code scanning
Análise que lê o código procurando vulnerabilidade — SQL injection, XSS, caminho perigoso de dado. O motor padrão do GitHub é o CodeQL.
rotacionar
Revogar a credencial antiga e criar uma nova no provedor. É a única ação que realmente encerra um vazamento.

02As três camadas

Antes de mexer em qualquer arquivo, separe três coisas que costumam virar uma só na cabeça de quem está começando. Elas não se substituem.

1 · O que roda

O workflow. Ele executa lint, formatação e teste e relata o resultado. Só isso. Ele nunca impede nada — nem quando fica vermelho.

2 · O que trava

A branch protection, exigindo aquele check. É ela que deixa o botão de merge cinza. Sem ela, o robô fala e ninguém precisa escutar.

3 · O que vigia

Dependabot, secret scanning e code scanning. Não dependem de você abrir PR: eles olham o repositório o tempo todo e escrevem na aba Security.

Repare: quase todo problema desta aula é confundir a camada 1 com a camada 2. "O check está vermelho e o merge não sai" — quem impede é a camada 2. "Marquei como obrigatório e nada acontece" — a camada 1 provavelmente nem rodou.
O robô que revisa

03Lint e testes no ci.yml que você já tem

Abra .github/workflows/ci.yml. Ele deve estar mais ou menos assim, do jeito que a aula 08 deixou:

.github/workflows/ci.yml — como estava
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - run: npm ci
      - run: npm run build

Comece pela branch, como sempre — nada direto na main:

terminal
git switch main
git pull
git switch -c ci/lint-e-testes

O arquivo inteiro, depois da mudança

Copie este e substitua o seu. As novidades são o bloco permissions e o job qualidade. O build continua igualzinho.

.github/workflows/ci.yml — completo
name: CI

on:
  push:
    branches: [main]
  pull_request:

# só leitura: este workflow não precisa escrever no repositório
permissions:
  contents: read

jobs:
  qualidade:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm

      - name: Instalar dependências
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Formatação
        run: npx prettier --check .

      - name: Testes
        run: npm test

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - run: npm ci
      - run: npm run build
Por que dois jobs e não seis passos num job só: jobs rodam em paralelo e viram checks separados no PR. Com dois jobs você vê num relance se o problema é qualidade ou build — e pode exigir um sem exigir o outro.
Cuidado com a ordem dos passos: lint e formatação são rápidos, teste é lento. Deixe os rápidos primeiro. O job para no primeiro passo que falha, então o retorno chega em segundos em vez de minutos.

Se o seu projeto não é Node

Muda o setup-* e mudam os comandos; o desenho é idêntico.

linguagemprepararlintteste
Nodeactions/setup-node@v4npm run lintnpm test
Pythonactions/setup-python@v5ruff check .pytest
Javaactions/setup-java@v4mvn checkstyle:checkmvn test
Goactions/setup-go@v5golangci-lint rungo test ./...
Rubyruby/setup-ruby@v1bundle exec rubocopbundle exec rspec

Commite e abra o Pull Request:

terminal
git add .github/workflows/ci.yml
git commit -m "ci: roda lint, formatação e testes no PR"
git push -u origin ci/lint-e-testes
$ git push -u origin ci/lint-e-testes remote: Create a pull request for 'ci/lint-e-testes' on GitHub by visiting: remote: https://github.com/voce/repo/pull/new/ci/lint-e-testes branch 'ci/lint-e-testes' set up to track 'origin/ci/lint-e-testes'.
Anote agora: o nome que vai aparecer na caixa de checks é o nome do job — aqui, qualidade e build. Se o job tiver um campo name:, é ele que aparece. É por esse nome, letra por letra, que a seção 05 vai exigir o check.

04Ler o resultado no Pull Request

Abra o PR e desça até o fim. Um minuto depois do push, a caixa de checks aparece:

Some checks were not successful ✓ build Successful in 41s Details ✕ qualidade Failing after 18s Details Merge pull request ← ainda clicável. por enquanto.
  1. Clique em Details, não em "re-run". Rodar de novo quase nunca muda o resultado — e queima dois minutos.
  2. Vá direto ao passo vermelho. A lista de passos fica à esquerda; o que falhou vem com um ✕. Clique nele para abrir o log.
  3. Leia de baixo para cima. A última linha vermelha costuma ser a resposta inteira: nome do arquivo, número da linha, regra que quebrou.
  4. Reproduza na sua máquina. Rode o mesmo comando do passo — npm run lint, npm test — e conserte localmente. É mais rápido que empurrar commit atrás de commit para ver se passou.
Repare: cada push novo na branch refaz os checks automaticamente. Não precisa fechar e reabrir o PR, nem apertar nada. E o log das execuções fica guardado por 90 dias.
Neste momento o merge ainda está liberado. O ✕ aparece e o botão continua verde. É isso que a próxima seção conserta — e é a diferença entre a aula 08 e a aula 09.
O portão

05Checks obrigatórios, tela por tela

Aqui a aula 08 e a aula 07 se encontram. Você vai pegar o resultado do workflow e transformar em condição de merge na regra que protege a main.

Antes de começar: o check precisa ter rodado pelo menos uma vez neste repositório. A busca do GitHub só oferece nomes que já reportaram recentemente — ela não aceita nome digitado à mão. Se você ainda não abriu o PR da seção 03, abra agora e deixe rodar.

Caminho A — regra clássica de branch protection

  1. Abra o repositório e clique em Settings. A aba fica na barra de cima, à direita, ao lado de Insights. Se ela não aparece, você não é administrador do repositório — peça a quem é.
  2. No menu da esquerda, clique em Branches. Você vai ver a regra que criou na aula 07, com o padrão main na coluna da esquerda.
  3. Clique em Edit na regra da main. Editar a regra existente, não criar outra: duas regras no mesmo padrão de branch é fonte garantida de confusão.
  4. Marque Require status checks to pass before merging. Um campo de busca aparece logo abaixo, com o texto Search for status checks in the last week for this repository.
  5. Digite qualidade no campo e clique no resultado. Ele desce para uma lista de checks exigidos, com a fonte ao lado — GitHub Actions. Repita para build se quiser exigir os dois.
  6. Decida sobre Require branches to be up to date before merging. Ele fica logo acima da busca. Leia o quadro abaixo antes de marcar.
  7. Role até o fim e marque Do not allow bypassing the above settings. Sem isso, quem é administrador passa por cima da regra — inclusive você, sem perceber, numa sexta às 18h.
  8. Clique em Save changes. O GitHub pede a sua senha ou o segundo fator se a conta tiver 2FA. É esperado.
Sobre o Require branches to be up to date: marcado, o PR só entra se a branch já tiver a main mais recente dentro dela. É mais seguro — evita o caso em que dois PRs passam sozinhos e quebram juntos. E é mais chato: cada merge na main obriga todos os outros PRs abertos a se atualizarem e rodarem tudo de novo. Em time pequeno, marque. Em repositório movimentado, ou você usa merge queue, ou desmarca.

Caminho B — ruleset (o jeito novo)

Se o seu repositório usa ruleset em vez da regra clássica, a caixinha é a mesma, só que em outro lugar:

  1. Settings → Rules → Rulesets e clique no ruleset que protege a main (ou em New branch ruleset, se ainda não existe).
  2. Em Target branches, confirme que a main está incluída — normalmente por Include default branch.
  3. Na lista Rules, marque Require status checks to pass e clique em + Add checks.
  4. Busque qualidade, escolha a fonte GitHub Actions e adicione.
  5. Deixe o ruleset em Active, não em Evaluate. Em Evaluate ele só simula e não bloqueia nada.
  6. Create ou Save changes.
Escolha um ou dois checks, não dez. Check obrigatório que demora sete minutos vira check que o time inteiro aprende a odiar — e o passo seguinte ao ódio é alguém desligar tudo numa sexta-feira. Exija o que é rápido e confiável; deixe o resto informativo.

06Provar que trava

Regra da casa: se você não viu o portão fechar, ele não está fechado. Faça um PR que quebra de propósito.

terminal
git switch main
git pull
git switch -c teste/quebrando-o-lint

# uma variável que ninguém usa: o lint reclama disso em qualquer linguagem
echo "const naoUsada = 42" >> src/index.js

git commit -am "test: quebra o lint de propósito"
git push -u origin teste/quebrando-o-lint

Abra o PR, espere o check e desça até o botão de merge. O que você tem que ver é isto:

✕ Some checks were not successful qualidade — Failing after 22s Merge pull request ← cinza, não clicável Required statuses must pass before merging

Agora conserte: apague a linha, commite de novo e não toque em mais nada. O check roda sozinho e o botão volta ao verde.

terminal
git restore src/index.js
git commit -am "revert: tira a variável de teste"
git push
Compare com a seção 04: lá o check ficou vermelho e o merge continuou possível. A única coisa que mudou entre um caso e outro foi uma caixinha marcada nas configurações. Nenhuma linha de código.
Quatro jeitos de travar o repositório inteiro sem querer: exigir um check que tem filtro de paths: e por isso não roda em todo PR; renomear o job depois de exigi-lo pelo nome antigo; usar matriz e exigir só uma das combinações; e exigir um check de um workflow que só dispara em push, nunca em pull_request. Os quatro estão detalhados na seção 12.
Os robôs que vigiam

07Dependabot

Dependência desatualizada é dívida que rende juros: quanto mais tempo passa, mais cara fica a atualização. O Dependabot troca a tarde perdida a cada seis meses por um Pull Request pequeno por semana.

São três coisas com o mesmo nome

recursoo que fazcomo liga
Dependabot alertsAvisa que uma dependência sua tem vulnerabilidade conhecida. Só o aviso, na aba Security.Botão em Settings → Code security
Dependabot security updatesAlém de avisar, abre o PR subindo para a versão corrigida.Botão logo abaixo do anterior
Dependabot version updatesAtualização de rotina, mesmo sem vulnerabilidade nenhuma.O arquivo .github/dependabot.yml

Ligar os dois primeiros

  1. Settings → Code security no menu da esquerda.
  2. Ligue Dependabot alerts. É o primeiro botão do bloco Dependabot.
  3. Ligue Dependabot security updates. Fica logo abaixo e só pode ser ligado depois do primeiro.

O arquivo, completo e copiável

Este liga as atualizações de rotina. Ele mora em .github/dependabot.yml — não em .github/workflows/.

.github/dependabot.yml
version: 2

updates:
  # --- as dependências do projeto ---
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "America/Sao_Paulo"
    open-pull-requests-limit: 5
    labels:
      - "dependências"
    # mensagem no padrão da aula 07
    commit-message:
      prefix: "chore"
      include: "scope"
    # um PR só para tudo que é ferramenta de desenvolvimento
    groups:
      ferramentas:
        dependency-type: "development"
        update-types:
          - "minor"
          - "patch"
    # major de framework a gente sobe na mão, com calma
    ignore:
      - dependency-name: "react"
        update-types: ["version-update:semver-major"]

  # --- as actions do seu workflow também envelhecem ---
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
    labels:
      - "ci"

Commite e mande para a main pelo caminho normal:

terminal
git switch -c chore/dependabot
git add .github/dependabot.yml
git commit -m "chore: liga o dependabot semanal"
git push -u origin chore/dependabot

Linha por linha

package-ecosystem
Qual gerenciador de pacotes. Um bloco por ecossistema: npm, pip, maven, gomod, docker, github-actions.
directory
Onde está o manifesto, a partir da raiz. Monorepo com três pastas quer três blocos.
open-pull-requests-limit
Teto de PRs abertos ao mesmo tempo por bloco. O padrão é 5 e raramente vale aumentar.
groups
Junta várias atualizações num PR só. É o que separa "um PR por semana" de "vinte e três PRs na segunda".
ignore
O que ele não deve propor. Útil para segurar major de framework, que quase nunca é atualização automática.
commit-message
Prefixo do commit, para os PRs dele entrarem no padrão de Conventional Commits da aula 07 — e no changelog da aula 10.

O que fazer com o PR que ele abrir

  1. Olhe os checks primeiro. É por isso que o Dependabot vale a pena: ele te entrega a atualização já testada pelo seu próprio CI.
  2. Leia o corpo do PR. Ele traz o changelog e as notas de release da biblioteca, colados ali. Procure a palavra breaking.
  3. Patch e minor com tudo verde: merge sem cerimônia. É o caso da grande maioria.
  4. Major: trate como mudança de verdade. Leia o guia de migração, rode na sua máquina, não faça de sexta.
  5. Check vermelho é informação valiosa, não incômodo: a biblioteca nova quebrou você, e você descobriu antes de instalar.
Cuidado: o PR do Dependabot roda com permissões reduzidas e não enxerga os secrets normais do repositório. Se algum passo do seu CI precisa de secret, cadastre em Settings → Secrets and variables → Dependabot, que é uma lista separada da de Actions.

08Secret scanning e push protection

São duas coisas ligadas no mesmo lugar e com efeitos bem diferentes: uma varre o que já está lá, a outra impede o que ainda vai entrar.

  1. Settings → Code security. Mesma tela do Dependabot, mais abaixo.
  2. Ligue Secret scanning. Ele varre o histórico inteiro e abre alerta em Security → Secret scanning para cada segredo que reconhecer.
  3. Ligue Push protection. Este é o que importa: recusa o git push no instante em que o segredo tentaria entrar.

Com o push protection ligado, é isto que você vê ao tentar empurrar uma chave:

$ git push remote: error: GH013: Repository rule violations found for refs/heads/main remote: — GITHUB PUSH PROTECTION remote: Push cannot contain secrets remote: —— AWS Access Key ID ————————————————— remote: locations: remote: commit: 8f2c1ab remote: path: .env:3 ! [remote rejected] main -> main (push declined due to repository rule violations)
Este é o melhor erro do curso inteiro. É a única defesa desta aula que age antes do vazamento. Todas as outras — alerta, varredura, revogação — chegam depois que o segredo já saiu da sua máquina.

O que fazer quando ele recusar

  1. Não force. --force não passa por cima disso, e insistir só faz você perder tempo.
  2. Veja se a chave é de verdade. Se for um valor de exemplo, troque por algo obviamente falso — SUA_CHAVE_AQUI — e refaça o commit.
  3. Se a chave é real: ela já valeu de verdade em algum lugar. Vá para a seção 10 e rotacione. O push foi recusado, mas o valor pode ter circulado em outro canto.
  4. Tire do commit, não só do arquivo. Se o segredo está num commit anterior da mesma branch, o push continua sendo recusado. Refaça o commit sem ele.
  5. Ponha o arquivo no .gitignore — o da aula 01 — para não acontecer de novo.
Sobre o "bypass": o GitHub oferece um link para você passar por cima, pedindo uma justificativa — é falso positivo, vou corrigir depois, uso apenas em teste. A escolha fica registrada com o seu nome. Só marque falso positivo quando for realmente falso positivo.
Repare: em repositório público o secret scanning é gratuito e liga em um clique. Em repositório privado depende do plano da conta ou da organização — se o botão não aparece na sua tela, é isso. Nos públicos há ainda um bônus: ao encontrar uma chave de provedor parceiro, o GitHub avisa o provedor, e vários revogam a credencial sozinhos em minutos.

09Code scanning com CodeQL

O lint acha erro de escrita. O CodeQL acha vulnerabilidade: ele segue o caminho que um dado percorre desde a entrada até um lugar perigoso. Este código passa no lint sem um único aviso:

src/rotas.js
app.get("/usuario", (req, res) => {
  const id = req.query.id
  db.query("SELECT * FROM users WHERE id = " + id)
})

E é isto que o CodeQL escreve no seu Pull Request:

CodeQL · src/rotas.js:3 · high Database query built from user-controlled sources este dado vem de: req.query.id (linha 2) e chega sem filtro em: db.query() (linha 3)

Ligar em dois cliques

  1. Settings → Code security → bloco Code scanning → Set up.
  2. Escolha Default. O GitHub detecta as linguagens do repositório e cuida do resto — você não escreve workflow nenhum.
  3. Confira as linguagens sugeridas e clique em Enable CodeQL. A primeira análise começa em seguida e pode levar alguns minutos.
  4. Olhe os resultados em Security → Code scanning. Cada alerta traz o caminho do dado, a explicação da classe de vulnerabilidade e um exemplo de correção.
Quando escolher Advanced: quando você precisa mandar no processo — compilar de um jeito específico, rodar em horário fixo, incluir consultas extras. Ele cria um .github/workflows/codeql.yml de verdade, que você edita como qualquer outro workflow da aula 08. Comece pelo Default; migre só quando ele não der conta.

O que fazer com um alerta

  1. Leia o caminho do dado. O valor é confiável na origem? Se vem de req, de arquivo enviado ou de variável de ambiente controlada por outro, não é.
  2. Corrija na causa. No exemplo acima: consulta parametrizada, não concatenação de string.
  3. Falso positivo acontece. Feche o alerta escolhendo o motivo — Used in tests, False positive, Won't fix. Fica registrado com o seu nome, o que é bem diferente de ignorar.
  4. Pense duas vezes antes de exigir o CodeQL como check obrigatório. Ele é lento. Todo merge do time vai esperar por ele.
Vale saber: num PR o CodeQL só comenta nas linhas que aquele PR mexeu. Ele não despeja em cima de você a dívida inteira do repositório — a dívida antiga fica na aba Security, para você atacar quando puder.
Emergência

10O segredo já foi para o histórico

Aconteceu: a chave da API está num commit que já foi para o GitHub. Esta seção é a mais séria do curso, e a ordem dos passos não é negociável. Leia inteira antes de fazer o primeiro.

A regra que resolve tudo: rotacione a credencial primeiro, limpe o histórico depois. Quem clonou o repositório já tem o valor no disco — nada que você faça no GitHub alcança a máquina de outra pessoa. A única ação que realmente encerra o vazamento é a chave deixar de funcionar.

Passo 1 — rotacione a credencial. Agora.

Antes de olhar o Git. Antes de avisar o time. Antes de qualquer coisa.

  1. Entre no painel do provedor — AWS, Stripe, Google Cloud, o banco de dados, o que for.
  2. Crie uma credencial nova. Primeiro a nova, para não derrubar o serviço no meio do conserto.
  3. Revogue a antiga. Este é o passo que encerra o vazamento. Sem ele, todo o resto é teatro.
  4. Confirme que a antiga morreu mesmo. Tente usá-la e veja dar erro de autenticação. Provedor que tem "desativar" e "excluir" costuma exigir os dois.

Passo 2 — troque onde ela era usada

Variável de ambiente do servidor, cofre do time, secret do repositório (que é assunto da aula 10), .env local de cada pessoa. E confirme que a aplicação voltou a funcionar com a chave nova antes de seguir.

Passo 3 — procure uso indevido

  1. Log de acesso do provedor. Alguma chamada de IP que você não reconhece, no intervalo entre o push e a revogação?
  2. Cobrança. Chave de nuvem vazada vira máquina de minerar em minutos, e a conta chega no fim do mês.
  3. Recurso criado que ninguém pediu. Usuário novo, bucket novo, regra de firewall nova.
  4. Se achar qualquer coisa, isso deixou de ser problema de Git: é incidente de segurança. Avise quem tem que saber, no mesmo dia.

Passo 4 — tire do código e ignore o arquivo

Agora sim, um commit normal e sem drama: o valor que está ali já não vale mais nada.

terminal
# o arquivo sai do rastreamento, mas continua na sua pasta
git rm --cached .env

# e nunca mais volta — o .gitignore da aula 01
printf '.env\n.env.*\n*.pem\n' >> .gitignore

git add .gitignore
git commit -m "chore: tira o .env do rastreamento e ignora segredos"
Repare: isto tira o arquivo do presente. O segredo continua vivo em todos os commits antigos — é exatamente por isso que existe o passo 5.

Passo 5 — só agora, limpe o histórico

A ferramenta é o git filter-repo. Não use git filter-branch: está aposentado, é lento e erra em casos de canto. Avise o time antes: isso reescreve o hash de todos os commits e todo mundo vai precisar clonar de novo.

terminal
# 1. instale a ferramenta
pip install git-filter-repo

# 2. clone espelhado, numa pasta separada do seu repositório de trabalho
git clone --mirror git@github.com:voce/repo.git
cd repo.git

# 3a. apagar o arquivo de todos os commits
git filter-repo --invert-paths --path .env

# 3b. ou, se o segredo estava solto no meio do código:
#     crie trocas.txt com uma linha por segredo, no formato
#     valor-que-vazou==>REMOVIDO
git filter-repo --replace-text ../trocas.txt

# 4. devolva o remoto (o filter-repo tira de propósito) e empurre
git remote add origin git@github.com:voce/repo.git
git push --force --mirror origin
$ git filter-repo --invert-paths --path .env Parsed 214 commits New history written in 1.34 seconds; now repacking/cleaning... Completely finished after 3.12 seconds.
O force-push vai esbarrar na branch protection da aula 07. É esperado — ela está fazendo o trabalho dela. Desligue a regra da main, faça o push, e religue na hora. Deixar desligada "só por hoje" é como esse tipo de coisa costuma ficar desligada por seis meses.

Passo 6 — feche as portas que sobraram

  1. Peça ao suporte do GitHub para expurgar as referências em cache. Depois do force-push, a URL /commit/8f2c1ab ainda abre para quem tem o hash. Só o suporte apaga isso.
  2. Verifique os forks. Um fork guarda os objetos do repositório de origem: o commit sobrevive lá mesmo depois de sumir aqui. Se o repositório é público e tem forks, considere o segredo permanentemente exposto — e agradeça por ter rotacionado no passo 1.
  3. Avise o time para reclonar. Quem tentar dar pull por cima do histórico antigo vai reintroduzir os commits removidos. O caminho é git clone de novo, do zero.
  4. Ligue o push protection (seção 08) se ainda não estiver ligado. Ele é a defesa que teria evitado tudo isto.

Por que apagar o commit não desfaz o vazamento

Esta é a parte que quase todo mundo erra. "Apaguei o commit em dois minutos, ninguém viu" é uma frase falsa por cinco motivos ao mesmo tempo:

onde o segredo continuapor quêdá para apagar?
No disco de quem clonouUm clone é uma cópia inteira do histórico. Está fora do seu alcance.Não
No cache do GitHubCommits ficam acessíveis pela URL do hash mesmo depois do force-push.Só pedindo ao suporte
Nos forks e nos PRsFork e Pull Request seguram referência ao objeto do commit.Raramente, e é trabalhoso
Nos robôs que varrem o GitHubExistem robôs que leem push público em segundos. Dois minutos é a janela inteira de que precisam.Não
Em logs e caches de CILog de execução, cache de build, artefato — e o git reflog da sua própria máquina.Parcialmente
Resumindo: limpar o histórico serve para o repositório não continuar distribuindo o segredo daqui para a frente. Não serve para desfazer o que já saiu. Quem desfaz é a rotação — e por isso ela é o passo 1, não o passo 5.

12Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
O check não aparece na lista de obrigatórios Ele nunca rodou neste repositório. A busca só oferece checks que reportaram nos últimos dias — e não aceita nome digitado à mão. Abra um PR qualquer, deixe o workflow rodar até o fim, volte a Settings → Branches e busque de novo. É a ordem: rodar primeiro, exigir depois.
Expected — Waiting for status to be reported, e não sai disso O check é exigido mas não roda neste PR: filtro de paths:, um if: que pulou o job, ou o workflow só dispara em push. Tire o filtro do job obrigatório, ou tire o job da lista de obrigatórios. Check exigido tem que rodar em todo PR, sem exceção.
Todos os PRs travaram de uma vez, sem ninguém mexer em nada Alguém renomeou o job. O nome antigo continua exigido e ninguém mais reporta por ele. Atualize a lista de checks obrigatórios com o nome novo. Renomear job é sempre uma mudança em dois lugares.
Exigi qualidade, mas aparecem qualidade (18) e qualidade (20) O job usa strategy: matrix. Cada combinação vira um check com nome próprio. Exija cada combinação pelo nome completo — ou tire a matriz do job obrigatório.
O merge continua liberado com o check vermelho O check está rodando, mas não foi marcado como obrigatório. É a camada 1 sem a camada 2. Seção 05. E confira se a regra atinge mesmo a main.
O merge trava para o time, mas eu consigo clicar Você é administrador e a regra permite bypass. Marque Do not allow bypassing the above settings. Regra que não vale para quem a criou não é regra.
O workflow nem começa Erro de indentação no YAML, ou o arquivo não está em .github/workflows/. A aba Actions mostra o erro de sintaxe. YAML é sensível a espaço — e não aceita tabulação.
O dependabot.yml não faz nada Está em .github/workflows/ em vez de .github/, ou ainda não chegou à main. Mova para .github/dependabot.yml e faça o merge. Configuração do GitHub só vale a partir da branch padrão.
Chegaram 23 PRs do Dependabot na segunda de manhã Sem groups e sem open-pull-requests-limit, ele abre um PR por dependência. Agrupe por tipo, limite a cinco e mantenha o intervalo semanal. Seção 07.
O PR do Dependabot falha num passo que precisa de secret PR do Dependabot não enxerga os secrets de Actions. Cadastre em Settings → Secrets and variables → Dependabot, que é uma lista à parte.
GH013 · Push cannot contain secrets O push protection reconheceu uma chave no que você ia enviar. Não force. Tire o segredo do commit e, se a chave for real, rotacione — seção 10.
Tirei o segredo do arquivo e o push continua recusado Ele está num commit anterior da mesma branch. O push manda a série inteira. Refaça o commit sem o segredo, ou limpe a branch antes de empurrar.
"Apaguei o commit do segredo, resolvido" Não resolveu. O valor saiu do seu controle no instante do push. Rotacione a credencial. Limpar histórico é o passo 5, nunca o passo 1.
O git push --force do filter-repo foi recusado A branch protection da aula 07 está fazendo o trabalho dela. Desligue a regra da main, empurre e religue na mesma hora.
Depois de limpar o histórico, os commits antigos voltaram Alguém do time deu pull por cima do clone velho e reintroduziu tudo. Avise o time para clonar de novo, do zero. Reescrita de histórico não sobrevive a um clone antigo.
Não acho Code security nas configurações Ou você não é administrador, ou o repositório é privado e o plano não inclui aquele recurso. Faça o exercício num repositório público seu: lá tudo desta aula é gratuito.
