Qualidade automática: testes, lint e segurança no PR

No fim de hoje a sua main não aceita mais código quebrado — o botão de merge fica cinza sozinho. E você sabe o que fazer nos dez primeiros minutos depois que uma chave vaza.

deixe aberto: o repositório da aula 08, com o ci.yml que já roda o build, e a main já protegida na aula 07. hoje a gente não cria workflow novo — a gente faz o de vocês crescer.

LGTM
1A Ana gastou duas horas fazendo o trabalho de um programa de 40 segundos.
2Ninguém olhou a decisão: se a função devia existir, se o nome faz sentido, se quebra alguém.
3"Rodei aqui e quebrou" não é evidência. É a máquina dela, com as dependências dela.
4Depois de doze comentários de espaço em branco, o LGTM sai por cansaço.
5E se a Ana estiver de férias, o PR entra sem ninguém olhar coisa nenhuma.

Pessoa revisa decisão; máquina revisa regra. Todo comentário de estilo escrito por um humano é sintoma de automação faltando — e a automação é a aula de hoje.

// o conceito

Três camadas, e uma não substitui a outra

1. O que roda

O workflow: lint, formatação e teste a cada Pull Request. Ele já existe desde a aula 08 — hoje ganha mais três passos.

2. O que trava

O status check obrigatório, ligado à branch protection da aula 07. Sem ele, o robô fala e ninguém é obrigado a escutar.

3. O que vigia

Dependabot, secret scanning e code scanning: três robôs que olham o repositório mesmo quando ninguém abriu PR nenhum.

// retomada da aula 08

O ci.yml que você já tem

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - run: npm ci
      - run: npm run build
1O gatilho pull_request já está lá. Metade do trabalho de hoje a aula 08 fez.
2Um job só: build. Ele responde "compila?" — não responde "funciona?".
3O resultado já aparece no PR, verde ou vermelho, e ninguém é obrigado a olhar.
4Este é o arquivo que a gente edita hoje. Não crie outro.

Repositório com cinco arquivos em .github/workflows/ é repositório onde ninguém sabe o que roda quando. Um workflow de CI, com vários jobs dentro. Deploy é outro assunto e outro arquivo — aula 10.

// vocabulário

Três robôs diferentes — e a confusão custa caro

Lint

Procura erro provável sem rodar o código: variável não usada, comparação frouxa, await esquecido, import que não existe. Opina sobre o que é certo.

Formatação

Não opina sobre certo e errado — só sobre aparência. Aspas, vírgula no fim, largura da linha. Não discute: reescreve.

Teste

Roda o código de verdade e compara com o esperado. É o único dos três que sabe dizer se a coisa funciona.

Lint é o revisor, formatação é o diagramador, teste é o leitor que confere se a história fecha. Nenhum faz o trabalho do outro.

eslintprettiervitestjestruffblackpytestrubocopgolangci-lint

Os nomes mudam com a linguagem; os três papéis não mudam nunca. Se o seu projeto não tem os três, comece pelo lint — é o que dá resultado no primeiro dia.

LAB 1

Lint e teste no mesmo ci.yml

~12 min

Abra o repositório da aula 08. Você vai acrescentar um job — não um arquivo.

Crie a branch de trabalho

Como na aula 07: nada direto na main, nem hoje.

git switch -c ci/lint-e-testes

Acrescente o job qualidade

No mesmo nível de indentação do build, dentro de jobs:. Os dois rodam em paralelo.

  qualidade:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - run: npm ci
      - name: Lint
        run: npm run lint
      - name: Formatação
        run: npx prettier --check .
      - name: Testes
        run: npm test

Commite e abra o Pull Request

Mensagem no padrão da aula 07.

git add .github/workflows/ci.yml
git commit -m "ci: roda lint, formatação e testes no PR"
git push -u origin ci/lint-e-testes

Olhe o fim do PR

Em um minuto devem aparecer dois checks: build e qualidade.

quando terminar

Anote o nome exato que apareceu na caixa de checks. É por esse nome, letra por letra, que a gente vai exigir o check no LAB 2 — e ele é o nome do job, não o do arquivo.

// a caixa de checks

O que o Pull Request mostra agora

Some checks were not successful ✓ build Successful in 41s Details ✕ qualidade Failing after 18s Details Merge pull request ← ainda verde. por enquanto.

Clique em Details e vá direto ao passo vermelho. A última linha vermelha do log é, quase sempre, a resposta inteira.

1O nome do check é o nome do job — ou o name: dele, se você deu um.
2✕ não é bronca. É economia: 18 segundos para achar o que custaria duas horas de revisão.
3Cada push novo na branch refaz os checks. Não precisa fechar e reabrir o PR.
4O log fica 90 dias. Depois some — se importa depois disso, vira artefato (aula 08).
// onde a aula 07 e a aula 08 se encontram

Avisar é diferente de travar

check informativo

O robô fala, o botão continua verde

O ✕ aparece e o "Merge pull request" segue clicável. Numa sexta às 18h, com gente esperando, alguém clica. E o time aprende que vermelho é decoração.

check obrigatório

O botão fica cinza sozinho

O GitHub escreve Required statuses must pass before merging e não deixa clicar. Sem conversa, sem pressa, sem exceção por cansaço.

A aula 07 protegeu a main. A aula 08 fez o robô falar. Hoje as duas se encontram: o resultado do workflow vira condição de merge. É esse encontro que transforma automação em regra.

// a tela

Onde o check vira obrigatório

Settings → Branches

Ou Settings → Rules → Rulesets, se o seu repositório já usa ruleset em vez da regra clássica. A caixinha é a mesma nos dois caminhos.

Edite a regra da main — a que você criou na aula 07

Edite, não crie outra. Duas regras na mesma branch é receita de confusão.

Marque Require status checks to pass before merging

Um campo de busca aparece logo abaixo. Digite qualidade e selecione o check na lista.

Decida sobre Require branches to be up to date

Marcado, o PR só entra atualizado com a main. Mais seguro — e mais chato: cada merge obriga os outros PRs a se atualizarem.

Salve — e marque Do not allow bypassing the above settings

Sem isso, quem é admin passa por cima. Inclusive você, sem perceber, às 18h de sexta.

Marque um ou dois checks, não dez. Check obrigatório que demora sete minutos é check que o time aprende a odiar — e o passo seguinte ao ódio é desligar tudo.

parada obrigatória

Sem seguir sem responder

Três perguntas. A terceira é a mais importante da aula — e a que mais gente erra.

1O check ficou vermelho e o merge não sai. Quem está impedindo: o workflow ou a branch protection?
2Você renomeou o job de qualidade para quality. O que acontece com o PR que já estava aberto?
3Alguém commitou a chave da API, percebeu em dois minutos e apagou o commit. O segredo está seguro?

respostas: 1 — a branch protection; o workflow só relata. 2 — o check exigido nunca mais reporta, e o PR trava esperando um nome que não existe mais. 3 — não, e o final da aula explica por quê.

LAB 2

Travar de propósito

~15 min

Regra da casa: se você não viu o portão fechar, ele não está fechado. Vamos quebrar o lint de propósito.

Faça o merge do PR do LAB 1

O check precisa ter rodado ao menos uma vez para aparecer na busca do próximo passo.

Exija o check

Settings → Branches → regra da main → Require status checks to pass before merging → busque qualidade → Save changes.

Abra um PR que quebra o lint

Uma variável não usada resolve. É feio de propósito.

git switch -c teste/quebrando-o-lint
echo "const naoUsada = 42" >> src/index.js
git commit -am "test: quebra o lint de propósito"
git push -u origin teste/quebrando-o-lint

Tente clicar em Merge

Não vai dar. Leia a frase que o GitHub escreve embaixo do botão cinza — é ela que você vai reconhecer quando alguém do time pedir socorro.

Conserte e veja liberar

Apague a linha, commite de novo e olhe o check virar verde sozinho, sem ninguém apertar nada.

quando terminar

Compare com o LAB 1: lá o check ficou vermelho e o merge continuou possível. A única coisa que mudou entre um e outro foi uma caixinha marcada — nenhuma linha de código.

// a pegadinha

Quatro jeitos de travar o repositório inteiro

1O check não aparece na busca. A lista só oferece checks que já rodaram naquele repositório nos últimos dias. Rode uma vez — abra um PR qualquer — e volte. Não adianta digitar o nome à mão e torcer.
2Check exigido que não roda naquele PR. Se o job tem filtro de paths: e o PR não tocou naqueles arquivos, o check nunca reporta: fica em Expected — waiting for status e o PR trava para sempre. Não misture paths: com check obrigatório.
3Matriz vira vários checks. Com strategy: matrix, cada combinação é um check com nome próprio — qualidade (18), qualidade (20). Exija cada um, ou nenhum.
4Renomear o job renomeia o check. O nome antigo continua exigido, ninguém mais reporta por ele, e todos os PRs param. Renomeou? Atualize a lista de obrigatórios no mesmo dia.

Toda vez que o merge travar sem explicação, a pergunta é uma só: o nome que está exigido na configuração é exatamente o nome que o workflow está reportando?

// dependabot

O robô que abre PR de atualização

Ele lê o seu package.json, compara com o registro, e quando sai versão nova abre um Pull Request — com o changelog da biblioteca no corpo do PR.

Alerts

Avisa que uma dependência sua tem vulnerabilidade conhecida. Só o aviso, na aba Security.

Security updates

Além de avisar, abre o PR que sobe para a versão corrigida. É o que você liga primeiro.

Version updates

Atualização de rotina, mesmo sem vulnerabilidade. Esta exige o arquivo dependabot.yml no repositório.

A vantagem não é a atualização — é o PR. O PR do Dependabot passa pelos mesmos checks que os seus: se a biblioteca nova quebra o teste, você descobre antes de instalar. Sem ele, atualizar é aquela tarde perdida a cada seis meses.

Ele também atualiza as actions do seu workflow. Aquele actions/checkout@v4 também envelhece.

// o arquivo

.github/dependabot.yml

.github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
    open-pull-requests-limit: 5
    groups:
      dev:
        dependency-type: "development"

  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
1Mora em .github/, não em .github/workflows/. É o erro número um.
2Um bloco por ecossistema: npm, pip, maven, docker, github-actions. Cada linguagem do repo tem o seu.
3directory é onde está o manifesto. Monorepo com três pastas quer três blocos.
4Agrupe e limite o número de PRs. Sem isso, segunda de manhã você abre o repositório com 23 Pull Requests e desliga tudo.
5O arquivo vale a partir do merge na main. Como todo arquivo de configuração do GitHub.

O manual traz este arquivo inteiro, com agrupamento, rótulos e prefixo de commit no padrão da aula 07 — pronto para copiar.

// secret scanning

A chave que não devia ter saído da sua máquina

$ git push remote: error: GH013: Repository rule violations found remote: — GITHUB PUSH PROTECTION remote: Push cannot contain secrets remote: —— AWS Access Key ID —————————— remote: locations: remote: commit: 8f2c1ab remote: path: .env:3 ! [remote rejected] main -> main (push declined)

Não é o robô sendo chato. É a única defesa que age antes do vazamento — todas as outras chegam depois.

1Ele trabalha de dois modos: varre o que já está no repositório e bloqueia o push na hora em que o segredo tenta entrar.
2Reconhece o formato das chaves dos provedores parceiros — AWS, Stripe, Slack, npm, o próprio GitHub.
3Quando acha uma chave de parceiro em repositório público, o GitHub avisa o provedor, e vários revogam sozinhos em minutos.
4Dá pra passar por cima, mas o GitHub pede uma justificativa e registra quem passou. Fricção de propósito.
5Em repositório público é grátis e liga em um clique. Em privado, depende do plano da conta.
// code scanning · codeql

O robô que lê o código procurando buraco

src/rotas.js
app.get("/usuario", (req, res) => {
  const id = req.query.id
  db.query(
    "SELECT * FROM users WHERE id = " + id
  )
})
CodeQL · alerta em src/rotas.js:4 Database query built from user-controlled sources req.query.id → db.query() severidade: high
1O lint não reclama disso: sintaticamente está tudo certo. O que está errado é o caminho do dado.
2O CodeQL segue o dado da entrada até o lugar perigoso e mostra o trajeto inteiro no alerta.
3No PR ele comenta na linha, como um revisor humano faria — e só nas linhas que aquele PR mexeu.
4Liga em dois cliques pelo default setup. Não precisa escrever workflow nenhum.
5Falso positivo acontece. Você fecha o alerta com justificativa — e a justificativa fica registrada. Ignorar não é opção.

Ele também pode virar check obrigatório. Só lembre que CodeQL é lento — pense duas vezes antes de pôr na frente de todo merge.

LAB 3

Ligar as três defesas

~12 min

Tudo numa tela só: Settings → Code security. Repositório público, para nenhum recurso ficar de fora.

Dependabot

Ligue Dependabot alerts e Dependabot security updates. São dois botões, um embaixo do outro.

Commite o dependabot.yml

Copie do manual, ajuste o ecossistema para a sua linguagem e abra o PR.

git switch -c chore/dependabot
git add .github/dependabot.yml
git commit -m "chore: liga o dependabot semanal"

Secret scanning e push protection

Ligue os dois. O segundo é o que bloqueia o push — sem ele, o robô só chora depois.

Code scanning

Em Code scanning → Set up → Default. Ele detecta as linguagens sozinho.

Confira na aba Security

Ela vira o painel do repositório: alertas de dependência, de segredo e de código, cada um na sua lista.

quando terminar

Teste o push protection de mentira: crie um arquivo com uma linha no formato ghp_ seguida de 36 caracteres quaisquer e tente o push. Deve ser recusado. Depois apague o arquivo — sem forçar nada.

// emergência
o segredo já está no histórico

A ordem certa — e ela não é negociável

Rotacione a credencial. Agora.

Revogue a chave antiga no provedor e crie uma nova. Antes de olhar o Git, antes de avisar o time, antes de qualquer coisa. Quem clonou já tem o valor — a única coisa que cancela o vazamento é a chave parar de funcionar.

Troque onde ela era usada e confirme

Servidor, variável de ambiente, cofre do time, secret do repositório (aula 10). E confirme que a aplicação voltou a funcionar com a nova.

Procure uso indevido

Log de acesso do provedor, cobrança fora do padrão, recurso criado que ninguém pediu. Se achar qualquer coisa, isso deixa de ser problema de Git e vira incidente — avise quem tem que saber.

Tire do código e ignore o arquivo

Commit normal, sem drama: o segredo já não vale mais nada. Se o .gitignore da aula 01 estivesse cobrindo o arquivo, nada disso teria acontecido.

Só então limpe o histórico

Com git filter-repo, reescrevendo todos os commits dali para a frente. Isso muda o hash de todo mundo: o time inteiro vai precisar clonar de novo. Por isso é o último passo, e nunca o primeiro.

A ordem não é estilo, é a diferença entre resolver e fingir que resolveu. Limpar o histórico com a chave ainda válida é arrumar a casa de porta aberta.

// o que quase todo mundo erra

Apagar o commit não desfaz o vazamento

1Quem já clonou tem o commit no disco. Nada que você faça no GitHub alcança a máquina de outra pessoa.
2O GitHub guarda em cache. A URL /commit/8f2c1ab continua abrindo depois do force-push. Quem tem o hash, lê. Só o suporte do GitHub expurga.
3Fork e Pull Request seguram o objeto. O commit sobrevive no fork mesmo depois de sumir do repositório de origem.
4Robôs varrem push público em segundos. "Ficou só dois minutos no ar" não é uma hipótese razoável — é a janela inteira de que eles precisam.
5Sobrou cópia em todo canto: log de execução do CI, cache de build, o reflog da sua própria máquina.
6E o git push --force ainda esbarra na branch protection da aula 07, que você vai ter que desligar e religar — mais um motivo para não ser o primeiro passo.
$ pip install git-filter-repo $ git clone --mirror git@github.com:voce/repo.git $ cd repo.git $ git filter-repo --invert-paths --path .env Parsed 214 commits · New history written # e só depois: git push --force --mirror origin

A única coisa que realmente cancela o vazamento é a chave deixar de funcionar. Todo o resto é higiene — importante, mas depois.
