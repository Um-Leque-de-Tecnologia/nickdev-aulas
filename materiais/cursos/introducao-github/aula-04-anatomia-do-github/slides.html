# README.md

Anatomia do GitHub: repositório, perfil e organização

Na aula 03 você publicou. Hoje a gente faz esse repositório ser entendido por quem chega de fora — e olha o perfil, que é o seu currículo público, queira você ou não.

deixe aberto: o navegador no seu repositório da aula 03 e o terminal na pasta dele. hoje quase tudo acontece na tela, não no terminal.

Publicado — e mudo

É exatamente o que você tem depois da aula 03. Funciona, está no ar — e não diz nada.

1O que é isso? Um site? Um exercício? Uma biblioteca pra instalar?
2Como eu rodo na minha máquina? Precisa de quê instalado?

Nenhuma dessas cinco perguntas se responde com código. Todas se respondem com arquivos de texto — e é isso que a gente escreve hoje.

// a volta guiada

A página do repositório, por partes

About
A caixinha da direita: descrição, link do site e tópicos. É o que aparece na busca do GitHub. Leva 40 segundos e quase ninguém preenche.
Code
A lista de arquivos, a branch atual, o botão de clonar e — logo abaixo — o README renderizado. A primeira tela é essa.
Issues
Onde se relata bug e se combina tarefa. É a aula 05 inteira.
Pull requests
Onde uma mudança é proposta e revisada antes de entrar. Aula 06.
Actions
Automação: testar e publicar sozinho a cada push. Aula 08.
Insights
Gráficos do repositório: quem commitou, quando, quanto. Bom pra entender projeto alheio.
Settings
Visibilidade, colaboradores, apagar o repositório. Só quem é admin vê esta aba.

O resto da aula mexe em três lugares só: o README, o About e o Settings.

// visibilidade

Público × privado

Uma chave só, em Settings, e ela decide quem consegue abrir o endereço do seu repositório.

público

Qualquer pessoa vê

Com ou sem conta no GitHub. Aparece na busca, no seu perfil, no Google. Ver não é mexer: só quem você autorizar consegue gravar. É o que você quer pra portfólio, estudo e open source.

privado

Só quem você convidar

Some da busca e do perfil de quem não tem acesso. Grátis e ilimitado em conta pessoal desde 2019. É o padrão pra trabalho de cliente, projeto de faculdade em grupo e coisa não terminada.

Dá pra trocar depois, nos dois sentidos. Mas trocar de privado para público publica o histórico inteiro de uma vez — é o próximo slide.

// honestidade técnica

O que privado não protege

Privado quer dizer "pouca gente vê". Não quer dizer "seguro".

1Quem tem acesso, vê tudo. Não existe arquivo secreto dentro de repositório privado. Deu acesso, deu acesso ao repositório inteiro.
2Inclusive o histórico. Aquela senha que você apagou no commit seguinte continua lá, num commit antigo, a dois cliques de distância.
3Tirar a pessoa do repositório não apaga a cópia dela. Quem clonou levou o histórico inteiro pra máquina dela.
4Virar público é irreversível na prática. No segundo em que vira, o histórico todo fica legível — e alguém pode ter clonado.
5Segredo se guarda fora do repositório: no .env ignorado (aula 01) ou nos secrets do GitHub (aula 10).

Se um segredo entrou no histórico, ele vazou. Não adianta apagar o arquivo: troque a chave. Rotacionar credencial e varredura automática de segredo são a aula 09.

// os arquivos de recepção

Três arquivos falam por você

O GitHub trata estes três com carinho especial: ele os procura pelo nome, sozinho, e muda a interface quando acha.

README.md

O que é e como se usa. Renderizado na primeira tela do repositório, abaixo da lista de arquivos. É a única coisa que a maioria vai ler.

LICENSE

O que os outros podem fazer com isso. O GitHub reconhece o texto e mostra o nome da licença no About. Sem ele, a resposta legal é "nada".

CONTRIBUTING.md

Como ajudar sem errar. Vira um link automático na hora em que alguém abre uma issue ou um pull request.

Os três são arquivos de texto na raiz, commitados como qualquer outro. Nada aqui é botão mágico — é git add e git commit de sempre.

// o README

O README que faz alguém usar

README.md
# nome-do-projeto

Uma frase dizendo o que é e pra quem.

## Para que serve

Dois ou três parágrafos curtos: o
problema que resolve, e quando não
é a ferramenta certa.

## Como rodar

```bash
git clone …
npm install
npm run dev
```

## Como contribuir

Leia o CONTRIBUTING.md.

## Licença

MIT — veja o arquivo LICENSE.
1A primeira frase é a mais importante. Quem lê decide em cinco segundos se continua. "Projeto da faculdade" não é uma frase.
2Como rodar tem que ser copiável. Comandos em bloco, na ordem, sem "instale as dependências" no lugar do comando.
3Diga o que o projeto não faz. Poupa a decepção de quem escolheu errado — e ganha respeito.
4Escreva pra pessoa que não te conhece. Nada de "é só rodar aquele script". Que script? Qual pasta?
5Um README de quinze linhas boas vence um de cem linhas desatualizadas. Curto e verdadeiro.

Markdown: a língua de tudo aqui

README, issue, comentário de pull request, descrição de release. Aprender uma vez serve pro curso inteiro.

markdown
# Título    ## Subtítulo

**negrito**   *itálico*   `código`

- item de lista
1. item numerado

- [x] tarefa feita
- [ ] tarefa pendente

[texto do link](https://exemplo.com)

| coluna | outra |
|--------|-------|
| valor  | valor |
  • Linha em branco separa parágrafo. Sem ela, duas linhas viram uma só.
  • Bloco de código com três crases e o nome da linguagem — é o que pinta as cores.
  • A checklist - [ ] vira caixa clicável em issue. Vale ouro na aula 05.
  • Dentro do repositório, prefira link relativo: [contribuir](CONTRIBUTING.md). Continua funcionando no fork.

// licença

Escolher licença sem virar advogado

Três respostas cobrem quase tudo que você vai publicar nos próximos anos.

licençaem uma fraseescolha quando
MITFaça o que quiser, inclusive vender, desde que mantenha o aviso de autoria. Sem garantia nenhuma.É o seu padrão. Curta, conhecida, aceita em qualquer lugar.
Apache 2.0Como a MIT, e mais: concede o uso das patentes de quem contribuiu e pede que mudanças em arquivos sejam sinalizadas.Projeto que empresa vai adotar — o jurídico delas gosta da cláusula de patente.
GPL v3Copyleft: pode usar e modificar, mas quem distribuir uma obra derivada tem que abrir o código sob a mesma licença.Você quer garantir que melhorias feitas em cima do seu trabalho voltem pra comunidade.

Existem dezenas de outras — BSD, MPL, CC0 — e choosealicense.com te leva à certa em três perguntas. Não invente licença própria: ninguém vai ler.

// o caso mais comum

Sem licença nenhuma = todos os direitos reservados

  • Código sem licença é protegido por direito autoral por padrão, na lei, sem você fazer nada.
  • Público não quer dizer livre. Qualquer pessoa pode ler o seu código — e, tecnicamente, não pode usar, copiar nem modificar.
  • Ao publicar no GitHub você já aceitou os termos que permitem ver e fazer fork dentro do próprio GitHub. Só isso.
  • Na dúvida, empresa séria não encosta em repositório sem licença. É risco jurídico de graça.

O efeito prático

O seu portfólio sem LICENSE diz, sem querer: "olhe, mas não use". Se você publicou pra ser útil, escolher a licença é parte de publicar.

O conserto

Um arquivo chamado LICENSE, sem extensão, com o texto oficial da licença, o ano e o seu nome. O GitHub tem um assistente que escreve por você.

Trabalho feito na empresa costuma ter dono definido em contrato. Não publique código do trabalho por conta própria — nem como portfólio.

parada obrigatória

Sem seguir sem responder

Três perguntas. A segunda derruba muita gente — inclusive gente com anos de profissão.

1Quais são as quatro seções mínimas de um README que presta?
2Um repositório privado guarda com segurança a senha do banco? Por quê?
3O seu repositório é público e não tem LICENSE. Eu posso usar o código num projeto meu?

respostas: 2 — não; quem tem acesso vê tudo, e o histórico guarda o que você apagou; 3 — não, sem licença é todos os direitos reservados.

// recepção

CONTRIBUTING.md e os vizinhos

meu-projeto/ README.md ← a vitrine LICENSE ← o que pode fazer CONTRIBUTING.md ← como ajudar CODE_OF_CONDUCT.md ← como se comportar SECURITY.md ← como relatar falha .github/ ISSUE_TEMPLATE/ ← aula 05 pull_request_template.md ← aula 06
  • O CONTRIBUTING responde: como rodar os testes, que padrão de commit usar, quanto tempo a resposta demora. Vira link automático na hora de abrir issue ou PR.
  • O código de conduta existe pra ser citado quando precisar. Sem ele escrito, moderar vira briga pessoal.
  • O SECURITY.md diz por onde relatar falha em segredo — segurança é assunto da aula 09.
  • A pasta .github/ é onde moram os templates e os workflows. Nomes reservados: o GitHub lê sozinho.

Repositório de estudo não precisa dos cinco. README e LICENSE já colocam você à frente da maioria.

LAB 2

Licenciar o repositório

~8 min

Este é pela interface — o GitHub escreve o arquivo, você só confere e commita.

Add file → Create new file

Na página do repositório, botão Add file, opção Create new file.

Digite LICENSE no nome do arquivo

Maiúsculas, sem extensão. Assim que você terminar de digitar, aparece um botão Choose a license template à direita.

Escolha MIT e confira ano e nome

O assistente preenche os dois. Leia — é o seu nome que vai ficar ali.

Commite pelo site e traga pra sua máquina

O commit foi feito no GitHub, então o seu clone local ficou pra trás.

git pull
git log --oneline -1
quando terminar

Na caixa About, à direita, deve aparecer MIT license. Se aparecer só o nome do arquivo, o texto foi editado demais e o GitHub não reconheceu a licença.

// o perfil

O seu perfil é um currículo público

Recrutador abre, colega de time abre, a pessoa que você pediu ajuda abre. Ele já está sendo lido — a escolha é se ele está sendo lido bem.

Foto, nome e bio

Uma linha dizendo o que você faz e o que está aprendendo. Foto de pessoa, não o gatinho cinza padrão.

Repositórios fixados

Até seis, na ordem que você quiser. É a sua vitrine — e a única parte do perfil que você controla inteira.

README de perfil

Um texto seu no topo da página, acima de tudo. Explica quem é você antes de qualquer código.

Três repositórios bem descritos batem trinta abandonados. Fixe os que você sabe explicar numa conversa.

// o truque do perfil

O repositório com o seu próprio nome

usuário: nicoly repositório: nicoly # idêntico arquivo: README.md visibilidade: Public # resultado: o README aparece no topo # de github.com/nicoly

O GitHub chama isso de repositório especial. Ao criar um com o nome exato do seu usuário, ele mesmo avisa que você achou o easter egg.

1O nome do repositório tem que ser exatamente igual ao seu usuário, maiúscula por maiúscula.
2Tem que ser público, e o README.md tem que estar na raiz. Privado ou em subpasta: não aparece.
3É Markdown normal. Escreva o que você faz, o que está estudando e como te achar.
4Não precisa de badge piscando nem contador de visitas. Duas linhas honestas funcionam melhor.
// o quadradinho verde

O que o gráfico de contribuições diz

o que ele conta

Commits na branch padrão dos seus repositórios, issues e pull requests que você abriu, e revisões que você fez. Tudo com data — e só isso.

Repositório privado entra como quadrado sem detalhe, se você ligar a opção no perfil.

o que ele não conta

Commit assinado com e-mail que não está na sua conta. Trabalho em GitLab, Bitbucket ou servidor da empresa. Commit em branch que não é a padrão. Pareamento, revisão de corredor, documentação em outro lugar.

E ele nunca disse nada sobre qualidade. Dá pra encher de verde com commit vazio todo dia. Ninguém sério contrata por quadradinho — mas muita gente se culpa por causa dele, e isso é besteira: descanso não aparece no gráfico e nem tem que aparecer.

// organizações

Quando o repositório não é seu

Empresa, coletivo, grupo da faculdade: o dono do repositório não é uma pessoa, é uma organização. Você entra nela como membro.

👤
conta pessoalé você quem entra, com o seu usuário de sempre
→
🏢
organizaçãodona dos repositórios, com faturamento e regras próprias
→
👥
timeum grupo de pessoas; o acesso é dado ao time, não a cada uma
  • Você não cria outra conta pra trabalhar. É o mesmo usuário, com um chapéu a mais.
  • Dar acesso por time é o que mantém a coisa administrável: entrou alguém, põe no time; saiu, tira do time.
  • Times podem ter subtimes, e o subtime herda o acesso do time de cima.
  • Quem é de fora e precisa de acesso pontual entra como colaborador externo — vê aquele repositório, e só.
// permissões

Os cinco níveis, do menor ao maior

nívelo que você consegue fazerquem costuma ter
readVer, clonar, abrir issue e comentar. Não consegue dar push.Todo mundo da empresa, em repositório interno.
triageTudo de read, mais organizar o que os outros abriram: rotular, fechar, reabrir, marcar duplicado. Continua sem push.Quem cuida da fila de issues sem escrever código.
writePush nas branches não protegidas, criar branch, abrir e revisar pull request. É o nível de quem programa.O time de desenvolvimento.
maintainTudo de write, mais cuidar do repositório: descrição, tópicos, releases. Sem apagar nem mexer em quem tem acesso.Quem toca o projeto no dia a dia.
adminTudo. Trocar visibilidade, dar e tirar acesso, proteger a branch, transferir, apagar o repositório.Uma ou duas pessoas. Nunca o time inteiro.

Os cinco níveis são de repositório de organização. Em repositório de conta pessoal existem só duas figuras: o dono e os colaboradores convidados. Proteger a main pra que nem quem tem write faça besteira é a aula 07.
