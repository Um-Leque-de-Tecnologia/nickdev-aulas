Anatomia do GitHub: repositório, perfil e organização

O passo a passo para deixar apresentável aquele repositório que você publicou na aula 03: escrever o README.md, escolher e adicionar a licença, montar o README de perfil e fixar os seus repositórios. Com uma seção de Markdown essencial — que é a língua de tudo aqui e você vai usar em issue e pull request nas próximas aulas.

Antes de começar

01O que você vai fazer aqui

Na aula 03 o seu repositório foi parar no GitHub. Ele funciona: tem commits, tem histórico, tem endereço. E não diz nada para quem chega. Este manual conserta isso.

No fim você vai ter:

  • Um README.md com as quatro seções que importam — o que é, para que serve, como rodar, como contribuir.
  • Um arquivo LICENSE escolhido de propósito, e não por acaso.
  • A caixa About preenchida, com descrição e tópicos.
  • Um README de perfil e até seis repositórios fixados.
  • Markdown na ponta da língua e o vocabulário de permissões de organização.
O que você precisa: o navegador aberto no seu repositório da aula 03, o terminal na pasta dele e uns 50 minutos. Quase tudo aqui acontece na tela do GitHub; o terminal entra só para commitar o README.

Palavras que vão aparecer

visibilidade
Se o repositório é público (qualquer pessoa abre) ou privado (só quem você convidar).
README
O arquivo de texto que o GitHub mostra formatado na primeira tela do repositório.
Markdown
A forma de escrever texto com formatação usando sinais simples — # para título, ** para negrito. Vira HTML sozinho.
licença
O texto que diz o que as outras pessoas podem fazer com o seu código. Sem ela, a resposta padrão da lei é "nada".
organização
Uma conta do GitHub que pertence a um grupo, não a uma pessoa. Empresas e coletivos usam essa.

02A página do repositório, por partes

Antes de mexer, saiba onde está o quê. Abra o seu repositório e acompanhe.

ondeo que é
About (coluna da direita)Descrição em uma linha, link do site e tópicos. É o que o GitHub usa na busca. Clique na engrenagem para editar.
CodeA lista de arquivos, a branch atual, o botão verde de clonar — e, logo abaixo, o README renderizado.
IssuesOnde bug e tarefa são registrados e discutidos. É a aula 05.
Pull requestsOnde uma mudança é proposta e revisada antes de entrar na main. É a aula 06.
ActionsAutomação: testar, construir e publicar sozinho. É a aula 08.
InsightsGráficos de atividade: quem commitou, quando, quanto. Útil para avaliar projeto alheio antes de depender dele.
SettingsVisibilidade, colaboradores, renomear, apagar. Só quem é admin enxerga esta aba — se você não a vê, o seu nível de acesso não é admin.

Preencha o About agora

Leva 40 segundos e quase ninguém faz. Clique na engrenagem ao lado de About e preencha:

  1. Description — uma linha que responda "o que é isso?". Nada de "meu projeto". Exemplo: Página de treino feita durante o curso de GitHub da NickDev.
  2. Website — se o projeto estiver publicado em algum lugar, o endereço vai aqui. Publicar página no GitHub Pages é a aula 10.
  3. Topics — de dois a cinco rótulos em minúsculas, tipo html, css, estudo. São eles que fazem o repositório aparecer em busca por assunto.
Repare: o About é o único lugar do repositório em que o GitHub mostra a licença detectada. Se ela não aparecer ali depois da seção 06, alguma coisa saiu errada no arquivo.

03Público × privado

É uma chave só, em Settings, lá no fim da página, na zona de perigo. Ela decide quem consegue abrir o endereço do seu repositório.

Público

Qualquer pessoa vê, com ou sem conta no GitHub. Aparece na busca, no seu perfil e no Google. Ver não é mexer: gravar, só quem você autorizar. É o que você quer para portfólio, estudo e open source.

Privado

Só você e quem você convidar. Some da busca e do seu perfil para os outros. Grátis e ilimitado em conta pessoal. É o padrão para trabalho de cliente, projeto de faculdade em grupo e coisa ainda pela metade.

O que "privado" não protege

Privado quer dizer "pouca gente vê". Não quer dizer "seguro". As cinco coisas abaixo pegam gente experiente:

  1. Quem tem acesso, vê tudo. Não existe arquivo secreto dentro de um repositório. Deu acesso à pessoa, deu acesso ao repositório inteiro.
  2. O histórico também. Aquela senha que você apagou no commit seguinte continua lá, num commit antigo, a dois cliques de distância — em Insights ou no git log -p.
  3. Remover a pessoa não recolhe a cópia. Quem clonou levou o histórico inteiro para a máquina dela, e você não tem como pedir de volta.
  4. Virar público é irreversível na prática. No instante em que vira, o histórico inteiro fica legível — e alguém pode ter clonado nesse meio-tempo. Voltar para privado depois não desfaz nada.
  5. Segredo mora fora do repositório. Em .env ignorado pelo .gitignore (aula 01) ou nos secrets do GitHub, que é a aula 10.
Se um segredo já entrou no histórico, ele vazou. Não adianta apagar o arquivo e commitar por cima: o valor antigo continua no commit antigo. A ordem é rotacionar a credencial primeiro — gerar uma chave nova e invalidar a velha — e só depois pensar em limpar o histórico. Varredura automática de segredo e o que fazer no dia do vazamento são a aula 09.

Trocar a visibilidade

  1. Repositório → Settings → role até Danger Zone.
  2. Change repository visibility → escolha e confirme digitando o nome do repositório.
  3. Antes de tornar público: rode o comando abaixo e leia o que aparecer. Ele procura no histórico inteiro qualquer arquivo com cara de segredo.
terminal
# todo arquivo que já existiu no histórico, com nome suspeito
git log --all --name-only --pretty=format: | sort -u | grep -Ei '\.env|\.pem|\.key|secret|senha|credential'

Se não voltar nada, siga. Se voltar qualquer linha, não torne público ainda — vá para a aula 09 antes.

04Markdown essencial

Markdown é texto comum com alguns sinais que viram formatação. README, issue, comentário de pull request, descrição de release: no GitHub tudo é escrito assim. Aprender uma vez serve para o curso inteiro.

Títulos

De um a seis #, sempre com um espaço depois. Um # só, uma vez, no topo do arquivo.

### Subseção

05O README que faz alguém usar

Quem abre o seu repositório decide em uns cinco segundos se continua lendo. O README é a única coisa que a maioria das pessoas vai ler — e a estrutura abaixo responde, na ordem, as perguntas que elas fazem.

seçãoa pergunta que responde
Título e uma fraseO que é isso, e para quem?
Para que serveQue problema resolve — e quando não é a ferramenta certa.
Como rodarO que preciso ter instalado e quais comandos eu digito, na ordem.
Como contribuirQuero ajudar: por onde começo?
LicençaEu posso usar isso?

Esqueleto para copiar

Copie inteiro, cole no seu README.md e troque o que está entre colchetes. Apague as seções que não fizerem sentido — é melhor curto e verdadeiro que longo e desatualizado.

README.md
# nome-do-projeto

Uma frase dizendo o que é e para quem serve.

## Para que serve

Dois ou três parágrafos curtos: o problema que isto resolve,
em que situação ajuda e em que situação não é a ferramenta certa.

## Como rodar

Você precisa de: Node 20 ou mais novo, Git.

```bash
git clone https://github.com/usuario/nome-do-projeto.git
cd nome-do-projeto
npm install
npm run dev
```

Abra http://localhost:3000 no navegador.

## Como usar

O exemplo mais curto que já mostra o projeto funcionando.

## Estrutura das pastas

- `src/` — o código
- `docs/` — imagens e documentação
- `tests/` — os testes

## Como contribuir

Sugestões e correções são bem-vindas. Leia o [CONTRIBUTING.md](CONTRIBUTING.md)
antes de abrir um pull request.

## Licença

MIT — veja o arquivo [LICENSE](LICENSE).

As cinco regras que separam um README bom de um ruim

  1. A primeira frase é a mais importante do arquivo. "Projeto da faculdade" não é uma frase. "Calculadora de frete para lojas pequenas, em Python" é.
  2. Como rodar tem que ser copiável. Comandos em bloco, na ordem exata, do jeito que se digita. Nada de "instale as dependências" no lugar do comando.
  3. Diga o que o projeto não faz. Poupa a decepção de quem escolheu errado e ganha respeito de quem escolheu certo.
  4. Escreva para quem não te conhece. Nada de "é só rodar aquele script". Que script? Em qual pasta? Com qual versão?
  5. Mantenha atualizado ou apague. Instrução que não funciona mais é pior que instrução nenhuma: faz a pessoa perder meia hora antes de desistir.

Faça agora, no seu repositório

terminal
# na pasta do repositório da aula 03
git status
git add README.md
git commit -m "docs: README com o que é, como rodar e licença"
git push
$ git push To github.com:usuario/meu-primeiro-repo.git a1c9f0e..3f7b2d1 main -> main

Atualize a página do repositório no navegador. O README tem que aparecer formatado, com título grande e bloco de código em fundo escuro. Se apareceu o texto cru com os # à mostra, o arquivo não se chama README.md — provavelmente ficou readme.txt.

Repare: o GitHub aceita README.md na raiz, e também um dentro de .github/ ou docs/. Na raiz é o padrão e é o que todo mundo espera. Um README dentro de qualquer subpasta aparece quando alguém abre aquela pasta — bom para explicar src/ por dentro.

06Escolher e adicionar a licença

Licença é o texto que diz o que os outros podem fazer com o seu código. Você não precisa entender de direito autoral para escolher: três respostas cobrem quase tudo que se publica.

licençaem uma fraseescolha quando
MITFaça o que quiser, inclusive vender e fechar o código, desde que mantenha o aviso de autoria. Sem garantia nenhuma.É o seu padrão. Curta, conhecidíssima, aceita em qualquer lugar.
Apache 2.0O mesmo que a MIT e mais: concede o uso das patentes de quem contribuiu e pede que arquivos modificados sejam sinalizados.Projeto que empresa vai adotar — o jurídico delas gosta da cláusula de patente.
GPL v3Copyleft: pode usar, estudar e modificar, mas quem distribuir uma obra derivada tem que abrir o código dela sob a mesma licença.Você quer garantir que melhorias feitas em cima do seu trabalho voltem para a comunidade.
nenhumaTodos os direitos reservados. Ninguém pode usar, copiar ou modificar — nem que o repositório seja público.Nunca de propósito. É o que acontece quando você esquece.

Sem licença nenhuma é o pior caso

Código sem licença já nasce protegido por direito autoral, sem você fazer nada. Público não quer dizer livre: qualquer pessoa pode ler o seu código e, tecnicamente, não pode usar. Ao publicar no GitHub você aceitou os termos que permitem que outras pessoas vejam e façam fork dentro do próprio GitHub — e é só até aí que vai.

Efeito prático: o seu portfólio sem LICENSE diz, sem querer, "olhe mas não use". E empresa séria não encosta em repositório sem licença, porque é risco jurídico de graça. Se você publicou para ser útil, escolher a licença é parte de publicar.

Adicionar pelo site — o jeito certo

Faça por aqui, não escreva o texto na mão. O GitHub só reconhece a licença se o texto for o oficial.

  1. Add file → Create new file, na página do repositório.
  2. Digite LICENSE no nome do arquivo. Maiúsculas, sem extensão. Assim que você terminar de digitar, aparece o botão Choose a license template à direita.
  3. Escolha a licença na lista da esquerda e clique em Review and submit.
  4. Confira o ano e o seu nome nas duas linhas que o assistente preencheu. Mude só isso — nada mais.
  5. Commit changes. O commit é feito no GitHub, então o seu clone local ficou uma versão atrás.
terminal
# trazer o commit que o site fez
git pull
git log --oneline -1
$ git pull Updating a1c9f0e..3f7b2d1 Fast-forward LICENSE | 21 +++++++++++++++++++++ 1 file changed, 21 insertions(+)

Volte à página do repositório: na caixa About, à direita, agora aparece MIT license. Se aparecer apenas o nome do arquivo, o texto foi alterado demais e o GitHub não reconheceu a licença — refaça pelo assistente.

Cuidado: código que você escreveu no trabalho costuma pertencer à empresa por contrato. Não publique trabalho da empresa por conta própria, nem como portfólio — pergunte antes. E não invente licença própria: ninguém vai ler, e na dúvida ninguém usa.

O perfil

08O README de perfil

Existe um repositório especial: se ele tiver o nome exato do seu usuário, o README dele aparece no topo do seu perfil, acima de tudo. É o texto que apresenta você antes de qualquer código.

usuário: nicoly repositório: nicoly # idêntico, letra por letra arquivo: README.md # na raiz visibilidade: Public # resultado: o README aparece em github.com/nicoly

Criar

  1. New repository, no canto superior direito do GitHub.
  2. Repository name: digite o seu nome de usuário. O próprio GitHub avisa que você achou um repositório especial e mostra um recado com estrelinha.
  3. Marque Public e marque Add a README file.
  4. Create repository e depois edite o README.md ali mesmo, pelo lápis.

Esqueleto para copiar

README.md
### Oi, eu sou a Nicoly

Estudo desenvolvimento web e escrevo sobre o que aprendo.

#### No que estou mexendo agora

- Curso de Git e GitHub na NickDev
- Um site pessoal em HTML e CSS

#### Onde me achar

- [LinkedIn](https://exemplo.com)
- Escreva para: voce@exemplo.com
o que costuma dar erradopor quê
Não aparece nada no perfilO nome do repositório não é idêntico ao usuário — o GitHub diferencia maiúscula de minúscula aqui.
Continua não aparecendoO repositório está privado, ou o README.md não está na raiz.
Aparece o texto cruO arquivo não tem a extensão .md.
Repare: não precisa de badge piscando, contador de visitas nem troféu animado. Duas linhas honestas e um jeito de te achar funcionam melhor — e continuam funcionando daqui a dois anos.

09Repositórios fixados e o gráfico de contribuições

O perfil tem duas partes que as pessoas realmente olham: os repositórios que você escolheu mostrar e o quadro de quadradinhos verdes.

Fixar até seis repositórios

  1. Abra o seu perfil, aba Overview.
  2. Clique em Customize your pins, à direita da lista.
  3. Marque até seis repositórios e salve. A ordem que aparece é a ordem em que você marcou.
  4. Confira o texto de cada um: o que aparece no cartão é a descrição do About. Repositório fixado sem descrição é vitrine com etiqueta em branco.
Três repositórios bem descritos batem trinta abandonados. Fixe os que você consegue explicar numa conversa de cinco minutos. O resto pode ficar na lista geral sem problema nenhum.

O gráfico de contribuições

O que ele conta

  • Commits na branch padrão dos seus repositórios.
  • Issues e pull requests que você abriu.
  • Revisões de pull request que você fez.
  • Trabalho em repositório privado, como quadrado sem detalhe, se você ligar a opção nas configurações do perfil.

O que ele não conta

  • Commit assinado com um e-mail que não está na sua conta do GitHub.
  • Trabalho em GitLab, Bitbucket ou servidor da empresa.
  • Commit em branch que não é a padrão do repositório.
  • Pareamento, revisão de corredor, documentação em outro lugar, estudo, descanso.

O caso mais comum de "eu commitei e não ficou verde" é o e-mail. Confira e conserte:

terminal
# qual e-mail está assinando os seus commits
git config --global user.email

# qual e-mail está no último commit deste repositório
git log -1 --format='%an <%ae>'

Esse e-mail precisa estar cadastrado na sua conta do GitHub, em Settings → Emails. Pode ser um e-mail secundário; só precisa estar lá e verificado.

E o gráfico nunca disse nada sobre qualidade. Dá para encher de verde com commit vazio todo dia, e dá para passar uma semana inteira resolvendo um problema difícil sem pintar nada. Ninguém sério contrata por quadradinho — mas muita gente se culpa por causa dele, e isso é besteira: descanso não aparece no gráfico e nem tem que aparecer.
Trabalhar em grupo

10Organizações, times e permissões

Cedo ou tarde você entra numa organização — empresa, coletivo, grupo da faculdade. Dali em diante o repositório não é seu, e o que você consegue fazer depende do nível de acesso que te deram.

Quem é quem

conta pessoal
Você. Não se cria outra conta para trabalhar — é o mesmo usuário, com um chapéu a mais.
organização
Uma conta que pertence a um grupo. É ela a dona dos repositórios, com faturamento e regras próprias.
membro
Quem faz parte da organização. Recebe um acesso básico a todos os repositórios dela, definido pelo dono.
time
Um grupo de pessoas dentro da organização. O acesso é dado ao time, não a cada pessoa. Times podem ter subtimes, e o subtime herda o acesso do time acima.
colaborador externo
Alguém de fora com acesso a um repositório específico. Não vê o resto da organização.
owner
Dono da organização. Manda em tudo, inclusive em apagar. São poucas pessoas, sempre.

Os cinco níveis de permissão

Do menor para o maior. Cada um inclui tudo do anterior.

nívelo que consegue fazero que não conseguequem costuma ter
read Ver e clonar o repositório, abrir issue, comentar, abrir pull request a partir de um fork. Dar push. Fechar issue dos outros. Todo mundo da empresa, em repositório interno.
triage Organizar o que os outros abriram: rotular, atribuir responsável, fechar, reabrir, marcar duplicado. Dar push. Continua sem escrever código. Quem cuida da fila de issues sem programar.
write Push nas branches não protegidas, criar branch, abrir e revisar pull request, aprovar. É o nível de quem programa. Mexer nas configurações do repositório. O time de desenvolvimento.
maintain Cuidar do repositório no dia a dia: descrição, tópicos, releases, arquivar issues. Apagar o repositório, trocar a visibilidade, mexer em quem tem acesso. Quem toca o projeto de perto.
admin Tudo: trocar visibilidade, dar e tirar acesso, proteger a branch, transferir, apagar o repositório. — Uma ou duas pessoas. Nunca o time inteiro.
Repare: os cinco níveis existem em repositório de organização. Em repositório de conta pessoal há só duas figuras: o dono e os colaboradores convidados, que na prática têm acesso de escrita. Se você está seguindo este manual no seu repositório pessoal, é por isso que não encontra a lista de cinco.

Como descobrir o seu nível

  1. Enxerga a aba Settings do repositório? Então você é admin ali.
  2. Consegue dar push direto numa branch nova? Então tem pelo menos write.
  3. Consegue fechar a issue de outra pessoa, mas não dar push? É triage.
  4. Só consegue comentar? É read — e é isso que você pede para mudar quando precisar.
Ao pedir acesso, diga três coisas: em qual repositório, qual nível e por quê. "Preciso de write no api-pagamentos para abrir a branch da tarefa 214" é um pedido que se resolve em um minuto. "Me dá acesso" gera três mensagens de ida e volta.
O que fica para as próximas: impedir que quem tem write faça besteira direto na main — isso é branch protection, na aula 07. Escolher quem é chamado para revisar cada pasta, com CODEOWNERS, é a aula 06. E contribuir com repositório de organização em que você não tem acesso nenhum, via fork, é a aula 12.

licenças

licençaem uma frase
MITUse como quiser, mantendo o aviso de autoria. O padrão.
Apache 2.0MIT mais concessão de patente e aviso de mudanças.
GPL v3Derivado distribuído tem que abrir o código, na mesma licença.
nenhumaTodos os direitos reservados. Ninguém pode usar.

permissões de repositório em organização

nívelem uma frase
readVê, clona, comenta.
triageOrganiza issue e pull request dos outros. Sem push.
writeDá push e revisa. O nível de quem programa.
maintainCuida do repositório, sem mexer em acesso nem apagar.
adminTudo, inclusive apagar.

12Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
O README aparece como texto cru, com os # à mostra O arquivo não tem a extensão .md. Renomeie para README.md e commite. Só .md é renderizado.
O README saiu tudo grudado numa linha só Faltou linha em branco entre os parágrafos. Uma linha vazia separando cada bloco. Confira na aba Preview antes de commitar.
A lista não virou lista Faltou espaço depois do -, ou faltou linha em branco antes do primeiro item. - item, com espaço. E uma linha vazia acima da lista.
O bloco de código saiu sem cor Faltou o nome da linguagem depois das três crases. Escreva bash, js, python logo após as crases de abertura.
A imagem não aparece O caminho está errado, ou o arquivo não foi commitado junto. Use caminho relativo a partir da raiz e confira com git status se a imagem entrou no commit.
O About não mostra a licença O texto do LICENSE foi editado, ou o arquivo tem outro nome. Refaça pelo assistente Choose a license template e mude só o ano e o nome.
O README de perfil não aparece O repositório não tem o nome exato do usuário, está privado, ou o arquivo não está na raiz. Confira as três coisas, nessa ordem. O nome diferencia maiúscula de minúscula.
Commitei, mas o quadradinho não ficou verde O e-mail do commit não está cadastrado na sua conta — ou o commit foi em branch que não é a padrão. git log -1 --format='%ae' e compare com Settings → Emails no GitHub.
Fiz git pull depois de commitar pelo site e deu conflito Você mexeu no mesmo arquivo nos dois lugares. Resolva o conflito como na aula 02. Para evitar: git pull antes de editar local.
Não vejo a aba Settings do repositório Você não é admin ali. Peça a um owner da organização. Diga qual repositório e qual nível você precisa.
Entrei na organização e não consigo dar push O seu nível é read ou triage. Peça write. Se a branch for protegida, nem write dá push direto — isso é a aula 07.
Commitei o .env e o repositório é público O .gitignore veio depois do git add .. Rotacione a chave agora. Depois git rm --cached .env e commite. Limpar histórico é a aula 09.
Tirei a pessoa do repositório privado, mas ela tem o código O clone que ela fez continua na máquina dela, com o histórico inteiro. Não há como recolher. Trate como vazado o que era sensível e troque as credenciais.
Quero renomear o repositório e tenho medo de quebrar Nenhum: o GitHub redireciona o endereço antigo. Renomeie em Settings e depois rode git remote set-url origin … no seu clone.
Antes de pedir ajuda: mande o link do repositório e diga o que você esperava ver. Metade dos problemas desta aula se resolve em dez segundos quando outra pessoa abre a página — porque quase tudo aqui é visível.
