git reflog

Desfazendo: reflog, revert, reset e amigos

Hoje a gente quebra o repositório de propósito — várias vezes — e traz tudo de volta. No fim da aula você não tem mais medo de digitar comando no Git.

deixe aberto: o terminal, dentro de um repositório de teste. tudo que a gente faz hoje é destrutivo de mentirinha — não use o repositório do trabalho.

// o problema

O medo trava mais gente que o erro

$ git status # 14 arquivos modificados # 3 commits que não deviam existir # uma senha no meio deles $ _ (a pessoa olha por 20 minutos e não digita nada)

É sempre a mesma cena. A pessoa sabe que errou, sabe mais ou menos o que quer — e não digita, porque acha que o próximo comando é o que apaga tudo.

1"Se eu rodar isso, perco o meu trabalho?"
2"Se eu rodar isso, estrago o repositório dos outros?"
3Aí vem a saída mais cara de todas: apagar a pasta e clonar de novo — jogando fora tudo que ainda não subiu.
4Ou pior: deixar o erro lá, commitado, porque mexer dá medo.

A verdade que ninguém conta: depois que você faz um commit, o Git é uma das ferramentas mais difíceis do mundo de se perder coisa. Ele quase não apaga — ele desencosta.

// o conceito

Onde a sua mudança pode estar

Todo comando de desfazer responde à mesma pergunta: em qual dos três lugares está o que você quer mudar? Escolher o comando errado é quase sempre ter errado o lugar.

🧰

Da esquerda para a direita, a coisa fica mais segura. Mudança que nunca foi commitada é a única que some de verdade. Por isso a regra do dia: na dúvida, commite antes de experimentar. Commit é barato, e a gente conserta o histórico depois.

sintoma 01 · "estraguei o arquivo e quero ele como estava"

Nem commitei ainda: restore

Dois comandos, dois lugares diferentes. A palavra --staged é o que decide qual dos dois.

tirar a mudança do arquivo

git restore estilo.css

Volta o arquivo ao estado do último commit. A sua edição vai embora e não existe reflog para ela — ela nunca foi um commit.

tirar o arquivo da bancada

git restore --staged estilo.css

Desfaz só o git add. A sua edição continua lá, intacta, apenas fora do commit que você está montando.

Leia sempre a saída do git status. Ele imprime esses dois comandos, em texto, logo abaixo de cada grupo de arquivos. O Git literalmente te diz o que digitar.

lab 01 · 6 minutos · em dupla
LAB 01restore × restore --staged

Desfaça as duas metades

Bagunce dois arquivos

Edite a.txt e b.txt num repositório de teste. Rode git status e leia a saída com atenção.

Coloque só um na bancada

git add a.txt. Rode git status de novo — agora são dois grupos, e cada grupo sugere um comando diferente.

Tire o a.txt da bancada

git restore --staged a.txt. Confira que a sua edição continua no arquivo — abra ele.

Jogue fora a edição do b.txt

git restore b.txt. Abra o arquivo. A edição sumiu, e sumiu de verdade.

sintoma 02 · "a mensagem está errada" / "esqueci um arquivo"

O commit recém-feito: --amend

O --amend não edita o commit. Ele faz um commit novo no lugar do anterior — hash novo, conteúdo corrigido — e desencosta o velho.

# só a mensagem estava errada $ git commit --amend -m "fix: corrige o cálculo do frete" # esqueceu um arquivo no commit? adicione e emende $ git add teste-frete.js $ git commit --amend --no-edit [main a9f3c21] fix: corrige o cálculo do frete 2 files changed, 18 insertions(+)

--no-edit quer dizer "mantenha a mensagem que já estava lá". Sem ele, o Git abre o editor pra você reescrever.

⚠ Só antes do push. O hash muda. Se o commit antigo já está no remoto, quem deu pull tem uma versão que você acabou de dizer que não existe — e o seu próximo push volta rejeitado com non-fast-forward (aula 03).

// a decisão mais importante da aula

revert × reset

Os dois "desfazem um commit". Mas fazem coisas opostas com a história — e é isso, não o efeito no código, que decide qual você pode usar.

revert

escreve uma errata

Cria um commit novo que desfaz o que o commit antigo fez. O antigo continua no histórico, visível, com a errata logo abaixo.

git revert 4f2a91c

Seguro em qualquer branch. Ninguém precisa fazer nada do outro lado.

reset

arranca a página

Move o ponteiro da branch para trás. Os commits somem da sua branch — como se nunca tivessem sido escritos.

git reset --hard HEAD~1

Só na sua branch local, que ninguém mais tem. Nunca na compartilhada.

A analogia: num diário já publicado você não passa corretivo na página — todo mundo tem a cópia impressa. Você escreve uma errata na página seguinte. No rascunho em casa, arrancar a página é o certo, porque ninguém mais leu.

// o comando com três personalidades

--soft, --mixed, --hard

Os três movem a branch para trás igualzinho. A diferença é o que acontece com o trabalho que estava nos commits removidos.

opçãohistóricobancadaseus arquivosquando usar
--softvoltamantém, montadointactosJuntar 3 commits em 1: volta e commita de novo.
--mixed (padrão)voltaesvaziaintactosRefazer os commits do zero, com outra divisão.
--hardvoltaesvaziasobrescritosJogar fora mesmo. É o único que apaga arquivo.

⚠ O --hard é o único comando desta aula que destrói trabalho não commitado. Commit removido você recupera pelo reflog. Edição que nunca virou commit, não. Antes de um --hard: git stash -u ou um commit "wip".

parada obrigatória

Você está na main, e o commit já foi pro GitHub. Anular com revert ou com reset?

Diga em voz alta a resposta e o motivo. O motivo vale mais que a resposta — é ele que você vai lembrar daqui a seis meses.

Anule um commit sem apagar nada

Cometa o erro

Crie bug.txt com qualquer besteira dentro e commite: git commit -m "feat: recurso que vai dar errado".

Faça mais um commit por cima

Qualquer coisa. Isso importa: o commit ruim não pode ser o último, senão o exercício fica fácil demais.

Pegue o hash do commit ruim

git log --oneline. Copie os 7 primeiros caracteres — basta isso.

Confira as duas coisas

sintoma 03 · "estou no meio de uma coisa e preciso trocar de branch"

O trabalho pela metade: stash

A gaveta. Você guarda a bagunça, a pasta fica limpa, você resolve o urgente e depois traz a bagunça de volta — exatamente como estava.

$ git stash push -m "meio do formulário de login" Saved working directory and index state On main: meio do formulário de login $ git switch hotfix # a pasta está limpa, dá pra trocar $ git switch main $ git stash list stash@{0}: On main: meio do formulário de login $ git stash pop # traz de volta E apaga da gaveta $ git stash apply # traz de volta E mantém na gaveta

Sempre com -m e uma frase. Um stash list com seis entradas anônimas de duas semanas atrás é lixo — ninguém lembra o que era, e ninguém tem coragem de apagar.

⚠ O stash ignora arquivo novo que o Git ainda não rastreia. Se o seu trabalho inclui arquivo recém-criado, use git stash -u — senão ele fica para trás e você troca de branch achando que guardou tudo.

sintoma 04 · "commitei na branch errada"

Levar um commit de lá pra cá: cherry-pick

O clássico: você commitou na main o que era pra estar numa branch. Conserto em dois tempos — copiar para o lugar certo, depois remover do lugar errado.

# 1. anote o hash do commit que está no lugar errado $ git log --oneline -1 7c1e0aa feat: filtro de busca na listagem # 2. vá para a branch certa e traga só aquele commit $ git switch -c feat/filtro-busca $ git cherry-pick 7c1e0aa [feat/filtro-busca 2b8d5f3] feat: filtro de busca na listagem # 3. volte e apague o commit da main LOCAL $ git switch main $ git reset --hard HEAD~1

O cherry-pick copia, não move: o commit ganha um hash novo no destino, e o original continua onde estava até você removê-lo.

⚠ O passo 3 só vale se você ainda não deu push. Se a main já subiu com esse commit, o passo 3 vira git revert 7c1e0aa — nunca o reset.

sintoma 05 · "commitei uma senha"

O caso que não é só técnico

Se ainda NÃO deu push

# era o último commit? git rm --cached .env git commit --amend --no-edit # estava alguns commits atrás? git reset --soft HEAD~3 # tire o segredo e commite de novo

Ponha o arquivo no .gitignore no mesmo commit (aula 01), senão ele volta amanhã.

Se JÁ deu push

1Rotacione a chave agora. Antes de qualquer comando de Git. Ela está no histórico, nos forks, nos caches e nos scanners que varrem o GitHub o dia inteiro.
2Só depois limpe o histórico — e isso é reescrever o repositório inteiro, com todo mundo tendo que clonar de novo.
3O procedimento completo, com secret scanning e o que comunicar ao time, é a aula 09. Aqui a gente viu só a parte mecânica do Git.

⚠ Apagar o arquivo num commit novo não resolve nada. O valor continua no commit antigo, e o commit antigo continua lá. Trocar a chave é o único passo que realmente fecha a porta.

sintoma 06 · "meus 9 commits são um vexame"

Limpar a série antes da revisão: rebase -i

Ninguém precisa ver os seus wip, agora vai e ops. Antes de abrir o PR (aula 06), você reescreve a sua própria série numa coisa legível.

o editor que abre com git rebase -i HEAD~4
pick a1b2c3d feat: adiciona o formulário de contato reword e4f5g6h fet: valdiação do email ← corrigir a mensagem squash i7j8k9l wip ← funde no de cima drop m0n1o2p console.log de teste ← some com ele
pick
Mantém o commit como está. É o padrão de todas as linhas.
reword
Mantém o conteúdo, abre o editor pra você corrigir só a mensagem.
squash
Funde este commit no da linha de cima. É assim que 9 commits viram 2.
drop
Descarta o commit inteiro. (Apagar a linha faz a mesma coisa.)

⚠ Rebase reescreve tudo que ele toca. Só na sua branch, e só antes de outra pessoa ter baixado. Se você já tinha empurrado a branch e é a única pessoa nela, o push seguinte precisa de --force-with-lease — que, ao contrário do --force, aborta se alguém tiver mandado algo que você não viu.

sintoma 07 · "funcionava mês passado, agora não funciona"

Achar o commit culpado: bisect

Busca binária no histórico. Com 200 commits suspeitos, o Git acha o culpado em 8 testes — e você só responde "funciona" ou "não funciona".

$ git bisect start $ git bisect bad # o commit de agora está quebrado $ git bisect good v1.4.0 # nesta tag funcionava Bisecting: 97 revisions left to test after this (roughly 7 steps) # o Git te joga num commit do meio. teste e responda: $ git bisect good # ou: git bisect bad Bisecting: 48 revisions left to test after this (roughly 6 steps) # ... seis respostas depois ... b3f9a1d is the first bad commit $ git bisect reset # SEMPRE. volta pra onde você estava

Esqueceu o reset no fim? Você fica preso num commit velho, em detached HEAD, achando que o projeto inteiro voltou no tempo. Não voltou — é só o bisect ainda aberto.

sintoma 08 · "achei que tinha perdido"

A rede de segurança: reflog

O git log mostra a história que a branch conta hoje. O git reflog mostra tudo por onde o seu HEAD passou — inclusive o que o reset "apagou".

$ git reflog a1f9c02 HEAD@{0}: reset: moving to HEAD~3 9d3e7bb HEAD@{1}: commit: feat: exportar relatório em CSV 4c81a90 HEAD@{2}: commit: feat: filtro por período 77b2d15 HEAD@{3}: commit: refatora o serviço de relatório a1f9c02 HEAD@{4}: commit: chore: sobe a versão # os três commits "apagados" estão ali. traga a branch de volta: $ git reset --hard 9d3e7bb HEAD is now at 9d3e7bb feat: exportar relatório em CSV

Todo commit que existiu na sua máquina passa por aqui e fica por volta de 90 dias. Reset, rebase, amend, merge desastrado, branch deletada — tudo deixa rastro. É por isso que "commite antes de experimentar" é o melhor conselho da aula.

O reflog é seu, local e intransferível. Não vai pro GitHub e não vem no clone. O reflog do colega não te salva.

LAB 03destruir e ressuscitar

Apague três commits e traga de volta

Faça três commits bobos

Três arquivos, três commits. Rode git log --oneline e olhe a saída — mas não copie os hashes. Vale a honra.

Destrua

git reset --hard HEAD~3. Rode git log --oneline e ls. Sumiu tudo. Sinta o frio na barriga — é o ponto do exercício.

Olhe onde ninguém olha

git reflog. Ache a linha do seu último commit bom, a de antes do reset. Copie o hash dela.

Ressuscite

git reset --hard <aquele hash>. Rode git log --oneline e ls: os três commits e os três arquivos estão de volta.

já foi pro remoto

Só revert

Qualquer coisa que troque hash quebra o repositório de quem já baixou. O revert resolve o mesmo problema sem apagar nada de ninguém — e é exatamente por isso que ele existe.

Três coisas que não são desta aula: conflito de merge (aula 02), segredo vazado como incidente de segurança (aula 09 — aqui foi só a mecânica) e voltar uma versão em produção (aula 10 — lá o assunto é deploy, não histórico).
