Desfazendo: reflog, revert, reset e amigos

O manual que você abre na hora do desespero. Comece pela tabela de emergência, ache o seu sintoma, pule direto para a seção. Cada comando vem com o que se espera ver na saída e com o aviso de quando ele é perigoso.

Comece por aqui

01Tabela de emergência

Você está aqui porque alguma coisa deu errado. Ache a linha que descreve o seu sintoma, veja o comando e clique no link para a seção com o passo a passo. Esta tabela também é a cola da aula — guarde o link.

A única regra que você precisa decorar: se o commit já foi para o remoto, o único comando aceitável é revert. Tudo que troca hash — amend, reset, rebase — só vale enquanto a coisa não saiu da sua máquina.

02Os três lugares onde a sua mudança pode estar

Escolher o comando errado é quase sempre ter errado o lugar. Antes de digitar qualquer coisa, descubra onde está o que você quer mexer.

diretório
O arquivo como está aberto no editor. Mudança viva, que o Git ainda não guardou em lugar nenhum.
bancada (staging)
O que você já colocou com git add. Está montado, mas o commit não fechou.
histórico
Os commits. Cada um tem hash, autor e data — e, uma vez criado, é praticamente indestrutível por 90 dias, mesmo que a branch deixe de apontar para ele.

Rode isto para ver os três de uma vez:

git status              # diretório e bancada, em dois grupos
git diff                # o que mudou e NÃO está na bancada
git diff --staged       # o que já está na bancada
git log --oneline -5    # o histórico recente
A regra do dia: na dúvida, commite antes de experimentar. Commit é barato e o histórico a gente conserta depois. Mudança que nunca virou commit é a única coisa que o Git realmente deixa você perder.
O que o reflog não salva: arquivo nunca commitado. Se você editou e não commitou, um git restore ou um git reset --hard apagam para sempre. Não existe undo para isso — nem no Git, nem em lugar nenhum.
Ainda não commitei

03Desfazer no arquivo e na bancada

Dois comandos parecidíssimos que fazem coisas bem diferentes. A palavra --staged é o que decide.

Tirar da bancada, mantendo a edição

Você deu git add em coisa demais e quer só desmontar o commit — sem perder o que escreveu.

git restore --staged estilo.css

Confira com git status. O arquivo sai de Changes to be committed e volta para Changes not staged for commit. A sua edição continua no arquivo.

Jogar fora a edição do arquivo

Você mexeu, não gostou e quer o arquivo como estava no último commit.

git restore estilo.css      # um arquivo
git restore .               # TODOS os arquivos modificados
Perigoso — e por quê: git restore arquivo sobrescreve o arquivo no disco com a versão do último commit. Aquela edição nunca foi um commit, então não existe reflog para ela. Some e acabou. Antes de rodar em cima de várias horas de trabalho, prefira git stash -u: é reversível.

Os dois de uma vez, quando você quer desfazer tudo

git restore --staged --worktree .

Tira tudo da bancada e devolve todos os arquivos ao estado do último commit. É o "cancelar tudo desde o último commit".

Atalho que o Git te dá de graça: rode git status e leia. Ele imprime exatamente esses comandos, em texto, embaixo de cada grupo de arquivos. Você quase nunca precisa lembrar de cabeça.

04Guardar o trabalho pela metade

Cena de todo dia: você está no meio de um formulário e chega um bug urgente. Trocar de branch com a pasta suja dá erro ou carrega a bagunça junto. O stash é a gaveta.

# guarda tudo (inclusive arquivo novo) e limpa a pasta
git stash push -u -m "meio do formulário de login"

# resolve o urgente
git switch hotfix
# ... conserta, commita, volta ...
git switch main

# traz de volta
git stash list
git stash pop

O que se espera ver:

$ git stash push -u -m "meio do formulário de login" Saved working directory and index state On main: meio do formulário de login $ git stash list stash@{0}: On main: meio do formulário de login $ git stash pop Dropped refs/stash@{0} (b71e0c4d5f2a9e3c8a11d7f4c2e5b8a0d3f6c9e1)
comandoo que faz
git stash popTraz de volta e remove da gaveta. É o normal.
git stash applyTraz de volta e mantém na gaveta. Use quando quiser aplicar em duas branches.
git stash listLista o que está guardado.
git stash show -p stash@{0}Mostra o diff de uma entrada, antes de aplicar.
git stash drop stash@{0}Descarta uma entrada.
git stash clearEsvazia a gaveta inteira. Sem confirmação.
Perigoso — e por quê: git stash clear apaga todas as entradas de uma vez, sem perguntar. E git stash sem -u ignora arquivo que o Git ainda não rastreia — você troca de branch achando que guardou tudo, e o arquivo novo fica para trás, aparecendo na outra branch como se fosse dela. Use sempre -u.
Sempre com -m e uma frase. Um stash list com seis entradas anônimas de duas semanas atrás é lixo: ninguém lembra o que era e ninguém tem coragem de apagar.
Já commitei

05Corrigir o último commit

O erro mais comum do mundo: você aperta enter e vê o erro de digitação na mensagem — ou percebe que esqueceu um arquivo.

Só a mensagem estava errada

git commit --amend -m "fix: corrige o cálculo do frete"

Esqueceu um arquivo

git add teste-frete.js
git commit --amend --no-edit

--no-edit quer dizer "mantenha a mensagem que já estava lá". Sem ele, o Git abre o editor. O que se espera ver:

$ git commit --amend --no-edit [main a9f3c21] fix: corrige o cálculo do frete Date: Mon Sep 1 14:22:10 2025 -0300 2 files changed, 18 insertions(+), 3 deletions(-)

Repare no hash: a9f3c21. Ele é diferente do hash que o commit tinha antes. O --amend não edita nada: ele cria um commit novo e desencosta o antigo.

Perigoso — e por quê: o --amend reescreve história. Se o commit antigo já subiu para o remoto, quem deu pull tem na máquina um commit que você acabou de dizer que não existe. O seu próximo push volta com ! [rejected] non-fast-forward (aula 03). Só use --amend antes do push.
Se já tinha subido e você é a única pessoa na branch: git push --force-with-lease. Ao contrário do --force, ele aborta se alguém tiver mandado algo que você ainda não viu — o que salva você de sobrescrever o trabalho do outro. Na main ou em branch compartilhada, nem isso: use revert.

06Anular um commit com revert

O revert não apaga o commit ruim. Ele escreve uma errata: um commit novo, logo abaixo, que desfaz exatamente o que o outro fez. Os dois ficam no histórico.

# 1. ache o hash do commit que você quer anular
git log --oneline

# 2. reverta (o editor abre com a mensagem pronta: salve e feche)
git revert 4f2a91c

# sem abrir o editor, aceitando a mensagem padrão
git revert --no-edit 4f2a91c

O que se espera ver:

$ git log --oneline e8c30d2 (HEAD -> main) Revert "feat: recurso que deu errado" 1a77b93 chore: ajusta o README 4f2a91c feat: recurso que deu errado b02de41 feat: listagem de produtos

Um commit a mais, não a menos. O 4f2a91c continua ali, e é isso que torna o revert seguro: quem já baixou aquele commit não precisa fazer nada — no próximo pull ele recebe a errata e pronto.

Reverter vários commits de uma vez

# os três últimos, cada um vira um commit de revert
git revert --no-edit HEAD~3..HEAD

# os três últimos, tudo num commit de revert só
git revert --no-commit HEAD~3..HEAD
git commit -m "revert: desfaz a série do filtro de busca"
Este é o comando que você usa em branch compartilhada. Na main, em branch protegida, em qualquer coisa que outra pessoa já tenha baixado: revert, sempre. Ele é o único que resolve o problema sem exigir nada de ninguém.
Um caso chato: reverter um commit de merge exige dizer qual lado manter (git revert -m 1 <hash>) e deixa o Git achando que aquele ramo já foi integrado — mesclar de novo depois não traz nada de volta. Se der para escolher, reverta os commits individuais em vez do merge.
Não confunda com rollback de produção. Reverter um commit conserta o histórico do código; tirar uma versão quebrada do ar é outro assunto, com tag e workflow de deploy, e é a aula 10.

07Apagar commits locais com reset

O reset move o ponteiro da sua branch para trás. Os commits que ficaram para frente somem da branch — mas continuam no repositório, alcançáveis pelo reflog. As três opções movem a branch igual; a diferença é o que acontece com o trabalho.

opçãohistóricobancadaseus arquivospara quê
--softvoltamantém, montadointactosJuntar vários commits em um: volta e commita de novo.
--mixed (padrão)voltaesvaziaintactosRefazer os commits do zero, escolhendo outra divisão.
--hardvoltaesvaziasobrescritosJogar fora mesmo. É o único que apaga arquivo.

Juntar os três últimos commits em um

git reset --soft HEAD~3
git status                # tudo já está na bancada, montado
git commit -m "feat: exportação de relatório em CSV"

Tirar os commits e recomeçar a divisão

git reset HEAD~3          # --mixed é o padrão
git status                # arquivos modificados, bancada vazia
git add -p                # escolha pedaço por pedaço

Jogar fora tudo mesmo

git stash -u              # ← rede de segurança, faça isto antes
git reset --hard HEAD~3
$ git reset --hard HEAD~3 HEAD is now at b02de41 feat: listagem de produtos
Perigoso — e por quê (duas coisas separadas):
1. --hard é o único comando desta aula que sobrescreve arquivo no disco. Commit removido você recupera pelo reflog; edição que nunca virou commit, não. Por isso o git stash -u antes.
2. reset reescreve história. Se os commits que você está removendo já foram para o remoto, a sua branch fica atrás da remota e o próximo push só passa com --force — que apaga da máquina de todo mundo commits que eles já baixaram. Em branch compartilhada, não é reset: é revert.
Reset de um arquivo só não existe com esse nome. Para desfazer o add de um arquivo, o comando moderno é git restore --staged arquivo (seção 03). O git reset arquivo antigo faz a mesma coisa e continua funcionando.
Situações clássicas

08Commitei na branch errada

Você estava distraído, commitou na main o que era para estar numa branch de feature. O conserto tem dois tempos: copiar para o lugar certo e depois remover do lugar errado.

  1. Anote o hash
    Ainda na branch errada, rode git log --oneline -3 e copie os 7 primeiros caracteres do commit (ou dos commits) que você quer mover.
  2. Crie a branch certa a partir daqui
    Ela nasce já com o commit dentro, então o passo 3 fica opcional. Se a branch já existir, pule para o cherry-pick.
  3. Copie o commit para lá
    O cherry-pick copia — o commit ganha um hash novo no destino e o original continua onde estava.
  4. Remova da branch errada
    Aqui entra o reset --hard, e é o passo onde você precisa saber se já deu push.
# 1. qual é o commit fora do lugar
git log --oneline -1
#   7c1e0aa feat: filtro de busca na listagem

# 2 e 3. branch certa + trazer só aquele commit
git switch -c feat/filtro-busca
git cherry-pick 7c1e0aa

# 4. voltar e limpar a main LOCAL
git switch main
git reset --hard HEAD~1
$ git cherry-pick 7c1e0aa [feat/filtro-busca 2b8d5f3] feat: filtro de busca na listagem Date: Mon Sep 1 15:04:33 2025 -0300 1 file changed, 42 insertions(+)
Perigoso — e por quê: o passo 4 só é legítimo se a main ainda não subiu com esse commit. Se já subiu, o passo 4 vira git revert 7c1e0aa — você deixa a errata na main e segue com a feature na branch nova. Nunca reset numa branch que outra pessoa tem.
Vários commits de uma vez: git cherry-pick a1b2c3d^..f4e5d6c traz o intervalo inteiro, na ordem. Se der conflito no meio, resolva, git add e git cherry-pick --continue; para desistir, git cherry-pick --abort. Conflito é a aula 02.

09Commitei uma senha

Aqui a resposta muda completamente conforme uma única pergunta: já deu push?

Ainda não deu push

É só um erro seu, na sua máquina. Dá para resolver em dois comandos.

# era o último commit
git rm --cached .env
git commit --amend --no-edit

# estava alguns commits atrás
git reset --soft HEAD~3
# tire o segredo, ajuste e commite de novo

Já deu push

Não é mais um problema de Git. É um incidente.

# 1. ROTACIONE A CHAVE. agora.
#    antes de qualquer comando de git.

# 2. só depois se pensa em limpar
#    o histórico

# 3. o procedimento completo é a
#    aula 09

E em qualquer um dos dois casos, no mesmo commit da correção:

echo ".env" >> .gitignore
git add .gitignore
git commit -m "chore: ignora o .env"
Perigoso — e por quê: apagar o arquivo num commit novo não resolve nada. O valor continua dentro do commit antigo, e o commit antigo continua no histórico, nos forks e no cache do GitHub. Enquanto a chave for válida, ela está exposta. Trocar a chave é o único passo que fecha a porta — limpar o histórico é higiene, não conserto.
Onde está o resto: aqui a gente viu só a parte mecânica do Git. Secret scanning, o que comunicar ao time, como o GitHub te avisa e o procedimento completo de rotação são a aula 09. Como impedir que aconteça de novo — .gitignore desde o primeiro dia — é a aula 01.

10Limpar a série antes da revisão

Você tem nove commits na sua branch e três deles se chamam wip. Antes de abrir o Pull Request (aula 06), o rebase -i transforma isso numa série que dá para revisar.

git rebase -i HEAD~4

Abre um editor com uma linha por commit, do mais antigo para o mais novo. Você troca a primeira palavra de cada linha:

o que abre no editor
pick   a1b2c3d feat: adiciona o formulário de contato
reword e4f5g6h fet: valdiação do email
squash i7j8k9l wip
drop   m0n1o2p console.log de teste
pick
Mantém o commit como está. É o padrão de todas as linhas.
reword
Mantém o conteúdo e abre o editor para você corrigir só a mensagem.
squash
Funde este commit no da linha de cima, juntando as duas mensagens.
fixup
Igual ao squash, mas joga fora a mensagem deste commit. É o que você quer para um wip.
drop
Descarta o commit inteiro. Apagar a linha faz o mesmo.
edit
Para o rebase naquele commit para você mexer no conteúdo e depois git rebase --continue.

Salve e feche. O Git reaplica commit por commit e abre o editor de mensagem quando encontrar um reword ou squash. No fim:

$ git rebase -i HEAD~4 Successfully rebased and updated refs/heads/feat/contato. $ git log --oneline -2 c9a4f81 feat: validação do e-mail 7d2e6b0 feat: adiciona o formulário de contato
Perigoso — e por quê: o rebase reescreve todos os commits que ele toca — todos ganham hash novo, inclusive os que você deixou como pick. Só faça isso na sua branch, e só enquanto ninguém mais tiver baixado. Se você já tinha empurrado a branch e é a única pessoa nela, o push seguinte precisa de git push --force-with-lease. Na main, nunca.
Perdeu a coragem no meio? git rebase --abort devolve tudo ao estado anterior, sem deixar rastro. Deu conflito? Resolva, git add, git rebase --continue — conflito é a aula 02. E se você já terminou o rebase e se arrependeu, o reflog ainda tem a série antiga inteira.

11Achar o commit que quebrou

"Funcionava na semana passada." Entre a semana passada e hoje tem 200 commits. O bisect faz busca binária: você responde "funciona" ou "não funciona" umas oito vezes e ele aponta o culpado.

git bisect start
git bisect bad                 # o commit atual está quebrado
git bisect good v1.4.0         # nesta tag (ou hash) funcionava

# o Git te leva a um commit do meio. TESTE e responda:
git bisect good                # ou: git bisect bad

# ... repita até ele anunciar o culpado ...

git bisect reset               # SEMPRE, no fim
$ git bisect start $ git bisect bad $ git bisect good v1.4.0 Bisecting: 97 revisions left to test after this (roughly 7 steps) [3fa71c0] refatora o cálculo de desconto $ git bisect good Bisecting: 48 revisions left to test after this (roughly 6 steps) # ... seis respostas depois ... b3f9a1d is the first bad commit Author: Fulano <fulano@exemplo.com> perf: troca o loop por reduce

Se você tem um teste automatizado que distingue os dois estados, dá para o Git rodar tudo sozinho:

git bisect start HEAD v1.4.0
git bisect run npm test
Não esqueça o git bisect reset. Durante o bisect você fica em detached HEAD — num commit solto, sem branch. Sem o reset no fim, você continua lá, achando que o projeto inteiro voltou no tempo. Não voltou: é só o bisect ainda aberto.
A rede de segurança

12git reflog: quase nada se perde

Esta é a seção que devolve a coragem. O git log mostra a história que a sua branch conta hoje. O git reflog mostra tudo por onde o seu HEAD passou — inclusive commits que um reset tirou da branch e que o log não enxerga mais.

git reflog                     # por onde o HEAD andou
git reflog show main           # por onde a branch main andou
git reflog --date=iso          # com data e hora legíveis
$ git reflog a1f9c02 HEAD@{0}: reset: moving to HEAD~3 9d3e7bb HEAD@{1}: commit: feat: exportar relatório em CSV 4c81a90 HEAD@{2}: commit: feat: filtro por período 77b2d15 HEAD@{3}: commit: refatora o serviço de relatório a1f9c02 HEAD@{4}: commit: chore: sobe a versão c05f8e7 HEAD@{5}: checkout: moving from feat/csv to main

Leia de cima para baixo como uma linha do tempo ao contrário. A linha HEAD@{0} é o que você acabou de fazer. Cada linha tem o hash de onde o HEAD estava depois daquela operação — e é esse hash que você usa para voltar.

Voltar para um ponto do reflog

# olhe antes de saltar: o que tem naquele hash?
git show 9d3e7bb --stat

# leve a sua branch de volta para lá
git reset --hard 9d3e7bb

# ou, mais seguro: abra uma branch nova naquele ponto
git switch -c recuperado 9d3e7bb
o reflog guardao reflog NÃO guarda
Commits que um reset tirou da branch. Edição de arquivo que nunca virou commit.
A série antiga de antes de um rebase. O que você apagou com git restore.
O commit original de antes de um --amend. Arquivo não rastreado que o reset --hard não chegou nem a ver.
Commits de uma branch que você deletou. Nada de um outro clone: o reflog é local e não viaja no push.
Prazo de validade: as entradas ficam por volta de 90 dias (e 30 para o que já ficou inalcançável) antes de a coleta de lixo do Git considerar apagar. Na prática, dá tempo de sobra — mas não conte com ele daqui a um ano.
O limite que importa: o reflog é seu, local e intransferível. Não vai para o GitHub e não vem junto no clone. Se você apagar a pasta do repositório para "começar do zero", o reflog vai junto — e aí sim os commits somem de verdade. Nunca apague a pasta: é justamente ela que guarda a rede.

13Laboratório: destruir de propósito e recuperar

Este é o exercício que faz a ficha cair. Você vai apagar três commits com reset --hard, ver a pasta vazia, e trazer tudo de volta. Faça num repositório de teste — nunca no do trabalho.

  1. Crie um repositório descartável
    Fora de qualquer projeto seu, numa pasta nova.
  2. Faça três commits bobos
    Três arquivos, três commits, para ter o que destruir.
  3. Olhe o histórico e NÃO copie os hashes
    O exercício só funciona se você tiver que achá-los no reflog depois. Vale a honra.
  4. Destrua
    git reset --hard HEAD~3. Confira que sumiu mesmo — log e ls.
  5. Olhe onde ninguém olha
    git reflog. Ache a linha do seu último commit bom, a de antes do reset.
  6. Ressuscite
    git reset --hard naquele hash. Confira que voltou tudo — log e ls.

Passos 1 a 3 — montar e olhar

mkdir lab-reflog && cd lab-reflog
git init

echo "um"   > a.txt && git add . && git commit -m "feat: arquivo a"
echo "dois" > b.txt && git add . && git commit -m "feat: arquivo b"
echo "três" > c.txt && git add . && git commit -m "feat: arquivo c"

git log --oneline
ls
$ git log --oneline 9d3e7bb (HEAD -> main) feat: arquivo c 4c81a90 feat: arquivo b 77b2d15 feat: arquivo a $ ls a.txt b.txt c.txt

Passo 4 — destruir

git reset --hard HEAD~3
git log --oneline
ls
$ git reset --hard HEAD~3 fatal: ambiguous argument 'HEAD~3': unknown revision # ↑ se você tem só 3 commits, não existe "3 antes do HEAD". # nesse caso use HEAD~2 e o exercício vale igual. $ git reset --hard HEAD~2 HEAD is now at 77b2d15 feat: arquivo a $ ls a.txt

O b.txt e o c.txt sumiram do disco. O git log não conhece mais aqueles dois commits. Para todos os efeitos, o trabalho acabou. Sinta o frio na barriga — é o ponto do exercício.

Passo 5 — procurar

git reflog
$ git reflog 77b2d15 HEAD@{0}: reset: moving to HEAD~2 9d3e7bb HEAD@{1}: commit: feat: arquivo c ← ele está aqui 4c81a90 HEAD@{2}: commit: feat: arquivo b 77b2d15 HEAD@{3}: commit (initial): feat: arquivo a

Ali está o 9d3e7bb, o commit "perdido". Ele nunca foi apagado: só deixou de ter uma branch apontando para ele. Antes de saltar, espie o que tem lá dentro:

git show 9d3e7bb --stat

Passo 6 — ressuscitar

# use o hash que VOCÊ viu no seu reflog, não o do exemplo
git reset --hard 9d3e7bb

git log --oneline
ls
$ git reset --hard 9d3e7bb HEAD is now at 9d3e7bb feat: arquivo c $ git log --oneline 9d3e7bb (HEAD -> main) feat: arquivo c 4c81a90 feat: arquivo b 77b2d15 feat: arquivo a $ ls a.txt b.txt c.txt
Está tudo de volta. Os três commits, os três arquivos, os mesmos hashes. Você desfez um reset --hard, que é o comando que mais assusta no Git inteiro. Guarde a sensação: da próxima vez que der ruim, você já sabe onde procurar.

A parte que NÃO volta

Refaça o laboratório com uma diferença: antes do passo 4, crie um d.txt e não commite.

echo "quatro" > d.txt
git add d.txt

O d.txt não volta com nada. Ele foi para a bancada mas nunca virou commit, e o reflog só guarda commit. É por isso que o --hard é o comando perigoso da aula, e é por isso que a regra é git stash -u antes de qualquer --hard. Repita o teste com o stash na frente e veja a diferença.
Alternativa mais segura ao passo 6: em vez de mover a sua branch com reset --hard, abra uma branch nova no commit recuperado — git switch -c recuperado 9d3e7bb. Aí você compara as duas com calma antes de decidir qual fica.

Antes de pedir ajuda: cole a saída de git status e as dez primeiras linhas de git reflog. Com esses dois textos, qualquer pessoa que conhece Git reconstrói o que aconteceu e diz o comando certo — sem eles, é adivinhação.
E o que fazer é o que NÃO fazer: não apague a pasta do repositório para "começar limpo". É dentro dela, no .git, que mora o reflog — a única cópia dos commits que você acha que perdeu. Apagar a pasta é o único jeito de transformar um susto num prejuízo de verdade.
