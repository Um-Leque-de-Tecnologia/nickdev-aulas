Pull Request e code review

O passo a passo pra você fazer sozinha: abrir um Pull Request do começo ao fim, com descrição que se lê e a issue vinculada, e depois revisar o PR de outra pessoa — que é o exercício em par da aula. No fim, as três formas de integrar e o CODEOWNERS.

Antes de abrir

01O que você vai fazer aqui

Este manual é o roteiro da aula 06 para refazer no seu ritmo. Ele tem duas metades, e as duas importam: primeiro abrir um PR, depois revisar o PR de outra pessoa. A segunda metade é a que quase ninguém treina — e é a que separa quem usa o GitHub de quem trabalha em time nele.

O que você precisa ter em mãos:

  • Um repositório seu no GitHub, com main e pelo menos uma issue aberta — serve o da aula 05.
  • Git configurado e autenticado (chave SSH ou token — isso foi a aula 03).
  • Um par. Para a parte de revisão, alguém precisa abrir um PR pra você olhar, e vice-versa. Se você está sozinha, crie uma segunda conta ou revise um PR aberto de qualquer projeto público — dá pra ler e comentar em quase todos.

O vocabulário desta aula

pull request (PR)
Um pedido para puxar os commits de uma branch para outra, com uma página onde esse pedido é discutido. É uma funcionalidade do GitHub, não do Git. No GitLab chama merge request — é a mesma coisa.
fork
Uma cópia do repositório inteiro na sua conta. Serve para contribuir com um projeto onde você não tem permissão de escrita.
base × compare
base é para onde a mudança vai (quase sempre main). compare é de onde ela vem (a sua branch). Inverter os dois é o erro nº 1 do primeiro PR.
review
Um conjunto de comentários enviados de uma vez, com um veredicto: approve, request changes ou comment.
draft
PR em rascunho: aberto e visível, mas sem pedir revisão e sem deixar dar merge.
Não é desta aula: tornar a revisão obrigatória e proibir push direto na main é branch protection, a aula 07. Testes e lint travando o botão de merge são a aula 09. Contribuir de verdade com um projeto open source — achar o projeto, ler o CONTRIBUTING, manter o fork em dia — é a aula 12. Aqui a gente aprende a mecânica e o tom.

02Fork ou branch: qual é o seu caso

Antes de qualquer coisa, responda uma pergunta: você tem permissão de escrita nesse repositório? A resposta decide o caminho inteiro.

situaçãocaminhopor quê
É seu, ou você é colaborador do repositórioBranch no próprio repositórioVocê consegue dar push direto na branch nova. Sem remoto extra, sem cópia para manter em dia.
Você está numa organização com acesso write ou maisBranchMesmo caso. Fork aqui é atrito à toa.
Projeto de outra pessoa, ou open sourceForkSem escrita, o push volta com Permission denied. Não é bug — é o modelo.
Você tem só read ou triage na orgForkEsses níveis não escrevem no repositório. Os níveis de permissão são da aula 04.

Caminho A — branch (de dentro)

terminal
# saia sempre de uma main atualizada
git switch main
git pull

# branch do assunto, com nome que se lê
git switch -c feat/busca-no-catalogo

# ... edite, commite ...
git push -u origin feat/busca-no-catalogo

Caminho B — fork (de fora)

Clique em Fork, no canto superior direito do repositório. O GitHub cria voce/projeto na sua conta. Aí você clona a sua cópia:

terminal
# clone o SEU fork, não o original
git clone git@github.com:voce/projeto.git
cd projeto

# guarde o original como um segundo remoto, chamado upstream
git remote add upstream git@github.com:original/projeto.git
git remote -v
$ git remote -v origin git@github.com:voce/projeto.git (fetch) origin git@github.com:voce/projeto.git (push) upstream git@github.com:original/projeto.git (fetch) upstream git@github.com:original/projeto.git (push)

Daí em diante é igual: branch, commit, git push -u origin sua-branch. Ao abrir o PR, o GitHub já entende que a base é original/main e o compare é voce/projeto:sua-branch.

Manter o fork em dia é git fetch upstream e depois git merge upstream/main (ou rebase) na sua main. Fork abandonado por três meses vira PR cheio de conflito. O procedimento completo, com o botão Sync fork da interface, é a aula 12.
Abrir o Pull Request

03Abrir um PR, do começo ao fim

Este é o exercício inteiro, na ordem. Faça no seu repositório da aula 05.

  1. Escolha uma issue aberta e anote o número. É o número depois do # no título dela. Se não tiver nenhuma issue, escreva uma agora — duas linhas bastam, e a aula 05 tem o modelo.
  2. Crie a branch a partir de uma main atualizada. Pular o git pull aqui é a origem da metade dos conflitos.
    terminal
    git switch main
git pull
git switch -c feat/busca-no-catalogo
  3. Faça a mudança e commite. Um assunto só. Se você se pegou mexendo em outra coisa, guarde para o próximo PR.
    terminal
    git add .
git commit -m "feat: busca por nome no catálogo"
  4. Empurre a branch com -u. O -u liga a branch local à de lá. Depois disso, git push sozinho basta.
    terminal
    git push -u origin feat/busca-no-catalogo
    $ git push -u origin feat/busca-no-catalogo remote: Create a pull request for 'feat/busca-no-catalogo' on GitHub by visiting: remote: https://github.com/voce/loja/pull/new/feat/busca-no-catalogo branch 'feat/busca-no-catalogo' set up to track 'origin/feat/busca-no-catalogo'.

    O próprio Git te dá o link. Pode clicar nele.

  5. Abra o PR. Pelo link acima, pelo aviso amarelo que aparece no topo do repositório (Compare & pull request) ou pela aba Pull requests → New pull request.
  6. Confira base e compare. No topo da tela: base: main ← compare: feat/busca-no-catalogo. Se aparecerem centenas de arquivos que você não tocou, é porque estão invertidos — ou a sua branch saiu de uma main velha.
  7. Escreva título e descrição. O título diz o que muda. A descrição responde três perguntas — está na seção 04. Não esqueça do Closes #NÚMERO.
  8. Abra como rascunho. No botão verde, use a setinha e escolha Create draft pull request. Assim ninguém é chamado antes da hora.
  9. Corrija empurrando por cima. Percebeu um erro? Não abra outro PR. Commite na mesma branch e dê git push: o PR se atualiza sozinho, porque ele aponta para a branch, não para um commit congelado.
Conferência: o seu PR tem número (#3, por exemplo), aparece na aba Pull requests com o selo cinza Draft, e a issue que você citou mostra uma linha dizendo que este PR vai resolvê-la.

04Título e descrição que valem a leitura

Quem revisa lê a descrição antes do código. Se ela não disser o que procurar, a revisão vira leitura de diff no escuro — e leitura de diff no escuro não acha nada.

O título

Uma linha, no imperativo ou no presente, dizendo o que o PR faz. Nada de ajustes, correções, WIP ou update.

Assim não

ajustes
correções finais
update catalogo.js
WIP

Assim sim

feat: busca por nome no catálogo
fix: total do carrinho zerava com lista vazia
docs: como rodar o projeto no Windows
Repare no prefixo: feat:, fix:, docs: são Conventional Commits, que é a aula 07. Você não precisa usar hoje — mas se o seu time usa, o título do PR é onde isso mais importa, porque em squash ele vira a mensagem do commit na main para sempre.

A descrição: três perguntas

Sempre as mesmas: o que muda, por que muda, como eu confirmo que funciona.

descrição do PR · markdown
Closes #12

## O que muda
Campo de busca no topo do catálogo. Filtra por nome,
ignorando acento e maiúscula/minúscula.

## Por quê
Com 300 produtos, rolar a lista virou o gargalo relatado
no suporte (issue #12). A busca resolve sem mudar a rota.

## Como testar
1. `npm install && npm run dev`
2. Abra `/catalogo`
3. Digite `cafe` — deve achar "Café Coado"

## O que ficou de fora
Busca por categoria e por preço. Vale outro PR.
A seção que mais rende: O que ficou de fora. Ela impede metade dos comentários do tipo "e por que você não fez também…" — porque você já respondeu.

05O template de PR

Ninguém lembra das três perguntas às seis da tarde. O template lembra por você: é um arquivo no repositório que preenche a caixa de descrição de todo PR novo, sozinho.

Crie o arquivo, commite na main e pronto — vale a partir do próximo PR.

É o mesmo mecanismo do template de issue da aula 05, do outro lado da mesa. Quem escreve a issue e quem escreve o PR passam a responder as mesmas perguntas — e aí o histórico do projeto fica legível de ponta a ponta.

06Rascunho e Closes #12

PR em rascunho (draft)

Abre o PR sem pedir revisão. Serve pra mostrar trabalho em andamento, pedir opinião cedo e deixar a automação rodar antes de a coisa estar pronta.

  • Ninguém é notificado como revisor, e revisor exigido não é cobrado.
  • O botão de merge fica travado — de propósito. É a proteção contra o merge distraído.
  • Quando estiver de pé, clique em Ready for review. Aí sim a turma é chamada.
  • Dá pra voltar pra rascunho depois (Convert to draft), se você percebeu que faltava coisa. Isso não é vergonha nenhuma.

Vincular a issue

Escreva a palavra-chave seguida de # e do número, na descrição do PR:

descrição do PR
Closes #12
formao que faz
Closes #12Vincula e fecha a issue 12 quando o PR entrar na branch padrão.
Fixes #12 · Resolves #12Exatamente o mesmo efeito. Escolha uma e siga.
Closes nickdev/loja#12Fecha uma issue de outro repositório, desde que você tenha permissão lá.
Closes #12, closes #15Fecha as duas. Repita a palavra-chave — Closes #12, #15 só fecha a primeira.
relacionado a #12Só cita: cria o link cruzado nas duas telas, sem fechar nada.
Onde tem que estar: na descrição do PR (o campo grande, de cima) ou na mensagem de um commit. Escrito num comentário do PR, o vínculo até aparece, mas a issue não fecha no merge. É o motivo nº 1 de "a issue não fechou sozinha".
É aqui que a aula 05 se encaixa na 06. A issue vira o "por quê" do seu PR de graça, e fecha sozinha quando o código entra. Por isso vale escrever a issue antes do código, mesmo trabalhando sozinha.

07O tamanho do PR é decisão técnica

PR de 40 linhas recebe revisão. PR de 2.000 recebe um LGTM 👍. Não porque a pessoa é preguiçosa — porque ninguém segura 2.000 linhas na cabeça ao mesmo tempo.

tamanho do diffo que acontece de verdade
até ~50 linhasRevisão linha a linha, comentários específicos, sugestões aplicáveis, retorno no mesmo dia.
~200 linhasAinda funciona, se for um assunto só. A atenção cai do primeiro arquivo pro último.
500+ linhasVira aprovação por confiança. Comentam-se nomes de variável, porque é o que ainda cabe.
1.000+ linhasNinguém lê. É carimbo. E ainda fica dias parado, porque abrir dá preguiça.

Como manter pequeno

  • Um assunto por PR. Refatoração + funcionalidade nova no mesmo PR são dois PRs mal embalados.
  • Formatação em massa vai em PR separado. Senão a mudança de verdade some no meio de 4.000 linhas de vírgula.
  • Se precisa de índice pra explicar, está grande demais. Quebre por camada, por arquivo ou por etapa.
  • Empilhe. Abra o PR 2 com base no PR 1 (base: feat/parte-1 em vez de main). Cada um é revisado sozinho, na ordem.
  • Separe o preparo da mudança. "Extrai a função" num PR, "usa a função pra resolver o bug" no outro: o segundo fica com dez linhas e o revisor enxerga o bug.
O argumento que convence: PR pequeno volta em uma hora; PR gigante fica três dias parado e depois dá conflito. O pequeno é mais rápido inclusive pra quem escreveu.
Revisar o PR de outra pessoa

08Revisar, passo a passo

Esta é a metade que a turma faz em par: pegue o link do PR de outra pessoa e siga daqui. Combinado da aula: hoje ninguém usa Request changes — o objetivo é treinar a escrita, não travar ninguém.

  1. Leia a descrição inteira antes do código. Se ela não te disser o que procurar, esse já é o seu primeiro comentário — e é um comentário útil.
  2. Abra a aba Files changed. É onde a revisão acontece. A aba Conversation é o mural; o diff está aqui.
  3. Comente em linha. Passe o mouse sobre a linha e clique no + azul. Para comentar um trecho, arraste o + por várias linhas. O comentário fica ancorado ali, visível junto do código.
  4. Use Start a review, não Add single comment. A revisão acumula tudo e envia de uma vez. Sem isso são dez comentários e dez notificações — e a pessoa começa a responder o primeiro enquanto você ainda escreve o quinto.
  5. Marque os arquivos já lidos com Viewed. Em PR com muitos arquivos, é o que impede você de reler o mesmo três vezes.
  6. Deixe uma sugestão aplicável. Está na seção 09. Uma basta pra treinar.
  7. Marque o peso de cada comentário. nit: pra detalhe, opcional: pra sugestão, bloqueante: pro que não pode entrar. Sem marca, quem recebe trata tudo como ordem.
  8. Clique em Submit review e escolha o veredicto. Escreva um resumo de duas linhas no campo de cima — é a única parte que a pessoa lê inteira, com certeza.

Os três veredictos

veredictoquer dizerquando usar
Approve"Pode entrar."Você não vê motivo pra segurar. Não quer dizer que está perfeito — comentário de gosto pode ir junto, marcado como opcional.
Request changes"Assim não entra."Tem algo que quebra, e você consegue dizer o quê em uma frase. Trava o PR de propósito. É o veredicto que exige mais cuidado na escrita.
Comment"Li, sem veredicto."Perguntas, contexto, revisão parcial ("olhei só o SQL"). A escolha honesta quando você tem opinião mas não a autoridade — ou o tempo — pra decidir.
Regra prática: se você não consegue escrever numa frase o que precisa mudar, não é request changes — é comment com uma pergunta. Segurar PR por vírgula é como o time aprende a ignorar revisão.

Do outro lado: responder à revisão

  • Responda todos os comentários, nem que seja "boa, corrigido" ou "prefiro manter, porque…".
  • Corrija empurrando por cima: git commit + git push na mesma branch. O PR se atualiza sozinho.
  • Clique em Resolve conversation só no que você já atendeu. O que sobrar aberto é o que ainda falta.
  • Peça nova revisão no ícone de reciclar ao lado do nome da pessoa (re-request review) — ela não é notificada sozinha.
Comentário escrito e não enviado é a queixa mais comum da turma. Se você usou Start a review, os comentários ficam guardados como rascunho até o Submit review. O botão Finish your review fica no topo da aba Files changed, com o número de comentários pendentes.

09Sugestão em um clique

Dentro da caixa do comentário em linha existe um botão com ícone de arquivo e ±. Ele insere um bloco especial: o que você escrever ali vira código aplicável com um clique.

na caixa do comentário em linha
Sem valor inicial, o `reduce` estoura com lista vazia.
Que tal:

```suggestion
  return itens.reduce((soma, item) => soma + item.preco, 0)
```

Quem recebe vê o antes e o depois lado a lado e clica em Commit suggestion. Vira um commit no PR, com você como coautor.

regrao que significa na prática
Substitui a seleçãoO bloco troca exatamente as linhas que você selecionou. Selecionou uma, sugere uma; arrastou por três, o bloco substitui as três.
Indentação entra literalEscreva o código já indentado como vai ficar no arquivo. O que está dentro do bloco é copiado como está.
Dá pra juntarAdd suggestion to batch acumula várias e commita todas de uma vez, num commit só.
Serve pro objetivoUm nome, um typo, uma linha mais simples, um valor padrão. Sugestão de trinta linhas é reescrever o PR da pessoa por cima dela.
Não serve pro desenhoPra mudança de arquitetura, escreva a pergunta. A sugestão responde "como escrever"; ela não responde "por que assim".
Por que vale tanto: a sugestão elimina a rodada mais cara da revisão — aquela que existe só porque a pessoa não entendeu o que você queria que ela escrevesse.

10Crítica técnica sem virar briga

Revisão é a hora em que uma pessoa lê o trabalho da outra e diz o que está errado. Não existe jeito de isso ser neutro — existe jeito de ser respeitoso e continuar sendo útil. Estas seis regras cobrem quase tudo.

  1. Critique o código, não a pessoa. O sujeito da frase é o código. "Este laço roda duas vezes" — não "você fez o laço errado". A diferença parece cosmética e não é: a primeira é um fato sobre um arquivo, a segunda é um veredicto sobre alguém.
  2. Pergunte em vez de sentenciar. "O que acontece se a lista vier vazia?" abre conversa; "isso quebra com lista vazia" fecha. E tem um bônus honesto: às vezes quem pergunta é quem está enganado, e a pergunta te salva de afirmar bobagem em público.
  3. Separe o que bloqueia do que é gosto. Marque cada comentário: bloqueante:, opcional:, nit:, pergunta:. Sem marcação, quem recebe trata tudo como ordem — e cinco "nits" seguidos parecem uma reprovação geral.
  4. Diga o porquê. "Prefiro map aqui" é gosto. "map evita o índice manual, que é onde nasce o erro de um a mais" é revisão. Sem o motivo, a pessoa obedece sem aprender — ou discorda sem argumento.
  5. Elogie o que está bom, e seja específico. "Ficou bom" não ensina nada. "O nome desta função já explica o bloco inteiro" ensina. Revisão que só aponta defeito ensina ao time que revisão dói.
  6. Duas idas e voltas, chame no áudio. Texto é péssimo pra discordar: some o tom, sobra a literalidade. Cinco minutos de conversa resolvem o que dez comentários azedam. Depois, escreva a conclusão no PR — pra quem chegar depois entender.

O que mudou entre as duas colunas: apareceu o motivo, apareceu a pergunta, e o peso de cada comentário está escrito. Custa trinta segundos a mais.

E quando você é quem recebe

  • O PR é seu; o código não é você. "Boa, não tinha pensado nisso" é uma resposta profissional completa — e a mais barata de todas.
  • Discordar é legítimo. Discorde com o motivo: "prefiro manter, porque isto aqui roda dentro de um laço quente".
  • Se um comentário te irritou, espere vinte minutos antes de responder. O comentário vai continuar lá.
  • Se a revisão foi útil, diga. Quem revisa também não recebe retorno quase nunca.
Combinado que vale escrever no CONTRIBUTING.md: "todo comentário de revisão que não for bloqueante começa com nit: ou opcional:". É uma linha, e muda o clima do repositório inteiro.

11Merge, squash ou rebase

O botão verde tem uma setinha. As três opções integram o mesmo código — e deixam três históricos bem diferentes na main. Retomando o grafo da aula 02:

create a merge commit
main  A─B─────────M      M = commit de merge, com dois pais
           \     /
feat        C─D─E        os 3 commits continuam lá
squash and merge
main  A─B─S              S = C+D+E num commit só, hash novo
rebase and merge
main  A─B─C'─D'─E'       reaplicados por cima; C' não é C

Qual usar

opçãoo que faz com o históricouse quandoevite quando
Merge commit
create a merge commit		 Guarda os commits da branch e cria um commit extra dizendo quando ela entrou. O grafo fica trançado, e dá pra ver o formato de cada contribuição. O histórico da branch importa (release, migração longa, contribuição externa grande). Times que leem o grafo com git log --graph. PR pequeno do dia a dia: cada um vira dois nós no grafo, e a main vira uma trança ilegível.
Squash
squash and merge		 Junta tudo num commit só na main. O título do PR vira a mensagem. O caminho até a solução — inclusive o commit "ops, esqueci o ponto e vírgula" — desaparece. Padrão que serve pra maioria dos times. A main vira a lista de PRs, que é a lista de decisões. Ótimo com PR pequeno e um assunto só. O PR tem commits que valem separados de verdade (duas mudanças independentes que você não quis separar em dois PRs).
Rebase
rebase and merge		 Reaplica cada commit por cima da main, sem commit de merge. Linha reta, commits preservados — mas com hashes novos: C' não é C. O time cuida dos commits um a um e quer histórico linear. Combina com quem já usa git pull --rebase (aula 03). Alguém mais trabalha na mesma branch: os commits reescritos quebram o histórico local dela. E se os commits forem bagunçados, a bagunça vai inteira pra main.
Escolha uma vez, com o time. Em Settings → General → Pull Requests dá pra desligar as opções que vocês não usam — assim ninguém escolhe errado às sete da noite. Nossa recomendação para começar: só squash ligado.

Depois do merge

terminal
# clique em "Delete branch" na tela do PR e depois, aqui:
git switch main
git pull
git branch -d feat/busca-no-catalogo

# limpa as branches remotas que já não existem lá
git fetch --prune
Conferência final: git log --oneline -5 na main mostra o seu PR, e a issue que você citou está fechada, com link para o PR. Se a issue continuar aberta, o Closes # não estava na descrição — veja a seção 06.

12CODEOWNERS

O CODEOWNERS diz quem é dono de qual pedaço do repositório. Quando um PR toca um desses caminhos, o GitHub adiciona os donos como revisores sozinho — ninguém precisa lembrar de chamar.

.github/CODEOWNERS

regrao que saber
Onde fica.github/CODEOWNERS, na raiz, ou em docs/. Um arquivo por branch — o que vale é o da branch base do PR.
Sintaxe dos caminhosA mesma do .gitignore: *, **, /pasta/, *.ext. Começar com / ancora na raiz.
A última regra venceO contrário da intuição e do .gitignore mental de todo mundo. Ordene do geral para o específico.
Quem pode ser donoUsuário (@nicoly), time de organização (@org/time) ou e-mail. Precisa ter acesso de leitura ao repositório — nome errado ou sem acesso é ignorado em silêncio.
Ele convida, não obrigaO dono é adicionado como revisor. Exigir a aprovação dele para liberar o merge é branch protection — aula 07.
Erro de sintaxeO GitHub mostra os erros ao abrir o arquivo na interface (aba Code). Confira lá depois de commitar — linha inválida não avisa em PR nenhum.
O problema que ele resolve ninguém admite ter: o PR que ficou três dias parado porque a pessoa certa não sabia que ele existia.

14Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
O PR mostra centenas de arquivos que você não tocou base e compare invertidos, ou a sua branch saiu de uma main desatualizada. Confira as duas pontas no topo do PR. Se for a main velha: git switch main && git pull, volte pra sua branch e traga a main pra dentro dela.
There isn't anything to compare Você não deu push na branch, ou ela é idêntica à base. git push -u origin sua-branch e recarregue a página. Se for idêntica, você esqueceu de commitar.
remote: Permission to … denied no push Você não tem escrita nesse repositório. Não é erro de senha nem de chave. Faça fork, empurre para a sua cópia e abra o PR de lá — seção 02.
A issue não fechou depois do merge O Closes #12 ficou num comentário, e não na descrição do PR. Ou o merge não foi para a branch padrão. Feche a issue na mão desta vez. No próximo PR, escreva na descrição — o template da seção 05 já lembra você.
O botão de merge está cinza PR em rascunho, conflito com a base, ou revisão pendente. Ready for review; conflito se resolve como na aula 02 (e o GitHub deixa resolver no navegador quando é pequeno); revisão obrigatória é a aula 07 e checks travando o merge, a aula 09.
Escrevi os comentários e a pessoa não recebeu A revisão ficou em rascunho: faltou o Submit review. Volte em Files changed e clique em Finish your review, no topo. Os comentários estavam guardados lá o tempo todo.
A sugestão não aplica / não aparece o botão O bloco não está entre ```suggestion e ```, ou a linha mudou depois que você escreveu. Reescreva a sugestão sobre a versão atual do arquivo, usando o botão ± da caixa de comentário.
Apliquei a sugestão e a indentação quebrou O conteúdo do bloco entra literal: faltaram (ou sobraram) espaços. Commite uma correção por cima. Da próxima, copie a linha original pro bloco e edite só o que muda.
Meus commits sumiram depois do merge Foi squash: os três viraram um só na main. É o comportamento esperado. Os originais seguem na branch, se ela não foi apagada. A seção 11 explica as três opções.
Dei merge e a branch continua aparecendo Foi apagada no GitHub, mas não na sua máquina — ou nem lá. git branch -d feat/nome local e git fetch --prune. Se o -d reclamar, é porque ela não foi integrada nessa main.
O CODEOWNERS não chamou ninguém Erro de sintaxe, pessoa sem acesso ao repositório, ou o arquivo não está na branch base. Abra o arquivo pela interface: o GitHub aponta as linhas inválidas ali. Confira também se o time é @org/time e tem acesso.
Ninguém revisou o meu PR em três dias Está grande demais, ou ninguém foi chamado. Peça revisão a uma pessoa específica (Reviewers), configure o CODEOWNERS — e da próxima, quebre em PRs menores (seção 07).
A revisão virou discussão azeda Texto some com o tom e sobra a literalidade. Pare de responder por escrito e chame num áudio de cinco minutos. Depois escreva a conclusão no PR. A seção 10 é justamente sobre evitar chegar aqui.
Antes de pedir ajuda: mande o link do PR, não a descrição do problema. Quase tudo que a pessoa precisa saber — base, compare, arquivos, conflito, checks — está naquela página, e ela lê em dez segundos.
