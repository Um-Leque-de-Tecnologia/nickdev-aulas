Pull Request e code review

No fim de hoje você abriu um PR de verdade, revisou o PR de outra pessoa sem estragar a relação e integrou os dois — sabendo qual dos três botões de merge apertar e o que cada um faz com o histórico.

deixe aberto: o repositório da aula 05, com pelo menos uma issue aberta. e combine um par — metade da aula de hoje é revisar o PR de outra pessoa.

use ← → pra navegar · manual desta aula

// o problema

O código já entrou. Agora é tarde.

$ git switch main $ git merge feat/busca $ git push origin main To github.com:time/loja.git b3f81a2..9d0c4e1 main -> main # pronto. ninguém viu. ninguém perguntou nada.

Tecnicamente funcionou. Foi por isso que ninguém percebeu o problema.

1Ninguém leu. O bug que outra pessoa veria em dez segundos entrou junto.
2Ninguém sabe por quê. A mensagem do commit diz o que mudou; o motivo continua na sua cabeça.
3Não dá mais pra discutir. Comentar depois do merge é reclamação, não revisão.
4Quem chegar no time daqui a seis meses não tem onde ler a decisão.
5A main não tem porteiro. Com uma pessoa só, dá sorte. Com duas, vira aposta.

Branch e merge você faz desde a aula 02; empurrar pro GitHub, desde a aula 03. O que falta é a mesa — o lugar onde a mudança é lida antes de entrar. Essa mesa chama Pull Request.

// o conceito

Um pedido com sala de reunião embutida

Você diz: "fiz isso aqui na minha branch — dá pra puxar pra main?". O GitHub abre uma página onde esse pedido fica de pé até alguém decidir. Essa página é o Pull Request.

🌿
a sua branchcommits que ainda não estão na main
→
📬
PR abertoo diff, a descrição e a conversa, num lugar só
→
👀
revisãoalguém lê, pergunta, sugere, aprova
→
🤝
mergeentra na main, com registro de quem deixou entrar

É uma comparação

O diff entre duas branches, arquivo por arquivo, linha por linha — atualizado sozinho a cada push novo.

É uma conversa

Comentários presos na linha do código, que continuam legíveis anos depois de o assunto ter passado.

É um portão

Nada entra na main enquanto alguém não apertar o botão. Quem apertou fica registrado.

PR é coisa do GitHub, não do Git. O Git só conhece merge. Por isso o GitLab chama a mesmíssima coisa de merge request — é o mesmo objeto com outro nome na porta.

// de onde sai a branch

Duas portas de entrada: branch e fork

branch

Contribuir de dentro

Você tem permissão de escrita no repositório (write pra cima — os níveis são da aula 04). Cria a branch ali mesmo, dá push e abre o PR de uma branch para a outra, dentro da mesma casa. É o caminho de todo dia dentro de um time.

fork

Contribuir de fora

Você não tem permissão de escrita. O botão Fork copia o repositório inteiro para a sua conta; você empurra para a sua cópia e abre o PR apontando de volta para o original. É assim que estranhos contribuem com projeto aberto.

1Dentro do time, fork é atrito à toa: mais um remoto para manter em dia, sem ganho nenhum.
2Fora do time, fork não é escolha: sem permissão de escrita, o git push no repositório alheio é rejeitado, e ponto.
3O PR é igual nos dois casos. Muda só de onde a branch sai — a tela de revisão, os comentários e o botão de merge são os mesmos.

Contribuir de verdade com um projeto open source — achar o projeto, ler o CONTRIBUTING, manter o fork em dia — é a aula 12. Hoje a gente treina a mecânica.

// a mecânica

De branch a PR, em quatro movimentos

terminal
# 1. sempre saia de uma main atualizada
git switch main
git pull

# 2. a branch do assunto, com nome que se lê
git switch -c feat/busca-no-catalogo

# 3. commits pequenos, e o push que cria a branch lá
git push -u origin feat/busca-no-catalogo

Depois do push, o GitHub coloca sozinho um aviso amarelo no topo do repositório com o botão Compare & pull request. É o atalho — mas o PR também se abre pela aba Pull requests, botão New.

4Na tela do PR, confira as duas pontas: base é para onde vai (quase sempre main); compare é de onde vem (a sua branch).
5Inverter base e compare é o erro clássico da primeira vez. O sintoma é um diff gigante e de cabeça pra baixo — centenas de arquivos que você não tocou.
6Num PR vindo de fork, a base fica original/main e o compare fica voce/repo:sua-branch. A tela mostra os dois donos, lado a lado.
7Todo push novo na mesma branch entra no PR sozinho. Não se abre PR de novo pra corrigir — corrige e empurra.

O PR aponta para a branch, não para um commit congelado. É por isso que responder a uma revisão é só commitar por cima e dar push.

LAB 1

Abra o seu primeiro PR

~12 min

Use o repositório da aula 05 e uma issue que já esteja aberta lá. Se não tiver nenhuma, escreva uma agora — de duas linhas serve.

Anote o número da issue

É o número que aparece depois do # no título dela. Você vai precisar dele no passo 4.

Branch, mudança pequena, commit

Resolva a issue de verdade — nem que seja uma linha. Um assunto só.

git switch main && git pull
git switch -c feat/busca-no-catalogo
# edite o arquivo
git commit -am "feat: busca por nome no catálogo"

Empurre a branch

O -u liga a sua branch local à de lá — depois disso, git push sozinho já basta.

git push -u origin feat/busca-no-catalogo

Abra o PR — e abra como rascunho

Título que diz o que muda. Na descrição, escreva Closes #12 com o número da sua issue. No botão verde, use a setinha e escolha Create draft pull request.

quando terminar

Cole o link do seu PR no chat da turma. Daqui a pouco ele vai ser revisado por outra pessoa — então deixe a descrição legível para quem não estava do seu lado quando você escreveu o código.

// abrir bem

Título e descrição: o que muda e por quê

Quem revisa lê a sua descrição antes do seu código. Se ela não disser o que procurar, a revisão vira leitura de diff no escuro — e leitura de diff no escuro não acha nada.

assim não 
ajustes

fiz umas mudanças, depois vejo o resto

Não diz o que muda, não diz por quê, não diz onde olhar. Quem revisa tem que descobrir tudo sozinho — e vai aprovar sem ler.

assim sim

## Por quê

2É o mesmo mecanismo do template de issue da aula 05, do outro lado da mesa.

// rascunho e issue

Rascunho, e o gancho que fecha a issue

PR em rascunho (draft)

  • Abre o PR sem pedir revisão: ninguém é notificado como revisor e o botão de merge fica travado.
  • Serve pra mostrar trabalho em andamento, pedir opinião cedo e deixar o CI rodar antes de a coisa estar pronta.
  • Quando estiver de pé, o botão Ready for review tira o rascunho e aí sim chama a turma.
  • Dá pra voltar pra rascunho depois, se você percebeu que faltava coisa. Ninguém morre por isso.

Vincular a issue

na descrição do PR
Closes #12
# também valem: Fixes #12, Resolves #12

# issue em outro repositório:
Closes nickdev/loja#12

# só citar, sem fechar nada:
relacionado a #12
  • Enquanto o PR está aberto, a issue mostra que existe um PR resolvendo ela.
  • No merge, a issue fecha sozinha — com link para o PR que a fechou.
  • Só vale na descrição do PR ou na mensagem do commit. Em comentário solto, não fecha nada.

Aqui as duas aulas se encaixam: a issue que você escreveu na aula 05 fecha sozinha quando este PR entra. É por isso que vale escrever a issue antes do código — ela vira o "por quê" do PR de graça.

// decisão técnica

O tamanho do PR é decisão técnica

PR de 40 linhas recebe revisão. PR de 2.000 recebe um LGTM 👍. Não porque a pessoa é preguiçosa — porque ninguém segura 2.000 linhas na cabeça ao mesmo tempo.

tamanho do diffo que acontece de verdade
até ~50 linhasRevisão linha a linha. Comentários específicos, sugestões aplicáveis, retorno no mesmo dia.
~200 linhasAinda dá, se for um assunto só. A pessoa lê com atenção decrescente do primeiro arquivo pro último.
500+ linhasA revisão vira aprovação por confiança. Comentam-se nomes de variável, porque é o que ainda cabe.
1.000+ linhasNinguém lê. É carimbo. E o PR ainda fica dias parado, porque abrir ele dá preguiça.
  • Um assunto por PR. Refatoração mais funcionalidade nova no mesmo PR são dois PRs mal embalados.
  • Formatação automática em massa merece PR separado — senão a mudança de verdade some no meio de 4.000 linhas de vírgula.
  • Se você precisa de um índice pra explicar o seu PR, ele já está grande demais.
  • PR pequeno volta em uma hora; PR gigante fica três dias parado e depois dá conflito. O pequeno é mais rápido inclusive pra você.
parada obrigatória

Sem seguir sem responder

Três perguntas sobre a primeira metade. A segunda metade — revisar — empilha em cima destas.

1Você quer contribuir com um repositório onde não tem permissão de escrita. Qual é o seu caminho, e por quê o outro não serve?
2O que muda num PR marcado como rascunho?
3Onde exatamente precisa estar escrito Closes #12 pra issue fechar sozinha no merge?

respostas: 1 — fork, porque sem escrita o push é rejeitado; 2 — não notifica revisor e não deixa dar merge; 3 — na descrição do PR (ou na mensagem do commit), nunca num comentário.

// o outro lado da mesa

Revisar começa na aba Files changed

1A aba Files changed tem o diff inteiro. É lá que a revisão acontece — não na aba de conversa.
2Passe o mouse sobre a linha e clique no + azul: nasce um comentário ancorado naquela linha, que fica visível junto do código.
3Arraste o + por várias linhas pra comentar um trecho inteiro em vez de uma linha só.
4Use Start a review, não Add single comment. A revisão junta tudo e envia de uma vez — senão são dez comentários, dez notificações.
5Viewed marca o arquivo como já lido. Em PR com muitos arquivos, é o que impede você de reler o mesmo três vezes.
6Quem recebeu resolve a conversa com Resolve conversation depois de atender — some da tela e fica no registro.
Files changed · src/catalogo.js
+ function total(itens) {
+   return itens.reduce((a, b) => a + b.preco)
+ }
   💬 você: e se `itens` vier vazio?

Comentário em linha é a diferença entre "tem um problema no arquivo de busca" e "esta linha aqui". O primeiro obriga a pessoa a caçar; o segundo já chega no lugar.

A revisão só sai do rascunho quando você clica em Submit review. Comentário escrito e não enviado é a queixa mais comum da turma — e não é bug.

// sugestão

A correção que entra com um clique

Dentro da caixa de comentário existe um botão com um ícone de arquivo e ±. Ele insere um bloco especial: o que você escrever ali vira código aplicável.

na caixa do comentário em linha
Sem valor inicial, o `reduce` estoura
com lista vazia. Que tal:

```suggestion
  return itens.reduce((a, b) => a + b.preco, 0)
```

Quem recebe vê o antes e o depois e clica em Commit suggestion. Vira commit no PR, com você como coautor.

1A sugestão substitui exatamente as linhas que você selecionou. Selecionou uma, sugere uma; selecionou três, o bloco troca as três.
2Escreva o código já indentado como ele vai ficar no arquivo — o que está no bloco entra literal.
3Dá pra juntar várias sugestões em Add suggestion to batch e commitar todas de uma vez só.
4Use pro que é objetivo: um nome, um typo, uma linha mais simples. Sugestão de trinta linhas é reescrever o PR da pessoa por cima dela.
5Pra mudança de desenho, escreva a pergunta. A sugestão responde "como escrever"; ela não responde "por que assim".

A sugestão economiza a rodada mais cara da revisão: aquela que existe só porque a pessoa não entendeu o que você queria que ela escrevesse.

// submit review

Os três veredictos

Ao clicar em Submit review, o GitHub pede que você escolha um dos três. Eles não são intercambiáveis.

approve

Pode entrar

Aprovar não é dizer que está perfeito: é dizer que você não vê motivo pra segurar. Comentário de gosto pode ir junto da aprovação, marcado como opcional — quem recebe decide.

request changes

Assim não entra

Trava o PR de propósito. Use quando tem algo que quebra — e diga exatamente o quê, em uma frase. É o veredicto que exige mais cuidado na escrita, porque é o que soa como porta na cara.

comment

Li, mas sem veredicto

Perguntas, contexto, revisão parcial — "olhei só o SQL". É a escolha honesta quando você tem opinião mas não a autoridade, ou o tempo, pra decidir.

  • Regra prática: se você não consegue escrever numa frase o que precisa mudar, não é request changes — é comment com uma pergunta.
  • Segurar PR por vírgula é como o time aprende a ignorar revisão. Gaste o request changes com o que merece.
  • Fazer o veredicto ser obrigatório pra dar merge é branch protection — aula 07. Hoje o botão de merge está liberado.

// a parte que ninguém ensina

Crítica técnica sem virar briga

Revisão é a hora em que uma pessoa lê o trabalho da outra e diz o que está errado. Não existe jeito de isso ser neutro — existe jeito de ser respeitoso e continuar sendo útil.

1Critique o código, não a pessoa. O sujeito da frase é o código: "este laço roda duas vezes", não "você fez o laço errado".
2Pergunte em vez de sentenciar. "O que acontece se a lista vier vazia?" abre conversa; "isso quebra com lista vazia" fecha. E às vezes quem pergunta é quem está enganado.
3Separe o que bloqueia do que é gosto. Marque: nit: pra detalhe, opcional: pra sugestão, bloqueante: pro que não pode entrar. Sem marca, quem recebe trata tudo como ordem — e se cansa.
4Diga o porquê. "Prefiro map aqui" é gosto. "map evita o índice manual, que é onde nasce o erro de um a mais" é revisão.
5Elogie o que está bom — específico, não genérico. Revisão que só aponta defeito ensina o time que revisão dói.
6Duas idas e voltas, chame no áudio. Texto é péssimo pra discordar. Cinco minutos de conversa resolvem o que dez comentários azedam.

Do outro lado da mesa vale o contrário: o PR é seu, o código não é você. "Boa, não tinha pensado nisso" é uma resposta profissional completa — e a mais barata de todas.

// fechar

Três formas de integrar, três históricos

Retomando o grafo da aula 02: o botão verde tem uma setinha. O que você escolhe ali muda a história da main pra sempre.

main A─B─────────M \ / feat C─D─E

merge commit

Guarda tudo: os três commits da branch mais um commit M dizendo quando aquilo entrou. Fiel à verdade, e o grafo fica trançado.

main A─B─S S = C+D+E num commit só

squash and merge

Um commit por PR. A main vira linha reta e legível; o caminho até a solução — inclusive o commit "ops, esqueci" — some.

main A─B─C'─D'─E' C' não é C: hash novo

rebase and merge

Reaplica os commits por cima da main, sem commit de merge. Linha reta com os commits preservados — mas reescritos.

Padrão que serve pra maioria dos times: squash, com o título do PR virando a mensagem do commit. Aí o histórico da main é a lista de PRs — que é a lista de decisões. Quem escolhe é o time, uma vez, e todo mundo segue. A tabela de quando usar cada um está no manual.

// codeowners

O revisor certo, chamado sozinho

.github/CODEOWNERS
# dono padrão de tudo que não casar abaixo
*                      @time/plataforma

# o front é revisto por quem cuida do front
/src/componentes/      @nicoly @rodolfo

# infra é assunto de uma equipe só
/.github/workflows/    @time/infra
Dockerfile             @time/infra

# a ÚLTIMA regra que casar é a que vale
/src/componentes/pagamento/**  @time/pagamentos
1O arquivo vive em .github/CODEOWNERS (ou na raiz, ou em docs/). A sintaxe dos caminhos é a mesma do .gitignore.
2Abriu o PR, o GitHub adiciona sozinho os donos dos arquivos tocados como revisores. Ninguém precisa lembrar de chamar.
3A última regra que casar vence — o contrário do que a intuição diz. Ordene do geral pro específico.
4Só funciona com quem tem acesso ao repositório. Time de organização se escreve @org/time, e o time precisa ter acesso também.
5Isto convida. Tornar a aprovação do dono obrigatória pra dar merge é branch protection — aula 07.

CODEOWNERS resolve o problema que ninguém admite ter: o PR que ficou três dias parado porque a pessoa certa não sabia que ele existia.
