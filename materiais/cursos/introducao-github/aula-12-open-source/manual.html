Open source, ecossistema e o que levar daqui

O passo a passo para você fazer a sua primeira contribuição open source sozinho, do começo ao fim: escolher o projeto, achar a issue, forkar, sincronizar, abrir o Pull Request e conviver com a revisão. Depois, o gh CLI e o resto do ecossistema. E no fim, a referência do curso inteiro — o ciclo completo, com a aula que ensinou cada etapa.

A primeira contribuição

01O que você vai fazer aqui

Este manual é o passo a passo da aula 12, a última do curso. No fim dele você tem um Pull Request aberto no repositório de outra pessoa, o gh instalado e funcionando, e um mapa do que estudar depois.

O que já vem pronto: este manual assume que você fez as aulas anteriores. A mecânica de abrir e revisar um PR é a aula 06; o remoto, o push e a autenticação são a aula 03; branch e merge são a aula 02. Aqui a gente só junta tudo num repositório que não é seu.

O vocabulário desta aula

fork
Uma cópia do repositório de outra pessoa na sua conta do GitHub. Você manda o que quiser nela, porque ela é sua.
upstream
O apelido que a gente dá ao repositório original na sua cópia local. Você lê dele; escrever, não dá.
origin
O apelido do seu fork. É para onde os seus push vão.
CONTRIBUTING
O arquivo em que o projeto escreve as regras da casa: branch base, padrão de commit, o que rodar antes do PR.
good first issue
Uma label que marca a tarefa que o mantenedor considera resolvível por quem nunca abriu aquele código.
mantenedor
Quem cuida do projeto e decide o que entra. Quase sempre voluntário, quase sempre fora do horário de trabalho.

Você vai precisar de: conta no GitHub, Git configurado (aula 01), autenticação funcionando (aula 03) e umas duas horas — sendo que boa parte delas é lendo o projeto, não digitando.

02Escolher o projeto e ler o CONTRIBUTING

Escolha um projeto que você usa. É o único critério que se sustenta: você já conhece o comportamento certo, então enxerga o errado.

A checagem de dois minutos

Abra a página do repositório e olhe estas cinco coisas, nesta ordem:

  1. Quando foi o último commit? Se faz mais de seis meses, o seu PR provavelmente vai dormir. Veja em Commits, ao lado do nome da branch.
  2. As issues estão sendo respondidas? Abra as três mais recentes. Se ninguém do projeto comentou em nenhuma, a porta está fechada.
  3. Existe CONTRIBUTING.md? Existir é ótimo sinal — quer dizer que eles querem contribuição de fora.
  4. Existe LICENSE? Sem licença, o projeto é público mas ninguém tem direito legal de usar (aula 04). Contribuir com um desses é gasto de tempo.
  5. Tem PR de gente de fora com merge? Filtre is:pr is:merged na aba Pull requests. Se todos os merges são de duas pessoas do time, a chance do seu é baixa.

O que procurar dentro do CONTRIBUTING

Não leia de cima a baixo. Procure estas cinco respostas — anote as duas primeiras num papel, você vai precisar delas hoje:

perguntapor que importa
Qual é a branch base do PR?Muito projeto não usa main. Abrir contra a errada é o erro mais comum, e não tem conserto: fecha e abre outro.
O que rodar antes de abrir o PR?Lint, teste, formatação. É o mesmo que os checks da aula 09 vão rodar — melhor descobrir o vermelho na sua máquina.
Como nomear branch e commit?Muitos exigem Conventional Commits (aula 07) porque o changelog da release sai daí.
Precisa de issue antes do PR?Em projeto grande, PR sem issue é fechado sem leitura.
Tem CLA para assinar?Contributor License Agreement: um robô comenta pedindo, e o PR fica travado até você aceitar.
Não tem CONTRIBUTING? Abra os três últimos PRs com merge e leia como eles foram escritos: qual a branch de destino, o formato do título, o tamanho do diff. Esse é o manual não escrito do projeto, e ele é tão obrigatório quanto o escrito.

03Achar a good first issue e avisar que você pegou

A busca

Cole na busca do GitHub, com o filtro de issues ligado. Troque a linguagem pela sua e a data por uns três meses atrás:

busca do github.com
is:issue is:open label:"good first issue" no:assignee language:javascript

Os filtros que mais economizam tempo:

  • no:assignee — o mais importante. Sem ele, metade da lista já tem dono.
  • pushed:>2026-06-01 — só projetos que ainda estão vivos.
  • stars:100..2000 — grande o bastante pra ter processo, pequeno o bastante pra você não ser o número 4.000 da fila.
  • comments:<3 — issue com quinze comentários já virou fila de espera.
A label tem vários nomes. Se a busca vier vazia, tente label:"good-first-issue", label:"help wanted", label:"beginner friendly" ou label:"E-easy". Cada projeto batiza a sua.

Antes de escrever qualquer código

  1. Leia a issue inteira, inclusive os comentários. Muita issue já foi resolvida em outro PR e ninguém fechou. Procure por links de PR no fim da conversa.
  2. Reproduza o problema na sua máquina. Se você não consegue ver o bug acontecer, não vai conseguir provar que consertou.
  3. Comente dizendo que vai pegar — e diga como. É o passo que evita duas pessoas gastarem o sábado no mesmo conserto.

Comentário que ninguém responde

  • assign me
  • can I work on this?
  • +1
  • any update?

Cinco pessoas já escreveram isso nessa issue e nenhuma voltou.

Comentário que abre a porta

"Oi! Posso pegar essa? Pelo que li, é trocar a validação em src/form.js pra aceitar CEP com hífen e ajustar o teste em form.test.js. É por aí? Consigo abrir o PR até quinta."

Mostra leitura, propõe caminho, dá prazo.

Se ninguém responder: espere uns três dias e comece assim mesmo, avisando no comentário. Silêncio é comum — a maioria dos mantenedores faz isso de graça, no tempo que sobra. O que não se faz é cobrar todo dia.

04Fork, clone e o remoto upstream

Agora o triângulo: o repositório original, o seu fork e a sua máquina.

1. O fork

Na página do repositório, canto superior direito: Fork → Create fork. Deixe marcado "copy the default branch only" — você não precisa das outras. O resultado mora em github.com/voce/projeto, com um "forked from" embaixo do nome.

2. O clone — do seu fork

Este é o erro que estraga tudo: clonar o repositório original em vez do fork. Fica tudo funcionando até a hora do push, que volta com 403 Permission denied. Confira que a URL tem o seu usuário.
terminal
git clone git@github.com:voce/projeto.git
cd projeto

3. O upstream

O clone já criou o origin apontando para o seu fork. Falta ensinar ao Git onde fica o original:

terminal
git remote add upstream https://github.com/dono/projeto.git
git remote -v
$ git remote -v origin git@github.com:voce/projeto.git (fetch) origin git@github.com:voce/projeto.git (push) upstream https://github.com/dono/projeto.git (fetch) upstream https://github.com/dono/projeto.git (push)

Quatro linhas, dois nomes. Se aparecerem só duas, o remote add não rodou. Se o origin apontar para dono/, você clonou o original — apague a pasta e clone de novo.

Por que HTTPS no upstream e SSH no origin? Porque no upstream você só lê, e HTTPS público lê sem autenticação nenhuma. No origin você escreve, e aí a chave SSH da aula 03 entra em ação. Usar SSH nos dois também funciona.

A regra de ouro

Puxa do upstream, empurra pro origin. Se você decorar essa frase, quase toda dúvida de fork se resolve sozinha. git push upstream vai dar erro de permissão — e está certo que dê.

05Manter o fork em dia

O fork é uma foto do dia em que você clicou no botão. O projeto original continuou andando; o seu fork, não. Duas semanas depois, o seu PR chega cheio de conflito que nem é seu.

A rotina — rode antes de criar qualquer branch

terminal
git switch main
git fetch upstream
git rebase upstream/main
git push origin main
comandoo que faz
git switch mainVolta para a branch base do fork. Você nunca trabalha nela — ela só serve de ponto de partida.
git fetch upstreamBaixa os commits novos do original. Não mexe em nada do que você tem — só traz a informação (aula 03).
git rebase upstream/mainPõe a sua main exatamente igual à do original.
git push origin mainAtualiza o fork lá no site, para o botão "Sync fork" parar de reclamar.
Rebase aqui é seguro. A aula 11 avisa para não reescrever história de branch compartilhada — e a regra continua valendo. A main do seu fork é a exceção honesta: ninguém mais usa aquela branch, e o que ela deveria ser é uma cópia idêntica do original.

Quando o PR já está aberto e pedem rebase

Acontece: o PR fica dez dias esperando, a main anda, e o mantenedor comenta "pode rebasear?". Na sua branch de trabalho:

terminal
git fetch upstream
git switch fix/link-quebrado-no-readme
git rebase upstream/main

# deu conflito? resolva, git add, e:
# git rebase --continue

git push --force-with-lease origin fix/link-quebrado-no-readme
--force-with-lease, nunca --force seco. O --force-with-lease se recusa a sobrescrever se alguém tiver empurrado algo na branch enquanto você trabalhava. É o cinto de segurança do rebase — e a sua branch de PR é sua, então aqui o push forçado é legítimo.

Pelo site, se preferir

Na página do seu fork tem o botão Sync fork → Update branch. Faz o mesmo que os quatro comandos acima, com uma diferença importante: ele atualiza só o fork no site. A sua cópia local continua velha, e você ainda precisa de um git pull origin main depois.

06A branch, o commit e o Pull Request

A mecânica de abrir PR é a aula 06 e não muda. O que muda em contribuição open source é de onde e para onde ele vai.

1. A branch

Sempre a partir da main recém-sincronizada. Nome no padrão que o CONTRIBUTING pediu; na dúvida, o da aula 07:

terminal
git switch main
git fetch upstream && git rebase upstream/main
git switch -c fix/link-quebrado-no-readme

2. A mudança e o commit

Uma mudança pequena e completa. Antes de commitar, rode o que o CONTRIBUTING mandou rodar:

terminal
# o que o projeto pedir — estes são só exemplos comuns
npm test
npm run lint

git add README.md
git commit -m "docs: corrige link da seção de instalação"
Não deixe o seu editor formatar o projeto inteiro. Se o Prettier ou o Black rodarem em salvar, o diff sai com 4.000 linhas e a sua correção some no meio. Rode git diff antes de commitar: se aparecer arquivo que você não abriu, desfaça com git restore (aula 11).

3. O push — para o origin

terminal
git push -u origin fix/link-quebrado-no-readme
$ git push -u origin fix/link-quebrado-no-readme remote: Create a pull request for 'fix/link-quebrado-no-readme' on GitHub by visiting: remote: https://github.com/voce/projeto/pull/new/fix/link-quebrado-no-readme branch 'fix/link-quebrado-no-readme' set up to track 'origin/fix/link-quebrado-no-readme'

O próprio Git te dá o link. Abra ele — ou vá ao seu fork, que mostra uma faixa amarela com Compare & pull request.

4. O PR, e a linha que todo mundo erra

No topo do formulário tem quatro campos. Confira os quatro antes de clicar em criar:

o cabeçalho do PR
base repository: dono/projeto    base: main
head repository: voce/projeto    compare: fix/link-quebrado-no-readme
campotem que ser
base repositoryO repositório do dono — o destino da sua contribuição.
baseA branch base que você anotou do CONTRIBUTING. Nem sempre é main.
head repositoryO seu fork. É de onde a mudança sai.
compareA sua branch, nunca a sua main.

Na descrição, três coisas — e nessa ordem, porque é a ordem em que quem revisa precisa delas:

  1. O que estava errado, e o link da issue. Se o PR vai para o mesmo repositório da issue, Closes #123 fecha ela sozinha no merge (aula 06).
  2. O que você mudou, em uma ou duas frases. Não repita o diff — explique a decisão.
  3. Como testar. Os comandos exatos que provam que funciona. É o que faz o mantenedor gastar cinco minutos em vez de trinta.
Marque Allow edits by maintainers. É a caixinha no canto direito do formulário. Com ela ligada, o mantenedor pode empurrar um retoque na sua branch em vez de te devolver o PR por causa de uma vírgula — e muito PR é aceito assim.
Se o PR nasceu contra a branch errada, não dá para consertar quando o destino é outro repositório: o GitHub não deixa trocar o base repository depois de criado. Feche o PR, explique em uma linha, e abra outro com a mesma branch. Ninguém liga.

07A revisão do mantenedor — e o lado humano

O PR está aberto. E aí, na maior parte das vezes, não acontece nada durante um bom tempo. Vale saber disso antes de acontecer com você.

Pode demorar semanas

Quem mantém o projeto quase sempre faz isso de graça, depois do trabalho. Duas ou três semanas de silêncio é o normal do open source, não desprezo. Um lembrete educado depois de duas semanas é aceitável — um:

Modelo: "Oi! Sem pressa, só passando pra saber se tem algo que eu possa ajustar aqui pra facilitar a revisão."

Pode virar dez comentários

Revisão detalhada é investimento em você: ninguém gasta meia hora comentando um PR que pretende ignorar. Como responder:

  • Responda todos os comentários, mesmo que seja só "boa, corrigi". Comentário sem resposta parece comentário não lido.
  • Corrigiu? Commite na mesma branch e dê push — o PR se atualiza sozinho. Não abra outro PR.
  • Discordou? Pode discordar, com argumento e uma frase só. Se insistirem, ceda: a casa é deles.
  • Vai demorar pra mexer? Diga isso. "Consigo olhar no fim de semana" evita que o PR seja fechado por inatividade.

Pode ser recusado

"Não é a direção do projeto." "Isso já está em outro PR." "Aqui a gente resolve de outro jeito." Nenhuma dessas frases é sobre a sua competência. São decisões de escopo tomadas por quem vai manter aquele código pelos próximos cinco anos — e que conhece dez restrições que você não tinha como saber.

O PR recusado continua sendo trabalho seu. Ele fica no seu perfil, você aprendeu o código de um projeto real, e a próxima issue daquele repositório você lê como quem já conhece a casa. O segundo PR é sempre mais fácil que o primeiro.

Quando dá merge

Você recebe a notificação, a branch pode ser apagada (pode apagar, o commit já está na main deles) e o seu nome entra na lista de contribuidores. Depois disso, limpe a sua casa:

terminal
git switch main
git fetch upstream && git rebase upstream/main
git push origin main
git branch -d fix/link-quebrado-no-readme
Sem sair do terminal

08Instalar e autenticar o gh CLI

O gh é o programa oficial do GitHub para o terminal. Ele não substitui o Git: faz a parte que o Git nunca soube fazer, porque não é dele — issue, Pull Request, release, workflow, fork.

Instalar

Windows

winget install --id GitHub.cli — ou o instalador em cli.github.com.

macOS

brew install gh.

Linux

Está no apt/dnf/pacman da maioria das distros. A instrução exata fica em cli.github.com.

terminal
gh --version

Se a versão aparecer, instalou. Se vier "command not found", feche e abra o terminal antes de reinstalar.

Entrar na conta

terminal
gh auth login
$ gh auth login ? What account do you want to log into? GitHub.com ? What is your preferred protocol for Git operations? SSH ? Generate a new SSH key to add to your GitHub account? Yes ? How would you like to authenticate? Login with a web browser ! First copy your one-time code: A1B2-C3D4 ✓ Authentication complete. ✓ Configured git protocol ✓ Logged in as voce
Isto resolve a aula 03 de uma vez. Respondendo SSH e aceitando gerar a chave, o gh cria a chave, cadastra ela na sua conta e configura o Git para usá-la. É o caminho mais curto de sair do Permission denied (publickey).
terminal
gh auth status

Confere quem está logado e o que o token pode fazer. É o primeiro comando a rodar quando qualquer gh começar a dar erro estranho.

10Discussions, Gists, Codespaces, Copilot e Sponsors

Cinco coisas que apareceram no menu o curso inteiro sem a gente parar nelas. Aqui é visão de uso: para que serve e quando vale.

Discussions — o fórum do repositório

Issue é tarefa: nasce para ser fechada. Discussion é conversa: pergunta de uso, ideia crua, enquete, anúncio de versão. Tem thread, categoria e resposta marcada como aceita.

  • Quando vale: quando o seu repositório começa a receber "como eu faço X?" em forma de issue. Ative em Settings → Features → Discussions e a fila de issues volta a ser só trabalho.
  • Como contribuidor: antes de abrir issue num projeto grande, olhe se a pergunta cabe melhor em Discussions. Alguns projetos fecham issue de dúvida na hora.

Gists — o repositório de um arquivo só

Um trecho de código com URL própria, histórico de versões e comentários, sem precisar criar um projeto. Público (aparece na busca) ou secreto (não é listado — mas quem tem o link, entra).

  • Quando vale: mandar um script de setup pra um colega, guardar aquele comando que você sempre esquece, ou anexar um log de 300 linhas num comentário de issue sem entupir a página.
Segredo nenhum em Gist — nem no secreto. "Secret gist" quer dizer "não listado", não "privado". Segredo mora no .env ignorado (aula 01) e nos Secrets do repositório (aulas 09 e 10).

Codespaces — a máquina de desenvolvimento na nuvem

Um ambiente completo rodando no servidor do GitHub, com o VS Code no navegador e o repositório já clonado. O ambiente é descrito num .devcontainer/devcontainer.json versionado junto com o código, então todo mundo abre exatamente a mesma máquina.

  • Quando vale: contribuir com um projeto cujo setup é um pesadelo; trabalhar de um computador que não é o seu; dar aula sem perder duas horas instalando dependência.
  • Cuidado: tem uma cota grátis por mês. Passou dela, cobra por hora de máquina ligada — e ela fica ligada se você só fechar a aba. Pare o codespace quando terminar.

Copilot — sugestão de código no editor

Completa código enquanto você digita, responde perguntas sobre o repositório e faz uma primeira passada de revisão em PR. Grátis na conta de estudante e para quem mantém projeto open source popular.

  • Quando vale: como um estagiário rápido e distraído. Acerta o repetitivo — teste parecido com o anterior, conversão de formato, boilerplate — e inventa o resto com muita confiança.
  • A regra que não muda: o que entra no commit é responsabilidade sua. O seu nome é o que fica no git log. Alguns projetos exigem que você declare o uso no PR — está no CONTRIBUTING.

Sponsors — em uma linha

Botão de doação recorrente no perfil ou no repositório: quem depende do seu trabalho paga por mês para ele continuar existindo. É a resposta do GitHub para a hora em que "de graça, no fim de semana" deixa de dar conta.

Tem muito mais — Pages, Packages, Wiki, Projects, GitHub Apps, a API REST e a GraphQL. Você não precisa conhecer tudo: precisa saber que existe, para procurar no dia em que a necessidade aparecer.

11O ciclo inteiro

Esta é a seção de referência do curso todo. Cada etapa aqui é uma coisa que você já fez com a mão — e a última coluna diz em que aula ela apareceu, para você voltar direto no manual certo.

etapao que aconteceo comando ou a telaaula
0. a máquina Git instalado e assinando com o seu nome. O que nunca deve entrar no histórico já está barrado. git config --global user.name · .gitignore 01
1. issue O trabalho vira texto: o que acontece, o que era esperado, como reproduzir. Label, milestone, responsável, quadro. Aba Issues · gh issue create 05
2. branch Uma linha do tempo só para esse assunto, a partir da main em dia. Nome no padrão do time. git switch -c feat/busca-no-topo 02 · 07
3. commit O ciclo de sempre, um assunto por commit, mensagem que diz por quê — no padrão que gera o changelog depois. git status → add → commit 01 · 07
4. push A branch sai da sua máquina. No projeto do time, para o origin do próprio repositório; no projeto de outra pessoa, para o origin que é o seu fork. git push -u origin minha-branch 03 · 12
5. pull request O pedido de merge, com descrição, Closes #12, revisores e — em fork — a branch base do outro repositório. Botão Compare & pull request · gh pr create 06 · 12
6. checks O robô revisa antes da pessoa: build, lint, testes, Dependabot, secret scanning. Vermelho barra o merge, porque a branch é protegida. .github/workflows/ · gh pr checks 08 · 09
7. review Gente lendo o diff: comentário em linha, sugestão aplicável em um clique, aprovar ou pedir alterações. CODEOWNERS chama quem entende. Aba Files changed · gh pr review 06
8. merge Entra na main — merge commit, squash ou rebase, conforme o combinado. A branch morre aqui. Botão Merge pull request 02 · 06 · 07
9. release Tag anotada, SemVer, changelog vindo dos commits, deploy com secrets e environment — com aprovação manual se for produção. git tag -a v1.2.0 · gh release create 10
10. deu ruim Desfazer sem apagar história: revert no que é compartilhado, reset só no que é seu, bisect pra achar o culpado, reflog pra resgatar o que sumiu. git revert · git reflog 11
É uma volta só, e ela não tem fim. O merge de hoje vira a main em que a branch de amanhã nasce. Todo o resto do curso — organização, permissões, fluxo de trabalho, proteção de branch — existe para essa volta acontecer sem alguém pisar no pé de alguém.

12Por onde seguir depois

Cinco caminhos, na ordem em que costumam aparecer na vida real. Nenhum deles é pré-requisito do outro — pegue o que a sua próxima semana pedir.

monorepo
Vários projetos num repositório só, com workspaces, build compartilhado e paths: nos workflows para rodar só o que mudou. Aparece assim que o time passa de dois repositórios que se conversam.
GitOps
O repositório como fonte da verdade da infraestrutura, não só do código: o estado desejado do cluster está versionado, e um agente aplica o que estiver na main. É a aula 10 levada até o fim.
self-hosted runners
Rodar o Actions da aula 08 em máquina sua, e não na do GitHub. Vale quando o build precisa de hardware específico, de rede interna, ou quando a conta de minutos começa a doer.
GitHub Enterprise
SSO, SAML, auditoria, política de organização em escala e — se for a versão Server — o GitHub inteiro rodando dentro da empresa. É a aula 04 com mil pessoas dentro.
assinar commits
GPG ou SSH provando que o commit é seu mesmo. Lembre que user.name e user.email da aula 01 são texto livre: qualquer pessoa pode commitar com o seu nome. A assinatura fecha esse buraco, e o selo Verified aparece no GitHub.
a API e os Apps
A REST e a GraphQL do GitHub, e os GitHub Apps que automatizam o que o Actions não alcança. Comece pelo gh api — ele já autentica sozinho.
O próximo passo não é uma aula 13. É o segundo Pull Request. Escolha outra issue, no mesmo projeto de hoje — você já conhece a casa, já tem o fork configurado, e o caminho inteiro cabe em quinze minutos agora.

13Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
Meu fork está atrás do original ("This branch is 47 commits behind") O fork é uma foto do dia do clique. O original andou; ele não. git switch main, git fetch upstream, git rebase upstream/main, git push origin main. Pelo site: botão Sync fork — que atualiza só o site, não a sua cópia local.
Abri o PR contra a branch errada O campo base veio com o padrão do repositório, e o projeto usa outra branch. Se o destino é o mesmo repositório, dá para editar o PR e trocar a base. Em PR vindo de fork, não dá: feche, explique em uma linha e abra outro com a mesma branch. Confira o CONTRIBUTING antes.
remote: Permission to dono/projeto.git denied Você clonou o repositório original em vez do seu fork, e está tentando dar push nele. git remote -v: o origin tem que ter o seu usuário. Conserto: git remote set-url origin git@github.com:voce/projeto.git.
fatal: 'upstream' does not appear to be a git repository O git remote add upstream não foi rodado nesta pasta. Rode o remote add da seção 04 e confira com git remote -v.
O PR mostra 200 arquivos alterados e eu mexi em um Ou o seu fork está velho, ou o formatador do editor rodou no projeto inteiro. Rebase na upstream/main primeiro. Se continuar, git diff upstream/main --stat mostra quem entrou de penetra.
Meu PR está aberto há três semanas e ninguém falou nada Não é erro. É o ritmo normal de quem mantém projeto de graça. Um lembrete educado, uma vez. Depois disso, siga a vida — e abra o próximo PR em outro lugar.
Pediram "rebase, por favor" e agora deu conflito A main do original andou por cima do que você mudou. Resolva o conflito como na aula 02, git add, git rebase --continue, e git push --force-with-lease. Se embolar, git rebase --abort volta tudo ao que era.
Commitei na main do fork sem querer Esqueceu do git switch -c antes de mexer. Crie a branch agora — ela nasce onde você está e leva os commits junto —, depois git switch main e git reset --hard upstream/main. Reset aqui é seguro: é o seu fork (aula 11).
Os checks do meu PR não rodam, ficam "waiting" Em muitos projetos, o primeiro PR de uma pessoa precisa de aprovação de um mantenedor para os workflows rodarem. Nada a fazer, só esperar. É proteção contra abuso dos runners (aula 08), não problema seu.
Um robô comentou pedindo pra assinar um CLA O projeto exige o Contributor License Agreement antes do merge. Clique no link, leia, aceite. O robô destrava o PR sozinho depois.
gh: command not found depois de instalar O terminal foi aberto antes de a instalação terminar. Feche e abra o terminal. Depois, gh --version e gh auth status.
gh pr create reclama que não acha o repositório Você não está dentro de uma pasta clonada, ou o remoto não é do GitHub. gh repo set-default dentro da pasta, ou passe --repo dono/projeto na mão.
Meu PR foi recusado Escopo, direção do projeto ou duplicidade — quase nunca a qualidade do seu código. Agradeça, pergunte se existe algo mais útil pra fazer ali, e abra o próximo. O trabalho continua sendo seu.
Antes de pedir ajuda: rode git remote -v e git status e cole as duas saídas. Em contribuição por fork, quase todo problema estranho é um remoto apontando para o lugar errado — e essas duas saídas mostram isso na primeira linha.
