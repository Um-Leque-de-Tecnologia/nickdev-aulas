Open source, ecossistema e o que levar daqui

Hoje você mexe no projeto de outra pessoa — do fork ao Pull Request aberto — conhece o resto do GitHub que ainda não apareceu, e vê o ciclo inteiro das doze aulas numa página só.

deixe aberto: o terminal, a sua conta do GitHub e um projeto que você usa de verdade. hoje a gente contribui pra valer.

use ← → pra navegar · manual desta aula

// o problema

"Eu não posso mexer nisso, não é meu"

Onze aulas depois, você já sabe tudo que é preciso para contribuir com qualquer projeto público do mundo. O que falta não é técnica — é permissão psicológica.

1"Vão descobrir que eu não sei nada." Ninguém revisa você, revisa o diff. E o diff que conserta um link quebrado é um diff válido.
2"Eu não tenho acesso de escrita." Nem precisa. É exatamente para isso que o fork existe.
3"Só vale se for código difícil." Documentação errada, teste faltando e tradução torta são contribuição de verdade — e costumam ser as mais bem-vindas.
4"E se recusarem?" Vão recusar alguma hora. Isso faz parte, e a gente fala disso com honestidade daqui a pouco.

Open source não é um clube com porteiro. É um repositório público onde qualquer pessoa pode abrir um PR — inclusive você, hoje.

// o conceito

O fork é a sua cópia no servidor

Na aula 06 fork e branch apareceram lado a lado. Agora é a hora de usar o fork para valer: quando o repositório não é seu, você não tem onde criar a branch — então cria um repositório que é seu.

🌍
upstreamo projeto original. você lê, mas não escreve
→
🍴
origino seu fork, na sua conta. aqui você manda o que quiser
→
💻
a sua máquinao clone do fork, onde o trabalho acontece

Três cópias do mesmo repositório, em três lugares. O Pull Request é o pedido que atravessa a seta de volta: da sua branch no origin para a branch base do upstream.

// escolher

Que projeto merece a sua primeira vez

Não escolha pela fama. Escolha pelo que você tem chance de entender — e pelos sinais de que tem gente atendendo a porta.

bom sinal

Vale abrir o PR

Commit na última semana. Issues sendo respondidas. Tem CONTRIBUTING.md. Tem LICENSE. PRs recentes com merge, não só abertos. E — decisivo — é uma ferramenta que você usa.

sinal ruim

Guarde para depois

Último commit há dois anos. Trezentos PRs abertos sem resposta. Sem licença — e a aula 04 já disse: sem licença, ninguém tem direito de usar. Ou o extremo oposto: um projeto gigante onde o seu PR é o número 4.000 da fila.

O melhor projeto para começar é aquele em que você já se irritou com alguma coisa. Erro de digitação no README, mensagem de erro confusa, exemplo da documentação que não roda — você achou o bug de graça, sem procurar.

// a regra da casa

Leia o CONTRIBUTING.md antes de digitar

Na aula 04 ele era um arquivo do repositório. Hoje ele é a regra que decide se o seu PR entra ou volta.

projeto/ README.md ← o que é e como usar CONTRIBUTING.md ← como contribuir. leia este CODE_OF_CONDUCT.md ← como se comportar por lá LICENSE ← o que você pode fazer .github/ PULL_REQUEST_TEMPLATE.md ISSUE_TEMPLATE/
1Qual branch base? Nem todo projeto usa main — muitos pedem PR contra develop ou next.
2Como nomear a branch e escrever a mensagem do commit. Vários exigem Conventional Commits, que é a aula 07.
3O que rodar antes de abrir o PR: lint, teste, formatação. É o que os checks da aula 09 vão cobrar de você lá.
4Se o projeto exige issue antes do PR, e se pede para assinar um CLA.
5Não existe CONTRIBUTING? Leia os três últimos PRs com merge. Eles são o manual não escrito da casa.

PR que ignora o CONTRIBUTING dá trabalho ao mantenedor. E trabalho a mais é o motivo número um de um PR ficar parado.

// a porta de entrada

good first issue: a placa de boas-vindas

É uma label — aquilo da aula 05 — que o mantenedor põe na issue que ele acha resolvível por quem nunca abriu aquele código.

a busca, no github.com
is:issue is:open label:"good first issue" no:assignee

# restringindo à sua linguagem e a projetos vivos:
is:issue is:open label:"good first issue" no:assignee
  language:python stars:>500 pushed:>2026-06-01

no:assignee é o filtro que importa: sem ele, metade da lista já tem dono.

1Outros nomes da mesma placa: good-first-issue, help wanted, beginner friendly, E-easy. Cada projeto batiza o seu.
2Leia a issue inteira, com os comentários. Muita issue já foi resolvida e ninguém fechou.
3Issue aberta há três dias e já com quinze comentários? Pule. Aquilo ali já virou fila.
4Não precisa ser da label: qualquer erro que você achou na documentação vale um PR — e esse nem pede issue antes.
// etiqueta

Comente antes de começar

É o passo que quase todo mundo pula — e é o que evita duas pessoas gastarem o fim de semana no mesmo conserto.

assim

"Oi! Posso pegar essa? Pelo que li, é trocar a validação em src/form.js pra aceitar CEP com hífen, e ajustar o teste em form.test.js. É por aí? Consigo abrir o PR até quinta."

Mostra que você leu, propõe um caminho e dá um prazo. O mantenedor responde "manda ver" em dez segundos.

não assim

"assign me"
"can I work on this?"
"+1"
"any update?"

Cinco pessoas escreveram isso na mesma issue e nenhuma voltou. Quem cuida da issue já aprendeu a ignorar essas linhas.

Se ninguém responder em uns dias, comece assim mesmo — avisando no comentário que você vai começar. O silêncio é comum: quase todo mantenedor faz isso de graça, no tempo que sobra.

LAB 1

Achar a sua issue

~10 min

Ainda sem código. Só escolher onde você vai entrar — que é a parte que decide todo o resto.

Liste três projetos que você usa

Biblioteca, CLI, tema do editor, tradução de documentação. Qualquer coisa que já esteja na sua máquina.

Rode a busca no github.com

Troque a linguagem pela sua e abra cinco issues em abas diferentes.

is:issue is:open label:"good first issue" no:assignee
  language:javascript pushed:>2026-06-01

Abra o CONTRIBUTING.md do escolhido

Anote duas coisas: qual é a branch base e o que precisa rodar antes do PR.

Escreva o comentário — e publique

Diga o que você entendeu do problema e o que pretende mudar. Duas linhas bastam.

quando terminar

Diga em voz alta: qual projeto, qual issue e qual é a branch base do PR. Se a terceira você não sabe, volte ao CONTRIBUTING — é o erro que mais faz PR nascer torto.

// os dois remotos

origin e upstream

Na aula 03 você teve um remoto só. Trabalhando em fork são dois — e trocar um pelo outro é a origem de metade da confusão.

terminal
# clonei o MEU fork, então origin já é ele
git clone git@github.com:voce/projeto.git
cd projeto

# o original vira um segundo remoto, chamado upstream
git remote add upstream https://github.com/dono/projeto.git

git remote -v
origin    git@github.com:voce/projeto.git (push)
upstream  https://github.com/dono/projeto.git (fetch)
1origin é sempre o seu fork. É para onde você dá push.
2upstream é o original. Você só faz fetch dele — push ali dá erro de permissão, e está certo que dê.
3O nome upstream é convenção, não regra do Git. Todo tutorial do mundo usa esse, então use também.
4Cuidado com o outro sentido de "upstream": na aula 03 era a branch remota que a sua branch segue. Mesma palavra, coisa diferente.

Puxa do upstream, empurra pro origin. Essa frase resolve quase toda dúvida de fork.

// o fork envelhece

Manter o fork em dia

O fork é uma foto do dia em que você clicou. O projeto continuou andando; o seu fork, não. Duas semanas depois, o seu PR chega cheio de conflito que nem é seu.

antes de criar qualquer branch
git switch main
git fetch upstream                # baixa, não mexe em nada
git rebase upstream/main          # põe a main igual à do original
git push origin main              # atualiza o fork no site

# e aí sim a branch nasce em dia:
git switch -c fix/cep-com-hifen

Se o PR já está aberto e o mantenedor pedir "rebase, por favor": faça o mesmo com a sua branch e depois git push --force-with-lease.

1Faça isso toda vez que for começar algo novo. Custa cinco segundos.
2Na sua main de fork, rebase é seguro: ninguém mais usa aquela branch. É a exceção honesta à regra da aula 11.
3Nunca trabalhe na main do fork. Uma branch por contribuição — senão o segundo PR carrega o primeiro junto.
4No site existe o botão Sync fork, que faz o mesmo pela interface. Só que ele não atualiza a sua cópia local.
parada obrigatória

Sem seguir sem responder

Quatro perguntas. As três primeiras são desta aula; a quarta é do curso inteiro.

1Você deu git push origin. O código foi para o projeto original ou para o seu fork?
2Por que se lê o CONTRIBUTING antes de escrever a primeira linha?
3O seu fork está três semanas atrás do original. Quais comandos resolvem — e de qual remoto eles puxam?
4Um check vermelho barrou o merge do seu PR. Em que aulas isso foi configurado?

respostas: 1 — pro seu fork, sempre; 3 — git fetch upstream e git rebase upstream/main; 4 — branch protection é a 07, o check obrigatório é a 09.

// mão na massa
LAB 2

Do fork até a branch pronta

~14 min

Agora é a sua vez de montar o triângulo: original, fork e máquina.

Fork pelo botão

No repositório escolhido, canto superior direito: Fork. Ele nasce em github.com/voce/projeto.

Clone o seu fork — não o original

Se você clonar o original por engano, o push vai falhar lá na frente.

git clone git@github.com:voce/projeto.git
cd projeto

Adicione o upstream e confira

Dois remotos devem aparecer. Se só aparecer origin, o comando não pegou.

git remote add upstream https://github.com/dono/projeto.git
git remote -v

Sincronize e crie a branch

Use o nome que o CONTRIBUTING pedir; na dúvida, o padrão da aula 07.

git fetch upstream
git switch main
git rebase upstream/main
git switch -c fix/link-quebrado-no-readme

Faça a mudança, commite e empurre

Uma mudança pequena e completa. Depois do push, o GitHub mostra um botão de abrir PR.

git commit -am "docs: corrige link da seção de instalação"
git push -u origin fix/link-quebrado-no-readme
quando terminar

O git remote -v tem que mostrar dois nomes diferentes. Se origin apontar para o repositório do dono, refaça o clone — daqui pra frente tudo dá errado por causa disso.

// o pedido

O PR que atravessa dois repositórios

Abrir e revisar PR foi a aula 06 — aqui muda uma coisa só, e é justamente onde todo mundo tropeça: o PR sai do seu fork e entra no repositório do outro.

o cabeçalho do PR, no site
base repository: dono/projeto   base: main
                                    ↑ o destino

head repository: voce/projeto   compare: fix/link-quebrado-no-readme
                                    ↑ a sua branch, no seu fork

Confira essa linha antes de clicar em criar. PR aberto contra a branch errada não se corrige: fecha e abre outro.

1Marque Allow edits by maintainers. É o que deixa o mantenedor dar um retoque em vez de te devolver o PR por uma vírgula.
2Escreva a descrição pensando em quem não estava na sua cabeça: o que quebrava, o que você mudou, como testar.
3Closes #123 só fecha a issue se o PR for para o mesmo repositório da issue — e aqui é. Aula 06.
4Os checks da aula 09 vão rodar no seu PR. Em muitos projetos, o primeiro PR de alguém precisa de aprovação para os workflows rodarem — espere.
// honestidade

Agora vem a parte que ninguém conta

O PR está aberto. E aí, provavelmente, não acontece nada durante um bom tempo.

Pode demorar semanas

Quem mantém o projeto quase sempre faz isso de graça, depois do trabalho. Duas, três semanas de silêncio é normal — não é desprezo.

Pode virar dez comentários

Revisão detalhada é investimento em você: ninguém gasta meia hora comentando um PR que pretende ignorar. Responda tudo, mesmo que seja "boa, corrigi".

Pode ser recusado

"Não é a direção do projeto", "isso já está em outro PR", "aqui a gente resolve de outro jeito". Nenhuma dessas frases é sobre a sua competência.

1Um lembrete educado depois de duas semanas é aceitável, e só um: "oi, tem algo que eu possa ajustar aqui?".
2Se pedirem mudança, não abra outro PR: commite na mesma branch e dê push. O PR se atualiza sozinho.
3PR recusado continua no seu histórico e continua sendo trabalho seu. E a próxima issue daquele projeto você já lê como quem conhece a casa.

Você não está sendo avaliado — está oferecendo um presente. Quem recebe presente escolhe se cabe na casa.

// ecossistema · gh

GitHub CLI: o site, sem o site

O gh é o programa oficial do GitHub para o terminal. Ele não substitui o Git — ele faz a parte que o Git nunca soube fazer: issue, PR, release, workflow.

instalar e entrar
# macOS: brew install gh
# Windows: winget install GitHub.cli
# Linux: veja cli.github.com

gh auth login
? What account do you want to log into? GitHub.com
? Preferred protocol for Git operations? SSH
? Authenticate Git with your GitHub credentials? Yes
✓ Logged in as voce
1O gh auth login resolve a autenticação da aula 03 de uma vez: chave SSH e credencial do Git, no mesmo passo.
2Ele sabe em que repositório você está. Dentro da pasta clonada, quase nenhum comando precisa dizer qual é o projeto.
3Vale mais quando você já sabe o que ia clicar. Não aprenda o gh antes de entender a tela que ele imita.
4gh não é obrigatório em lugar nenhum. É conforto — e conforto que economiza uns dez minutos por dia.

LAB 3

Abrir o PR sem sair do terminal

~10 min

A mesma coisa do LAB 2, agora em quatro linhas. Se você já abriu o PR pelo site, use os comandos de leitura no lugar.

Instale e entre

Escolha SSH quando ele perguntar o protocolo, e deixe ele configurar o Git também.

gh auth login
gh auth status

Ache uma issue pela linha de comando

Sem --repo ele usa o repositório da pasta em que você está.

gh issue list --repo dono/projeto --label "good first issue"
gh issue view 123 --repo dono/projeto

Abra o PR a partir da sua branch

--fill aproveita a mensagem do commit como título e corpo. --web abre no navegador pra revisar antes de enviar.

gh pr create --base main --fill --web

Acompanhe sem abrir o navegador

O --watch fica na tela até o último check terminar.

gh pr status
gh pr checks --watch
quando terminar

Cole no chat o link que o gh pr create devolveu. É a sua primeira contribuição open source — e ela existe mesmo que o merge demore um mês.

// ecossistema

Discussions e Gists

discussions

O fórum do repositório

Issue é tarefa: nasce para ser fechada. Discussion é conversa: pergunta de uso, ideia crua, enquete, anúncio de versão. Tem thread, resposta marcada como aceita e categoria.

Quando vale: quando o seu repositório começa a receber "como eu faço X?" como issue. Ative em Settings → Features, e a fila de issues volta a ser só trabalho.

gists

O repositório de um arquivo só

Um trecho de código com URL, histórico de versões e comentários — sem criar projeto para isso. Público ou secreto (secreto = link não listado, não é privado de verdade).

Quando vale: mandar um script de setup para um colega, guardar aquele comando que você sempre esquece, anexar um log inteiro num comentário de issue sem entupir a página.

Nenhum segredo em Gist — nem no secreto. Quem tiver o link, entra. Segredo é .env e Secrets do repositório, como na aula 09.

// ecossistema

Codespaces, Copilot e Sponsors

☁️ Codespaces

Um computador de desenvolvimento na nuvem, com o VS Code no navegador e o repositório já clonado. O ambiente vem descrito num .devcontainer/ versionado junto com o código.

Quando vale: contribuir num projeto cujo setup é um pesadelo, dar aula sem perder duas horas instalando, ou revisar de um computador que não é o seu. Tem cota grátis por mês; passou dela, cobra por hora.

🤖 Copilot

Sugestão de código dentro do editor, revisão automática de PR e chat sobre o repositório. Grátis para conta de estudante e para quem mantém projeto open source popular.

Quando vale: como quem tem um estagiário rápido e distraído. Ele acerta o repetitivo e inventa o resto com muita confiança — o que entra no commit continua sendo responsabilidade sua.

💜 Sponsors

Botão de doação recorrente no perfil ou no repositório: quem depende do seu trabalho paga por mês para ele continuar existindo.

Quando vale: a hora em que "de graça, no fim de semana" deixa de dar conta.

Tem muito mais — Pages, Packages, Wiki, Projects, Apps, API. Você não precisa conhecer tudo; precisa saber que existe, para procurar no dia em que a necessidade aparecer.
