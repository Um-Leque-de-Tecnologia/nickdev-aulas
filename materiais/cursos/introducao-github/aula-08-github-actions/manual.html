GitHub Actions: a primeira automação

O passo a passo para você montar sozinha o seu primeiro pipeline: criar o .github/workflows/ci.yml do zero, ver ele rodar a cada push e a cada Pull Request, quebrar de propósito e ler o log, acrescentar matriz de versões e cache — e terminar com o badge de status no README.

Antes de começar

01O que você vai fazer aqui

Este manual é o passo a passo da aula 08 para você refazer sozinha, do começo, sem depender da gravação. No fim dele o seu repositório tem um workflow que roda o build e os testes a cada push e a cada Pull Request, em três versões de Node, com cache — e um badge verde no topo do README.

Você vai precisar de:

  • Um repositório seu no GitHub, com package.json e package-lock.json commitados.
  • Um script de teste que funcione. Se o projeto ainda não tem testes, vale um "test": "node --test" ou qualquer comando que termine bem.
  • A main protegida desde a aula 07 — então todo trabalho acontece em branch, como já é o hábito desde a aula 06.
  • Uns 45 minutos.
Importante: nesta aula o robô só avisa. Quando um check ficar vermelho no seu Pull Request, o botão de merge continua clicável — o GitHub não trava nada por conta própria. Transformar esse ✗ em check obrigatório, amarrado na branch protection da aula 07, é a aula 09. Se você fizer merge com o check vermelho hoje, o GitHub deixa. E está certo assim.

Os exemplos são em Node.js, mas o desenho é o mesmo em qualquer stack. Troque actions/setup-node + npm ci por actions/setup-java + mvn verify, ou actions/setup-python + pytest: evento, job, runner e steps não mudam uma vírgula. O assunto aqui é o processo, não a linguagem.

02Por que existe integração contínua

A cena é sempre a mesma. Você roda os testes, tudo verde, empurra. Duas horas depois alguém baixa o seu código e nada funciona:

você@casa ~/projeto $ npm test ✓ 14 testes passaram em 2.1s você@casa ~/projeto $ git push # ...duas horas depois, na máquina de outra pessoa colega@trabalho ~/projeto $ npm test ✗ Cannot find module 'dayjs'

Você não mentiu: na sua máquina funciona mesmo. Só que a sua máquina tem anos de coisa instalada que o repositório não tem. As causas mais comuns:

  • Você instalou uma dependência e esqueceu de commitar o package.json.
  • Você está no Node 22; o servidor de produção roda Node 18.
  • Um arquivo de que o build precisa está no seu disco — e no .gitignore.
  • Ninguém rodou os testes antes do merge. Ninguém nunca roda.

Integração contínua é a resposta: toda vez que alguém integra código ao tronco, uma máquina neutra e vazia clona o repositório, instala só o que está commitado, roda o build e os testes, e diz verde ou vermelho. Contínua porque acontece a cada mudança, não uma vez por mês.

A conta que importa: um erro descoberto em três minutos custa um comentário no PR. O mesmo erro descoberto três semanas depois custa uma reunião e uma investigação. O pipeline não existe pra ser bonito — existe pra encurtar essa distância.

Na aula 07 você protegeu a main e passou a exigir revisão de gente. O CI entra antes dessa revisão: quando a pessoa abre o seu PR, o robô já rodou tudo e deixou o log linkado. Ela revisa o desenho da solução, que é o que só ela sabe fazer.

03Onde mora e o vocabulário

Um workflow do GitHub Actions é um arquivo .yml versionado dentro do próprio repositório. Não tem painel pra configurar nem servidor pra alugar — quem clonar o projeto leva o pipeline junto.

meu-projeto/
  .github/
    workflows/
      ci.yml            ← o robô desta aula mora aqui
      deploy.yml        ← outro robô, outro assunto (aula 10)
  src/
  package.json
  package-lock.json
  README.md
O caminho é literal: .github/workflows/ — com ponto na frente, no plural, na raiz do repositório. Um caractere fora e o GitHub simplesmente não enxerga o arquivo: sem erro, sem aviso, aba Actions vazia. O nome do .yml, esse sim, é livre.

Cinco palavras e você lê qualquer workflow

workflow
O arquivo inteiro: uma receita automatizada, com nome.
evento (on:)
O gatilho. O que precisa acontecer no repositório para a receita começar: um push, um PR aberto, um horário, um clique.
job
Um bloco de trabalho que roda numa máquina só. Dois jobs rodam em paralelo, em máquinas diferentes, e não compartilham nada entre si.
step
Uma linha da receita, dentro do job. Rodam em ordem, de cima para baixo. Se um falha, os de baixo nem começam.
runner
A máquina que executa o job. O GitHub liga uma virgem para você, roda, e destrói no fim.
action (uses:)
Um step pronto que alguém já escreveu e publicou. Você chama pelo nome em vez de reescrever.

A hierarquia, numa frase: um workflow reage a um evento, tem um ou mais jobs, cada job roda num runner e é feito de steps — que são comando seu (run:) ou action de terceiro (uses:).

YAML em 30 segundos

Não é uma linguagem de programação: é um formato de dados. Três regras resolvem 100% do que você vai escrever hoje.

  1. A indentação é a estrutura. O que está mais à direita pertence ao que está acima e à esquerda.
  2. Só espaços. Tab é erro de sintaxe em YAML — não é preciosismo, é o padrão. Dois espaços por nível.
  3. Traço é item de lista. - name: ... abre um item; as linhas seguintes daquele item alinham com o name, não com o traço.
Antes de escrever: ligue no seu editor a conversão de Tab em espaço para arquivos .yml. No VS Code é "editor.insertSpaces": true com "editor.tabSize": 2. Isso sozinho evita metade dos erros desta aula.
O primeiro workflow

04Criar o ci.yml do zero

Comece por uma branch — a main está protegida desde a aula 07 — e crie a pasta com o caminho exato.

git switch -c ci/primeiro-workflow
mkdir -p .github/workflows
touch .github/workflows/ci.yml

Confirme que o caminho ficou certo antes de escrever qualquer coisa dentro:

$ ls .github/workflows ci.yml

O arquivo inteiro, comentado

Abra o ci.yml e cole isto. Cada comentário explica a linha de cima — pode deixar os comentários no arquivo, eles não atrapalham nada.

.github/workflows/ci.yml
# O nome que aparece na aba Actions. Escolha um curto.
name: CI

# O EVENTO: quando este workflow deve rodar.
on:
  # toda vez que alguém empurra commits para a main
  push:
    branches: [main]
  # e toda vez que um Pull Request mira a main —
  # inclusive a cada commit novo dentro de um PR já aberto
  pull_request:
    branches: [main]

# Os JOBS. Cada um roda numa máquina própria, em paralelo.
jobs:
  # "build" é um id que você inventa. Só precisa ser único no arquivo.
  build:
    # O nome legível do job, que aparece na interface.
    name: Build e testes

    # O RUNNER: a máquina virgem que o GitHub liga para você.
    # Também existem windows-latest e macos-latest.
    runs-on: ubuntu-latest

    # Os STEPS, executados em ordem, de cima para baixo.
    steps:
      # A ACTION de checkout clona o seu repositório dentro do runner.
      # O runner nasce vazio: sem este step não existe código nenhum lá.
      - name: Baixar o código
        uses: actions/checkout@v4

      # Instala o Node e coloca o npm no PATH da máquina.
      - name: Instalar o Node
        uses: actions/setup-node@v4
        with:
          node-version: "20"

      # "run" é comando seu, rodando no shell do runner.
      # npm ci (e não npm install) instala exatamente o lockfile.
      - name: Instalar dependências
        run: npm ci

      # Se este comando sair com código diferente de zero,
      # o step falha e o job inteiro fica vermelho.
      - name: Rodar os testes
        run: npm test

Confira a indentação antes de commitar

Olhe as colunas, não as palavras. Este é o esqueleto que precisa bater:

colunao que fica aliexemplo
0 espaçosas três chaves de toponame:, on:, jobs:
2 espaçoso id do jobbuild:
4 espaçosas chaves do jobname:, runs-on:, steps:
6 espaçoso traço que abre cada step- name: Baixar o código
8 espaçosas demais chaves do stepuses:, run:, with:
10 espaçosos parâmetros dentro do with:node-version:
Um step tem ou uses, ou run. Nunca os dois no mesmo step. uses chama código que outra pessoa publicou; run é um comando de shell escrito por você.

por que o @v4 no fim da action

actions/checkout@v4 quer dizer: dono actions (a própria GitHub), repositório checkout, versão v4. Prenda sempre a versão. Sem isso, quem mantém a action muda o comportamento do seu pipeline sem você tomar conhecimento.

05Commitar e ver rodar

Conventional Commits, como na aula 07. Isto é infraestrutura de repositório, então o prefixo é ci:.

git add .github/workflows/ci.yml
git commit -m "ci: roda build e testes a cada push e PR"
git push -u origin ci/primeiro-workflow

Antes de sair da linha de comando, confirme que o arquivo foi mesmo commitado no caminho certo. Este comando lista o que o Git rastreia dentro de .github:

$ git ls-files .github .github/workflows/ci.yml
Se essa saída vier vazia, o arquivo não está no repositório e nada vai rodar. Os suspeitos, em ordem: você criou github/ sem o ponto; criou workflow/ no singular; ou criou a pasta dentro de uma subpasta em vez da raiz.

Abra o Pull Request

Vá ao repositório no GitHub. Vai aparecer a faixa amarela oferecendo Compare & pull request. Abra o PR mirando a main, como na aula 06.

Assim que o PR abre, duas coisas acontecem sozinhas:

  1. Uma caixa nova aparece embaixo dos commits, com o nome do job e uma bolinha amarela girando.
  2. A aba Actions do repositório ganha uma execução nova, com o título do seu commit.

Clique em Details ao lado do job para ir direto ao log ao vivo.

Rodou duas vezes? É normal e é esperado. O push na branch e o pull_request são eventos diferentes — e testam coisas diferentes: o pull_request roda sobre a sua branch já combinada com a main (o resultado do merge que ainda não aconteceu), e o push na main roda sobre o que ficou depois que o merge aconteceu.

06Ler a aba Actions

A aba Actions tem três níveis, e vale saber em qual você está. Da esquerda para a direita, é o mesmo caminho de clique:

Actions
  CI                                    ← o name: do workflow
    ✓ ci: roda build e testes...   #7   ← a EXECUÇÃO (run), pelo título do commit
        ✓ Build e testes   1m 04s       ← o JOB
             ✓ Set up job
             ✓ Baixar o código          ← os STEPS, cada um com o seu log
             ✓ Instalar o Node
             ✓ Instalar dependências
             ✓ Rodar os testes
             ✓ Complete job
    ✗ feat: filtro de busca        #6
    ✓ docs: ajusta o README        #5

Os steps Set up job e Complete job você não escreveu: o GitHub põe sozinho, para ligar e desligar a máquina. Clique em qualquer step para abrir o log dele.

coro que quer dizero que fazer
✓ verdeTodos os steps passaram.Nada. Mas vale abrir e olhar o tempo de cada step — é assim que você descobre o gargalo antes de ele incomodar.
✗ vermelhoUm step terminou com código diferente de zero. Os de baixo nem começaram.Abrir o step com ✗ e ler. É a seção 07.
🟡 amareloEstá rodando agora.Dá para acompanhar o log ao vivo, linha por linha, sem esperar acabar.
cinzaCancelado, ou pulado por um if: que deu falso.Ler o motivo no topo da execução.
Botões úteis no canto superior direito da execução: Re-run all jobs refaz tudo (bom quando você desconfia de instabilidade de rede), e Re-run failed jobs refaz só o que quebrou. Nenhum dos dois muda o seu código — rodam o mesmo commit de novo.
Quando fica vermelho

07Quebrar de propósito e ler o log

Um pipeline em que você nunca viu o vermelho é um pipeline em que você não confia. Então vamos quebrar de propósito, ainda na mesma branch, e voltar atrás depois.

Aviso: este passo vai deixar o seu PR vermelho de propósito. É isso mesmo. No fim da seção você desfaz e ele volta ao verde sozinho.

1. Escreva um teste que não tem como passar

cat > src/quebra.test.js <<'FIM'
test('quebra de propósito', () => {
  expect(2 + 2).toBe(5);
});
FIM

2. Empurre e espere o vermelho

git add src/quebra.test.js
git commit -m "test: quebra proposital pra ler o log"
git push

O PR já está aberto, então você não precisa fazer mais nada: o commit novo dispara o workflow outra vez, sozinho.

3. Abra o step com ✗

Não leia o log de cima para baixo. Vá direto no step marcado com ✗ — o GitHub já abre esse expandido — e leia as últimas linhas:

▸ Instalar dependências ✓ 8s ▾ Rodar os testes ✗ 4s Run npm test FAIL src/quebra.test.js ● quebra de propósito expect(received).toBe(expected) Expected: 5 Received: 4 at Object.<anonymous> (src/quebra.test.js:2:17) Tests: 1 failed, 13 passed, 14 total Error: Process completed with exit code 1.
A armadilha: Error: Process completed with exit code 1 não é o erro. É o robô contando que o comando terminou mal. O erro de verdade está algumas linhas acima — aqui, o Expected: 5 / Received: 4.

Toda vez que ficar vermelho, responda estas três perguntas nesta ordem:

  1. Qual step quebrou? Instalação, build e teste falham por motivos completamente diferentes. Se quebrou no npm ci, o problema é de dependência e nem chegou no seu código.
  2. Qual é a mensagem de erro real? Procure a última linha que fala de arquivo e número de linha, não a última linha do log.
  3. Dá para reproduzir aqui? Rode na sua máquina exatamente o comando que está no run: que falhou. Se passar aqui e falhar lá, a diferença é ambiente — versão, dependência não commitada ou arquivo ignorado.

4. Conserte e veja voltar ao verde

rm src/quebra.test.js
git commit -am "test: remove a quebra proposital"
git push

O mesmo PR fica verde sozinho, sem você clicar em nada. Esse é o ciclo inteiro: empurrou, rodou, avisou.

Deixar o pipeline bom

08Matriz de versões

Você promete no README que o projeto roda no Node 18, 20 e 22. Com um job só, você torce. Com strategy.matrix, você sabe: o GitHub cria um job por valor da lista e roda todos em paralelo, em máquinas separadas.

Acrescente o bloco strategy entre o runs-on: e o steps:, e troque o node-version fixo pela referência à matriz:

.github/workflows/ci.yml — só o job
jobs:
  build:
    runs-on: ubuntu-latest

    strategy:
      # sem isto, a primeira versão que falhar cancela as outras
      fail-fast: false
      matrix:
        # "node" é um nome que você inventa. Vira uma variável.
        node: [18, 20, 22]

    # o nome do job passa a mostrar a versão: "Node 18", "Node 20"...
    name: Node ${{ matrix.node }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          # cada job recebe um valor diferente da lista
          node-version: ${{ matrix.node }}

      - run: npm ci
      - run: npm test
A sintaxe ${{ ... }} é como o GitHub Actions lê um valor em tempo de execução. Aqui ela pega o valor daquele job na matriz. Dá para usar em quase qualquer campo do YAML — e é a mesma sintaxe que aparece nos secrets, na aula 10.
Não pule o fail-fast: false. O padrão é true: assim que um job da matriz falha, o GitHub cancela os outros. Você fica sabendo que quebrou no Node 18 e sem saber se o 20 e o 22 estavam bem — que é justamente a informação que faz diferença.

Empurre e volte na aba Actions. A execução agora tem três jobs em vez de um, rodando ao mesmo tempo. O tempo de relógio é quase o mesmo — você ganhou duas respostas de graça.

outras matrizes úteis

A matriz não é só de versão de linguagem. Duas listas juntas viram a combinação de todas com todas — 3 × 2 = 6 jobs:

      matrix:
        node: [18, 20, 22]
        os: [ubuntu-latest, windows-latest]
Cuidado com o tamanho. Matriz cresce por multiplicação, e cada job é uma máquina. Seis jobs por push é a diferença entre um pipeline útil e um pipeline que consome a cota do repositório à toa. Comece pequeno.

09Cache de dependências

O runner nasce vazio toda vez. Sem cache, o npm ci baixa as mesmas centenas de pacotes em cada execução, e isso costuma ser o step mais demorado do pipeline inteiro.

sem cache

Instalar dependências added 812 packages in 47s total do job: 1m 12s

com cache

Instalar dependências Cache restored from key: node-a3f9... added 812 packages in 6s total do job: 0m 24s

E ligar custa uma linha, porque a própria actions/setup-node faz o serviço:

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          # a chave do cache sai do package-lock.json, sozinha
          cache: "npm"

Como funciona: a action calcula um hash do lockfile e usa isso como chave. Se o package-lock.json não mudou, ela restaura a pasta de cache e o npm ci voa. Se mudou uma dependência, a chave muda, o cache é refeito e a próxima execução já aproveita.

Por que npm ci e não npm install: o ci apaga o node_modules e instala exatamente o que está no lockfile, sem atualizar nada. É isso que torna a execução reprodutível — e é por isso que ele falha na hora se o lockfile estiver faltando ou desatualizado, em vez de consertar em silêncio.

Na primeira execução depois de ligar o cache você vai ver Cache not found no log. Está certo: não havia nada guardado ainda. O ganho aparece da segunda em diante.

10Artefatos

O runner é destruído no fim do job. Tudo que ele produziu — a pasta dist/, o relatório de cobertura, o print do teste que falhou — evapora junto, a menos que você peça para guardar. É para isso que serve um artefato.

      - name: Guardar o build
        uses: actions/upload-artifact@v4
        # guarde mesmo se um step anterior falhou
        if: always()
        with:
          # o nome que aparece no botão de download
          name: build-dist
          # o que empacotar: arquivo, pasta ou padrão
          path: dist/
          # some sozinho depois de uma semana
          retention-days: 7

O arquivo aparece para download na página da execução, lá embaixo, num quadro chamado Artifacts. Vale a pena guardar:

  • o build pronto, para conferir o que saiu do forno sem precisar buildar de novo;
  • o relatório de cobertura em HTML;
  • o log de teste completo, quando a saída do terminal é grande demais para ler;
  • o screenshot do teste de interface que falhou.
O if: always() é o detalhe que separa quem já sofreu. Sem ele, o step é pulado quando algo antes falha — e o artefato mais útil é justamente o do job que quebrou. Se você só vai lembrar de uma linha desta seção, lembre desta.
Artefato não é lugar de segredo. Em repositório público, qualquer pessoa baixa o que você subir ali. Chave, token e .env têm um mecanismo próprio — secrets — e é assunto da aula 10.

11Pipeline rápido é pipeline usado

Isto não é papo de performance. É comportamento humano, e mata mais CI do que qualquer bug:

tempo do pipelineo que as pessoas fazem
até 5 minVocê espera olhando. O erro é consertado enquanto você ainda lembra do que fez. Saudável.
10 minVocê troca de tarefa e volta depois, com a cabeça em outro lugar.
25 minVocê faz merge sem olhar. "Depois eu vejo." Ninguém vê depois.
40 min ou maisNasce o "esse teste sempre falha, ignora". O vermelho vira paisagem. O pipeline morreu — só ninguém desligou.

Um CI vermelho que o time aprendeu a ignorar é pior que nenhum CI: dá a sensação de segurança sem a segurança. O que segura o tempo, em ordem de retorno:

  1. Cache de dependências. Uma linha, e costuma cortar metade do tempo. É a seção 09.
  2. Jobs em paralelo, não steps em série. Lint e teste não dependem um do outro: em jobs separados eles rodam ao mesmo tempo, e o total passa a ser o do mais lento, não a soma dos dois.
  3. Só o necessário em cada evento. O teste de ponta a ponta, que é caro, pode rodar só no push para a main. O teste unitário roda em tudo.
  4. Olhe o cronômetro de cada step. A aba Actions mede todos, e o gargalo quase nunca é onde você acha que é. Meça antes de otimizar.
Regra prática: se o pipeline passar de dez minutos, pare de acrescentar coisa nele e vá cortar tempo. Um pipeline de cinco minutos que roda sempre vale mais que um de trinta que ninguém espera.

12O badge no README

O badge é uma imagem que o GitHub desenha na hora, dizendo se a branch padrão está passando. Quem chega no repositório descobre isso antes de clonar.

Coloque no topo do README.md, logo abaixo do título, trocando usuario/repo pelo seu:

README.md
# Meu Projeto

![CI](https://github.com/usuario/repo/actions/workflows/ci.yml/badge.svg)

A anatomia da URL, da esquerda para a direita:

pedaçoo que é
usuario/repoO seu usuário (ou a organização) e o nome do repositório.
actions/workflows/Fixo. Não mude.
ci.ymlO nome do arquivo do workflow — não o name: que está dentro dele. É o erro mais comum aqui.
/badge.svgFixo. É o que faz o GitHub devolver a imagem.
?branch=mainOpcional, no fim de tudo. Fixa o badge numa branch específica.

São três estados possíveis:

estadoo que significa
passingA última execução na branch padrão passou. É o que você quer ver.
failingA main está quebrada agora. Isso é um chamado, não um enfeite.
no statusO caminho do arquivo na URL está errado, ou o workflow ainda não rodou na branch padrão nenhuma vez.
Se o badge estiver no status logo depois do LAB, é quase sempre a segunda causa: o seu workflow só rodou na branch do PR. Depois que o PR entrar na main, ele roda lá e o badge acende. O README ganhou seções de verdade na aula 04 — este é só mais um morador.

13Cola de YAML

Tudo que apareceu nesta aula, numa tabela só.

chaveo que faz
name:No topo, o nome do workflow. Dentro do job ou do step, o nome legível daquele bloco.
on:O evento que dispara. Abre o bloco de gatilhos.
on.pushDispara quando alguém empurra commits.
on.pull_requestDispara na abertura do PR e a cada commit novo nele.
on.scheduleDispara por horário, em sintaxe cron (UTC).
on.workflow_dispatchCria um botão "Run workflow" na aba Actions.
jobs:Abre a lista de jobs. Cada job roda numa máquina própria.
runs-on:O runner. ubuntu-latest, windows-latest ou macos-latest.
steps:A lista ordenada de passos do job.
uses:Chama uma action pronta. Sempre com a versão presa: @v4.
run:Roda um comando de shell seu no runner.
with:Os parâmetros da action do uses daquele step.
if:Condição para o step rodar. always() roda mesmo depois de falha.
strategy.matrixMultiplica o job por uma lista de valores.
strategy.fail-fastfalse impede que uma falha cancele os outros jobs da matriz.
actions/checkout@v4Clona o seu repositório dentro do runner. Sempre o primeiro step.
actions/setup-node@v4Instala o Node. Com cache: "npm", também guarda as dependências.
actions/upload-artifact@v4Guarda arquivos do runner para download depois.
O que fica para as próximas: tornar esse check obrigatório para o merge, além de lint, Dependabot e scanning de segurança, é a aula 09. Publicar de verdade — deploy, secrets, environments e aprovação manual — é a aula 10. E a proteção de branch que já está ligada na sua main veio da aula 07, se você precisar rever.

O workflow não aparece na aba Actions (aba vazia, nenhum erro) Caminho ou nome do arquivo errado. O GitHub só olha em .github/workflows/ — e falha em silêncio se não achar. git ls-files .github. Tem que sair .github/workflows/ci.yml. Cheque o ponto em .github, o plural em workflows, a extensão .yml e se a pasta está na raiz do repositório.
O arquivo está no lugar certo e mesmo assim nada roda Ele foi criado mas não commitado, ou o commit ficou numa branch que você não empurrou. git status e git log --oneline -1. Se o arquivo aparece como não rastreado, falta git add e git push.
Invalid workflow file apontando uma linha Erro de indentação de YAML. Na esmagadora maioria das vezes é um Tab no lugar de espaços — YAML não aceita Tab. Abra a linha citada e as duas acima. Troque todo Tab por espaço (dois por nível) e confira as colunas contra a tabela da seção 04.
O YAML "está igual ao do manual" e continua inválido Colar de um PDF ou de um slide traz espaço não separável e aspas curvas no lugar das retas. Use o botão copiar dos blocos deste manual. Se já colou, reescreva a linha na mão.
npm: command not found Faltou o step do actions/setup-node, ou ele veio depois do npm ci. Steps rodam em ordem: checkout, setup-node, e só então os run:.
Erro no primeiro step: não achou nenhum arquivo Faltou o actions/checkout. O runner nasce vazio, sem uma linha do seu código. Ponha - uses: actions/checkout@v4 como primeiro step do job.
npm ci reclama que não achou o lockfile O package-lock.json está no .gitignore, ou nunca foi commitado. Tire do .gitignore e commite. O lockfile deve ir para o repositório — é ele que torna a instalação reprodutível.
npm ci reclama que o lockfile está fora de sincronia Alguém editou o package.json na mão sem regenerar o lock. Rode npm install na sua máquina e commite o package-lock.json junto.
Passa na minha máquina e quebra no runner Versão de linguagem diferente, dependência instalada só localmente, ou arquivo ignorado de que o build precisa. Compare o node-version do workflow com o seu node -v. Rode git status e veja se falta commitar algo. Depois rode na mão o comando do run: que falhou.
O log é enorme e eu não acho o erro Você está lendo de cima para baixo. Clique no step com ✗ e leia as últimas linhas antes do exit code 1. Essa linha final não é o erro — é só o aviso de que o comando terminou mal.
A matriz roda mas só uma versão aparece no fim O fail-fast está no padrão (true) e uma falha cancelou as outras. Acrescente fail-fast: false dentro do strategy.
O cache não acelerou nada Primeira execução depois de ligar: não havia o que restaurar. O log diz Cache not found. Nada a consertar. Empurre mais um commit e compare a segunda execução com a primeira.
O badge aparece como no status O nome do arquivo na URL está errado, ou o workflow ainda não rodou na branch padrão. Confira que o pedaço final é o nome do arquivo (ci.yml), não o name: de dentro dele. Se estiver certo, espere o PR entrar na main.
O check ficou vermelho e o merge liberou assim mesmo Esperado. Nesta aula o check só informa. Não há o que consertar — está certo. Tornar o check obrigatório é a aula 09.
O workflow roda duas vezes no mesmo commit push e pull_request valendo para a mesma branch que está em PR. Não é erro, e as duas execuções testam coisas diferentes. Se incomodar, limite o push a branches: [main].
Antes de pedir ajuda: diga em qual step quebrou e cole as últimas dez linhas daquele step — não o log inteiro nem só o exit code 1. Com essas duas informações, quase toda dúvida de CI vira uma resposta de uma linha.
