GitHub Actions: a primeira automação

No fim de hoje o seu repositório tem um robô contratado. A cada push e a cada Pull Request ele pega o código numa máquina limpa, instala, roda o build e o teste — e escreve na tela se passou ou se quebrou.

deixe aberto: um repositório seu no GitHub, com package.json e a main protegida desde a aula 07.

use ← → pra navegar · manual desta aula

// o problema

"Na minha máquina funciona"

A frase mais cara do desenvolvimento de software. E o pior é que ela quase sempre é verdade — é justamente esse o problema.

você@casa ~/projeto $ npm test ✓ 14 testes passaram em 2.1s você@casa ~/projeto $ git push # ...duas horas depois, na máquina de outra pessoa colega@trabalho ~/projeto $ npm test ✗ Cannot find module 'dayjs'
1Você instalou o dayjs e esqueceu de commitar o package.json.
2Você está no Node 22; o servidor de produção roda Node 18.
3Um arquivo de que o build precisa está no seu disco — e no .gitignore.
4Ninguém rodou os testes antes do merge. Ninguém nunca roda.

A sua máquina tem anos de sujeira acumulada que o repositório não tem. Só uma máquina limpa diz a verdade sobre o seu código.

// o conceito

Integração contínua

Toda vez que alguém integra código ao tronco, uma máquina neutra recomeça o projeto do zero e confere se ele ainda funciona.

Contínua quer dizer: a cada mudança, não uma vez por mês. Um erro descoberto em três minutos custa um comentário. O mesmo erro descoberto três semanas depois custa uma reunião.

// de onde a gente veio

O robô revisa antes da pessoa

Na aula 07 você protegeu a main e passou a exigir revisão de gente. Hoje entra mais uma camada — e ela vem antes.

Sem CI

Quem revisa gasta os primeiros dez minutos baixando a branch, instalando e rodando os testes na mão. Se der erro, escreve "quebrou aqui" — e o autor responde "quebrou como?".

Com CI

O robô já rodou tudo e deixou o log linkado no PR. A pessoa revisa o desenho da solução, que é o que só ela sabe fazer. O serviço braçal ficou com a máquina.

Hoje o robô só avisa. Ele pinta um ✗ no Pull Request, mas o botão de merge continua clicável. Transformar esse ✗ em check obrigatório — que trava o merge de verdade, amarrado na branch protection da 07 — é a aula 09.

// onde mora

Um arquivo. Dentro do próprio repositório.

Não tem painel pra configurar nem servidor pra alugar. A automação é um .yml versionado junto com o código — quem clonar o projeto leva o pipeline junto.

meu-projeto/ .github/ workflows/ ci.yml ← o robô de hoje mora aqui deploy.yml ← outro robô, outro assunto (aula 10) src/ package.json package-lock.json README.md

O caminho é exatamente .github/workflows/: com ponto na frente, no plural, na raiz do repositório. Um caractere fora e o GitHub simplesmente não enxerga o arquivo — sem erro, sem aviso. O nome do .yml, esse sim, é livre.

// vocabulário

Cinco palavras e você lê qualquer workflow

workflow
O arquivo inteiro: uma receita automatizada, com nome.
evento (on:)
O gatilho. O que precisa acontecer no repositório pra receita começar: um push, um PR aberto, um horário.
job
Um bloco de trabalho que roda numa máquina só. Dois jobs rodam em paralelo, em máquinas diferentes, e não compartilham nada.
step
Uma linha da receita, dentro do job. Rodam em ordem, de cima pra baixo. Se um falha, os de baixo nem começam.
runner
A máquina que executa o job. O GitHub liga uma virgem pra você, roda, e destrói no fim.
action (uses:)
Um step pronto que alguém já escreveu e publicou. Você chama pelo nome em vez de reescrever.

A hierarquia, numa frase: um workflow reage a um evento, tem um ou mais jobs, cada job roda num runner e é feito de steps — que são comando seu ou action de terceiro.

// on:

O gatilho

Tudo começa no on:. Hoje a gente usa os dois primeiros — os outros ficam aqui só pra você saber que existem.

on:
  # toda vez que alguém empurra pra main
  push:
    branches: [main]

  # e toda vez que um PR mira a main — inclusive a cada commit novo no PR
  pull_request:
    branches: [main]

  # todo dia às 3h da manhã, horário UTC
  schedule:
    - cron: "0 3 * * *"

  # um botão "rodar agora" na aba Actions
  workflow_dispatch:

Por que os dois, push e pull_request? O pull_request testa a sua branch já combinada com a main: é o resultado do merge que ainda não aconteceu. O push na main testa o que ficou de fato depois que o merge aconteceu. São duas perguntas diferentes.

// o primeiro workflow

Linha por linha

.github/workflows/ci.yml 
name: CI                            # o nome que aparece na aba Actions

on:                                  # O EVENTO — quando rodar
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:                                # O JOB — um bloco de trabalho
  build:                              # "build" é um id que você inventa
    name: Build e testes
    runs-on: ubuntu-latest         # O RUNNER — a máquina virgem

    steps:                            # OS STEPS, em ordem
      - name: Baixar o código
        uses: actions/checkout@v4    # A ACTION — step pronto de terceiro

      - name: Instalar o Node
        uses: actions/setup-node@v4
        with:
          node-version: "20"

      - name: Instalar dependências
        run: npm ci                   # comando seu, no shell do runner

      - name: Rodar os testes
        run: npm test

O exemplo é Node, mas o desenho é o mesmo em qualquer stack: troque setup-node + npm ci por setup-java + mvn verify, ou setup-python + pytest. Evento, job, runner e steps não mudam uma vírgula. O assunto da aula é o processo, não a linguagem.

// uses:

Duas actions fazem quase todo o trabalho

actions/checkout@v4

O runner nasce vazio — ele não tem o seu código. Esta action clona o repositório na branch certa. Sem ela nada funciona: é sempre o primeiro step.

actions/setup-node@v4

Instala a versão do Node que você pedir e põe o npm no PATH. Com cache ligado, ainda guarda as dependências entre execuções.

o que você lêo que significa
uses:Chama código de terceiro. Por baixo, é um repositório do GitHub.
actions/checkoutDono actions (a própria GitHub), repositório checkout.
@v4A versão. Prenda sempre — sem isso, quem mantém a action muda o seu pipeline sem avisar.
with:Os parâmetros daquela action. Cada uma documenta os seus.
run:O oposto de uses: um comando de shell escrito por você.

Um step tem ou uses, ou run. Nunca os dois no mesmo step.

// mão na massa
LAB 1

O seu primeiro pipeline

~12 min

Do arquivo vazio ao check verde no Pull Request. Faça numa branch — a main está protegida desde a aula 07.

Crie a pasta e o arquivo

O caminho é literal. Confira o ponto, o plural e a raiz do repositório.

git switch -c ci/primeiro-workflow
mkdir -p .github/workflows
touch .github/workflows/ci.yml

Escreva o workflow

Copie o YAML de dois slides atrás — ou do manual, que tem o arquivo inteiro pra copiar num clique. Indentação com espaços, nunca Tab.

Commite e empurre

Conventional Commits, como na aula 07. Isto é infraestrutura, então o prefixo é ci:.

git add .github/workflows/ci.yml
git commit -m "ci: roda build e testes a cada push e PR"
git push -u origin ci/primeiro-workflow

Abra o PR e olhe pra baixo

Abaixo dos commits aparece uma caixa nova de checks. Clique em Details e acompanhe ao vivo.

quando terminar

Levante a mão se a aba Actions continuar vazia depois do push. Em nove de cada dez casos é o caminho do arquivo — .github, não github; workflows, não workflow.

parada obrigatória

Sem seguir sem responder

Quatro perguntas. Daqui pra frente a gente só melhora o pipeline que você já entendeu — então é agora.

1Em que pasta exata o arquivo do workflow precisa estar?
2Qual a diferença entre um step com uses: e um com run:?
3Por que o actions/checkout tem que ser o primeiro step?
4O check ficou vermelho no seu PR. O botão de merge trava?

respostas: 1 — .github/workflows/; 3 — porque o runner nasce vazio, sem uma linha do seu código; 4 — não, hoje ele só avisa. Travar o merge é a aula 09.

// a aba actions

Onde o robô mostra serviço

Cada disparo do evento vira uma execução na lista. Dentro dela, os jobs. Dentro do job, os steps — cada um com o seu próprio log e o seu cronômetro.

Actions CI ← o name: do workflow ✓ ci: roda build e testes... #7 ← a execução, pelo título do commit ✓ Build e testes 1m 04s ← o job ✓ Set up job ✓ Baixar o código ← os steps ✓ Instalar o Node ✓ Instalar dependências ✓ Rodar os testes ✓ Complete job ✗ feat: filtro de busca #6 ✓ docs: ajusta o README #5

✓ verde

Todos os steps passaram. O log fica guardado do mesmo jeito — e vale ler quando você quiser saber quanto tempo cada coisa levou.

✗ vermelho

Um step terminou com código diferente de zero. Os steps abaixo dele nem chegaram a começar.

🟡 amarelo

Está rodando agora. Dá pra acompanhar o log ao vivo, linha por linha, sem esperar acabar.

// quando fica vermelho

Ler o log é uma habilidade

Não leia de cima pra baixo. Clique no step que tem o ✗ — o GitHub já abre esse expandido — e leia as últimas linhas.

▸ Instalar dependências ✓ 8s ▾ Rodar os testes ✗ 4s Run npm test FAIL src/carrinho.test.js ● soma o total do carrinho expect(received).toBe(expected) Expected: 30 Received: 25 at Object.<anonymous> (src/carrinho.test.js:12:29) Tests: 1 failed, 13 passed, 14 total Error: Process completed with exit code 1.
1Qual step quebrou. Instalação, build e teste falham por motivos completamente diferentes.
2A mensagem de erro real — que costuma estar algumas linhas acima do exit code 1.
3Se dá pra reproduzir na sua máquina: rode o mesmo comando do run:, igualzinho.

Process completed with exit code 1 não é o erro — é o robô contando que o comando terminou mal. O erro está acima dessa linha.

// mão na massa
LAB 2

Quebre de propósito

~10 min

Um pipeline em que você nunca viu o vermelho é um pipeline em que você não confia. Vamos quebrar de propósito, na mesma branch do LAB 1.

Escreva um teste que não tem como passar

É feio de propósito. A ideia é justamente ficar vermelho.

cat > src/quebra.test.js <<'FIM'
test('quebra de propósito', () => {
  expect(2 + 2).toBe(5);
});
FIM

Empurre e espere o vermelho

O PR já está aberto: o commit novo dispara o workflow de novo, sozinho.

git add src/quebra.test.js
git commit -m "test: quebra proposital pra ler o log"
git push

Abra o log e ache a linha do erro

Actions → a execução vermelha → o job → o step com ✗. Ache o Expected: 5 e o Received: 4.

Conserte e veja voltar ao verde

Apague o arquivo e empurre. O mesmo PR fica verde sozinho, sem você clicar em nada.

rm src/quebra.test.js
git commit -am "test: remove a quebra proposital"
git push
quando terminar

Responda duas coisas: em qual step quebrou, e qual foi a última linha útil antes do exit code 1. Quem sabe responder isso sabe ler qualquer log de CI.

// strategy.matrix

Matriz: o mesmo job, várias versões

Você promete no README que o projeto roda no Node 18, 20 e 22. Sem matriz, você torce. Com matriz, você sabe.

jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false          # não cancele as outras quando uma falhar
      matrix:
        node: [18, 20, 22]
    name: Node ${{ matrix.node }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test

Um job vira três, cada um na sua máquina, em paralelo: custa quase o mesmo tempo de relógio e devolve três respostas. O fail-fast: false é importante — sem ele, o Node 18 quebrando cancela o 20 e o 22, e você fica sem saber se o problema é geral ou só daquela versão.

// cache

Não baixe a internet duas vezes

O runner nasce vazio toda vez. Sem cache, o npm ci rebaixa as mesmas centenas de pacotes em cada execução.

sem cache
Instalar dependências added 812 packages in 47s total do job: 1m 12s
com cache
Instalar dependências Cache restored from key: node-a3f9... added 812 packages in 6s total do job: 0m 24s

E ligar custa uma linha, porque a própria setup-node faz o serviço:

      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"       ← a chave sai do package-lock.json, sozinha

A chave do cache é o hash do lockfile: mudou uma dependência, muda a chave, o cache é refeito. Por isso npm ci e não npm install — o ci obedece o lockfile ao pé da letra, e é isso que torna a execução reprodutível.

// artefatos

Trazer arquivo de volta do runner

O runner é destruído no fim do job. Tudo que ele produziu — a pasta dist/, o relatório de cobertura, o print do teste que falhou — evapora junto, a menos que você peça pra guardar.

      - name: Guardar o build
        uses: actions/upload-artifact@v4
        if: always()                # guarde mesmo se o teste falhou
        with:
          name: build-dist
          path: dist/
          retention-days: 7         # some sozinho depois de uma semana

O arquivo aparece pra download na página da execução, lá embaixo, num quadro chamado Artifacts.

o build prontorelatório de coberturalog de teste em HTMLscreenshot do teste que falhou

O if: always() é o detalhe que separa quem já sofreu: o artefato mais útil é o do job que quebrou. Sem essa linha ele não é gerado justamente quando você mais precisa dele.

// a regra que ninguém conta

Pipeline lento é pipeline ignorado

Isto não é papo de performance. É comportamento humano — e mata mais CI do que qualquer bug.

até 5 minVocê espera olhando. O erro é consertado enquanto você ainda lembra do que fez.saudável
10 minVocê troca de tarefa. Volta depois, com a cabeça em outro lugar.atenção
25 minVocê faz merge sem olhar. "Depois eu vejo." Ninguém vê depois.ruim
40 min +Nasce o "esse teste sempre falha, ignora". O vermelho vira paisagem.morto

O que segura o tempo, em ordem de retorno:

  • Cache de dependências. Uma linha, e costuma cortar metade do tempo.
  • Jobs em paralelo. Lint e teste são jobs separados, não steps do mesmo job.
  • Só o necessário em cada evento. O teste de ponta a ponta pode rodar só no push pra main.
  • Olhe o cronômetro de cada step. A aba Actions mede todos. O gargalo quase nunca é onde você acha que é.

Um CI vermelho que o time aprendeu a ignorar é pior que nenhum CI: dá a sensação de segurança sem a segurança.

LAB 3

Matriz, cache e o crachá

~12 min

Ainda na mesma branch. O pipeline vai passar a responder três perguntas em vez de uma — e a ficar mais rápido no caminho.

Acrescente a matriz ao job

Entre o runs-on: e o steps:. Cuide da indentação: strategy alinha com runs-on.

strategy:
  fail-fast: false
  matrix:
    node: [18, 20, 22]

Use a versão da matriz e ligue o cache

Duas mudanças dentro do mesmo step do setup-node.

  with:
    node-version: ${{ matrix.node }}
    cache: "npm"

Empurre e conte os jobs

Agora são três jobs na mesma execução, ao mesmo tempo. Compare o tempo do "Instalar dependências" com o da primeira rodada.

Pendure o badge no topo do README

Troque usuario/repo pelo seu. O nome no fim do caminho é o do arquivo.

![CI](https://github.com/usuario/repo/actions/workflows/ci.yml/badge.svg)
quando terminar

O badge tem que aparecer verde na página do repositório. Se aparecer "no status", o caminho no link está errado — ou o workflow ainda não rodou na main.

// badge

O crachá no README

Uma imagem que o GitHub desenha na hora, dizendo se a branch padrão está passando. Quem chega no repositório descobre isso antes de clonar.

README.md 
# Meu Projeto

![CI](https://github.com/usuario/repo/actions/workflows/ci.yml/badge.svg)
                             └─usuário─┘└repo┘                └ o nome do ARQUIVO

passing

A última execução na branch padrão passou. É o que você quer ver.

failing

A main está quebrada agora. Isso é um chamado, não um enfeite.

no status

O caminho do arquivo está errado, ou o workflow nunca rodou na branch padrão.

Dá pra apontar pra uma branch específica com ?branch=main no fim da URL. E o badge não é decoração: repositório com failing parado há meses conta uma história — só que não é a que você queria contar.
