O repositório remoto

Hoje o GitHub entra. Aquele repositório das aulas 01 e 02 — com os seus commits, as suas branches e o seu merge — sai da sua máquina e vai para a internet, inteiro.

deixe aberto: o terminal, o repositório da aula 02 e uma conta no github.com já criada. hoje a gente vai precisar dela de verdade.

use ← → pra navegar · manual desta aula

// o problema

Todo o seu histórico cabe num HD só

meu-primeiro-repo/ .git/ ← duas aulas de história moram aqui README.md index.html .gitignore e existe uma cópia disso em: nenhum outro lugar.

O Git é excelente guardando história. Ele só não sabe guardar história em dois lugares sozinho — isso é você que manda fazer.

1Notebook roubado, HD queimado, formatação sem querer: a história inteira vai junto.
2Você não consegue continuar o trabalho na máquina do trabalho, nem na de casa.
3Ninguém consegue ver o que você fez — nem revisar, nem contribuir, nem contratar.
4Duas pessoas em duas máquinas não têm ponto de encontro. Voltou o zip por e-mail.

Remoto não é backup, é ponto de encontro. Backup é consequência — o que importa é ter um lugar onde todas as máquinas conversam.

// o conceito

O remoto é um repositório igual ao seu

Não é uma "pasta na nuvem", nem um servidor especial. É um repositório Git — com os mesmos commits e os mesmos hashes — que por acaso mora num computador de outra pessoa.

  • Todo mundo tem tudo. O Git é distribuído: cada cópia tem o histórico inteiro, não um pedaço.
  • origin é só um apelido para um endereço. Não tem nada de mágico no nome — é a convenção de "o remoto principal".
  • O GitHub não roda nada de diferente. Roda Git. Por isso o mesmo repositório funciona no GitLab, no Codeberg ou num servidor seu.
  • Sincronizar é uma escolha sua, feita por comando. O Git nunca manda nada sozinho.
// antes de qualquer comando

Autenticação primeiro

Esta é a parte em que a turma trava. Não é por ser difícil — é por ser a única do curso que depende de um site, de uma conta e de um cadastro. Faça isso antes de tentar o primeiro push.

morreu em 2021

Senha da conta

Em 13 de agosto de 2021 o GitHub desligou a senha da conta para operações de Git. Digitar sua senha no terminal hoje devolve um erro — e é um erro que engana, porque parece que a senha está errada.

o que funciona

Chave SSH ou token

Ou você cadastra uma chave SSH na sua conta, ou gera um personal access token e usa ele no lugar da senha. São dois caminhos; escolha um e siga só ele hoje.

Autenticar é provar quem você é para o servidor. Nada a ver com o git config user.name da aula 01 — aquilo é só o texto que assina o commit, e o Git não confere nada.

// escolha um

Se você não tem um motivo pra escolher, escolha SSH. Configura uma vez e não expira.

// chave ssh

Gerar o par de chaves

terminal
# 1. gerar o par (aceite o caminho padrão com Enter)
ssh-keygen -t ed25519 -C "voce@exemplo.com"

# 2. ver a chave PÚBLICA — é esta que vai pro site
cat ~/.ssh/id_ed25519.pub

# 3. testar depois de cadastrar
ssh -T git@github.com

Sai um id_ed25519 (privada) e um id_ed25519.pub (pública). O .pub é o único que se mostra.

1O e-mail no -C é só um rótulo pra você lembrar de qual máquina é a chave. Não precisa ser o do GitHub.
2A passphrase é opcional e é uma senha da chave, não da conta. Pode deixar em branco hoje.
3No site: foto do perfil → Settings → SSH and GPG keys → New SSH key. Cole o conteúdo inteiro do .pub, do ssh-ed25519 até o fim.
4Uma chave por máquina. Não copie a chave do notebook pro desktop — gere outra e cadastre as duas.

Nunca abra o arquivo sem .pub. Se você colar a chave privada em algum lugar, ela deixa de valer — gere outra e apague a antiga do GitHub.

LAB 1

Autenticar de verdade

~12 min

Ninguém segue pro resto da aula sem a linha successfully authenticated na tela.

Veja se você já tem chave

Se listar um id_ed25519.pub, pule o próximo passo.

ls -a ~/.ssh

Gere o par

Três Enters: caminho padrão, passphrase vazia, confirmação vazia.

ssh-keygen -t ed25519 -C "voce@exemplo.com"

Copie a pública e cadastre no site

Settings → SSH and GPG keys → New SSH key. Título: o nome da sua máquina.

cat ~/.ssh/id_ed25519.pub

Teste a conexão

Na primeira vez ele pergunta se confia no host: responda yes.

ssh -T git@github.com
quando terminar

A resposta certa é Hi seu-usuario! You've successfully authenticated, but GitHub does not provide shell access. — a segunda metade da frase não é erro, é o GitHub avisando que ali não tem terminal. Se veio Permission denied (publickey), a chave não chegou ao site.

// o outro caminho

Personal access token, passo a passo

Settings → Developer settings

Lá no fim do menu lateral esquerdo, depois de tudo.

Personal access tokens → Fine-grained tokens

Escolha a validade e só os repositórios que este token pode tocar.

Permissão Contents: Read and write

É o mínimo pra dar push. Não marque o resto "por garantia".

Generate token e copie na hora

Ele aparece uma vez. Fechou a página, perdeu — só resta gerar outro.

terminal · quando o git perguntar
Username for 'https://github.com': seu-usuario
Password for 'https://github.com': ← cole o TOKEN aqui

# o campo não mostra nada enquanto você cola. é normal.

# pra não digitar de novo a cada push:
# windows — já vem com o Git, não faça nada
# macos
git config --global credential.helper osxkeychain
# linux
git config --global credential.helper store

No Linux, store grava o token em texto puro no seu home. Em máquina compartilhada, prefira SSH.

// dois caminhos

Já existe lá × já existe aqui

A pergunta que decide o comando é uma só: o repositório já existe no GitHub?

existe lá, não existe aqui

git clone

git clone git@github.com:voce/repo.git
cd repo

Um comando faz tudo: cria a pasta, roda o init, cadastra o origin, baixa a história inteira, abre a branch principal e já deixa o upstream ligado.

existe aqui, não existe lá

remote add

# o repo local você já tem desde a aula 01
git remote add origin git@github.com:voce/repo.git
git push -u origin main

É o caso de hoje. Você faz à mão os dois passos que o clone faria por você: apontar o endereço e mandar a história.

Clonar não é baixar um zip. Vem o .git junto — todos os commits, todas as branches, todo o histórico. É por isso que dá pra trabalhar offline logo depois.

parada obrigatória

Sem seguir sem responder

Quatro perguntas. A partir daqui todo comando fala com um servidor — e servidor não perdoa quem pulou etapa.

1O seu ssh -T git@github.com respondeu successfully authenticated? Sim ou não.
2Por que a senha da sua conta não serve mais no terminal?
3Você tem um repositório local com commits. Vai usar clone ou remote add?
4O que origin é, exatamente?

respostas: 2 — o GitHub desligou em agosto de 2021; 3 — remote add, porque a história já é sua; 4 — um apelido para um endereço.

// git remote

Ler e mexer no que está ligado

$ git remote -v origin git@github.com:voce/repo.git (fetch) origin git@github.com:voce/repo.git (push) $ git remote add origin git@github.com:voce/repo.git $ git remote set-url origin git@github.com:voce/outro.git $ git remote remove origin

Sem nenhum remoto cadastrado, git remote -v não imprime nada. Silêncio aqui quer dizer "não está ligado em lugar nenhum".

1O -v mostra o endereço. Sem ele você vê só o apelido, que não ajuda em nada quando o erro é de URL.
2Aparecem duas linhas pro mesmo remoto: uma pra buscar, outra pra enviar. Normalmente são iguais.
3Errou a URL? set-url conserta. Não precisa apagar nada nem clonar de novo.
4Dá pra ter mais de um remoto — o seu e o do projeto original. Isso vira upstream de verdade nas aulas 06 e 12, com fork.
// push -u

O que aquele -u faz

$ git push -u origin main Enumerating objects: 12, done. Writing objects: 100% (12/12), 1.24 KiB, done. To github.com:voce/repo.git * [new branch] main -> main branch 'main' set up to track 'origin/main'. $ git branch -vv * main a1c9f0e [origin/main] feat: horário das aulas

A última linha do push é a que interessa: set up to track. É o -u falando.

Upstream é um casamento entre duas branches

  • O -u anota, no repositório, que a sua main local corresponde à origin/main.
  • Depois disso, git push e git pull secos já sabem para onde ir. Sem ele, você repete origin main pra sempre.
  • É por causa do upstream que o git status passa a dizer "your branch is ahead of origin/main by 2 commits".
  • Uma vez por branch. A branch nova da aula 02 vai precisar do próprio -u no primeiro push dela.

Esqueceu o -u? O Git avisa com has no upstream branch e escreve o comando completo pra você colar.

LAB 2

O repositório da aula 02 vai pro GitHub

~15 min

Mesma pasta das duas primeiras aulas, com os commits e o merge que você já fez. Nada some.

Crie o repositório vazio no site

Botão + → New repository. Nome igual ao da pasta. Não marque "Add a README", "Add .gitignore" nem licença — o repositório precisa nascer vazio.

Confira onde você está

Tem que existir .git e tem que existir commit.

cd meu-primeiro-repo
git log --oneline
git remote -v

Ligue o local ao remoto

Copie a URL SSH da tela do repositório recém-criado.

git remote add origin git@github.com:SEU-USUARIO/meu-primeiro-repo.git
git remote -v

Primeiro push

E depois recarregue a página do GitHub.

git push -u origin main
git status
quando terminar

Abra o repositório no site e clique em commits. Todos os seus commits das aulas 01 e 02 estão lá, com data e autor de quando você fez — não de agora. O push não criou história nova: ele copiou a que já existia.

// o detalhe que destrava tudo

origin/main não é a main

Depois do primeiro push você passa a ter três coisas com nome parecido. Confundir as três é a origem de quase todo susto com remoto.

main

A sua branch, na sua máquina. É nela que você commita. Só você mexe.

origin/main

Uma anotação local: "da última vez que eu olhei, a main do servidor estava neste commit". Fica velha sozinha, sem avisar.

a main lá

A branch de verdade no github.com. Pode ter andado agora mesmo, e a sua máquina não faz ideia.

origin/main só muda quando você roda fetch, pull ou push. É exatamente por isso que o próximo slide existe: alguém precisa ir lá perguntar.

// fetch × pull

Buscar × buscar e integrar

seguro sempre

git fetch

Vai ao servidor, baixa o que tem de novo e atualiza o origin/main. E para por aí: não encosta nos seus arquivos, não mexe na sua branch, não gera conflito.

git fetch origin
git log --oneline --graph --all
git diff main origin/main
mexe no seu trabalho

git pull

É fetch + integrar, numa tacada. Baixa e já junta o que veio com o que você tem — e é aqui que pode aparecer conflito, aquele mesmo da aula 02.

git pull origin main

# equivale a:
git fetch origin
git merge origin/main

Na dúvida, fetch primeiro. Você olha o que chegou antes de deixar entrar. É a diferença entre espiar pelo olho mágico e abrir a porta.

// pull --rebase

Por que o histórico fica legível

git pull (merge) · o padrão
*   9f2a1b0 Merge branch 'main' of github.com…
|\
| * 7c4d8e2 fix: typo no README   (do colega)
* | 3b9a5f1 feat: rodapé          (seu)
|/
* a1c9f0e feat: horário das aulas

Um commit de merge que não diz nada, só "sincronizei". Multiplique por vinte por semana.

git pull --rebase
* 5d1e7c3 feat: rodapé          (seu, reescrito por cima)
* 7c4d8e2 fix: typo no README   (do colega)
* a1c9f0e feat: horário das aulas
  • O rebase pega os seus commits, guarda, aplica o que veio e recoloca os seus por cima. Linha reta, sem commit de merge.
  • Repare no hash: 3b9a5f1 virou 5d1e7c3. São commits novos — mesmo conteúdo, identidade diferente.
  • Vale a pena porque o seu commit ainda não foi pra lugar nenhum. Reescrever o que já é público é outra história — e é a aula 11.
deixar como padrão
git config --global pull.rebase true

LAB 3

Quebrar de propósito: o push rejeitado

~12 min

Este lab foi feito pra dar erro. O erro é o conteúdo — a gente provoca, lê e conserta.

Mude o README pelo site

No GitHub, abra o README.md, clique no lápis, escreva uma linha e clique em Commit changes. Agora existe um commit lá que você não tem aqui.

Mude o mesmo arquivo aqui, sem saber de nada

É o que acontece na vida real: você estava trabalhando, não recarregou página nenhuma.

echo "linha escrita no terminal" >> README.md
git commit -am "docs: linha local"
git push

Leia o erro inteiro, sem pular

Ele tem a palavra rejected, a palavra non-fast-forward e um bloco de hint: que já diz o conserto.

Conserte do jeito certo

Traga o que falta, ponha o seu por cima e mande de novo.

git pull --rebase origin main
git log --oneline
git push
quando terminar

Compare o git log --oneline de antes e de depois: os dois commits estão lá, em linha reta, sem commit de merge no meio. Nenhum trabalho foi perdido — nem o seu, nem o que você fez pelo site.

// o erro mais comum da vida real

rejected: non-fast-forward

$ git push To github.com:voce/repo.git ! [rejected] main -> main (fetch first) error: failed to push some refs hint: Updates were rejected because the remote hint: contains work that you do not have locally. hint: You may want to first integrate the remote hint: changes (e.g., 'git pull ...') before pushing.
o conserto, sempre este
git pull --rebase
git push
1Fast-forward é quando o servidor só precisa andar pra frente na mesma linha. Aí o push passa.
2Non-fast-forward é o contrário: as duas histórias se separaram. Aceitar o seu push apagaria o commit que está lá.
3Então isto não é um erro — é o Git te protegendo. Ele se recusa a destruir trabalho de alguém sem perguntar.
4Quase sempre a causa é banal: você editou pelo site, ou alguém do time deu push cinco minutos antes.

Traduzindo o erro em uma frase: "tem coisa lá que não tem aqui — pega antes de mandar".

// a tentação

Por que --force não é a resposta

A internet vai te dizer pra usar git push --force. Funciona — no sentido em que uma marreta abre uma porta.

o que ele faz de verdade

--force não resolve a divergência: ele manda o servidor substituir a branch pela sua. O commit que estava lá sai do histórico — e sai também de todo mundo que der pull depois. O trabalho do colega não fica "em outro lugar". Ele some do repositório, e só existe ainda se alguém tiver a cópia local intacta.

e ainda por cima
  • Quem já tinha dado pull passa a ter um histórico que não bate com o servidor, e o próximo pull dessa pessoa vira um nó.
  • Em repositório de trabalho, --force na main costuma ser bloqueado — a proteção de branch da aula 07.
  • Existe o --force-with-lease, que ao menos checa se ninguém mexeu desde a sua última olhada. É a versão adulta, e mesmo assim só na sua branch.

Regra que vale a carreira inteira: nunca --force numa branch compartilhada. Reescrever história tem hora e lugar, e é a aula 11. Para o non-fast-forward do dia a dia, o conserto é pull --rebase e mais nada.
