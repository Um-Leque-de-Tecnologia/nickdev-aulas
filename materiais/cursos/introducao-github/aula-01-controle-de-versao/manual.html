Controle de versão e o primeiro repositório

O passo a passo para você refazer a aula sozinho, no seu ritmo: instalar o Git, configurar a sua identidade, criar um repositório, fazer três commits e escrever o .gitignore. Tudo local — o GitHub, o site, entra só na aula 03.

Antes de começar

01O que você vai fazer aqui

Este manual é o passo a passo da aula 01 para você refazer sozinho, do zero, sem depender da gravação. Do fim dele você sai com o Git instalado, com a sua identidade configurada, um repositório na sua máquina, três commits e um .gitignore funcionando.

Importante: tudo aqui acontece só na sua máquina. Nada do que você commitar hoje vai parar no site do GitHub — porque a gente não manda nada pra lá nesta aula. Conectar o repositório ao GitHub, com push e clone, é a aula 03. Se você abrir o github.com procurando o seu projeto, não vai achar, e está tudo certo.

Git e GitHub, de novo e com calma

É o mal-entendido que atrapalha o curso inteiro, então vale repetir:

Git
Um programa que roda na sua máquina, pelo terminal. Grava o histórico, compara versões e volta no tempo. Funciona sem internet e sem conta em lugar nenhum.
GitHub
Um site que guarda uma cópia de repositórios Git na internet, para outras pessoas verem e contribuírem. Precisa de conta, login e internet. Existem concorrentes — GitLab, Bitbucket, Codeberg — e o Git é o mesmo em todos.
repositório
Uma pasta de projeto que tem um .git dentro. É o .git que guarda a história inteira.
commit
Uma foto do projeto num instante, com autor, data e uma mensagem dizendo por que aquilo mudou.

O que você vai precisar: um terminal, uma pasta vazia e uns 40 minutos. No Windows, o terminal é o Git Bash, que vem junto com o instalador.

02Instalar o Git

Escolha o seu sistema, instale e volte aqui para o teste — que é o mesmo nos três.

Windows

Baixe o instalador em git-scm.com e siga com as opções padrão. Vem junto o Git Bash: é ele que você abre para digitar os comandos, não o CMD nem o PowerShell.

macOS

Digite git --version no Terminal: o próprio sistema oferece instalar as ferramentas de linha de comando. Com Homebrew, brew install git traz uma versão mais nova.

Linux

Use o gerenciador da sua distribuição — os três comandos mais comuns estão logo abaixo.

terminal · linux
# debian / ubuntu / mint
sudo apt update && sudo apt install git

# fedora
sudo dnf install git

# arch / manjaro
sudo pacman -S git

O teste que vale

Não é o instalador dizer "concluído": é o terminal responder. Feche e abra o terminal depois de instalar — senão ele não enxerga o programa novo.

terminal
git --version

O que se espera ver:

$ git --version git version 2.47.1
Repare: qualquer versão 2.x serve para este curso. Se aparecer command not found ou não é reconhecido como comando, a instalação não terminou — veja a seção Se travar.

03Dizer quem você é

O Git carimba nome e e-mail em cada commit. Enquanto você não disser quais são, ele se recusa a commitar. Isto se faz uma vez por máquina, não uma vez por projeto.

terminal
# a sua identidade — troque pelos seus dados
git config --global user.name "Seu Nome"
git config --global user.email "voce@exemplo.com"

# o nome da primeira branch de todo repositório novo
git config --global init.defaultBranch "main"

Nenhum dos três imprime nada quando dá certo — silêncio aqui é sucesso. Para conferir:

terminal
git config --global --list
$ git config --global --list user.name=Seu Nome user.email=voce@exemplo.com init.defaultBranch=main
pedaçoo que significa
--globalVale para todos os repositórios do seu usuário. Sem ele, a configuração vale só no repositório onde você está no momento.
user.nameO nome que vai assinar os commits. Texto livre — pode ser o seu nome de verdade ou o seu apelido de sempre.
user.emailO e-mail que entra em cada commit. Em repositório público, ele fica visível.
init.defaultBranchEvita a confusão entre master (antigo) e main (atual) daqui pra frente.
Cuidado: isto não é login. O Git não confere nada: você pode escrever qualquer nome e qualquer e-mail. Autenticação de verdade — chave SSH ou token — só aparece quando existe servidor no meio, na aula 03.
O primeiro repositório

04Criar o repositório

Um repositório é uma pasta de projeto com um .git dentro. Crie a pasta, entre nela e rode o init.

terminal
mkdir meu-primeiro-repo
cd meu-primeiro-repo
git init
$ git init Initialized empty Git repository in /home/voce/meu-primeiro-repo/.git/

A palavra que importa nessa saída é empty: existe repositório, mas ainda não existe nenhum commit. As duas coisas são diferentes.

Onde a história mora

O init não mexeu em nenhum arquivo seu. Ele só criou a pasta oculta .git ao lado deles:

terminal
ls -a
$ ls -a . .. .git
Cuidado: apagar a pasta .git apaga a história inteira, sem desfazer. Os seus arquivos continuam lá; a memória deles é que some. E não rode git init na sua pasta pessoal inteira nem na Área de Trabalho — um repositório por projeto.
Repare: se você rodar git init por engano no lugar errado, dá pra desfazer com rm -rf .git — desde que você tenha certeza de que está na pasta errada e que ela não tem histórico que importa.

05O ciclo: status → add → commit

São três verbos, sempre nesta ordem, e é o que você vai repetir pelo resto da vida com o Git.

  1. git status — em que pé eu estou? Não muda nada, é de graça, e ainda sugere o próximo comando. Rode sempre que estiver perdido.
  2. git add — o que entra neste commit? Põe as mudanças escolhidas na bancada. Não grava nada ainda.
  3. git commit — fecha a foto e escreve o bilhete. Aí sim a mudança entra no histórico, com o seu nome e a data.

Ler o git status

Toda a dificuldade do começo é ler essa saída. Ela tem três listas, e cada uma quer uma coisa de você:

$ git status On branch main Changes to be committed: modified: index.html Changes not staged for commit: modified: estilo.css Untracked files: notas.txt
listao que quer dizerentra no próximo commit?o que fazer
Changes to be committedEstá na bancada (staged).SimNada — ou git restore --staged arquivo para tirar de lá.
Changes not stagedO Git já cuida do arquivo, mas esta mudança está fora da bancada.Nãogit add arquivo.
Untracked filesArquivo novo, que o Git nunca viu.Nãogit add arquivo — ou listar no .gitignore.
working tree cleanA pasta e o último commit são idênticos.Não há o que commitarNada. É o estado bom.
Hábito: status antes de add, status depois de add, status depois de commit. Três segundos que evitam quase todo erro desta aula.

06A bancada (staging)

Staging é o pedaço do Git que confunde todo mundo — e ele destrava quando você para de pensar nele como "um passo a mais" e passa a pensar nele como bancada.

A oficina

Os seus arquivos, do jeito que estão na pasta agora. Você mexeu em cinco arquivos, mas só três deles resolvem um assunto.

A bancada

Você põe na bancada só o que vai virar este commit. git add é o gesto de pôr na bancada; git commit embala o que está lá, cola o bilhete e guarda na prateleira. A bancada esvazia sozinha depois.

É por causa dela que você consegue commitar um assunto por vez mesmo tendo mexido em tudo ao mesmo tempo. Sem a bancada, todo commit seria "mexi em umas coisas" — e o histórico voltaria a ser tão inútil quanto a pasta projeto-final-v2-AGORA-VAI.

terminal
# um arquivo por vez — o jeito consciente
git add index.html

# tudo que mudou na pasta, respeitando o .gitignore
git add .

# tirar da bancada (o arquivo não some, nem perde a mudança)
git restore --staged index.html
Repare: git add . é prático e perigoso na mesma medida. Ele leva junto tudo que estiver solto na pasta — por isso o .gitignore vem antes dele, na seção 09.

07Os seus três primeiros commits

Faça na ordem, sem pular, dentro de meu-primeiro-repo. Leia a saída de cada comando antes de digitar o próximo — é aí que o aprendizado acontece.

Commit 1 — o README

terminal
echo "# Meu primeiro repo" > README.md
git status

O README aparece como untracked: existe na pasta, mas o Git ainda não cuida dele.

$ git status On branch main No commits yet Untracked files: README.md nothing added to commit but untracked files present
terminal
git add README.md
git status
git commit -m "chore: primeiro commit"
$ git commit -m "chore: primeiro commit" [main (root-commit) e05a4c8] chore: primeiro commit 1 file changed, 1 insertion(+) create mode 100644 README.md

root-commit aparece só uma vez na vida do repositório: é o commit que não tem pai.

Commit 2 — uma página de verdade

terminal
printf '<h1>Oi, mundo</h1>\n' > index.html
git add index.html
git commit -m "feat: página inicial"
$ git commit -m "feat: página inicial" [main 7d3b112] feat: página inicial 1 file changed, 1 insertion(+)

Commit 3 — mudar algo que já existe

Este é o commit que ensina a diferença entre arquivo novo e arquivo modificado.

terminal
printf '<h1>Oi, mundo</h1>\n<p>Aulas toda terça, às 20h.</p>\n' > index.html
git status
git add index.html
git commit -m "feat: horário das aulas na home"

Repare que agora o status diz modified, e não mais untracked.

Como escrever a mensagem

Mensagem ruim

  • ajustes
  • mudanças
  • asdf
  • agora vai

Daqui a seis meses, nenhuma delas te diz nada.

Mensagem boa

  • fix: menu não abria no celular
  • feat: campo de busca no topo
  • chore: ignora .env

Cada uma responde sozinha: por que este commit existe?

  • Diga o porquê, não o quê — o quê o git diff já mostra sozinho.
  • Imperativo e presente: "adiciona o rodapé", não "adicionei o rodapé".
  • Um assunto por commit. Se a mensagem precisa de um "e", provavelmente são dois commits.
  • Os prefixos feat:, fix: e chore: viram convenção de time na aula 07. Comece a usar desde já; custa nada.
Cuidado: git commit sem o -m abre um editor dentro do terminal. Se você cair no Vim sem querer: aperte Esc, digite :q! e Enter para sair sem commitar.
Ler o que aconteceu

08Ver o histórico: log e diff

Commit gravado é commit que dá pra ler depois. Estes dois comandos não mudam nada — são só leitura, pode rodar à vontade.

git log — a lista das fotos

terminal
# uma linha por commit — o formato do dia a dia
git log --oneline

# o último commit, com autor e data
git log -1
$ git log --oneline a1c9f0e feat: horário das aulas na home 7d3b112 feat: página inicial e05a4c8 chore: primeiro commit $ git log -1 commit a1c9f0e2b8d4f6a1c3e7b9d5f2a8c4e6b1d3f7a9 Author: Seu Nome <voce@exemplo.com> Date: Mon Sep 1 09:14:02 2026 -0300 feat: horário das aulas na home
o que você vêo que é
a1c9f0eO hash: o nome único do commit. É por ele que você chama qualquer commit em qualquer comando.
ordem da listaDo mais novo para o mais antigo, de cima para baixo.
AuthorO nome e o e-mail que você pôs no git config. É por isso que aquele passo não era burocracia.
Repare: se a saída travar com um : piscando no fim, é o paginador, não um erro. Use as setas para rolar e a tecla q para sair.

git diff — linha a linha

O diff responde "o que exatamente mudou?". Ele tem duas versões, e a diferença entre elas é a bancada:

terminal
# o que mudou e AINDA NÃO está na bancada
git diff

# o que JÁ está na bancada, ou seja, o que vai entrar no commit
git diff --staged
$ git diff diff --git a/index.html b/index.html @@ -1,2 +1,2 @@ <h1>Oi, mundo</h1> - <p>Em breve.</p> + <p>Aulas toda terça, às 20h.</p>

Linha com - saiu; linha com + entrou. As linhas sem sinal estão ali só para você se situar.

Hábito que salva: rode git diff --staged antes de todo commit. É esse olhar de cinco segundos que impede senha, console.log esquecido e arquivo errado de entrarem no histórico.
Repare: depois do git add, o git diff puro fica vazio. Não é bug — a mudança apenas trocou de lugar, e agora aparece no --staged.

09O .gitignore

É um arquivo de texto na raiz do projeto, escrito por você, com uma regra por linha. Ele diz ao Git: "estes aqui, nem me mostre". E ele mesmo entra no commit — a regra vale para o time inteiro, não só para a sua máquina.

.gitignore
# dependências — voltam com um comando, não vão pro histórico
node_modules/
vendor/
.venv/

# segredos — senha, token, chave de API
.env
.env.local
*.pem
*.key

# lixo do sistema operacional e do editor
.DS_Store
Thumbs.db
.vscode/
.idea/

# o que é gerado a partir do código
dist/
build/
*.log
regrao que ela pega
.envExatamente esse arquivo, em qualquer pasta do projeto.
node_modules/A pasta inteira, com tudo que tem dentro. A barra no fim deixa claro que é pasta.
*.logQualquer arquivo terminado em .log. O * vale por qualquer texto.
# comentárioLinha ignorada pelo Git. Use para explicar por que a regra existe.
!importante.logA exceção da regra: o ! traz o arquivo de volta, mesmo que um padrão acima o tenha excluído.

Faça agora, no seu repositório

terminal
# um segredo de mentira e uma pasta pesada de mentira
echo "API_KEY=segredo-que-nao-pode-vazar" > .env
mkdir -p node_modules && touch node_modules/coisa.js
git status

Neste ponto os dois aparecem como untracked. Agora a regra:

terminal
printf '.env\nnode_modules/\n' > .gitignore
git status
git add .gitignore
git commit -m "chore: ignora .env e node_modules"
$ git status On branch main nothing to commit, working tree clean

Os arquivos continuam na sua pasta, intactos. O Git é que parou de olhar para eles.

Cuidado — a pegadinha que pega todo mundo: o .gitignore só funciona para arquivo que o Git ainda não rastreia. Se você já commitou o .env, botar ele na lista não faz nada: o Git continua seguindo o arquivo. Aí é git rm --cached .env e um novo commit — e, mesmo assim, o segredo continua no histórico antigo. Segredo commitado é segredo vazado: troque a chave. Limpar histórico e rotacionar credencial é assunto da aula 09.
Regra de ouro: escreva o .gitignore antes do primeiro git add .. Custa trinta segundos e evita o problema inteiro.

11Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
git: command not found (ou "não é reconhecido como comando") O Git não instalou, ou o terminal foi aberto antes da instalação terminar. Feche e abra o terminal. Se continuar, reinstale — no Windows, use o Git Bash, não o CMD.
fatal: not a git repository Você está fora da pasta do projeto, ou esqueceu o git init. pwd para ver onde está, cd até a pasta certa e ls -a para conferir se existe .git.
Author identity unknown Faltou configurar nome e e-mail. Rode as duas linhas do git config --global da seção 03 e commite de novo.
nothing added to commit Você mudou arquivos mas não deu git add. A bancada está vazia. git add . e depois git commit -m "…".
nothing to commit, working tree clean Não é erro. Quer dizer que a pasta e o último commit são idênticos. Nada. Mude alguma coisa antes de tentar commitar de novo.
O terminal virou uma tela estranha e não sai Você caiu no editor Vim, porque rodou git commit sem o -m. Esc, depois :q!, depois Enter. Refaça com -m "mensagem".
A saída travou com um : no fim É o paginador do git log, não um travamento. Setas para rolar, tecla q para sair.
O git diff não mostra nada, mas eu mudei o arquivo A mudança já está na bancada. git diff --staged.
O .env continua no status mesmo no .gitignore Ele já era rastreado antes de a regra existir. git rm --cached .env e commite. E troque a chave: o valor antigo ficou no histórico.
Commitei o node_modules inteiro sem querer git add . antes de existir o .gitignore. git rm -r --cached node_modules, crie o .gitignore e commite os dois juntos.
Não acho o meu repositório no site do GitHub Ele é local. Nesta aula você não mandou nada para lá. Não há o que consertar — está certo. Conectar ao GitHub é a aula 03.
Commitei errado e quero desfazer Acontece com todo mundo, o tempo todo. Tem conserto para cada caso, e é a aula 11 inteira. Por enquanto: faça um commit novo por cima corrigindo.
Antes de pedir ajuda: rode git status e cole a saída inteira. Em nove de cada dez casos, a resposta já está escrita ali — o Git costuma sugerir o comando certo logo abaixo de cada bloco.
