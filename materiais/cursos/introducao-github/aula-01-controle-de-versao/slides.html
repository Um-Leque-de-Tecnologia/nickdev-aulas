Controle de versão e o primeiro repositório

No fim de hoje você tem um repositório de verdade na sua máquina, três commits feitos por você e um .gitignore segurando o que não pode entrar no histórico.

deixe aberto: o terminal e uma pasta vazia pra experimentar. o site do GitHub a gente só abre na aula 03 — hoje é tudo local.

use ← → pra navegar · manual desta aula

// o problema

Isto aqui não é controle de versão

projetos/ site/ site-backup/ site-v2/ site-v2-FINAL/ projeto-final-v2-AGORA-VAI/ ← este? projeto-final-v2-AGORA-VAI (cópia)/ site-antes-do-joao-mexer.zip

Todo mundo já teve essa pasta. Ela é uma tentativa honesta de resolver um problema real — só que resolve mal.

1Você não sabe o que mudou entre duas pastas. Só o nome — e o nome já mente.
2Você não sabe por que mudou. O motivo morreu na sua cabeça na semana passada.
3Você não sabe quem mexeu, nem quando.
4Não dá pra voltar só um pedaço. Ou é a pasta inteira, ou nada.
5Duas pessoas na mesma pasta: alguém sobrescreve alguém. Sempre.

Copiar pasta guarda estados. Controle de versão guarda a história. A diferença entre as duas coisas é a aula de hoje.

// o conceito

O que o Git resolve

O Git é um gravador de história da sua pasta. Em vez de cópias inteiras com nomes cada vez mais desesperados, ele guarda uma sequência de fotos — e cada foto vem com bilhete.

Cada foto tem autor

Nome, e-mail, data e hora de quem gravou. Ninguém precisa lembrar de nada depois.

Cada foto tem recado

A mensagem do commit diz por que aquilo mudou — a informação que a pasta com sufixo nunca teve.

Dá pra comparar

Linha a linha, entre quaisquer duas fotos. É o que o git diff faz.

$ git log --oneline a1c9f0e feat: formulário de contato 7d3b112 fix: menu quebrado no celular e05a4c8 chore: primeiro commit

Três linhas dizem mais que sete pastas. E dá pra voltar a qualquer uma delas.

// o mal-entendido central

Git não é GitHub

Se você sair daqui com uma coisa só, que seja esta. Confundir os dois atrapalha as outras onze aulas.

git

Um programa na sua máquina

Você instala, ele roda no terminal e funciona sem internet. É ele que grava os commits, guarda o histórico e sabe voltar no tempo. Nasceu em 2005, é software livre, e ninguém é dono dele.

github

Um site que hospeda repositórios

Uma empresa — da Microsoft desde 2018 — que guarda uma cópia do seu repositório na internet, para outras pessoas verem e contribuírem. Precisa de conta, de login e de internet.

Git é o gravador; GitHub é a prateleira compartilhada onde a fita fica. Existem outras prateleiras — GitLab, Bitbucket, Codeberg — e o Git é exatamente o mesmo em todas.

// honestidade técnica

github.comclone, push, pull — aula 03, não hoje
  • Tudo que você fizer hoje mora numa pasta escondida chamada .git, dentro do seu projeto.
  • Não adianta procurar no site. Nada do que você commitar hoje aparece no github.com — porque você não mandou nada pra lá.
  • Isso não é limitação, é a ordem certa de aprender. Quem aprende push antes de entender commit fica refém do botão.
  • Na aula 03 a gente conecta este mesmo repositório ao GitHub. O histórico de hoje vai junto, inteiro.

Pode criar a conta no GitHub hoje se quiser — só não vai precisar dela ainda.

// instalação

Instalar o Git nos três sistemas

Windows

Baixe em git-scm.com e instale com as opções padrão. Vem junto o Git Bash — é nele que a gente digita, não no CMD nem no PowerShell.

macOS

Digite git --version: o sistema oferece instalar as ferramentas de linha de comando sozinho. Com Homebrew, brew install git.

Linux

Debian e Ubuntu: sudo apt install git. Fedora: sudo dnf install git. Arch: sudo pacman -S git.

$ git --version git version 2.47.1 # qualquer 2.x serve. se vier "command not found", não instalou de verdade.

O teste de que deu certo é a versão aparecer no terminal. Não é o instalador dizer "concluído".

// mão na massa
LAB 1

Instalar e assinar

~8 min

Antes de gravar qualquer história, o Git precisa saber quem está gravando.

Abra o terminal e confirme a instalação

Windows: Git Bash. macOS e Linux: o terminal de sempre.

git --version

Diga o seu nome e o seu e-mail

Use o nome que você quer ver assinando os commits — ele fica no histórico para sempre.

git config --global user.name "Seu Nome"
git config --global user.email "voce@exemplo.com"

Confira o que ficou gravado

Se as duas linhas voltarem com o que você digitou, está pronto.

git config --global --list
quando terminar

Levante a mão se o --list não mostrou o seu nome. Sem isso, o commit da próxima parte falha com um erro sobre identidade.

// git config

Quem assina o commit

terminal
# identidade — vale pra todos os projetos da máquina
git config --global user.name "Nicoly Almeida"
git config --global user.email "nicoly@exemplo.com"

# o nome da primeira branch de todo repositório novo
git config --global init.defaultBranch "main"

# conferir tudo de uma vez
git config --global --list

Isto se faz uma vez por máquina, não uma vez por projeto.

1--global grava no seu usuário. Sem ele, a configuração vale só no repositório em que você está.
2O e-mail entra em cada commit, e commit não se apaga fácil. Se for repositório público, use um e-mail que você aceita expor.
3Nome e e-mail são texto livre: o Git não confere nada, não existe login aqui. Autenticação de verdade é assunto da aula 03.
4init.defaultBranch evita a briga entre master e main mais adiante.

Configurar é assinar o caderno antes de escrever. Sem isso o Git se recusa a commitar — e faz bem.

// o repositório

git init: a pasta vira repositório

$ mkdir meu-primeiro-repo $ cd meu-primeiro-repo $ git init Initialized empty Git repository in /home/voce/meu-primeiro-repo/.git/
meu-primeiro-repo/ .git/ ← o repositório em si index.html ← os seus arquivos estilo.css
1init não muda os seus arquivos. Cria só a pasta .git ao lado deles.
2Dentro do .git mora todo o histórico. Apagou essa pasta, apagou a história — os arquivos ficam, a memória some.
3Ela é escondida: no gerenciador de arquivos, ligue "mostrar arquivos ocultos" pra ver.
4Não rode git init na sua pasta pessoal inteira. Um repositório por projeto.

Nenhum arquivo foi salvo no histórico ainda. Ter repositório e ter commit são coisas diferentes.

// o ciclo

status → add → commit

Este é o ciclo que se repete pelo resto da sua vida com o Git. Três verbos, nesta ordem.

👀
git statuso que mudou desde o último commit?
→
🧺
git addescolho o que entra neste commit
→
📸
git commitfecho a foto e escrevo o bilhete

Sempre comece pelo status. É de graça, não muda nada, e responde a única pergunta que importa antes de commitar: em que pé eu estou?

// a área de staging

A bancada onde você monta o commit

Staging é a parte que confunde todo mundo — e some quando você para de pensar nela como "um passo a mais" e passa a pensar nela como bancada.

1. A oficina

Os seus arquivos, do jeito que estão na pasta agora. Você mexeu em cinco, mas só três resolvem um assunto.

2. A bancada (staging)

Você põe na bancada só o que vai virar este commit. git add é o gesto de pôr na bancada.

3. A prateleira

git commit embala o que está na bancada, cola o bilhete e guarda no histórico. A bancada esvazia.

A bancada existe pra você commitar um assunto por vez. Sem ela, todo commit seria "mexi em tudo" — e o histórico voltaria a ser inútil, como a pasta AGORA-VAI.

parada obrigatória

Sem seguir sem responder

Três perguntas. Se alguma travar, é agora que a gente resolve — o resto da aula empilha em cima destas.

1Em uma frase: qual a diferença entre Git e GitHub?
2Você rodou git init e criou um arquivo. Ele já está no histórico? Por quê?
3O que a bancada (staging) tem que a pasta não tem?

respostas: 2 — não, ainda falta add e commit; 3 — a escolha do que entra no commit.

// mão na massa
LAB 2

O primeiro repositório e o primeiro commit

~12 min

Do zero ao histórico, no ciclo inteiro. Leia a saída de cada comando antes de digitar o próximo.

Crie a pasta e entre nela

Fora de qualquer pasta que já seja repositório.

mkdir meu-primeiro-repo
cd meu-primeiro-repo
git init

Crie um arquivo e olhe o status

O Git vai chamar o arquivo de untracked — ele existe na pasta, mas o Git ainda não cuida dele.

echo "# Meu primeiro repo" > README.md
git status

Ponha na bancada e feche o commit

Depois do add, rode status de novo e repare que o arquivo mudou de lista.

git add README.md
git status
git commit -m "chore: primeiro commit"

Prove que existe história

Uma linha, com o seu nome nela.

git log --oneline
quando terminar

O que o git status diz agora? A resposta certa é nothing to commit, working tree clean — e essa frase quer dizer "a pasta e o último commit são idênticos".

// git status

Ler o status sem medo

terminal
git status

On branch main
Changes to be committed:
  modified:   index.html          ← na bancada

Changes not staged for commit:
  modified:   estilo.css          ← mudou, fora da bancada

Untracked files:
  notas.txt                       ← o Git nem conhece
1Changes to be committed — está na bancada. Entra no próximo commit.
2Changes not staged — o Git já cuida do arquivo, mas essa mudança fica de fora até você dar add.
3Untracked — arquivo novo, nunca commitado. Ou você adiciona, ou ignora no .gitignore.
4O status ainda sugere o comando pra cada situação, logo abaixo de cada bloco. Leia — ele está te ensinando.

Ninguém decora o Git; a gente aprende a ler a saída dele. Rode status sempre que estiver perdido.

// add e commit

Montar a bancada e fechar a caixa

terminal
# um arquivo por vez — o mais consciente
git add index.html

# a pasta inteira, respeitando o .gitignore
git add .

# tirar da bancada (o arquivo não some, só sai da lista)
git restore --staged index.html

# fechar o commit com o bilhete
git commit -m "feat: formulário de contato"

A mensagem é para quem vem depois

  • Escreva o porquê, não o quê. O quê o diff já mostra.
  • Imperativo e presente: "adiciona o rodapé", não "adicionei o rodapé".
  • Um assunto por commit. "Ajustes" é o pior título do mundo.
  • O prefixo feat: fix: chore: vira padrão de time na aula 07.

git commit sem o -m abre um editor de texto no terminal. Se cair no Vim sem querer: Esc, depois :q!, Enter.

// git log

O histórico, do jeito que dá pra ler

$ git log --oneline a1c9f0e feat: formulário de contato 7d3b112 fix: menu quebrado no celular e05a4c8 chore: primeiro commit $ git log -1 commit e05a4c8f2b1d9c7a3e6f0b4d8a2c5e9f1a7b3d6c Author: Nicoly Almeida <nicoly@exemplo.com> Date: Mon Sep 1 09:14:02 2026 -0300 chore: primeiro commit
1Aquele código de sete letras é o hash — o nome único do commit. É por ele que você chama qualquer commit.
2O log vem do mais novo para o mais antigo.
3Se a saída travar com um : no fim, é o paginador: seta pra baixo pra rolar, q pra sair.
4git log --graph desenha o grafo — vira útil de verdade na aula 02, com branches.
// git diff

Exatamente o que mudou

git diff
diff --git a/index.html b/index.html
@@ -8,7 +8,7 @@
   <h1>Bem-vindo</h1>
-  <p>Em breve.</p>
+  <p>Aulas toda terça, às 20h.</p>
   </main>

Linha com − saiu, linha com + entrou. Só isso.

1git diff mostra o que mudou e ainda não está na bancada.
2git diff --staged mostra o que já está na bancada — ou seja, o que vai entrar no commit.
3Depois do add, o git diff puro fica vazio. Não é bug: a mudança mudou de lugar.
4Leia o diff antes de commitar. É o hábito que evita commitar senha, console.log e arquivo errado.
// .gitignore

O que nunca pode entrar no histórico

.gitignore
# dependências: baixa de novo em 30 segundos
node_modules/

# segredos: senha, token, chave de API
.env
.env.local
*.pem

# lixo do sistema e do editor
.DS_Store
Thumbs.db
.vscode/

# o que é gerado a partir do código
dist/
build/
*.log
  • É um arquivo de texto na raiz do projeto, criado por você. Uma regra por linha.
  • Ele mesmo entra no commit — a regra vale para o time inteiro, não só pra você.
  • node_modules/ são dezenas de milhares de arquivos que o npm install traz de volta. Nunca versione.
  • Segredo commitado é segredo vazado, mesmo que você apague depois: ele fica no histórico. Rotacionar a chave é assunto da aula 09.

Escreva o .gitignore antes do primeiro git add .. O Git ignora arquivo novo — arquivo já rastreado ele continua seguindo, mesmo listado ali.

// mão na massa
LAB 3

Ignorar o que não é seu

~10 min

No mesmo repositório do LAB 2. A gente vai criar um segredo de mentira e provar que o Git não encosta nele.

Crie um arquivo que não pode vazar

E uma pasta pesada de mentira, pra fazer companhia.

echo "API_KEY=segredo-que-nao-pode-vazar" > .env
mkdir node_modules && touch node_modules/coisa.js
git status

Escreva o .gitignore

Repare no ponto no começo do nome — é ele que torna o arquivo oculto.

printf '.env\nnode_modules/\n' > .gitignore
git status

Commite só o .gitignore

O terceiro commit do dia.

git add .gitignore
git commit -m "chore: ignora .env e node_modules"
git log --oneline
quando terminar

Rode git status de novo: o .env e o node_modules/ sumiram da lista. Os arquivos continuam na pasta — o Git é que parou de olhar pra eles.
