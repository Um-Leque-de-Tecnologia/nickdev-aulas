Fluxos de trabalho e proteção da main

O passo a passo para você fazer sozinha, no seu ritmo: escolher o fluxo do seu projeto, escrever o CONTRIBUTING.md com a convenção de branch e de commit que o time adota, e trancar a main no GitHub para que a regra pare de depender da boa memória de todo mundo.

Escolher o fluxo

01O que você vai fazer aqui

Este manual é o passo a passo da aula 07 para você refazer sozinha, do começo. No fim dele o seu repositório tem três coisas que ele não tinha: um fluxo escolhido de propósito, um CONTRIBUTING.md que qualquer pessoa consegue seguir sem falar com você, e uma main que recusa push direto — inclusive o seu.

O que você precisa ter em mãos

  • Um repositório seu no GitHub em que você seja admin. Sem esse nível de permissão a tela de proteção nem abre — os níveis foram a aula 04.
  • O repositório clonado na sua máquina, com push funcionando (aula 03).
  • Uns 50 minutos. A parte do GitHub é rápida; a parte de decidir é a que demora — e é a que vale.
Ordem importa: configure a proteção por último. Se você trancar a main antes de commitar o CONTRIBUTING.md, vai precisar abrir um Pull Request para o próprio arquivo que ainda está escrevendo. Não é o fim do mundo, mas atrapalha o aprendizado.

O vocabulário do dia

fluxo de trabalho
O combinado do time sobre onde o código nasce, por onde passa e quando vira produção. Não é um programa que se instala: é um acordo entre pessoas.
branch de longa vida
Uma branch que nunca é apagada, porque representa um estado permanente do projeto — main é a mais comum.
Conventional Commits
Uma convenção pública, com especificação escrita, para a primeira linha da mensagem de commit: tipo(escopo): descrição.
branch protection
Regras que o servidor do GitHub aplica sobre uma branch. Como moram no servidor, não têm como ser contornadas do seu terminal.
ruleset
O formato novo dessas regras no GitHub. Substitui a tela antiga de branch protection rules, faz a mesma coisa e um pouco mais.

02Os três modelos lado a lado

Os três fazem a mesma coisa com o mesmo Git. O que muda é quantas branches de longa vida existem e quanto ritual tem entre escrever o código e ele estar no ar.

GitHub Flow

Uma branch eterna, a main. Toda mudança nasce numa branch curta, passa por Pull Request e volta pra main. A main está sempre pronta para ir ao ar.

o ciclo
git switch main
git pull
git switch -c feat/42-login-com-google
# … trabalha, commita …
git push -u origin feat/42-login-com-google
# abre o PR, é revisada, mescla, apaga a branch
assumeo que isso quer dizer
Time de qualquer tamanhoFunciona de 1 a 50 pessoas. É o mais fácil de aprender e de sustentar.
Deploy quando quiserWeb, API, app com entrega contínua. Se a sua entrega depende de janela de manutenção, precisa de ajuste.
Uma versão vivaSó existe o que está no ar. Ninguém está usando a versão de dois meses atrás.

Trunk-based

O GitHub Flow apertado até o limite: a branch vive horas, não dias, e integrar na main é evento diário. Muita gente ainda usa PR — só que PRs pequenininhos, revisados no mesmo dia.

assumeo que isso quer dizer
Teste automático rápidoSe a suíte demora 40 minutos, ninguém integra várias vezes por dia. É pré-requisito, não detalhe.
Tarefa quebrada em pedaços pequenosExige prática. Quem só sabe entregar a funcionalidade inteira de uma vez não consegue.
Feature flagO código entra desligado e só liga quando estiver pronto. É o que permite integrar algo incompleto sem quebrar quem usa.
Cuidado com a imitação: trunk-based sem teste automático é só empurrar direto na main com um nome bonito. Aí você tem todo o risco e nenhum benefício.

Git Flow

Cinco tipos de branch e duas de longa vida. Foi desenhado em 2010, quando o normal era o cliente instalar o software e você dar suporte a várias versões ao mesmo tempo.

as branches do Git Flow
main        # o que está em produção, marcado com tags
develop     # integração do que vem na próxima versão
feature/*   # sai de develop, volta pra develop
release/*   # congela, estabiliza, vira versão
hotfix/*    # sai da main, volta pra main E pra develop

Ele é bom no problema para o qual foi feito. O problema é que a maioria dos times de hoje não tem esse problema:

  • Toda mudança é mesclada duas vezes — na develop e depois na main. Dobra o conflito e dobra a chance de alguém esquecer um dos lados.
  • A develop só faz sentido se existe um momento de virar versão. Quem faz deploy toda hora não tem esse momento, e a develop vira uma cópia da main com atraso.
  • Branch de feature longa é convidada pelo modelo, e branch longa é merge gigante semanas depois — exatamente a dor que um fluxo deveria evitar.
  • São cinco regras para decorar. Regra que ninguém entende é regra que todo mundo contorna.
  • O próprio autor publicou depois uma nota de rodapé recomendando que quem entrega continuamente não use o modelo.
Em resumo: Git Flow é pesado demais para a maioria dos times de hoje. Adote se você mantém versões em paralelo de verdade — biblioteca, SDK, aplicativo de desktop, firmware. Se você entrega uma web app com uma versão só no ar, ele cobra um preço alto por um benefício que você não vai usar.

03Escolher o fluxo do seu projeto

Fluxo não se copia do emprego anterior nem do vídeo mais visto. Escolhe-se respondendo três perguntas sobre o seu time.

  1. Quantas pessoas commitam neste repositório? Conte de verdade, incluindo você. Uma pessoa sozinha não precisa de duas branches eternas. Oito pessoas precisam de algum acordo escrito.
  2. Com que frequência isso vai pro ar? Anote a frequência real, não a desejada. Se é "quando alguém lembra", o seu problema não é fluxo — é entrega, e isso é a aula 10.
  3. Existe mais de uma versão viva ao mesmo tempo? Alguém ainda usa a versão antiga e você precisa consertar bug lá? Se a resposta é não, você acabou de eliminar o Git Flow — e sobra a escolha fácil.
se o seu time…o fluxo épor quê
1 a 3 pessoas, projeto de estudo ou produto novoGitHub FlowCerimônia mínima e o PR já funciona como registro do que mudou.
Entrega várias vezes por dia, com teste automático rápidoTrunk-basedIntegrar todo dia é mais barato que resolver conflito de dez dias.
Mantém 2.x e 3.x vivas ao mesmo tempoGit Flow ou varianteVocê precisa mesmo de mais de uma linha de manutenção.
Entrega em janela fixa, com homologação separadaGitHub Flow + release/*Uma branch de release só quando existe janela — não as cinco de uma vez.
Copiou o fluxo do emprego anterior sem perguntar por quêNenhum aindaVolte à pergunta 1. Fluxo que ninguém entende vira burocracia contornada.
Escreva a frase: antes de seguir, complete em voz alta — "Neste projeto a gente usa ___ porque ___." Se o "porque" for "é o que todo mundo usa", você copiou. Ela vai virar o primeiro parágrafo do seu CONTRIBUTING.md na seção 08.
Dá pra mudar depois. O caminho barato é começar no GitHub Flow e apertar o que doer. O caro é começar no Git Flow e tentar tirar peça de um ritual que já virou hábito do time.

04Nomear as branches

O nome da branch é a primeira coisa que qualquer pessoa vê na lista do repositório. Ele tem que responder o que tem lá dentro, não quem criou — quem criou o Git já grava sozinho.

o formato
tipo/numero-da-issue-descricao-curta
funciona
feat/42-login-com-google
fix/57-menu-quebrado-no-mobile
chore/61-atualiza-dependencias
docs/63-readme-de-instalacao
refactor/70-extrai-validacao
não funciona
nicoly                  # quem fez, o Git já grava
teste2                  # teste de quê?
nova-branch             # todas são novas
correcao                # correção de quê?
feature/ajustes-gerais  # "geral" nunca é um assunto
Feat/Login Com Google   # maiúscula e espaço quebram em algum sistema
a peçaa regra
tipoO mesmo vocabulário dos commits: feat, fix, chore, docs, refactor. Um vocabulário só para o time inteiro, em branch e em commit.
numero-da-issueLiga a branch ao contexto. Quem abrir o repositório daqui a três meses acha a discussão inteira em um clique. Sem issue, pule este pedaço — não invente número.
descricao-curtaTrês a cinco palavras, minúsculas, separadas por hífen. Sem acento, sem espaço, sem maiúscula: sistema de arquivos que não diferencia caixa transforma isso em bug de verdade.
terminal
# sempre saia da main atualizada
git switch main
git pull

# cria e já entra na branch nova
git switch -c feat/42-login-com-google

O que se espera ver:

$ git switch -c feat/42-login-com-google Switched to a new branch 'feat/42-login-com-google'
A barra não cria pasta. O / em feat/42-... é só parte do nome — mas o GitHub e a maioria das ferramentas usam ele para agrupar as branches visualmente. É de graça e organiza a lista.

05Conventional Commits

Até aqui, no curso, a mensagem de commit era só uma frase bem escrita. A partir de hoje ela tem formato — e essa é a diferença entre um texto que só uma pessoa lê e um texto que um programa também lê.

a forma canônica
tipo(escopo)!: descrição no imperativo
peçaobrigatória?regra
tiposimUm da lista fechada da seção 06. Minúsculo.
(escopo)nãoA parte do sistema que mudou: (auth), (carrinho), (api). Combine a lista com o time e não invente na hora.
!nãoVem logo antes dos dois-pontos e marca mudança incompatível. Detalhe na seção 07.
: descriçãosimEspaço depois dos dois-pontos. Imperativo e presente, minúscula, sem ponto final, até uns 72 caracteres.

Por que isto não é frescura

Esta é a parte que decide se você vai manter o hábito ou abandonar na terceira semana. A convenção não existe para o commit ficar bonito. Existe para que uma máquina consiga ler o que antes só uma pessoa lia, e mal:

  • Um robô separa as feat das fix das perf sem perguntar nada a ninguém.
  • Com essa separação ele monta o changelog sozinho, agrupado por assunto.
  • E decide a versão: fix vira patch (1.4.2 → 1.4.3), feat vira minor (1.4.2 → 1.5.0), BREAKING CHANGE vira major (1.4.2 → 2.0.0).
  • Você consegue achar quando um comportamento entrou filtrando o log por tipo e escopo, sem ler diff nenhum.
Isto é exatamente a aula 10. Lá a gente liga a ferramenta que lê estes commits e cospe tag, changelog e release. Hoje é o plantio: se a convenção não estiver de pé agora, na aula 10 não há de onde tirar nada.
git log --oneline · antes e depois

agora vai

# depois: oito commits e um resumo da entrega

Bons e ruins, lado a lado

Esta é a tabela de consulta. Deixe aberta nas primeiras semanas — depois de uns trinta commits você para de olhar.

tipoquando usarexemplo realefeito na versão
feat Funcionalidade nova para quem usa o sistema. feat(carrinho): permite aplicar cupom de desconto minor
1.4.2 → 1.5.0
fix Correção de um bug que chegou ao usuário. fix(login): aceita e-mail com letra maiúscula patch
1.4.2 → 1.4.3
docs Só documentação: README, comentário, guia, este manual. docs: explica como rodar os testes localmente nenhum
style Formatação, espaço em branco, ponto e vírgula, ordem de import. Zero mudança de comportamento. style: aplica o prettier em todo o src nenhum
refactor Reescreve o código sem mudar o que ele faz nem consertar bug. refactor(api): extrai a validação para um módulo nenhum
test Acrescenta, conserta ou reorganiza teste. Nada de código de produção. test(carrinho): cobre o caso de cupom expirado nenhum
chore Manutenção que não é nenhuma das outras. É o saco de retalhos — use por último. chore: remove arquivo de exemplo não usado nenhum
build Empacotamento, dependências, ferramenta de build. build: sobe o Vite para a versão 6 nenhum
ci Arquivos de integração contínua — o que vive em .github/workflows/. ci: roda os testes também no Node 22 nenhum
perf Melhora de desempenho, sem mudar o resultado. perf(lista): evita renderizar item fora da tela patch
1.4.2 → 1.4.3
Só feat e fix são obrigatórios pela especificação. Os outros oito são convenção de mercado — e é a que praticamente todo mundo usa, porque veio do projeto Angular. Não invente tipo novo sem o time inteiro concordar: tipo desconhecido é tipo que a ferramenta da aula 10 vai ignorar em silêncio.
A dúvida mais comum: chore ou refactor? Se você mexeu em código que roda em produção sem mudar o comportamento, é refactor. Se você mexeu em coisa em volta — configuração, arquivo solto, limpeza —, é chore. Na dúvida, chore não estraga nada.

07Corpo, rodapé e BREAKING CHANGE

A primeira linha resolve 90% dos commits. Os outros 10% precisam explicar o porquê ou avisar que alguma coisa quebrou — e para isso existem o corpo e o rodapé.

mensagem completa
feat(api)!: troca o token de sessão por JWT

O token antigo era um UUID guardado em tabela, o que
obrigava uma consulta ao banco a cada request. Agora o
próprio token carrega a expiração e o identificador.

BREAKING CHANGE: quem consome /v1/login precisa ler o
campo access_token em vez de session_id. O campo antigo
sai na próxima versão.

Refs: #128
parteregra
linha em brancoObrigatória entre o título e o corpo, e entre o corpo e o rodapé. Sem ela o Git entende tudo como título — e é o erro número um de quem está começando.
corpoO porquê e o contexto. O o quê o git diff já mostra. Quebre as linhas em ~72 colunas para o git log não ficar horrível.
rodapéMetadado, uma chave por linha: Refs: #128, Closes #42, Co-authored-by: …, Reviewed-by: ….
BREAKING CHANGE:Em maiúsculas, no rodapé. Diga o que a pessoa precisa fazer, não só o que mudou. É a linha que vai parar em destaque no changelog.
!Vem antes dos dois-pontos: feat(api)!:. É o atalho visual do mesmo aviso. Pode usar os dois juntos — o ! chama atenção na lista, o rodapé explica.
Isto muda o número da versão. Um commit marcado como quebra faz a versão pular de 1.4.2 para 2.0.0, e não para 1.5.0. Marcar sem precisar assusta quem usa; não marcar quando precisa quebra quem usa. A mecânica inteira do versionamento é a aula 10.

Escrever mensagem com corpo, na prática

Com corpo, o -m na linha de comando fica ruim. Duas saídas:

terminal
# 1. sem -m: abre o editor configurado
git commit

# 2. com vários -m: cada um vira um parágrafo
git commit -m "feat(api)!: troca o token de sessão por JWT" \
           -m "BREAKING CHANGE: leia access_token em vez de session_id."
Se o editor for o Vim e você não souber sair: Esc, depois :wq para salvar, ou :q! para cancelar. Para trocar por outro: git config --global core.editor "code --wait".

08Escrever o CONTRIBUTING.md

Combinado de boca some. Combinado versionado fica no repositório e o GitHub mostra sozinho para quem abre um Pull Request. O arquivo vive na raiz do projeto — o papel dele na plataforma foi a aula 04; aqui a gente enche de conteúdo.

  1. Crie a branch na convenção Já praticando o que você acabou de definir.

# Como contribuir

## O nosso fluxo

Neste projeto a gente usa **GitHub Flow**: a `main` está sempre
pronta para ir ao ar, e todo trabalho nasce numa branch curta que
volta por Pull Request.

Escolhemos assim porque somos um time pequeno, entregamos toda
semana e existe uma versão só no ar. Não usamos `develop` nem
branch de release.

A `main` é protegida: ninguém empurra direto nela, nem quem tem
permissão de admin.

## Nome das branches

    tipo/numero-da-issue-descricao-curta

Exemplos:

    feat/42-login-com-google
    fix/57-menu-quebrado-no-mobile
    docs/63-readme-de-instalacao

Regras: minúsculas, hífen no lugar de espaço, sem acento. Se não
houver issue, omita o número — não invente um.

## Mensagem de commit

Seguimos [Conventional Commits](https://www.conventionalcommits.org):

    tipo(escopo)!: descrição no imperativo

    corpo opcional, explicando o porquê

    BREAKING CHANGE: o que quem usa precisa mudar
    Refs: #123

Tipos aceitos: `feat`, `fix`, `docs`, `style`, `refactor`, `test`,
`chore`, `build`, `ci`, `perf`.

Escopos deste projeto: `auth`, `carrinho`, `busca`, `api`, `ui`.

A descrição é minúscula, no imperativo e sem ponto final.

    OK   feat(busca): filtra por categoria
    OK   fix(login): aceita e-mail com maiúscula
    NAO  Ajustes finais
    NAO  Update index.html

Por que isso importa: é a partir destes commits que a versão e o
changelog são gerados automaticamente na hora da release.

## Abrindo o Pull Request

1. Um assunto por PR. PR pequeno é revisado no mesmo dia.
2. Título do PR na mesma convenção do commit.
3. Vincule a issue com `Closes #123` na descrição.
4. Marque como rascunho enquanto ainda estiver trabalhando.
5. Resolva todas as conversas antes de pedir o merge.

## O que trava o merge

- Falta de aprovação de pelo menos uma pessoa.
- Conversa de revisão em aberto.
- Branch desatualizada em relação à `main`.
terminal
git add CONTRIBUTING.md
git commit -m "docs: define fluxo, nome de branch e padrão de commit"
git push -u origin docs/1-contributing

O que se espera ver:

$ git push -u origin docs/1-contributing remote: Create a pull request for 'docs/1-contributing' on GitHub by visiting: remote: https://github.com/voce/seu-repo/pull/new/docs/1-contributing branch 'docs/1-contributing' set up to track 'origin/docs/1-contributing'.
O teste do modelo: leia o arquivo fingindo que você chegou hoje no projeto. Se em algum ponto for preciso perguntar alguma coisa para uma pessoa, esse ponto ainda não está escrito.
Um irmão útil: o mesmo raciocínio vale para o .github/pull_request_template.md, que preenche a descrição do PR sozinho. O template de PR foi a aula 06.

09Proteger a main

Tudo até aqui é acordo, e acordo depende de memória. Proteção de branch é o acordo escrito num lugar que cobra sozinho — o servidor do GitHub. Ela não pede licença, não abre exceção por antiguidade e não some numa sexta-feira corrida.

Você precisa ser admin do repositório. Se o menu Rules não aparecer em Settings, o seu nível de permissão não chega lá — peça a quem administra. Em repositório pessoal você é admin por padrão.

O caminho, clique a clique

  1. Abra as regras do repositório Settings → Rules → Rulesets → botão New ruleset → New branch ruleset.
  2. Dê um nome e ative Nome: protege a main. Em Enforcement status, escolha Active. Se ficar em Disabled, a regra existe e não vale nada.
  3. Escolha o alvo Em Target branches, Add target → Include default branch. Assim a regra segue a branch padrão, mesmo que ela mude de nome um dia.
  4. Deixe a lista de bypass vazia Em Bypass list, não adicione ninguém. É aqui que a regra deixa de ter exceção para o admin — que é você.
  5. Marque as regras As da seção 10. Para hoje: pull request obrigatório com 1 aprovação, conversas resolvidas e histórico linear.
  6. Salve Create. A regra passa a valer no próximo push.

Testar a tranca

Regra que não foi testada é esperança. Este push tem que falhar — a falha é o resultado certo.

terminal
git switch main
echo "teste de proteção" >> README.md
git commit -am "chore: testa a protecao da main"
git push origin main

O que se espera ver:

$ git push origin main remote: error: GH006: Protected branch update failed for refs/heads/main. remote: error: Changes must be made through a pull request. ! [remote rejected] main -> main (protected branch hook declined) # deu certo: a regra recusou o push. inclusive o seu.

Agora desfaça o commit de teste, que ficou só na sua máquina, e volte a main local ao que o servidor tem:

terminal
git reset --hard origin/main
O --hard apaga mudança não commitada. Aqui é seguro porque a única coisa na frente é o commit de teste que a gente acabou de fazer. Se você tinha outro trabalho solto na main, guarde antes com git stash — e isso é a aula 11.
Fecha o ciclo: volte ao PR do CONTRIBUTING.md que ficou aberto na seção 08 e mescle por lá. É o mesmo arquivo, entrando pelo caminho que ele mesmo descreve.

10As opções, uma a uma

A tela tem muita caixinha e nem toda é para hoje. Aqui está o que cada uma faz, e a recomendação para um projeto de curso ou time pequeno.

Require a pull request before merging

A caixa principal. Com ela ligada, ninguém empurra direto na main: toda mudança passa por Pull Request. É a regra que sustenta todas as outras — sem PR, não há revisão, não há conversa e não há check. Ligue. Ao marcar, abrem-se as sub-opções abaixo.

Required approvals

Quantas pessoas precisam aprovar antes do merge. 1 é o número saudável para time pequeno. 2 trava um time de três pessoas quando alguém tira férias. 0 mantém a obrigação do PR mas não a da revisão — útil em projeto de uma pessoa só, onde o PR serve como registro.

Dismiss stale pull request approvals when new commits are pushed

Sem isto acontece o seguinte: alguém aprova o seu PR, você empurra mais três commits e mescla — e esses três ninguém viu. Com isto ligado, push novo zera a aprovação. Ligue. É a diferença entre revisão de verdade e carimbo.

Require review from Code Owners

Chama automaticamente a pessoa dona daquela parte do código, conforme o arquivo CODEOWNERS. Só faz sentido se o arquivo existir — ele foi a aula 06. Deixe desligado por enquanto.

Require conversation resolution before merging

Cada comentário de revisão vira uma conversa, e cada conversa precisa ser marcada como Resolve conversation antes do merge. Impede o clássico "mescla logo que depois eu vejo" — que nunca é depois. Ligue.

Require linear history

Proíbe commit de merge na main, o que na prática obriga o time a mesclar por squash ou por rebase. O resultado é um histórico em linha reta, que se lê de cima para baixo sem grafo. As três formas de mesclar foram a aula 06. Ligue se o time já combinou usar squash — e a maioria combina.

Require branches to be up to date before merging

Aparece junto com os status checks. Obriga a branch a estar em dia com a main antes do merge, para você não mesclar código que foi testado contra uma versão velha. Custa um git pull --rebase origin main a mais por PR. Vale em time que mescla muito no mesmo dia.

Require status checks to pass

É onde os testes e o lint viram porteiro do merge. Deixe para depois: não existe check para exigir enquanto não existir workflow. A gente cria o workflow na aula 08 e volta nesta caixa na aula 09.

Block force pushes

Impede reescrever o histórico já publicado da main — o famoso git push --force, que apaga commit de outras pessoas sem avisar. Já vem ligado. Não desligue.

Restrict deletions

Impede apagar a branch. Parece exagero até o dia em que não é. Já vem ligado. Não desligue.

Bypass list

Quem pode furar todas as regras acima. A tentação é se colocar aí "para emergências". Não faça isso. Regra com exceção para o chefe não é regra: é sugestão com decoração. Se a emergência for real, o admin desativa o ruleset por três minutos — e o GitHub registra quem desativou e quando, o que é bem melhor do que uma porta permanentemente destrancada.

Ruleset ou branch protection rule? O GitHub tem as duas telas. A antiga (Settings → Branches) continua funcionando e faz quase o mesmo. A nova (Settings → Rules) permite várias regras convivendo, alvo por padrão de nome e histórico de quem mudou o quê. Comece pela nova.

O ciclo completo, do começo ao merge

terminal
# 1. parte da main atualizada
git switch main
git pull

# 2. branch com nome na convenção
git switch -c feat/42-login-com-google

# 3. trabalha e commita na convenção
git add .
git commit -m "feat(auth): aceita login com Google"

# 4. publica a branch
git push -u origin feat/42-login-com-google

# 5. abre o PR no GitHub, é revisada, mescla por lá
#    a main está protegida: este é o único caminho

# 6. limpa depois do merge
git switch main
git pull
git branch -d feat/42-login-com-google

12Se travar

Os tropeços desta aula, do mais comum ao mais raro. Vários deles não são erro — são a proteção funcionando.

sintomacausaconserto
Protegi a main e agora não consigo mais dar push nem eu Está exatamente certo. Você deixou a bypass list vazia de propósito: a regra não abre exceção para o admin. Nada a consertar. Trabalhe por branch e PR: git switch -c fix/12-descricao, git push -u origin fix/12-descricao, abra o PR. Se for emergência real, Settings → Rules, mude o ruleset para Disabled, faça o que precisa e volte para Active — o GitHub registra a mudança com o seu nome.
GH006: Protected branch update failed Não é erro: é a proteção recusando push direto. Crie a branch, empurre a branch, abra o PR e mescle por lá.
protected branch hook declined A mesma coisa, dita pelo lado do git push. Idem acima.
Empurrei na main mesmo com a regra ativa Ou o ruleset está Disabled, ou você está na bypass list. Settings → Rules: status Active e lista de bypass vazia. Confira também se o alvo é mesmo a branch padrão.
Commitei 20 vezes na main local antes de descobrir a trava Trabalho todo na branch errada. Nada foi perdido — está tudo commitado. git switch -c feat/12-descricao leva os commits junto. Depois git push -u origin feat/12-descricao e, se quiser limpar a main local, git switch main e git reset --hard origin/main.
O menu Rules não aparece em Settings Você não é admin do repositório. Peça a quem administra, ou teste num repositório pessoal seu. Os níveis de permissão foram a aula 04.
Botão de merge cinza com tudo aprovado Sobrou conversa não resolvida na revisão. Percorra os comentários e clique em Resolve conversation em cada um. Quem abriu a conversa é quem deveria resolvê-la.
PR diz This branch is out-of-date with the base branch A main andou depois que você abriu o PR, e a regra exige branch em dia. Botão Update branch no próprio PR, ou git pull --rebase origin main e git push --force-with-lease na sua branch.
PR diz que o merge quebraria o histórico linear Require linear history está ligado e você escolheu merge commit. Use Squash and merge ou Rebase and merge. Se as opções nem aparecem, ligue-as em Settings → General → Pull Requests.
Aprovaram o PR, empurrei mais commits e a aprovação sumiu Dismiss stale approvals está ligado. É o comportamento desejado. Peça nova revisão. Se for coisa mínima, avise no comentário do PR o que mudou desde a aprovação.
Errei o tipo do commit e já empurrei Acontece com todo mundo. Se você é a única pessoa na branch: git commit --amend e git push --force-with-lease. Em branch compartilhada, deixe como está e explique no PR — reescrever histórico alheio dá muito mais dor de cabeça. Desfazer é a aula 11.
Ninguém segue a convenção de commit Ela está na cabeça de quem propôs, não no repositório. CONTRIBUTING.md na raiz e template de PR. Validar a mensagem por robô no PR é a aula 09.
Não sei se um commit é chore ou refactor A fronteira é mesmo cinza. Mexeu em código que roda em produção sem mudar o comportamento: refactor. Mexeu em volta: chore. Nenhum dos dois muda a versão, então o custo do erro é baixo.
Quero começar a usar a convenção num projeto com 300 commits antigos Não dá para reescrever o passado — e nem se quer. Comece hoje, daqui pra frente. A ferramenta da aula 10 ignora o que ela não entende e gera changelog só do que estiver na convenção.
Antes de pedir ajuda: diga em qual branch você está (git status responde na primeira linha) e cole a mensagem inteira do GitHub. Nesta aula, nove em cada dez "erros" são a proteção funcionando exatamente como você pediu.
