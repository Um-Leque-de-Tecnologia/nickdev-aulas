Fluxos de trabalho e proteção da main

No fim de hoje o seu repositório tem um fluxo escolhido de propósito, um CONTRIBUTING.md dizendo como se nomeia branch e commit, e uma main que recusa push direto — inclusive o seu.

deixe aberto: o terminal e um repositório seu no github.com em que você seja admin. sem ser admin, a tela de proteção não abre.

use ← → pra navegar · manual desta aula

// o problema

O time combinou. E aí veio a sexta-feira.

$ git log --oneline -8 3f9a1c2 ajustes c14b8e0 Update index.html 9b2d770 WIP 51e6aa4 agora vai 0dd3f19 Merge branch 'nicoly-teste-2' 88c0b45 fix bug a7e2f31 . 6c5d012 hotfix direto na main (desculpa)

Este histórico é de um time que combinou tudo direitinho. Numa reunião. Em março.

1Ninguém sabe o que entrou na versão de ontem sem abrir arquivo por arquivo.
2As branches se chamam o nome de quem criou — o que não diz nada sobre o que tem dentro.
3Alguém empurrou direto na main às 18h50. Quebrou. Foi descoberto na segunda.
4Não dá pra gerar nota de versão disso. Nem à mão, nem por robô.

Combinado que depende de todo mundo lembrar não sobrevive a uma sexta-feira corrida. A aula de hoje é sobre trocar a memória do time por uma regra que o servidor cobra.

// o conceito

Fluxo é um acordo, não uma ferramenta

Nenhum destes três é um programa que se instala. São combinados sobre onde o código nasce, por onde passa e quando vira produção. O Git faz os três sem saber a diferença.

GitHub Flow

Uma branch eterna (main) e branches curtas de trabalho. Toda mudança passa por PR. É o padrão do curso.

Trunk-based

Todo mundo integra na main quase todo dia. As branches vivem horas, não dias.

Git Flow

Cinco tipos de branch, duas eternas, ritual de release. Nasceu em 2010 para software com versões instaladas.

A pergunta certa não é "qual é o melhor". É: quantas pessoas somos, com que frequência a gente entrega, e existe mais de uma versão viva ao mesmo tempo?

1Só existe uma branch de longa vida: a main. Tudo o mais é temporário.
2A main sempre funciona. Essa é a promessa central — e o que a proteção de branch existe pra garantir.
3A branch morre no merge. Vida útil de horas a poucos dias.
4Assume que você consegue entregar quando quiser — típico de web, API, app com deploy contínuo.

É o que a gente adota no curso — e o que a esmagadora maioria dos times de produto usa hoje. A mecânica do PR em si foi a aula 06.

// modelo 2

Trunk-based

O GitHub Flow levado ao extremo: a branch vive horas, e integrar é o evento diário — não o evento da semana.

O que ele assume sobre o time

  • Suíte de testes automática e rápida, rodando a cada integração.
  • Gente experiente o bastante pra quebrar tarefa grande em pedaços pequenos que já podem entrar.
  • Feature flag: o código entra desligado e só liga quando estiver pronto. É isso que permite integrar algo incompleto sem quebrar ninguém.
  • Deploy várias vezes por dia, sem cerimônia.

O que ele resolve

  • Conflito de merge quase some. Quem integra todo dia nunca fica dez dias longe da main.
  • Ninguém segura trabalho pronto esperando uma data.
  • O feedback de erro chega em minutos, não em semanas.

Sem teste automático, trunk-based vira empurrar direto na main com nome bonito. Aí é o pior dos mundos.

// modelo 3

Git Flow — e por que ele pesa

main ← o que está em produção, com tags develop ← integração do que vem depois feature/* ← sai de develop, volta pra develop release/* ← congela, estabiliza, vira versão hotfix/* ← sai da main, volta pras duas

Cinco tipos de branch. Duas de longa vida. Toda entrega tem ritual.

1Foi desenhado em 2010, para software que o cliente instala e mantém versões antigas rodando. Nesse mundo ele é excelente.
2Hoje a maioria dos times entrega web: existe uma versão viva só, a que está no ar. As duas branches eternas viram trabalho sem dono.
3Toda mudança é mesclada duas vezes (develop e main). Dobra o conflito e dobra a chance de esquecer um lado.
4Branch de feature longa vira merge gigante semanas depois. É exatamente a dor que o fluxo devia evitar.
5O próprio autor publicou uma nota dizendo que, se você entrega continuamente, não use isto.

Git Flow é pesado demais para a maioria dos times de hoje. Não porque é errado — porque resolve um problema que o seu time provavelmente não tem. Adote se você mantém versões em paralelo: biblioteca, SDK, app desktop, firmware.

se o seu time…o fluxo épor quê

Você pode começar simples e apertar depois. O caminho barato é GitHub Flow e acrescentar o que doer. O caro é começar no Git Flow e tentar tirar peça de um ritual que já virou hábito.

// mão na massa
LAB 1

Escolher o fluxo do seu projeto

~8 min

Sem terminal. Pegue um projeto real seu — o do curso serve — e responda por escrito.

Quantas pessoas commitam nele?

Conte de verdade, incluindo você. Uma pessoa e oito pessoas pedem coisas diferentes.

De quanto em quanto tempo vai pro ar?

Todo dia? Toda semana? Quando alguém lembra? Anote a frequência real, não a desejada.

Existe mais de uma versão viva ao mesmo tempo?

Alguém ainda usa a versão antiga e você precisa consertar bug lá? Se a resposta é não, você acabou de eliminar o Git Flow.

Escreva a frase

Uma linha só, no formato: "Neste projeto a gente usa ___ porque ___." Ela vai virar o primeiro parágrafo do seu CONTRIBUTING.md daqui a pouco.

quando terminar

Leia a sua frase em voz alta. Se o "porque" for "é o que todo mundo usa", volte ao passo 1 — isso é copiar, não escolher.

// convenção · branches

O nome da branch é um recado

o formato
tipo/numero-da-issue-descricao-curta

# exemplos bons
feat/42-login-com-google
fix/57-menu-quebrado-no-mobile
chore/61-atualiza-dependencias
docs/63-readme-de-instalacao
o que não ajuda ninguém
nicoly
teste2
nova-branch
correcao
feature/ajustes-gerais
1O tipo é o mesmo vocabulário dos commits: feat, fix, chore, docs. Um vocabulário só pro time inteiro.
2O número da issue é o que liga a branch ao contexto. Quem abrir daqui a três meses acha a discussão inteira em um clique.
3Minúsculas e hífen. Nada de espaço, acento ou maiúscula: sistema de arquivos que não diferencia caixa transforma isso em bug de verdade.
4Curto. A branch é temporária — o nome só precisa durar até o merge.
5Nome de pessoa não é tipo. Quem fez o Git já grava sozinho; o nome tem que dizer o quê.
$ git switch -c feat/42-login-com-google Switched to a new branch 'feat/42-login-com-google'
// conventional commits

Conventional Commits: a estrutura

Uma convenção pública, com especificação escrita, para a primeira linha da mensagem de commit. Três peças e dois sinais de pontuação.

a forma canônica
tipo(escopo)!: descrição no imperativo
└┬─┘ └──┬──┘ ┬  └────────┬────────┘
 │      │    │           └── minúscula, sem ponto final, até ~72 caracteres
 │      │    └────────────── opcional: marca mudança incompatível
 │      └─────────────────── opcional: a parte do sistema que mudou
 └────────────────────────── obrigatório: um da lista fechada de tipos

feat(auth): aceita login com Google

Tipo, escopo e descrição. Lê-se como uma frase.

fix: corrige menu no Safari

O escopo é opcional. Sem ele continua válido.

Ajustes finais

Não tem tipo, não tem assunto, não gera nada. É o commit que a gente está aposentando hoje.

É a mesma mensagem de sempre — só que com um prefixo que um programa consegue ler. Essa é a diferença inteira.

Só feat e fix são obrigatórios pela especificação — o resto é convenção de mercado, e é a que praticamente todo mundo usa. Não invente tipo novo sem o time inteiro concordar.

// conventional commits · o resto da mensagem

Corpo, rodapé e o quebra-tudo

a mensagem completa
feat(api)!: troca o token por JWT
← linha em branco obrigatória
O token antigo era um UUID guardado em tabela,
o que obrigava uma consulta ao banco por request.
Agora o próprio token carrega a expiração.
← outra linha em branco
BREAKING CHANGE: quem usa /v1/login precisa ler
o campo access_token em vez de session_id.

Refs: #128
Reviewed-by: Nicoly Almeida
1O corpo é o porquê. Separado do título por uma linha em branco — sem ela, o Git entende tudo como título.
2O rodapé guarda metadado: Refs: #128, Closes #42, coautoria.
3BREAKING CHANGE: no rodapé anuncia que quem já usava vai quebrar. Escreva o que fazer, não só o que mudou.
4O ! antes dos dois-pontos é o atalho visual da mesma coisa. Pode usar os dois juntos — e é o que se recomenda.
5Esse marcador é o que faz a versão pular de 1.4.2 para 2.0.0 em vez de 1.5.0. O detalhe é a aula 10.

Oito commits, nenhuma informação. Pra saber o que mudou você tem que ler o diff dos oito.

como fica 
feat(busca): filtra por categoria
fix(busca): ignora acento no termo
test(busca): cobre termo vazio
docs: documenta o parâmetro categoria
refactor(busca): extrai o normalizador
perf(busca): indexa o campo categoria
chore: remove o console.log esquecido
ci: roda os testes no Pull Request

Oito commits e um resumo da entrega. Sem abrir um arquivo.

Repare no que mudou de verdade: não é o capricho. É que agora cada linha responde o que e onde — e um programa consegue separar as feat das fix sem perguntar pra ninguém.

parada obrigatória

Sem seguir sem responder

Três perguntas. A segunda metade da aula empilha em cima destas.

1Você mantém um app web com uma versão só no ar, entrega toda semana, time de quatro. Qual fluxo e por quê?
2Você renomeou uma função interna sem mudar o comportamento. Qual tipo de commit? E se tivesse renomeado um parâmetro da API pública?
3Por que escrever bem a mensagem não basta — por que ela precisa ter um formato?

respostas: 1 — GitHub Flow; 2 — refactor, e na API pública vira feat! com BREAKING CHANGE; 3 — porque texto livre humano nenhum programa lê.

// por que isso importa

Isso não é frescura de commit bonito

Convenção existe pra que uma máquina consiga ler o que antes só uma pessoa lia — e mal.

✍️
você escrevefeat(busca): filtra por categoria
→
🤖
o robô agrupasepara feat de fix de perf sozinho
→
🏷️
sai versão e changelog1.4.2 → 1.5.0, com as notas prontas
  • fix vira patch (1.4.2 → 1.4.3). feat vira minor (1.4.2 → 1.5.0). BREAKING CHANGE vira major (1.4.2 → 2.0.0).
  • O changelog deixa de ser aquele arquivo que alguém escreve na véspera da entrega, de memória, errado.
  • Dá pra achar quando um comportamento entrou filtrando o log por tipo e escopo.
  • Um robô só decide isso se a informação estiver num lugar previsível. Daí o formato.

Gerar changelog e versão a partir destes commits é a aula 10 inteira. Hoje a gente planta; lá a gente colhe. Se você pular a convenção agora, a aula 10 não tem de onde tirar nada.

LAB 2

Escrever o combinado no repositório

~12 min

Combinado de boca some. Combinado versionado fica. Vamos escrever o CONTRIBUTING.md — o manual tem o modelo inteiro pra copiar.

Crie a branch com o nome na convenção

Já praticando o que a gente acabou de ver.

git switch main
git pull
git switch -c docs/1-contributing

Escreva o CONTRIBUTING.md

Quatro blocos: o fluxo escolhido (a sua frase do LAB 1), o padrão de nome de branch, o padrão de commit e como se abre um PR.

Commite na convenção que você acabou de escrever

É o primeiro teste dela — se ficar difícil de nomear o próprio commit, o combinado ainda está confuso.

git add CONTRIBUTING.md
git commit -m "docs: define fluxo, nome de branch e padrão de commit"
git push -u origin docs/1-contributing

Abra o PR e deixe aberto

Não faça o merge ainda. A gente vai proteger a main no LAB 3 e usar este PR pra provar que a proteção funciona.

quando terminar

Abra o seu CONTRIBUTING.md e pergunte: alguém que nunca falou comigo consegue seguir isto sozinho? Se precisar de você para explicar, ainda não está pronto.

// a trava

Branch protection: o combinado vira regra

Tudo até aqui é acordo. Acordo depende de memória — e memória falha às 18h50 de sexta. Proteção de branch é o acordo escrito num lugar que cobra sozinho.

só combinado

"A gente não empurra direto na main"

Funciona nos dias bons. Na correria alguém pula — quase sempre a pessoa mais experiente, que "sabe o que está fazendo". E ninguém fica sabendo até quebrar.

com proteção

O servidor recusa o push

Não tem exceção por antiguidade, nem por pressa. O GitHub responde que a branch é protegida, e o push simplesmente não acontece.

$ git push origin main remote: error: GH006: Protected branch update failed for refs/heads/main. remote: error: Changes must be made through a pull request. # não é bug. é a regra funcionando — e ela vale pra você também.

A regra mora no servidor, não na sua máquina. Não adianta clonar de novo, trocar de computador ou usar outro cliente Git.

// a tela de proteção

Caixa por caixa, o que cada uma faz

a opçãoo que ela impede
Require a pull request before mergingPush direto na main. Toda mudança passa por PR — inclusive a sua.
Require approvals (1 ou 2)Merge sem ninguém ter olhado. Uma aprovação já muda o jogo; duas travam time pequeno.
Dismiss stale approvalsAprovar, empurrar mais commits e mesclar coisa que ninguém revisou. Push novo, aprovação zerada.
Require conversation resolutionMerge com comentário de revisão em aberto. Cada linha discutida precisa ser resolvida.
Require linear historyCommit de merge na main. Obriga squash ou rebase — histórico em linha reta, legível.
Require branches to be up to dateMesclar código testado contra uma main velha.
Do not allow bypassingQue admin (você) fure a própria regra. Ligue. Regra com exceção pro chefe não é regra.
Block force pushes · Restrict deletionsReescrever ou apagar a main. Já vêm ligadas por padrão — não desligue.

Nessa mesma tela existe Require status checks to pass — os testes e o lint como porteiro do merge. Isso é a aula 09: primeiro a gente cria os checks na aula 08, depois volta aqui pra torná-los obrigatórios.

// mão na massa
LAB 3

Trancar a main — e testar a tranca

~14 min

No seu repositório, onde você é admin. O passo a passo detalhado está no manual.

Crie a regra

Settings → Rules → Rulesets → New branch ruleset. Alvo: Default branch. Status: Active.

Marque as quatro caixas do dia

Pull request obrigatório com 1 aprovação, conversas resolvidas, histórico linear e sem bypass — nem pra você.

Prove que a tranca fecha

Este push tem que falhar. É o resultado esperado.

git switch main
echo "teste" >> README.md
git commit -am "chore: testa a protecao"
git push origin main   # ← vai ser recusado

Limpe a bagunça e mescle pelo caminho certo

Desfaça o commit local de teste e volte ao PR do LAB 2 — que agora só entra por merge revisado.

git reset --hard origin/main
quando terminar

Se o push na main passou, a regra não está ativa ou o bypass de admin ficou ligado. Volte no ruleset: status Active e a lista de bypass vazia.
