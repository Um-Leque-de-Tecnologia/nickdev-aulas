Release, versionamento e deploy contínuo

O passo a passo para você levar o seu repositório do merge até a produção: criar a primeira tag anotada, publicar a Release com changelog, guardar um secret, exigir aprovação humana antes do deploy, escrever o workflow que publica no GitHub Pages — e voltar a versão anterior quando der ruim, sem apagar nada do histórico.

Antes de começar

01O que você vai fazer aqui

Este é o passo a passo da aula 10, para você refazer sozinho, no seu ritmo. No fim dele o seu repositório tem uma versão marcada, uma Release publicada, um secret guardado, um ambiente de produção com aprovação manual e um site que sobe no ar sozinho toda vez que você cria uma tag.

De onde você vem

Este manual continua o repositório das aulas 08 e 09. Antes de começar, confira que você tem:

  • Um repositório no GitHub com alguma coisa estática para publicar — um index.html já basta.
  • A main protegida e o CI verde, como na aula 09.
  • Commits no padrão Conventional Commits da aula 07 — feat:, fix:, chore:. É deles que o changelog sai pronto.
  • Permissão de administrador no repositório: secrets, environments e Pages moram todos em Settings.
Não tem o repositório da aula 09? Serve qualquer repositório seu com um index.html na raiz de uma pasta. O que você vai perder é só a parte de “o CI já barrava merge quebrado” — o resto funciona igual.
Fora do escopo de hoje: desfazer commit com git revert, reset e reflog é a aula 11 inteira. Criar um workflow do zero, com a explicação de evento, job, step e runner, foi a aula 08 — se travar no YAML, o manual de lá é o lugar. E os checks de qualidade que barram o merge são a aula 09.

02Versionamento semântico

Antes de criar a tag, decida o número. SemVer é o combinado de três números — MAJOR.MINOR.PATCH — em que cada um promete uma coisa diferente para quem depende do seu projeto.

MAJOR
Quebrei alguma coisa que você já usava. Atualizar vai dar trabalho: leia as notas antes.
MINOR
Tem funcionalidade nova, e o seu código antigo continua funcionando igual.
PATCH
Só correção de bug. Atualize sem medo.

Quebra de contrato é qualquer mudança que faz o código de quem te usa parar de funcionar sem que essa pessoa tenha mexido em nada. Renomear uma função pública, tirar um parâmetro, mudar o formato da resposta de uma API, exigir uma configuração que antes tinha valor padrão. Tudo isso é MAJOR.

Que número sobe?

o que você fezque número sobede → para
Corrigiu um bug, sem mudar mais nadaPATCH1.4.2 → 1.4.3
Melhorou o desempenho, mesmo comportamentoPATCH1.4.3 → 1.4.4
Adicionou uma função novaMINOR1.4.4 → 1.5.0
Adicionou um parâmetro opcional, com valor padrãoMINOR1.5.0 → 1.6.0
Marcou algo como obsoleto, mas ainda funcionandoMINOR1.6.0 → 1.7.0
Renomeou ou apagou uma função públicaMAJOR1.7.0 → 2.0.0
Tornou obrigatório um parâmetro que era opcionalMAJOR2.0.0 → 3.0.0
Mudou o formato da resposta da APIMAJOR3.0.0 → 4.0.0
Subiu a versão mínima de Node exigidaMAJOR4.0.0 → 5.0.0
Corrigiu um erro de português no READMEnenhumdocumentação não vira versão
As duas regras que ninguém decora: quando o MINOR sobe, o PATCH zera. Quando o MAJOR sobe, os dois zeram. De 1.6.4 com quebra você vai para 2.0.0 — nunca para 2.6.4.
E antes do 1.0.0? Tudo com 0.x.y é assumidamente instável: a promessa vale a partir do 1.0.0. Publicar o 1.0.0 é você dizendo “dá para confiar nisto agora”.

Como o commit vira o número

É aqui que a aula 07 volta. Com Conventional Commits, o próprio tipo do commit já diz que número sobe:

fix: corrige total errado com desconto        # PATCH
feat: exporta o relatório em CSV              # MINOR
feat!: remove o endpoint /v1/user            # MAJOR (o ! é a quebra)
chore: atualiza dependências de teste       # nada

O ! depois do tipo — ou um rodapé BREAKING CHANGE: no corpo do commit — é a marca de quebra de contrato. É o que faz o changelog abrir uma seção separada e gritante.

Marcar a versão

03A primeira tag anotada

A tag é uma etiqueta permanente colada num commit. A branch anda a cada merge; a tag fica. É por isso que release se marca com tag.

Leve × anotada

Tag leve — evite

Só um apelido para o hash. Sem autor, sem data, sem mensagem.

git tag v1.0.0

Tag anotada — use esta

Um objeto de verdade no repositório: guarda quem criou, quando e por quê.

git tag -a v1.0.0 -m "primeira versão pública"

Passo a passo

  1. Vá para a main atualizada A tag marca o commit em que você está agora — então esteja no commit certo. 
    git switch main
git pull
git log --oneline -3
  2. Crie a tag anotada O -a é o que transforma a tag num objeto com autor e data. O -m é a mensagem dela. 
    git tag -a v1.0.0 -m "primeira versão pública"
  3. Confira o que você criou 
    git tag
git show v1.0.0
    Você deve ver algo assim — repare no Tagger, que a tag leve não tem:
    $ git show v1.0.0 tag v1.0.0 Tagger: Seu Nome <voce@exemplo.com> Date: Mon Sep 1 10:12:44 2025 -0300 primeira versão pública commit a3f9c2e... (HEAD -> main, tag: v1.0.0, origin/main)
  4. Mande a tag para o GitHub Este é o passo que todo mundo esquece: git push sozinho não leva tag nenhuma. 
    # uma tag específica — o jeito recomendado
git push origin v1.0.0

# ou todas as tags locais de uma vez
git push --tags
  5. Confirme no site Abra o repositório no GitHub e clique no seletor de branch → aba Tags. A v1.0.0 tem que estar lá.
Errou a tag e ainda não publicou? Dá para apagar local e remota — git tag -d v1.0.0 e git push origin --delete v1.0.0. Mas só faça isso nos primeiros minutos, antes de alguém baixar. Tag publicada é imutável na cabeça de quem já usou: erro de versão se conserta com versão nova, não mexendo na antiga.

Comandos úteis de tag

# tags que começam com v1., em ordem de versão
git tag -l "v1.*" --sort=-v:refname

# marcar um commit antigo, que não é o atual
git tag -a v0.9.0 a3f9c2e -m "versão que foi pro cliente"

# o que mudou entre duas versões
git log --oneline v1.0.0..v1.1.0

# em que versão este commit entrou
git describe --tags

04A Release e o changelog

A tag é do Git e vive no repositório. A Release é do GitHub: é a página que pendura na tag um título, um texto de notas e, se você quiser, arquivos prontos para download.

  1. Abra o formulário No repositório, vá em Releases (coluna da direita, na página inicial) e clique em Draft a new release.
  2. Escolha a tag que você já subiu Em Choose a tag, selecione a v1.0.0. Se ela não aparecer na lista, você não deu git push origin v1.0.0 — volte à seção 03.
  3. Dê um título Pode ser o próprio número (v1.0.0) ou o número com um apelido: v1.0.0 — primeira pública.
  4. Clique em “Generate release notes” Este é o botão que faz o trabalho. O GitHub lê todos os commits e PRs desde a tag anterior e monta o changelog sozinho.
  5. Revise e publique Apague o que ficou repetido, escreva uma linha de resumo no topo e clique em Publish release.

Por que o changelog sai bom (ou ruim)

O botão não faz mágica: ele só organiza o que você escreveu. Compare.

Histórico sem padrão

ajustes
agora vai
correções do fulano
testando

Changelog gerado: quatro linhas que não dizem nada. E ninguém consegue decidir se a próxima versão é 1.0.1 ou 2.0.0.

Conventional Commits (aula 07)

feat: exporta relatório em CSV
fix: total errado com desconto
feat!: remove o endpoint /v1/user

Changelog com Features e Bug fixes separados, e o ! avisando que a versão é MAJOR.

Este é o laço da aula 07: aquele padrão de mensagem não era mania de organização. Ele existe para que o changelog e o próximo número de versão saiam sozinhos, sem ninguém abrir o histórico à mão na véspera do lançamento.

Deixar o changelog mais bonito, de graça

Crie este arquivo e o gerador passa a agrupar por tipo e a ignorar o que não interessa:

.github/release.yml
changelog:
  exclude:
    labels:
      - ignore-for-release
  categories:
    - title: 🚨 Mudanças que quebram
      labels: [breaking-change]
    - title: ✨ Novidades
      labels: [feature, enhancement]
    - title: 🩹 Correções
      labels: [bug]
    - title: 📦 Outras
      labels: ["*"]
Pré-release: marque Set as a pre-release quando a versão for v2.0.0-beta.1 ou qualquer coisa que você não quer que as pessoas peguem como estável. A Release fica visível, mas o GitHub para de anunciá-la como “Latest”.
Preparar a produção

05Cadastrar um secret

Para publicar, o workflow quase sempre precisa de uma credencial. Essa credencial não pode estar num arquivo do repositório — é exatamente o vazamento que a aula 09 te ensinou a caçar. O lugar dela é o secret.

  1. Abra o cofre Settings → Secrets and variables → Actions, aba Secrets.
  2. Clique em “New repository secret” Nome em MAIÚSCULAS com sublinhado: TOKEN_DE_DEPLOY. Valor: o token de verdade — ou, para treinar hoje, teste-123.
  3. Salve e tente ver de novo Você não consegue. O GitHub só deixa substituir ou apagar. Se desse para ler de volta, não era cofre.

Como o workflow lê o secret

steps:
  - name: Publica no provedor
    env:
      TOKEN_DE_DEPLOY: ${{ secrets.TOKEN_DE_DEPLOY }}
    run: ./publica.sh

No log do Actions, o valor sai como ***. O arquivo do workflow, que está no repositório e todo mundo lê, tem só o nome do segredo.

Secret × variable

secretvariable
Serve paraToken, senha, chave de APIURL do ambiente, nome do bucket, flag de build
Dá para ler depoisNão, só substituirSim, fica visível
No logSai mascarado como ***Sai como está
Como se lêsecrets.NOMEvars.NOME
O mascaramento cobre descuido, não má-fé. Quem tem permissão de editar um workflow tem, na prática, permissão de imprimir o segredo — basta montar o valor em pedaços que o filtro não reconhece. Nunca dê echo em secret, nem para depurar. E se um vazou: rotacione primeiro, limpe depois — o procedimento é o da aula 09.

06Environment com aprovação

Um environment é um destino nomeado — staging, production — com regras próprias. Ele serve para três coisas: guardar secrets que só valem naquele destino, restringir quem pode publicar ali e, a mais importante hoje, exigir que uma pessoa aprove antes do job rodar.

  1. Crie o environment Settings → Environments → New environment. Nome: production.
  2. Ligue a aprovação manual Marque Required reviewers e adicione você mesmo (ou o time). Até seis pessoas; qualquer uma delas destrava.
  3. Restrinja quem dispara Em Deployment branches and tags, escolha Selected branches and tags e adicione a regra v*. Assim só tag de versão publica em produção.
  4. Guarde o secret aqui, e não no repositório Ainda na tela do environment, Add environment secret. Um secret de environment só é legível por um job que declarou aquele environment — ou seja, por um job que passou pela aprovação.
  5. Amarre o job ao environment É uma linha no YAML: 
    jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: echo "só chego aqui depois que alguém aprovou"

O que você vê quando roda

O job aparece na aba Actions com o estado Waiting e um botão Review deployments. Quem está na lista recebe notificação, abre, escolhe o environment, escreve um comentário opcional e clica em Approve and deploy. Fica registrado quem aprovou, quando e para qual versão.

Deploy contínuo não é deploy sem gente. É deploy que cabe num clique, em vez de trinta passos manuais na mão de uma pessoa só. O arranjo mais comum: staging automático a cada merge na main, production com aprovação a cada tag.

07Ligar o GitHub Pages

O Pages hospeda arquivos estáticos direto do seu repositório, de graça e com HTTPS. É o destino que a gente usa hoje porque não exige conta em lugar nenhum.

Serve bem

Site estático, portfólio, documentação, landing page, o resultado do build de um projeto de front.

Não serve

Qualquer coisa que precise de servidor: banco de dados, login de verdade, API. Não existe backend no Pages.

  1. Abra as configurações do Pages Settings → Pages.
  2. Escolha o Source certo Em Build and deployment → Source, selecione GitHub Actions. Não deixe em “Deploy from a branch”.
  3. Anote o endereço Vai ser https://SEU-USUARIO.github.io/NOME-DO-REPO/. Guarde — é para lá que você olha no fim.
O susto número um desta aula: se o Source ficar em “Deploy from a branch”, o seu workflow roda, fica verde — e o site não muda uma vírgula, porque o Pages está servindo outra coisa. Confira este campo antes de sair caçando erro no YAML.
Repositório privado? No plano gratuito, Pages de repositório privado é público ou não existe, dependendo do plano da conta. Se a aba reclamar, torne o repositório público — para o exercício de hoje não tem problema nenhum.
O deploy

08O workflow de deploy

Agora o arquivo. A mecânica de workflow — evento, job, step, runner, action — é a aula 08; se alguma palavra aqui parecer nova, o manual de lá explica. O que muda no deploy é uma coisa só, e é onde todo mundo trava: permissões.

O arquivo completo

Crie .github/workflows/deploy.yml com este conteúdo. Ele publica a pasta ./site no Pages toda vez que você sobe uma tag que começa com v.

.github/workflows/deploy.yml
name: deploy

# Dispara só em tag de versão. A main continua sendo testada pelo CI da
# aula 09 — o que publica é a tag, não o merge.
on:
  push:
    tags: ['v*']
  workflow_dispatch:

# É AQUI QUE A TURMA INTEIRA TRAVA. Sem estas três linhas o job morre com 403
# na última etapa, depois de o build ter dado tudo certo.
permissions:
  contents: read
  pages: write
  id-token: write

# Um deploy por vez. Sem cancelar o que já começou: deploy pela metade
# é pior que deploy atrasado.
concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Baixa o código
        uses: actions/checkout@v4

      - name: Prepara o Pages
        uses: actions/configure-pages@v5

      - name: Empacota a pasta do site
        uses: actions/upload-pages-artifact@v3
        with:
          # A pasta que tem o index.html. Use ./ se ele está na raiz.
          path: ./site

  deploy:
    needs: build
    runs-on: ubuntu-latest
    # O environment 'github-pages' é criado pelo próprio GitHub.
    # Troque por 'production' se quiser a sua aprovação manual aqui.
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Publica
        id: deployment
        uses: actions/deploy-pages@v4

Linha por linha, o que importa

linhapor que ela existe
tags: ['v*']Só tag que começa com v dispara. Push na main não publica nada.
contents: readLer o código do repositório. Sem isto o checkout falha.
pages: writePublicar no Pages. É a que falta em nove de cada dez 403.
id-token: writeEmitir o token OIDC que prova ao Pages que é este workflow falando. Sem ela, 403 também.
concurrencyDuas tags subidas juntas não brigam pelo mesmo destino.
needs: buildSó publica depois que o pacote existe.
path: ./siteA pasta que vira o site. Errar isto é o segundo motivo de “verde, mas não mudou nada”.
environment: url:Faz o endereço do site aparecer clicável no resumo do job.
Onde ficam as permissions: na raiz do arquivo, na mesma indentação de on: e jobs: — zero espaço antes. Se você indentar por engano, o YAML vira outra coisa e o Actions ignora em silêncio. Depois de colar, confira a coluna.

Se o seu projeto precisa de build

Troque o step que empacota por estes três — é o caso de qualquer projeto de front com npm run build:

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: npm

      - run: npm ci
      - run: npm run build

      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist

Rodar e conferir

  1. Mande o workflow pela main Pelo PR, como sempre — a branch protegida da aula 07 continua valendo. 
    git switch -c ci/deploy-pages
git add .github/workflows/deploy.yml
git commit -m "ci: publica no GitHub Pages a cada tag"
git push -u origin ci/deploy-pages
  2. Depois do merge, suba uma tag 
    git switch main
git pull
git tag -a v1.0.1 -m "primeiro deploy automático"
git push origin v1.0.1
  3. Acompanhe na aba Actions Se você pôs aprovação, o job deploy fica em Waiting até alguém clicar. Aprove.
  4. Abra a URL Ela aparece no resumo do job, no cartão do environment. É a página no ar.

09Quando o destino é outro

Vercel, Netlify, Cloudflare, um servidor da empresa, um bucket na nuvem. A forma do workflow não muda: um evento dispara, um job constrói, um passo autenticado envia. O que muda é de onde vem a autorização e qual é o último step.

peçano GitHub Pagesem outro provedor
Quem autorizapermissions: com pages: write e id-token: writeUm token do provedor, guardado como secret
Onde a credencial moraNão existe credencial: é o OIDC do próprio GitHubsecrets.VERCEL_TOKEN, secrets.CLOUDFLARE_API_TOKEN…
O step que publicaactions/deploy-pages@v4A action oficial deles, ou a CLI: vercel deploy, wrangler deploy, rsync
Onde o site ficausuario.github.io/repoO domínio do provedor, ou o seu
Aprovação manualenvironmentenvironment — igualzinho
RollbackRe-rodar o deploy da versão anteriorRe-rodar, ou o botão “promote” do painel deles

O esqueleto genérico

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production      # a aprovação manual continua aqui
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build

      - name: Envia para o provedor
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
        run: npx --yes alguma-cli deploy --prod
Não decore action, entenda a forma. Toda documentação de provedor descreve a mesma coisa com nomes diferentes. Se você sabe onde entra o secret e qual step publica, trocar de provedor é reescrever um step.
Quando dá errado

10Voltar a versão anterior

Subiu quebrado. A tentação é apagar o commit ruim e fingir que nunca existiu. Não faça isso: a main é compartilhada, e reescrever o histórico dela estraga o repositório de todo mundo que já deu pull.

O procedimento certo tem três tempos, nesta ordem.

1. Pare o sangramento (segundos)

Não corrija código ainda. Só coloque a versão boa de volta no ar.

  1. Ache o deploy da versão anterior Aba Actions → o workflow deploy → a execução da tag v1.0.0.
  2. Clique em “Re-run all jobs” O mesmo commit é construído e publicado de novo. Em poucos minutos o ar volta a ser a versão que funcionava. Se houver aprovação, aprove.
Por que isto é seguro: você não mexeu em uma linha de código nem em uma tag. Só mandou o robô repetir uma publicação que já tinha dado certo.

2. Corrija por cima (minutos ou horas)

Agora, com calma, conserte de verdade — em branch, com PR e CI verde, como qualquer outra mudança. E marque a correção com uma tag nova.

git switch main
git pull

# conserta, commita, abre o PR, faz o merge... e só então:
git tag -a v1.0.2 -m "corrige o deploy quebrado da v1.0.1"
git push origin v1.0.2

O histórico ganhou uma linha. Não perdeu nenhuma. v1.0.1 continua lá, com a sua data e o seu autor, contando o que aconteceu.

3. Sinalize a versão ruim (um minuto)

Abra a Release da v1.0.1, clique em Edit, marque Set as a pre-release e escreva uma linha no topo das notas:

> ⚠️ Esta versão quebra o carregamento da página inicial.
> Use a v1.0.2.

Assim quem chegar daqui a seis meses entende o que houve sem precisar perguntar.

O que NÃO fazer: git push --force na main, apagar a tag ruim para “limpar”, ou apagar a Release. As três apagam a evidência de um incidente que aconteceu de verdade — e a segunda quebra o repositório de quem já baixou aquela tag.
E o git revert? Ele é o comando que desfaz um commit específico criando um commit contrário, sem apagar nada — exatamente a filosofia desta seção. Mas ele, o reset, o reflog, o stash e o cherry-pick são a aula 11 inteira. O rollback de hoje é de deploy: você troca o que está no ar, não o histórico.

12Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
A tag não subiu. Criei, mas não aparece no GitHub git push sozinho não leva tag. Ele só empurra commits da branch. git push origin v1.0.0 para aquela tag, ou git push --tags para todas. Confira depois em Tags, ao lado de Branches.
Error: Resource not accessible by integration (HTTP 403 no fim do deploy) Faltou o bloco permissions. O token padrão do runner não pode publicar no Pages. Acrescente pages: write e id-token: write na raiz do arquivo, sem indentação. Veja a seção 08.
Pus permissions e continua 403 Ou o bloco ficou indentado dentro de jobs:, ou a organização restringe o token padrão a somente leitura. Confira a coluna zero do permissions. Depois, Settings → Actions → General → Workflow permissions: precisa estar em Read and write.
O job ficou verde, mas o site não mudou O Source do Pages está em “Deploy from a branch”. Settings → Pages → Source: GitHub Actions. Depois rode o workflow de novo.
Verde, Source certo, e o site está em branco (ou dá 404) O path: do upload-pages-artifact aponta para pasta sem index.html. Ajuste o path: — ./ se o arquivo está na raiz, ./dist ou ./build se vem de um build.
Empurrei a tag e nenhum workflow rodou O on: não casa com o nome da tag, ou o arquivo do workflow ainda não estava na main quando a tag foi criada. Confira tags: ['v*'] contra o nome que você usou. E lembre: a tag executa o workflow daquele commit — faça o merge antes de taguear.
O job está parado em Waiting e não anda Não é erro: é o environment esperando aprovação. Abra a execução e clique em Review deployments → Approve and deploy. Se o botão não aparece, você não está na lista de Required reviewers.
fatal: tag 'v1.0.0' already exists Você já criou essa tag antes. Use um número novo. Se a antiga era um erro e ninguém baixou ainda: git tag -d v1.0.0 e git push origin --delete v1.0.0.
A Release não encontra a minha tag na lista A tag existe só na sua máquina. git push origin v1.0.0 e recarregue o formulário.
O changelog gerado saiu vazio ou inútil Não há tag anterior para comparar, ou as mensagens de commit não seguem padrão nenhum. Na primeira Release é normal vir cru — escreva à mão. Da próxima, use os Conventional Commits da aula 07: é deles que o texto sai.
secrets.MEU_TOKEN chega vazio no step O secret está no environment e o job não declarou environment:. Ou o nome está diferente — secret diferencia maiúscula de minúscula. Adicione a linha environment: production ao job, ou copie o nome exato da tela de secrets.
Vi um segredo escrito por extenso no log Alguém montou o valor em pedaços, ou deu echo nele. O mascaramento não pega isso. Rotacione o segredo primeiro — gere um token novo e troque o secret. Só depois limpe o log. É o procedimento da aula 09.
Subiu quebrado e eu quero apagar o commit Reescrever a main quebra o repositório de todo mundo que já deu pull. Não apague. Re-rode o deploy da versão anterior, corrija por cima e publique uma tag nova — seção 10. O revert em si é a aula 11.
Não sei se a próxima versão é 1.5.0 ou 2.0.0 A dúvida é sempre a mesma: alguém precisa mudar o código por sua causa? Se sim, é MAJOR. Se é só coisa nova que ninguém é obrigado a usar, é MINOR. Tabela completa na seção 02.
Antes de pedir ajuda: abra a execução na aba Actions e leia o último step vermelho de baixo para cima. O Actions diz o nome do recurso que faltou — e, em deploy, esse nome quase sempre é uma linha ausente do bloco permissions.
