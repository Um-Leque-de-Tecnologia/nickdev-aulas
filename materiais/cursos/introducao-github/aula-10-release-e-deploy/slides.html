Release, versionamento e deploy contínuo

Na aula 09 o robô passou a barrar merge quebrado. Hoje o mesmo repositório passa a publicar sozinho: você marca a versão, a Release sai com changelog e o site sobe no ar.

deixe aberto: o repositório da aula 09, com CI verde na main, e a aba Settings dele.

use ← → pra navegar · manual desta aula

// o problema

“Qual versão está no ar?”

A pergunta mais cara do time. E a resposta, quando não existe release, é sempre a mesma: alguém abre o histórico e chuta.

1O cliente reclama de um bug. Em que commit está o que ele está usando?
2Subiu quebrado às 18h de sexta. Para onde você volta? Para o commit de antes — se souber qual era.
3Outra equipe depende do seu projeto. Você mudou o nome de uma função. Ninguém foi avisado.
4O deploy é o Fulano arrastando arquivo por FTP. Só o Fulano sabe fazer — e ele está de férias.

Hash de commit é endereço, não nome. a3f9c2e não diz nada a ninguém. v1.4.2 diz.

// o conceito

Tag é o nome que você dá a um commit

Pensa numa fita de vídeo com um contador de 40 mil posições. A tag é a etiqueta colada na caixa dizendo “aqui começa o capítulo 3”. A fita não muda — a etiqueta só aponta.

Branch anda

A main aponta para o commit mais novo. A cada merge, ela se move.

Tag fica

v1.0.0 aponta para aquele commit, para sempre. É o marco que não escorrega.

Por isso release se faz com tag, e não com branch: você precisa que “a versão 1.0.0” signifique a mesma coisa daqui a dois anos.

// duas tags, uma certa

Leve × anotada

tag leve

Só um apelido

Um ponteiro solto. Sem autor, sem data, sem mensagem, sem assinatura. Serve para marcador pessoal e temporário.

git tag v1.0.0
tag anotada

Um objeto de verdade

Guarda quem criou, quando e por quê. É a que o GitHub entende bem e a única que faz sentido para release.

git tag -a v1.0.0 -m "primeira versão pública"

Regra prática: se é release, é -a. E a tag só existe no seu computador até você mandar — git push sozinho não leva tag nenhuma.

// versionamento semântico

MAJOR.MINOR.PATCH é uma promessa

SemVer não é numeração bonitinha. É um contrato com quem depende do seu projeto: o número diz o tamanho do susto antes de a pessoa atualizar.

💥
MAJORquebrei o que você já usava. Vai dar trabalho.
·
✨
MINORtem coisa nova, e o seu código antigo continua funcionando.
·
🩹
PATCHconsertei um bug. Atualize sem medo.

Quebra de contrato é qualquer coisa que faz o código de quem te usa parar de funcionar sem ele ter mexido em nada: função renomeada, parâmetro que virou obrigatório, resposta de API com campo a menos. Isso é MAJOR — sempre.

// na prática

Que número sobe?

o que você fezsobede → para
Corrigiu um bug, nada maisPATCH1.4.2 → 1.4.3
Adicionou um parâmetro opcionalMINOR1.4.3 → 1.5.0
Adicionou uma função novaMINOR1.5.0 → 1.6.0
Renomeou uma função públicaMAJOR1.6.0 → 2.0.0
Tornou um parâmetro obrigatórioMAJOR2.0.0 → 3.0.0
Só mexeu no READMEnadadocumentação não vira versão

Quando o MINOR sobe, o PATCH zera. Quando o MAJOR sobe, os dois zeram — 1.6.4 → 2.0.0, nunca 2.6.4. E antes do 1.0.0 vale tudo: 0.x é o aviso de que nada está estável ainda.

LAB 1

A primeira tag anotada

~8 min

No repositório da aula 09, com a main atualizada e o CI verde.

Garanta que você está no commit certo

A tag marca o commit em que você está agora.

git switch main
git pull
git log --oneline -3

Crie a tag anotada

O -a faz a tag guardar autor, data e mensagem.

git tag -a v1.0.0 -m "primeira versão pública"

Confira e mande para o GitHub

git push normal não leva tags. Precisa pedir.

git tag
git show v1.0.0
git push origin v1.0.0
quando terminar

Abra o repositório no GitHub e clique em Tags, ao lado de Branches. A sua v1.0.0 tem que estar lá. Se não estiver, faltou o push da tag.

// github

Release é a tag com roupa de gente

A tag é do Git. A Release é do GitHub: pega a tag e pendura nela um título, um texto de notas e os arquivos prontos para download.

A tag

Qual commit, exatamente. É a âncora — todo o resto pendura aqui.

As notas

O que mudou, em português, para quem não lê commit. O changelog.

Os artefatos

O .zip, o instalador, o binário. Opcional — e o Git nunca guardaria isso bem.

Uma Release também é um evento: dá para disparar workflow com on: release ou com on: push: tags. É esse gancho que a gente usa no deploy, daqui a pouco.

// fechando o laço com a aula 07

O changelog se escreve sozinho — se você deixou

Lembra dos Conventional Commits da aula 07? feat:, fix:, chore:. Aquilo não era firula de organização. Era isto aqui:

histórico sem padrão 
ajustes
agora vai
correções do fulano
testando

Changelog gerado: quatro linhas inúteis. E ninguém sabe se a próxima versão é 1.0.1 ou 2.0.0.

conventional commits 
feat: exportar relatório em CSV
fix: total errado com desconto
feat!: remove o endpoint /v1/user

Changelog em seções, com Features e Bug fixes separados. E o ! grita: é MAJOR.

No GitHub isso é um botão: Generate release notes. Ele lê os commits e os PRs desde a tag anterior e escreve as notas. A qualidade do texto é exatamente a qualidade dos seus commits.

parada obrigatória

Sem seguir sem responder

Quatro perguntas. Daqui pra frente a gente mexe em produção — é melhor travar agora.

1Você fez git tag -a v1.0.0 e depois git push. A tag está no GitHub? Por quê?
2Você tornou obrigatório um parâmetro que era opcional. De 2.3.1 você vai para qual número?
3Qual a diferença entre uma tag e uma Release?
4Por que os commits da aula 07 importam para o changelog de hoje?

respostas: 1 — não, push não leva tag, falta push origin v1.0.0; 2 — 3.0.0, é quebra de contrato; 3 — tag é do Git, Release é a página do GitHub em cima dela.

// o que o robô precisa saber

Secrets: a senha que nunca entra no código

Para publicar, o workflow precisa de credencial. E credencial dentro do repositório é justamente o que a aula 09 te ensinou a caçar. O secret é o cofre: você guarda uma vez em Settings → Secrets and variables → Actions, e o workflow lê pelo nome.

# o valor nunca aparece no arquivo — só o nome dele
env:
  TOKEN_DE_DEPLOY: ${{ secrets.TOKEN_DE_DEPLOY }}

Secret

Valor sensível. Some depois de salvo — nem você lê de volta, só substitui. Sai mascarado como *** no log.

Variable

Configuração que não é segredo — a URL do ambiente, o nome do bucket. Fica visível, e tudo bem.

O mascaramento cobre o descuido, não a má-fé: quem consegue editar um workflow consegue imprimir o segredo. Por isso o próximo assunto é quem tem permissão de mandar em produção.

// o freio de mão

Environment: onde mora o “tem certeza?”

Um environment é um destino nomeado — staging, production — com regras próprias. Ele guarda os secrets daquele destino e, principalmente, pode exigir aprovação humana antes de o job rodar.

O job pede o environment

Uma linha no YAML: environment: production.

O Actions congela o job

Ele fica Waiting. Não roda, não consome, não publica.

Alguém da lista aprova

Chega a notificação e a pessoa clica em Review deployments → Approve and deploy.

Fica registrado

Quem aprovou, quando e para qual versão. Auditoria de graça.

Deploy contínuo não quer dizer “sem ninguém olhando”. Quer dizer um clique, e não trinta passos manuais. Em muitos times: staging automático, production com aprovação.

// o destino de hoje

GitHub Pages: hospedagem que já vem junto

O Pages serve arquivos estáticos direto do seu repositório, de graça, com HTTPS. Perfeito para o que a gente vai fazer hoje: um site que sobe sozinho a cada tag.

Serve bem

Site estático, portfólio, documentação, landing page, o build pronto de um projeto de front.

Não serve

Qualquer coisa com servidor: banco de dados, login de verdade, API. Não existe backend no Pages.

Em Settings → Pages, escolha Source: GitHub Actions. Se ficar em “Deploy from a branch”, o seu workflow roda, fica verde — e o site não muda. É o susto mais comum da aula.

// o workflow

Onde todo mundo trava: permissions

Criar workflow do zero foi a aula 08 — retome o manual dela se precisar. O que muda aqui é que publicar exige permissão explícita, e o padrão do runner não tem.

on:
  push:
    tags: ['v*']

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  deploy:
    environment: github-pages
    runs-on: ubuntu-latest
    steps:
      - uses: actions/deploy-pages@v4

Sem pages: write e id-token: write o job morre com 403 na última linha do log — depois de o build ter dado tudo certo. O YAML inteiro e comentado está no manual.

LAB 2

Secret e environment com aprovação

~10 min

Tudo pela interface do GitHub. Nenhuma linha de terminal aqui.

Cadastre um secret

Settings → Secrets and variables → Actions → New repository secret. Nome TOKEN_DE_DEPLOY, valor teste-123. É de mentira — ninguém vai usar hoje.

Tente ver o valor de novo

Você não consegue. Só dá para substituir. É assim mesmo: se desse para ler de volta, não era cofre.

Crie o environment

Settings → Environments → New environment. Chame de production.

Ligue a aprovação manual

Marque Required reviewers e ponha você mesmo na lista. Salve.

quando terminar

Em duplas: por que o secret de produção fica no environment, e não solto no repositório? Porque assim só um job que passou pela aprovação consegue lê-lo.

LAB 3

O deploy de verdade

~15 min

Da tag ao site no ar. O YAML completo está no manual — copie de lá, não digite.

Ligue o Pages no modo certo

Settings → Pages → Source: GitHub Actions. Sem isso, nada do resto funciona.

Crie o workflow e mande para a main

Pelo PR, como manda a aula 09 — a branch protegida continua valendo.

.github/workflows/deploy.yml

Suba a tag e assista

É a tag que dispara. Vá na aba Actions e acompanhe ao vivo.

git tag -a v1.0.1 -m "primeiro deploy automático"
git push origin v1.0.1

Aprove o deploy

Se você ligou a aprovação, o job espera por você. Clique em Review deployments.

quando terminar

Abra a URL que apareceu no fim do job. Se voltou 403, faltou o bloco permissions. Se ficou verde mas o site não mudou, o Source do Pages ainda está em “Deploy from a branch”.

// quando não é o pages

Troca o destino, o resto continua igual

Vercel, Netlify, Cloudflare, um servidor seu, a nuvem da empresa. A forma é sempre a mesma — muda o passo final e de onde vem a credencial.

peçano github pagesem outro provedor
Quem autorizapages: write + id-token: writeUm token do provedor, guardado como secret
O passo de publicaractions/deploy-pages@v4A action oficial deles, ou a CLI: vercel deploy, wrangler deploy
Onde o site ficausuario.github.io/repoO domínio do provedor, ou o seu
Aprovação manualenvironmentenvironment — igualzinho

Não decore action, entenda a forma: evento dispara → build gera os arquivos → um passo autenticado envia. Trocar de provedor é reescrever um step, não a sua cabeça.

// quando dá ruim

Voltar sem apagar

Subiu quebrado. A tentação é apagar o commit e fingir que não houve. Não faça isso — a main é compartilhada, e reescrever histórico ali estraga o repositório de todo mundo.

Primeiro: pare o sangramento

Abra o deploy da Release anterior e use Re-run all jobs. Em minutos o que está no ar volta a ser a versão boa.

Depois: corrija por cima

Um commit novo que desfaz o estrago, com PR e CI verde, e uma tag nova. O histórico ganha uma linha, não perde nenhuma.

git tag -a v1.0.2 -m "corrige o deploy quebrado"
git push origin v1.0.2

E marque a versão ruim

Na Release problemática, ative Set as pre-release e escreva o porquê nas notas. Quem chegar depois entende.

O comando que desfaz um commit específico sem apagar nada é o git revert — e ele, junto com reset, reflog e stash, é a aula 11 inteira. Hoje o rollback é de deploy, não de commit.

// erros comuns

Os cinco tropeços de sempre

1A tag não subiu. git push não leva tag. É git push origin v1.0.0 — ou git push --tags para todas.
2403 no fim do deploy. Faltou o bloco permissions, com pages: write e id-token: write.
3Job verde, site igual. O Source do Pages não está em GitHub Actions. Ou o path do upload aponta para a pasta errada.
4Corrigir a tag mexendo nela. Tag publicada é imutável na cabeça de quem já baixou. Erro de versão se conserta com versão nova.
5Segredo impresso no log. O mascaramento não pega valor montado em pedaços. Nunca dê echo em secret — e se vazou, rotacione, como na aula 09.

Cada um destes está na tabela “Se travar” do manual, com o conserto passo a passo.
