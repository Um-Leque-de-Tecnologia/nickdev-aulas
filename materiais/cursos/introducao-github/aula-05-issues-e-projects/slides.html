Issues, labels, milestones e Projects

No fim de hoje o seu repositório tem issues que outra pessoa consegue pegar, um conjunto de labels, um milestone com data, um template que barra o "não funciona" — e um quadro mostrando o trabalho andar.

// o problema

O relato de bug mais comum do mundo

issue #41 · aberta por @alguem
título: nao funciona

corpo:  ta dando erro na hora de salvar

        alguem olha ai pfv

Não é má vontade. É a pessoa achando que o que está óbvio na cabeça dela está óbvio na sua.

1Salvar o quê? Que tela, que formulário, que botão?
2Como chegar lá? Quem for consertar precisa ver o erro acontecer.
3Erro qual? A mensagem inteira, não a lembrança dela.
4O que deveria ter acontecido? Às vezes o "bug" é o programa fazendo o certo.
5Onde? Navegador, sistema, versão. Bug que só existe num lugar é a maioria deles.

Issue mal escrita não custa cinco minutos: custa três dias de ida e volta. Cada pergunta ali em cima vira um comentário, e cada comentário espera a outra pessoa acordar.

// o conceito

Issue é uma conversa com um assunto só

Pense numa ordem de serviço. Tem número, tem descrição do problema, tem quem pediu, tem quem vai fazer — e sai da parede quando o serviço acaba.

Tem número para sempre

A #12 é a décima segunda coisa que alguém abriu ali. O número nunca é reaproveitado — dá pra citar em qualquer lugar, pra sempre.

Tem estado, e só dois

Aberta ou fechada. O GitHub não tem "quase pronto" — quem inventa os estados do meio é o quadro, no fim da aula.

É Markdown

O mesmo da aula 04: título, lista, bloco de código, caixinha de tarefa. Uma issue bem formatada se lê em dez segundos.

Serve pra bug, pra ideia de funcionalidade, pra tarefa de documentação e pra pergunta interna. Não serve pra três assuntos ao mesmo tempo — aí vira issue que nunca fecha.

// anatomia

As cinco partes de uma issue que se resolve

Título específico

Uma frase que já diz o problema. Salvar cadastro com CEP vazio derruba a página — não erro no cadastro.

Contexto

Duas linhas: o que você estava tentando fazer e por que isso importa. É o que separa urgente de chato.

Passo a passo para reproduzir

Numerado, do zero, como se fosse pra alguém que nunca abriu o sistema. É a parte que mais falta e a que mais vale.

Esperado × obtido

Duas linhas, uma embaixo da outra. Sem elas, quem lê tem que adivinhar qual dos dois comportamentos você considera o certo.

Ambiente

Versão, navegador, sistema. E, se houver, a mensagem de erro copiada inteira — não descrita, não lembrada.

Numa issue de funcionalidade, os passos viram critério de aceite: como a gente vai saber que ficou pronto?

// o texto de verdade

O corpo da issue, em Markdown

corpo da issue #12
## Contexto
Ao cadastrar cliente sem CEP, a página cai
e o formulário some. Acontece toda vez.

## Passos para reproduzir
1. Abrir a tela de cadastro
2. Preencher só o campo Nome
3. Clicar em Salvar

## Resultado esperado
Aviso "CEP é obrigatório" abaixo do campo.

## Resultado obtido
Tela branca. No console do navegador:
TypeError: Cannot read properties of null

## Ambiente
- v1.4.2 · Chrome 129 · Windows 11
- Reproduz também no Firefox 131

Por que este formato ganha

  • Os títulos ## deixam a issue varrível: dá pra achar o passo 2 sem ler o resto.
  • A mensagem de erro está copiada, então dá pra procurar por ela dentro do código.
  • "Reproduz também no Firefox" já elimina metade das hipóteses.
  • O Markdown é o mesmo da aula 04 — você não aprendeu nada novo aqui, só passou a usar no lugar certo.

Caixinha de tarefa (- [ ]) funciona dentro da issue, e o GitHub conta quantas já foram marcadas. Ótimo pra issue com três subtarefas óbvias.

LAB 1

A sua primeira issue de verdade

~10 min

No seu repositório da aula 04. Aba Issues → botão New issue. Se a aba não aparecer, ela está desligada em Settings → Features.

Escolha um incômodo real do seu projeto

Um link quebrado no README, uma instrução que falta, um botão sem estilo. Real é bem melhor que inventado.

Escreva o título como uma frase

Sujeito, verbo, problema. Se o título sozinho na lista de issues já fizer sentido, está bom.

Preencha as cinco partes

Contexto, passos, esperado, obtido, ambiente — cada uma com o seu ##.

## Contexto
## Passos para reproduzir
## Resultado esperado
## Resultado obtido
## Ambiente

Antes de enviar, use a aba Preview

É onde você descobre que a lista não virou lista porque faltou uma linha em branco antes dela.

quando terminar

Troque de cadeira com quem está do lado e leia a issue da outra pessoa. Você conseguiria reproduzir? Se a resposta for "acho que sim", falta alguma coisa.

// labels

Cinco labels resolvem a vida de um time pequeno

labelquando usar
bugEstá quebrado. Alguma coisa faz o que não devia fazer.
featureNão existe ainda, e a gente quer que exista.
docsO código está certo; o texto que explica é que não está.
good first issuePequena, isolada, com o caminho descrito. A porta de entrada de quem chega.
blockedNão dá pra andar por causa de outra coisa. Diga qual, no comentário.
1Label é filtro, não enfeite. Se ninguém filtra por ela, ela não deveria existir.
2Comece com cinco. Trinta labels no primeiro mês é um jeito elegante de não classificar nada.
3A label diz o tipo; a coluna do quadro diz o estado. Misturar os dois é o erro clássico.
4good first issue tem esse nome exato porque o próprio GitHub usa a label pra recomendar o seu projeto a iniciantes.
5Apague as de fábrica que você não usa. duplicate, wontfix e invalid ficam — são respostas de fechamento.

Onde ficam: Issues → Labels → New label. Nome, descrição e cor. Escreva a descrição — ela aparece no mouse por cima, e é ela que evita duas pessoas usando a mesma label pra coisas diferentes.

parada obrigatória

Sem seguir sem responder

Três perguntas. O resto da aula — template e quadro — só faz sentido se estas estiverem firmes.

1Qual é a parte da issue que mais falta na prática — e por que é justo a que mais economiza tempo?
2A label diz o tipo da issue. Quem diz o estado dela?
3Você abriu uma issue que precisa de outra pra andar. O que você escreve nela?

respostas: 1 — o passo a passo para reproduzir; 2 — a coluna do quadro, que a gente monta daqui a pouco; 3 — a label blocked e um comentário citando #numero da outra.

// milestones

Milestone é o pacote com data

A label agrupa por tipo. A milestone agrupa por entrega: um conjunto de issues que fazem sentido juntas e têm um prazo.

milestone v1.1 — lançamento de outubro prazo 31/10/2026 7 de 12 concluídas · 58% #12 Salvar cadastro com CEP vazio derruba a página #14 Tela de login sem estado de carregando #19 README sem instrução de instalação
1Uma issue tem uma milestone só. Isso força a pergunta boa: isto entra nesta entrega, ou não?
2A barra de progresso é automática — ela conta issues fechadas. Não é chute de gerente.
3Chegou a data e sobrou coisa? Mova pra próxima milestone. Milestone que fica aberta pra sempre parou de significar alguma coisa.
4Nomeie pelo que alguém de fora entende: v1.1, MVP, Sprint 4. Versão de verdade, com tag e release, é a aula 10.

Onde ficam: Issues → Milestones → New milestone. Título, data e uma descrição de duas linhas dizendo o que essa entrega significa.

// responsáveis

Uma pessoa por issue — e ela sabe disso

Assignee

Quem está fazendo. O GitHub aceita mais de um, mas dois donos é o mesmo que nenhum: alguém precisa ser a pessoa a quem se pergunta.

Menção com @

@fulano num comentário notifica a pessoa. Serve pra pedir opinião sem transferir a tarefa.

Issue sem dono

É o normal do backlog, e está tudo certo. Só não pode ser o estado de uma issue que alguém jurou que estava fazendo.

  • Atribuir não é mandar. Em time saudável, a pessoa se atribui quando pega — e isso vira o sinal público de "esta é minha, não mexe".
  • Sem responsável e sem quadro, duas pessoas consertam o mesmo bug na quinta-feira. Já aconteceu com todo mundo.
  • Vai parar no meio? Tire o seu nome e comente o que já descobriu. A próxima pessoa começa de onde você parou.
  • Quem revisa o código não é o assignee — é o reviewer, e ele aparece no Pull Request, na aula 06.

1Escrever #9 cria um link nos dois sentidos: a #9 passa a mostrar que alguém a citou. Rastro de graça.
2Feche com um comentário explicando, nunca no silêncio. Quem abriu merece saber o que foi feito.

5Tem um jeito de a issue fechar sozinha quando o código entra — Closes #12 na descrição do Pull Request. É a aula 06.

formuláriocom os campos obrigatórios já ali
  • Os arquivos moram em .github/ISSUE_TEMPLATE/, na branch principal do repositório. Fora dali, o GitHub não enxerga.
  • O formato moderno é o issue form, em YAML (.yml): campos de verdade, com validação.
  • O arquivo config.yml desliga a issue em branco e manda pergunta pra outro lugar.
  • Template de Pull Request é outro arquivo e outra aula — aula 06.

Template é a sua regra de qualidade escrita uma vez. Depois ela trabalha sozinha, pra sempre, com gente que você nunca vai conhecer.

// issue form

O template, por dentro

.github/ISSUE_TEMPLATE/bug.yml
name: Relato de bug
description: Alguma coisa não funciona
title: "[bug]: "
labels: ["bug"]
body:
  - type: textarea
    id: passos
    attributes:
      label: Passo a passo para reproduzir
      description: Numere. Alguém vai seguir na mão.
      value: |
        1.
        2.
        3.
    validations:
      required: true
1title e labels já chegam preenchidos na issue. Ninguém mais esquece de rotular.
2Os tipos de campo: input, textarea, dropdown, checkboxes e markdown — este último é texto fixo, só pra ler.
3required: true é a linha que faz o trabalho todo: sem ela preenchida, o botão de enviar não libera.
4value deixa o campo começar com um esqueleto — 1. 2. 3. convida a numerar.
5YAML é sensível a indentação: só espaço, nunca tabulação. O arquivo inteiro está no manual, pronto pra copiar.

LAB 2

Instalar o template no repositório

~12 min

Dá pra fazer direto pelo site — e hoje a gente faz pelo site, pra você ver o efeito na hora.

Crie o arquivo pelo próprio GitHub

Add file → Create new file. Digite o caminho inteiro no nome: as barras criam as pastas sozinhas.

.github/ISSUE_TEMPLATE/bug.yml

Cole o YAML do manual e commite na branch principal

Mensagem: chore: template de issue para bug. Confira a indentação antes de salvar.

Repita para o config.yml

Ele desliga a issue em branco e oferece um link de contato no lugar. Também está no manual.

Teste como quem chega de fora

Vá em Issues → New issue. Em vez da caixa vazia, aparece a lista de tipos.

quando terminar

Abra o formulário e tente enviar vazio. Ele tem que recusar. Se enviou, ou faltou o required: true, ou o arquivo não está na branch principal.

// github projects

O quadro que mostra o trabalho andando

A lista de issues responde "o que existe?". Ela não responde "em que pé está?". Quem responde isso é o Project.

Project · Time do site Backlog #19 #23 #24 #27 Refinamento #21 Em andamento #12 (nicoly) Em revisão #14 (joao) Pronto #08 #11
1O cartão é a issue, não uma cópia dela. Mudou o título lá, mudou aqui.
2Fechou a issue, o cartão anda sozinho pra Pronto — o Project já vem com esse fluxo ligado.
3Um Project junta issues de vários repositórios. É o quadro do time, não o quadro do repositório.
4Além do quadro, o mesmo Project vira tabela e linha do tempo — é a mesma informação, vista de outro jeito.
5Automatizar o quadro de verdade — mover cartão quando o teste passa, por exemplo — é Actions, na aula 08.
// as colunas

Coluna só vale se alguém move

O que mata um quadro

  • Doze colunas. Ninguém lembra a diferença entre "Em análise" e "Sendo analisado".
  • Coluna que descreve desejo — "Prioridade alta" — em vez de estado. Prioridade é campo, não coluna.
  • Quinze cartões em "Em andamento". Isso não é andamento, é pilha.
  • Quadro que só o líder atualiza. Duas semanas depois ele mente, e todo mundo sabe.

O que funciona

  • Quatro ou cinco colunas. Cada uma responde a uma pergunta clara sobre a issue.
  • Um limite combinado em "Em andamento" — duas por pessoa é um bom começo.
  • Quem pega move o cartão e se atribui à issue. Um gesto, dois sinais.
  • O quadro é olhado junto, uma vez por semana. Quadro que ninguém abre já morreu.

A coluna diz o estado; a label diz o tipo; a milestone diz a entrega. Três eixos diferentes — quando um começa a fazer o trabalho do outro, o quadro fica confuso.

// vocabulário de processo

As palavras que vêm junto com o quadro

backlog
Tudo que a gente quer fazer e ainda não começou. É uma lista de intenções, não uma promessa. Backlog pode e deve ser podado.
refinamento
A conversa que transforma ideia solta em issue executável: passos, critério de aceite, tamanho. É onde a issue mal escrita é consertada — antes de alguém pegar.
critério de aceite
A lista que diz como se sabe que acabou. Escrita antes de começar, senão vira opinião no fim.
em andamento
Alguém está fazendo agora. Se você não trabalhou nisso hoje, o cartão provavelmente está na coluna errada.
pronto
Combinado uma vez, pro time inteiro: código na branch principal, revisado, testado, documentado. "Funciona na minha máquina" não é pronto.
bloqueada
Depende de outra coisa pra andar. Fica visível — label blocked mais um comentário dizendo do que depende.

Você vai ouvir esse vocabulário em toda entrevista e em todo time. Ele não é do GitHub — o GitHub só deu botões pra ele.

LAB 3

Montar o quadro e ligar as issues

~15 min

Você precisa de pelo menos três issues abertas. Se só tem uma, abra mais duas rapidinho — tarefa pequena serve.

Crie o Project

No seu perfil, aba Projects → New project → modelo Board. Dê o nome do time ou do produto, não "Projeto 1".

Ajuste as colunas

Ele nasce com três. Renomeie e acrescente até ficar assim:

Backlog · Refinamento · Em andamento · Em revisão · Pronto

Puxe as suas issues pra dentro

Botão Add item → digite # e o número, ou procure pelo título. Faça com as três.

Encene uma semana

Mova uma pra Em andamento e atribua a você. Feche outra pela aba Issues e volte no quadro pra ver o cartão andar sozinho.

Crie a milestone e ponha duas issues nela

Issues → Milestones → New milestone, com data. Depois abra cada issue e escolha a milestone na barra da direita.

quando terminar

Olhe o quadro e responda em voz alta: quem está fazendo o quê agora? Se você precisou abrir uma issue pra descobrir, falta assignee em algum cartão.
