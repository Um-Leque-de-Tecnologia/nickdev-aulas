Issues, labels, milestones e Projects

O passo a passo para você organizar o trabalho sozinha, no seu ritmo: abrir uma issue que outra pessoa consegue pegar, criar o conjunto de labels, criar um milestone, instalar um template que barra o "não funciona" e montar um quadro com as suas issues dentro. Nenhuma linha de código nesta aula — e é de propósito.

Antes de começar

01O que você vai fazer aqui

Este manual é o passo a passo da aula 05 para você refazer sozinha, do zero. No fim você tem: três issues bem escritas, cinco labels, um milestone com data, um template de issue instalado no repositório e um Project com as issues ligadas a ele.

Você vai precisar de: uma conta no GitHub, o repositório que ficou apresentável na aula 04 e uns 50 minutos. Nada disso passa pelo terminal — é tudo pelo site.

Continuidade: tudo que você escrever aqui é Markdown, o mesmo da aula 04. Título com ##, lista com -, bloco de código com três crases, caixinha de tarefa com - [ ]. Se estiver enferrujado, abra o README daquela aula ao lado.

O vocabulário mínimo

issue
Uma conversa com um assunto só dentro do repositório: um bug, uma ideia, uma tarefa. Ganha um número (#12) que nunca é reaproveitado, e tem dois estados: aberta ou fechada.
label
Uma etiqueta que diz o tipo da issue — bug, docs. Uma issue pode ter várias.
milestone
Um pacote de issues com data de entrega. Uma issue tem no máximo uma.
assignee
A pessoa responsável pela issue. Quem está fazendo, não quem pediu.
Project
O quadro do time: colunas com o estado real de cada issue. Vive fora do repositório e pode juntar issues de vários.
Fora do escopo de hoje: fazer a issue fechar sozinha quando o código entra, com Closes #12 na descrição do Pull Request, é a aula 06. Automatizar o quadro com robô — mover cartão quando o teste passa — é Actions, na aula 08. Discussions, que é o lugar de pergunta e não de tarefa, é a aula 12.

02A anatomia de uma issue

Antes de abrir qualquer coisa, o critério. A issue está boa quando alguém que nunca viu o seu projeto consegue reproduzir o problema só com o que está escrito ali. Não é rigor por rigor: cada informação que falta vira um comentário, e cada comentário espera a outra pessoa acordar.

A mesma issue, escrita de dois jeitos

Como chega na maioria dos repositórios

nao funciona ta dando erro na hora de salvar alguem olha ai pfv

Quatro perguntas antes de escrever a primeira linha de código: salvar o quê, como chegar lá, qual erro e o que deveria ter acontecido.

A mesma pessoa, três minutos a mais

Salvar cadastro com CEP vazio derruba a página passos · esperado · obtido · ambiente tudo preenchido, erro copiado inteiro

Quem for consertar começa pelo conserto. É essa a diferença que o resto desta seção descreve.

As cinco partes

  1. Título específico Uma frase que já diz o problema, e que faz sentido sozinha na lista de issues. Salvar cadastro com CEP vazio derruba a página, não erro no cadastro.
  2. Contexto Duas linhas: o que você estava tentando fazer e por que isso importa. É o que separa urgente de chato.
  3. Passo a passo para reproduzir Numerado, do zero, como se fosse para alguém que nunca abriu o sistema. É a parte que mais falta e a que mais economiza tempo.
  4. Resultado esperado × resultado obtido Duas linhas, uma embaixo da outra. Sem elas, quem lê tem que adivinhar qual dos dois comportamentos você considera o certo — e às vezes o "bug" é o programa fazendo exatamente o que foi pedido.
  5. Ambiente Versão, navegador, sistema. E a mensagem de erro copiada inteira, não descrita de memória: é por ela que quem conserta busca dentro do código.
Para issue de funcionalidade — coisa que ainda não existe — os passos viram critério de aceite: a lista que responde "como a gente vai saber que ficou pronto?". Escrita antes de começar, senão vira opinião no fim.
Um assunto por issue. "Arrumar o cadastro, melhorar o rodapé e revisar o README" é uma issue que nunca fecha, porque sempre sobra um terço dela. Três assuntos, três issues — e se elas dependem uma da outra, cite o número de uma na outra.
Abrir e organizar

03Abrir a primeira issue

Abra o seu repositório e vá na aba Issues → botão verde New issue. Se a aba não existir, ela está desligada: Settings → Features → marque Issues.

O modelo, pronto para copiar

Cole isto no corpo da issue e troque o conteúdo de cada bloco. Os títulos ## são o que deixa a issue varrível — dá para achar o passo 2 sem ler o resto.

corpo da issue · markdown
## Contexto
Uma ou duas frases: o que você estava tentando fazer
e por que isso importa.

## Passos para reproduzir
1. Abrir a tela X
2. Preencher só o campo Y
3. Clicar em Z

## Resultado esperado
O que deveria ter acontecido, em uma frase.

## Resultado obtido
O que aconteceu de verdade. Cole a mensagem de erro
inteira aqui, entre crases:

```
TypeError: Cannot read properties of null
```

## Ambiente
- Versão: v1.4.2
- Navegador: Chrome 129
- Sistema: Windows 11

## Observações
Reproduz também no Firefox 131. Não acontece quando
o CEP está preenchido.

Um exemplo preenchido, para você ver o resultado:

issue #12 · título
Salvar cadastro com CEP vazio derruba a página
Antes de enviar, clique em Preview. É ali que você descobre que a sua lista numerada não virou lista — quase sempre porque faltou uma linha em branco antes dela.

A barra da direita

Depois de criar a issue, a coluna da direita é onde você a organiza. Vamos preencher cada campo nas próximas seções:

Faça três. Uma de bug, uma de feature e uma de docs. Você vai precisar das três para montar o quadro na seção 08, e três é o mínimo para um quadro parecer um quadro.

04O conjunto inicial de labels

Vá em Issues → Labels → New label. Cada label tem nome, descrição e cor. Escreva a descrição: ela aparece quando alguém passa o mouse por cima, e é ela que evita duas pessoas usando a mesma etiqueta para coisas diferentes.

Este conjunto de cinco cobre um time pequeno inteiro. Nome, descrição e cor, um por linha:

o conjunto inicial
bug
Está quebrado: alguma coisa faz o que não devia.
cor #d73a4a

feature
Não existe ainda e a gente quer que exista.
cor #0e8a16

docs
O código está certo; o texto que explica é que não está.
cor #0075ca

good first issue
Pequena, isolada e com o caminho descrito. Porta de entrada.
cor #7057ff

blocked
Não dá para andar por causa de outra coisa. Diga qual no comentário.
cor #b60205

Algumas das cinco já vêm de fábrica com esse nome — bug, documentation, good first issue. Aproveite as que existem, renomeie o que quiser e apague o resto.

As regras que fazem a label servir para alguma coisa

  • Label é filtro, não enfeite. Se ninguém filtra por ela, ela não deveria existir.
  • Comece com cinco. Trinta labels no primeiro mês é um jeito elegante de não classificar nada.
  • A label diz o tipo; a coluna do quadro diz o estado. Se você criar uma label em andamento, ela vai brigar com o quadro da seção 08 e as duas vão mentir.
  • good first issue tem esse nome exato de propósito: o próprio GitHub usa essa label para recomendar o seu repositório a quem está começando. Escrever bem essas issues é o que traz gente nova.
  • Guarde duplicate, wontfix e invalid, que vêm de fábrica. Não são tipos de trabalho — são respostas de fechamento.

Filtrar por label

A caixa de busca da aba Issues entende uma linguagem própria. Estas quatro resolvem quase tudo:

busca da aba Issues
# bugs abertos, sem responsável
is:issue is:open label:bug no:assignee

# o que é bom para quem está chegando
is:issue is:open label:"good first issue"

# o que está travado e precisa de conversa
is:issue is:open label:blocked

# o que é meu
is:issue is:open assignee:@me
Repare: label com espaço no nome vai entre aspas — label:"good first issue". Sem as aspas, o GitHub entende duas buscas separadas e não acha nada.

05Criar um milestone

Vá em Issues → Milestones → New milestone. São três campos: título, data e descrição.

  1. Título Um nome que alguém de fora entende: v1.1, MVP, Sprint 4, Lançamento de outubro.
  2. Data de entrega Ponha uma. Milestone sem data é uma label mal disfarçada.
  3. Descrição Duas linhas dizendo o que essa entrega significa — não a lista de issues, que o próprio GitHub já mostra.
  4. Ligue as issues Abra cada issue, clique em Milestone na barra da direita e escolha. Ou, na lista de issues, marque várias e use o menu Milestone no topo para fazer tudo de uma vez.

Pronto isso, a página da milestone passa a mostrar sozinha em que pé a entrega está:

milestone v1.1 — lançamento de outubro prazo 31/10/2026 7 de 12 concluídas · 58% #12 Salvar cadastro com CEP vazio derruba a página #14 Tela de login sem estado de carregando #19 README sem instrução de instalação
o que agrupapor quêquantas por issue
labelPelo tipo do trabalho.Várias.
milestonePela entrega e pela data.Uma só.
coluna do ProjectPelo estado atual.Uma só, por quadro.
Quando a data chegar e sobrar coisa: mova o que sobrou para a próxima milestone e feche esta. Milestone que fica aberta para sempre parou de significar alguma coisa, e a barra de progresso vira decoração.
Não confunda com release. Milestone é planejamento — o que a gente pretende entregar. Release é o pacote publicado, com tag e changelog, e é a aula 10.

06Responsáveis e referência cruzada

Duas coisas pequenas que evitam o desperdício mais comum de um time: duas pessoas consertando o mesmo bug na quinta-feira.

Assignee: quem está fazendo

  • Na barra da direita da issue, clique em Assignees. O atalho assign yourself se atribui em um clique.
  • O GitHub aceita mais de um responsável, mas dois donos é o mesmo que nenhum: alguém precisa ser a pessoa a quem se pergunta.
  • Atribuir não é mandar. Em time saudável a pessoa se atribui quando pega — e isso vira o sinal público de "esta é minha, não mexe".
  • Vai parar no meio? Tire o seu nome e comente o que já descobriu. A próxima pessoa começa de onde você parou, não do zero.
  • Issue sem dono é o normal do backlog. Só não pode ser o estado de uma issue que alguém jurou que estava fazendo.
Assignee não é revisor. Quem revisa o código é o reviewer, e ele aparece no Pull Request — aula 06.

Citar outra issue, chamar alguém, fechar explicando

Tudo isto se escreve no corpo de um comentário, em texto puro:

comentários em issues
# citar outra issue deste repositório
Bloqueada pela #9 — sem o endpoint novo não dá
para validar o CEP.

# citar issue de outro repositório
Mesmo caso da nickdev/api#31.

# chamar alguém sem transferir a tarefa
@nicoly isso muda o contrato da API?

# fechar explicando, no mesmo comentário
Resolvido no commit a1c9f0e: o campo agora valida
antes de enviar. Fechando.
  • Escrever #9 cria um link nos dois sentidos: a #9 passa a mostrar, no histórico dela, que alguém a citou. Rastro de graça.
  • Feche com um comentário, nunca no silêncio. Quem abriu a issue merece saber o que foi feito — e, seis meses depois, você também.
  • Não vai fazer? Feche assim mesmo, dizendo por quê, e ponha wontfix. Issue aberta há dois anos é ruído: ela some da cabeça de todo mundo mas continua contando na lista.
  • Fechar não apaga nada. Número, texto e discussão continuam lá, e reabrir é um clique.
Existe um jeito de a issue fechar sozinha quando o código entra: a frase Closes #12 na descrição do Pull Request. Não é hoje — é a aula 06, junto com o resto do PR. Por enquanto, feche na mão e explique.
Padronizar o que chega

07O template de issue

Você não vai convencer cem pessoas a escrever bem uma issue. Mas você pode fazer o campo ser obrigatório. É isso que um template de issue faz: em vez da caixa de texto vazia, quem clica em New issue recebe um formulário com os campos certos já ali.

Os arquivos moram em .github/ISSUE_TEMPLATE/, na branch principal. Fora dali o GitHub não enxerga.

Como criar o arquivo pelo site

  1. Add file → Create new file No topo da página do repositório.
  2. Digite o caminho inteiro no nome As barras criam as pastas sozinhas. Repare no ISSUE_TEMPLATE em maiúsculas — o GitHub é exigente com isso.
  3. Cole o conteúdo Os dois arquivos completos estão logo abaixo.
  4. Commite direto na principal Com a mensagem chore: template de issue para bug.
caminho do arquivo
.github/ISSUE_TEMPLATE/bug.yml

O formulário de bug, completo

Este é o arquivo inteiro. Cole como está e depois ajuste os textos para o seu projeto.

.github/ISSUE_TEMPLATE/bug.yml
name: Relato de bug
description: Alguma coisa não está funcionando como deveria
title: "[bug]: "
labels: ["bug"]
body:
  - type: markdown
    attributes:
      value: |

        mais rápido o conserto — preencha tudo que der.

        1.

      required: true

O config.yml: desligar a issue em branco

Sem ele, o link "abrir uma issue em branco" continua aparecendo — e é por ele que o "não funciona" volta a entrar.

.github/ISSUE_TEMPLATE/config.yml
blank_issues_enabled: false
contact_links:
  - name: Dúvida de uso
    url: https://github.com/SEU-USUARIO/SEU-REPO/discussions
    about: Pergunta não é bug. Pergunte nas Discussions.
Troque SEU-USUARIO/SEU-REPO pelo seu. E ligue as Discussions em Settings → Features antes, senão o link vai para uma página que não existe. Discussions é assunto da aula 12; aqui ele entra só como destino de desvio.

Teste como quem chega de fora: vá em Issues → New issue. Em vez da caixa vazia, tem que aparecer a lista com os dois tipos. Abra o de bug e tente enviar vazio — ele precisa recusar. Se enviou, ou faltou o required: true, ou o arquivo não está na branch principal.
YAML é sensível a indentação. Só espaço, nunca tabulação, e dois espaços por nível. Se o GitHub reclamar de sintaxe ao salvar, cole o modelo de novo e edite por cima em vez de caçar o espaço perdido.
O quadro do time

08Montar o Project

A lista de issues responde "o que existe?". Ela não responde "em que pé está?". Quem responde isso é o Project — o quadro, com uma coluna por estado.

  1. Crie o quadro No seu perfil, aba Projects → New project → modelo Board. Em uma organização, o caminho é o mesmo, dentro da org.
  2. Dê um nome de verdade O nome do time ou do produto. "Projeto 1" não diz nada para quem entra depois.
  3. Ajuste as colunas Ele nasce com três. Renomeie e acrescente até chegar em cinco.
  4. Puxe as issues Botão Add item na última coluna, digite # e o número — ou procure pelo título. Faça com as três issues da seção 03.
  5. Encene uma semana Mova uma para Em andamento e se atribua a ela. Depois feche outra pela aba Issues e volte ao quadro: o cartão anda sozinho para Pronto.
as cinco colunas
Backlog · Refinamento · Em andamento · Em revisão · Pronto

O quadro cheio se parece com isto:

Project · Time do site Backlog #19 #23 #24 #27 Refinamento #21 Em andamento #12 (nicoly) Em revisão #14 (joao) Pronto #08 #11

O que é bom saber sobre o Project

  • O cartão é a issue, não uma cópia dela. Mudou o título na issue, mudou no cartão.
  • Um Project junta issues de vários repositórios. É o quadro do time, não o quadro do repositório.
  • Além do quadro, o mesmo Project vira tabela e linha do tempo — botão + ao lado do nome da visão. É a mesma informação, vista de outro jeito.
  • Dá para criar campos próprios: prioridade, estimativa, área. Um de cada vez, e só quando alguém sentir falta.
  • Project pode ser público ou privado, independente do repositório. Confira isso antes de escrever nome de cliente em cartão.
Automatizar de verdade — mover o cartão quando o teste passa, avisar no chat quando alguém pega uma issue — é trabalho de Actions, na aula 08. O fluxo padrão que o Project já traz (fechou a issue, foi para Pronto) você liga em Workflows, dentro do próprio quadro, sem escrever nada.

09O vocabulário do quadro

As colunas trazem um vocabulário junto. Ele não é do GitHub — é de como times trabalham; o GitHub só deu botões para ele. Você vai ouvir estas palavras em toda entrevista e em todo time.

backlog
Tudo que a gente quer fazer e ainda não começou. É uma lista de intenções, não uma promessa — e pode, e deve, ser podada.
refinamento
A conversa que transforma ideia solta em issue executável: passos, critério de aceite, tamanho. É onde a issue mal escrita é consertada, antes de alguém pegar.
critério de aceite
A lista que diz como se sabe que acabou. Escrita antes de começar, senão vira opinião no fim.
trabalho em andamento
Alguém está fazendo agora. Se você não trabalhou nisso hoje, o cartão provavelmente está na coluna errada.
pronto
Combinado uma vez, para o time inteiro: na branch principal, revisado, testado, documentado. "Funciona na minha máquina" não é pronto.
bloqueada
Depende de outra coisa para andar. Fica visível: label blocked e um comentário citando de que issue ela depende.

O que mata um quadro, e o que o mantém vivo

Mata

  • Doze colunas — ninguém lembra a diferença entre "Em análise" e "Sendo analisado".
  • Coluna que descreve desejo ("Prioridade alta") em vez de estado. Prioridade é campo, não coluna.
  • Quinze cartões em "Em andamento". Isso não é andamento, é pilha.
  • Quadro que só o líder atualiza. Duas semanas depois ele mente, e todo mundo sabe.

Mantém vivo

  • Quatro ou cinco colunas, cada uma respondendo a uma pergunta clara.
  • Um limite combinado em "Em andamento" — duas por pessoa é um bom começo.
  • Quem pega move o cartão e se atribui à issue: um gesto, dois sinais.
  • O quadro é olhado junto, uma vez por semana. Quadro que ninguém abre já morreu.
A regra que evita a confusão mais comum: a coluna diz o estado, a label diz o tipo e a milestone diz a entrega. São três eixos diferentes. No dia em que um deles começa a fazer o trabalho do outro — uma label chamada em andamento, por exemplo — os dois passam a mentir.

11Se travar

Ache o sintoma na primeira coluna — é quase sempre um destes.

sintomacausaconserto
A aba Issues não aparece no repositório Ela foi desligada. Em fork, vem desligada de fábrica. Settings → Features → marque Issues.
O template não aparece ao clicar em New issue O arquivo não está na branch principal, ou o caminho tem uma letra fora do lugar. Confira .github/ISSUE_TEMPLATE/ — com ISSUE_TEMPLATE em maiúsculas e o arquivo terminando em .yml.
Erro de sintaxe ao salvar o .yml Tabulação no lugar de espaço, ou indentação irregular. Só espaços, dois por nível. Cole de novo o modelo da seção 07 e edite por cima.
O formulário deixa enviar vazio Faltou o required: true — e ele fica dentro de validations, não de attributes. Confira a indentação desses dois blocos no modelo.
Ainda aparece o link de abrir issue em branco Falta o config.yml, ou ele está com blank_issues_enabled: true. Crie .github/ISSUE_TEMPLATE/config.yml com false.
Escrevi #12 e não virou link Não existe issue com esse número neste repositório, ou o texto está dentro de um bloco de código. Confira o número. Dentro de crases o GitHub não converte nada — é para isso que as crases servem.

Fechei a issue e o cartão não foi para Pronto O fluxo padrão do quadro está desligado, ou a coluna de destino tem outro nome. No Project: menu ⋯ → Workflows → ligue Item closed e escolha a coluna.
A barra da milestone não anda Ela conta issues fechadas. Se ninguém fecha nada, não há o que contar. Feche o que já está pronto, com um comentário explicando.
O quadro vive desatualizado Só uma pessoa move os cartões, e não é quem faz o trabalho. Combine em voz alta, uma vez: quem pega a issue move o cartão e se atribui.
Trinta labels e ninguém filtra por nenhuma Foram criadas por precaução, antes de existir a necessidade. Apague o que não foi usado no último mês e volte às cinco da seção 04.
Quero que a issue feche sozinha quando o código entrar Isso é o Pull Request fazendo o trabalho, não a issue. Closes #12 na descrição do PR. É a aula 06.
Antes de pedir ajuda numa issue alheia: releia o que você escreveu fingindo que nunca viu o projeto. Se ficar em pé sozinho, está bom. Se você precisar completar alguma coisa de cabeça para entender, é essa coisa que está faltando no texto.
