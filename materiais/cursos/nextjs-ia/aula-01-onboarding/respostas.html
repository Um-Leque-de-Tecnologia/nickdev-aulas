Respostas dos tickets

Os dezesseis cards da Aula 01, do LP-101 ao LP-116, com o diagnóstico de cada bug, o código que resolve, os critérios de aceite conferidos um a um e o que a IA teria acertado — ou inventado — em cada um deles.

Isto é gabarito. Ler antes de tentar troca o aprendizado por uma leitura: você concorda com tudo, fecha a página e continua sem saber decidir onde a fronteira fica. Tente primeiro, erre, e só então confira.

00Como ler este gabarito

Um documento de conferência, não um tutorial. Cada card aqui já está resolvido — o que interessa é o porquê de cada decisão, porque é o porquê que o review cobra.

A regra de uso

Abra a seção do card depois de ter tentado, e de preferência depois de ter aberto o PR. O valor de um gabarito está na comparação: você vê onde a sua fronteira ficou diferente da daqui e descobre se foi decisão ou descuido. Lido antes, ele vira um texto plausível que você acha que entendeu.

Se você já leu antes de tentar, não desista do card. Faça mesmo assim, e no PR escreva o que você teria decidido sozinho e o que copiou daqui. Isso é honesto e é revisável — copiar em silêncio não é nem uma coisa nem outra.

Existe mais de uma resposta certa

Em vários cards a resposta daqui é uma resposta, não a resposta. O caso explícito é o LP-106: ordenar no servidor e ordenar no navegador se defendem as duas, com trade-offs diferentes, e este documento implementa uma delas por inteiro sem dizer que a outra está errada. O mesmo vale para o corte da sinopse no LP-108 (CSS ou string) e para o carregamento das abas no LP-109 (tudo junto ou por aba).

O que o review cobra é a decisão defendida — não a resposta idêntica a esta. Um PR que escolhe o outro caminho e explica por quê passa; um PR que escolhe o caminho daqui sem saber dizer o motivo, não. E meia-implementação dos dois caminhos é o pior resultado possível em qualquer um desses cards.

O tema único da semana

Os dezesseis bugs são variações de uma coisa só: a fronteira entre Server e Client Component. O aquecimento de cada card é a correção pequena que faz você atravessar o fluxo do time uma vez — branch, PR, review, merge, deploy. A lição é o "use client", e o que vale nota não é usá-lo: é onde ele entra.

A frase que resolve quase todos: extraia só o controle interativo; os dados continuam vindo do servidor e descem por props. Marcar a página inteira resolve o sintoma e estraga o resto — joga a busca de dados para o navegador e manda para o pacote código que não precisava sair de casa.

A anatomia de cada seção

  • O diagnóstico — por que quebrava, na causa e não no sintoma.
  • O aquecimento — a correção pequena, resolvida.
  • A lição — a fronteira, com o código e o motivo de a diretiva estar naquele arquivo.
  • Os critérios de aceite — os seis do card, conferidos um a um.
  • Sobre a IA — o que ela teria acertado e o que você precisaria conferir. Esta parte não é decorativa: é metade do valor do curso.
O fecho vale para os dezesseis. Branch com o slug do card, PR com a decisão técnica escrita, review aprovado, merge, publicado. Um card sem a frase da decisão no PR não está pronto, mesmo funcionando na tela.
a home

LP-101O contador do acervo diz 0 e o filtro "ainda não vi" não responde

O card de abertura da semana, e o único em que a pista está no que não acontece.

O diagnóstico

São dois bugs sem relação entre si, e é de propósito. O contador diz 0 porque o número está escrito no JSX e nunca olhou a resposta da API. O toggle não responde porque o componente é renderizado no servidor: o onClick existe no arquivo, mas nunca chega ao navegador como função — o React serializa a marcação e descarta o manipulador.

A pista é o console limpo. Bug de JavaScript quebrado grita. Este não grita nada, porque não há JavaScript nenhum daquela página no cliente. Silêncio absoluto num clique é quase sempre fronteira, não erro.

O aquecimento

O total vem da mesma resposta que já preenche a grade — não precisa de segunda chamada. E o rótulo concorda em número:

app/page.tsx · o contador
const total = acervo.length;

// Concordância no plural: "1 título" e "12 títulos". Detalhe pequeno,
// visível na tela o tempo todo — e o review vai ver.
<p>{total} {total === 1 ? "título" : "títulos"}</p>

A lição

O filtro precisa de estado, então precisa de cliente. A tentação é escrever "use client" na primeira linha de app/page.tsx — resolve o clique e joga fora a renderização no servidor da home inteira. O que se extrai é o menor pedaço que precisa de estado: o toggle e a grade que ele filtra.

Antes — a página inteira vira client

// app/page.tsx
"use client";

export default function Home() {
  // e agora o fetch precisa de useEffect,
  // e o HTML inicial chega vazio.
}

Depois — só o controle

// app/page.tsx — continua Server Component
import { AcervoFiltravel } from "./acervo-filtravel";

export default async function Home() {
  const acervo = await listarAcervo();
  return <AcervoFiltravel itens={acervo} />;
}
app/acervo-filtravel.tsx · a folha interativa
"use client"; // aqui, e não na página: é este arquivo que tem estado

import { useState } from "react";
import type { Midia } from "@/lib/api";

export function AcervoFiltravel({ itens }: { itens: Midia[] }) {
  const [soNaoVistos, setSoNaoVistos] = useState(false);

  // Os dados já chegaram prontos por props. O cliente só escolhe
  // o que mostrar — não busca nada.
  const visiveis = soNaoVistos ? itens.filter((m) => !m.visto) : itens;

  return (
    <>
      <button aria-pressed={soNaoVistos} onClick={() => setSoNaoVistos(!soNaoVistos)}>
        ainda não vi
      </button>
      <Grade itens={visiveis} />
    </>
  );
}

Os critérios de aceite

CritérioComo foi satisfeito
Contador vem do total da APIacervo.length sobre a mesma resposta que monta a grade — sem segunda chamada e sem número chumbado.
Singular e plural concordamTernário no rótulo: 1 título / 12 títulos.
O toggle filtra de verdadeEstado soNaoVistos no Client Component; a lista visível é derivada dele.

Sobre a IA

O mapa do repositório recém-clonado ela acerta: as pastas, o caminho geral, onde a home mora. Erra o detalhe — o nome exato da função que busca o acervo, ou o arquivo em que ela vive. Confira cada afirmação abrindo o arquivo antes de usar.

Onde ela quase sempre erra aqui: pedida para "fazer o botão funcionar", a resposta mais comum é "use client" no topo da página. Funciona, passa no seu teste manual e reprova no review. A diferença Server × Client ela explica bem — a fronteira deste projeto é sua, e a frase do PR precisa ser escrita com as suas palavras.

LP-104As setas do carrossel de destaques estão mortas e a legenda é sempre a mesma

O card que instala o padrão que se repete o curso inteiro: buscar no servidor, passar por props.

O diagnóstico

O carrossel não tem índice: mostra destaques[0] e as setas não têm para onde mover nada. A legenda é uma string fixa, "Destaque da semana", escrita no JSX em vez de sair do slide atual. E, como em todo card desta semana, o onClick das setas está num componente de servidor — mesmo com o índice implementado, nada aconteceria.

O aquecimento

A legenda passa a ler o slide atual. Uma linha, e ela já cobre o segundo bug de graça: se a legenda vem do índice, ela muda quando o índice muda.

A lição

A decisão que o review olha não é o índice — é onde a lista de destaques é buscada. Ela vem da API e não precisa ir para o navegador como código: desce como dado, pronta, para o componente client.

app/page.tsx · a busca fica de fora
export default async function Home() {
  // A chamada acontece no servidor. O navegador recebe os destaques
  // já serializados no HTML — não a função que sabe buscá-los.
  const destaques = await listarDestaques();

  return <Carrossel slides={destaques} />;
}
app/carrossel.tsx · só o controle de índice
"use client";

import { useState } from "react";
import type { Destaque } from "@/lib/api";

export function Carrossel({ slides }: { slides: Destaque[] }) {
  const [i, setI] = useState(0);
  const atual = slides[i];

  // Sem dar a volta, e com intenção: nas pontas o botão fica
  // desabilitado, o que também comunica o limite a quem navega por teclado.
  return (
    <section aria-roledescription="carrossel">
      <button onClick={() => setI(i - 1)} disabled={i === 0}
              aria-label="destaque anterior">←</button>

      <figure>
        <figcaption>{atual.titulo}</figcaption>
      </figure>

      <button onClick={() => setI(i + 1)} disabled={i === slides.length - 1}
              aria-label="próximo destaque">→</button>
    </section>
  );
}
Por que <button> e não <div onClick>: o botão nativo já é focável, já responde a Enter e espaço e já anuncia o estado desabilitado. Metade dos critérios de teclado deste card se resolve por escolher a tag certa.

Os critérios de aceite

  • Setas avançam e voltam — setI(i ± 1) sobre o estado local.
  • Legenda mostra o título do slide atual — atual.titulo, derivado do índice; a string fixa saiu.
  • Busca dos destaques continua no servidor — o await listarDestaques() ficou em app/page.tsx.
  • Dados chegam por props — slides entra pronto; não há fetch nem useEffect no arquivo do carrossel.
  • Setas alcançáveis pelo teclado — são <button> nativos, com aria-label dizendo a ação.
  • Não passa dos limites — disabled nas pontas; a alternativa de dar a volta também vale, desde que o PR diga que foi escolha.

Sobre a IA

Ela escreve o controle de índice em segundos, e escreve bem. O que ela não diz sozinha é que a busca dos destaques fica do lado de fora, no servidor: a resposta padrão dela é um componente client com useEffect buscando os destaques ao montar — que funciona e desfaz exatamente o que este card ensina. A decisão é sua, e é ela que o review olha.

LP-105O chip "Todos" nunca fica marcado e os gêneros vieram com acento quebrado

O primeiro card em que a resposta certa está na documentação da API, não no seu editor.

O diagnóstico

Ficç?o e Document�rio não são erro de dado: são erro de codificação na hora de montar o rótulo. A API entrega UTF-8; algum ponto do caminho tratou os bytes como latin-1. E o chip "Todos" nunca acende porque o estado inicial do filtro é uma string vazia, enquanto o chip compara contra o literal "todos" — duas representações do mesmo "nada selecionado" que nunca se encontram.

O aquecimento

Corrigir a codificação e, de brinde, fazer a primeira leitura séria da documentação da API para confirmar em que formato os gêneros chegam — se é string[], se é objeto com id e nome, se o rótulo já vem pronto ou precisa ser montado. É essa leitura que evita o resto do bug.

Estado nulo, não string vazia. O "nada selecionado" fica sendo null, e o chip "Todos" é marcado quando selecionado === null. Um só valor representa o vazio, e o bug de comparação desaparece por construção.

A lição

Os chips vão para o cliente porque têm estado de seleção. A lista de gêneros não: ela é dado, vem do servidor e desce por props — o mesmo padrão do LP-104.

app/chips-genero.tsx
"use client"; // só os chips; a lista veio pronta do servidor

export function ChipsGenero({ generos }: { generos: string[] }) {
  const [sel, setSel] = useState<string | null>(null);

  return (
    <div role="group" aria-label="filtrar por gênero">
      <button aria-pressed={sel === null} onClick={() => setSel(null)}>
        Todos {sel === null && "✓"}
      </button>

      {generos.map((g) => (
        // aria-pressed dá o estado a quem usa leitor de tela; o ✓ dá
        // a quem não distingue as cores. O estado não depende só de cor.
        <button key={g} aria-pressed={sel === g} onClick={() => setSel(g)}>
          {g} {sel === g && "✓"}
        </button>
      ))}
    </div>
  );
}

Os critérios de aceite

  • Acentuação correta — o rótulo é montado em UTF-8, conferido contra a resposta real da API.
  • "Todos" marcado quando nada está selecionado — sel === null é o único jeito de representar o vazio.
  • Clicar num chip marca ele e desmarca "Todos" — consequência direta do estado único; não há dois estados para sincronizar.
  • Lista continua vindo do servidor — generos é prop, buscada na página.
  • Navegáveis pelo teclado com foco visível — <button> nativos, e o :focus-visible do projeto não foi removido.
  • O estado marcado não depende só de cor — aria-pressed mais a marca visual.

Sobre a IA

Este é o card feito para pegá-la. Peça o formato dos gêneros a partir da documentação e ela responde com confiança total — frequentemente um formato inventado, plausível, do jeito que a maioria das APIs faz. Resposta inventada sobre formato de dado é o erro mais comum e mais caro dela: você escreve o componente inteiro em cima de um contrato que não existe e só descobre na tela. Confira contra a resposta real, com o endpoint aberto ao lado.

No mais, o padrão ARIA dos chips ela entrega bem, e a lembrança de não depender só de cor costuma vir junto se você perguntar por acessibilidade.

LP-106A ordenação do catálogo não reordena nada e o rótulo diz sempre "Relevância"

O card com a pergunta boa embutida — e o único em que este gabarito escolhe um caminho sabendo que o outro também passa.

O diagnóstico

O <select> não tem value nem onChange: é um controle decorativo. O rótulo mostra a string fixa "Relevância" porque nunca houve escolha guardada em lugar nenhum para ele ler. Escolher "A-Z" muda o que aparece dentro do próprio select nativo e mais nada.

A decisão: quem ordena?

No navegador

O seletor vira client e recebe a lista inteira por props. Ordenar é [...itens].sort(), instantâneo, sem ida ao servidor.

Defende-se quando a lista já veio inteira e é pequena. Custa não sobreviver ao recarregar nem ser compartilhável por link.

No servidor

A escolha sai do componente e vira informação que o servidor enxerga — searchParams. A página lê a ordem e devolve a lista já ordenada.

Defende-se quando a lista é grande ou paginada, e quando o link precisa carregar a escolha. Custa uma ida ao servidor por troca.

Meia-implementação das duas é o pior resultado possível. Ler searchParams e também guardar a ordem em useState cria duas fontes de verdade que discordam na primeira navegação — e o bug que nasce daí é muito mais caro que o bug original.

A lição — o caminho escolhido aqui

Este gabarito ordena no navegador, porque nesta semana o catálogo da home já chega inteiro do servidor e a lista é curta: mandar ordenação para a URL agora seria pagar uma ida ao servidor por uma operação que custa microssegundos. O PR diz isso, e diz também o gatilho da mudança: quando o catálogo for paginado, a ordenação sobe para o servidor.

app/catalogo-ordenavel.tsx
"use client";

type Ordem = "relevancia" | "az" | "recentes";

const ROTULOS: Record<Ordem, string> = {
  relevancia: "Relevância", az: "A-Z", recentes: "Mais recentes",
};

export function CatalogoOrdenavel({ itens }: { itens: Midia[] }) {
  const [ordem, setOrdem] = useState<Ordem>("relevancia");

  // itens NUNCA é mutado: sort() mexe no array original, e o original
  // é a ordem de relevância que precisamos devolver depois.
  const lista =
    ordem === "az"       ? [...itens].sort((a, b) => a.titulo.localeCompare(b.titulo, "pt-BR"))
  : ordem === "recentes" ? [...itens].sort((a, b) => b.ano - a.ano)
  : itens; // relevância = a ordem que o servidor mandou

  return (
    <>
      <label htmlFor="ordem">Ordenar por</label>
      <select id="ordem" value={ordem}
              onChange={(e) => setOrdem(e.target.value as Ordem)}>
        {(Object.keys(ROTULOS) as Ordem[]).map((o) => (
          <option key={o} value={o}>{ROTULOS[o]}</option>
        ))}
      </select>
      <Grade itens={lista} />
    </>
  );
}
O <select> nativo é a resposta de teclado inteira. Setas, digitar a primeira letra, Enter, Esc: tudo já funciona, em todo sistema operacional. Um dropdown feito à mão custaria meio card só para empatar.

Os critérios de aceite

  • As três ordenações funcionam — relevância, A-Z (com localeCompare em pt-BR, que ordena acento direito) e mais recentes.
  • Rótulo mostra a escolhida — o value controlado pelo estado; o rótulo saiu do ROTULOS, não de string fixa.
  • Escolha explicada no PR — cliente, por lista curta já carregada, com o gatilho de revisão anotado.
  • Abordagem implementada por inteiro — nada de searchParams sobrando no arquivo.
  • Funciona pelo teclado — <select> nativo com <label htmlFor>.
  • Voltar para "Relevância" devolve a ordem original — só porque a cópia [...itens] preservou o array do servidor.

Sobre a IA

Aqui ela ajuda de verdade: descreva as duas abordagens e peça prós e contras, e a tabela que volta é boa — ela conhece bem os trade-offs de estado na URL contra estado local. O que ela não faz é escolher pelo seu projeto, porque a escolha depende de coisas que não estão no código: o tamanho futuro do catálogo, se o link precisa ser compartilhável, o que a semana 6 vai pedir.

E ela mistura os dois caminhos. Peça "implemente a ordenação" sem decidir antes e há boa chance de voltar um componente com useState e um router.push com query string — exatamente a meia-implementação que este card proíbe.

LP-102A busca do cabeçalho não abre e o placeholder fala de "produtos"

O card em que o alcance da diretiva custa caro: o cabeçalho é o componente mais compartilhado do app.

O diagnóstico

A lupa é um <button> com onClick dentro do cabeçalho, que é Server Component — o mesmo silêncio do LP-101. O placeholder "Buscar produtos..." é herança de template: o LequePlay não vende produto, tem acervo.

O aquecimento

Trocar a palavra. Parece trivial, e é o momento de reparar que o vocabulário do produto é uma decisão de time — "acervo", "títulos", "episódios" — e que placeholder herdado de template é dívida que aparece na tela de todo mundo.

<input placeholder="Buscar no acervo..." aria-label="Buscar no acervo" />

A lição

Cuidado com o alcance. Marcar app/components/cabecalho.tsx inteiro como client manda para o pacote do navegador a lista de rotas, a marca, e — o que dói — a lógica de sessão que o cabeçalho lê para decidir o que mostrar a quem está logado. Nada disso tem interação. Extraia só o botão e o campo.
app/components/busca-cabecalho.tsx
"use client"; // o cabeçalho continua server; só esta folha desce

import { useEffect, useRef, useState } from "react";

export function BuscaCabecalho() {
  const [aberta, setAberta] = useState(false);
  const campo = useRef<HTMLInputElement>(null);

  // Foco no campo assim que abre: quem abriu a busca quer digitar,
  // e quem navega por teclado não deveria ter que procurar o campo.
  useEffect(() => { if (aberta) campo.current?.focus(); }, [aberta]);

  // Esc no documento inteiro, porque o foco pode estar fora do campo.
  useEffect(() => {
    if (!aberta) return;
    const aoTeclar = (e: KeyboardEvent) => { if (e.key === "Escape") setAberta(false); };
    addEventListener("keydown", aoTeclar);
    return () => removeEventListener("keydown", aoTeclar);
  }, [aberta]);

  return (
    // onBlur na casca fecha ao clicar fora sem precisar de listener global:
    // se o foco saiu da caixa inteira, ninguém está usando a busca.
    <div onBlur={(e) => { if (!e.currentTarget.contains(e.relatedTarget)) setAberta(false); }}>
      <button aria-expanded={aberta} aria-label="Buscar no acervo"
              onClick={() => setAberta(!aberta)}>🔍</button>

      {aberta && <input ref={campo} placeholder="Buscar no acervo..." />}
    </div>
  );
}
app/components/cabecalho.tsx · o que ficou no servidor
// Sem diretiva nenhuma: rotas, marca e sessão continuam no servidor.
import { BuscaCabecalho } from "./busca-cabecalho";

export default async function Cabecalho() {
  const sessao = await lerSessao();
  return (
    <header>
      <Marca />
      <Rotas />
      <BuscaCabecalho /> {/* a única ilha de cliente */}
      <Conta sessao={sessao} />
    </header>
  );
}

Os critérios de aceite

  • Placeholder fala do acervo — e o aria-label repete o texto, para quem não vê o placeholder.
  • Clicar na lupa abre e clicar fora fecha — onBlur na casca, testando relatedTarget.
  • Esc fecha — ouvinte de keydown no documento, registrado só enquanto aberta e removido na limpeza.
  • Só o controle da busca é client — a diretiva está na folha; o cabeçalho permanece async lendo a sessão no servidor.
  • O foco vai pro campo ao abrir — useEffect com ref, disparado pela mudança de aberta.
  • PR explica a escolha da fronteira — "recusei marcar o cabeçalho inteiro: ele carrega rotas e sessão que não têm interação nenhuma".

Sobre a IA

Pergunte onde colocar a diretiva e ela quase sempre sugere o arquivo inteiro — é a resposta rápida, e é a que funciona na primeira tentativa. Decida você. O trecho do PR que este card cobra é literalmente "por que recusei a sugestão": não é penalidade, é o campo do template que mais aparece em entrevista.

O que ela acerta bem: o useEffect do foco e a limpeza do ouvinte de teclado. É código repetitivo e ela não erra — desde que você confira que o return de limpeza existe, porque a versão sem limpeza também aparece e vaza ouvintes a cada abertura.

LP-103O menu mobile não fecha ao navegar e repete o item "Início"

O único card em que o componente já é client — e mesmo assim o problema é a fronteira.

O diagnóstico

O item duplicado é literal: "Início" aparece duas vezes no array de navegação. O menu que fica aberto por cima é mais interessante — navegação no App Router não recarrega a página. O React troca a árvore da rota e o menu, que é um componente com estado próprio, continua montado com aberto === true. Ninguém avisou ele. No mundo do recarregamento completo esse bug não existia, e é por isso que ele pega tanta gente.

O aquecimento

Remover a linha duplicada do array. E notar que o array de links é dado estático: ele não precisa de cliente nenhum, e pode ficar num módulo que o servidor também importa.

A lição

O menu precisa ser client porque tem estado aberto/fechado. A lista de links não precisa — ela é constante, desce por props e nunca muda no navegador. E o fechamento ao navegar sai do caminho da rota atual: quando usePathname() muda, o efeito fecha.

app/components/menu-mobile.tsx
"use client";

import { usePathname } from "next/navigation"; // App Router, não next/router
import { useEffect, useState } from "react";

export function MenuMobile({ links }: { links: { href: string; rotulo: string }[] }) {
  const [aberto, setAberto] = useState(false);
  const rota = usePathname();

  // A rota mudou => o menu fecha. Não é o clique que fecha: é a
  // navegação. Assim funciona também no voltar do navegador.
  useEffect(() => { setAberto(false); }, [rota]);

  // Trava a rolagem do corpo enquanto o painel cobre a tela.
  useEffect(() => {
    document.body.style.overflow = aberto ? "hidden" : "";
    return () => { document.body.style.overflow = ""; };
  }, [aberto]);

  useEffect(() => {
    const esc = (e: KeyboardEvent) => { if (e.key === "Escape") setAberto(false); };
    addEventListener("keydown", esc);
    return () => removeEventListener("keydown", esc);
  }, []);

  return (
    <>
      <button aria-expanded={aberto} aria-label="Abrir menu"
              onClick={() => setAberto(true)}>☰</button>

      {aberto && (
        <nav>
          <button aria-label="Fechar menu" onClick={() => setAberto(false)}>✕</button>
          {links.map((l) => <Link key={l.href} href={l.href}>{l.rotulo}</Link>)}
        </nav>
      )}
    </>
  );
}
Por que fechar pelo usePathname e não pelo onClick do link: o onClick fecha quando a pessoa clica, mesmo que a navegação falhe, e não fecha quando ela volta pelo botão do navegador. Reagir à rota cobre os dois casos com uma linha a menos.

Os critérios de aceite

Tocar num item navega e fechauseEffect em [rota] — fecha na navegação, inclusive no voltar.

Sobre a IA

Este é o card do Pages Router. Pergunte como saber, dentro de um Client Component, que a rota mudou, e há grande chance de vir useRouter de next/router com router.events.on("routeChangeComplete") — que é API do Pages Router e simplesmente não existe aqui. O import parece certo, o erro só aparece em execução, e a explicação que acompanha é convincente. Confirme na documentação oficial da versão instalada: no App Router o caminho é usePathname de next/navigation.

LP-107O alternador de tema não alterna e o ícone está invertido

O diagnóstico

O botão não alterna porque está num Server Component — de novo. O ícone invertido não é bug de código, é bug de conceito: ele mostra o tema atual. No escuro aparece a lua, que é onde a pessoa já está. Botão comunica ação, não estado: no escuro deve aparecer o sol, que é o que se obtém clicando.

LP-110O "voltar ao topo" não funciona e o rodapé ainda diz 2024

Tamanho P, de propósito: é o card para atravessar branch, PR e deploy com folga no primeiro dia.

O diagnóstico

O botão não rola porque o onClick está no rodapé, que é servidor. O ano é uma string fixa. E a pegadinha está aí: calcular o ano é uma linha, mas onde essa linha roda muda o resultado.

Antes — ano calculado no cliente

}

Depois — ano no servidor

// app/components/rodape.tsx — sem diretiva

  return (

      <p>© {ano} LequePlay</p>

  • Só o que precisa de interatividade virou client — o rodapé inteiro continua no servidor.

Sinopse, Elenco, Detalhes — e um padrão de acessibilidade que quase ninguém aplica.

O diagnóstico

Os três conteúdos descem juntos, ou cada aba busca o seu ao abrir? Para textos curtos, tudo junto é mais simples e mais rápido — uma requisição só, troca instantânea, nada de estado de carregando. app/midias/[slug]/abas.tsx · só o controle
"use client";

export function Abas({ abas }: { abas: Aba[] }) {
  const [i, setI] = useState(0); // a primeira já vem selecionada

  // Padrão ARIA de abas: setas navegam entre elas, Tab sai do conjunto.
  const aoTeclar = (e: KeyboardEvent<HTMLDivElement>) => {
    if (e.key === "ArrowRight") setI((i + 1) % abas.length);
    if (e.key === "ArrowLeft")  setI((i - 1 + abas.length) % abas.length);
  };

  return (
    <>
      <div role="tablist" onKeyDown={aoTeclar}>
        {abas.map((a, n) => (
          <button key={a.id} role="tab"
                  aria-selected={n === i}
                  aria-controls={`painel-${a.id}`}
                  id={`aba-${a.id}`}
                  tabIndex={n === i ? 0 : -1} // só a selecionada entra no Tab
                  onClick={() => setI(n)}>
            {a.rotulo}
          </button>
        ))}
      </div>

      <div role="tabpanel" id={`painel-${abas[i].id}`} aria-labelledby={`aba-${abas[i].id}`}>
        {abas[i].conteudo}
      </div>
    </>
  );
}
O tabIndex={-1} nas abas não selecionadas é o detalhe que separa o padrão certo do quase certo. Sem ele, o Tab passa por cada aba uma por uma; com ele, o Tab entra no conjunto uma vez e as setas fazem o resto — que é como abas funcionam em qualquer sistema operacional.

Os critérios de aceite

  • Primeira aba selecionada ao abrir — useState(0).
  • Clicar troca aba e conteúdo — o painel deriva do mesmo índice.
  • Setas do teclado navegam — ArrowLeft e ArrowRight com volta circular.
  • Aba selecionada anunciada — role="tab" mais aria-selected, e o painel amarrado por aria-controls/aria-labelledby.
  • Conteúdos vêm do servidor — renderizados na página e passados prontos; o client não busca nada.
  • PR explica a escolha — tudo junto, porque os três textos são curtos e uma requisição só é mais rápida que três.

Sobre a IA

Peça o padrão ARIA de abas: ela conhece bem e poupa meia hora de documentação — tablist, tab, tabpanel, a relação de id, o tabIndex gerenciado. É um dos usos em que ela é claramente melhor que a busca. Confira navegando só com o teclado, porque o detalhe que ela às vezes esquece é mover o foco junto com a seleção quando a seta troca a aba.

LP-112O botão de copiar link não copia e a URL sai com localhost

O card de variáveis de ambiente — e a distinção que volta na semana 2 e na semana 4.

O diagnóstico

A URL é montada com a string http://localhost:3000 escrita no código, então o link que a pessoa compartilha em produção aponta para a máquina dela. E o botão não copia porque navigator.clipboard é API de navegador chamada de um componente que roda no servidor.

O aquecimento

O endereço público é configuração, não código: muda entre a sua máquina, a prévia do PR e produção. Sai do arquivo e vira variável de ambiente.

.env.local · e o mesmo nome configurado na Cloudflare
# Público de propósito: o navegador precisa deste valor para montar o link.
NEXT_PUBLIC_SITE_URL=http://localhost:3000

# Em produção: https://lequeplay.exemplo.br
# Na prévia: a URL do deploy de PR
Cuidado com o prefixo. NEXT_PUBLIC_ não "permite" o valor no navegador — ele embute o valor no JavaScript que qualquer pessoa baixa e lê. Para uma URL pública é aceitável, porque ela já está na barra de endereço. Para token, chave de API ou segredo de sessão é vazamento, e vazamento que fica no histórico do repositório. Segredo fica sem prefixo e só é lido no servidor.

app/midias/[slug]/copiar-link.tsx
"use client"; // clipboard é API de navegador: precisa estar aqui

export function CopiarLink({ url }: { url: string }) {
  const [copiado, setCopiado] = useState(false);

  async function copiar() {
    try {
      await navigator.clipboard.writeText(url);
      setCopiado(true);
      setTimeout(() => setCopiado(false), 1500);
    } catch {
      // Sem permissão de área de transferência, não finja que copiou.
      setCopiado(false);
    }
  }

  return (
    <>
      <button onClick={copiar}>{copiado ? "Link copiado ✓" : "Copiar link"}</button>
      {/* aria-live para quem não vê a mudança do rótulo */}
      <span role="status" aria-live="polite">{copiado && "Link copiado"}</span>
    </>
  );
}

Os critérios de aceite

  • URL vem de variável de ambiente — NEXT_PUBLIC_SITE_URL; nenhuma string de host no código.
  • Link funciona em produção e na prévia — porque cada ambiente define o próprio valor.
  • O botão copia de verdade — navigator.clipboard.writeText num Client Component.
  • A interface confirma que copiou — o rótulo troca e um role="status" anuncia.
  • PR explica por que essa variável pode ser pública — é o endereço do site, já visível na barra de endereço; publicá-lo não revela nada.
  • Nenhum segredo foi para uma NEXT_PUBLIC_ — conferido lendo o .env inteiro, uma variável por vez.

Sobre a IA

Pergunte quando NEXT_PUBLIC_ é seguro e quando é vazamento: a resposta é boa e vale gravar agora, porque essa distinção volta na semana 2, quando o BFF passar a guardar a chave da API, e na semana 4, quando o token de sessão entrar em cena.

O que conferir: pedida para "fazer a URL funcionar em produção", ela às vezes sugere prefixar variáveis existentes com NEXT_PUBLIC_ para resolver um undefined no navegador. Se a variável é um segredo, essa sugestão é o vazamento — e o undefined era o sistema funcionando como devia.

LP-113A rota /sobre devolve 404 e o link do rodapé leva a lugar nenhum

O coração do App Router: a URL não é registrada em lugar nenhum, é o caminho da pasta.

O diagnóstico

O conteúdo já existe no repositório. O que não existe é a rota — o arquivo está com nome quase certo: app/sobre/index.tsx, ou Page.tsx com maiúscula, ou solto em app/sobre.tsx. Nome quase certo não vira rota: vira arquivo ignorado, sem erro nenhum. Nada quebra, nada avisa, e o 404 é a única mensagem que você recebe.

Por que isso engana tanto: em frameworks com rota declarada num arquivo de configuração, uma rota faltando aparece como erro de importação. Aqui a convenção é o registro — e uma convenção não atendida é apenas silêncio.

O aquecimento

Renomear para app/sobre/page.tsx, tudo minúsculo, exportando um componente padrão. E conferir o href do rodapé, que apontava para /sobre/ com barra final ou para #.

a convenção, em quatro nomes
app/
├─ sobre/
│  └─ page.tsx        ← isto, e só isto, cria a rota /sobre
├─ layout.tsx         casca que envolve as rotas abaixo
├─ loading.tsx        o que aparece enquanto a página carrega (semana 2)
└─ not-found.tsx      a tela de 404 do projeto

A lição

A página é Server Component — é texto estático, não tem nada que precise do navegador. Só o acordeão de perguntas é client.

app/sobre/page.tsx
// Sem "use client": é conteúdo, renderizado no servidor e indexável.
import { Acordeao } from "./acordeao";
import { PERGUNTAS } from "./perguntas";

export default function Sobre() {
  return (
    <main>
      <h1>Sobre o LequePlay</h1>
      {/* as respostas descem inteiras: o acordeão só esconde */}
      <Acordeao itens={PERGUNTAS} />
    </main>
  );
}
app/sobre/acordeao.tsx
"use client";

export function Acordeao({ itens }: { itens: Pergunta[] }) {
  const [aberto, setAberto] = useState<string | null>(null);

  return (
    <dl>
      {itens.map((p) => (
        <div key={p.id}>
          <dt>
            <button aria-expanded={aberto === p.id} aria-controls={p.id}
                    onClick={() => setAberto(aberto === p.id ? null : p.id)}>
              {p.titulo}
            </button>
          </dt>
          <dd id={p.id} hidden={aberto !== p.id}>{p.resposta}</dd>
        </div>
      ))}
    </dl>
  );
}

Os critérios de aceite

  • /sobre responde e mostra o conteúdo que já existia — o arquivo virou app/sobre/page.tsx e o conteúdo não foi reescrito.
  • O link do rodapé leva até lá — <Link href="/sobre">, conferido na tela.
  • A página é Server Component — nenhuma diretiva no page.tsx.
  • O acordeão abre e fecha — estado com um item aberto por vez; clicar no aberto fecha.
  • Só o acordeão é client — a diretiva está no arquivo dele.
  • PR explica a regra em uma frase — "a rota é o caminho da pasta em app/, e só um arquivo chamado exatamente page.tsx a cria".

Sobre a IA

Peça a convenção de arquivos do App Router e o que cada nome especial faz. A lista que volta é boa e serve a semana 2 inteira, quando loading, error e not-found entram em cena — vale guardar. Confira contra a documentação da versão instalada mesmo assim: nomes especiais foram acrescentados entre versões, e ela mistura o conjunto de uma versão com o de outra sem avisar.

LP-114O contador de caracteres da resenha não conta e o limite está errado

Mente em dobro: mostra "0/280" que nunca muda, e a API recusa acima de 500.

O diagnóstico

O <textarea> não é controlado — não há value nem onChange, então o contador não tem de onde ler nada e o "0" é literal. O limite 280 veio de outro produto (é o do Twitter, e ninguém conferiu). O jeito de descobrir o número certo é ler a documentação da API, e essa é a habilidade da semana: não chute.

O aquecimento

Ler o contrato do endpoint de resenha, achar o limite real e usá-lo — de preferência a partir de uma constante única, para o campo, o contador e a mensagem nunca divergirem.

A lição

app/midias/[slug]/campo-resenha.tsx
"use client"; // campo controlado + contador: estado a cada tecla

// Um número, uma fonte. Confirmado em docs/api-contrato.md, não chutado.
const LIMITE = 500;

export function CampoResenha() {
  const [texto, setTexto] = useState("");
  const restam = LIMITE - texto.length;
  const estourou = restam < 0;

  return (
    <>
      <label htmlFor="resenha">Sua resenha</label>
      <textarea id="resenha" value={texto} aria-describedby="contador"
                onChange={(e) => setTexto(e.target.value)} />

      {/* aria-live="polite" só perto do limite: anunciar a cada tecla
            transformaria o leitor de tela em ruído. */}
      <p id="contador" className={estourou ? "erro" : undefined}
         aria-live={restam <= 20 ? "polite" : "off"}>
        {estourou
          ? `${-restam} caracteres acima do limite`
          : `${texto.length}/${LIMITE}`}
      </p>

      <button disabled={estourou || texto.length === 0}>Publicar</button>
    </>
  );
}
Desabilitar o botão não é validação. É conveniência de interface — some com o DevTools aberto, com um cliente que não seja este, ou com uma requisição feita à mão. A validação de verdade é do servidor recusar, e isso é assunto da semana 5. Anote no PR que você viu: notar o buraco antes de ele virar incidente é metade do trabalho.

Os critérios de aceite

CritérioComo foi satisfeito
O limite é o que a API aceita500, confirmado na documentação do endpoint e isolado na constante LIMITE.
Contador atualiza a cada teclatextarea controlado, com value e onChange.
Passando do limite avisa visualmenteClasse de erro mais texto que diz quantos caracteres sobram — não só a cor.
Só o campo e o contador são clientA ficha e o restante do formulário continuam no servidor.
Anunciado ao se aproximar do limitearia-live="polite" a partir de 20 caracteres restantes; aria-describedby amarra o contador ao campo.
PR registra a validação de servidorEscrito que o disabled é interface e que a recusa real fica para a semana 5.

Sobre a IA

Este card existe para mostrar a falha mais cara dela na prática. Peça o limite de caracteres da resenha e ela responde um número — com confiança, sem hesitar, e há uma boa chance de ser 280, porque é o número que mais aparece em texto sobre campos de resenha na internet. Ela não diz "não confirmei". Confirme na fonte, com o contrato aberto, e repare que a resposta errada e a certa chegam com exatamente o mesmo tom.

No resto ela ajuda: o campo controlado e o padrão de aria-live saem corretos, e a lembrança de não anunciar a cada tecla costuma vir se você perguntar por acessibilidade.

LP-115A tela de "nada encontrado" tem um botão morto e uma mensagem genérica

Escrita de produto — e a diferença entre a pessoa desistir e tentar de novo.

O diagnóstico

"Nenhum item encontrado." não diz o que foi buscado, não sugere o que fazer, e usa uma palavra que não é do produto: o LequePlay tem títulos, filmes, séries e podcasts — não "itens". E o "limpar filtros" é um botão sem onClick ligado a nada, num componente de servidor.

O aquecimento

Reescrever o texto com o termo buscado dentro e uma saída oferecida. Estado vazio bem escrito não é enfeite: é o momento em que a pessoa decide se insiste.

Antes

"Nenhum item encontrado."

Não diz o que foi buscado, não diz o que fazer, e "item" é palavra de template.

Depois

"Nenhum título encontrado para "tarkovski". Tente outra grafia, limpe os filtros ou dê uma olhada nos destaques da semana."

Repete o termo, usa o vocabulário do produto e oferece três saídas.

A lição

app/busca/estado-vazio.tsx
"use client"; // só por causa do botão que limpa

export function EstadoVazio({ termo, aoLimpar }: { termo: string; aoLimpar: () => void }) {
  return (
    // role="status" para o leitor de tela anunciar que a busca não achou nada;
    // sem isso, quem não vê a tela fica esperando um resultado que não vem.
    <div role="status">
      <p>Nenhum título encontrado para <b>“{termo}”</b>.</p>
      <p>Tente outra grafia, limpe os filtros ou veja os destaques da semana.</p>

      <button onClick={aoLimpar}>Limpar filtros</button>
      <Link href="/">Ver destaques</Link>
    </div>
  );
}
Por que aoLimpar vem por prop: quem é dono do estado de filtro é o componente da lista, do LP-105. O estado vazio não precisa saber o que "limpar" significa — recebe a função e chama. Fronteira também é isso: cada componente sabendo o mínimo.

Os critérios de aceite

  • A mensagem repete o termo buscado e usa o vocabulário do LequePlay — "título", com o termo entre aspas.
  • O botão limpa e a grade volta — aoLimpar zera os filtros no componente que os guarda.
  • Sugere um caminho — limpar filtros e ver destaques, os dois oferecidos.
  • Só o botão é client — o restante da página de busca segue no servidor.
  • Anunciado por leitor de tela — role="status" no bloco inteiro.
  • Busca com resultado continua igual — o estado vazio é uma alternativa da renderização, não uma mudança na grade.
Encosta na semana 6, quando o filtro virar estado da URL e "limpar filtros" passar a ser uma navegação. Por enquanto resolve-se no cliente, e o PR pode anotar isso como próximo passo.

Sobre a IA

Texto de interface é onde ela é genuinamente útil. Peça três versões, com tons diferentes, e escolha uma ajustando ao tom do produto. O que não vale é aceitar a primeira sugestão sem ler em voz alta: ela tende ao publicitário — "Ops! Parece que não encontramos nada por aqui!" — que é simpático na primeira leitura e cansativo na terceira.

LP-116A barra de "continuar assistindo" mostra percentual errado e o botão retomar não retoma

87% num episódio mal começado — e o caso de borda que a IA vai jurar que não existe.

O diagnóstico

O campo progresso da API vem em segundos assistidos, e o componente o trata como se já fosse porcentagem. Oitenta e sete segundos viram 87%. A conta que falta é a divisão pela duração. E o botão retomar não retoma porque nunca recebeu o episódio: navega para a série, não para o ponto.

O aquecimento

Ler a documentação com atenção — não passar o olho. É lá que está escrito que progresso é em segundos, e é lá que se descobre que duracao pode faltar.

A lição — e o caso de borda

lib/progresso.ts · a conta, no servidor
// Duração ausente ou zero não pode virar NaN% nem barra quebrada.
// Divisão por zero em JavaScript não lança erro: devolve Infinity,
// e 0/0 devolve NaN. Os dois chegam calados até a tela.
export function calcularProgresso(assistidoSeg: number, duracaoSeg?: number): number | null {
  if (!duracaoSeg || duracaoSeg <= 0) return null; // não sabemos: não invente 0%
  return Math.min(100, Math.round((assistidoSeg / duracaoSeg) * 100));
}
app/continuar-assistindo.tsx
// Server Component: a faixa inteira é dado renderizado no servidor.
export default async function ContinuarAssistindo() {
  const historico = await listarHistorico();

  // Conta sem histórico não mostra a faixa — nem o título dela.
  if (historico.length === 0) return null;

  return (
    <section>
      <h2>Continuar assistindo</h2>
      {historico.map((h) => {
        const pct = calcularProgresso(h.progressoSeg, h.episodio.duracaoSeg);
        return (
          <article key={h.episodio.id}>
            {pct !== null && (
              <div role="progressbar" aria-valuenow={pct}
                   aria-valuemin={0} aria-valuemax={100}
                   aria-label={`${h.episodio.titulo}: ${pct}% assistido`}>
                <span style={{ width: `${pct}%` }} />
              </div>
            )}

            {/* Retomar é um link para o episódio certo, com o ponto de parada.
                  Link não precisa de client — e ainda funciona no botão do meio. */}
            <Link href={`/series/${h.serie.slug}/${h.episodio.id}?t=${h.progressoSeg}`}>
              Retomar
            </Link>
          </article>
        );
      })}
    </section>
  );
}
Repare no que não virou client neste card. Nada. A faixa inteira é dado renderizado no servidor, e "retomar" é um link — não um botão com onClick chamando router.push. O critério "só o que precisa de interação é client" pode ser satisfeito com zero diretivas, e essa é a resposta mais forte que ele aceita.

Os critérios de aceite

  • Percentual calculado a partir de segundos e duração — em calcularProgresso, uma função pura e testável.
  • Duração ausente ou zero não gera NaN nem barra quebrada — a guarda devolve null e a barra não é renderizada; não se inventa 0%.
  • Retomar leva ao episódio certo — link para o identificador do episódio, com o ponto de parada na query.
  • Barra com rótulo acessível contendo o percentual — role="progressbar", aria-valuenow e um aria-label com título e porcentagem.
  • Só o que precisa de interação é client — nada precisava.
  • Conta sem histórico não mostra a faixa — return null antes do título.

Sobre a IA

Peça os tipos da resposta a partir da documentação e você recebe uma interface TypeScript bem formada. Depois audite campo por campo: ela vai declarar duracaoSeg: number, sem ?, porque duração "obviamente" existe. É exatamente esse o caso de borda deste card — e o compilador, contente com o tipo mentiroso, não vai avisar de nada.

É a mesma auditoria que salva a semana 2 inteira (LP-212). Depois de qualquer tipo gerado por IA, faça uma pergunta só: quais destes campos a documentação garante que sempre vêm, e quais podem faltar? A resposta separada é o que você confere — não o código.
o padrão da semana

17A semana em uma página

Dezesseis cards, um padrão. Se você sair da Aula 01 com esta página na cabeça, o resto do curso fica mais barato.

A fronteira

No App Router, tudo é Server Component até você dizer o contrário. A diretiva "use client" não "liga o JavaScript": ela marca o ponto a partir do qual o módulo e tudo que ele importa passam a ser empacotados e enviados ao navegador. Por isso a pergunta nunca é "preciso de use client?" — é onde ela entra, porque a resposta define o tamanho do que desce.

Fica no servidor

  • toda busca de dados — await na API;
  • segredo, chave, cookie de sessão;
  • texto, marcação e conteúdo indexável;
  • cálculo estável — o ano do LP-110, o percentual do LP-116;
  • listas e constantes que nunca mudam no navegador.

Sobe para o cliente

  • estado que muda com o uso — useState;
  • evento de pessoa — clique, digitação, tecla;
  • efeito e ciclo de vida — useEffect;
  • API de navegador — clipboard, scrollTo, localStorage;
  • hooks de rota do cliente — usePathname.

O movimento, sempre o mesmo

  1. Identifique o menor controle interativo. Não o componente onde ele está: o controle. O botão da busca, não o cabeçalho. O toggle, não a home.
  2. Extraia esse controle para o próprio arquivo, e ponha "use client" na primeira linha desse arquivo.
  3. Continue buscando os dados no servidor, no componente pai, com await.
  4. Passe os dados por props. Prontos, serializados. O client recebe resultado, não a capacidade de buscar.
  5. Escreva no PR por que a fronteira ficou ali. Uma frase. Se você não consegue escrevê-la, o ticket não terminou — mesmo funcionando.

Os três sintomas que denunciam a fronteira

SintomaCausa quase certa
Clique sem reação e console limpoo onClick está num Server Component (LP-101, LP-102, LP-104, LP-107)
Hydration mismatchalgo calculado no cliente diverge do que o servidor renderizou (LP-110)
Tudo funciona, mas o HTML inicial chega vazioa diretiva subiu demais e a busca foi junto para o navegador

O que a IA fez bem, e onde ela custou caro

  • Boa em: padrões de acessibilidade (abas do LP-109, aria-live do LP-114), texto de interface (LP-115), explicar erros grandes (LP-110), listar prós e contras de duas abordagens (LP-106).
  • Cara em: inventar formato de dado (LP-105), inventar número que estava na documentação (LP-114), declarar campo opcional como garantido (LP-116), misturar Pages Router com App Router (LP-103) e — o mais frequente — sugerir "use client" no arquivo inteiro (LP-102).
O padrão dos erros dela é um só: ela erra onde a versão mudou depois do treino, e erra onde o dado real não está no código. Nos dois casos a checagem é a mesma — abrir a fonte. A documentação da versão instalada, ou a resposta de verdade do endpoint.

A frase que a turma leva para a semana 2

Extraia só o controle interativo. Os dados continuam vindo do servidor e descem por props. Na semana 2, quando o BFF entrar e a chave da API tiver que ficar escondida, essa mesma frase é o que decide onde cada coisa mora — e quem a entendeu aqui vai achar aquela aula fácil.

Terminou os dezesseis? Então você atravessou o fluxo do time dezesseis vezes: branch, PR com a decisão escrita, review, merge, publicado. A parte que fica não é o código — é a frase que você aprendeu a escrever no PR.
