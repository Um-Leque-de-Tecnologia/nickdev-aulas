ato 1 de 4

O componente
que espera

Buscar dado de fora leva tempo. Em React, no navegador, isso custa useEffect, um estado de carregando e um bug de corrida. Aqui custa duas palavras.

ato 1 · duas palavras

Um Server Component pode ser async

Como ele roda no servidor — foi o que vocês provaram no lab 1 da aula passada, com o console.log que só apareceu no terminal — ele pode simplesmente parar e esperar antes de devolver o HTML. Ninguém está olhando ainda.

app/vagas/page.tsx
export default async function Vagas() { const resposta = await fetch("https://.../dados/vagas.json"); const vagas: Vaga[] = await resposta.json(); return <MuralDeVagas vagas={vagas} />; }

O que some

Nenhum useEffect. Nenhum estado carregando. Nenhum useState guardando a lista. O componente devolve HTML já com os dados dentro.

O que não vale

Componente de cliente não pode ser async. Se o arquivo tem "use client" na primeira linha, essa porta está fechada — e o erro é bem claro sobre isso.

A fronteira da aula 03 continua valendo, e agora ela ganha um segundo motivo de existir: quem busca é o servidor, quem reage é o cliente.

ato 2 · o que o Next faz com o seu fetch

O fetch do Next não é o do navegador

É o mesmo nome e a mesma assinatura, com um argumento a mais que só existe aqui. E o padrão dele mudou de opinião no meio do caminho — o que explica metade dos tutoriais errados na internet:

versãoo que o fetch fazia sem você pedir nada
Next 13 e 14Guardava para sempre. Você buscava uma vez no build e a página nunca mais mudava — e ninguém entendia por quê.
Next 15 e 16 (o de vocês)Não guarda nada. Toda vez que a página é montada, ele vai buscar de novo. Cache virou coisa que você pede.

Foi por isso que o lab 1 mostrou três linhas no terminal para três recargas. O Next não está sendo burro: está sendo previsível. Guardar dado sem avisar é o tipo de gentileza que vira bug às onze da noite.

Se você achar um tutorial dizendo "o Next cacheia tudo por padrão", ele é de 2023. Confira a versão antes de copiar — package.json, linha do next.

ato 2 · três opções, e você escolhe

Quão fresco esse dado precisa estar?

Esta é a pergunta, e ela não é técnica: é sobre o produto. A resposta vira uma opção no segundo argumento do fetch.

sempre novo

o padrão

Nada escrito. Busca a cada pedido. Correto e caro — a pessoa espera a rede toda vez.

saldo, estoque, notificação
nunca mais

cache: "force-cache"

Busca uma vez e guarda. A página fica instantânea e o dado, congelado até o próximo deploy.

termos de uso, lista de estados
novo de vez em quando

next: { revalidate: 60 }

Guarda por 60 segundos. Passou disso, o próximo pedido dispara uma busca nova em segundo plano.

o Leque de Vagas ✅
lib/api.ts
const resposta = await fetch(`${FONTE}/vagas.json`, { next: { revalidate: 60, tags: ["vagas"] }, });

A terceira opção tem nome de gente grande — ISR, Incremental Static Regeneration — e é uma linha. Quem espera é o primeiro pedido depois do minuto, e mesmo ele recebe a versão antiga na hora: a busca nova acontece atrás. As tags ficam guardadas para a aula 05, quando um formulário puder dizer "esse dado que você guardou já era".

lab 2 · ~10 min · mão na massa
LAB 2conte as buscas

Faça o número parar de subir

  • Com o console.log ainda no listarVagas(), recarregue /vagas cinco vezes e conte as linhas do terminal.
  • Acrescente { cache: "force-cache" } ao fetch. Derrube o servidor, suba de novo, recarregue cinco vezes. Conte de novo.
  • Troque por { next: { revalidate: 20 } }. Recarregue várias vezes seguidas; depois espere meio minuto olhando o teto e recarregue mais uma.
  • Sem parar o servidor, edite o vagas.json no GitHub pela web, salve, e recarregue a página depois dos 20 segundos.
a pergunta do lab

No passo 4, a vaga editada apareceu na primeira recarga depois dos 20 segundos, ou na seguinte? E o que isso diz sobre quem paga a conta da espera?

Em desenvolvimento o cache mente um pouco. O npm run dev recompila e joga cache fora o tempo todo, para você ver a sua mudança. O comportamento de verdade é o do npm run build && npm start — e é lá que este lab tem que ser conferido, se o número não bater.

ato 3 · a legenda que ninguém lê

Toda rota é decidida em um de dois momentos

Rode npm run build. No fim sai uma tabela — e a legenda embaixo dela é, literalmente, o conteúdo desta aula:

$ npm run build Route (app) Size ○ / 5.1 kB ○ /vagas 6.4 kB ● /vagas/[id] 3.2 kB ƒ /vagas/busca 4.8 kB ○ (Static) pré-renderizada como conteúdo estático ● (SSG) pré-renderizada com generateStaticParams ƒ (Dynamic) renderizada sob demanda, a cada pedido
○ ● no build

O HTML já existe

Foi montado uma vez, na sua máquina ou na Vercel. Chega à pessoa como arquivo pronto, do servidor mais perto dela. Rápido de um jeito que nenhum servidor alcança.

ƒ a cada pedido

O HTML é montado na hora

Porque a página precisa de algo que só existe no pedido: quem está logado, qual filtro veio na URL, que horas são.

Você quase nunca escolhe isso escrevendo uma configuração. Você escolhe sem perceber, ao usar — ou não — um dado que só existe no pedido: searchParams, cookies(), headers(). Uma dessas linhas em qualquer lugar da árvore e a rota inteira vira ƒ.

ato 3 · a pasta [id] volta

Doze páginas prontas de uma pasta só

A aula 02 deixou app/vagas/[id]/page.tsx atendendo infinitos endereços. O Next não tem como adivinhar quais — a menos que você conte. E contar é uma função exportada:

app/vagas/[id]/page.tsx
export async function generateStaticParams() { const vagas = await listarVagas(); return vagas.map((vaga) => ({ id: vaga.id })); // [{ id: "1" }, { id: "2" }, ...] }

O nome da chave

id aqui é o mesmo id da pasta [id]. Errou o nome e o Next não reclama — só não gera nada.

Sempre texto

{ id: 1 } quebra o build. Endereço é texto: String(vaga.id) quando o dado for número.

E o id que não existe?

Continua funcionando — é montado na hora, na primeira visita. Pré-gerar é otimização, não muro.

Repare no que aconteceu: a mesma função listarVagas() serve a listagem, a página de detalhe e agora o build. É o que o lib/api.ts comprou — uma pergunta, um lugar só.

ato 4 · dois tamanhos de espera

A rota inteira, ou só o pedaço lento

arquivo · a rota toda

loading.tsx

Já existe desde a aula 02. Enquanto qualquer coisa da rota estiver esperando, ele ocupa a tela inteira. Simples e grosso: um dado lento segura o cabeçalho, o menu e o rodapé junto.

a página inteira depende do dado
componente · um pedaço

<Suspense>

Você desenha uma cerca em volta da parte lenta. O resto da página é entregue na hora, e o buraco é preenchido depois, sozinho, sem recarregar nada.

um bloco é mais lento que os outros
app/vagas/page.tsx
import { Suspense } from "react"; export default function Vagas() { // repare: NÃO é async return ( <> <h1>Vagas</h1> // chega imediatamente <Suspense fallback={<NumerosEsqueleto />}> <NumerosDoCatalogo /> // este é async, e demora </Suspense> </> ); }

A regra que economiza uma hora: quem espera é o componente de dentro do Suspense, e o await tem que estar dentro dele. Se a página fizer o await e passar o resultado por prop, ela já esperou — e o Suspense não tem mais nada para fazer.

ato 4 · a mesma página, em dois momentos

Streaming: a resposta chega em pedaços

O servidor não segura a resposta até tudo ficar pronto. Ele manda o que já tem, deixa o buraco marcado, e empurra o resto pela mesma conexão quando ficar pronto. Não é uma segunda requisição — não há nada para o navegador pedir de novo.

0 mso cascomenu, título, layout — tudo o que não depende de rede
~10 mso esqueletoo fallback ocupa o lugar do bloco lento, do tamanho certo
~400 mso conteúdoo dado chega e o React troca o esqueleto pelo bloco real
sem piscara página inteiranenhuma recarga, nenhum salto — o layout não se mexeu

O fallback tem uma regra de decência: ele deve ter mais ou menos o tamanho do conteúdo real. Um "Carregando…" de uma linha no lugar de um bloco de 300px faz a página inteira pular quando o dado chega — e o dedo de quem já ia clicar acerta outra coisa.

Partial Prerendering, o cacheComponents do Next 16, é este slide levado ao extremo: o casco estático servido pronto e os buracos dinâmicos preenchidos por streaming, na mesma página, sem ter que escolher entre ○ e ƒ. Ainda é opcional; fica anotado para quando o projeto de vocês pedir.

fecho · o que o Google e o WhatsApp veem

Cada rota com o seu próprio título

Hoje as 12 vagas de vocês compartilham o mesmo título de aba: o que está no layout.tsx da aula 02. Quem manda o link de uma vaga no grupo vê "Leque de Vagas" — e não a vaga. O App Router resolve isso com uma exportação, no mesmo arquivo da página:

rota fixa

export const metadata

Um objeto. Serve para /sobre, /empresas, qualquer página cujo título não dependa de dado.

rota dinâmica

generateMetadata

Uma função async, que recebe os mesmos params da página e pode buscar dado.

app/vagas/[id]/page.tsx
export async function generateMetadata({ params }: Props): Promise<Metadata> { const { id } = await params; const vaga = await buscarVaga(id); if (!vaga) return { title: "Vaga não encontrada · Leque de Vagas" }; return { title: `${vaga.titulo} · ${vaga.empresa}`, description: vaga.descricao.slice(0, 150), }; }

Parece que o dado é buscado duas vezes — uma aqui, outra na página. Não é. O Next junta os dois fetch iguais do mesmo pedido num só; é a request memoization. Escreva o código óbvio, que a otimização já veio de fábrica.

fim · aula 04 · o que fica

O que fica de hoje

  • Server Component pode esperar. async na função, await no corpo, e o HTML sai com o dado dentro — sem useEffect, sem estado de carregando.
  • Cache é escolha sua. O padrão do Next 16 é não guardar nada; revalidate é você dizendo quão velho o dado pode ficar.
  • Estático e dinâmico não se configuram. Você decide sem querer, ao usar algo que só existe no pedido. A legenda do build é onde isso aparece.
  • Suspense divide a espera, não a encurta. O total é o mesmo; o que muda é quando a pessoa vê a primeira coisa.
  • Cada rota tem o seu título. generateMetadata recebe os mesmos params da página e pode buscar dado — e o Next não busca duas vezes.
