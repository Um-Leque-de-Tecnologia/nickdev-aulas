Exercícios em aula · Aula 04

O dado vem de fora 🌐

Quatro labs, na ordem em que um depende do outro. No fim da aula o Leque de Vagas não tem mais nenhuma vaga escrita dentro do projeto — e você sabe dizer, olhando o terminal, quantas vezes ele foi buscar.

🧭

A ordem importa

Primeiro o dado sai do projeto (lab 1). Só então faz sentido perguntar quantas vezes ele é buscado (lab 2), porque antes disso não havia busca nenhuma. Com o cache resolvido, dá para olhar o build e entender por que umas rotas já estão prontas e outras não (lab 3). E no fim, com uma espera de verdade no caminho, o Suspense tem o que fazer (lab 4).

Os labs 1 e 2 são de todo mundo: sem eles o desafio da semana não começa. Os labs 3 e 4 já são pedaços do desafio — o 4 é literalmente a parte da frente 4.

📋

O formato que se repete

Toda busca de hoje tem este desenho. Copiar daqui é o esperado — o que muda de um lugar para o outro é o nome do arquivo e a opção de cache.

// lib/api.ts — o único arquivo que conhece a URL
const resposta = await fetch(`${FONTE}/vagas.json`, { next: { revalidate: 60 } });
if (!resposta.ok) throw new Error(`vagas.json respondeu ${resposta.status}`);
return resposta.json();
a URLAbsoluta, com https://. No servidor não existe "o site atual".

o .okA linha que separa "deu 404" de uma hora de depuração.

Antes de começar

  • O projeto da aula 03 sobe: npm run dev mostra Ready in ... ms.
  • /vagas lista as vagas e /vagas/1 abre uma delas.
  • Você consegue dar push no repositório da equipe — vai precisar disso no lab 1.
  • O terminal do npm run dev está visível ao lado do navegador. Hoje ele é metade da aula.

Se alguma falhar, resolva agora. Chame na aula: quinze minutos aqui valem mais do que uma hora tentando fazer o lab 4 em cima de um projeto que não sobe.

Os labs
LAB 1

O dado sai do projeto

~12 min

Trocar o import por uma busca de verdade — e ver, com os seus olhos, o componente esperar.

Os passos 1 a 4 são da frente 1, na máquina dela, com as outras três acompanhando na tela e conferindo a URL. Não são quatro pessoas criando quatro vagas.json: é um arquivo, e ele precisa estar no ar antes de qualquer outra coisa. Do passo 5 em diante cada pessoa dá git pull e repete o exercício na tela que já é dela — frente 4 em /vagas, frente 1 em /vagas/[id], frente 2 em /empresas/[slug].

  1. [frente 1] Crie dados/vagas.json na raiz do repositório (fora de app/, fora de public/) e mova para lá o array que estava em data/vagas.ts. JSON não tem export, não tem const e não aceita vírgula sobrando no fim.
  2. [frente 1] Em data/vagas.ts deixe só o tipo — e aproveite para renomear o arquivo para lib/tipos.ts, já que ele não guarda mais dado nenhum.
  3. [frente 1] git add, commit, push. Abra o arquivo no GitHub, clique em Raw e cole a URL no grupo. É ela que o projeto inteiro vai usar.
  4. [frente 1] Crie lib/api.ts com a constante FONTE e a função listarVagas(). Commit e push — agora as outras três podem começar.
  5. [cada pessoa, na sua tela] git pull. Depois: async antes de function, await listarVagas() no corpo, e apague o import do array. A frente 4 faz isso em /vagas, a frente 1 em /vagas/[id], a frente 2 em /empresas/[slug].
  6. Ponha um console.log dentro do listarVagas(), recarregue a sua tela três vezes e conte as linhas no terminal.
// lib/api.ts
import type { Vaga } from "@/lib/tipos";

// A URL mora AQUI, e só aqui. Quando a API do Spring Boot ficar de pé,
// é esta linha que muda — e nenhuma página fica sabendo.
const FONTE = "https://raw.githubusercontent.com/SUA-EQUIPE/leque-de-vagas/main/dados";

export async function listarVagas(): Promise<Vaga[]> {
  console.log("[api] buscando vagas.json");   // temporário: é o que este lab conta

  const resposta = await fetch(`${FONTE}/vagas.json`);
  if (!resposta.ok) throw new Error(`vagas.json respondeu ${resposta.status}`);

  return resposta.json();
}
// app/vagas/page.tsx — o antes e o depois

// ANTES (aula 03)
import { vagas } from "@/data/vagas";
export default function Vagas() { ... }

// DEPOIS

  return <MuralDeVagas vagas={vagas} />;
}
3 recargas =linhas

Cuidado com a URL. A do github.com/... devolve a página do GitHub, em HTML — e o .json() quebra com "Unexpected token '<'". A que serve começa com raw.githubusercontent.com. Abra no navegador antes de colar no código: você tem que ver o JSON cru, sem barra lateral e sem botão.

responda
  1. Quantas linhas saíram no terminal para três recargas?
  2. Você não escreveu useEffect nem estado de carregando. Por que não precisou?
  3. Tente pôr "use client" na primeira linha do page.tsx. Que erro aparece — e o que ele diz sobre onde a busca pode acontecer?
ver a resposta — depois de tentar

1. Três — uma por recarga. E é essa a surpresa do lab 2: o Next 16 não guarda o resultado do fetch por conta própria. Se você jurava que "o Next cacheia tudo", jurava certo para a versão 13, e errado para a sua.

2. Porque ninguém está olhando ainda. A função rodou no servidor, antes de qualquer coisa chegar ao navegador — ela podia parar e esperar à vontade. O useEffect existe para buscar dado depois que a tela já apareceu; aqui a tela ainda não apareceu, e por isso não há estado intermediário para guardar. O HTML sai do servidor já com as vagas dentro.

3. <SeuComponente> is an async Client Component. Only Server Components can be async at the moment. — e a frase seguinte já entrega o diagnóstico sozinha: "This error is often caused by accidentally adding 'use client' to a module that was originally written for the server." A fronteira da aula 03 continua exatamente onde estava, e agora ganhou um segundo motivo: quem busca é o servidor, quem reage é o cliente. O MuralDeVagas continua com "use client" e continua guardando a busca no useState — só que agora ele recebe as vagas prontas por prop, em vez de importá-las.

LAB 2

Conte as buscas

~10 min

Fazer o número do lab 1 parar de subir — e descobrir quem paga a conta da espera quando o cache vence.

  1. Recarregue /vagas cinco vezes e anote o número de linhas. É a coluna "sem nada".
  2. Acrescente { cache: "force-cache" } ao fetch. Derrube o servidor (Ctrl+C), suba de novo, recarregue cinco vezes. Anote.
  3. Troque por { next: { revalidate: 20 } }. Recarregue cinco vezes rápido, uma atrás da outra. Anote.
  4. Agora espere meio minuto sem tocar em nada e recarregue mais uma vez. O número mudou?
  5. Sem parar o servidor, edite o vagas.json direto no GitHub (botão do lápis → Commit changes), volte, espere 20 segundos e recarregue duas vezes seguidas. Em qual delas a mudança apareceu?
// as três formas, no mesmo fetch — uma de cada vez

fetch(url)                                     // padrão: busca sempre
fetch(url, { cache: "force-cache" })          // busca uma vez e guarda
fetch(url, { next: { revalidate: 20 } })      // guarda por 20 segundos

Em desenvolvimento o cache mente um pouco. O npm run dev recompila e joga cache fora a toda hora, para você ver a sua mudança na tela. O comportamento de verdade é o do npm run build seguido de npm start. Se o seu número não bater com o do colega, é quase sempre isto — confira nos dois.

responda
  1. Com force-cache, quantas linhas para cinco recargas? Por que esse número?
  2. No passo 5, a vaga editada apareceu na primeira recarga depois dos 20 segundos, ou na segunda?
  3. O revalidate: 20 promete o quê, exatamente: "o dado nunca terá mais de 20 segundos", ou outra coisa?
ver a resposta — depois de tentar

1. Uma. A primeira busca guardou a resposta; as outras quatro leram do que estava guardado, sem sair da máquina. É por isso que o passo 2 pede para derrubar e subir o servidor: sem isso você estaria medindo o cache da rodada anterior.

2. Na segunda, quase sempre — e essa é a parte que surpreende. Passados os 20 segundos, o dado guardado fica velho, mas não é jogado fora. A próxima pessoa que chega recebe a versão velha na hora, e é a chegada dela que dispara a busca nova, em segundo plano. Quem vê o dado novo é quem chega depois. Isso tem nome: stale-while-revalidate — sirva o velho, atualize atrás. E é a razão de ninguém nunca esperar pela revalidação.

3. A segunda coisa. A promessa é "não vou buscar de novo antes de 20 segundos", e não "o que você vê tem no máximo 20 segundos". Se ninguém visitar a página por duas horas, o dado guardado tem duas horas de idade — e a primeira pessoa a chegar vai vê-lo assim. Um cache só trabalha quando alguém bate na porta.

LAB 3

Leia o seu próprio build

~10 min

Fazer uma rota trocar de símbolo de propósito, e saber qual linha causou isso.

  1. Rode npm run build. Copie a tabela inteira num arquivo de rascunho — é o seu "antes".
  2. Acrescente generateStaticParams em app/vagas/[id]/page.tsx. Rode o build de novo.
  3. Conte: quantas rotas apareceram embaixo de /vagas/[id], e que símbolo elas têm?
  4. Em app/vagas/page.tsx, receba searchParams e mostre o valor de q em qualquer canto da tela. Build de novo.
  5. Olhe o símbolo do /vagas. Ele mudou. Desfaça o passo 4 e confirme que ele volta ao que era.
// app/vagas/[id]/page.tsx
export async function generateStaticParams() {
  const vagas = await listarVagas();

  // Uma entrada por página a gerar. A CHAVE tem que se chamar `id`,
  // igual ao nome da pasta [id] — e o valor tem que ser TEXTO.
  return vagas.map((vaga) => ({ id: String(vaga.id) }));
}

Não achou a tabela? Ela sai no fim do npm run build, depois dos avisos. Se o build falhou, ela nem chega a existir — leia o erro de cima para baixo, que a primeira linha é a única que interessa.

responda
  1. Quantas rotas o passo 2 gerou, e de onde saiu esse número?
  2. Que linha, exatamente, tornou o /vagas dinâmico no passo 4?
  3. Se alguém abrir /vagas/999, que não foi pré-gerada, o site quebra?
ver a resposta — depois de tentar

1. Uma por vaga do vagas.json — doze, se vocês fizeram o mínimo do desafio 03. O número não está escrito em lugar nenhum: ele sai do dado. Publicar uma vaga nova e refazer o build gera a página nova sozinha, e é essa a graça.

2. A que usa o searchParams. Não a que o recebe como parâmetro: a que lê o valor. Enquanto o Next consegue montar a página sem saber nada sobre quem pediu, ele monta uma vez e reaproveita para todo mundo. No instante em que a página depende do que veio na URL, não existe "uma versão para todo mundo" — e ela passa a ser montada a cada pedido. cookies() e headers() fazem o mesmo efeito, pelo mesmo motivo.

3. Não. Ela é montada na hora, na primeira visita, e a partir daí fica guardada como as outras. generateStaticParams é uma lista de adiantamentos, não uma lista de permissões. Quem decide que /vagas/999 não existe é o notFound() dentro da página — e isso é a parte da frente 3 no desafio.

LAB 4

Divida a espera em dois

~12 min

Fazer o título aparecer antes do dado — e entender por que isso é performance, mesmo com o total igual. Este lab é a parte 4 do desafio começando em aula.

  1. Crie components/NumerosDoCatalogo.tsx: async, chama listarVagas(), mostra "{vagas.length} vagas · {iniciantes} aceitam quem está começando".
  2. Acrescente um atraso proposital de 2 segundos antes do return. É temporário e sai antes do commit — está aqui só para você sentir a espera.
  3. Use o componente em /vagas, sem Suspense. Recarregue e cronometre: quando o <h1>Vagas</h1> aparece?
  4. Agora embrulhe em <Suspense>, com um fallback do mesmo tamanho do bloco real. Recarregue e cronometre de novo.
  5. Tire o async e o await da página — os que o lab 1 pôs lá — e mova a busca da listagem para um ListagemDeVagas async, dentro do seu próprio <Suspense>. Enquanto a página for async, ela espera antes de mandar qualquer coisa, e o <h1> não chega cedo coisa nenhuma.
  6. Apague o atraso do passo 2 antes de commitar.
// components/NumerosDoCatalogo.tsx — FRENTE 4
import { listarVagas } from "@/lib/api";

export default async function NumerosDoCatalogo() {
  // TEMPORÁRIO — só para sentir a espera. Apague antes do commit.
  await new Promise((ok) => setTimeout(ok, 2000));

  const vagas = await listarVagas();
  const iniciantes = vagas.filter((v) => v.aceitaIniciante).length;

  return (
    <p className="numeros">
      {vagas.length} vagas · {iniciantes} aceitam quem está começando
    </p>
  );
}
// app/vagas/page.tsx — a cerca em volta do pedaço lento
import { Suspense } from "react";

export default function Vagas() {      // repare: NÃO é async
  return (
    <>
      <h1>Vagas</h1>

      <Suspense fallback={<p className="numeros esqueleto">&nbsp;</p>}>
        <NumerosDoCatalogo />
      </Suspense>

      <Suspense fallback={<ListaEsqueleto />}>
        <ListagemDeVagas />   {/* a listagem do lab 1, agora num filho */}
      </Suspense>
    </>
  );
}

// O await que saiu da página mora aqui. É este componente que espera —
// e por isso é ele que o Suspense de cima consegue cercar.
async function ListagemDeVagas() {
  const vagas = await listarVagas();
  return <MuralDeVagas vagas={vagas} />;
}

O fallback tem que ter o tamanho do conteúdo real. Um "Carregando…" de uma linha no lugar de um bloco de 300px faz a página inteira pular quando o dado chega — e o dedo de quem já ia clicar acerta outra coisa. Dê ao esqueleto a mesma altura, com min-height se precisar.

responda
  1. Sem Suspense, quando o <h1> apareceu? E com?
  2. A página termina de carregar mais cedo com Suspense?
  3. Se o total não mudou, por que isso conta como performance?
ver a resposta — depois de tentar

1. Sem Suspense, o <h1> só aparece depois dos 2 segundos — junto com tudo. O servidor segurou a resposta inteira esperando o pedaço mais lento, e a pessoa ficou olhando uma tela em branco. Com Suspense, o título aparece quase imediatamente, com o esqueleto embaixo.

2. Não. Os 2 segundos continuam lá — o dado não chega mais rápido porque você desenhou uma cerca em volta dele. Os dois carregamentos terminam praticamente no mesmo instante.

3. Porque performance, para quem está do outro lado, não é o tempo total: é o tempo até a primeira coisa útil. Uma página que mostra o título e o menu em 100ms e completa em 2s parece rápida. Uma que mostra tudo de uma vez em 2s parece travada — e é a mesma página, com os mesmos 2 segundos. É a diferença entre esperar em pé na fila e esperar sentada com o cardápio na mão.

Quando der errado
a mensagemo que aconteceuo conserto
<SeuComponente> is an async Client Component. Only Server Components can be async at the moment. O arquivo tem "use client" na primeira linha e você pôs async na função. Quem busca é o componente de servidor. Tire o async daqui, busque no pai e passe por prop.
Failed to parse URL from /dados/vagas.json URL relativa. No servidor não existe "o site atual" para completar o endereço — não há navegador ali. URL absoluta, sempre, começando em https://.
Unexpected token '<', "<!DOCTYPE "... is not valid JSON O .json() recebeu HTML. Quase sempre é a página 404 do GitHub, porque a URL está errada ou o arquivo ainda não subiu. Abra a URL no navegador. Confira resposta.ok antes do .json().
SyntaxError: Expected double-quoted property name O vagas.json ainda tem sintaxe de TypeScript: vírgula sobrando no fim, aspas simples, ou comentário. JSON puro: aspas duplas em toda chave, sem vírgula final, sem comentário.
a página mudou no GitHub e o site não O cache está fazendo exatamente o que você mandou. Espere o revalidate vencer, recarregue duas vezes, ou confira com build + start.
o fallback do Suspense nunca aparece O await está na página, e não dentro do componente cercado — a página já esperou antes de chegar no Suspense. Mova a busca para dentro do filho. A página não pode ser async.
generateStaticParams não gerou nada A chave do objeto não bate com o nome da pasta, ou o valor não é texto. Pasta [id] → chave id. String(vaga.id).
a rota virou ƒ e você não pediu Alguém na árvore usou searchParams, cookies() ou headers(). Nem sempre é erro. Só descubra quem foi — e decida se era para ser.
Antes de fechar o computador
  1. Tire os console.log e o setTimeout de 2 segundos.
  2. npm run build passa sem erro, e você sabe explicar o símbolo de cada rota.
  3. Não sobrou nenhum import de array de dados em app/.
  4. Commit, push, e a Vercel publicou. Abra o site no celular e confira que as vagas aparecem.
