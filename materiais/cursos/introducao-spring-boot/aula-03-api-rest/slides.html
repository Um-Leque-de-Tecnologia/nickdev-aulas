// o vocabulário

Recurso, verbo e status

Uma requisição HTTP diz três coisas. Cada uma tem um lugar certo.

📍

O recurso é a URL

E é substantivo, no plural. /vagas, /empresas.

Nunca verbo: /criarVaga está errado — quem diz a ação é o método.

🔤

O verbo é o método

GET lê, POST cria, PUT troca, DELETE apaga.

A mesma URL faz quatro coisas diferentes, dependendo do verbo.

🚦

O status é a resposta

Um número de três dígitos que diz o que aconteceu.

2xx deu certo · 4xx quem pediu errou · 5xx o servidor quebrou

os cinco status de hoje
200OK — li e estou te entregando.
201Created — criei. E digo onde ficou.
204No Content — fiz, e não tenho nada pra devolver.
404Not Found — isso que você pediu não existe.
400Bad Request — o que você mandou está malformado.
a mesma URL, quatro sentidos
GET    /vagas        // me dá todas
POST   /vagas        // crie mais uma

GET    /vagas/42     // me dá a 42
PUT    /vagas/42     // troque a 42
DELETE /vagas/42     // apague a 42

Só existem duas URLs aqui. O resto é verbo.

// quem decide o status
PASSO 1 DE 4

ResponseEntity

Até agora o seu controller devolvia o objeto, e o Spring carimbava 200 sozinho. ResponseEntity é você tomando essa decisão de volta.

VagaService.java
// devolve Optional: "pode ser que não tenha"
public Optional<Vaga> buscarPorId(String id) {
    return repository.todas().stream()
        .filter(v -> v.id().equals(id))
        .findFirst();
}
VagaController.java
@GetMapping("/{id}")
public ResponseEntity<Vaga> porId(@PathVariable String id) {
    return service.buscarPorId(id)
        .map(ResponseEntity::ok)
        .orElse(ResponseEntity.notFound().build());
}
1O service devolve Optional — ele sabe se achou, mas não sabe o que é um 404. Status é assunto de HTTP, e o service não conhece HTTP.
2O controller traduz: achou vira ok, não achou vira notFound. É exatamente o trabalho dele — falar HTTP.
3.build() fecha uma resposta sem corpo. Um 404 não precisa devolver nada além do número.

Repare que nenhum if apareceu. Optional + map + orElse diz a mesma coisa e não deixa você esquecer o caso do “não achou”.

PASSO 2 DE 4

POST: o corpo vem na requisição

Até agora tudo que a sua API recebia vinha na URL. Para criar, o dado é grande demais pra caber lá — e vem no corpo.

VagaController.java
@PostMapping
public ResponseEntity<Vaga> criar(@RequestBody Vaga nova) {
    Vaga salva = service.criar(nova);

    URI onde = URI.create("/vagas/" + salva.id());
    return ResponseEntity.created(onde).body(salva);
}
api.http
### criar uma vaga
POST http://localhost:8080/vagas
Content-Type: application/json

{
  "titulo": "Pessoa Desenvolvedora Java",
  "area": "Back-end",
  "senioridade": "Júnior"
}
1@RequestBody diz ao Spring: pegue o JSON que veio e transforme neste objeto. Ele faz sozinho, casando pelos nomes dos campos.
2O status é 201, não 200. Existe um status que significa exatamente “criei uma coisa nova” — use ele.
3.created(uri) devolve 201 e põe o cabeçalho Location com o endereço do que nasceu. Quem chamou não precisa adivinhar onde a coisa ficou.

O Location é a parte que quase todo mundo esquece. Ele é o que diferencia “criei” de “criei, e está bem ali”.

LAB 3

Crie pelo POST

~15 min

Deixe o repository aceitar mais um

Sua lista hoje é List.of(...), que é imutável — não dá pra adicionar. Troque por new ArrayList<>(List.of(...)) e crie um método salvar(Coisa c).

No service, gere o id

Quem chama o POST não manda id — quem decide o id é a API. Use UUID.randomUUID().toString() e monte a coisa nova com ele.

No controller, @PostMapping e 201

Com @RequestBody no parâmetro e ResponseEntity.created(...) no retorno.

Teste e confira o cabeçalho

Mande o POST pelo api.http. Depois procure Location na resposta, copie o endereço e chame ele com GET.

quando terminar

O POST devolveu 201 com Location, e o GET naquele endereço achou o que você acabou de criar? O ciclo fechou.

// trocar e apagar
PASSO 3 DE 4

PUT, DELETE e uma palavra difícil

VagaController.java
@PutMapping("/{id}")
public ResponseEntity<Vaga> trocar(
        @PathVariable String id,
        @RequestBody Vaga nova) {
    return service.trocar(id, nova)
        .map(ResponseEntity::ok)
        .orElse(ResponseEntity.notFound().build());
}

@DeleteMapping("/{id}")
public ResponseEntity<Void> apagar(@PathVariable String id) {
    if (!service.apagar(id)) {
        return ResponseEntity.notFound().build();
    }
    return ResponseEntity.noContent().build();
}
🔁

Idempotente

Quer dizer: chamar uma vez ou dez vezes dá no mesmo.

PUT e DELETE são. POST não é.

!Mandar o mesmo POST três vezes cria três vagas. Por isso o botão de “enviar” some depois do clique nos sites bem-feitos.
✓Mandar o mesmo PUT três vezes deixa a vaga do mesmo jeito nas três. É seguro repetir quando a internet cai no meio.
204No Content no DELETE: apaguei, e não sobrou nada pra te mostrar. Devolver o objeto apagado seria estranho.

Aqui o if aparece porque apagar devolve boolean, não Optional — não há objeto para embrulhar. Está certo assim.

LAB 4

Complete o CRUD

~20 min

No repository: trocar e remover

Ache o índice pelo id. Para trocar, lista.set(i, nova). Para remover, lista.removeIf(c -> c.id().equals(id)), que já devolve boolean.

No service, preserve o id

O corpo do PUT não traz id — ele veio na URL. Monte a coisa nova com o id do caminho e os campos do corpo. Se deixar o id do corpo passar, ele vem null e você perde o registro.

No controller: @PutMapping e @DeleteMapping

Os dois com "/{id}". PUT devolve 200 ou 404; DELETE devolve 204 ou 404.

Prove a idempotência

Mande o mesmo DELETE duas vezes. A primeira dá 204, a segunda dá 404 — e a lista fica igual nas duas. Depois mande o mesmo PUT duas vezes e confira que o resultado não muda.

quando terminar

Você tem GET, POST, PUT e DELETE funcionando, cada um com o seu status? Então a sua API virou um CRUD de verdade.

PASSO 4 DE 4

@RequestParam: a busca

Filtro não é recurso. /vagas/Back-end estaria dizendo que “Back-end” é o id de uma vaga — e não é.

VagaController.java
@GetMapping("/busca")
public List<Vaga> buscar(
        @RequestParam(required = false) String area,
        @RequestParam(required = false) String senioridade) {
    return service.buscar(area, senioridade);
}
### os dois filtros
GET /vagas/busca?area=Back-end&senioridade=Júnior

### só um — o outro fica null
GET /vagas/busca?area=Dados

### nenhum: devolve tudo
GET /vagas/busca
1O que vem depois do ? é parâmetro de consulta: filtro, ordenação, página. O caminho identifica o quê; a consulta refina quais.
2required = false deixa o filtro opcional. Sem isso, faltar um parâmetro vira 400.
3Busca que não acha nada devolve 200 com lista vazia — e agora isso está certo: você procurou, e o resultado é zero. Diferente de pedir um id que não existe.
4/vagas/busca e /vagas/{id} convivem: o Spring escolhe pela especificidade, e caminho literal ganha de variável. A ordem em que você declara não importa — em Express importaria.

Essa é a diferença que fecha o dia: lista vazia é resposta, coisa inexistente é 404. O mesmo corpo, sentidos opostos.

// fechando

O que fica de hoje

1A URL é substantivo, o verbo é a ação. /criarVaga nunca mais.
2Status é contrato. 200, 201, 204, 404 — cada um diz uma coisa que o corpo da resposta não diz.
3O service devolve Optional; quem traduz para HTTP é o controller. Camada nenhuma invade a outra.
4201 leva Location. Criar sem dizer onde ficou é meio trabalho.
5PUT e DELETE são idempotentes, POST não. Repetir os dois primeiros é seguro.
6Filtro vai em @RequestParam, depois do ?. Nunca vira caminho.

A segunda evolução do Leque de Vagas. Quatro partes, uma por frente — e todas elas mexem em status.
