Os quatro status, parte por parte

O desafio resolvido. A parte 1 está comentada linha por linha porque é a referência das outras; as partes 2 e 3 mostram só o que muda, e a parte 4 volta a vir inteira porque estreia @RequestParam.

Tente antes de abrir isto

Esta é a referência de quando travar, não o ponto de partida. Nesta aula especialmente: o que está sendo aprendido é qual status usar quando, e isso não se aprende lendo — se aprende decidindo e errando.

A combinação, antes de qualquer código

O corpo do POST não é o objeto que a API devolve. Nesta aula vocês ainda usam o mesmo record nos dois lados — aceitando que o id chega null e é ignorado. Funciona, e é o suficiente hoje.

o que entra e o que sai
// o cliente MANDA (sem id — quem inventa o id é a API)
{ "titulo": "Dev Java Júnior", "area": "Back-end",
  "senioridade": "Júnior", "empresaSlug": "aurora-tech" }

// a API DEVOLVE, com 201 e o cabeçalho Location
{ "id": "9c1f4e2a-…", "titulo": "Dev Java Júnior", … }

Guardem o incômodo de mandar um record com campo que não se usa: a aula 04 tem nome para ele — DTO.

Dois controllers no mesmo caminho

A parte 4 precisa de /vagas/busca, e o VagaController é da parte 1. Duas pessoas no mesmo arquivo, na mesma semana, é conflito de merge na certa — então a parte 4 cria o próprio controller.

O Spring aceita. O que ele recusa são duas rotas idênticas, e /vagas/busca não é /vagas/{id}. E não há ambiguidade: o Spring escolhe por especificidade, e caminho literal ganha de variável — a ordem em que você declara não importa, ao contrário do que acontece em Express.

Parte 1 · VagaRepository
VagaRepository.java
@Repository
public class VagaRepository {

    // List.of(...) é IMUTÁVEL — não aceita add nem set. Envolver num
    // ArrayList é o que torna o repository escrevível.
    private final List<Vaga> vagas = new ArrayList<>(List.of(
        new Vaga("1", "Pessoa Desenvolvedora Front-end Júnior", …),
        // … as 12 vagas da aula 02
    ));

    // copyOf protege a lista interna: quem recebe não consegue
    // alterá-la por fora, e a única porta de escrita continua aqui.
    public List<Vaga> todas() {
        return List.copyOf(vagas);
    }

    public Optional<Vaga> porId(String id) {
        return vagas.stream().filter(v -> v.id().equals(id)).findFirst();
    }

    public Vaga salvar(Vaga nova) {
        vagas.add(nova);
        return nova;
    }

    // Devolve Optional: vazio quer dizer "esse id não existe aqui",
    // que é o que o controller precisa para escolher o 404.
    public Optional<Vaga> trocar(String id, Vaga nova) {
        for (int i = 0; i < vagas.size(); i++) {
            if (vagas.get(i).id().equals(id)) {
                vagas.set(i, nova);
                return Optional.of(nova);
            }
        }
        return Optional.empty();
    }

    // removeIf já devolve true/false: apagou ou não achou.
    public boolean remover(String id) {
        return vagas.removeIf(v -> v.id().equals(id));
    }
}
Parte 1 · VagaService
VagaService.java
@Service
public class VagaService {

    private final VagaRepository repository;

    public VagaService(VagaRepository repository) {
        this.repository = repository;
    }

    public List<Vaga> listar() {
        return repository.todas();
    }

    // Nenhum ResponseEntity por aqui: o service não conhece HTTP.
    public Optional<Vaga> buscarPorId(String id) {
        return repository.porId(id);
    }

    // O id nasce AQUI. Se viesse do cliente, dois clientes poderiam
    // escolher o mesmo e um sobrescreveria o outro em silêncio.
    public Vaga criar(Vaga nova) {
        Vaga comId = new Vaga(
            UUID.randomUUID().toString(),
            nova.titulo(), nova.descricao(), nova.area(),
            nova.senioridade(), nova.local(),
            nova.aceitaIniciante(), nova.empresaSlug());
        return repository.salvar(comId);
    }

    // A ARMADILHA: o id vem da URL, não do corpo. Usar nova.id() aqui
    // gravaria null no lugar do id e você perderia o registro.
    public Optional<Vaga> trocar(String id, Vaga nova) {
        Vaga comId = new Vaga(
            id,
            nova.titulo(), nova.descricao(), nova.area(),
            nova.senioridade(), nova.local(),
            nova.aceitaIniciante(), nova.empresaSlug());
        return repository.trocar(id, comId);
    }

    public boolean apagar(String id) {
        return repository.remover(id);
    }
}
Parte 1 · VagaController

É aqui, e só aqui, que se fala HTTP.

VagaController.java
@RestController
@RequestMapping("/vagas")
public class VagaController {

    private final VagaService service;

    public VagaController(VagaService service) {
        this.service = service;
    }

    // Lista sempre existe, mesmo vazia — 200 direto, sem ResponseEntity.
    @GetMapping
    public List<Vaga> listar() {
        return service.listar();
    }

    // map roda se achou, orElse se não achou. O if está aí dentro —
    // e o compilador não deixa você esquecer o segundo caso.
    @GetMapping("/{id}")
    public ResponseEntity<Vaga> porId(@PathVariable String id) {
        return service.buscarPorId(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }

    // 201 + Location: criei, e está bem ali.
    @PostMapping
    public ResponseEntity<Vaga> criar(@RequestBody Vaga nova) {
        Vaga salva = service.criar(nova);
        URI onde = URI.create("/vagas/" + salva.id());
        return ResponseEntity.created(onde).body(salva);
    }

    @PutMapping("/{id}")
    public ResponseEntity<Vaga> trocar(@PathVariable String id,
                                       @RequestBody Vaga nova) {
        return service.trocar(id, nova)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }

    // ResponseEntity<Void>: não há corpo nenhum para tipar.
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> apagar(@PathVariable String id) {
        return service.apagar(id)
            ? ResponseEntity.noContent().build()
            : ResponseEntity.notFound().build();
    }
}
Parte 2 · Empresa — o que muda

A estrutura é idêntica à da parte 1. Uma coisa é diferente, e é ela que a frente 2 explica na apresentação: o identificador não é gerado pela API — vem no corpo, escolhido por quem cria.

EmpresaController.java · só o POST
@PostMapping
public ResponseEntity<Empresa> criar(@RequestBody Empresa nova) {
    Empresa salva = service.criar(nova);

    // Na parte 1 o Location aponta para um id que a API inventou.
    // Aqui aponta para o slug que O CLIENTE escolheu. Mesmo 201,
    // responsabilidade sobre o endereço em lados opostos.
    URI onde = URI.create("/empresas/" + salva.slug());
    return ResponseEntity.created(onde).body(salva);
}

O GET /empresas/{slug} e o DELETE /empresas/{slug} seguem a parte 1 letra por letra — troque id por slug e Vaga por Empresa.

Parte 3 · Pessoa — o que muda

O código é o da parte 1, com Pessoa no lugar de Vaga. A entrega diferente da frente 3 não é código: é a evidência de que PUT e DELETE são idempotentes e POST não é.

Parte 3 · idempotencia.http
idempotencia.http · versionado na raiz do repositório
### 1 · POST duas vezes — NÃO é idempotente
POST http://localhost:8080/pessoas
Content-Type: application/json

{ "nome": "Ana", "email": "ana@exemplo.com" }

// 1ª: 201 Created · id a1b2
// 2ª: 201 Created · id c3d4  ← existem DUAS Anas agora

### 2 · PUT duas vezes — é idempotente
PUT http://localhost:8080/pessoas/a1b2
Content-Type: application/json

{ "nome": "Ana Nogueira", "email": "ana@exemplo.com" }

// 1ª: 200 OK · 2ª: 200 OK, e o registro está IDÊNTICO

### 3 · DELETE duas vezes — é idempotente
DELETE http://localhost:8080/pessoas/a1b2

// 1ª: 204 No Content · 2ª: 404 Not Found
// As respostas diferem; o ESTADO não — a pessoa não existe nas duas.
// Idempotência é sobre o servidor, não sobre o que ele responde.
Parte 4 · BuscaService e BuscaController
BuscaService.java
@Service
public class BuscaService {

    // O repository da parte 1, não o service dela — igual à aula 02.
    private final VagaRepository repository;

    public BuscaService(VagaRepository repository) {
        this.repository = repository;
    }

    // Boolean, e não boolean: só o objeto pode ser null, e null é
    // exatamente como "o filtro não foi enviado" chega aqui.
    public List<Vaga> buscar(String area, String senioridade,
                             Boolean aceitaIniciante) {
        return repository.todas().stream()
            .filter(v -> area == null
                      || v.area().equalsIgnoreCase(area))
            .filter(v -> senioridade == null
                      || v.senioridade().equalsIgnoreCase(senioridade))
            .filter(v -> aceitaIniciante == null
                      || v.aceitaIniciante() == aceitaIniciante)
            .toList();
    }
}
BuscaController.java
@RestController
@RequestMapping("/vagas")   // mesmo caminho base do VagaController
public class BuscaController {

    private final BuscaService service;

    public BuscaController(BuscaService service) {
        this.service = service;
    }

    // Busca sem resultado devolve 200 com lista vazia — e isso está
    // CERTO. Você procurou, o resultado é zero. Diferente de pedir
    // um id que não existe, que é 404.
    @GetMapping("/busca")
    public List<Vaga> buscar(
            @RequestParam(required = false) String area,
            @RequestParam(required = false) String senioridade,
            @RequestParam(required = false) Boolean aceitaIniciante) {
        return service.buscar(area, senioridade, aceitaIniciante);
    }
}

Sem required = false, faltar um parâmetro vira 400 Bad Request — e a busca só funcionaria com os três filtros preenchidos, o que não é busca.

O que a correção procura
  • 404 em todo GET de item. Nas três frentes que têm recurso, não só na 1.
  • 201 com Location. 201 sem Location conta metade.
  • 204 no DELETE, sem corpo. 200 com o objeto apagado está errado.
  • Nenhum ResponseEntity no service. Status é do controller; achar ou não achar é do service.
  • O id do PUT vem da URL. Se o corpo mandar id e ele for usado, o registro se perde.
  • required = false nos três filtros da parte 4.
  • GET /estatisticas ainda funcionando. Evoluir não pode quebrar o que já existia.
  • Um commit por pessoa, e o README dizendo o que cada frente aprendeu de diferente.
Se der errado

415 Unsupported Media Type no POST
Faltou a linha Content-Type: application/json no api.http. Sem ela o Spring não sabe que o corpo é JSON, e o @RequestBody não tem conversor para escolher.

UnsupportedOperationException no POST
A lista ainda é List.of(...), que é imutável. Envolva num new ArrayList<>(List.of(...)).

O PUT gravou null no id
Você usou nova.id() em vez do id do @PathVariable. O corpo do PUT não traz id — ele veio na URL.

Ambiguous mapping ao subir
Duas rotas idênticas em controllers diferentes. /vagas/busca e /vagas/{id} podem conviver; duas /vagas/busca, não.

O DELETE devolve 200 em vez de 204
Você usou ResponseEntity.ok(). O correto é noContent() — e o tipo do método é ResponseEntity<Void>, não <Vaga>.
