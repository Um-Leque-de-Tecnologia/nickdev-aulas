Exercícios em aula · Aula 03

Faça a sua API dizer a verdade 🚦

Você vai pegar as três classes da aula 02 e ensiná-las a responder o status certo — e a aceitar os verbos que faltavam. Quatro labs, no seu projetinho pessoal.

🧭

A ordem importa de novo

Lab 1 só olha. Lab 2 conserta a leitura. Lab 3 ensina a criar. Lab 4 fecha com trocar e apagar. Cada um depende do anterior — não pule.

📮

A ferramenta de hoje é um arquivo de texto

Nada de instalar Insomnia ou Postman. Um arquivo api.http na raiz do projeto, executado pelo IntelliJ ou pelo VS Code com a extensão REST Client, faz o mesmo — e vai versionado no Git, o que Insomnia nenhum faz de graça.

Quem clonar o seu projeto recebe as requisições junto com o código. É assim que time de verdade compartilha chamada de API antes de existir documentação.

Os quatro labs
LAB 1

Ouça o que a sua API responde

~10 min

Antes de consertar, ver o defeito com os próprios olhos — e ganhar a ferramenta do semestre.

  1. Crie api.http na raiz do projeto, ao lado do pom.xml.
  2. Escreva as três chamadas abaixo, separadas por ###.
  3. Rode a aplicação e clique em Send Request acima de cada uma.
  4. Anote o status das três — o número no topo da resposta, não o corpo.
### todos os itens
GET http://localhost:8080/receitas

### um que existe
GET http://localhost:8080/receitas/1

### um que NÃO existe
GET http://localhost:8080/receitas/nao-existe
responda
  1. Qual o status da terceira chamada?
  2. O corpo dela veio vazio. Quem está do outro lado consegue saber por quê?
  3. Se essa API alimentasse uma tela, o que a pessoa veria?
conferir depois de responder

1. 200 OK — o mesmo status da chamada que deu certo. É esse o problema.

2. Não. 200 com corpo vazio é ambíguo: pode ser “não existe” ou “existe e está vazio”. O cliente teria que adivinhar, e adivinhação vira bug.

3. Uma tela em branco, sem mensagem — porque para o front deu certo. O erro fica invisível até para o monitoramento, que não acusa 200.

LAB 2

Faça a sua API dizer 404

~15 min

Devolver o status certo quando o item não existe — sem pôr regra de HTTP dentro do service.

  1. No service, mude buscarPorId para devolver Optional<Coisa>: termine o stream com .findFirst() em vez de .toList().
  2. No controller, importe org.springframework.http.ResponseEntity.
  3. Troque o retorno do método para ResponseEntity<Coisa> e traduza o Optional.
  4. Rode o api.http de novo: a terceira chamada precisa virar 404, e a segunda continuar 200.
// no service — ele sabe se achou, mas não sabe o que é um 404
public Optional<Receita> buscarPorId(String id) {
    return repository.todas().stream()
        .filter(r -> r.id().equals(id))
        .findFirst();
}

// no controller — aqui, sim, se fala HTTP
@GetMapping("/{id}")
public ResponseEntity<Receita> porId(@PathVariable String id) {
    return service.buscarPorId(id)
        .map(ResponseEntity::ok)
        .orElse(ResponseEntity.notFound().build());
}
responda
  1. Por que o service devolve Optional em vez de já devolver o 404?
  2. O que .build() faz, e por que ele aparece no notFound mas não no ok?
  3. Não apareceu nenhum if. Onde foi parar a decisão?
conferir depois de responder

1. Porque status é assunto de HTTP, e o service não conhece HTTP. Se ele devolvesse 404, você não conseguiria reusá-lo numa tarefa agendada, num teste ou numa tela de terminal — todos lugares onde “404” não quer dizer nada.

2. .build() fecha uma resposta sem corpo. O ok(objeto) já recebeu o corpo e se fecha sozinho; o notFound() não tem corpo nenhum para receber, então precisa ser fechado à mão.

3. Para dentro do Optional. map só roda se houver valor, orElse só roda se não houver — é um if que o compilador não deixa você esquecer. Com if escrito à mão, esquecer o caso do “não achou” é o bug mais comum que existe.

LAB 3

Crie pelo POST

~15 min

Receber dado no corpo da requisição, gerar o id e responder 201 dizendo onde a coisa nasceu.

  1. No repository: sua lista é List.of(...), que é imutável. Troque por new ArrayList<>(List.of(...)) e crie salvar(Coisa c).
  2. No service: gere o id com UUID.randomUUID().toString() e monte a coisa nova com ele. O id nunca vem do cliente.
  3. No controller: @PostMapping, parâmetro com @RequestBody, retorno com ResponseEntity.created(...).
  4. Teste, ache o cabeçalho Location na resposta, copie o endereço e chame ele com GET.
@PostMapping
public ResponseEntity<Receita> criar(@RequestBody Receita nova) {
    Receita salva = service.criar(nova);
    URI onde = URI.create("/receitas/" + salva.id());
    return ResponseEntity.created(onde).body(salva);
}
### no api.http — repare no Content-Type
POST http://localhost:8080/receitas
Content-Type: application/json

{ "titulo": "Cuscuz", "minutos": 10 }
responda
  1. O que acontece se você esquecer a linha Content-Type: application/json?
  2. Por que o id é gerado no service, e não recebido do cliente?
  3. Para que serve o Location, se o objeto criado já veio no corpo?
conferir depois de responder

1. O Spring devolve 415 Unsupported Media Type. Sem o cabeçalho ele não sabe que o corpo é JSON, e o @RequestBody não tem como escolher o conversor.

2. Porque o id identifica, e quem responde pela identidade é quem guarda. Se o cliente escolhesse, dois clientes escolheriam o mesmo — e um sobrescreveria o outro sem ninguém perceber.

3. Para quem só precisa do endereço não ter que vasculhar o corpo atrás do id e montar a URL na mão. E porque nem toda API devolve o objeto no 201 — algumas devolvem só o Location, e quem consome precisa funcionar nos dois casos.

LAB 4

Complete o CRUD e prove a idempotência

~20 min

Os dois verbos que faltam — e um experimento que mostra por que eles são diferentes do POST.

  1. No repository: trocar(String id, Coisa nova) com lista.set(i, nova), e remover(String id) com lista.removeIf(...), que já devolve boolean.
  2. No service: no trocar, monte a coisa nova com o id que veio da URL, não o do corpo.
  3. No controller: @PutMapping("/{id}") devolvendo 200 ou 404, e @DeleteMapping("/{id}") devolvendo 204 ou 404.
  4. O experimento: mande o mesmo DELETE duas vezes, e depois o mesmo PUT duas vezes. Anote os quatro status.
@DeleteMapping("/{id}")
public ResponseEntity<Void> apagar(@PathVariable String id) {
    return service.apagar(id)
        ? ResponseEntity.noContent().build()
        : ResponseEntity.notFound().build();
}
responda
  1. O DELETE repetido deu 204 e depois 404. Isso quebra a idempotência?
  2. Por que o DELETE devolve 204 e não 200 com o objeto apagado?
  3. Se a internet cair depois de você mandar um POST, dá para repetir com segurança? E um PUT?
conferir depois de responder

1. Não. Idempotência é sobre o estado do servidor, não sobre a resposta: depois de uma ou de dez chamadas, aquele item não existe. As respostas diferem; o resultado, não.

2. Porque não sobrou nada para mostrar. Devolver o objeto que você acabou de apagar sugere que ele ainda está lá — 204 No Content diz exatamente o que aconteceu: fiz, e não tenho corpo para você.

3. POST, não: repetir cria um segundo item. PUT, sim: o estado final é o mesmo. É por isso que sistemas de pagamento gastam tanto esforço tornando a cobrança idempotente — cair a rede no meio não pode virar cobrança dobrada.
