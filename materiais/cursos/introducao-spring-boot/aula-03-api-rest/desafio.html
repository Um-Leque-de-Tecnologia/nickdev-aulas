Uma API que não mente 🚦

Na aula 02 vocês montaram o esqueleto, e ele ficou com um defeito combinado: pedir uma coisa que não existe devolvia 200. Agora a API aprende a responder a verdade — e ganha os verbos que faltavam.

Ainda não leu o briefing?

O briefing do Leque de Vagas explica o projeto inteiro, as quatro frentes e onde isso chega em dezembro. Este desafio é o segundo passo dele.

Agora as quatro partes são diferentes

Na aula 02 as quatro tinham a mesma forma, de propósito: todo mundo precisava escrever o padrão com as próprias mãos. Isso acabou. Cada frente ganha um problema próprio a partir de hoje — e cada uma aprende uma coisa que as outras não vão aprender sozinhas.

Por isso, na entrega, cada pessoa explica a sua. Não dá mais para copiar a do lado e trocar o nome.

Antes de codar — a combinação de 30 minutos
🤝

Duas decisões, e nenhuma delas é código

São as mesmas duas perguntas que qualquer equipe responde ao abrir um endpoint de escrita. Respondam juntos, escrevam no README, e só então abram a IDE.

1

Quais campos o cliente manda no POST — e quais ele não manda

O corpo do POST não é o mesmo objeto que a API devolve. Quem cria uma vaga não escolhe o id dela, e provavelmente não escolhe a data de publicação: quem decide isso é a API.

// o que o cliente MANDA                    o que a API DEVOLVE
{                                         {
  "titulo": "Dev Java Júnior",           "id": "a3f1…",        // ← a API gerou
  "area": "Back-end",                   "titulo": "Dev Java Júnior",
  "senioridade": "Júnior",               "area": "Back-end",
  "empresaSlug": "aurora-tech"            "senioridade": "Júnior",
}                                           "empresaSlug": "aurora-tech"
                                          }

Nesta aula vocês vão usar o mesmo record nos dois lados, aceitando que o id vem null no corpo e é ignorado. Funciona, e é o suficiente hoje. Guardem o incômodo: a aula 04 tem nome para ele — DTO.

2

Quem encosta no VagaController

A parte 4 precisa de uma rota que começa com /vagas, e o VagaController é da parte 1. Duas pessoas no mesmo arquivo, na mesma semana, é conflito de merge na certa.

A saída é a parte 4 criar o próprio controller, mapeado no mesmo caminho base. Spring permite: o que não pode é duas rotas idênticas, e /vagas/busca não é /vagas/{id}.

Combinem também o que a busca recebe. A parte 4 vai chamar o VagaRepository da parte 1 — como já fazia na aula 02 para as estatísticas. Se a parte 1 mudar a assinatura de todas(), avisa antes.

As quatro partes
PARTE 1

Vaga — o CRUD completo

frente 1

A parte mais longa, e a referência das outras. Você implementa os quatro verbos com os quatro status.

  • No VagaRepository: troque List.of(...) por new ArrayList<>(List.of(...)) — a lista de hoje é imutável e não aceita escrita. Acrescente salvar, trocar e remover.
  • No VagaService: buscarPorId passa a devolver Optional<Vaga>. O id é gerado aqui, com UUID.randomUUID().toString() — nunca vem do cliente.
  • No VagaController: os quatro mapeamentos, todos devolvendo ResponseEntity.
rotastatusquando
GET /vagas/{id}200 · 404404 se o id não existe — o conserto da aula 02
POST /vagas201com cabeçalho Location apontando para a vaga criada
PUT /vagas/{id}200 · 404404 se o id não existe
DELETE /vagas/{id}204 · 404204 sem corpo nenhum

A armadilha do PUT: o corpo não traz id — ele veio na URL. Monte a vaga nova com o id do caminho e os campos do corpo. Se deixar o id do corpo passar, ele chega null e você perde o registro em vez de trocá-lo.

PARTE 2

Empresa — quando o id é escolhido por quem cria

frente 2

Sua parte tem uma diferença que a parte 1 não tem: o identificador da empresa é o slug, e ele vem de fora.

  • GET /empresas/{slug} passa a devolver 404 quando não existe, com Optional no service.
  • POST /empresas cria e devolve 201 com Location.
  • DELETE /empresas/{slug} devolve 204 ou 404.
rotastatusquando
GET /empresas/{slug}200 · 404404 se o slug não existe
POST /empresas201Location montado com o slug que veio no corpo
DELETE /empresas/{slug}204 · 404—

Repare na diferença e escreva sobre ela no README. Na parte 1 o Location aponta para um id que a API acabou de inventar. Na sua, ele aponta para um slug que o cliente escolheu. As duas coisas são 201, mas a responsabilidade sobre o endereço mudou de lado — e isso é uma decisão de projeto de API, não um detalhe.

PARTE 3

Pessoa — e a prova de que PUT e DELETE são idempotentes

frente 3

Você implementa o CRUD de Pessoa e produz a evidência de uma propriedade que a aula só falou por cima.

  • GET /pessoas/{id} com 404, POST /pessoas com 201, PUT /pessoas/{id} e DELETE /pessoas/{id}.
  • Um arquivo idempotencia.http na raiz do repositório, versionado, com as chamadas repetidas e o status de cada uma anotado em comentário.
### 1 · cria — repetir CRIA DE NOVO, então POST não é idempotente
POST http://localhost:8080/pessoas
Content-Type: application/json

{ "nome": "Ana", "email": "ana@exemplo.com" }
// 1ª vez: 201 · 2ª vez: 201 e agora existem DUAS Anas

### 2 · troca — repetir dá no mesmo
PUT http://localhost:8080/pessoas/{{id}}
// 1ª vez: 200 · 2ª vez: 200, e o registro está idêntico

### 3 · apaga — repetir não apaga "mais"
DELETE http://localhost:8080/pessoas/{{id}}
// 1ª vez: 204 · 2ª vez: 404, e a lista continua igual

O 404 na segunda chamada não quebra a idempotência. Idempotente é sobre o estado do servidor, não sobre a resposta: depois de uma ou de dez chamadas, aquela pessoa não existe. É essa frase que você precisa saber defender na apresentação.

PARTE 4

Busca — filtrar sem inventar recurso

frente 4

Sua frente estreia o @RequestParam. E, como não tem recurso próprio, estreia também o controller que convive com o de outra pessoa.

  • Um BuscaController seu, com @RestController — não mexa no VagaController da parte 1.
  • Um BuscaService, recebendo o VagaRepository por construtor.
  • Os três filtros opcionais e combináveis. Sem nenhum, devolve tudo.
  • O GET /estatisticas da aula 02 continua funcionando — não o quebre.
rotastatusquando
GET /vagas/busca?area=Dados200as vagas de Dados
GET /vagas/busca?area=Dados&senioridade=Júnior200os dois filtros juntos
GET /vagas/busca?aceitaIniciante=true200só as que aceitam iniciante
GET /vagas/busca200sem filtro: a lista inteira

Busca que não acha nada devolve 200 com lista vazia, e isso está certo — você procurou, e o resultado é zero. É o oposto do /vagas/{id}, onde lista vazia era mentira. Saber explicar essa diferença é a sua parte da aula.

Depois: juntar
5

As quatro partes na mesma main

  • Cada pessoa na sua branch, uma Pull Request por frente.
  • Suba a aplicação e rode o api.http inteiro, de cima a baixo.
  • Confira os status, não só os corpos: é neles que está a entrega de hoje.
  • Chame GET /vagas/busca e GET /vagas/{id} na mesma execução — se o Spring reclamar de rota ambígua, as duas ficaram idênticas em algum ponto.

Depois de juntar, crie uma vaga pelo POST e busque por ela no filtro da parte 4. Se ela aparecer, as quatro partes estão de fato falando com o mesmo repositório — e não cada uma com a sua cópia.
