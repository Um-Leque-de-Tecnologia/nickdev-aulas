Por que existe

O problema: HTML que se repete

Antes de falar de Next.js, vale entender que dor ele resolve. E é uma dor que você provavelmente já sentiu.

Imagine um site em HTML puro, com duas páginas. O cabeçalho é o mesmo nas duas:

<!-- index.html -->
<header>
  <h1>Minha Loja</h1>
  <nav>
    <a href="index.html">Início</a>
    <a href="sobre.html">Sobre</a>
  </nav>
</header>
<main>Bem-vindo!</main>

<!-- sobre.html — o MESMO cabeçalho, copiado -->
<header>
  <h1>Minha Loja</h1>
  <nav>
    <a href="index.html">Início</a>
    <a href="sobre.html">Sobre</a>
  </nav>
</header>
<main>Quem somos</main>

Copiar e colar funciona bem — com duas páginas. O problema aparece na décima.

A conta que não fecha

Agora o cliente pede pra adicionar "Contato" no menu. Seu site tem 12 páginas. Então:

  • Você abre 12 arquivos
  • Faz a mesma edição 12 vezes
  • Esquece uma — e o site fica inconsistente sem ninguém perceber

Repare no absurdo: o cabeçalho é uma coisa só, conceitualmente. Mas está escrito em doze lugares diferentes. É esse descompasso que todo o resto desta aula existe pra resolver.

React e Next: quem faz o quê

Dois nomes vão aparecer o semestre inteiro. Vale saber de quem é cada um — principalmente na hora de pesquisar no Google.

NomeO que éO que traz
React A biblioteca que permite escrever interface em componentes Componente, JSX, e a forma de combinar as peças
Next.js A ferramenta construída em volta do React Endereços, organização de pastas, e publicar no ar

React sozinho não sabe o que é uma página, nem o que é um endereço como /sobre. Ele sabe montar peças de interface — e só. Next.js é o que transforma essas peças num site de verdade.

A analogia. React é o motor. Next.js é o carro montado em volta do motor: direção, portas, placa. Você dirige o carro sem precisar pensar no motor separadamente — mas quando o erro é do motor, ajuda saber que ele tem outro nome.

Na prática, você vai escrever componentes (React) dentro da estrutura de pastas do Next. Sem precisar separar as duas coisas na cabeça.

React essencial

Componente: a peça reutilizável

E se o cabeçalho fosse uma peça? Escrita uma vez, com um nome próprio, e usada em quantas páginas você quiser. Mudou a peça, mudou em todas de uma vez.

Essa peça tem nome: componente.

Guarde esta definição. Um componente é um pedaço de interface com nome próprio, escrito uma vez e reaproveitado onde precisar. É a palavra mais importante do semestre inteiro — tudo que vem depois é variação disso.

A analogia do LEGO

Você não esculpe um castelo de LEGO de um bloco só. Você monta peças pequenas — uma parede, uma janela, uma torre — e depois combina. Se a janela precisar mudar, você muda o molde da janela, não cada castelo.

Uma página em Next.js é isso: um monte de peças combinadas. Cabeçalho, lista de produtos, rodapé. Cada uma escrita separadamente, cada uma com seu nome.

JSX: HTML dentro do JavaScript

Na prática, um componente é uma função JavaScript comum — a mesma que você já sabe escrever. Com duas diferenças: o nome começa com letra maiúscula, e ela devolve HTML.

function Cabecalho() {
  return (
    <header>
      <h1>Minha Loja</h1>
      <nav>
        <a href="/">Início</a>
        <a href="/sobre">Sobre</a>
      </nav>
    </header>
  );
}

Esse HTML escrito dentro do JavaScript tem nome: JSX. Não é uma string, não está entre aspas — é escrito direto, e o Next entende.

Como se usa

Depois de criado, o componente vira uma tag:

<Cabecalho />

Igualzinho a uma tag HTML — só que quem inventou a tag foi você. É por isso que o nome precisa começar com maiúscula: é assim que o Next diferencia <header> (tag do HTML) de <Cabecalho /> (peça sua).

Três detalhes que pegam no começo

No HTML você escreveNo JSX viraPor quê
class="botao"className="botao"class já é palavra reservada do JavaScript
<br><br />toda tag precisa fechar, sem exceção
vários elementos soltostudo dentro de um elementoa função só consegue devolver uma coisa
O erro mais comum da primeira semana. Escrever class em vez de className. O estilo simplesmente não aplica e nenhum erro aparece. Quando o CSS "não funcionar sem motivo", confira isso primeiro.

Props — os parâmetros do componente

Props são os dados que um componente recebe de quem o usa. É exatamente a mesma ideia dos parâmetros de função da aula 02.

// definindo
function Selo({ texto, cor }) {
  return <span style={{ color: cor }}>{texto}</span>;
}

// usando (parece uma tag HTML sua)
<Selo texto="Remoto" cor="#A98CE0" />
<Selo texto="Júnior" cor="#F24487" />

Texto vai entre aspas; qualquer outra coisa (número, objeto, array, função, variável) vai entre chaves:

<VagaCard vaga={vaga} destaque={true} posicao={1} />

Com TypeScript

function Selo({ texto, cor }: { texto: string; cor: string }) {
  return <span style={{ color: cor }}>{texto}</span>;
}
Vale o esforço: com os tipos escritos, o VS Code passa a completar os nomes pra você e avisa na hora quando você digita vaga.titlo.

children — o conteúdo entre as tags

function Caixa({ children }) {
  return <div className="caixa">{children}</div>;
}

<Caixa><p>isto aqui vira o children</p></Caixa>

É exatamente assim que o layout.tsx funciona. 😉

Listas e keys

O .map() da aula 02 continua sendo a ferramenta — só que agora ele devolve componentes:

<div className={estilos.grade}>
  {vagas.map((vaga) => (
    <VagaCard key={vaga.slug} vaga={vaga} />
  ))}
</div>
A key é obrigatória. Ela é o "RG" de cada item: é como o React sabe qual card é qual quando a lista muda de ordem ou tamanho. Use algo único e estável — o slug, o id. Evite o índice do array quando a lista puder ser reordenada ou filtrada.

Lista vazia

{vagas.length === 0 ? (
  <p>Nenhuma vaga com esses filtros 😔</p>
) : (
  vagas.map((v) => <VagaCard key={v.slug} vaga={v} />)
)}

Nunca esqueça deste caso — é o que separa um projeto de estudo de um projeto que parece profissional.

useState e estado derivado

Estado é a memória do componente: um dado que, quando muda, faz a tela se redesenhar sozinha.

const [busca, setBusca] = useState("");
//      ↑       ↑                  ↑
//  o valor  como mudar     o valor inicial
  • busca — o dado agora. Você lê, nunca escreve direto
  • setBusca(novo) — troca o dado e redesenha a tela
  • busca = "x" — ❌ nunca. O React não fica sabendo
O erro que todo mundo comete uma vez: mudar a variável na mão e ficar quinze minutos procurando por que a tela não atualizou. Se não passou pelo setAlgumaCoisa, o React não redesenha.

⭐ Estado derivado — a regra que evita metade dos bugs

Se dá pra calcular a partir do que você já tem, não guarde em estado.

❌ dois estados que precisam combinar

const [busca, setBusca] = useState("");
const [lista, setLista] = useState(vagas);

// e agora, em TODO lugar que mexe na
// busca, você tem que lembrar de
// atualizar a lista também. Um dia
// você esquece — e a tela mente.

✅ um estado, o resto é conta

const [busca, setBusca] = useState("");

// recalculado a cada renderização,
// sempre coerente com a busca
const visiveis = filtrarVagas(vagas, { busca });

Dois estados que precisam "combinar" um com o outro são uma dupla que um dia vai brigar. Guarde o mínimo; derive o resto.

Componente controlado

No projeto, o MuralDeVagas guarda o estado e o Filtros só recebe valores e funções:

<Filtros
  busca={busca}
  aoMudarBusca={setBusca}
/>

O Filtros não guarda nada — ele avisa quem manda. Isso deixa ele simples de entender, fácil de reaproveitar e sem duas versões da verdade na aplicação.

useEffect: pra depois que a tela apareceu

useEffect(() => {
  // só roda no navegador, depois de renderizar
  setSalva(lerDoLocalStorage(slug));
}, [slug]);   ← roda de novo quando slug mudar
Por que não ler localStorage direto no corpo do componente? Porque o servidor não tem localStorage. O HTML do servidor sairia diferente do que o navegador desenha, e o React reclama: "hydration mismatch". Leia sempre dentro do useEffect.

A regra do App Router

Pasta = rota. Arquivo page.tsx = a página. Não existe arquivo de configuração de rotas.

Você criaURL que nasce
app/page.tsx/
app/sobre/page.tsx/sobre
app/contato/page.tsx/contato
app/blog/posts/page.tsx/blog/posts
Pegadinha nº 1: criar app/sobre.tsx em vez de app/sobre/page.tsx. Sem o arquivo chamado exatamente page.tsx dentro da pasta, a rota não existe — e você toma 404 sem nenhum erro no terminal.

App Router

Rotas por pasta

A regra do App Router cabe numa frase: pasta = rota, arquivo page.tsx = a página. Não existe arquivo de configuração de rotas.

Você criaURL que nasce
app/page.tsx/
app/sobre/page.tsx/sobre
app/vagas/page.tsx/vagas
app/vagas/[slug]/page.tsx/vagas/qualquer-coisa
Pegadinha nº 1 da aula: criar app/sobre.tsx em vez de app/sobre/page.tsx. Sem o arquivo chamado exatamente page.tsx dentro da pasta, a rota não existe e você toma 404.

Os arquivos com nome reservado

ArquivoO que faz
page.tsxa página. Só ela cria a rota.
layout.tsxmoldura ao redor da página e de tudo abaixo dela
error.tsxaparece se algo quebrar (precisa de "use client")
not-found.tsxseu 404
loading.tsx (aula 04)aparece automaticamente enquanto a página espera dados de fora. Enquanto as vagas moram num arquivo do projeto, não há o que esperar.

Pastas que NÃO viram rota (grupos de rotas)

Uma pasta entre parênteses serve só pra organizar — ela não entra na URL. É o que o projeto usa nas telas de conta:

app/(conta)/layout.tsx           ← layout só destas telas
app/(conta)/entrar/page.tsx      → /entrar   (e não /conta/entrar)
app/(conta)/cadastro/page.tsx    → /cadastro

Assim /entrar e /cadastro compartilham aquele cartão centralizado, sem que a URL fique mais comprida por causa disso. E os layouts se aninham: o cabeçalho e o rodapé do layout raiz continuam aparecendo por fora.

layout e page

Aqui a promessa do começo do guia é paga. Lembra do cabeçalho copiado em doze arquivos? O layout.tsx é onde ele passa a existir uma vez só.

📄 app/layout.tsx
export default function RootLayout({ children }) {
  return (
    <html lang="pt-BR">
      <body>
        <header>Minha Loja</header>   {/* ← escrito UMA vez */}

        {children}                       {/* ← cada página entra aqui */}

        <footer>© 2026</footer>      {/* ← e o rodapé também */}
      </body>
    </html>
  );
}
  • O que está no layout aparece em todas as páginas do site
  • Mudou o menu aqui? Mudou no site inteiro, de uma vez
  • O layout raiz é obrigatório e é o único lugar com <html> e <body>
  • children é o buraco onde a página da vez é encaixada
Por que "children". É a palavra que o React usa pra dizer "o conteúdo que vem de dentro". Você não precisa entender o mecanismo hoje — só saber que é ali que a página entra.
📄 app/page.tsx
export default function Home() {
  return (
    <main>
      <h1>Bem-vindo à Minha Loja</h1>
    </main>
  );
}

Uma função com nome, que devolve HTML. É um componente — o mesmo conceito das seções anteriores. O export default na frente é o que diz ao Next: "esta é a página desta pasta".

Layouts aninhados

Na aula 01, o layout.tsx era um só, na raiz, com o cabeçalho do site. Agora vem a parte boa: cada pasta pode ter o seu, e eles se encaixam um dentro do outro.

app/
├── layout.tsx          cabeçalho e rodapé do site
├── page.tsx             /
└── vagas/
    ├── layout.tsx      título e filtros da área de vagas
    ├── page.tsx         /vagas
    └── [id]/
        └── page.tsx     /vagas/12

Ao abrir /vagas/12, a tela é montada assim, de fora pra dentro:

┌─ layout da raiz ──────────────────────┐
│  cabeçalho do site                    │
│  ┌─ layout de vagas ────────────────┐ │
│  │  filtros                         │ │
│  │  ┌─ page de [id] ──────────────┐ │ │
│  │  │  os dados da vaga 12        │ │ │
│  │  └─────────────────────────────┘ │ │
│  └──────────────────────────────────┘ │
│  rodapé                               │
└───────────────────────────────────────┘

  );
}
Só o layout da raiz tem <html> e <body>. Os layouts de dentro devolvem só um pedaço — uma <div>, uma <section>. Se você escrever <html> num layout aninhado, quebra.

A parte que responde o gancho da aula passada

Ao navegar de /vagas/12 pra /vagas/13, os dois layouts não são remontados. Eles continuam ali, do jeito que estavam — só o miolo troca.

É por isso que a navegação não pisca: o Next não joga a página fora e monta outra. Ele substitui só a parte que mudou. Se você tivesse um campo de busca digitado no layout, o texto continuaria lá.

layout × template

O template.tsx faz a mesma coisa que o layout — envolve a página — com uma diferença única:

layout.tsx

Sobrevive à navegação. Vai de /vagas/12 pra /vagas/13 e ele continua o mesmo, sem remontar.

É o que você quer em 99% dos casos.

template.tsx

Remonta do zero a cada navegação. Toda troca de página, ele nasce de novo.

Útil quando você quer uma animação de entrada repetindo a cada página, por exemplo.

Na dúvida, use layout. Sério. O template está aqui pra você saber que existe e não se assustar ao ver num projeto alheio. Se os dois existirem na mesma pasta, o template fica dentro do layout.

O problema: 200 vagas

Imagine o Leque de Vagas com duzentas vagas cadastradas. Cada uma precisa da sua página, com seu endereço próprio — porque a pessoa vai querer mandar o link daquela vaga específica pra alguém.

Com o que você sabe até agora, a única saída seria:

Duzentas pastas. Duzentos arquivos praticamente idênticos — muda só o texto dentro. E quando a empresa publicar uma vaga nova amanhã, alguém tem que criar a pasta na mão e publicar de novo.

É a mesma dor da aula 01, em escala maior. Lá era o cabeçalho copiado em doze páginas. Aqui é a página inteira copiada em duzentas. A solução também segue o mesmo espírito: escrever uma vez o que é um só.

A pasta entre colchetes

A resposta do Next é uma pasta cujo nome é um espaço em branco. Você escreve o nome entre colchetes, e ele passa a aceitar qualquer coisa naquele lugar do endereço.

app/
└── vagas/
    └── [id]/page.tsx     ← atende /vagas/qualquer-coisa

Uma pasta. Um arquivo. Infinitas páginas. O que muda de uma pra outra é só o pedacinho que veio no endereço.

O nome dentro dos colchetes é escolha sua. [id], [slug], [vaga] — tanto faz. Ele vira o nome da chave que você vai ler lá dentro. Escolha um que descreva o que aquele pedaço da URL significa.
O que chega é sempre texto. Mesmo acessando /vagas/12, o id vale "12" — com aspas, como texto. Se você for comparar com um número, converta: Number(id). Essa é a fonte de uns bons vinte minutos de confusão na primeira vez.

params e o await

A página recebe uma caixinha chamada params com o que veio na URL. Assim:

📄 app/vagas/[id]/page.tsx
export default async function PaginaDaVaga({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;

  return <h1>Vaga {id}</h1>;
}

São três coisas acontecendo, e vale separar cada uma:

  1. { params } — a página recebe a caixinha
  2. await params — espera a caixinha ficar pronta
  3. const { id } = — tira de dentro dela a chave id

Por que esse await?

Porque no Next 16 o params não chega pronto: ele chega como um vale — uma promessa de que o valor vem num instante. O await é o que troca o vale pelo valor.

Não precisa entender o motivo hoje. O porquê tem a ver com como o Next prepara a página antes de mandar pro navegador, e isso é assunto da aula 04. Por enquanto vale a receita: params sempre com await, e a função sempre com async.
O sintoma de esquecer o await. Ou o Next reclama no terminal, ou aparece [object Promise] na tela em vez do valor. Quando ver isso, procure um await faltando — é quase sempre isso.

As chaves em volta de params não são enfeite

Este é o erro que mais aparece, e o mais difícil de achar sozinho. Repare nos dois:

// ERRADO — sem as chaves
export default async function PaginaDaVaga(params: Promise<{ id: string }>) {
  const { id } = await params;   id fica undefined

// CERTO — com as chaves
export default async function PaginaDaVaga({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;   "12"

O Next não entrega a caixinha na sua mão. Ele entrega uma sacola com a caixinha dentro — mais ou menos assim:

{ params: Promise<{ id }>, searchParams: Promise<{ … }> }

As chaves em { params } são o que diz "tire o params de dentro da sacola". Sem elas, você só deu o apelido params pra sacola inteira — e a sacola não tem nenhum id dentro. O resultado é undefined.

Por que ele é traiçoeiro. O React simplesmente não escreve nada quando o valor é undefined. Então não há erro vermelho, não há aviso no terminal, e o npm run build passa normalmente. Você só vê "Vaga" sozinho na tela, sem o número.

A regra: sumiu o valor e o terminal está limpo? Olhe as chaves antes de olhar o await. O [object Promise] é o sintoma do await faltando; o buraco calado é o sintoma das chaves faltando.

Um jeito mais curto de escrever o tipo

Escrever Promise<{ id: string }> à mão funciona, mas o Next 16 já sabe quais são os pedaços de cada rota. Dá pra pedir pra ele:

export default async function Page(props: PageProps<"/vagas/[id]">) {
  const { id } = await props.params;
  return <h1>Vaga {id}</h1>;
}

Não precisa importar nada: PageProps já existe sozinho. As duas formas estão certas — use a que você entender melhor. No desafio, qualquer uma serve.

Uma vantagem concreta desta forma. Aqui não existe chave pra esquecer: você escreve props.params e pronto. E se errar mesmo assim, o editor sublinha na hora, com o nome do problema: Property 'id' does not exist on type PageProps<"/vagas/[id]">. Na forma escrita à mão, o mesmo erro passa calado. Se você é do tipo que prefere o computador avisando, fique com esta.

E o que vem depois do ? na URL

Endereços como /vagas?area=dados têm uma segunda caixinha, chamada searchParams. Funciona igual, inclusive no await:

export default async function Vagas({ searchParams }) {
  const { area } = await searchParams;   "dados"
}
A diferença entre as duas. params é o que está no caminho (/vagas/12); searchParams é o que vem depois do ? (/vagas?area=dados). Filtro e busca usam a segunda — e isso volta com força na aula de listagem.

Catch-all: [...slug]

O [id] pega um pedaço do endereço. Às vezes você não sabe quantos vêm — em documentação, por exemplo, onde as categorias podem ter três ou cinco níveis.

PastaPegaNão pegaO que chega

[...slug]/docs/a, /docs/a/b/c/docslista
[[...slug]]/docs e tudo abaixo—lista (às vezes vazia)
// app/docs/[...slug]/page.tsx acessado em /docs/guia/rotas
const { slug } = await params;   ["guia", "rotas"]
Provavelmente você não vai usar isto no projeto. Está aqui porque é uma das quatro formas de rota que existem, e porque quando você ler o código de outra pessoa vai esbarrar nela. Reconhecer já basta.

loading.tsx

Toda página leva um tempinho pra ficar pronta — às vezes milissegundos, às vezes segundos, se tiver que buscar dados. O loading.tsx é o que aparece nesse intervalo.

📄 app/vagas/loading.tsx
export default function Loading() {
  return <p>Carregando vagas…</p>;
}

Pronto. Não precisa importar nem ligar em lugar nenhum — o Next encontra sozinho e usa quando a página daquela pasta estiver se preparando.

  • O layout continua na tela — cabeçalho, filtros, tudo. Só o miolo mostra o "carregando"
  • Ele vale pra pasta onde está e as de dentro
  • Dá pra ter vários: um em app/vagas/, outro em app/vagas/[id]/, cada um com sua mensagem
Melhor que "Carregando…": um esqueleto. Em vez de texto, desenhe caixinhas cinzas no formato do conteúdo que vai chegar. A pessoa já entende o que está vindo, e a troca fica bem menos brusca. É CSS comum — algumas div com fundo cinza e altura fixa.
Você pode não ver o loading no seu projeto hoje. Se a página fica pronta em 5 milissegundos, ele pisca e some. Pra testar de verdade, o código de referência da aula tem um truque: uma função que segura a página por dois segundos de propósito.

error.tsx

Quando alguma coisa quebra dentro de uma rota, sem esse arquivo a pessoa vê uma tela de erro feia — ou, em produção, uma tela genérica. Com ele, vê uma tela sua, e o resto do site continua de pé.

📄 app/vagas/error.tsx
"use client";   // ← obrigatório neste arquivo

export default function Error({
  error,
  retry,
}: {
  error: Error & { digest?: string };
  retry: () => void;
}) {
  return (
    <div>
      <h2>Algo deu errado ao carregar as vagas</h2>
      <button onClick={() => retry()}>Tentar de novo</button>
    </div>

O que chega pra ele

Sobre o "use client". Essa linha diz "este arquivo também roda no navegador da pessoa". Ela é obrigatória no error.tsx — sem ela, o Next reclama. Por que isso é necessário é exatamente o assunto da aula 03. Hoje: escreva a linha e siga.
O erro do layout escapa daqui. Um error.tsx não pega erros do layout.tsx da mesma pasta — porque o layout está por fora dele. Quem pega é o error da pasta de cima. Veja o desenho na próxima seção.
Você vai ver reset por aí. Era o nome antigo. A partir do Next 16.3 o recomendado é retry, que além de limpar o erro busca os dados de novo. Se a IA te devolver reset, não está errado — está velho.

not-found.tsx

Rota dinâmica aceita qualquer coisa no lugar do [id] — inclusive /vagas/banana. Alguém vai digitar isso, ou clicar num link antigo de uma vaga que já saiu do ar. O que aparece nessa hora é você quem decide.

Passo 1 — avise que não achou

📄 app/vagas/[id]/page.tsx
import { notFound } from "next/navigation";

export default async function PaginaDaVaga({ params }) {
  const { id } = await params;
  const vaga = vagas.find((v) => v.id === id);

  if (!vaga) {
    notFound();   // ← para tudo aqui e mostra o not-found

}

Passo 2 — escreva a tela

Sempre ofereça um caminho de volta. Um 404 sem link é um beco sem saída. Um 404 com "ver todas as vagas" transforma um erro em mais uma chance de a pessoa encontrar o que queria.

O not-found da raiz é especial

O arquivo app/not-found.tsx faz duas coisas: atende o notFound() chamado na raiz e vira a tela de qualquer endereço que não bate com rota nenhuma do site. Digitou /pagina-que-nao-existe? É ele que aparece.

Todo projeto deveria ter um. Sem app/not-found.tsx, o visitante que erra o endereço vê a tela padrão do Next — cinza, em inglês, sem o seu cabeçalho e sem saída. São dez linhas pra resolver.

A ordem das camadas

Os arquivos especiais se envolvem numa ordem fixa. Vale guardar este desenho — ele explica vários comportamentos que parecem estranhos.

<layout>                    a moldura
  <error>                  pega o que quebrar aqui dentro
    <loading>              enquanto o miolo não vem
      <not-found>
        <page />           o conteúdo
      </not-found>
    </loading>
  </error>
</layout>

Duas consequências práticas que caem em prova de vida real:

  • O layout está por fora do error. Então um erro dentro do layout.tsx não é pego pelo error.tsx da mesma pasta — quem pega é o da pasta de cima. E um erro no layout raiz só é pego por um global-error.tsx.
  • O error está por fora do loading. Então se a página quebrar enquanto carregava, o "carregando" é substituído pela tela de erro — não fica um em cima do outro.

Paralelas e interceptadas

Existem mais duas formas de rota no App Router. Nenhuma das duas cai no desafio — estão aqui pra você reconhecer o nome quando esbarrar.

Rotas paralelas — @pasta

Duas telas no mesmo endereço, cada uma navegando por conta própria. Pense num painel dividido: a metade de cima e a de baixo mudam sem uma esperar a outra.

app/painel/
├── layout.tsx        recebe as duas metades como props
├── @vagas/page.tsx
└── @candidaturas/page.tsx

Rotas interceptadas — (.)pasta

Aquele comportamento do Instagram: você clica numa foto do feed e ela abre num modal por cima, mas a URL muda como se fosse página cheia. Se você recarregar ou mandar o link pra alguém, aí sim vem a página cheia.

Por que estou mostrando. Porque essas duas resolvem problemas que a gente normalmente resolve com gambiarra — e porque, quando você ler que "Next tem rotas interceptadas", vai saber que é aquele modal, não algo mágico e inalcançável.
Navegação

Link e prefetch

Na aula 01 ficou a regra: use <Link>, não <a>. Agora o porquê completo.

Com <a href>

O navegador joga fora a página inteira e baixa tudo de novo: HTML, CSS, JavaScript. Tela branca no meio, cabeçalho remontado, rolagem perdida.

Com <Link>

O Next troca só o pedaço que mudou. Os layouts continuam de pé. E, antes do clique, ele já foi buscar a página de destino em segundo plano.

import Link from "next/link";

// link fixo
<Link href="/vagas">Ver vagas</Link>

// link montado a partir de um dado
<Link href={`/vagas/${vaga.id}`}>{vaga.titulo}</Link>
Aquelas crases são propositais. Em JavaScript, `texto ${variavel}` é um texto com um buraco preenchido na hora. É como você monta endereços que dependem de um dado.

Prefetch: o adiantamento

Quando um <Link> aparece na tela, o Next já começa a buscar a página de destino em segundo plano. Quando a pessoa clica, boa parte do trabalho já está feita — por isso parece instantâneo.

Prefetch só acontece no site publicado. Em npm run dev ele fica desligado de propósito. Se a navegação parecer lenta na sua máquina e instantânea na Vercel, está tudo certo — é exatamente esse o motivo.

Três props que vale conhecer

PropO que faz
replaceNavega sem deixar rastro no histórico. O botão voltar pula essa página. Útil depois de um login.
scroll={false}Não mexe na posição da rolagem ao trocar de página.
prefetch={false}Desliga o adiantamento naquele link. Use em listas gigantes, onde adiantar tudo seria desperdício.
E o <a>, morreu? Não. Ele continua certo pra links que saem do seu site: LinkedIn, GitHub, o site da empresa que publicou a vaga. A regra é: dentro do seu site, Link; pra fora, <a>.

Link ativo com usePathname

Todo menu decente marca em que página a pessoa está. Pra isso você precisa saber qual é o endereço atual — e quem sabe disso é o navegador.

📄 components/MenuLink.tsx
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";

export default function MenuLink({
  href,
  children,
}: {
  href: string;
  children: React.ReactNode;
}) {
  const caminho = usePathname();   "/vagas", por exemplo
  const ativo = caminho === href;

  return (
    <Link href={href} className={ativo ? "menu-link ativo" : "menu-link"}>
      {children}
    </Link>
  );
}

E o CSS, comum, no globals.css:

.menu-link { color: #a1a1aa; }
.menu-link.ativo { color: #fafafa; font-weight: 600; }
Por que este arquivo precisa de "use client". Saber em que endereço a pessoa está só é possível no navegador dela — e por padrão os arquivos do Next rodam antes disso, no servidor. A linha é o que autoriza este a rodar também no navegador. A aula 03 explica isso inteiro; por hoje, a regra prática é: usou algo que começa com use, escreva "use client" no topo.
O detalhe que pega todo mundo. Com caminho === href, o link "Vagas" acende em /vagas mas apaga em /vagas/12. Se você quiser que ele fique aceso na seção inteira, use caminho.startsWith(href) — mas cuidado: o link da home ("/") aí acende em tudo. Trate a home à parte.

useRouter

Às vezes não existe link pra clicar: a navegação precisa acontecer depois de alguma coisa — enviar um formulário, fechar um modal, clicar num botão "voltar". Pra isso existe o useRouter.

📄 components/BotaoVoltar.tsx
"use client";

import { useRouter } from "next/navigation";

export default function BotaoVoltar() {
  const router = useRouter();

  return (
    <button onClick={() => router.back()}>
      ← Voltar
    </button>
  );
}
MétodoO que faz
router.push("/vagas")Vai pra lá e guarda no histórico — o botão voltar do navegador funciona.
router.replace("/vagas")Vai pra lá apagando a página anterior do histórico. Depois de um login, pra ninguém "voltar" pro formulário.

Vem de next/navigation. Sempre. Existe um useRouter antigo em next/router, do Next de antigamente. Se você importar dele, quebra — e a mensagem de erro não é nada óbvia. É um dos erros mais comuns de quem segue tutorial velho.
A regra de ouro. Se dá pra usar <Link>, use <Link>. Ele funciona sem JavaScript, o navegador entende, dá pra abrir em nova aba com o botão do meio, e tem prefetch. O useRouter é pro que sobra.
Servidor e cliente

Componentes de Servidor

Este é o conceito mais importante da aula. No App Router, todo componente é de servidor por padrão.

Isso significa que o código dele roda no servidor, monta o HTML, e o navegador recebe a página já pronta. O componente em si não vira JavaScript enviado pro navegador.

Você ganhaNa prática
Página levemenos JavaScript pra baixar = abre rápido no 4G
SEOo Google lê o conteúdo já no HTML
Segurançachave de API e senha de banco ficam no servidor
Buscar dados sem enrolaçãoquando os dados vierem de fora (aula 04), basta await — sem useEffect, sem estado de "carregando" na mão

O que ele NÃO pode fazer

  • useState, useEffect e outros hooks
  • onClick, onChange e outros eventos
  • window, document, localStorage

Pra isso existe o Componente de Cliente. 👇

Componentes de Cliente — "use client"

Quando o componente precisa reagir a quem usa, ele também precisa rodar no navegador. Você marca isso com uma linha:

📄 components/SalvarButton.tsx
"use client";   ← tem que ser a PRIMEIRA linha do arquivo

import { useState } from "react";

export default function SalvarButton() {
  const [salva, setSalva] = useState(false);

  return (
    <button onClick={() => setSalva(!salva)}>
      {salva ? "★" : "☆"}
    </button>
  );
}

useState em 30 segundos

const [valor, setValor] = useState(inicial);
  • valor — o dado atual
  • setValor(novo) — troca o dado e redesenha a tela
  • Nunca faça valor = novo na mão: o React não fica sabendo

useEffect: pra depois que a tela apareceu

useEffect(() => {
  // só roda no navegador, depois de renderizar
  setSalva(lerDoLocalStorage(slug));
}, [slug]);   ← roda de novo quando slug mudar
Por que não ler localStorage direto no corpo do componente? Porque o servidor não tem localStorage. O HTML do servidor sairia diferente do que o navegador desenha, e o React reclama: "hydration mismatch". Leia sempre dentro do useEffect.

Quando precisa de "use client"

Preciso de…Qual componente
Buscar dados, ler banco, usar chave secretaServidor (padrão)
Só mostrar conteúdoServidor (padrão)
useState, useEffectCliente

A fronteira: empurre o "use client" pra baixo

Este é o erro mais comum de quem está começando: colocar "use client" no topo da página. Aí tudo dentro dela vira cliente, e você perde as vantagens do servidor.

❌ "use client" na página

A página, a lista, os 9 cards — tudo vira JavaScript baixado pelo navegador. 
"use client";
export default function Pagina() {
  ...9 cards...
}

✅ "use client" só no botão

A página e os cards continuam no servidor. Só a estrela vai pro navegador. 
// SalvarButton.tsx
"use client";

A diretiva contamina pra baixo

Esta é a parte que confunde: tudo que um componente de cliente importa também vira cliente, mesmo sem ter a linha. No Leque de Vagas, o Filtros.tsx não tem "use client" — e mesmo assim roda no navegador, porque quem importa ele é o MuralDeVagas.

Por isso a diretiva vai na fronteira: no componente mais alto que realmente precisa de estado. Daí pra baixo, é automático.

Quem é cliente no nosso projeto

ArquivoPor quê
SalvarButton.tsxtem useState e onClick
MuralDeVagas.tsxguarda a busca e os filtros
FormEntrar.tsx / FormCadastro.tsxformulários com estado
error.tsxtem o botão "tentar de novo"
Filtros.tsx, CampoTexto.tsxpor contágio — não têm a diretiva

Todo o resto — páginas, layouts, Cabecalho, Rodape, VagaCard — é servidor.

Regras da fronteira

  • Um componente de cliente não pode importar um de servidor diretamente
  • Mas ele pode receber um de servidor como children ou prop
  • Props que atravessam a fronteira precisam ser "serializáveis": texto, número, array, objeto simples
  • De cliente pra cliente, função atravessa normalmente — é assim que o MuralDeVagas passa o aoMudarBusca pro Filtros
Custo honesto: filtrar no cliente obriga a lista inteira de vagas a viajar pro navegador. Funciona bem com 9 vagas — e é o que a gente sabe fazer hoje. Na aula 06 o filtro sai do estado e vai pra URL, com searchParams, e esse custo some.

Formulários controlados

É aqui que quase todo mundo trava — e é o pedaço de interface que mais aparece em teste técnico de vaga júnior. Vale dominar.

A ideia: o valor vem do estado

const [email, setEmail] = useState("");

<input
  value={email}
  onChange={(evento) => setEmail(evento.target.value)}
/>

O ciclo é: você digita → o onChange dispara → o estado muda → o React redesenha → o input mostra o valor novo. Parece uma volta desnecessária, mas é o que te dá controle: dá pra validar, formatar e desabilitar o botão a cada tecla.

Campo travado? Você colocou value={email} e esqueceu do onChange. Aí você digita e nada aparece: o valor está preso num estado que ninguém atualiza. É o bug nº 1 de formulário em React.

Enviar sem recarregar a página

function enviar(evento) {

Uma função que devolve os erros

function validar() {
  const novos = {};

  if (!email.trim()) {
    novos.email = "Escreva seu e-mail.";
  } else if (!email.includes("@")) {

  if (senha.length < 6) {

Deploy na Vercel

Deploy é colocar o site no ar — tirar o projeto da sua máquina e botar num computador que fica ligado o tempo todo, pra qualquer pessoa conseguir abrir.

Até agora o seu site só existe em localhost:3000, e "localhost" quer dizer "aqui mesmo": só você enxerga. Vamos mudar isso hoje, na aula 1, antes de escrever a segunda linha de código. Não é enfeite — é o que transforma "na minha máquina funciona" num link que você manda pra qualquer pessoa.

O caminho, passo a passo

  1. Rode npm run build no seu computador. Esse comando empacota o projeto no formato final. Se ele reclamar de alguma coisa, conserte antes de continuar — é o mesmo comando que a Vercel vai rodar
  2. Mande o projeto pro GitHub (é onde o código fica guardado na internet). O repositório precisa ser público
  3. Entre em vercel.com e faça login com a sua conta do GitHub
  4. Clique em Add New… → Project e escolha o repositório que você acabou de subir
  5. Não mexa em configuração nenhuma. A Vercel reconhece que é um projeto Next sozinha
  6. Clique em Deploy e espere. Em um ou dois minutos ela te devolve um link
Abra o link no celular. Sério, faça isso. É o momento em que deixa de ser exercício e vira um site de verdade — e essa sensação é metade do motivo da gente publicar já na primeira aula.

E depois?

A partir daqui você não publica mais nada na mão. Toda vez que você mandar código novo pro GitHub, a Vercel percebe sozinha e atualiza o site em um ou dois minutos. Você programa, manda, e pronto.

Mais pra frente, quando vocês estiverem trabalhando em equipe, ela ainda vai gerar um link separado pra cada mudança em teste — assim dá pra ver como ficou antes de mexer no site de verdade. Isso é assunto da aula de deploy, mas já vale saber que existe.

Rode npm run build antes de mandar pro GitHub. É exatamente o mesmo comando que a Vercel vai rodar. Se ele reclamar aqui, ia reclamar lá também — e é bem mais rápido descobrir no seu computador do que esperar o site falhar.

Erros comuns 🔧

404 numa página que acabei de criar

O arquivo precisa se chamar exatamente page.tsx, dentro de uma pasta. app/sobre.tsx não vira rota.

Port 3000 is already in use

Tem outra execução rodando. Pare a anterior, ou use npm run dev -p 3001.

O CSS não aplica e nenhum erro aparece

Quase sempre é class escrito no lugar de className. No JSX o atributo tem outro nome.

Adjacent JSX elements must be wrapped…

Você devolveu dois elementos soltos. Envolva tudo num só — <main>, <div>, ou <>…</> se não quiser criar uma tag de verdade.

Unexpected token / erro estranho no JSX

Confira se toda tag fechou. No JSX <br> e <img> precisam virar <br /> e <img />.

Module not found: Can't resolve '@/components/…'

Confira a maiúscula no nome do arquivo. No Windows funciona botao quando o arquivo é Botao; no servidor da Vercel (Linux) não. É um erro que só aparece no deploy.

O build passa local e falha na Vercel

Quase sempre uma destas três: diferença de maiúscula em import, variável de ambiente que existe só na sua máquina, ou versão de Node diferente.

Disco cheio

node_modules de um projeto Next passa de 500 MB. Com vários projetos, o disco enche rápido — e o sintoma costuma ser um erro que não fala nada de disco. Se algo parar de funcionar sem explicação, confira o espaço livre antes de qualquer outra hipótese.

Erros comuns 🔧

Apareceu [object Promise] na tela

Faltou await antes de params. E confira se a função tem async na frente — os dois andam em par.

A página abre, mas o valor não aparece

Aparece "Vaga" e o número some, sem nenhum erro no terminal. Quase sempre são as chaves: é ({ params }: { params: … }), e não (params: …). Sem as chaves, params vira a sacola inteira de props e o id sai undefined — e undefined o React não escreve na tela. Detalhe cruel: o npm run build passa mesmo assim.

404 na rota dinâmica que acabei de criar

Confira se a pasta está com colchetes de verdade: [id], não (id) nem id. E se o arquivo dentro dela se chama exatamente page.tsx.

O route group virou parte da URL

Você usou colchetes em vez de parênteses. (institucional) some da URL; [institucional] vira um pedaço dinâmico do endereço.

You're importing a component that needs useRouter…

Faltou "use client" na primeira linha do arquivo — antes de qualquer import. Vale pra usePathname, useRouter e para o error.tsx.

NextRouter was not mounted

Você importou o useRouter de next/router. No App Router é next/navigation.

O loading.tsx nunca aparece

Sua página fica pronta rápido demais — o que é ótimo. Pra testar, segure a página de propósito por dois segundos; o código de referência da aula mostra como.

O error.tsx não pegou o erro

Se o erro aconteceu no layout.tsx da mesma pasta, ele escapa — o layout fica por fora. Ponha um error.tsx na pasta de cima.

A comparação com o id nunca dá certo

O que vem da URL é sempre texto. Se os seus dados guardam o id como número, "12" === 12 dá falso. Converta com Number(id), ou guarde os ids como texto desde o começo.

Build falha com "duplicate page" ou rota repetida

Dois arquivos querem o mesmo endereço — quase sempre por causa de route groups. Lembre que os parênteses somem da URL.

Funciona no dev, quebra na Vercel

Continua sendo o suspeito nº 1 da aula 01: maiúscula em nome de arquivo. Windows perdoa, o servidor da Vercel (Linux) não.
