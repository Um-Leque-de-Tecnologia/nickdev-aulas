Guia de GitHub 🌿

A referência de Git e GitHub da NickDev — organizada por assunto, não por aula. Serve pra quem nunca abriu o curso e precisa achar em trinta segundos como desfazer o último commit, e serve pra quem fez o curso inteiro e voltou meses depois. Cada seção se sustenta sozinha; quando o assunto é ensinado a fundo em alguma aula, o guia diz qual.

Como usar: a barra da esquerda é o índice. Com pressa? Vá direto pra tabela de emergência (sintoma → comando), pra cola de comandos ou pra tabela de erros comuns. Todo bloco de código tem botão de copiar no canto — passe o mouse.
Começar

01Git × GitHub

O mal-entendido que atrapalha tudo o que vem depois. São duas coisas diferentes, de donos diferentes, e uma funciona sem a outra.

Pense num caderno de receitas. O Git é o método de anotar: cada alteração ganha data, autor e um bilhete dizendo o que mudou, e você pode voltar em qualquer página antiga. O GitHub é a estante da praça onde você deixa uma cópia do caderno pra todo mundo ler, comentar e sugerir receita nova.

Git
Um programa que roda na sua máquina. Criado em 2005 pelo Linus Torvalds. Grava versões do seu projeto numa pasta escondida chamada .git. Funciona sem internet, sem conta, sem nada. É software livre.
GitHub
Um site (da Microsoft desde 2018) que hospeda repositórios Git e acrescenta o que o Git não tem: página do projeto, issues, Pull Requests, revisão de código, automação, controle de acesso.
Alternativas
GitLab, Bitbucket, Codeberg, Gitea. Todas falam o mesmo Git — o que muda é a camada social por cima. O que você aprende de Git aqui vale em qualquer uma delas.
PerguntaGitGitHub
Onde rodaNa sua máquinaNum servidor, acessado pelo navegador
Precisa de internetNãoSim
Precisa de contaNãoSim
Quem fezLinus Torvalds, 2005Chris Wanstrath e sócios, 2008
Você usa porComando (git ...)Telas — e também por gh no terminal

Consequência prática: dá pra usar Git a semana inteira sem abrir o GitHub. E dá pra ter conta no GitHub sem entender Git — só que aí você trava no primeiro push rejeitado. Aprenda o Git primeiro; o site é a parte fácil.

Por que Git e não uma pasta projeto-v3-agora-vai

Todo mundo já fez isso. O problema não é o nome feio — é que a pasta duplicada não responde a três perguntas que o Git responde de graça:

  • Quem mudou e quando? — cada commit carrega autor, data e mensagem.
  • O que exatamente mudou? — git diff mostra linha por linha.
  • Como eu volto? — o histórico inteiro está na sua máquina; voltar é um comando, não um Ctrl+Z desesperado.

E tem a quarta, que só aparece quando você trabalha em grupo: como duas pessoas mexem no mesmo arquivo sem uma apagar a outra? É pra isso que existem branch, merge e conflito.

No curso: esta conversa é a aula 01, junto com a instalação e os primeiros commits.

02Instalar e configurar

Instalar leva cinco minutos. Configurar leva trinta segundos — e sem essa parte o Git se recusa a commitar.

Instalar

Windows

Baixe o Git for Windows em git-scm.com e aceite os padrões. Ele traz junto o Git Bash, um terminal estilo Linux — use ele, não o cmd.exe, que não entende metade dos exemplos da internet.

macOS

Quase sempre já vem. Rode git --version: se aparecer o convite pra instalar as Command Line Tools, aceite. Pra versão mais nova, brew install git.

Linux

Debian e Ubuntu: sudo apt install git. Fedora: sudo dnf install git. Arch: sudo pacman -S git.

# deu certo se imprimir alguma versão
git --version
git version 2.45.2

Dizer quem você é

O Git carimba nome e e-mail em todo commit. Sem isso configurado ele reclama e não deixa commitar. O --global vale pra todos os repositórios da máquina.

git config --global user.name "Seu Nome"
git config --global user.email "voce@exemplo.com"
Use o mesmo e-mail da sua conta do GitHub. É por ele que o site liga o commit ao seu perfil — e-mail diferente vira commit órfão, sem foto e sem link. Se você não quer expor o endereço real, o GitHub te dá um @users.noreply.github.com em Settings → Emails; use esse.

Os três ajustes que evitam dor de cabeça

# 1. a branch inicial se chama main, não master
git config --global init.defaultBranch main

# 2. no pull, integrar por merge — previsível, sem adivinhação
git config --global pull.rebase false

# 3. fim de linha: mata o diff fantasma entre Windows e Linux
git config --global core.autocrlf true    # Windows
git config --global core.autocrlf input   # macOS e Linux

Conferir o que ficou

# tudo, com o arquivo de onde veio cada linha
git config --list --show-origin

# só um valor
git config user.email

A configuração mora em três camadas, e a mais específica vence:

CamadaFlagArquivoVale para
Sistema--system/etc/gitconfigTodo mundo na máquina
Usuário--global~/.gitconfigVocê, em todos os repositórios
Repositório--local (padrão).git/configSó aquele projeto
Truque de quem tem dois "eus": trabalho e pessoal com e-mails diferentes. Deixe o pessoal no --global e, dentro do repo do trabalho, rode git config user.email "voce@empresa.com" sem o --global. O local ganha.

Editor e apelidos

# qual editor abre quando o Git precisa de um texto seu
git config --global core.editor "code --wait"   # VS Code
git config --global core.editor "nano"          # nano

# apelidos: git st, git lg…
git config --global alias.st "status -sb"
git config --global alias.lg "log --oneline --graph --all --decorate"

03O primeiro repositório

Repositório é uma pasta comum com uma pasta escondida .git dentro. É ali que mora o histórico inteiro.

Do zero, na sua máquina

mkdir meu-projeto
cd meu-projeto
git init
Initialized empty Git repository in /home/voce/meu-projeto/.git/

Só isso. A pasta .git apareceu — escondida, use ls -a pra ver — e a partir de agora o Git observa tudo o que acontece ali dentro.

Apagou o .git, apagou o histórico. A pasta é o repositório. Copiar o projeto sem ela é copiar só a foto de hoje. E nunca rode git init na sua pasta pessoal inteira: o Git vai querer versionar o computador todo.

Ou clonando um que já existe

git clone git@github.com:usuario/projeto.git
cd projeto

O clone faz três coisas de uma vez: baixa o projeto, cria o .git com o histórico completo e já deixa o remoto origin configurado. Detalhe em clone, push, pull, fetch.

O que colocar num repositório novo

ArquivoPara que serve
README.mdA vitrine. O que é, como instalar, como rodar. É o que o GitHub mostra na página inicial do repo.
.gitignoreO que o Git deve fingir que não existe. Escreva antes do primeiro commit.
LICENSESem licença ninguém pode legalmente usar o seu código — público não quer dizer livre.

CODE_OF_CONDUCT.mdAs regras de convivência. Praxe em projeto público.

Um README que funciona

A regra é responder, nesta ordem, ao que quem acabou de cair ali quer saber: o que é isso, como eu rodo, como eu ajudo.

README.md
# nome-do-projeto

Uma frase dizendo o que faz e pra quem.

são um bom começo.

## Licença

MIT

Público × privado

Público

Qualquer pessoa lê, clona e abre issue. Só quem você autoriza escreve. Actions de graça. É o portfólio — recrutador entra aqui.

Privado

Só quem você convida enxerga. Não aparece no perfil. Actions tem cota. Use pra código de cliente, trabalho pago, e pra qualquer coisa com segredo dentro.

Na dúvida, em projeto pequeno: MIT. O site choosealicense.com resolve em três cliques e o próprio GitHub oferece o modelo na hora de criar o arquivo.

04Os três lugares e o ciclo

Quase todo erro de iniciante em Git é confusão sobre em qual dos três lugares a sua alteração está agora.

Imagine que você está montando uma mala. A bancada do quarto é onde as roupas estão espalhadas. A mala aberta é onde você separa o que vai levar. E o lacre é quando você fecha e etiqueta. Git tem exatamente isso:

LugarNome técnicoO que éComo sai de lá
Quartoworking tree (diretório de trabalho)Seus arquivos como estão agora no discogit add
Malastaging area / indexO que vai entrar no próximo commitgit commit
Mala lacradarepositório (.git)O histórico — commits gravados pra sempregit push, pro remoto
working tree  ──git add──▶  staging  ──git commit──▶  repositório  ──git push──▶  remoto
     ▲                          │                          │
     └──git restore ────────────┘                          │
     └──────────── git restore --source=HEAD ──────────────┘

O ciclo, em três comandos

# 1. o que mudou?
git status

# 2. o que eu quero neste commit?
git add arquivo.txt

# 3. lacra, com uma etiqueta
git commit -m "Adiciona a tela de login"

Repita isso o dia inteiro. É todo o dia a dia do Git. O resto do guia são casos especiais.

Ler o git status

$ git status On branch main Changes to be committed: (use "git restore --staged <file>..." to unstage) new file: index.html Changes not staged for commit: modified: estilo.css Untracked files: rascunho.txt

Três blocos, três lugares:

  • Changes to be committed — está na mala. Entra no próximo commit.
  • Changes not staged for commit — o Git já conhece o arquivo, mas a alteração de agora não entra.
  • Untracked files — o Git nunca viu esse arquivo. Ou você adiciona, ou ele vai pro .gitignore.
Versão curta: git status -sb. Duas colunas — a primeira é a mala, a segunda é o quarto. A  novo em staging,  M modificado fora, MM modificado nos dois, ?? desconhecido.

Escolher o que entra: a mala é opcional de propósito

Você mexeu em cinco arquivos, mas só três formam uma ideia fechada. Commite os três agora e os outros dois depois — é pra isso que a staging existe. Commit é unidade de sentido, não "tudo o que eu fiz até a hora do almoço".

git add index.html estilo.css   # dois arquivos
git add .                       # tudo desta pasta pra baixo
git add -A                      # tudo do repositório, inclusive apagados
git add -p estilo.css          # pedaço por pedaço, ele pergunta
git add -p é o comando que separa o iniciante do resto. Ele mostra cada trecho alterado e pergunta: y entra, n fica de fora, s quebra em pedaços menores, q sai. Serve pra tirar aquele console.log de dentro do commit sem apagar do arquivo.

Tirar da mala sem perder o trabalho

git restore --staged arquivo.txt   # volta pro quarto, alteração intacta
git restore arquivo.txt            # DESCARTA a alteração do quarto
Os dois se parecem e fazem coisas opostas. Com --staged você só desfaz o add. Sem --staged, você joga fora o que escreveu — e isso não tem reflog pra resgatar, porque nunca virou commit.

Ver o que mudou, de verdade

git diff              # quarto × mala (o que ainda NÃO entrou)
git diff --staged     # mala × último commit (o que VAI entrar)
git diff HEAD         # tudo que mudou desde o último commit
git diff main..feat   # o que a branch feat tem a mais
git diff --stat       # só o resumo: arquivos e nº de linhas
Hábito que salva: rode git diff --staged antes de todo commit. É a última chance de ver a senha, o console.log e o arquivo que você não queria ter mexido.

Ler o histórico

git log                          # completo, um bloco por commit
git log --oneline                # uma linha por commit
git log --oneline --graph --all  # com o desenho das branches
git log -3                       # só os três últimos
git log -p arquivo.txt           # histórico com o diff de um arquivo
git log --author="Ana"          # só o que a Ana commitou
git log --since="2 weeks ago"    # recorte por tempo
git show a1b2c3d                 # um commit inteiro, com diff
No curso: o ciclo, a staging, log e diff são a aula 01.

05A mensagem de commit

A mensagem é para o futuro — pra você daqui a seis meses tentando entender por que aquela linha existe. Escreva pensando em quem vai ler o git log, não em quem está te vendo digitar.

A forma

tipo(escopo opcional): resumo em até ~50 caracteres, no imperativo

Corpo, se precisar. Explique o PORQUÊ, não o quê — o "o quê"
já está no diff. Quebre as linhas em ~72 colunas.

Rodapé: Closes #42

Assim não

ajustes
correções
final
agora vai
update
wip
mudei o arquivo login.js

Nenhuma dessas te ajuda a achar nada daqui a seis meses.

Assim sim

fix: corrige o login que caía sem cookie
feat: adiciona filtro por data na listagem
refactor: extrai a validação para um módulo
docs: explica como rodar os testes

Cada uma responde "o que este commit faz" sozinha.

As regras que valem em qualquer projeto

  • Imperativo. "Adiciona", não "adicionado" nem "adicionei". O truque: a frase tem que completar "Se aplicado, este commit vai ___".
  • Primeira linha curta — até uns 50 caracteres, sem ponto final. É o que aparece na listagem.
  • Linha em branco antes do corpo. Sem ela, o Git trata tudo como título.
  • Um commit, uma ideia. Se a mensagem precisa de "e", provavelmente eram dois commits.

Conventional Commits

É uma convenção de nomes pro prefixo da mensagem. Não é regra do Git — é combinado de time. O ganho: a máquina consegue ler o histórico e gerar changelog e número de versão sozinha (veja tags, SemVer e deploy).

Quebra de compatibilidade

Duas formas, as duas valem — e as duas viram MAJOR:

# com o ! depois do tipo
feat!: remove o endpoint /v1/usuarios

# ou com o rodapé, que aceita explicação
feat: troca o formato de resposta da API

BREAKING CHANGE: /usuarios agora devolve um objeto com
paginação em vez de um array. Quem consome precisa ler .items.

Commit em várias linhas, sem abrir editor

git commit -m "feat: adiciona filtro por data" \
           -m "A listagem carregava tudo. Agora o filtro vai no SQL." \
           -m "Closes #42"

Cada -m vira um parágrafo. Sem nenhum -m, o Git abre o editor configurado — e aí você escreve à vontade.

Palavras que fecham issue sozinhas: Closes #42, Fixes #42, Resolves #42. Na mensagem do commit ou na descrição do PR, o GitHub fecha a issue quando aquilo chega na branch padrão. Só #42 sem verbo apenas cria o link, não fecha.

06O .gitignore

O arquivo que diz ao Git: "isso aqui não é meu problema". Escreva ele antes do primeiro commit — depois é bem mais chato.

Três famílias de arquivo nunca devem entrar no histórico:

FamíliaExemplosPor quê
Segredo.env, credenciais.json, *.pemVaza senha, chave de API, certificado. O pior dos três.
Geradonode_modules/, dist/, build/, target/, __pycache__/Dá pra recriar com um comando. Só incha o repo — node_modules sozinho passa de 200 MB.
Da sua máquina.DS_Store, Thumbs.db, .idea/, .vscode/Não interessa a mais ninguém e gera conflito bobo.

!.env.example

build/

A sintaxe, em seis regras

PadrãoO que pega

O .gitignore só vale pra arquivo que o Git ainda NÃO rastreia. Se o .env já entrou num commit, acrescentar a linha não tira ele de lá. Você precisa tirar do rastreamento — e, se a senha já subiu pro remoto, ela está comprometida: rotacione o segredo antes de qualquer limpeza. Veja segredo vazado.
# tira do rastreamento mas MANTÉM o arquivo no disco
git rm --cached .env
git commit -m "chore: para de versionar o .env"

Quando o Git ignora e você não entende por quê

# qual regra, de qual arquivo, está pegando?
git check-ignore -v caminho/do/arquivo

# forçar a entrada de um arquivo ignorado
git add -f arquivo-ignorado.txt
Não escreva do zero. O github/gitignore tem modelo pronto pra dezenas de linguagens, e o GitHub oferece um na hora de criar o repositório. Existe também o ~/.gitignore_global, pras coisas do seu editor — assim você não obriga o time a carregar o seu .idea/.
Vizinho útil: o .gitattributes resolve fim de linha e diff de arquivo binário. Menos comum, mas é onde você põe * text=auto quando o time mistura Windows e Linux.
No curso: o .gitignore fecha a aula 01.

07Branches

Branch é uma linha do tempo paralela. Você experimenta à vontade sem tocar no que já funciona — e, se der errado, apaga a linha e ninguém fica sabendo.

A analogia boa: o documento compartilhado. Em vez de editar o original enquanto os outros leem, você faz uma cópia sua, mexe nela, e só devolve pro original quando estiver pronto. A diferença é que no Git a "cópia" é barata — uma branch é literalmente um post-it apontando pra um commit. Criar custa nada.

main    A───B───C───────────F      ← linha principal, sempre funcionando
                 \         /
feat/login        D───E───┘        ← sua linha paralela, com o merge de volta

Os comandos

git branch                       # listar as locais (* = onde você está)
git branch -a                    # incluir as remotas
git branch -vv                   # com o último commit e o upstream

git switch -c feat/login         # criar E ir pra ela
git switch main                  # voltar
git switch -                     # voltar pra anterior (como o cd -)

git branch -m nome-novo          # renomear a atual
git branch -d feat/login         # apagar (só se já foi mergeada)
git branch -D feat/login         # apagar à força
switch ou checkout? O git checkout antigo fazia coisa demais: trocava de branch e restaurava arquivo. Em 2019 o Git separou em git switch (branch) e git restore (arquivo). O checkout continua funcionando — a internet inteira ainda usa —, mas prefira os novos: erro de dedo com switch não apaga o seu trabalho.

O arquivo que "some"

Você cria login.html na branch feat/login, commita, volta pra main — e o arquivo sumiu da pasta. Está tudo certo. A main não conhece aquele commit; o Git reescreveu a sua pasta pra ficar igual ao que a main conhece. Volte pra branch e o arquivo reaparece.

Só some o que está commitado. Alteração não commitada viaja com você na troca de branch — e se ela conflitar com o destino, o Git barra a troca. Aí você commita, ou usa git stash.

Como nomear

Não é regra do Git, é convenção de time — mas o time inteiro agradece:

PadrãoPara
feat/filtro-por-dataFuncionalidade nova
fix/login-sem-cookieCorreção de bug
docs/readme-instalacaoDocumentação
chore/atualiza-depsManutenção
fix/142-login-sem-cookieCom o número da issue — dá pra rastrear

Minúsculas, hífen no lugar do espaço, sem acento, curto. Evite teste, nova, branch-do-joao — daqui a duas semanas ninguém sabe o que era.

HEAD, e o "detached HEAD"

HEAD é o ponteiro que diz onde você está. Normalmente ele aponta pra uma branch, que aponta pro commit. Quando você dá git checkout a1b2c3d direto num commit, o HEAD aponta pro commit sem branch no meio: é o detached HEAD. Você pode olhar à vontade, mas commit feito ali não pertence a branch nenhuma e se perde quando você sair.

# commitou em detached HEAD e quer salvar? crie a branch ali mesmo
git switch -c salva-o-que-eu-fiz

# só queria dar uma olhada
git switch -
No curso: branches são a aula 02; nomenclatura e estratégia de branch, a aula 07.

08Merge e rebase

Duas formas de trazer o trabalho de uma branch pra outra. Merge junta e preserva a história. Rebase reescreve pra parecer que tudo foi feito em fila.

Merge

Você vai pra branch que vai receber e manda vir. Sempre nessa ordem — é o erro mais comum: mergear no sentido errado.

git switch main            # 1. vá pra quem RECEBE
git merge feat/login       # 2. traga quem foi feito

Fast-forward × commit de merge

Fast-forward

A main não andou desde que a branch nasceu. O Git só empurra o post-it pra frente. Não cria commit novo.

main  A───B───C───D
                  ↑
              main e feat

Commit de merge

As duas andaram. O Git cria um commit com dois pais — e aí ele pode precisar de você, se houver conflito.

main  A───B───────M
           \     /
feat        C───D
git merge feat/login              # ff quando dá, commit de merge quando precisa
git merge --no-ff feat/login       # força o commit de merge, sempre
git merge --squash feat/login      # junta tudo num commit só, sem o merge
git merge --abort                 # cancela um merge que deu conflito
Por que alguém força --no-ff? Porque o commit de merge deixa registrado que aquilo foi uma unidade de trabalho — dá pra reverter a funcionalidade inteira com um revert -m 1. É por isso que muito time liga "always create a merge commit" no PR.

Apagar a branch depois

git branch -d feat/login                # local
git push origin --delete feat/login     # remota
git fetch --prune                       # limpa as remotas que já sumiram

Branch mergeada e não apagada só polui a lista. O trabalho está na main — não se perde nada.

Rebase

O rebase pega os seus commits e os reaplica em cima de outra base, um por um. O resultado é uma linha reta, como se você tivesse partido do estado mais novo da main.

# estando na sua branch
git switch feat/login
git fetch origin
git rebase origin/main
ANTES                          DEPOIS DO REBASE
main  A───B───C                main  A───B───C
       \                                      \
feat    D───E                  feat            D'──E'

Repare no D': não é o mesmo commit D. É um commit novo, com hash novo, com o mesmo conteúdo. Rebase reescreve o histórico — e é daí que vem a regra de ouro:

09O conflito

Conflito não é erro. É o Git avisando que duas pessoas mexeram nas mesmas linhas e que ele não vai escolher por você.

O Git resolve sozinho quase tudo: arquivos diferentes, partes diferentes do mesmo arquivo. Ele só para quando as alterações se sobrepõem na mesma região — aí decidir é trabalho de gente.

$ git merge feat/login CONFLICT (content): Merge conflict in index.html Automatic merge failed; fix conflicts and then commit the result.

Ler os marcadores

O Git escreve os dois lados dentro do arquivo, marcados assim:

index.html
<<<<<<< HEAD
    <h1>Bem-vindo ao site</h1>
=======
    <h1>Bem-vinda ao portal</h1>
>>>>>>> feat/login
  • Entre <<<<<<< HEAD e =======: o que está na branch onde você está.
  • Entre ======= e >>>>>>>: o que vem da branch que você mandou vir.

Resolver, em três passos

  1. Edite o arquivo Escolha um lado, o outro, ou escreva a terceira versão que junta os dois. Apague as três linhas de marcador — elas não podem sobrar no arquivo final.
  2. Marque como resolvido 
    git add index.html
  3. Feche o merge 
    git commit
    O Git já traz a mensagem pronta ("Merge branch..."). Aceite — ela é boa.
O erro clássico: resolver o texto e esquecer de apagar =======. O código quebra de um jeito bizarro e ninguém entende por quê. Antes de commitar, procure por <<<<<<< no projeto inteiro.

Ferramentas que ajudam

git status                        # lista os arquivos em conflito
git diff                          # mostra os dois lados
git checkout --ours arquivo       # fica com o lado de onde você está
git checkout --theirs arquivo     # fica com o lado que veio
git mergetool                     # abre a ferramenta visual configurada
Cuidado com --ours e --theirs: eles pegam o arquivo inteiro de um lado só, jogando fora tudo do outro. Ótimo pra arquivo gerado (um package-lock.json, por exemplo). Péssimo pra código escrito por gente. E num rebase o significado se inverte, porque quem está sendo reaplicado é você.

A saída de emergência

git merge --abort     # cancela o merge, volta ao estado anterior
git rebase --abort    # idem, pro rebase
git rebase --continue # resolveu um passo do rebase? siga
git rebase --skip     # pula o commit em conflito (raro, pense antes)
Não tenha medo de abortar. Enquanto o merge está em aberto nada foi gravado. Abortar te devolve exatamente ao segundo antes — respire, entenda o conflito, tente de novo.

Como ter menos conflito

  • Branch curta. Conflito cresce com o tempo que a branch fica viva. Dois dias é bem menos briga que duas semanas.
  • Atualize sempre. git pull (ou rebase origin/main) todo dia, em vez de uma vez no fim.
  • Combine quem mexe onde. Metade dos conflitos é falta de conversa, não falta de ferramenta.
  • Formate automaticamente. Um formatador no projeto acaba com o conflito que é só espaço em branco.

Caminho A — chave SSH

Um par de chaves: a privada fica na sua máquina e não sai de lá nunca; a pública você entrega ao GitHub. Cadeado e chave.

Só a que termina em .pub. O arquivo sem extensão é a chave privada — ela nunca vai pra lugar nenhum, nem pro GitHub, nem pro chat, nem pro commit.

Caminho B — token pessoal (PAT)

Um token é uma senha descartável, com prazo e com escopo. Existem dois tipos, e o novo é melhor:

  • Fine-grained — você escolhe quais repositórios e qual permissão. É o recomendado.
  • Classic — permissões amplas por marcação (repo, workflow…). Mais fácil, mais perigoso.

Gere em Settings → Developer settings → Personal access tokens. Escolha um prazo (90 dias é razoável) e dê só a permissão que você precisa — pra push, Contents: Read and write.

O token aparece uma vez só. Fechou a aba, perdeu — só resta gerar outro. Guarde no gerenciador de senhas, nunca num arquivo do projeto. E se ele vazar, revogue imediatamente: token vazado é conta invadida.
# faça o Git guardar o token, pra não digitar toda vez
git config --global credential.helper store     # Linux (arquivo em texto puro)
git config --global credential.helper osxkeychain  # macOS
git config --global credential.helper manager   # Windows (Credential Manager)

No primeiro push ele pergunta usuário e senha: o usuário é o seu login, e a senha é o token (colado, não digitado).

Ligue 2FA na conta. É obrigatório pra quem contribui em código no GitHub, e é a única coisa que separa "roubaram a minha senha" de "roubaram os meus repositórios". App autenticador ou passkey.

11clone, push, pull, fetch

O remoto é outro repositório Git, que por acaso mora num servidor. Você sincroniza com ele de propósito, quando quer — nada é automático.

O vocabulário

remote
Um apelido pra uma URL de outro repositório. origin é o nome tradicional do "meu remoto principal".
origin
Convenção, não palavra reservada. É o remoto que o clone cria automaticamente.
upstream
Duas coisas com o mesmo nome, cuidado. (1) A branch remota que a sua branch local acompanha — origin/main. (2) Em fork, o apelido do repositório original.
origin/main
Uma branch de rastreamento: a sua foto local de como a main do servidor estava no último fetch. Não é o servidor ao vivo.

Ligar um repositório local a um remoto

Crie o repositório vazio no GitHub — sem README, sem licença, sem .gitignore. Se ele nascer com arquivo, o primeiro push é rejeitado, porque os dois históricos não têm nada em comum.

git remote add origin git@github.com:usuario/projeto.git
git branch -M main
git push -u origin main
O -u é o que importa. Ele grava que a sua main local acompanha a origin/main. Depois disso, git push e git pull pelados já sabem pra onde ir. Sem o -u, você digita git push origin main a vida inteira.

clone × init + remote add

git clone

O projeto já existe no GitHub. Um comando: baixa, cria o .git, configura o origin e já deixa a branch com upstream. É o caminho de 90% dos dias.

init + remote add

O projeto já existe na sua máquina e você quer mandar pro GitHub agora. É o caminho de quando o código nasceu antes do repositório.

git clone git@github.com:usuario/projeto.git
git clone git@github.com:usuario/projeto.git nome-da-pasta   # outro nome
git clone --depth 1 URL                                      # só o último commit (rápido)
git clone -b feat/login URL                                  # já numa branch específica

Mandar: push

git push                                 # pro upstream já configurado
git push -u origin feat/login            # primeira vez desta branch
git push origin --delete feat/login      # apagar a branch remota
git push --tags                          # mandar as tags também

Trazer: fetch × pull

Aqui mora a confusão mais útil de desfazer do Git inteiro:

git fetchgit pull
Baixa do servidorSimSim
Mexe nos seus arquivosNãoSim
Pode dar conflitoNuncaSim
É, na verdade—fetch + merge
O hábito profissional: git fetch e depois git log origin/main --oneline pra ver o que vem antes de integrar. Aí você decide se quer merge, rebase, ou nem isso agora. pull direto é o atalho — ótimo quando você sabe que não tem nada demais chegando.
git fetch                       # atualiza origin/*, não toca em nada seu
git fetch --all --prune         # todos os remotos, limpando o que já morreu
git log HEAD..origin/main       # o que tem lá e não tem aqui
git diff HEAD origin/main       # o diff completo do que vem

git pull                        # fetch + merge
git pull --rebase               # fetch + rebase (histórico linear)
git pull --ff-only              # só se der pra avançar sem criar nada

pull --rebase

O pull comum, quando os dois lados andaram, cria um commit de merge com a mensagem "Merge branch 'main' of github.com...". Um por dia, por pessoa, e o histórico vira macarrão. O --rebase reaplica os seus commits por cima do que veio, e a linha fica reta.

# adotar de vez, se o time gosta de histórico linear
git config --global pull.rebase true
Vale a regra de ouro do rebase. É seguro aqui porque ele reescreve só os seus commits, os que ainda não subiram. Se você já tinha feito push deles, o rebase troca os hashes e o próximo push é rejeitado — e aí o conserto é --force-with-lease, que é assunto da próxima seção.

git remote set-url origin NOVA-URL             # trocar o endereço
git remote rename origin gh                    # renomear
git remote remove upstream                     # remover
git remote show origin                         # tudo sobre um remoto

12Push rejeitado e o que --force destrói

O non-fast-forward é o erro que mais assusta e o menos perigoso. Ele é o Git te protegendo.

$ git push ! [rejected] main -> main (fetch first) error: failed to push some refs to 'github.com:usuario/projeto.git' hint: Updates were rejected because the remote contains work that you hint: do not have locally. This is usually caused by another repository hint: pushing to the same ref.

O que aconteceu

Alguém — outra pessoa, ou você mesmo pela tela do GitHub — commitou no servidor depois do seu último pull. Aceitar o seu push agora apagaria aquele commit. O Git se recusa.

servidor   A───B───X        ← o commit X, que você não tem
                \
você       A───B───Y        ← o seu commit Y

push direto sobrescreveria o X. Por isso: rejeitado.

O conserto, em duas linhas

git pull --rebase     # traz o X e reaplica o seu Y por cima
git push              # agora vira A─B─X─Y, fila reta

Se aparecer conflito no meio, resolva, git add e git rebase --continue. É o mesmo procedimento da seção de conflito.

Isto é rotina, não acidente. Em time ativo você vai ver esse erro várias vezes por semana. Duas linhas e segue o dia.

O que --force faz

O git push --force diz ao servidor: "apaga o que está aí e põe o meu no lugar". O commit X do desenho acima some. Quem já tinha o X no computador continua com ele, e agora tem um histórico que não bate com o do servidor — é o cenário em que trabalho de gente desaparece de verdade.

--force nunca é o conserto do non-fast-forward normal. Se você chegou aqui procurando "como forçar o push", o que você quer é git pull --rebase. Force serve pra um caso só: você reescreveu a sua própria branch de PR de propósito (rebase, amend, squash) e precisa atualizar o remoto dela.

--force-with-lease, o force com trava

# nunca use isto
git push --force

# use isto, quando precisar mesmo
git push --force-with-lease

A diferença: o --force-with-lease só sobrescreve se o remoto estiver exatamente onde você viu pela última vez. Se alguém commitou nesse meio-tempo, ele recusa em vez de atropelar. É o cinto de segurança de uma operação que, por natureza, é perigosa.

ComandoSobrescreve se alguém commitou?Quando usar
git pushNão — rejeitaSempre
git push --force-with-leaseNão — recusa e avisaDepois de reescrever a sua branch de PR
git push --forceSim, sem perguntarPraticamente nunca
A trava institucional: branch protection na main bloqueia force push pra todo mundo, inclusive pra quem é admin. É a razão número um pra ligar proteção de branch já no primeiro dia do projeto.

14Pull Request

PR é o pedido: "olha o que eu fiz — dá pra entrar?". Não é do Git; é do GitHub. É onde o código é lido, discutido, testado e só então integrado.

Tecnicamente, um PR é um merge com sala de espera: você propõe trazer a branch A pra branch B e, enquanto ninguém aprova, nada acontece na main.

O fluxo completo

  1. Atualize a base 
    git switch main
git pull
  2. Crie a branch 
    git switch -c feat/filtro-por-data
  3. Trabalhe e commite Commits pequenos, mensagens no padrão do time.
  4. Publique a branch 
    git push -u origin feat/filtro-por-data
    A resposta do push já vem com o link pra abrir o PR. Ou o GitHub mostra a faixa amarela "Compare & pull request".
  5. Abra o PR Confira as duas pontas: base (pra onde vai, normalmente main) e compare (a sua branch). Escreva título e descrição.
  6. Responda à revisão Commite os ajustes na mesma branch e dê push — o PR se atualiza sozinho.
  7. Merge e limpeza Depois de aprovado e com os checks verdes. Apague a branch — o botão aparece ali mesmo.

Título como mensagem de commit: curto, imperativo, específico. Descrição respondendo o que, por quê e como testar.

Rascunho (draft)

Abra como Draft quando quer feedback cedo mas o trabalho não está pronto. O botão de merge fica travado e ninguém é notificado como revisor. Quando ficar pronto, Ready for review.

O tamanho do PR

PR pequeno

Até uns 400 linhas de diff. Revisado no mesmo dia, com comentário de verdade. Bug passa menos.

PR gigante

2000 linhas. Fica três dias parado, recebe "LGTM 👍" sem leitura, e conflita com tudo. Revisão grande é revisão fingida.

Se ficou grande, quebre. Um PR de refactor, outro de funcionalidade. Ou abra em série, cada um baseado no anterior. É mais trabalho pra você e muito menos pro time.

15Code review e CODEOWNERS

Revisar não é procurar defeito na pessoa. É a segunda leitura que pega o que a primeira não pegou — e, de quebra, é como o conhecimento do projeto se espalha.

Como revisar, na prática

  1. Leia a descrição antes do código Sem saber o objetivo, você revisa estilo em vez de solução.
  2. Abra "Files changed" Vá arquivo por arquivo. Use Viewed pra marcar o que já leu — em PR grande isso salva.
  3. Comente na linha Clique no + ao lado da linha. Comentário ancorado no código vale dez no chat.
  4. Junte tudo numa revisão só Use Start a review em vez de Add single comment: os comentários saem juntos, com uma notificação, e não em conta-gotas.
  5. Escolha o veredito Comment (opinião, sem bloquear) · Approve (pode entrar) · Request changes (trava até você voltar).

Sugestão em um clique

No comentário, use o bloco suggestion: quem abriu o PR aceita com um botão e vira commit.

Faltou tratar o caso de lista vazia:

```suggestion
  if (!itens.length) return [];
```
Perfeito pra typo, nome de variável, ajuste de uma linha. Poupa a viagem "comenta → pessoa lê → pessoa edita → pessoa faz push".

Crítica que ajuda em vez de brigar

Assim não

"Isso está errado."
"Por que você fez desse jeito?"
"Ninguém escreve mais assim."
"Refaz."

Ataca a pessoa, não explica nada e não propõe saída.

Assim sim

"Se a lista vier vazia isso quebra na linha 12 — dá pra tratar antes?"
"Sugiro extrair pra uma função, fica mais fácil de testar. O que você acha?"
"Não é bloqueante, mas find ficaria mais legível aqui."

  • Comente o código, nunca a pessoa. "Esta função" e não "você".
  • Diga o que bloqueia e o que não. Um "nit:" na frente avisa que é gosto, não exigência.
  • Pergunte antes de acusar. Metade das vezes tem um motivo que você não conhece.
  • Elogie o que ficou bom. Revisão só com crítica desgasta o time.
  • Aprove sem drama. Se está bom, aprove. Segurar PR bom por perfeccionismo custa caro.

Do lado de quem recebe

  • Responda todo comentário, nem que seja "boa, ajustado".
  • Discordar é legítimo — explique o porquê, com argumento técnico.
  • Não faça force push no meio da revisão sem avisar: os comentários perdem a âncora.
  • Resolva a conversa (Resolve conversation) só depois de tratar de verdade.

A última linha que bater vence — ao contrário do .gitignore, onde a exceção precisa vir depois com !. E o dono precisa ter acesso de escrita ao repositório, senão o GitHub ignora a regra em silêncio.

16Fork e projeto alheio

Fork é a sua cópia, na sua conta, de um repositório onde você não tem permissão de escrever. É como se contribui com projeto de outra pessoa.

Branch

Você tem acesso de escrita. Cria a branch no próprio repositório e abre o PR ali. É o caminho dentro do time.

Fork

Você não tem acesso. Copia o repositório pra sua conta, trabalha lá e abre o PR do seu fork pro original. É o caminho do open source.

O caminho completo

# 1. no site: botão Fork (vai pra sua conta)

# 2. clone o SEU fork, não o original
git clone git@github.com:voce/projeto.git
cd projeto

# 3. aponte pro original com o nome upstream
git remote add upstream https://github.com/original/projeto.git
git remote -v
origin git@github.com:voce/projeto.git (fetch) origin git@github.com:voce/projeto.git (push) upstream https://github.com/original/projeto.git (fetch) upstream https://github.com/original/projeto.git (push)

Dois remotos, dois papéis: origin é seu (você dá push), upstream é deles (você só puxa).

Manter o fork em dia

Fork não se atualiza sozinho. Duas semanas parado e ele já está velho.

git switch main
git fetch upstream
git merge upstream/main      # ou: git rebase upstream/main
git push origin main
No site tem atalho: o botão Sync fork na página do seu fork faz o mesmo em um clique — e o gh repo sync faz do terminal. Faça isso antes de criar cada branch nova.

Trabalhar e abrir o PR

git switch -c fix/typo-no-readme
# … edite …
git commit -m "docs: corrige typo na seção de instalação"
git push -u origin fix/typo-no-readme

No site, o PR abre do seu fork pro repositório original. Confira as duas pontas — a base é a main deles.

Antes de abrir PR em projeto que não é seu

  • Leia o CONTRIBUTING.md. Ele diz o padrão de commit, se precisa de teste, se precisa de issue antes. Ignorar isso é o motivo número um de PR recusado.
  • Comece pela issue. Procure good first issue ou help wanted. Comente que vai pegar, pra ninguém fazer duas vezes.
  • Um assunto por PR. "Corrige typo e também refatora o build" não passa.
  • Aceite a revisão. O mantenedor conhece o projeto há anos. Pedido de mudança é normal, não é rejeição.
  • Tenha paciência. Muito mantenedor faz isso de graça, no tempo livre. Semanas de espera acontecem.
Contribuição não é só código. Documentação, tradução, exemplo que faltava, issue bem escrita reproduzindo um bug — tudo isso é contribuição de verdade, e costuma ser mais bem-vindo que um refactor não solicitado.
No curso: fork × branch é a aula 06; o ciclo inteiro de contribuição em open source é a aula 12.

18Actions: o vocabulário

GitHub Actions é um robô que roda comandos quando algo acontece no repositório. Você descreve o robô num arquivo YAML e ele passa a trabalhar de graça, no servidor deles.

Cinco palavras dão conta do assunto inteiro. Se você entender estas cinco, lê qualquer workflow do mundo:

evento (on)
O quando. push, pull_request, schedule (cron), release, workflow_dispatch (botão manual).
job
Um bloco de trabalho, com máquina própria. Jobs rodam em paralelo, a não ser que você use needs: pra encadear.
step
Um passo dentro do job, na ordem. Ou roda um comando (run:) ou usa uma action pronta (uses:).
runner
A máquina virtual que executa o job — ubuntu-latest, windows-latest, macos-latest. Nasce limpa e morre no fim.
action
Um bloco pronto que alguém já escreveu. actions/checkout@v4 baixa o seu código; actions/setup-node@v4 instala o Node.

Onde mora

.github/
└── workflows/
    ├── ci.yml
    ├── deploy.yml
    └── qualquer-nome.yml
O caminho é exato. .github/workflows/, no plural, na raiz do repositório. .github/workflow/ ou github/workflows/ — o GitHub simplesmente ignora, sem erro nenhum. Se o seu workflow "não roda", confira o caminho antes de qualquer outra coisa.

A anatomia de um workflow

.github/workflows/ci.yml
name: CI                        # o nome que aparece na aba Actions

on:                             # EVENTO: quando roda
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:                        # JOB: o id, escolhido por você
    runs-on: ubuntu-latest      # RUNNER: a máquina
    steps:
      - uses: actions/checkout@v4          # ACTION pronta

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Instalar dependências        # STEP com comando
        run: npm ci

      - name: Rodar os testes
        run: npm test
O actions/checkout@v4 não é opcional. Sem ele o runner está numa máquina vazia — o seu código não está lá. É o primeiro passo de praticamente todo workflow.

YAML: as três armadilhas

  • Indentação é sintaxe — espaços, nunca tab. Dois espaços por nível.
  • on: vira true em YAML antigo. Nos Actions funciona, mas se o seu editor reclamar, escreva "on":.
  • Traço é item de lista. Cada - name: começa um step novo; o resto do step fica alinhado embaixo.

19CI: o workflow do PR

Integração contínua é uma frase só: toda alteração é testada automaticamente, sozinha, antes de entrar. O robô nunca esquece de rodar o teste.

O problema que a CI resolve: "na minha máquina funciona". O runner nasce limpo — se o projeto só roda porque você tem uma variável de ambiente esquecida desde 2022, a CI descobre no primeiro minuto.

Um CI completo, comentado

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  qualidade:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'          # cache de dependências de graça

      - run: npm ci               # ci, não install: respeita o lockfile

      - name: Lint
        run: npm run lint

      - name: Testes
        run: npm test -- --coverage

      - name: Build
        run: npm run build

      - name: Guardar o resultado do build
        uses: actions/upload-artifact@v4
        if: always()            # mesmo se um passo acima falhou
        with:
          name: dist
          path: dist/
npm ci e não npm install. O ci instala exatamente o que está no package-lock.json e falha se o lock estiver fora de sincronia. É a diferença entre um build reprodutível e um build que muda de comportamento na terça.

Matriz de versões

Rodar o mesmo job em várias combinações, em paralelo, sem duplicar o YAML:

jobs:
  testes:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false          # um falhou? os outros continuam
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: ['18', '20', '22']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci && npm test

Duas listas de 2 e 3 → seis jobs em paralelo. Matriz cresce multiplicando; não exagere nas dimensões.

Jobs encadeados

jobs:
  testes:
    runs-on: ubuntu-latest
    steps: [...]

  deploy:
    needs: testes                     # só roda se testes passar
    if: github.ref == 'refs/heads/main'   # e só na main
    runs-on: ubuntu-latest
    steps: [...]

Ler a aba Actions quando fica vermelho

  1. Abra o run que falhou Aba Actions, ou o próprio PR — o check vermelho tem link Details.
  2. Ache o step vermelho Os passos aparecem em lista; o do X é o culpado.
  3. Leia de baixo pra cima A causa costuma estar algumas linhas antes do "Process completed with exit code 1", que é só o eco final.
  4. Reproduza local Rode exatamente o comando do run: na sua máquina. 90% das vezes o erro aparece igual.
  5. Se não reproduzir, é ambiente Versão diferente, variável que só existe aí, arquivo que está no seu disco e no .gitignore.
Botão Re-run jobs. Falha de rede e serviço externo instável acontecem. Mas se o mesmo teste falha às vezes, o problema é o teste — re-run vira analgésico e o time perde a confiança no CI.

Pipeline rápido é pipeline usado

  • Cache. cache: 'npm' no setup, ou actions/cache pra qualquer pasta.
  • Paralelize. Lint e teste em jobs separados terminam junto em vez de em fila.
  • Filtre. paths: no evento evita rodar o build inteiro quando só o README mudou.
  • Cancele o antigo. concurrency mata o run anterior da mesma branch quando você dá push de novo.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
Passou de dez minutos, o time começa a ignorar. CI lento vira "mergeia que depois a gente vê". Cinco minutos é a meta.

CI sozinha só informa. Vira portão quando você liga o check obrigatório — aí o vermelho realmente impede o merge.

Status checks obrigatórios

São a ponte entre a CI e a branch protection. Em Settings → Branches, na regra da main: ligue Require status checks to pass before merging e escolha os checks na busca.

O check só aparece na busca depois de ter rodado pelo menos uma vez. Se a lista está vazia, abra um PR qualquer, deixe a CI rodar, e volte. E o nome que aparece é o do job (a chave em jobs:), não o do workflow — renomear o job depois quebra a regra em silêncio.

Dependabot

Um robô que olha as suas dependências e abre PR quando sai versão nova ou quando aparece vulnerabilidade conhecida. Liga em Settings → Code security, ou por arquivo:

.github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5

      interval: "monthly"
O par que funciona: Dependabot abre o PR, a CI testa, você olha o check verde e mergeia. Sem CI, PR de dependência vira uma pilha que ninguém tem coragem de aceitar.

O segredo já foi para o histórico

Ordem certa, e ela não é intuitiva: 1. rotacione o segredo (revogue a chave no provedor e gere outra). 2. Só depois limpe o histórico. Quem inverte a ordem passa horas reescrevendo commit enquanto a chave ainda válida circula. Assuma que qualquer segredo que chegou a um repositório está comprometido — bots varrem o GitHub em minutos.
  1. Rotacione Revogue no provedor (AWS, Stripe, GitHub…) e gere uma chave nova. A partir daqui, a antiga não vale mais e o vazamento virou pó.
  2. Tire do rastreamento e ignore 
    git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: remove o .env do versionamento"
  3. Limpe o histórico, se precisar mesmo 
    # git-filter-repo, a ferramenta recomendada hoje
git filter-repo --invert-paths --path .env
    Isto reescreve todos os hashes. Todo mundo do time precisa reclonar. Avise antes.
  4. Ligue o push protection Pra não repetir. Settings → Code security → Secret scanning → Push protection.

23Antes do commit: restore, amend, stash

O território mais seguro. Aqui quase tudo é reversível — com uma exceção importante, que vem logo no primeiro comando.

git restore

# tirar da staging, alteração intacta no arquivo
git restore --staged arquivo.txt

# DESCARTAR a alteração do arquivo, voltando ao último commit
git restore arquivo.txt

# descartar tudo (perigoso, sem volta)
git restore .

# trazer um arquivo como estava em outro commit
git restore --source=HEAD~3 arquivo.txt
Esta é a única operação do Git que apaga de verdade. git restore arquivo sem --staged joga fora o que você escreveu e nunca commitou — e não existe reflog pra isso, porque nunca virou commit. Se estiver em dúvida, faça git stash em vez de restore: guarda em vez de queimar.

Limpar arquivo não rastreado

git clean -n      # só MOSTRA o que apagaria — rode sempre este antes
git clean -f      # apaga os arquivos
git clean -fd     # apaga também as pastas
git clean -fdx    # inclui o que está no .gitignore (mata node_modules)

git commit --amend

Substitui o último commit por um novo, com o conteúdo corrigido. Não "edita": cria outro commit e joga o antigo fora.

# só trocar a mensagem
git commit --amend -m "fix: corrige o cálculo do frete"

# esqueci um arquivo — junta ao commit anterior sem mudar a mensagem
git add esquecido.js
git commit --amend --no-edit

# consertar o autor (e-mail errado no config)
git commit --amend --author="Nome <email@exemplo.com>"
amend troca o hash. Se aquele commit já foi pro remoto, o próximo push é rejeitado. Na sua branch de PR, o conserto é git push --force-with-lease. Na main: não faça amend, faça um commit novo.

git stash

A gaveta. Guarda o trabalho pela metade, limpa a pasta, e devolve quando você pedir. Serve pra "preciso trocar de branch agora e não quero commitar lixo".

git stash                              # guarda e limpa
git stash push -m "meio do filtro"       # guarda com etiqueta (melhor)
git stash -u                           # inclui arquivos novos (untracked)

git stash list                         # o que tem na gaveta
git stash show -p stash@{0}            # ver o diff de um

git stash pop                          # devolve o último E tira da gaveta
git stash apply stash@{1}              # devolve um específico e MANTÉM guardado
git stash drop stash@{0}               # descarta um
git stash clear                        # esvazia (sem volta fácil)
pop ou apply? pop devolve e esquece. apply devolve e guarda cópia — melhor quando você não tem certeza de que vai dar certo, ou quando quer aplicar o mesmo stash em duas branches.
Stash é gaveta, não arquivo. Ele não vai pro remoto, não aparece no log, e é fácil esquecer o que tem lá. Se o trabalho importa de verdade, faça um commit numa branch temporária — commit você acha depois, stash de três meses atrás ninguém acha.

Commitei na branch errada

Situação clássica: você fez três commits achando que estava na feat/x e estava na main.

# 1. crie a branch certa AQUI — ela leva os commits junto
git switch -c feat/x

# 2. volte pra main e recue os três commits
git switch main
git reset --hard HEAD~3

# 3. confira
git log --oneline -3
Se você já tinha feito push da main com esses commits, o passo 2 não serve: aí é git revert. Reescrever a main compartilhada quebra o repositório de todo mundo.
No curso: restore, amend e stash são a aula 11.

24revert × reset

Os dois desfazem um commit. Um anda pra frente, o outro anda pra trás — e é essa diferença que decide qual você pode usar.

git revert

Cria um commit novo que faz o inverso do antigo. O commit ruim continua no histórico, e a marca de que foi desfeito também.

A───B───C───B'
          ↑    ↑
        ruim  desfaz B

Seguro em branch compartilhada.

git reset

Apaga commits movendo o ponteiro pra trás. Como se nunca tivessem existido.

A───B───C   →   A───B
        ↑           ↑
     antes        depois

Só na sua máquina, antes do push.

revert

git revert a1b2c3d                # desfaz um commit, abre editor pra mensagem
git revert HEAD                   # desfaz o último
git revert --no-edit a1b2c3d      # aceita a mensagem automática
git revert a1b2c3d..f4e5d6c       # um intervalo
git revert -n a1b2c3d             # só prepara, você commita depois

Reverter um commit de merge precisa dizer qual pai é o "normal" — quase sempre o 1, a branch que recebeu:

git revert -m 1 <hash-do-merge>
No GitHub tem botão. Todo PR mergeado tem Revert: ele abre um PR novo que desfaz aquele. É o rollback mais usado em produção, porque passa pela mesma revisão e pela mesma CI.

reset e os seus três modos

O que muda entre eles é até onde o desfazer vai — lembre dos três lugares:

ModoMove o ponteiroMexe na stagingMexe nos seus arquivosResultado prático
--softSimNãoNãoO commit some, tudo fica na mala pronto pra recommitar
--mixed (padrão)SimLimpaNãoO commit some, as alterações ficam no quarto
--hardSimLimpaSobrescreveSome tudo. Só use com certeza.
# "a mensagem ficou ruim, quero refazer o commit"
git reset --soft HEAD~1
git commit -m "feat: mensagem decente agora"

# "esses três commits deveriam ser um só"
git reset --soft HEAD~3
git commit -m "feat: a funcionalidade inteira"

# "quero revisar tudo de novo antes de commitar"
git reset HEAD~1

# "joga tudo fora, volta pro estado do remoto"
git reset --hard origin/main
reset --hard é o comando mais destrutivo do uso diário. Ele sobrescreve os seus arquivos sem perguntar. Alteração não commitada some pra sempre; commit apagado ainda dá pra achar pelo reflog por uns 90 dias. Rode git status antes. Sempre.

Como decidir, em uma pergunta

O commit já foi pro remoto?

   SIM ──▶ git revert     (anda pra frente, ninguém quebra)
   NÃO ──▶ git reset      (mais limpo, e ninguém vai saber)

25cherry-pick e rebase -i

Escolher um commit a dedo, e reescrever uma série inteira antes de mostrar pro mundo.

cherry-pick

Pega um commit específico de qualquer lugar e aplica onde você está. Literalmente colher a cereja.

git switch main
git cherry-pick a1b2c3d              # um commit
git cherry-pick a1b2c3d f4e5d6c      # vários
git cherry-pick a1b2c3d..f4e5d6c     # um intervalo
git cherry-pick -n a1b2c3d           # aplica sem commitar
git cherry-pick -x a1b2c3d           # anota de onde veio na mensagem

Casos em que ele é a ferramenta certa:

  • Hotfix. A correção está numa branch grande que ainda não está pronta — traga só o commit do fix pra main.
  • Commit na branch errada. Colha na branch certa e apague na errada.
  • Backport. Levar a correção da main pra uma branch de versão antiga.
Cherry-pick duplica. O commit ganha um hash novo, e o conteúdo passa a existir em dois lugares. Se depois você mergear as duas branches, o Git costuma resolver sozinho — mas cherry-pick usado como rotina, no lugar de merge, é caminho garantido pra conflito bobo.

rebase -i: reescrever a sua série

O rebase interativo abre um editor com a lista dos últimos commits e deixa você reordenar, juntar, renomear e apagar antes de mostrar o trabalho pra alguém.

git rebase -i HEAD~4       # os 4 últimos
git rebase -i main         # tudo que a sua branch tem a mais que a main
pick a1b2c3d feat: adiciona o filtro
squash f4e5d6c corrige typo
squash 9a8b7c6 agora vai
reword 1122334 feat: adiciona exportação

# pick   = mantém como está
# reword = mantém o código, muda a mensagem
# squash = junta no de cima, JUNTANDO as mensagens
# fixup  = junta no de cima, DESCARTANDO a mensagem
# edit   = para ali pra você mexer no commit
# drop   = apaga o commit

Você edita a primeira palavra de cada linha, salva e fecha. O Git executa o roteiro. Reordenar linhas reordena commits.

Leia de cima pra baixo. Ao contrário do git log, aqui o commit mais antigo fica em cima. E o squash/fixup sempre junta na linha de cima.
git rebase --continue    # resolvi o conflito, siga
git rebase --abort       # cancela tudo, volta ao estado anterior
git rebase --skip        # pula este commit
Regra de ouro, de novo: rebase -i reescreve todos os hashes daquela série. Faça na sua branch, antes do PR ou antes do push. Nunca na main, nunca em branch que outra pessoa já baixou.
O fluxo que vale a pena: commite sujo enquanto trabalha ("wip", "tenta de novo", "agora vai") e limpe tudo com rebase -i antes de abrir o PR. Você fica livre pra commitar de qualquer jeito e o time recebe uma história legível.

Atalho: --fixup + --autosquash

# marca o commit como conserto de outro
git commit --fixup a1b2c3d

# o rebase já posiciona e marca sozinho
git rebase -i --autosquash HEAD~5

26reflog e bisect

O reflog é a rede de segurança que quase ninguém conhece. O bisect é o detetive. Juntos, resolvem os dois piores dias do ano.

git reflog: o diário do HEAD

O Git anota todo lugar por onde o seu HEAD passou — commit, troca de branch, merge, rebase, reset. Esse diário é local, não vai pro remoto, e guarda por volta de 90 dias. É por isso que "commit apagado" quase nunca é apagado de verdade.

git reflog
a1b2c3d HEAD@{0}: reset: moving to HEAD~3 9f8e7d6 HEAD@{1}: commit: feat: adiciona exportação 5c4b3a2 HEAD@{2}: commit: feat: adiciona filtro 1122334 HEAD@{3}: checkout: moving from main to feat/x

Leia de cima (mais recente) pra baixo. O que você quer é o hash da linha imediatamente anterior ao estrago.

Os três resgates

# 1. desfiz um reset --hard e quero voltar
git reflog
git reset --hard 9f8e7d6

# 2. apaguei uma branch que ainda precisava
git reflog
git switch -c feat/x-recuperada 5c4b3a2

# 3. o rebase deu errado e virou salada
git reflog
git reset --hard HEAD@{5}      # o estado antes do rebase
Antes de entrar em pânico, rode git reflog. Se aquilo chegou a ser um commit, está ali. Isso vale pra reset, rebase, amend, merge desastroso e branch apagada. Só não vale pra alteração que nunca foi commitada.
Também tem por branch: git reflog show main mostra só o histórico de movimentação da main. Útil pra descobrir "quando foi que essa branch andou pra trás?".

git bisect: achar o commit que quebrou

Funciona quando ninguém sabe quando quebrou. Você diz um ponto bom e um ruim, e o Git faz busca binária: em vez de testar 1000 commits, você testa 10.

git bisect start
git bisect bad                 # o estado atual está quebrado
git bisect good v1.2.0         # nesta versão funcionava

# o Git te leva pro meio do caminho. Teste e responda:
git bisect good                # funciona aqui
git bisect bad                 # quebrado aqui
# … repita até ele apontar o culpado …

git bisect reset               # volta pra onde você estava
9f8e7d6 is the first bad commit Author: Fulano <fulano@exemplo.com> refactor: simplifica a validação

Bisect automático

Se você tem um comando que responde "funciona ou não" (código de saída 0 = bom), o Git faz tudo sozinho:

git bisect start HEAD v1.2.0
git bisect run npm test
Café e volta. Ele testa, decide, anda, repete, e no fim imprime o commit culpado. É o argumento mais forte a favor de commit pequeno e main sempre verde: bisect só funciona bem quando cada commit do histórico é um estado testável.
No curso: bisect e reflog, com um laboratório de destruir e recuperar, são a aula 11.

  • Leia histórico bom. Abra o git log de um projeto grande e veja como as mensagens e os PRs são escritos.
